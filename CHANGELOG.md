# Changelog

## Unreleased

### Upgrade steps
- **Migrations: stricter checks, and a check after every file.** `hadavin-sdk migrate` (the command that applies the SQL files of `store/migrations/` to the database, in number order, all in one transaction, so a refusal keeps nothing) now works in these steps:
  1. **Before it changes anything** it refuses: a file name that is not exactly four ASCII digits, an underscore, lower-case letters, digits or underscores and `.sql`; a file numbered 0000; a directory or a broken link named like a migration; a file numbered below one that is already applied (it would run late); and a ledger row with no file (the message now tells a renamed file from a database that is newer than the code). The ledger is the table `schema_migrations`, which lists the files already applied.
  2. **A role-membership statement** without `ON` (`GRANT r TO s`, `REVOKE r FROM s`) is refused in a file, even when a name holds `$` and `on` (`app$on`, `on$x`), which PostgreSQL reads as one name. A text scan also refuses `ALTER DEFAULT PRIVILEGES`, `ALTER PUBLICATION`, and a `GRANT` or `REVOKE` of a right on anything but a table, view, sequence, column or function (see "Refused in a file by text" below), and refuses `SET` and `RESET` of any setting, `SET LOCAL lock_timeout` and `SET LOCAL statement_timeout` included (`migrate` sets those two limits itself; a file may not change them).
  3. **Each file is read once** and the text that was checked is the text that runs.
  4. **Released files.** `src/hadavin_sdk/store/migrations_released.json` (shipped inside the package; the one list, the tests read the same file) records the SHA-256 (a fingerprint of the file's text) of every released migration file, and `migrate` refuses, before it connects, a released file that was edited or deleted and a new file numbered at or below the highest released one (`released_problems` in `store/migration_numbers.py`; it hashes the text that will run). A released file must never be edited (add a new file instead). The list names all five files today because there is no release tag yet and the last migration on main is the released base.
  5. **The migration role.** In this file a *role* is a login or a group inside the database, and the *owner* of a table, view, sequence or function is the role that created it (only the owner, or a member of the owner, may change it). The *migration role* is the login `migrate` connects as. `migrate` refuses to run when that role holds one of the powers listed below, or could not change this package's objects:
     - **Refused: powerful flags.** The role is a superuser or holds `CREATEROLE`, `CREATEDB`, `BYPASSRLS` or `REPLICATION` (it reads the five flags of the role right after it takes its lock; a role with `REPLICATION` can read every change made on the whole server). It reads the flags for both the current user and the login (`session_user`: a login that is a superuser and then switches to a plain role is refused, because a file could switch back). Why: a migration file could use those flags to change roles or data outside its schema.
     - **Refused: borrowed rights.** The role is a member of a role that holds one of those flags, or of a built-in server role (`pg_*`, for example `pg_execute_server_program`), for either name (a member could use those rights or switch to that role); the message names the roles and says to `REVOKE` the membership. It also refuses a role that holds a grant on a server setting (`GRANT SET ON PARAMETER ...` or `ALTER SYSTEM`; PostgreSQL 15 and later keep these in `pg_parameter_acl`); this is asked for both names and for every role either belongs to, also a role it belongs to without inheriting its rights, because it could switch to that role.
     - **Refused: `REPLICATION`.** A role that holds `REPLICATION`, or is a member of a role that holds it, is refused like the other four flags, for either name. The printed `CREATE ROLE` and the role the tests create say `NOREPLICATION` in so many words, so a role made from them never has it, whatever the server default. A setup that passed before is refused now: remove the flag (`ALTER ROLE <the migration role> NOREPLICATION`) or use another role.
     - **Refused: rights of the runtime, portal and purge roles beyond the grant map.** On PostgreSQL 17 the right `MAINTAIN` is one more right in the access lists that `verify` reads; there is no version branch for it. The whole suite runs in CI on PostgreSQL 17.10. The portal role is now checked like the other two, by what it can really do: every table right (`REFERENCES` and `TRIGGER` included), rights on one column, rights that come through a group role, `SELECT` on `schema_migrations` and `CREATE` on the schema. Each right is one line that starts with the kind and the name of the object and then names the role, for example `table app.plans: portal_role has DELETE.` or, for a right that comes through a group role, `table app.plans: portal_role can use it through the role grp, SELECT.`; the statement that removes the right follows after `To remove:`. The words of these lines are listed under "Words of the message lines" below, and a test checks that each of them is in the code. This only tightens the check: a setup that passed before is refused now; remove the extra right. These are refused now, each of which a setup may have had before: a table of another application in the schema that the portal role can read; a right given to everyone (`PUBLIC`), for example `CREATE` on the schema through `PUBLIC` or `SELECT` on a table that is not in the portal grant map; any of the five role flags (superuser, `CREATEROLE`, `CREATEDB`, `BYPASSRLS`, `REPLICATION`); owning a table, view or sequence; a right on a foreign table of the schema (a table whose rows live on another server; the check reads tables, views, sequences and foreign tables); any right on a sequence; `SELECT` on `schema_migrations`; and `CREATE` on the schema. ("Portal grant map" is the short list in the code of the tables the portal role may read, and the one right it may have on each.)
     - **Refused: objects owned by another role.** Before the first file, `migrate` refuses a database where another role owns a table, view, sequence or function that this package manages in the migration schema (its own tables, `schema_migrations` and the functions its files create; objects of other applications in the schema are never listed; the usual case is a first build made with a superuser login). The message prints the `ALTER ... OWNER TO` lines for a database administrator (Migration repair steps, case (h)); a procedure, an aggregate and a partitioned table are named as such, every `ALTER` line is printed (not only the first 20 names), objects of an installed extension are not listed, an owner that the role belongs to without inheriting its rights counts as foreign, and a name with a control or unusual character is never copied into a printed line (the message says a person must write that one by hand).
     - **What migrate promises.** `migrate` checks the final state of the database with one check called `verify`: it reads who holds which right, on every schema, from the access lists and the role memberships, and judges them against the grant map. It runs three times: before the first file (nothing is changed yet, "No file ran"), at the end of the run before the commit (a problem refuses the whole run and keeps nothing), and again after the commit on a new connection (a problem is reported, because the files are already committed). "Stopped" means: the run is refused and everything it did is undone, unless a file ended the transaction itself (a hidden COMMIT); that case is reported separately with its own message. "Detected" means: the run reports it loudly, but the change is already in the database and a person must act. "Lasting right" means a right that is still there when the check looks.

       [promise table]
       | Who wrote the file | What `migrate` does | Word |
       |---|---|---|
       | 1. We did, and made an honest mistake | When the file leaves a named role, or everyone, with a right outside the grant map, the run is refused and undone. Catching the same mistake before release, by running the shipped files on an empty database and testing what each role can really do, is NOT BUILT YET (planned for commit 5 of this package); until then the build server runs a smaller test of the same kind. | STOPPED |
       | 2. Someone careless, or a file copied from elsewhere | The same, for lasting rights only. Nothing is promised about lost data, and nothing about code the file leaves behind to run later. | STOPPED, for lasting rights only |
       | 3. Someone who wants to do harm | NOT stopped. Lasting excess rights that exist when the check after the commit runs are reported, with the statements that remove them. Such a file can also cheat the check after the commit, or make it fail to run; a check that cannot run ends in the same loud "applied, not verified" result, never in "applied". | DETECTED, not stopped |
       [end of promise table]

       Why row 3 cannot be better: the file runs as the owner of every table. The real protections against a harmful file are elsewhere: a person reviews every file, each released file's fingerprint is recorded and checked, and a separate read-only login that only checks is a later ticket.

       Not proven yet: until the full test matrix is built (commit 5 of this package), rows 1 and 2 are backed only by unit tests of the rules and a few real-server tests, not by a real-server test of every kind of change, for these kinds: role memberships, handing an object to another owner, default rights, large objects, SECURITY DEFINER functions and a few rarer cases of the ticket. The package must not be called done without that matrix.
     - **What it cannot notice.** A change that a file makes and takes back before it ends; a file that reads data or changes data; code a file leaves behind (in a trigger, a rule, a column default, a view or a function) that runs later, as whoever touches the table next; a right that someone gives again one second after the check; anything a file does outside its transaction (for example through a second connection); what the server reports when the reader itself is cheated (the check after the commit still connects as the migration role); who else can act as owner when the package's tables are owned by a group role (`migrate` does not judge the other members of an owning group); a table in the schema of the run that is not one of the package's tables and that a file hands to a third role (once handed over it is no longer the family's); rights for a role that is neither a named role nor everyone, on an object the migration role owns outside the schema of the run. On objects outside the schema of the run, `migrate` judges what the three named roles and everyone can do, not what other roles can do. A clean run therefore means "no excess right was there when we looked", not "the database is safe from now on".
     - **What is refused, and the baseline.** The kinds of problem are: `flag`, `built_in_role`, `can_act_as_family`, `named_roles_overlap`, `owns`, `right`, `grant_option`, `definer_callable`, `unread_catalog`, `unread_relation_kind`, `foreign_owner`, `other_grantee`, `everyone`, `object_grant_option`, `definer_unreviewed`, `schema_right`, `default_for_named`, `default_for_everyone`, `default_for_other`, `default_unknown_kind` and `missing_schema_usage`. The baseline, in four lines: (1) what everyone holds on the system schemas (`pg_catalog`, `information_schema`) is the server as shipped and is not judged; a right there that names a named role is judged. (2) Where everyone holds nothing by default (table, view, sequence, column, a schema right beyond USAGE, CREATE on the database, large object, foreign server, foreign-data wrapper, tablespace, parameter), any right for a named role, a role it belongs to, or everyone, that the grant map does not give, is refused, in every schema of the database. USAGE on a schema is allowed. (3) Where everyone holds a right by default (EXECUTE on a function, USAGE on a type, a domain or a language): on an object of the migration role family in the schema of the run everyone gets nothing (`migrate` removes the default from the functions its files name; anything else is refused with the REVOKE printed); USAGE on the row type of a table, view, materialized view, partitioned table or foreign table is not refused; a grant that names a named role is refused anywhere. (4) On the database: CONNECT is expected; TEMPORARY for everyone is the server default and is not judged; CREATE on the database is refused. Every built-in `pg_*` role is refused for the three roles, also the harmless ones. A SECURITY DEFINER function of the migration role in another schema that only its owner may call is no longer refused. A SECURITY DEFINER function (it runs with the rights of its owner, the migration role) is judged in three ways. (1) A function of the migration role family in the schema of the run that is SECURITY DEFINER is refused unless its schema, name and argument types are in `REVIEWED_DEFINER_FUNCTIONS` in `store/migrate.py` (empty today; changed only by a reviewed code change), whoever may call it. (2) If everyone may call it, it is also refused unless it is on that list. (3) Any EXECUTE right of a named role on any function is refused as a plain right, listed or not, because the grant map gives no function rights. The check does not read a function's body or its `search_path` setting; the person who adds a function to the list reviews those. The owner of such a function must be a role of the migration role family.
     - **The three calls, the statements and the exit codes.** Exit 2: refused, nothing kept. Exit 5: the files are applied and committed, but the check after the commit found excess rights (or could not run, or the commit's outcome is unknown): the message says so in its first sentence, and the statements that remove the rights are printed on standard output, one per line, so `hadavin-sdk migrate ... > fix.sql` captures them; `migrate` does not run them itself. Statements for objects that are not this package's (another schema, or another owner) are printed in a second block marked NOT THIS PACKAGE'S OBJECTS; confirm each with the object's owner before running it. Before the commit the eight reads may each see the database at a slightly different moment; the check after the commit reads one consistent picture. A saved `statement_timeout` or `lock_timeout` of the migration role cannot stop the check; on PostgreSQL 17 and later a saved `transaction_timeout` can, and then `migrate` says the check could not run. After the commit that is exit 5. Before the commit `migrate` refuses with exit 2 and keeps nothing, as it does for any other driver error that the check raises (for example a lost connection); it never prints a raw driver error as a crash (exit 3) for the check and never says "applied".
     - **Words of the message lines.** (A test reads this block: every fixed piece must occur in `store/migration_verify.py`, and the three forms must be what `Problem.line()` writes.)

       [message words]
       has {right}
       can use it through the role {via}, {right}
       To remove: {statement}
       [end of message words]
     - **An object that belongs to an extension** (for example the view `pg_stat_statements`, which everyone may read) is refused like any other object, with no statement printed: a REVOKE would come back with the next extension update. Such a database needs a decision by its administrator, for example a database of its own for this package, or the extension installed in another schema. The refusal text says so.
     - **Upgrade note.** A setup with rights beyond the grant map is now refused before any file runs. Earlier versions only refused rights that changed during the run, so a database that passed before can be refused now. `migrate` prints one line per right and, on standard output, the statements that remove them. A database administrator runs those statements (they are REVOKE statements and membership removals; none of them changes data), then runs `migrate` again. Typical cases: a table of another application that everyone may read; a login used as runtime role that is also a member of a group; a function in the same schema, owned by the migration role, that everyone may call; a default right set long ago with `ALTER DEFAULT PRIVILEGES`. Two things `migrate` repairs by itself and does not refuse: rights the migration role itself gave the named roles on the package's own tables (they are reset to the grant map as before), and the right of everyone to call the package's own functions (removed as before). In a shared database, the check covers the whole database: any table of another application that everyone may read is refused, whatever schema it is in. If such an object belongs to another application that needs the right as it is, do not remove it: give this package a database of its own, or roles that no other application uses. A schema of its own is not enough. The schema of the run may be owned by a database administrator when the migration role may create in it (the setup the refusal message prints); only a change of its owner during the run is refused.
     - **Refused in a file by text: rights anywhere but on a table, view, sequence, column or function, and any change of owner.** `GRANT` and `REVOKE` of a right on a schema, a database, a type, a domain, a language, a large object, a foreign server, a tablespace, a parameter, a procedure or `ALL ... IN SCHEMA`, `ALTER DEFAULT PRIVILEGES` and `ALTER PUBLICATION` are refused by the text scan before the file runs. A right there is a reviewed exception to be made by a database administrator, not by a migration file. `ALTER <anything> OWNER TO <role>` is refused the same way: no file of this package hands an object to another role (the one statement with the words `owner to` that passes is the rename of a column, an attribute or a constraint that is called `owner`, for example `ALTER TABLE t RENAME COLUMN owner TO owner_name`). These text rules refuse common accidents early with a plain message. They are not the guard; dynamic SQL passes them, and `verify` judges what is in the database afterwards.
     - **What to do when it is a table or a function of another application.** If a listed table really belongs to another application and only shares a name with one of ours (for example `spend` or `runs`), do not hand it over: point `migrate` at another schema, because the changes would fail with "must be owner" and the grants would silently do nothing. The same holds for a function: functions are matched by name only (not by argument types), so read the text of each listed function first, and hand it over only if it is this package's own code. A function made `SECURITY DEFINER` runs with the rights of its owner, so handing it over to the migration role also hands over everything that function can do with those rights.
     - **What to do when you only have a superuser login** (a demo database, or the administrator account of a managed database): create a separate plain migration role once and run `migrate` as that role. The refusal message prints the SQL, for example `CREATE ROLE migration_role LOGIN NOSUPERUSER NOCREATEROLE NOCREATEDB NOBYPASSRLS NOREPLICATION; GRANT CREATE ON SCHEMA <schema> TO migration_role; GRANT USAGE ON SCHEMA <schema> TO migration_role WITH GRANT OPTION;` (CREATE has no grant option, so the role cannot hand out the right to create objects; the grant option on USAGE lets that role pass USAGE on to the runtime and portal roles; after the grants `migrate` checks that each named role can use the schema and refuses if not; add the login method that fits your database; no password is written here). There is no switch, argument or setting that turns the refusals off.
  6. **The advisory lock and the time limits.**
     - **The advisory lock.** An advisory lock is a lock that the database offers to programs under a number of their choice. `migrate` takes one number, the same for every `migrate`, so two runs started together wait for each other and each file is applied once.
     - **How long it waits.** Any role that may connect can take a lock number and never let go, so `migrate` waits for the lock at most `lock_wait_seconds` (default `MIGRATE_LOCK_WAIT_SECONDS`, 600 seconds, in `migration_numbers`). Then it stops, changes nothing and says which session holds the lock (the user, the process number, the application name, the state and the time it connected; a detail that the server hides from this login is printed as "not visible to this login"), or, when a prepared transaction holds the lock (a transaction that a session set aside with `PREPARE TRANSACTION`; it keeps its locks and has no session), says that, lists the oldest prepared transactions of the database and names the two statements that finish one (`ROLLBACK PREPARED`, `COMMIT PREPARED`); when the server shows no holder at all, it says "a session this login cannot see". A long migration on a big table may need a larger value: `--lock-wait-seconds <seconds>` on the command line or `lock_wait_seconds` in code, from 1 to 2147483 (the most that the server accepts; a value above it is refused with a plain message before anything runs).
     - **The time limits.** `migrate` also sets, for its transaction, the same lock-wait and statement time limits as the hand recipe (the numbers are in the paragraph "Rule for every hand step" of the Migration repair steps at the end of this file; one constant in the code, `RECIPE_TIMEOUTS`, so the code and the recipe cannot differ). They start right after `migrate` takes its advisory lock and cover the rest of the run: every file, and also the role checks and grants, so a normal run with no new file is covered too: a `GRANT` that waits for a busy table longer than the lock limit stops the run. The statement limit is for each statement (a file with several statements is not timed as a whole; seen on PostgreSQL 16.15).
     - **When a limit is reached.** The run stops (it is recognised by the error code, not by the words of the server message, which follow the server language: 57014 for the statement limit, and 55P03 for the lock limit; a statement cancelled by another session has the code 57014 and is reported the same way), keeps nothing and prints a plain message that names the step and the setting. The wait for the migration lock has the lock limit only: a statement limit saved for the migration role (`ALTER ROLE ... SET statement_timeout`) is switched off for that one wait, so it cannot end the wait early and make the message blame the wrong limit. Run `migrate` again when nothing holds the table, and apply a file that really needs longer by hand.
  7. **The read-back after every file.** Reading the same facts again after the file ran and comparing them with what they were before the first file. It runs in the same transaction.
     - **What it reads.** The database user names, the replication-role setting, the search path, three settings that change how SQL text is read, the two time limits, the transaction clock and the transaction id (a hidden `COMMIT` starts a new transaction, so these two change), the role memberships and the settings saved per role. The memberships and saved settings are read only for the roles that matter here: the migration login and current user, the roles `migrate` was told to grant to, and every role the two users or those named roles are a member of. A membership row counts when its member is one of those, or when the role is the migration user or a named role. `pg_auth_members` is the table in which the database keeps who is a member of which role; a *grant option* on a membership means the member may pass that role on to others.
     - **What happens on a change.** The run is refused with "a role membership changed while the file ran (it may be another session; run migrate again)". A membership is shown in words: with or without the grant option, whether the member uses the rights at once, whether it may switch to the role. A saved setting is shown as "in every database" or "in database X". No raw data is shown. A second session changing unrelated roles at the same moment does not stop the run.
     - **The checks of item 5 run again.** After each file the checks of item 5 are asked again (flags, borrowed roles, parameter grants, named roles that belong to each other), so a role granted or changed by a file and used later is found at once. If any of them was left changed, the whole run is refused.
     - **What it cannot do.** It detects a change after the file; it cannot undo anything a hidden `COMMIT` or a second connection (`dblink_exec` runs outside the transaction) already kept. A role granted to a role inside a function body that a file then calls is found by this read-back and by the repeated checks, not by the statement rule above.
  8. **Triggers.** The read-back also reads every trigger in the migration schema: its enabled state, its definition, and for its function the text, the security mode, the owner and the saved settings. A trigger that existed before the file must come out exactly as it went in: a changed definition, a replaced function body, a changed owner, any change of the enabled state of an existing trigger (including "always" to "origin only") and a renamed table all refuse the run, and the message names the trigger and what changed (it does not call this a changed session). The one way to allow such a change is a reviewed entry in `src/hadavin_sdk/store/migrations_trigger_changes.json` (shipped inside the package, next to the released-files list): the migration file name without `.sql`, the schema (optional; without it the entry fits the migration schema in use), the table, the trigger name and a one-line reason. The list is empty today. An entry allows a change of that one trigger on that one table by that file only, never a trigger that disappears, and an existing trigger left disabled (`D`) or replica-only (`R`) is refused unless the entry names that state in `enabled_state` (that key applies to an existing trigger only; a trigger a file creates is not checked by this list). The planned audit change that uses `CREATE OR REPLACE TRIGGER` gets its own entry when it lands.
  9. **What this change does not yet check.** The check that a new migration only adds columns and never removes or retypes one (the column-safety check) is not in force until the next change merges. Until then the only column check is the test `test_the_previous_release_columns_survive_the_newest_migrations`, which reads the old columns after the newest migrations ran. No release tag and no client deploy happen between the two changes.
  10. **A late file** is applied by hand by a database administrator: the refusal message prints the recipe (a file of SQL run with `psql -X -v ON_ERROR_STOP=1 -f`); see the Migration repair steps at the end of this file.
  11. **Tested on:** PostgreSQL 16.15, on the build machine. PostgreSQL 16 is the lowest version `migrate` runs on; an older server is refused with a plain message before anything is read or changed (the role checks read `pg_auth_members` columns that 16 added). PostgreSQL 17.10 runs the whole suite in CI; PostgreSQL 18 has not been run. The read of role memberships takes every column of `pg_auth_members` as JSON (minus the row id and the two name columns), because the columns differ between PostgreSQL versions (16 added `inherit_option`, `set_option` and a row id).
- **Breaking: the first stage is now called `demo`; `environment: dev` is refused.** The stages are exactly `demo`, `pilot` and `prod`. A config that says `environment: dev` stops at start with "environment: dev was renamed to demo; write environment: demo (allowed values: demo, pilot, prod)" (shown beside any other problem found in the same file, and also for `Dev`, `DEV` and spellings with spaces, which are refused all the same); any other value (`Demo`, `staging`, `uat`, an empty value) is refused too, and values are never tidied or guessed. To upgrade: (1) change `environment:` in your config to `demo`; (2) if your code imports `backends.table.DEV_ONLY`, import `DEMO_ONLY` instead (same six kind pairs, no old name kept); (3) a project label such as `uat` is not a stage: map it to one stage in your own config. Also: the pilot and prod checks (`deferred.py`, `registry.py`, `app.py`) now ask one function, `hadavin_sdk.stages.is_live(environment)`, which treats anything that is not exactly `demo` as live; the prod-only rules (no local key file, a retention-agreed anchor) ask `hadavin_sdk.stages.is_prod(environment)`, which is true for `prod` and for any value that is not a stage. `STAGES`, `is_live` and `is_prod` live in the new leaf module `hadavin_sdk/stages.py`, not in `config.py`; the list `deferred.LIVE` is removed. The redactor no longer sweeps the words `demo` and `pilot` as a name (it already skipped `prod`), but a secret that reads `demo` is still swept. No stage is stored today; the first change that stores one must map an old `dev` value to `demo` on read, for display only and never for a guard decision, and add a test through that real read site.
- **Code-quality scanner fixes (SonarCloud, an automated code-quality scanner); one public name removed.** `guard.runmap.PARTIAL_ESCAPE` is gone. If your code imports it, call `guard.runmap.partial_escape_start(text, pos)` instead; it returns the start position as a number (or None), not a match object, so replace a `.search(...)` call and its `.start()` with it. The old pattern looked for a cut-off percent code such as `%C3` at the end of a text and slowed down sharply on a long run of them (about 65 s for 40,000 codes in a row, measured 2026-11-06); the new function takes milliseconds. `guard/http.py` now holds the cloud-metadata addresses that no tool may reach as one documented table `METADATA_ENDPOINTS` (the same six addresses as before; the other refused ranges are unchanged).
- **Redaction behaviour you may notice.** The producers of text that reaches a model, a vendor screen, a card or a log line (listed in `guard/producers.py`, each tested by `tests/test_k5_round9.py` with a percent-, entity- and assignment-encoded secret) go through one function, `guard.runmap.redact_text`, which also undoes percent, HTML-entity, backslash-u, `\u{41}`, `%u0041`, backslash-x, backslash-U (eight digits) and three-digit octal escapes (not one- and two-digit octal or named escapes: `\1` and Windows paths would decode wrongly) and NFKC to a fixed point before it redacts: a secret written as `%41KIA...`, `&#65;KIA...` or `password%3Dx` is masked in those places, not only in tool results. Not on that list: the text of the ask-your-data demo's own ledger and command line (see its README). A text nested deeper than `defaults.SCRUB_MAX_LAYERS` (8) layers is not shown. A tool result is redacted whole up to 262,144 characters before it is cut; when it IS cut (at that cap, or again after a short handed-out secret was replaced by the longer marker), the last 8,192 characters of the result are dropped so a token that straddles the cut leaves no fragment (`defaults.CUT_MARGIN`; a PEM key is about 1.7 KB for RSA-2048, 3.2 KB for RSA-4096 and 6.4 KB for RSA-8192). Cost: redacting a hostile text at the cap takes one to four seconds on a laptop (one pass per distinct view); a call that has spent `defaults.REDACT_BUDGET_S` (6 s) before a further view is refused (`InputTooLarge`, nothing shown), and the perf step bounds it. A card text is sanitised and has commands withheld first and is redacted once, last (and once more with tags deleted, real placeholders and line breaks kept, when markup split a key from its value; that view is used only when it finds a secret value the text pass did not). A card summary is shown whole or replaced by a short note (never cut); a summary whose inputs are too large to redact says so. In a case bundle, camelCase credential keys (`clientSecret`, `dbPassword`), numbers and nested values under a credential key are masked too. The Kubernetes source defaults (`K8S_*`) stay in `defaults.py`, under their own header, with every other default.

- **The scrub of a tool result.** The limits below are pinned by tests in `tests/test_k5_fixes5.py` to `test_k5_fixes9.py` and `tests/test_k5_layers.py`; the two figures on the end of a cut text (the proportion that loses a group) are estimates from a run, not pinned.
  - **Size.** Scrubbing grows a short secret (6 characters become the 17-character `<SECRET_REDACTED>`), so a result far below the 262,144-character cap could pass it and was refused (`InputTooLarge`; 15,421 copies of a 6-character secret was the smallest case). The grown text is now cut back to the cap with the `[truncated]` marker. `max_bytes` of a tool and `legacy_max_output_bytes` may be at most 262,144. Two refusals remain, both `InputTooLarge` and a `redaction_error` abstention: a decoded view of the result that would pass the cap, and a text that the escaping of result markers and placeholder look-alikes (the neutralise step of `redact_untrusted`) grows past the cap (it needs look-alike characters within a few times of the cap).
  - **Cuts.** A cut can split a handed-out secret (the raw-size cut, the window cut, the cut after a replace inside the scrub), and then no whole spelling is left to mask. After EVERY such cut, and before any swap of the text for its decoded view, the scrub removes: a half-written escape at the end (`\u005`, `&#9`, `%C3`, half of a surrogate pair); the longest stretch before the marker that reads (layers and NFKC undone) as the start of a spelling of any handed-out secret (a compatibility-character spelling can need more than one character to read as a start) (hex in any case); and the front of a base64 token that wraps a secret (standard or URL-safe alphabet, token of 8 characters or more, cut back to the 4-character group that holds the first byte). A reply loses the last few characters to this; ordinary text at the very end can lose a trailing `&T`, a `%C3%A9`, or (about 3 in 100, when the tail looks like base64) its last group. The look-back is at most `evidence.scrub.fragment_scan` (4,096) start positions with one decode each.
  - **Exception messages.** The message of a tool's exception is scrubbed in full BEFORE it is cut to 160 characters (200 for a refusal), so the cut cannot leave the front of a secret.
  - **What the scrub undoes.** A handed-out secret (6 characters or more) is found as it is, URL-quoted, hex (any case), base64 and base32 (base64 also two or three times), and behind JSON string escapes (`\uXXXX` with surrogate pairs joined, `\/`, `\"`, `\\`, `\n`, `\t`; PHP writes every slash as `\/`), percent-encoding (twice), HTML entities, NFKC compatibility characters (full-width, mathematical, circled, superscript) and invisible characters. The layers are undone to a fixed point, at most 8 rounds (`defaults.SCRUB_MAX_LAYERS`; deeper is cut or replaced, see the next entry), so they may nest either way (`&#37;41`, a double-escaped entity). The redactor's second pass (`guard/runmap.py`) joins surrogate pairs and reads `\/` too.
  - **What it does not undo.** Hex of a percent-encoded value, ROT13 or any substitution cipher, reversed text, a character separator (`V-h-5`), one- and two-digit octal escapes, named escapes, a base32 token that wraps a secret, a base64 token shorter than 8 characters (`tools.B64_MIN_TOKEN`, the one bound), and any layer not listed: the text stays as it came and a cut inside such a spelling leaves its first characters next to the marker. This is a limit, not a guarantee: the control is that a tool is not handed a secret it does not need (least privilege). `tests/test_k5_fixes7.py` pins the unhandled layers so a change is seen.
  - **Settings.** The thresholds are validated configuration under `evidence.scrub` (`tail_window` 256, `min_redaction_window` 4096, `min_secret` 6, `fragment_scan` 4096, `fragment_min` 1, `partial_end` 10; ranges in `config.ScrubSettings`), one set of defaults in `hadavin_sdk/defaults.py`.
- **Layered encodings.** Every tool result, whether or not a secret was handed out, also gets a decode-to-fixed-point view (percent, entity, backslash escapes, NFKC) that is redacted too, so a pattern-shaped secret (`%41KIA...`, `password%3Dx`) is found; a text nested deeper than the cap is not shown. The scrub undoes any ordered stack of percent, HTML entity (decimal and hex), backslash-u, backslash-slash and NFKC full-width layers, and a base64 token front, to a fixed point: each round applies NFKC, JSON escapes, percent-decoding and entity-decoding ONE AT A TIME (a combined step turned the half entity `&#10`, which percent-decoding had just exposed, into a newline, so `percent(entity(secret))` cut inside the token left its front: 7 of 451 cut points). A half-written escape at the end is dropped before every decoder. The depth is capped at `defaults.SCRUB_MAX_LAYERS` (8); a text that still changes after the cap is not shown (the tail is cut back to its start; a whole result becomes `<SECRET_REDACTED>` + `[truncated]`): fail closed. Our own design (not a quoted standard): CWE-174 (double decoding) warns that decoding twice lets values past a check and says to reject non-conforming input; OWASP Input Validation Cheat Sheet says to decode before checking and to cap parser nesting depth (both pages fetched 2026-11-03); neither describes decoding to a fixed point, which is what finding a secret in any spelling needs. `error_reason` and every tool result go through the same `_scrub`. Pinned by `tests/test_k5_layers.py` (seeded fuzz of 20,000 orderings and depths at the default and a small window, the recorded failing cut points, a sensitivity control, a perf-marked 100 KB timing test).

### Tests
- **The role the migration tests use, and how a stale one is cleaned up.** Every test that is not about the refusals above runs `migrate` as a plain role; the tests that prove a refusal connect as the superuser on purpose.
  - **The role.** It has a random name starting with `hadavin_test_migrator_`, is looked up before it is created, and is created once with a password hash (never a clear password, so none reaches the server log). Every login role that a test makes and then logs in as gets a hash the same way, including the role made from the SQL the refusal message prints (the test sets its password after running that SQL). Each such test passes the password through `login_dsn` or a `password=` argument of `make_conninfo`; a guard test fails when a test calls `make_conninfo` or `connect` with `user=` and no password. The guard reads Python calls only: a connection string written as text is not seen, and a line marked `# pw-env` is skipped (the password then travels in the environment).
  - **Why a test run keeps a connection open.** So that another test run on the same database server can see that this run is still using its role and does not drop it. The connection is called the mark.
  - **How the mark works.** A role belongs to the whole database server, but an advisory lock belongs to one database. So the mark is one connection per database that is named after the role (`application_name`, which every database of the server can see) and also holds an advisory lock. If the connection dies it is opened again at the next connect. A later run drops a stale test role only when no connection on the server uses or is named like it, its lock is free, it owns nothing outside the test schemas of the current database (a *test schema* is a schema whose name starts with `hadavin_test_`; the check covers schemas, tables, views, sequences, functions and types), and the login can see the sessions of other users (a superuser or a member of `pg_read_all_stats`; otherwise it sweeps nothing and says so in one line). A role that owns objects in another database cannot be dropped from here; the one-line message names those databases.
  - **When the test process ends.** On a normal exit it drops what the role owns in every database it used, then the role itself, once. A killed process runs no exit step; the next run's sweep takes care of it.

### Migration repair steps

For a database administrator when `hadavin-sdk migrate` refuses a database or a folder of migration files. The runtime code never calls `migrate` (in `src/` only the `migrate` command in `cli.py` does), so a refused `migrate` does not stop a service that is already running; a deployment that runs `migrate` as an init step would stop (not checked for any real deployment). This change adds no migration and changes no stored data, so reverting it needs no database step; after a revert the refusals below vanish silently.

**Rule for every hand step.** A hand step is a FILE of SQL run with `psql -X -v ON_ERROR_STOP=1 -f <file>` and your own connection settings (a `PGSERVICE` entry or the usual `PG*` variables): never typed line by line, never an include command, and no connection string in any text. (`-X` keeps `psql` from reading a startup file that could switch the stop at the first error off.) The file starts with the line `\set ON_ERROR_STOP on`, then `SET search_path TO "<the schema migrate uses>";` (in double quotes, as the recipe prints it; read the name with `SELECT current_schema()` over your usual connection; the refusal message prints it), then `BEGIN;`, then `SET LOCAL lock_timeout = '5s';` and `SET LOCAL statement_timeout = '60s';` (an `ALTER TABLE` on a live table needs a lock that stops every reader while it waits: a lock not had within the first limit, or a statement over the second, stops the file and keeps nothing; raise a number only with a reviewer, for a reason you write in the change log; `migrate` sets the same two lines itself, from the same constant in the code, `RECIPE_TIMEOUTS`), then `SELECT pg_advisory_xact_lock(3760701656253510835);` (the lock every `migrate` run takes: do this only while no `migrate` runs), and ends with `COMMIT;`. After every `UPDATE schema_migrations` the file holds a `DO` check that raises unless exactly one row with the new version exists and none with the old one (an `UPDATE` that matches no row succeeds silently); the error stops the script and nothing is kept:

```sql
DO $$ BEGIN
  IF (SELECT count(*) FROM schema_migrations WHERE version = '<NEW>') <> 1
     OR (SELECT count(*) FROM schema_migrations WHERE version = '<OLD>') <> 0 THEN
    RAISE EXCEPTION 'the ledger row was not renamed';
  END IF;
END $$;
```

- **(a) A late file** (a new file numbered at or below a number the database has already applied; or a hotfix that needs an out-of-order number). Do not rename the file. Objects made by another role are owned by it, so the file must run as the migration role: after the `BEGIN;` line of the recipe add this check, with the name of the migration role in place of `<MIGRATION ROLE>` (it stops the file and keeps nothing when you are connected as someone else):

```sql
DO $$ BEGIN
  IF current_user <> '<MIGRATION ROLE>' THEN
    RAISE EXCEPTION 'this file must be run by the migration role';
  END IF;
END $$;
```

  Then follow the recipe in the refusal message (save the lines between the two RECIPE lines to a file and run it as above), then run `hadavin-sdk migrate` with the usual role options (that applies the grants again). Running the same recipe twice is safe: the second run fails, and keeps nothing (the file's own SQL stops it, or at the latest the ledger row, whose version is a primary key). If the refusal message prints no recipe and says "A person must write the steps by hand" (an unusual schema name, or a file that holds a backslash, a colon followed by a name, the words RECIPE begins or RECIPE ends, or a hidden or control character), the administrator, with a reviewer, writes the hand file: the header of the rule above, then for each late file in number order its whole SQL text (checked line by line for what `psql` would read as a command or a variable) followed by `INSERT INTO schema_migrations (version) VALUES ('<file name without .sql>');`, then `COMMIT;`, and runs it as above. Write the date, the files and your name in the change log.
- **(b) A renamed file, or a ledger row that was renamed.** Find the file in the folder whose name after the number is the same as the row's. Then `UPDATE schema_migrations SET version = '<file_stem>' WHERE version = '<wrong name>';` (`<file_stem>` is that file's name without `.sql`) followed by its `DO` check. The step trusts the name only: it does not compare the text the old row ran with the file. For a released file the proof is the list `src/hadavin_sdk/store/migrations_released.json` (the SHA-256 of each released file, checked by `migrate` and the tests): confirm that the folder file is listed there. The new name is the name of the one folder file that has the same text after the number as the old row; the evidence row, if it was given another number (a database that followed the older note and holds a row numbered 0006 with the name `evidence` is exactly this), goes back to `0005_evidence`. For the evidence row, put the block of case (g) (the evidence tables check) into the same file right after the `DO` check: it stops the file, and nothing is kept, if `tool_calls` or `redaction_maps` is missing (a scratch database whose data you can lose: see case (e); otherwise a person must look), and it adds a missing `tool_calls.error` before the file commits. Without that block the rename would accept a broken table for good.
- **(c) A collision between a release branch and main** (two files with one number): renumber the file that is NOT listed in `src/hadavin_sdk/store/migrations_released.json`. A released file (one listed there) can never be renumbered, renamed or edited: its recorded hash and name are checked, and `migrate` and the tests refuse the change. If the unreleased file is the one some database has already applied, renumber it anyway and change those databases' ledger rows to its new name with case (b). If both files are listed there, stop: a person must look.
- **(d) A database NEWER than the code** (the code was reverted after a newer migration ran): the refusal says so. Do not rename, drop or edit the ledger; run the newer release, or run the older image without `migrate`.
- **(e) A database built from a branch** (a ledger row `0005_measure` or `0005_reservations`, and possibly the evidence row under a number other than `0005`). `migrate` refuses it, because this folder has no file for those names. Until the renamed files exist in a release, keep the database, do NOT run this release's `migrate` on it, and run the code of the branch that built it. A scratch database whose data you can lose is dropped as a whole and `migrate` runs on an empty one: this is the only place a drop is advised. After the renamed file exists (the name of the folder file with the same text after the number as the branch row), make one complete hand file: the header above, then for each branch row `UPDATE schema_migrations SET version = '<NEW>' WHERE version = '<OLD>';` with its `DO` check. For the evidence migration choose ONE variant after running `SELECT to_regclass('tool_calls'), to_regclass('redaction_maps');` over your usual connection: **E1** the evidence row was given another number and both tables exist: `UPDATE schema_migrations SET version = '0005_evidence' WHERE version = '<the wrong name>';` with its check; **E2** no evidence row and neither table exists: paste the whole text of `0005_evidence.sql` in this place, then `INSERT INTO schema_migrations (version) VALUES ('0005_evidence');` (the pasted file makes the two tables, so run this hand file connected as the migration role and put the check of case (a) right after the `BEGIN;` line: tables made by another login are refused by `migrate`, case (h)); **E3** no evidence row but both tables exist (made by hand): only that `INSERT`. If only one table exists, stop: a person must look. In **E1** and **E3** always put the block of case (g) into the file before `COMMIT;`: the tables exist and nothing else has looked at their columns, and the block stops the file if a table is missing or differs, and adds a missing `tool_calls.error` (an early version of the migration). **E2** does not need it (the pasted file makes the tables). Then `COMMIT;` and run `hadavin-sdk migrate` with the usual role options. Once a branch row is renamed to a number above 5, `0005_evidence` is below the highest applied number, which is why E2 applies it by hand and E1 and E3 only fix its row. Variants E1, E2 and E3 (with and without a missing `tool_calls.error`) are run by `tests/test_migration_postgres.py` on made-up tables with a made-up branch row; nothing has run them on a real database.
- **(f) Statements that cannot run in a transaction** (such as an online index build): a migration with one fails the run and rolls everything back (and fails CI on the real folder). An administrator creates the index outside `migrate`, and a later migration uses `CREATE INDEX IF NOT EXISTS`. `migrate` sets the same lock and statement limits as the hand file (the two `SET LOCAL` lines of the rule above) for the whole run, role grants included: a file that waits too long for a table lock, or runs too long, fails the whole run and keeps nothing, with a plain message. The order differs on purpose: the hand file sets the limits before the advisory lock, `migrate` after it (a second `migrate` started at the same time waits for the first without a limit; that is how two runs apply a file once). A migration file may not change either limit: the read-back after the file refuses the run if `lock_timeout` or `statement_timeout` differs from the value `migrate` set. A file that really needs longer is applied by hand (a hand file with a raised number, the rule above) and the ledger row goes in with it; run migrations in a quiet window all the same.
- **(g) An early evidence migration** (the ledger row is `0005_evidence`, or a row numbered 0006 with the name `evidence` before case (b) is done, but the table `tool_calls` has no column `error`, because the database was built by an early version of `0005_evidence.sql`). `migrate` does not compare table structure with the ledger: it sees the row, does nothing and does not refuse, and the service then fails on every tool-call write. **Check** (read only; any role that can read the schema; run it with the same `search_path` as `migrate`): `SELECT column_name FROM information_schema.columns WHERE table_schema = current_schema() AND table_name = 'tool_calls' AND column_name = 'error';`. One row: nothing to repair. No row: repair. **Who:** a database administrator connected as the migration role (the owner of the tables; `ALTER TABLE` needs the owner; never the runtime role or the purge role), after a snapshot, while no `migrate` runs. **What changes:** only the table `tool_calls` gets one column, `error`, and every row already there gets `FALSE` (an early version stored no failure flag, so earlier failed calls cannot be told apart afterwards). The tables `redaction_maps` and `schema_migrations` are only read; no ledger row changes. Nothing is dropped. **How:** one hand file made by the rule above (the header, this block, `COMMIT;`):

```sql
DO $$ BEGIN
  IF to_regclass('tool_calls') IS NULL OR to_regclass('redaction_maps') IS NULL THEN
    RAISE EXCEPTION 'tool_calls or redaction_maps is missing: stop, a person must look';
  END IF;
END $$;
ALTER TABLE tool_calls ADD COLUMN IF NOT EXISTS error BOOLEAN NOT NULL DEFAULT FALSE;
DO $$ BEGIN
  IF (SELECT string_agg(column_name::text || ' ' || data_type || ' ' || is_nullable, ', ' ORDER BY column_name::text COLLATE "C")
        FROM information_schema.columns WHERE table_schema = current_schema() AND table_name = 'tool_calls')
     IS DISTINCT FROM 'attempt integer YES, call_id text NO, created_at timestamp with time zone NO, duration_ms integer YES, error boolean NO, inputs jsonb NO, output text NO, output_sha256 text NO, run_id text NO, tool text NO'
  OR (SELECT string_agg(column_name::text || ' ' || data_type || ' ' || is_nullable, ', ' ORDER BY column_name::text COLLATE "C")
        FROM information_schema.columns WHERE table_schema = current_schema() AND table_name = 'redaction_maps')
     IS DISTINCT FROM 'mapping jsonb NO, run_id text NO, updated_at timestamp with time zone NO' THEN
    RAISE EXCEPTION 'the columns of the evidence tables differ from 0005_evidence.sql in more than the error column: stop, a person must look';
  END IF;
END $$;
```

The last check compares columns only (name, type, nullable); it does not look at the primary keys or at the index `tool_calls_by_run`, so after the file a person compares those with `0005_evidence.sql` (`\d tool_calls` and `\d redaction_maps` in `psql`). If the block raises, the whole file is undone and nothing is kept (a table missing, or a column other than `error` differs: a person must look; a scratch database whose data you can lose is handled by case (e)). Running the file twice is safe. **Verify:** `psql` ends without an error; the check query above now returns one row; run `hadavin-sdk migrate` with the usual role options (it applies the grants again and lists nothing applied); then start the service and make one tool call.


- **(h) Objects owned by another role** (the first build was made with a superuser login, or by another administrator login, and `migrate` now runs as a plain migration role). `migrate` refuses before it changes anything and says "cannot change N object(s) of this package in schema ... that another role owns", naming each object with its owner. Only objects this package manages are listed: its own tables and functions (`schema_migrations` and the names in the grant map) and the functions the migration files create. Another application's tables in the same schema never cause a refusal and are never listed. Types and domains are not listed, because a migration file cannot create them. Why: PostgreSQL lets only the owner (or a member of the owner role) alter a table or replace a function, so a later `ALTER TABLE` would fail with "must be owner of table", and the `GRANT` and `REVOKE` lines of `migrate` would do nothing and print no error. **Who:** a database administrator connected as a superuser, or as a role that is a member of both the old owner and the migration role, after a snapshot, while no `migrate` runs. **What changes:** only the owner of the listed objects, to the migration role; no row, column or grant is changed by this step itself (`migrate` applies the grants again afterwards). **How:** one hand file made by the rule above: the header, then the `ALTER ... OWNER TO "<migration role>";` lines exactly as the refusal prints them (one line for each object; a sequence that belongs to a table column moves with its table and is not listed), then `COMMIT;`. `REASSIGN OWNED BY <old owner> TO <migration role>;` would also move other applications' objects in this schema and everything the old owner owns in the other schemas; use it only after you have read what that owner owns, and only if the old owner is this package's own first-build login. If a listed table belongs to another application and only shares a name with one of this package's tables (for example `spend` or `runs`), do not hand it over: point `migrate` at another schema (the `search_path` of the connection) for this package. **Verify:** `hadavin-sdk migrate` no longer refuses (a second run lists nothing applied). Objects that belong to an installed extension are not listed and not touched. The same refusal also shows when you create the plain migration role by the SQL in the refusal message of a superuser login and forget this step.
