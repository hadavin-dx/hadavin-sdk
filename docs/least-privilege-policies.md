# Least-privilege policies per backend kind

Generated by `python tools/policy_page.py --write` from the `POLICY` literal in each kind module. Do not edit by
hand: a test regenerates this page and fails when it differs.

A "kind" is one backend choice (for example `vault`). For each kind below the page lists the permissions its
code needs (one reason each), the requests that need no permission, and what the identity must never be given.

## What the tests show, and what they do not

- Three backend kinds ship a declared permission set tied to the calls their code makes: `vault` (secrets),
  `vault_transit` (signer) and `kubernetes` (source). A test reads each module and fails when a request written
  there by the listed call shapes is not declared, or when a declared request is no longer made.
- The two Vault kinds are also refused by a real Vault server, in CI only: the generated policy text is the only
  thing the test token holds, and the requests on the never-list are refused. Kubernetes is checked against the
  code's own read-only rule, not against a cluster.
- The call check is name-based. It sees requests written in the kind module in these shapes: `.call(...)`,
  `.authed(...)` and the Transit signer's `._call(...)` for Vault; `._fetch`, `._call`, `._get` and `._items`
  with a constant operation id for Kubernetes. It does not see a client object handed to another module.
- No test shows that a permission NAME is right. That comes from a separate check of the vendor's own
  documentation sources on the date shown per row (`tests/fixtures/policy_sources_2026-11-11.txt` lists them).
  The rendered vendor pages were not reachable; the documentation source files they are built from were read.
- No policy on this page has been confirmed on a real account or a real cluster ("accepted by a real account"
  says `no` everywhere).
- One process uses one identity. Give that identity the text of every kind the process runs.
- The Transit signer signs a test message at start-up, and verifying the audit trail builds the signer, so a
  process that only verifies still needs the signing permission today.

## vault (secrets)

Read first: the `path_prefix` setting is empty by default, and with an empty prefix this kind reads every secret in the mount. Set a prefix. No copy-ready text is produced for an empty prefix.

Declared in `src/hadavin_sdk/actions/secrets_vault.py`.

- Create the token or the sign-in role so that it holds this policy only. Vault adds its `default` policy to every token unless told not to (`no_default_policy` when a token is created, `token_no_default_policy` on an AppRole or Kubernetes role).

| id | permission | on what | what limits a wildcard | the call it serves | why | when | name and form found in a vendor source | accepted by a real account | claims not checked |
|---|---|---|---|---|---|---|---|---|---|
| R17 | `read` | `{mount}/data/{path_prefix}*` | the prefix is this deployment's `path_prefix` setting and must not be empty; the `*` then covers only what lies under that prefix | `GET {mount}/data/{path_prefix}{name}` | reads one named secret | always | 2026-11-11, sources V-KV, V-POL, B-KV, B-POL | no | none |

Requests that need no permission:

- `POST auth/{auth_mount}/login`: the sign-in request of auth `approle` and `kubernetes` carries no token; auth `token` sends no sign-in request. Checked: 2026-11-11, sources V-API, V-APPROLE, V-K8S, B-API.

Never give this identity (each line would undo what the kind promises):

| type | name | why | name found in a vendor source |
|---|---|---|---|
| role | `root` | the built-in policy that may do everything | 2026-11-11, sources V-POL |
| path | `sys/*` | the server's own settings: mounts, policies, audit devices | 2026-11-11, sources V-POL |
| path | `{mount}/data/*` with create, update, delete | the reader could replace or remove what it reads | 2026-11-11, sources V-POL, V-KV |
| path | `{mount}/metadata/*` | lists every secret name and can delete every version of a secret | 2026-11-11, sources V-KV, B-KV |
| path | `{mount}/destroy/*` | removes versions of a secret for good | 2026-11-11, sources V-KV, B-KV |

Credential: A Vault token: read from an environment variable (auth `token`), or issued at sign-in through AppRole or through the pod's Kubernetes service account. Lifetime: long.
Exception for the long-lived case: With auth `token` the operator supplies the token, so how long it lives is the operator's choice and this kind cannot shorten it. A token issued through AppRole or Kubernetes sign-in lives as long as the Vault role says. Ticket Q8a-1 covers the token from the environment.

Tested: declared calls equal the calls written in the module: yes. Engine: a real Vault server, in CI only: the generated policy text is given to a token that holds nothing else; the read works; with the grant removed the read is refused; a read outside the prefix, a write, the metadata and destroy paths and `sys/mounts` are refused.
Not covered by any test: OpenBao was never run; sign-in through AppRole or Kubernetes roles; a real deployment's own mounts.

Copy-ready text (replace every `{setting}` with this deployment's setting and every `<NAME>` with your own name):

```hcl
# R17: reads one named secret
path "{mount}/data/{path_prefix}*" {
  capabilities = ["read"]
}
```

## vault_transit (signer)

Declared in `src/hadavin_sdk/audit/signer_vault.py`.

- The sign-in request of this kind is written in the imported module `actions/secrets_vault.py` and is declared there, not here.
- In the call column, `{mount}` is this signer's own name for the `transit_mount` setting, and the permission is written with the setting's name.
- The signer signs a test message when it is built, and verifying the audit trail builds the signer, so a process that only verifies needs R18 too.
- Create the token or the sign-in role so that it holds this policy only. Vault adds its `default` policy to every token unless told not to (`no_default_policy` when a token is created, `token_no_default_policy` on an AppRole or Kubernetes role).

| id | permission | on what | what limits a wildcard | the call it serves | why | when | name and form found in a vendor source | accepted by a real account | claims not checked |
|---|---|---|---|---|---|---|---|---|---|
| R18 | `update` | `{transit_mount}/sign/{key_name}` | no wildcard | `POST {mount}/sign/{key_name}` | signs each audit checkpoint and the start-up test message | always | 2026-11-11, sources V-TR, B-TR, V-POL | no | none |
| R19 | `read` | `{transit_mount}/keys/{key_name}` | no wildcard | `GET {mount}/keys/{key_name}` | reads the pinned version's public key and the key type | always | 2026-11-11, sources V-TR, B-TR | no | none |

Requests that need no permission:

- none

Never give this identity (each line would undo what the kind promises):

| type | name | why | name found in a vendor source |
|---|---|---|---|
| role | `root` | the built-in policy that may do everything | 2026-11-11, sources V-POL |
| path | `sys/*` | the server's own settings: mounts, policies, audit devices | 2026-11-11, sources V-POL |
| path | `{transit_mount}/keys/{key_name}` with delete | deletes the key that signs the audit trail | 2026-11-11, sources V-TR, B-TR |
| path | `{transit_mount}/keys/{key_name}/config` | can allow the key to be deleted or exported | 2026-11-11, sources V-TR, B-TR |
| path | `{transit_mount}/export/*` | copies the private key out | 2026-11-11, sources V-TR, B-TR |
| path | `{transit_mount}/backup/*` | copies the private key out as a backup | 2026-11-11, sources V-TR, B-TR |

Credential: The same Vault client and sign-in as the `vault` secrets kind. A Vault token: read from an environment variable (auth `token`), or issued at sign-in through AppRole or through the pod's Kubernetes service account. Lifetime: long.
Exception for the long-lived case: With auth `token` the operator supplies the token, so how long it lives is the operator's choice and this kind cannot shorten it. A token issued through AppRole or Kubernetes sign-in lives as long as the Vault role says. Ticket Q8a-1 covers the token from the environment.

Tested: declared calls equal the calls written in the module: yes. Engine: a real Vault server, in CI only: signing and reading the public key work; with either grant removed that request is refused; signing with another key, changing the key's settings, exporting it, backing it up and deleting it are refused.
Not covered by any test: OpenBao was never run; sign-in through AppRole or Kubernetes roles.

Copy-ready text (replace every `{setting}` with this deployment's setting and every `<NAME>` with your own name):

```hcl
# R18: signs each audit checkpoint and the start-up test message
path "{transit_mount}/sign/{key_name}" {
  capabilities = ["update"]
}

# R19: reads the pinned version's public key and the key type
path "{transit_mount}/keys/{key_name}" {
  capabilities = ["read"]
}
```

## kubernetes (source)

Declared in `src/hadavin_sdk/sources/kubernetes.py`.

- One Role and one RoleBinding per namespace in `namespaces`. Never a ClusterRole or a ClusterRoleBinding.
- At every start-up the kind asks the cluster what this identity may do and reports write verbs, shell subresources and any read of `secrets`. It does not report the verb `watch`.

| id | permission | on what | what limits a wildcard | the call it serves | why | when | name and form found in a vendor source | accepted by a real account | claims not checked |
|---|---|---|---|---|---|---|---|---|---|
| R20 | `list` | `apps/deployments in {namespaces}` | no wildcard | `k8s.list_deployments` | reads deployments, their rollout revision and images | always | 2026-11-11, sources K-AUTHZ, K-SRC | no | none |
| R21 | `list` | `core/events in {namespaces}` | no wildcard | `k8s.list_events` | reads events in the time window | always | 2026-11-11, sources K-AUTHZ, K-SRC | no | none |
| R22 | `get` | `core/pods/log in {namespaces}` | no wildcard | `k8s.pod_log` | reads one pod's log lines | always | 2026-11-11, sources K-RBAC, K-SRC | no | none |

Requests that need no permission:

- `k8s.rules_review`: asks the cluster what this identity may do; it creates nothing. Note: default clusters only: a cluster that took this right away from signed-in identities must grant `create` on `selfsubjectrulesreviews`. Checked: 2026-11-11, sources K-RBAC, K-SRC, K-SSRR.

Never give this identity (each line would undo what the kind promises):

| type | name | why | name found in a vendor source |
|---|---|---|---|
| role | `cluster-admin` | a built-in role that may write | not yet checked |
| role | `admin` | a built-in role that may write | not yet checked |
| role | `edit` | a built-in role that may write | not yet checked |
| action | `create` | a write verb: this source only reads | 2026-11-11, sources K-AUTHZ |
| action | `update` | a write verb: this source only reads | 2026-11-11, sources K-AUTHZ |
| action | `patch` | a write verb: this source only reads | 2026-11-11, sources K-AUTHZ |
| action | `delete` | a write verb: this source only reads | 2026-11-11, sources K-AUTHZ |
| action | `deletecollection` | a write verb: this source only reads | 2026-11-11, sources K-AUTHZ |
| action | `escalate` | lets the identity widen its own rights | 2026-11-11, sources K-AUTHZ |
| action | `bind` | lets the identity widen its own rights | 2026-11-11, sources K-AUTHZ |
| action | `impersonate` | lets the identity act as another one | 2026-11-11, sources K-AUTHZ |
| resource | `pods/exec` | opens a shell or a tunnel into a workload | 2026-11-11, sources K-RBAC, K-SRC |
| resource | `pods/attach` | opens a shell or a tunnel into a workload | 2026-11-11, sources K-SRC |
| resource | `pods/portforward` | opens a shell or a tunnel into a workload | 2026-11-11, sources K-SRC |
| resource | `pods/proxy` | opens a shell or a tunnel into a workload | 2026-11-11, sources K-SRC |
| resource | `nodes/proxy` | opens a shell or a tunnel into a workload | 2026-11-11, sources K-KUBELET |
| resource | `services/proxy` | opens a shell or a tunnel into a workload | 2026-11-11, sources K-SRC |
| resource | `secrets` | reading a secret reveals its value | 2026-11-11, sources K-AUTHZ |

Credential: The ServiceAccount token that the tool's fetch attaches to each request. This module holds no credential. Lifetime: long.
Exception for the long-lived case: Whether the token expires is decided by the cluster and the operator, and this code cannot tell. From the builder's memory, not checked against the Kubernetes pages: a token projected into the pod expires and is renewed, a token stored in a Secret does not expire. Use a projected token. No ticket removes this yet.

Tested: declared calls equal the calls written in the module: yes. Engine: no cluster in any test. The generated Role is given to the kind's own read-only rule (the function that judges a real cluster's answer at every start-up), which finds no problem in it and does find one when a write verb, `pods/exec` or a read of `secrets` is added.
Not covered by any test: whether the three rules are enough on a real cluster; clusters that changed the default right of every signed-in identity to ask what it may do.

Copy-ready text (replace every `{setting}` with this deployment's setting and every `<NAME>` with your own name):

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: "<ROLE_NAME>"
  namespace: "{namespaces}"
rules:
  # R20: reads deployments, their rollout revision and images
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["list"]
  # R21: reads events in the time window
  - apiGroups: [""]
    resources: ["events"]
    verbs: ["list"]
  # R22: reads one pod's log lines
  - apiGroups: [""]
    resources: ["pods/log"]
    verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: "<ROLE_NAME>"
  namespace: "{namespaces}"
subjects:
  - kind: ServiceAccount
    name: "<SERVICE_ACCOUNT>"
    namespace: "<SERVICE_ACCOUNT_NAMESPACE>"
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: "<ROLE_NAME>"
```
