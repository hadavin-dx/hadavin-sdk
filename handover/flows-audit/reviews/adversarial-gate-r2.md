# Adversarial gate read r2 (read-only; reader tries to break the claim "a lead sent twice with the same id is processed once")
Nothing ran. Made-up data only. Line numbers: FP = FIX-PLAN.md, FD = FINDINGS.md, RM = flow-check/README.md, DC = inputs/DECISIONS-2026-11-16.md.

## Ways the claim can still be false, unproven or filmed wrongly while every gate passes
1. **Old rows in the table get worked on during the take.** FP:7 checks 0 rows only for the take's own keys. Leftover rehearsal or loopback rows still in state 'processing' with attempts under 3 are re-claimed by the recovery flow (every 30 s; its ClaimStuck query selects every stuck row), which sends mails and calls the CRM for old leads. Mailbox then shows extra mail; FP:12 says "stop and retake" but nothing prevents it. Fix: gate (a) also requires `select count(*) from mf_leads where state not in ('done','review','unknown','failed')` = 0, or truncate the take's own table before the first send.
2. **The gate greps files, not what n8n holds.** FP:6 greps the filled copy; the lead imports with scripts\n8n_api.py (DC:7), which this audit never saw (FD:47, item 18). The imported flow can differ (FP:6 does not export back). Fix: after import, export each flow with the same script and re-run take_check and the greps on the export.
3. **Wrong-patch run.** RM:25 says take_check exits 4 on unpatched files, but FP:6 only says "exits without code 4". F-002 (key check) and F-008 (saved runs) are not in the committed files (RM:25). A copy with F-008 but without F-002 or an old patch order passes exit 4 test only partly: the key check is reported per file, not required. Fix: gate lists the sha and path of the patched filled folder, and requires the take_check key-check lines to say "present" for mf-form and mf-hook.
4. **Contradiction: no `$env` vs. DESK_ALERT_TO.** FP:6 requires 0 `$env` in the filled copy, yet today AlertSend in mf-recovery reads an environment variable (RM:36) and Q20 item 4 says DESK_ALERT_TO is "never typed in a file" (QUESTIONS.md:72). Both cannot hold; the lead will either type it in (breaking Q20) or fail the gate. Fix: decide in writing which one wins; if the file route, name where the literal lives and that it is a made-up address.
5. **Different spellings of the same lead id.** The claim is `ON CONFLICT (lead_key)` (mf-hook Claim, text, case-sensitive). "LEAD-1" vs "lead-1", a trailing space, or the same person under two ids is two leads, two mails. The gate says "same id" but nothing says POST 2 is byte-identical to POST 1 (same key, same text). Fix: the rehearsal script sends the same stored request body twice; record both bodies in the take notes.
6. **POST 2 timing is chosen but its meaning is not.** FP:10 asks the lead to pick when POST 2 goes. If sent while the first run holds the claim, the reply is "stored"/'processing' and the proof "state done" may not yet be true when the screen is filmed; if sent after done, the claim never meets a race, so it shows only a repeat, not a double-send race. Two different claims, one caption. Fix: caption the exact case filmed ("sent again after the first finished") and do not say "sent at the same time".
7. **"Under 10 s" has no source.** FP:8 / RUNSHEET-WORDING.md:34 give 10 s as the pass line, but no file derives it (no measured reply time exists; n8n never ran, FD:30). Pass line chosen after seeing the take is not a gate. Fix: write the number and who set it before the rehearsal, with the rehearsal's measured reply times beside it.
8. **Lease 45 s versus slow steps, and a second mail by recovery.** FP:11 says the lead "decides before the take" with no threshold. Qualify has 2 tries x 10 s plus the CRM step; a slow run can pass 45 s, recovery re-claims, and Qualify/CRM run twice (MailClaim stops a second mail, but the CRM and the stage service are called twice, and the stage service may be a paid model call with no spend figure, FD:35, item 6). The claim "processed once" is then false for the CRM step even if 1 mail shows. Fix: rule "if any rehearsal step over 20 s, set recovery off for the take (and say so on screen)", with the lead as owner and a number.
9. **Word with two meanings: "processed once".** RM:34 defines it as 1 mail + row done + reply fast, then forbids saying "CRM called once". A viewer, and the caption, will read "processed" as every step. Fix: the caption says "one mail sent, one row in state done" (FP:8 already says so) and the run sheet caption A-016f is changed to those words, not left as the old sentence.
10. **Counts proof from a rehearsal screenshot (DC:9).** FP:9 labels it "from rehearsal, take id X", but a rehearsal screenshot cannot show the take's own rows; a viewer reads it as the take. The proof for the claim is then not from the filmed run. Fix: take the counts from the take's own run by a SELECT-only login after the take, and film the label.
11. **Gates nobody can run on film day.** Every gate has owner "lead, at re-pin, time TBD" (FP:6, FD:52-56), yet the owner only types y, the challenge and end (DC:7). The HubSpot id probe needs the owner's written yes with numbers (FD:49, item 20); the model key revoke is owner-only (DC:5). No row says the take is cancelled if the lead's re-pin has no time. Fix: one dated line in OWNER-STEPS: "no re-pin time written by <date> = take postponed", and the owner's yes text for the probe.
12. **Sender retries and extra mails after the filming.** FP:10 admits whether the sender retries after a non-200 is unknown. A retried POST 3 or POST 4 arrives while filming and can put a "stored" answer in the wrong place or, if the table write fails (F-002 case), 503 then resend; the gate only says "watch the mailbox". Fix: the take script, not the lead by hand, sends the two POSTs, logs every POST and reply with time, and the run sheet says the script log is the proof of "twice".
