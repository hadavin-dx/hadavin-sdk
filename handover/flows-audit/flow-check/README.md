# flow-check: read-only check of the exported n8n flow files

Nothing here starts n8n. The take uses the **real-v5** flows only (lead decision 2026-11-16): the folder `handover/demo/n8n-flows-real-v5`. The `film-v5` folder is **NOT FOR THE TAKE**; `run_all.sh` still runs it, in a separate block that never changes the exit status. **PARKED (lead answer Q17-2):** the `run_all.sh` film-v5 block and the `--baseline` option are parked; `take_check.sh` is the one live tool for the take, and nothing in the take needs the parked parts. Needs **Python 3.10 or newer** (the checker says so and stops with exit 3 on an older one).

Words used below: a **flow file** is one exported n8n workflow (a `.json` text file). A **step** is one box in a flow. A **web address flow** is a flow that starts when someone calls a web address (a webhook) or fills a form. A **run list** is the list of past runs that n8n shows; it is empty when saving of runs is switched off. The **take** is the filmed recording.

## Before the take: what a person must do (the script cannot)

In psql, before the first send, run `select column_name from information_schema.columns where table_name='mf_leads' and column_name in ('alert_sent','alert_token','alert_until','alert_attempts');` It must list all four columns. No file check can see the database.
2. **Fill in every placeholder** in n8n: the mail addresses (sender and receiver) and the credential and sub-workflow ids. `take_check.sh` lists them. The checker cannot see what you type into n8n afterwards; it can only see the files.
3. **Decide the open points** below (no password on two web addresses; environment variables inside steps).
4. **Try one import into n8n.** Nothing here proves that n8n accepts these files.
5. **Start state:** use lead keys and e-mail addresses never used before (new ones on every retake); before the first send the table has 0 rows for them, the mailbox and the n8n run list are empty or filtered to the take, and a HubSpot search finds nothing.
6. **Proof words:** 'processed once' is shown by exactly 1 mail after the stated wait plus the table row in state done (FIX-PLAN rule (b)). The time of the second reply is logged, but it is not proof (Q25-3). Do not say 'the CRM was called once' (the CRM step upserts on the e-mail, so a contact count proves nothing).
7. **Timing:** write down the run list you expect and when the second POST is sent; rehearse that exact choice. Time Qualify and the CRM write against the 45 s lease.
8. **Screens:** list the screens shown but not opened; made-up addresses only; watch the whole recording once for personal data and secrets before publishing. An extra or stray mail means stop and retake; the lead calls an abort.
9. **Rows left in the table (gate 2 r2):** run `select count(*) from mf_leads where state not in ('done','review','unknown','failed')`; it must be 0 for the whole table, not only the take's keys, because the recovery flow re-claims old stuck rows and sends their mail.
10. **Export back after import:** export the four flows from n8n with the lead's own script (not in this tree), then run `take_check.sh` and `grep -c '$env'` and the placeholder greps on the export; they must match the filled copy. Name the patched folder and its sha; F-002 and F-008 must both be in it, and `take_check.sh` must print `key check present (F-002 applied)` for `mf-form.json` and `mf-hook.json`. The unfilled files hold 3 `$env` reads (`DESK_ALERT_TO`, `DESK_URL`, `DESK_TIMEOUT_MS`); the filled copy and the export must hold 0.
11. **Proof of 'twice':** the take script sends one stored request body twice (same bytes) and logs both bodies and both replies with the time of each; that log is the proof. Caption the POST 2 timing that was filmed (after the first run finished, or while it held the claim). The 10 s line and the lease threshold are numbers set by the lead and measured in the rehearsal (not set yet; not measured facts).
12. **Counts and postponing:** the counts shown come from the take, read afterwards with a SELECT-only login. If no re-pin time is set by date X (date X: lead to set), the take is postponed.

## Open decisions (read first)
1. **Two web addresses have no password** (`mf-form`, `mf-hook`). Exit 0 does NOT mean a password was checked.
2. **Some steps read environment variables** (today: `AlertSend` in `mf-recovery`, `Qualify` in `mf-sub-crm-mail`; the checker prints the current list). If n8n on the filming machine blocks environment-variable access inside steps, they stop working. No file check can see that n8n setting. Add `--block-env-access` to see which steps depend on it (exit 1 expected today).
3. **Two yes/no steps lack their second branch** (`StuckRow`, `AlertRow` in `mf-recovery`). Recorded as an accepted decision with `--accept-if`, not hidden.
4. **Saving of runs.** In the committed real-v5 files it is switched off in all four (`saveDataSuccessExecution` and `saveDataErrorExecution` are `none`, `saveManualExecutions` is false), so the run list in n8n stays empty. The take needs that list, so patch F-008 switches saving ON (successful runs, failed runs and runs started by hand with "Test workflow") for the two entry flows and the sub-workflow. The recovery flow (`mf-recovery.json`) keeps saving off on purpose: it fires every 30 seconds, and the one video makes no claim about recovery (decision 4). `take_check.sh` therefore prints `ACCEPTED: recovery flow not part of the take (decision 4)` for that one file and an `INFO` line for each flow with saving on, saying it is on on purpose. Saved runs hold made-up lead keys, e-mails and names. The take never deletes them, and no owner step deletes saved runs (lead decision Q19-1). **Run the take check on the patched copy** (F-002 and F-008 applied): on the committed unpatched files it exits 4, because saving is off there and the key check is absent. How to run it on the patched copy: `bash take_check.sh --flows <path of the patched folder>` (round 10: the old environment variable `TAKE_CHECK_FLOWS` is now a test-only override and gives exit 4 unless `TAKE_CHECK_TEST=1` is set). Nothing else is needed: the script finds the F-002 patch by the step named `KeyOk` in each entry flow and then expects 15 steps and 14 links in `mf-form` and `mf-hook` (12 and 11 in an unpatched file), so the old `TAKE_CHECK_FORM_EXPECT=15:14` variable is now only a test override. When both entry flows have `KeyOk`, the checker also runs its F-002 content check on them (`--patch-checks F002`). The two patches F-002 (checks that a lead key is well formed, answers a bad key, answers when the table write fails) and F-008 (saving of runs) are **not** in the committed real-v5 files; `take_check.sh` says per file whether the key check is present (it reads the step list of the file, not any text). **F-002 is required for the take** (round 9): a missing `KeyOk` in either entry flow makes `take_check.sh` exit 4. **Overrides** (round 10): the top block and the FINAL line print `OVERRIDES: none` or `ACTIVE ENVIRONMENT OVERRIDES: ...`. Any of `TAKE_CHECK_CK`, `TAKE_CHECK_WARN_PIN`, `TAKE_CHECK_FLOWS`, `TAKE_CHECK_DDL`, `TAKE_CHECK_FORM_EXPECT` makes the take exit 4 unless the test flag `TAKE_CHECK_TEST=1` is set (only `run_all.sh` and `test_take_check.sh` set it). **Run saving is checked exactly** (round 9): every flow except `mf-recovery.json` must have `saveDataSuccessExecution` = `all`, `saveDataErrorExecution` = `all` and `saveManualExecutions` = `true`; a missing settings block, a missing key or any other word (for example `off`) is exit 4, not only `none` and `false`. **WARN baseline** (round 9): the top block and the FINAL line print `RESULT: x FAIL, y WARN`; the expected WARN lines of the take are pinned in `take-warns.pin` (folder paths removed) and any new or vanished WARN line is exit 4, with the difference printed. The pin file also carries a date (UTC) and the sha256 of its WARN lines in its header; a pin edited by hand, or without those two lines, is exit 4. The top block prints how many WARN lines are pinned and says they stand for known defects that are not fixed (for example a missing answer to the caller when a step fails, steps that turn an error into normal-looking data, IF branches that lead nowhere, ids still to fill). **How a person installs a new pin** (round 10): after a person has read a changed set and accepts it (for example after the placeholders are filled in n8n and the flows are exported back, which removes the placeholder WARNs), run `bash take_check.sh --flows <folder> --write-warn-pin <path of a file that does not exist yet>`. The run writes that new file only when the checker found no FAIL and gave a RESULT line, prints the difference against the pin in use, and exits 4 when it wrote the file (writing a pin is never a pass; it refuses an existing file, so the pin in use is never overwritten). Its other exit codes are the real ones: **2** when it refuses (the file exists or is the pin in use, or a bad command line), **1** when the checker found a FAIL (nothing is written), **3** when the checker broke (nothing is written), and **4** when nothing was written because the run had other problems or no RESULT line. Then read the file, copy it over `take-warns.pin` by hand, commit it, and run `bash take_check.sh` again: it must exit 0. A disabled external-call step (mail, database, web request, CRM, sub-workflow) is a FAIL in the checker, because n8n passes data through it while it sends and writes nothing.

- **The take check:** `bash take_check.sh [--flows DIR] [--write-warn-pin NEWFILE]`. Bare `bash take_check.sh` checks the committed folder `demo/n8n-flows-real-v5`, which is NOT patched, so it exits **4** (run saving is off there and the F-002 key check is absent); the take runs on the patched copy: `bash take_check.sh --flows <patched folder>`. `--flows DIR` names the folder to check. `--write-warn-pin NEWFILE` writes a NEW pin file (NEWFILE must not exist; when the file is written the run exits 4 on purpose, writing a pin is never a pass; refused = 2, checker FAIL = 1, checker broke = 3, other problems = 4 and nothing written). It writes only when the checker found no FAIL and the run has no other problem besides a changed WARN set (an unpatched folder, a missing key check, a missing table file, run saving off or an environment override each stop it). The written file says it is NOT YET READ BY A PERSON and holds a `# reviewed by: PLACEHOLDER-...` line; a person reads every WARN line, replaces that line with `# reviewed by: NAME, YYYY-MM-DD` and installs the file by hand. A pin whose header still has the placeholder (or has no `reviewed by` line) is exit 4. **The reviewer line (round 10c):** the output prints it exactly as written (`reviewed by (as written in the pin): ...`) and never says that a person read the pin, because the script cannot know that. The first exit 0 therefore needs the lead's own line. The top block and the `FINAL` line print a sha256 of the four flow files (`mf-form.json`, `mf-hook.json`, `mf-recovery.json`, `mf-sub-crm-mail.json`; the combined value is the sha256 of the four per-file lines): compare it with the sha written down at re-pin. ## What the exit codes mean

| Exit of `check_flows.py` | Meaning |
|---|---|
| 0 | No FAIL line. It does NOT mean the flows are ready, safe to import, or that a password is set on the web addresses. Read the closing block. |
| 1 | At least one FAIL line: a definite fault in a file (or an open decision you turned into a fault with an option below). |
| 2 | Wrong command line: unknown option, missing value, unknown patch name, bad `--expect`, `--expect-credential`, `--accept-if` or `--expect-json` value, a `--ddl` file that cannot be read (missing, or not valid UTF-8 text) or that holds no `CREATE TABLE`. |
| 3 | The checker itself broke, or could not write its `--diff-out` file. Never a verdict about the flows. |

`take_check.sh` uses the same 0 to 3 and adds **4**. If the checker ever returns a number above 3 (for example 127 = command not found, 137 = killed), the take shows that number and exits **3** (round 10c); 4 is never passed through from the checker. A real FAIL stays exit **1** and is not turned into 4: for example `TAKE_CHECK_FLOWS=/tmp/x` pointing at a folder that does not exist gives exit 1 (the checker cannot read the four listed flow files), not 4; that is intended, not a bug. Exit 4 is: the checker found no FAIL, but run saving is not exactly all / all / true on a flow the take uses (or the recovery accept excused nothing), or the F-002 key check is absent, or the set of WARN lines differs from `take-warns.pin` (or that file, its date, its `reviewed by` line, its sha256 line or the RESULT line is missing, or the `reviewed by` line still holds the placeholder or names a session or says `lead to confirm`, or the sha256 does not match), or a flow file changed (or could not be read) while the check ran, or an environment override is active without `TAKE_CHECK_TEST=1`, or a helper of the script failed, or a new pin was written (never a pass), or the table check did not happen or found a mismatch (table file missing, 0 query strings read, a column or table the file does not define, or a database step with no query text).

Line types: `FAIL` = fault. `WARN` = read it, exit stays 0. `WARN-LEAD-DECISION` = a decision for the lead or owner (no password on a web address, steps that read the environment); exit stays 0 on purpose.

## Options (what each really does)
- `--ddl FILE`: reads the `CREATE TABLE` definitions in FILE and compares **names** only. For each database step it reads the text of the `query` setting, takes the table names after `from`, `update`, `into`, `join` and the other plain words, and warns for a table or column the FILE does not define. It is a **WARN** (exit 0), and `take_check.sh` turns a column or table WARN into exit 4. What it does NOT do: it does not run SQL; it ignores words inside `{{ }}` and inside quotes, words directly before a `(`, and SQL words and type names it knows; it reads only `CREATE TABLE` (a column added later by `ALTER TABLE` looks missing); a table alias or an SQL word it does not know can give a false WARN; steps in table or column mode (no `query` text) are not compared and are counted and warned. A query string that names no table after blanking (for example only a `{{ }}` expression) is **not counted as compared**: it is a WARN and is counted on the line `SQL NOT COMPARED`, which also counts compared queries whose `{{ }}` parts were blanked, and table-file columns named like an SQL word (never compared). It prints how many query strings it compared; **0 compared is said loudly** (`SQL COLUMNS NOT CHECKED`) and is exit 4 in the take. Without `--ddl` it warns `no --ddl file was given`.
- `--accept-no-save FILE` (repeatable): records one decision: this flow may keep run saving off. The value is one exact file name (the take passes `mf-recovery.json` and nothing else; there is no blanket accept). It is honoured only for a flow whose triggers are all schedule triggers, so naming `mf-form.json` or the sub-workflow does not hide their WARN (the checker adds a second WARN saying the accept was refused). A name that excuses nothing (file missing, saving already on) is a WARN. Smaller than a new mechanism because it reuses the same recorded-decision pattern as `--accept-if` and changes no exit code of the checker; `take_check.sh` turns any remaining run-saving WARN into exit 4.
- `--accept-if FILE=NODE:OUT[,OUT]` (repeatable): records one decision: this yes/no step of this file is accepted to lack exactly these outputs. `OUT` is 0 or 1 (in n8n, 0 is the "yes" output and 1 the "no" output; that is from memory of n8n). More than one OUT may be given with commas, for example `mf-recovery.json=StuckRow:0,1`. It is a WARN, counted as a known open problem and listed in the closing block. Any other missing branch is a FAIL. It applies to every folder of the same run. An `--accept-if` that matches nothing is itself a WARN (`matched nothing`).
- `--baseline DIR` (**PARKED**: not used by the take and not needed for it; kept only because an older tool had it): a yes/no step that already lacks the same branch in DIR is only a WARN (and is not counted as a known open problem). If you point it at the folder you are checking, it excuses every missing branch there; do not do that. The take command does not use it.
- `--quiet-info`: hides the type table and the per-file line about placeholder words and environment variables. It does NOT hide the credential list per file, any WARN or FAIL, or the closing block (placeholders, credential ids, environment steps, SQL counts, open problems).
- `--require-webhook-auth`, `--block-env-access`, `--require-real-credential-ids`: each turns an open decision into a FAIL. `--require-real-credential-ids` also fails a placeholder in a node setting such as a mail address, not only credential ids.
- `--fail-unverified`: turns every rule tagged `n8n rule UNVERIFIED` into a FAIL. The rules are: the allowed webhook `authentication` values (webhook: none, basicAuth, headerAuth, jwtAuth; form trigger: none, basicAuth); the credential kind each needs; the credential kinds of postgres, smtp and hubspot steps; the position of the error output and "cannot tell which output is the error output"; the default `responseMode` and a webhook with none set; a webhook or form with no usable path; two webhooks with the same method and path or the same `webhookId` (compared across all folders of one run); the `onError` value list; the retry limits (`maxTries`, `waitBetweenTries`). The take check does NOT pass it, so these stay WARN there.

## The closing block of the checker (always printed, also with `--quiet-info`)
Open decisions count, accepted IF branches, placeholders in node settings, credential and sub-workflow ids that are still placeholders, steps that read environment variables, the SQL counts (`SQL columns compared ...`, `SQL WARNS: column WARNs=.. table WARNs=..`), the list of known open problems, and what is not proven.

What the placeholder scan can and cannot see: it looks at every node setting and at credential and sub-workflow ids, for these words: `PLACEHOLDER`, `PG_CREDENTIAL_ID`, `SMTP_CREDENTIAL_ID`, `SUB_WORKFLOW_ID`, `HS_CRED`, `HUBSPOT_CREDENTIAL_ID`, `CHANGE_ME`, `CHANGEME`, `REPLACE_ME`, `TODO`; and it flags a mail setting (`fromEmail`, `toEmail`, `ccEmail`, `bccEmail`, `replyTo`) that is not shaped like one address. A wrong but well-formed address, or a different placeholder word, passes. Anything you change inside n8n after import is invisible to it.
