Patch F-002 may make a lost lead worse (UNVERIFIED, needs an n8n run): Claim has alwaysOutputData: true (mf-form.json, mf-hook.json, real-v5 and film-v5); the patch adds onError: continueErrorOutput (pg() default always=True) but does not remove alwaysOutputData. 2. Patch F-008 sets success saving to "all" in the shared ST dict so it also applies to mf-recovery: fires every 30 s, about 2,880 saved executions a day, each swept row carrying lead_key and email; the audit clean-up step does not mention this flood: leave recovery at "none" for success or add a prune interval; patch comment "run n8n execution pruning off the take database" is unclear.
3. F-002 trims the key in Valid so the stored and echoed key become the trimmed key (Nit, sender must compare trimmed); the patch only fixes empty keys: no `^L[0-9a-f]{16}$` shape or length cap before Claim; an attacker-chosen key goes into the mail subject and the primary key.
