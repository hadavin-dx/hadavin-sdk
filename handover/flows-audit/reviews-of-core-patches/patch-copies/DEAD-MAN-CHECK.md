## What it checks
A tick that has stopped (scheduler dead, container gone, store unreachable) writes nothing, so it cannot report its own silence. The check asks the store whether each step has
succeeded recently. Steps that run every tick: `sweep`, `reconcile`, `stuck`, `checkpoint`, and `audit_reconcile` (only after A-01). Steps with their own interval (`purge_evidence`,
`reprobe_sources`) are left out; to add one, use its interval plus a margin as its own age limit.

## The query, in a runnable form
Save it as `dead-man-check.sql` on the machine that runs the scheduler (T1), in a folder only the scheduler's user can write; the job checks the file against the recorded fingerprint before every run. Placeholder rule: `:limit_s` is a `psql` variable, set on the command line
with `-v limit_s=<seconds>`; it must be a plain number (no quotes). Without it `psql` stops with a syntax error and exit code 3, which counts as "cannot check" (rule 4 below). An
unreachable store gives exit code 2. Suggested value (D2): 3 times the SLOWEST tick period (a tick runs every 30 to 60 seconds), so `180`; if the scheduler runs the tick every 30 seconds
only, `90` is enough. The query names the table together with its schema, `public.tick_state`, so that the search path of the login cannot point it at another table of the same name. The migration file creates it with an unqualified name (`store/migrations/0003_approvals_tick.sql:30`, `CREATE TABLE tick_state`), so it lands in the first schema of the search path of the login that runs the migrations, which is `public` unless the store setting says otherwise (the migration code names the same schema when it grants rights: `store/migrate.py:172-173` reads `current_schema()`; those two lines show the grant, they do not show the creation, so "the creation lands in `public`" is an inference, UNVERIFIED on a real store). If it is in another schema, replace `public.` by that schema in the query, in S5 and its rollback and in check b of the real-store checks.
Clock note: `now()` is the database server's clock and `last_ok_at` is written with the clock of the machine that ran the tick; keep both on network time, or a skew of more than the
margin gives false alarms or hides a stop. A `last_ok_at` more than one minute ahead of the database clock is reported as `CLOCK AHEAD` (without that test a tick machine whose clock runs ahead would never look stale); a skew inside that minute is not reported.

```sql
-- One line per tick step that is MISSING from tick_state, never succeeded, has not succeeded within the age limit, or has a last success in the future,
-- and ALWAYS one last line "OK|||<n>" (n = how many names the query watches). Healthy = that one line and no other.
WITH w(step) AS (VALUES ('sweep'), ('reconcile'), ('stuck'), ('checkpoint')),   -- four names; add ('audit_reconcile') only after A-01 is applied
p AS (
    SELECT w.step,
           t.last_ok_at,
           t.last_run_at,
           CASE
               WHEN t.step IS NULL THEN 'MISSING (no row: never ran)'
               WHEN t.last_ok_at IS NULL THEN 'NEVER SUCCEEDED'
               WHEN t.last_ok_at > now() + interval '1 minute' THEN 'CLOCK AHEAD (last success is in the future)'
               ELSE 'STALE (last success older than the limit)'
           END AS problem
    FROM w
    LEFT JOIN public.tick_state t ON t.step = w.step
    WHERE t.step IS NULL
       OR t.last_ok_at IS NULL
       OR t.last_ok_at < now() - make_interval(secs => :limit_s)
       OR t.last_ok_at > now() + interval '1 minute'
)
SELECT step, last_ok_at, last_run_at, problem FROM p
UNION ALL
SELECT 'OK', NULL, NULL, (SELECT count(*) FROM w)::text
ORDER BY 1;
```
Set the values first, as shell variables, so that no placeholder in angle brackets is ever pasted (a pasted `<name>` is a shell redirection that reads or creates a file): `CA=/path/of/the/CA/file; DBHOST=the-host; DBPORT=5432; DBNAME=the-database` (your own values; the database administrator hands them over). **MANUAL TEST OF THE QUERY (one line; for a person at a terminal, to see the output once; NOT for scheduling).** It has no check of the query file's fingerprint, no timeout, no cleared `PG*` variables and no exact-output test, and `psql` can exit 0 and print nothing (an empty query file, or a `psqlrc` that discards output) which this line alone would let pass as healthy; the scheduled run is the job script in the section "The job around the query ...", and that is what T2 schedules. The password must already be available to `psql` for this one command, through a `PGPASSFILE` (built without anyone seeing the secret: Block 2b of the password procedure below; the scheduled job builds its own): with `-w` and no password source `psql` stops with exit code 2 (`no password supplied`), the same exit code as an unreachable store, so a missing password looks like "cannot connect" (see the alert rule below):

## The job around the query, and the watching of the job (PROPOSAL written in the eleventh pass; NOT RUN; lead to confirm)
The query alone cannot report its own silence. If the scheduled job is stopped, deleted, moved to another machine, or its mail command is missing, nothing runs and nothing is printed, and silence looks like health. So the job sends an "all is well" signal and something OUTSIDE the scheduler machine alarms when the signal stops. **What the signal means, exactly:** when the job ran, the check found every watched step (four, or five after A-01) with a recorded success within `LIMIT_S` seconds. It does NOT mean that the store is healthy, that the audit outbox is empty, or that the tick did the right thing (see "What it does not cover"). The text of the signal carries `LIMIT_S` and `NAMES_EXPECTED`, so the receiver can see which limit and how many names the run used (the fingerprint covers the query file, not these two settings).
1. The job (script below) sends the signal ONLY when `psql` exited 0 AND printed exactly the one line `OK|||<n>`. Any other result (including no output at all) sends the alert instead. The script also refuses a query file whose fingerprint differs from the recorded one, and ends the run after 60 seconds (65 at the latest: `timeout -k 5`).
2. The receiver of the signal alarms when no signal has arrived for N minutes. AUDIT PROPOSAL, lead to confirm: N = 5 when the job runs every minute (about 3 run periods). A mailbox alone cannot alarm about a mail that never comes, so the receiver is one of these options (options first, the client chooses, the choice goes into the quote and the contract): (a) the client's own monitoring tool, if it can alarm on a missing signal (no new data path); (b) a hosted heartbeat monitor with a free tier (a third party that learns only "a signal arrived at time T", no database content; needs the client's written yes; a paid plan needs the studio head's yes with numbers); (c) a second small job on ANOTHER machine that reads the newest signal (a file or a mailbox time) and alarms when it is older than N minutes (our own code; it needs its own scheduler, so it must not run on the same machine). D7 names the choice and N; T2 cannot be completed before D7 is answered.
3. The job checks six names first: `psql`, `timeout`, `sha256sum`, `send_alert`, `send_ok` and `read_deadman_secret`. A missing one ends the job with exit 71 and a message on stderr and sends NO signal, so the receiver alarms anyway. It does NOT check the other programs it uses (`stat`, `mktemp`, `cp`, `cut`, `wc`, `head`, `tr`, `date`, `cat`, `rm`, `printf` is part of the shell); what happens when one of those is missing was not tested, UNVERIFIED.
Job script (PROPOSAL; never run against a database or a real scheduler: `bash -n`, and runs with FAKE stand-ins for `psql`, `send_ok`, `send_alert` and `read_deadman_secret` in the fifteenth and sixteenth passes; `send_alert`, `send_ok` and `read_deadman_secret` are provided by the scheduler operator, D6, none is named in this folder (`send_ok` is called with ONE text argument, `limit_s=<n> names=<n>`, which it must put into the signal), and each must be an executable file on the PATH of the job or a shell function defined in the file named by `DEADMAN_LIB`, because the check `command -v` finds nothing else; the `trap` line cannot run after `kill -9` or a power cut):
```
#!/usr/bin/env bash
set -u
set +a                                   # no variable that is set later is exported by default (an inherited `set -a` or SHELLOPTS=allexport is switched off)
```

Five facts about the job script that its comments cannot hold (the script was run in the fifteenth and again in the sixteenth pass with FAKE `psql`, `send_ok`, `send_alert` and `read_deadman_secret` stand-ins in a scratch folder: healthy run, failing `psql`, disk folder refused with exit 70, relative error-log path refused with exit 73, hash with file name refused with exit 73; in the sixteenth pass also: a changed query file refused with exit 74, an output of `OK|||4` followed by an empty line refused (alert), a host written as an IPv6 address written correctly into the password file, a hang-up ending with exit 129 and leaving no folder, and no trace of the secret in the output of `bash -x`; no real database, scheduler or alert channel was involved, see "STATUS OF THE TESTS"):
1. **The error text of `psql` is kept, outside the alert.** The text of "$D/err" is the only place where a missing password, a refused login, a wrong host, a certificate problem, an expired password (check 2 below) or `permission denied` is named, and the trap deletes "$D". So the job appends it, with the time and the exit code, to the file named by the scheduler setting `DEADMAN_ERRLOG` (an absolute path outside "$D"; the job ends with exit 73 if it is not absolute, is a link, or is a file of another user). The job sets the mode of the file to 600 on every run, so only the user the job runs as, and root, can read it. The error text can name the host, the user and the database (UNVERIFIED: not run) and is therefore never sent in the alert. Who rotates or deletes that file (it grows by one entry per run that failed or printed an error text) is the scheduler operator's decision (D6), not made here.
2. **The password file is never written to a disk folder.** The job refuses to run (exit 70, no signal) unless the folder for its temporary files is memory-backed: default `/dev/shm`, or the folder named by `DEADMAN_TMP`, and the test is that GNU `stat -f -c %T` reports `tmpfs` or `ramfs` (tested standalone on Linux: `/dev/shm` accepted, `/tmp` and a missing folder refused). A `tmpfs` can still be written to swap space; whether the swap is on an encrypted disk is not known here (UNVERIFIED). After `kill -9` or a power cut the folder stays in memory until a reboot or until someone deletes it. On macOS the `stat` form differs and `sha256sum` and `timeout` are missing: the job refuses to run there (exit 70) until the scheduler operator replaces that one check and defines wrapper functions in `DEADMAN_LIB` (for example `timeout() { gtimeout "$@"; }` with GNU coreutils installed).
3. **Where the scheduler keeps the standard error of the job is NOT KNOWN here** (UNANSWERED, open question for the lead, who asks the studio head): the messages of the exits 70 to 76 (a missing command, a fingerprint that differs, a failed `send_alert`) are written to the standard error, and which scheduler is used, whether it keeps that text, for how long and who reads it is not written anywhere in this folder or in `REVIEW.md`. Until it is answered, treat the exits 70 to 76 as visible only by the missing signal (the receiver alarms), not by their text.
4. **After an alert that was sent successfully, the job itself ends with exit 0.** The job's own exit code therefore says "the job ran and the alert went out", not "the store is healthy": a scheduler that shows only exit codes shows a green job on an unhealthy store. The alarm is the alert message (and the missing "all is well" signal), not the scheduler's colour. Exit 75 or 76 means the alert or the signal could not be sent.
5. **What "exactly one line" means.** The job sends the "all is well" signal only when `psql` exited 0, the output equals `OK|||<n>` and it has exactly one line (`wc -l` counts one newline). The comparison with the output text ignores trailing empty lines (the shell strips them), which is why the line count is tested too. A signal (stop, interrupt, hang-up) sent to the job while `psql` runs takes effect after `psql` ends, at most 65 seconds later; a hang-up ends the job with exit 129, not 130.

## What it does not cover
Two different outages must not be mixed up: an outage while THIS check runs makes `psql` exit 2 and the job alerts (rule 4 above); an outage of the store between the audit write and the delete inside the tick makes the step raise, and this check then reports `STALE` for that step. A database outage that turns the audit drain red (`chain.py:244`, the `DELETE`, is not guarded either, so a store that goes away between the write and the delete makes the step raise: this check then reports `STALE`; true for the store, not a dead tick). A tick that runs and succeeds while doing the wrong thing; a slow mail server (the step finishes, the mail is late); a stuck backlog: `audit_reconcile` that drains 0 events because the
audit write path itself is broken records a success, so this check stays green ("green" means the step ran, not that the outbox is empty). The reverse also holds once A-01 is applied
without its per-row guard (`REVIEW.md` row RV-A6): one unreadable outbox row in the chain kind makes the drain raise on every tick, so the step goes RED and this check reports
`NEVER SUCCEEDED` or `STALE` although nothing is lost; the alarm then means "a bad outbox row blocks the drain", not "the tick is dead". The A-01 warning and error log lines are written at
the moment a write fails, but NOTHING reads those lines or alerts on them (no alert kind exists in `src`; a person or a log tool the client sets up would have to), so today they cover
nothing automatically. An audit kind with no `reconcile` method: with the A-01 patch in this folder the step FAILS (its `last_ok_at` stays empty, so this check reports NEVER SUCCEEDED);
an earlier version of the patch skipped quietly and recorded a success, which would have shown green. `K1bAudit` (`k1b/audit_sink.py`) has no `reconcile`, but it is made only by `build_audit` (`k1b/audit_sink.py:59`), whose only caller in `src` is the `k1b` command code (`cli.py:216`, import at `:213`), not by the tick (`app.py:161`).
