## What it checks
A tick that has stopped (scheduler dead, container gone, store unreachable) writes nothing, so it cannot report its own silence. The check asks the store whether each step has
succeeded recently. Steps that run every tick: `sweep`, `reconcile`, `stuck`, `checkpoint`, and `audit_reconcile` (only after A-01). Steps with their own interval (`purge_evidence`,
`reprobe_sources`) are left out; to add one, use its interval plus a margin as its own age limit.

## The query, in a runnable form
Save it as `dead-man-check.sql` on the machine that runs the scheduler (T1), in a folder only the scheduler's user can write; the job checks the file against the recorded fingerprint before every run. Placeholder rule: `:limit_s` is a `psql` variable, set on the command line
with `-v limit_s=<seconds>`; it must be a plain number (no quotes). Without it `psql` stops with a syntax error and exit code 3, which counts as "cannot check" (rule 4 below). An
unreachable store gives exit code 2. Suggested value (D2): 3 times the SLOWEST tick period (a tick runs every 30 to 60 seconds), so `180`; if the scheduler runs the tick every 30 seconds
only, `90` is enough. The query assumes the table is the unqualified `tick_state` and that the login's search path finds it; the migration file creates it with an unqualified name (`store/migrations/0003_approvals_tick.sql:30`, `CREATE TABLE tick_state`), so it lands in the first schema of the search path of the login that runs the migrations, which is `public` unless the store setting says otherwise (the migration code names the same schema when it grants rights: `store/migrate.py:172-173` reads `current_schema()`; those two lines show the grant, they do not show the creation, so "the creation lands in `public`" is an inference, UNVERIFIED on a real store). If it is in another schema, write the schema name in front of `tick_state` in the query and in the `GRANT` lines.
Clock note: `now()` is the database server's clock and `last_ok_at` is written with the clock of the machine that ran the tick; keep both on network time, or a skew of more than the
margin gives false alarms or hides a stop. A `last_ok_at` more than one minute ahead of the database clock is reported as `CLOCK AHEAD` (without that test a tick machine whose clock runs ahead would never look stale); a skew inside that minute is not reported.

```sql
-- One line per tick step that is MISSING from tick_state, never succeeded, has not succeeded within the age limit, or has a last success in the future,
-- and ALWAYS one last line "OK|||<n>" (n = how many names the query watches). Healthy = that one line and no other.
WITH w(step) AS (VALUES ('sweep'), ('reconcile'), ('stuck'), ('checkpoint')),   -- four names; add ('audit_reconcile') only after A-01 is applied
p AS (
    SELECT w.step,
           t.last_ok_at,
           t.last_run_at,
           CASE
               WHEN t.step IS NULL THEN 'MISSING (no row: never ran)'
               WHEN t.last_ok_at IS NULL THEN 'NEVER SUCCEEDED'
               WHEN t.last_ok_at > now() + interval '1 minute' THEN 'CLOCK AHEAD (last success is in the future)'
               ELSE 'STALE (last success older than the limit)'
           END AS problem
    FROM w
    LEFT JOIN tick_state t ON t.step = w.step
    WHERE t.step IS NULL
       OR t.last_ok_at IS NULL
       OR t.last_ok_at < now() - make_interval(secs => :limit_s)
       OR t.last_ok_at > now() + interval '1 minute'
)
SELECT step, last_ok_at, last_run_at, problem FROM p
UNION ALL
SELECT 'OK', NULL, NULL, (SELECT count(*) FROM w)::text
ORDER BY 1;
```
Set the values first, as shell variables, so that no placeholder in angle brackets is ever pasted (a pasted `<name>` is a shell redirection that reads or creates a file): `CA=/path/of/the/CA/file; DBHOST=the-host; DBPORT=5432; DBNAME=the-database` (your own values; the database administrator hands them over). Then run (T2), as ONE line; the two settings before `psql` apply to that one command only (see "Connection" below); `${CA:?}` and the other `:?` stop the line while a variable is empty; `-X` means "read no `psqlrc` file" (a `psqlrc` could silence the output) and `-w` means "never ask for a password". The password must already be available to `psql` for this one command (a `PGPASSFILE`, or `PGPASSWORD`, as in the first bullet below): with `-w` and no password source `psql` stops with exit code 2 (`no password supplied`), the same exit code as an unreachable store, so a missing password looks like "cannot connect" (see the alert rule below):
`PGSSLMODE=verify-full PGSSLROOTCERT="${CA:?}" psql -X -w -h "${DBHOST:?}" -p "${DBPORT:?}" -U deadman_reader -d "${DBNAME:?}" -v ON_ERROR_STOP=1 -v limit_s=180 -At -f dead-man-check.sql`
- `DBHOST`, `DBPORT` and `DBNAME`: the same host, port and database name as the store setting of the deployment's config; the database administrator (D3) hands them over.
- Password: never on the command line (a process list shows it), and not as an environment variable if a password file is possible. First choice: a password file (`PGPASSFILE`, permission 600, written by the
  scheduler at job start from the secret `deadman_reader_password` read through the secrets kind (a named lookup), removed by a `trap ... EXIT` line at job end however the job ends, except `kill -9` or a power cut (job script below, NOT RUN); the one line in it has the form `<host>:<port>:<database>:deadman_reader:<password>`); the `psql` manual calls it the safer form. Second choice, only where a password file is
  impossible: the environment variable `PGPASSWORD` set on that single command (a process environment can be read by the same user on some systems). If the client's database supports short-lived tokens or client certificates, use those instead.
- Connection (UNVERIFIED against the real store): the password must not cross the network in clear text. Set `PGSSLMODE=verify-full` and `PGSSLROOTCERT` to the CA file of the database's certificate for that one command, so the check refuses a server it cannot verify. If the database cannot offer TLS (for example a socket on the same machine), the studio head accepts that in writing.
- Alert when the standard output (stdout) is anything other than exactly the one line `OK|||<n>` (n = the number of names the query watches: 4, or 5 after A-01; the query always prints that line, so a silent `psql`, an empty query file or a `psqlrc` that discards the output can never look healthy), OR when `psql` exits non-zero, OR when the "all is well" signal of the job has not arrived for N minutes (section "The job around the query ..."; this third rule is what catches a job that is stopped, deleted or unable to send). Only stdout is watched for lines: `psql` writes errors and notices to the error stream (stderr), so the alert rule must not depend on stderr being empty or non-empty; the exit code carries failures. A database outage also makes `psql` exit non-zero (exit 2), so an outage of the store alarms too; that is wanted. Exit codes of `psql` (its manual): 2 = it could not connect (store unreachable or login refused); 3 = the script failed
  (with `ON_ERROR_STOP`), for example a missing `-v limit_s` or `permission denied`; 1 = another fatal error of `psql` itself.
- The scheduler and the alert are not part of core and no `alert` kind exists in `src` (at `b4cce5b`); the scheduler operator (D6) wires the alert (D4).
The query reads only `step`, `last_ok_at` and `last_run_at`. It does not read `last_error`, so error text can never reach the alert channel.

## The job around the query, and the watching of the job (PROPOSAL written in the eleventh pass; NOT RUN; lead to confirm)
The query alone cannot report its own silence. If the scheduled job is stopped, deleted, moved to another machine, or its mail command is missing, nothing runs and nothing is printed, and silence looks like health. So the job sends an "all is well" signal and something OUTSIDE the scheduler machine alarms when the signal stops.
1. The job (script below) sends the signal ONLY when `psql` exited 0 AND printed exactly the one line `OK|||<n>`. Any other result (including no output at all) sends the alert instead. The script also refuses a query file whose fingerprint differs from the recorded one, and ends the run after 60 seconds.
2. The receiver of the signal alarms when no signal has arrived for N minutes. AUDIT PROPOSAL, lead to confirm: N = 5 when the job runs every minute (about 3 run periods). A mailbox alone cannot alarm about a mail that never comes, so the receiver is one of these options (options first, the client chooses, the choice goes into the quote and the contract): (a) the client's own monitoring tool, if it can alarm on a missing signal (no new data path); (b) a hosted heartbeat monitor with a free tier (a third party that learns only "a signal arrived at time T", no database content; needs the client's written yes; a paid plan needs the studio head's yes with numbers); (c) a second small job on ANOTHER machine that reads the newest signal (a file or a mailbox time) and alarms when it is older than N minutes (our own code; it needs its own scheduler, so it must not run on the same machine). D7 names the choice and N; T2 cannot be completed before D7 is answered.
3. The job checks its own tools first. A missing command ends the job with a non-zero exit and a message on stderr and sends NO signal, so the receiver alarms anyway.
Job script (PROPOSAL, NOT RUN: `bash -n` only; `send_alert`, `send_ok` and `read_deadman_secret` are provided by the scheduler operator, D6, none is named in this folder, and each must be an executable file on the PATH of the job or a shell function defined in the file named by `DEADMAN_LIB`, because the check `command -v` finds nothing else; the `trap` line cannot run after `kill -9` or a power cut):
```
#!/usr/bin/env bash
set -u
umask 077
: "${DBHOST:?}" "${DBPORT:?}" "${DBNAME:?}" "${CA:?}" "${QUERY:?}" "${QUERY_SHA256:?}" "${LIMIT_S:?}" "${NAMES_EXPECTED:?}"      # set by the scheduler's own settings, never written in this file
case "$LIMIT_S" in ''|*[!0-9]*) echo "dead-man job: LIMIT_S is not a plain number" >&2; exit 73 ;; esac
case "$NAMES_EXPECTED" in ''|*[!0-9]*) echo "dead-man job: NAMES_EXPECTED is not a plain number" >&2; exit 73 ;; esac
unset PGPASSWORD PGSERVICE PGSERVICEFILE PGSYSCONFDIR PGOPTIONS PGHOSTADDR PSQLRC      # nothing in the scheduler's environment may change what psql does
PGCONNECT_TIMEOUT=10; export PGCONNECT_TIMEOUT                                           # a connection attempt gives up after 10 seconds
D=$(mktemp -d "${DEADMAN_TMP:-${TMPDIR:-/tmp}}/deadman.XXXXXX") || { echo "dead-man job: mktemp failed" >&2; exit 70; }   # mode 700; set DEADMAN_TMP to a memory-backed folder where there is one
trap 'rm -rf "$D"' EXIT                  # removes the password file and the output files however the job ends, except kill -9 or a power cut (then the 700 folder stays until the next clean-up of that folder)
trap 'exit 143' TERM; trap 'exit 130' INT HUP    # so that the EXIT line above also runs on these signals
[ -z "${DEADMAN_LIB:-}" ] || . "$DEADMAN_LIB"    # optional: a file of the scheduler operator that defines send_alert, send_ok and read_deadman_secret as shell functions (a file the operator controls: nobody else may write it)
for c in psql timeout sha256sum send_alert send_ok read_deadman_secret; do command -v "$c" > /dev/null || { echo "dead-man job: missing command $c" >&2; exit 71; }; done   # no signal is sent in this case; command -v finds executables on PATH and functions defined before this line (macOS has shasum -a 256 instead of sha256sum: use a wrapper)
printf '%s  %s\n' "$QUERY_SHA256" "$QUERY" | sha256sum -c - > /dev/null 2>&1 || { send_alert "dead-man check: the query file differs from its recorded fingerprint" || echo "dead-man job: send_alert failed" >&2; exit 74; }   # an empty, cut or changed query file is refused
PW=$(read_deadman_secret) && [ -n "$PW" ] || { send_alert "dead-man check: cannot read the secret"; exit 72; }
PGPASSFILE="$D/pgpass"; export PGPASSFILE
printf '%s:%s:%s:deadman_reader:%s\n' "$DBHOST" "$DBPORT" "$DBNAME" "$PW" > "$PGPASSFILE"; unset PW     # a colon or backslash inside a value must get a backslash in front (psql manual)
PGSSLMODE=verify-full PGSSLROOTCERT="$CA" timeout 60 psql -X -w -h "$DBHOST" -p "$DBPORT" -U deadman_reader -d "$DBNAME" -v ON_ERROR_STOP=1 -v limit_s="$LIMIT_S" -At -f "$QUERY" > "$D/out" 2> "$D/err"   # -X: no psqlrc file; -w: never ask for a password; timeout: the whole run is cut after 60 seconds (exit 124)
rc=$?
if [ "$rc" -eq 0 ] && [ "$(cat "$D/out")" = "OK|||$NAMES_EXPECTED" ]; then send_ok || { echo "dead-man job: send_ok failed" >&2; exit 76; }
else send_alert "dead-man check: psql exit $rc, $(wc -l < "$D/out" | tr -d ' ') output line(s), expected exactly one line OK|||$NAMES_EXPECTED" || { echo "dead-man job: send_alert failed" >&2; exit 75; }; fi   # the text of "$D/err" is never sent: it can name hosts
```

## The read-only identity (PROPOSAL: the studio head decides; `REVIEW.md` RV-D3 (2) and the identity table row `dead-man reader` under RV-X6.6)

### Which login runs each statement (rights come from the Postgres manual; UNVERIFIED on a real store, see "STATUS OF THE TESTS")
| Statement | It needs | Why (Postgres rule) | Tested? |
|---|---|---|---|
| S1 `CREATE ROLE` | a login with the `CREATEROLE` attribute, or a superuser | creating a role is a right of those attributes; the migrations login does not normally have it. At Postgres 15 and older a login with `CREATEROLE` may also change the password and settings of every non-superuser role, which is wider than at 16 (UNVERIFIED: from the manual, not run); prefer a superuser or the provider's top login there | only as a superuser on a throwaway (S1, S3, S4, S5 seen once); not tested with a plain `CREATEROLE` login |

| S3 `GRANT CONNECT ON DATABASE` | the database-owning login (normally the one that created the database), a superuser, or a login that holds `CONNECT` with the grant option | a grant needs the right to give it | only as a superuser |
| S4 `GRANT USAGE ON SCHEMA public` | the schema-owning login (at Postgres 15 and later the schema `public` belongs to the built-in role `pg_database_owner`, which means the database-owning login), a superuser, or a login with the grant option | same | only as a superuser |
| S5 `GRANT SELECT (...) ON tick_state` | the table-owning login (the migrations login, `store/migrate.py`), a superuser, or a login with the grant option on that column | same | only as a superuser |
| S6, S7, S8 `ALTER ROLE ... SET / CONNECTION LIMIT` | a superuser, or a login with `CREATEROLE` that is allowed to change that role (at Postgres 16 the login that created the role is; at 15 and older every `CREATEROLE` login may change any non-superuser role, UNVERIFIED) | changing another role's settings needs those rights | NOT tested at all (static) |
S3 and S4 change nothing while the group `PUBLIC` still holds `CONNECT` on the database and `USAGE` on the schema `public`, which is the default (UNVERIFIED on the real store); they stay so that the login keeps working if `PUBLIC` is tightened later.
**Plainly:** the only rows tested were run on a throwaway where the login was almost certainly a superuser. What the manual says, not what was seen, is in this table. One sentence decides: a superuser login (or, on a managed database service, the provider's top login) can run all eight statements alone; any other login can run only the statements its right allows in the table above (for S5 the table-owning login), so then two logins are needed. A managed database service may not allow a superuser at all: then the provider's administrator login stands in, and what it may do is the provider's documentation (not read here).

**How the database administrator finds which login to use** (read-only queries; run each as the login you are considering, in `psql`; this was NOT run against a database in any pass):
```
SELECT current_user, rolsuper, rolcreaterole FROM pg_roles WHERE rolname = current_user;      -- S1, S2, S6, S7, S8: rolsuper = t, or rolcreaterole = t
SELECT pg_get_userbyid(datdba) AS database_owner FROM pg_database WHERE datname = current_database();   -- S3
SELECT nspowner::regrole AS schema_owner FROM pg_namespace WHERE nspname = 'public';          -- S4
SELECT tableowner FROM pg_tables WHERE tablename = 'tick_state';                               -- S5 (the table-owning login)
```

**Password procedure (S2), typeable.** Nobody types or sees the secret on the screen, and it is never put in a command line, a chat or a shell history. On the database administrator's machine, in `bash`:

```

F=''; D=$(mktemp -d /dev/shm/deadman.XXXXXX 2>/dev/null) || D=$(mktemp -d)   # a private folder (mode 700, made by mktemp -d) in memory-backed storage where the system has /dev/shm (Linux), otherwise on disk (macOS: say so in your notes)

[ -n "$F" ] && ( set -o pipefail; umask 077; openssl rand -base64 24 | tr -d '\n' > "$F" ) && [ -s "$F" ] || echo "STOP: no secret was written; do not go on"   # the brackets keep `umask 077` (file readable by you only) and `pipefail` (a failed `openssl` counts) inside; `-s` = the file is not empty. 24 random bytes = 32 characters, written to a file, not shown

# shred -u "$F" 2>/dev/null || rm -f "$F"; rmdir "$D"
```
Plain limits of this block (written in the tenth pass from the manuals, the `trap` line added in the eleventh, NOT run): the file lives in a private folder (mode 700) made by `mktemp -d`, in memory-backed storage where the system has `/dev/shm`, and exists at most until the window closes or the last line runs, because of the `trap` line (it does not run after `kill -9`); it is no longer put in the home folder, which may be synchronised or backed up, and the secret still passes through the clipboard, which some systems keep in a history: the block says when not to use it; `shred` and `rm` cannot promise that the bytes are gone on a solid-state disk or a copy-on-write file system, so the real protection is that the secret can be replaced at any time: if the local file was deleted before the secret was stored, or its safety is in doubt, the recovery is to repeat the whole procedure with a new secret (the old one stops working at once). The block needs `bash` (`set -o pipefail`).

`\password` hashes the secret on the client before sending it (with the default `password_encryption = scram-sha-256` of Postgres 14 and later; UNVERIFIED here), so the plain value is not written to the server log by that command. **Where the scheduler stores it: UNANSWERED lead item; it blocks T2, the password procedure (S2) and the negative test below until it is answered.** Which secrets-kind backend the scheduler machine reads `deadman_reader_password` from (a file the scheduler writes, a vault of the client's cloud, an environment of the job) is chosen by the scheduler operator (D6) and is not named anywhere in this folder or in `REVIEW.md`; the lead asks the studio head. ## Rules for where it runs (to keep it independent)
1. It runs as `deadman_reader` only: no other table, no write right (least privilege). The agent and the tick do not hold this login; that nobody holds more than this was asserted by
   the rule, not checked here. Which login the tick itself runs under: the patches do not say; `REVIEW.md` RV-X6 says one runtime login serves agent, tick and approval receiver; whether
   a deployment splits them is decision-table row 5 in `README.md` (the studio head decides).
2. It runs outside the process and outside the scheduler it watches. If it runs on the same machine as the tick, a machine failure silences both; whoever sets it up writes down which failure it
   does and does not cover.
3. Its alert goes over a channel that is not the one the tick or the app uses (D4); this note does not pick one.
4. It alerts on an unreachable store and on any non-zero exit too: a check that cannot read the store has failed, and says so.

5. The check itself is watched: the job sends its "all is well" signal only when the check succeeded, and a receiver outside the scheduler machine (D7) alarms when the signal stops; the negative test below disables the job to prove it.
## What it does not cover
A database outage that turns the audit drain red (`chain.py:244`, the `DELETE`, is not guarded either, so a store that goes away between the write and the delete makes the step raise: this check then reports `STALE`; true for the store, not a dead tick). A tick that runs and succeeds while doing the wrong thing; a slow mail server (the step finishes, the mail is late); a stuck backlog: `audit_reconcile` that drains 0 events because the
audit write path itself is broken records a success, so this check stays green ("green" means the step ran, not that the outbox is empty). The reverse also holds once A-01 is applied
without its per-row guard (`REVIEW.md` row RV-A6): one unreadable outbox row in the chain kind makes the drain raise on every tick, so the step goes RED and this check reports
`NEVER SUCCEEDED` or `STALE` although nothing is lost; the alarm then means "a bad outbox row blocks the drain", not "the tick is dead". The A-01 warning and error log lines are written at
the moment a write fails, but NOTHING reads those lines or alerts on them (no alert kind exists in `src`; a person or a log tool the client sets up would have to), so today they cover
nothing automatically. An audit kind with no `reconcile` method: with the A-01 patch in this folder the step FAILS (its `last_ok_at` stays empty, so this check reports NEVER SUCCEEDED);
an earlier version of the patch skipped quietly and recorded a success, which would have shown green. `K1bAudit` (`k1b/audit_sink.py`) has no `reconcile`, but it is made only by `build_audit` (`k1b/audit_sink.py:59`), whose only caller in `src` is the `k1b` command code (`cli.py:216`, import at `:213`), not by the tick (`app.py:161`).
