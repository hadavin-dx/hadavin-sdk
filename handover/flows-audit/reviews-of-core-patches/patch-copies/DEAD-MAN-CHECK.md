## What it checks
A tick that has stopped (scheduler dead, container gone, store unreachable) writes nothing, so it cannot report its own silence. The check asks the store whether each step has
succeeded recently. Steps that run every tick: `sweep`, `reconcile`, `stuck`, `checkpoint`, and `audit_reconcile` (only after A-01). Steps with their own interval (`purge_evidence`,
`reprobe_sources`) are left out; to add one, use its interval plus a margin as its own age limit.

## The query, in a runnable form
Save it as `dead-man-check.sql` on the machine that runs the scheduler (T1), in a folder only the scheduler's user can write; the job checks the file against the recorded fingerprint before every run. Placeholder rule: `:limit_s` is a `psql` variable, set on the command line
with `-v limit_s=<seconds>`; it must be a plain number (no quotes). Without it `psql` stops with a syntax error and exit code 3, which counts as "cannot check" (rule 4 below). An
unreachable store gives exit code 2. Suggested value (D2, LEAD DECIDES, see the table): 3 times the SLOWEST tick period (a tick runs every 30 to 60 seconds) PLUS the clock skew you allow (recommended 60 seconds), so `240`; if the scheduler runs the tick every 30 seconds
only, `150` is enough. The query names the table together with its schema, `public.tick_state`, so that the search path of the login cannot point it at another table of the same name. The migration file creates it with an unqualified name (`store/migrations/0003_approvals_tick.sql:30`, `CREATE TABLE tick_state`), so it lands in the first schema of the search path of the login that runs the migrations, which is `public` unless the store setting says otherwise (the migration code names the same schema when it grants rights: `store/migrate.py:172-173` reads `current_schema()`; those two lines show the grant, they do not show the creation, so "the creation lands in `public`" is an inference, UNVERIFIED on a real store). If it is in another schema, replace `public.` by that schema in the query, in S5 and its rollback and in check b of the real-store checks.
Column type (read in the twenty-first pass at `b4cce5b`, `store/migrations/0003_approvals_tick.sql:30-35`): `last_run_at` is `TIMESTAMPTZ NOT NULL`, `last_ok_at` is `TIMESTAMPTZ` (an exact moment, with the time zone), so the comparison with `now()` does not depend on the time zone of the session. If a real store holds the column WITHOUT time zone (`timestamp without time zone`), every age would be off by the zone offset (a stopped tick hidden, or an alarm for ever): real-store check 1d reads the type and the age from the store. The job also sets `timezone=UTC` for the session (`PGOPTIONS`), so the times printed in the alert are UTC.
Clock note: `now()` is the database server's clock and `last_ok_at` is written with the clock of the machine that ran the tick; keep both on network time, or a skew of more than the
margin gives false alarms or hides a stop. A `last_ok_at` more than one minute ahead of the database clock is reported as `CLOCK AHEAD` (without that test a tick machine whose clock runs ahead would never look stale); a skew inside that minute is not reported. Effect of a skew on `LIMIT_S`: a tick machine that runs BEHIND by `s` seconds makes every age look `s` seconds older (an alarm comes `s` seconds early); one that runs ahead by less than a minute makes it look younger (a stop is found `s` seconds late). So keep `LIMIT_S` at least 3 tick periods PLUS the largest skew you allow (D2).

```sql
-- One line per tick step that is MISSING from tick_state, never succeeded, has not succeeded within the age limit, or has a last success in the future,
-- and ALWAYS one more line "WATCHED|||<n>" (n = how many names the query watches; the line is sorted in among the others, it is not necessarily the last). It is called WATCHED, not OK, because it is also printed beside problem lines: it says only "this many names were watched". Healthy = that one line and no other.
WITH w(step) AS (VALUES ('sweep'), ('reconcile'), ('stuck'), ('checkpoint')),   -- four names; add ('audit_reconcile') only after A-01 is applied
p AS (
    SELECT w.step,
           t.last_ok_at,
           t.last_run_at,
           CASE
               WHEN t.step IS NULL THEN 'MISSING (no row: never ran)'
               WHEN t.last_ok_at IS NULL THEN 'NEVER SUCCEEDED'
               WHEN t.last_ok_at > now() + interval '1 minute' THEN 'CLOCK AHEAD (last success is in the future)'
               ELSE 'STALE (last success older than the limit)'
           END AS problem
    FROM w
    LEFT JOIN public.tick_state t ON t.step = w.step
    WHERE t.step IS NULL
       OR t.last_ok_at IS NULL
       OR t.last_ok_at < now() - make_interval(secs => :limit_s)
       OR t.last_ok_at > now() + interval '1 minute'
)
SELECT step, last_ok_at, last_run_at, problem FROM p
UNION ALL
SELECT 'WATCHED', NULL, NULL, (SELECT count(*) FROM w)::text
ORDER BY 1;
```

## The job around the query, and the watching of the job (PROPOSAL written in the eleventh pass; NOT RUN; lead to confirm)
The query alone cannot report its own silence. If the scheduled job is stopped, deleted, moved to another machine, or its mail command is missing, nothing runs and nothing is printed, and silence looks like health. So the job sends an "all is well" signal and something OUTSIDE the scheduler machine alarms when the signal stops. **What the signal means, exactly:** when the job ran, the check found every watched step (four, or five after A-01) with a recorded success within `LIMIT_S` seconds. It does NOT mean that the store is healthy, that the audit outbox is empty, or that the tick did the right thing (see "What it does not cover"). The text of the signal carries `LIMIT_S`, `NAMES_EXPECTED`, the short name of the store (`STORE_LABEL`) and the UTC moment the run started (`run_at`), so the receiver can see which limit and how many names the run used, and for which store (the fingerprint covers the query file, not these settings). **The receiver must check the `run_at` of the newest signal against its own clock** and alarm when `run_at` is older than N minutes (a signal that was queued or held up in a mailbox then looks old, not fresh), and it needs ONE entry per `STORE_LABEL`: a second store's signals must not keep the first one quiet. `run_at` comes from the clock of the scheduler machine; keep it on network time (D2).
1. The job (script below) sends the signal ONLY when `psql` exited 0 AND printed exactly the one line `WATCHED|||<n>`. Any other result (including no output at all) sends the alert instead. The script also refuses a query file whose fingerprint differs from the recorded one. **What is bounded in time, exactly:** only the one `psql` program (60 seconds, 65 at the latest: `timeout -k 5`). The programs `send_alert`, `send_ok` and `read_deadman_secret` and the `cp` of the files have no time limit of their own, so the whole job could hang. Therefore the scheduler MUST (a) set a maximum run time for the whole job (proposal: 120 seconds; the scheduler then ends the job, and a folder left in memory is described in fact 2) and (b) never start a second run while one still runs; as a second line of defence the job refuses a second run itself (it holds a lock on the error log; exit 77, no signal, no alert: if a run hangs for good, every later run exits 77, no signal arrives and the receiver alarms). Both are settings of the scheduler (T2), not of the script, and which scheduler is used is UNANSWERED (fact 3).
2. The receiver of the signal alarms when no signal has arrived for N minutes. AUDIT PROPOSAL, lead to confirm: N = 5 when the job runs every minute (5 run periods). Eight facts about the job script that its comments cannot hold (the script was run in the fifteenth, the sixteenth, the eighteenth, the nineteenth and the twentieth pass with FAKE `psql`, `send_ok`, `send_alert` and `read_deadman_secret` stand-ins in a scratch folder; the nineteenth-pass cases are in the paragraph "Negative test" and in `../fix-patchcopies19.md`; the cases of the fifteenth and sixteenth pass: healthy run, failing `psql`, disk folder refused with exit 70, relative error-log path refused with exit 73, hash with file name refused with exit 73; in the sixteenth pass also: a changed query file refused with exit 74, an output of `WATCHED|||4` followed by an empty line refused (alert), a host written as an IPv6 address written correctly into the password file, a hang-up ending with exit 129 and leaving no folder, and no trace of the secret in the output of `bash -x`; no real database, scheduler or alert channel was involved, see "STATUS OF THE TESTS"):
1. **The error text of `psql` is kept, outside the alert.** The text of "$D/err" is the only place where a missing password, a refused login, a wrong host, a certificate problem, an expired password (check 2 below) or `permission denied` is named, and the trap deletes "$D". So the job appends it, with the time and the exit code, to the file named by the scheduler setting `DEADMAN_ERRLOG` (an absolute path outside "$D"). The job opens that file ONCE (file descriptor 9) and checks the OPEN file, not the name: it must be a plain file of the job's user with one hard link (else exit 73), the folder it stands in must belong to the job's user and be writable by nobody else (else exit 73), a link in the name is refused (exit 73), a pipe or a device at that path is refused BEFORE the open (exit 73: opening a pipe with no reader would wait for ever), right after the open the name and the open file must be the same file (`stat` without `-L` on the name against `stat -L` on the open file; a link swapped in before that line gives another number: exit 73; tested in the twentieth pass by moving the file away and putting a new one in its place after the open, and the same run without that check was accepted), the mode is set to 600 on every run, and every later write goes to the same open file, so a link swapped in after the check changes nothing. What remains: the check and the open are not one atomic step, and only the job's user or root can plant a link there (the folder is closed to others). The time of each entry is UTC with a final Z (IST = UTC + 5:30). A hard link, a link, a folder, a file of another user and a folder open to others were each refused with exit 73 in the nineteenth pass (fake data, run as `root`, other owner made with `chown nobody`). The error text can name the host, the user and the database (UNVERIFIED: not run) and is therefore never sent in the alert. Who rotates or deletes that file (it grows by one entry per run that failed or printed an error text) is the scheduler operator's decision (D6), not made here.
2. **The password file is written only to a memory-backed folder (a memory-backed folder can still be swapped out to disk).** The job refuses to run (exit 70, no signal) unless the folder for its temporary files is memory-backed: default `/dev/shm`, or the absolute path named by `DEADMAN_TMP` (a relative one: exit 73), and the test is that GNU `stat -f -c %T` reports `tmpfs` or `ramfs` (tested standalone on Linux: `/dev/shm` accepted, `/tmp` and a missing folder refused; on a machine where `/tmp` is itself memory-backed the job accepts `/tmp`). A `tmpfs` can still be written to swap space; whether the swap is on an encrypted disk is not known here (UNVERIFIED). After `kill -9` or a power cut the private folder stays in memory until the NEXT run, which removes every old folder named `deadman-job.` plus six characters that belongs to its own user and is not a link (it holds the lock at that moment, so no other run of this job uses one; a different job must have its own `DEADMAN_TMP`), or until a reboot. The job script does not run on macOS: it needs `/proc/self/fd`, GNU `stat` and GNU `timeout`. A wrapper function in `DEADMAN_LIB` cannot fix that, because the checks of the programs, of `stat` and of `sha256sum` run BEFORE the library is loaded (the library file is itself checked with `sha256sum`), so an earlier text that suggested `timeout() { gtimeout "$@"; }` in the library was wrong; a port to macOS would be a new design and nobody has made it (UNVERIFIED).
3. **Where the scheduler keeps the standard error of the job is NOT KNOWN here** (UNANSWERED, open question for the lead, who asks the studio head): the messages of the exits 70 to 77 (a missing command, a malformed setting, a failed `send_alert`, a lock that is held) are written to the standard error, and which scheduler is used, whether it keeps that text, for how long and who reads it is not written anywhere in this folder or in `REVIEW.md`. Until it is answered, treat the exits 70, 71, 73, 76 and 77 and the signal exits 129 to 143 as visible only by the missing signal (the receiver alarms), not by their text. The exits 72 and 74 first try an alert (visible by the alert text when `send_alert` works); exit 75 means that alert failed.
4. **After an alert that was sent successfully, the job itself ends with exit 0.** The job's own exit code therefore says "the job ran and the alert went out", not "the store is healthy": a scheduler that shows only exit codes shows a green job on an unhealthy store. The alarm is the alert message (and the missing "all is well" signal), not the scheduler's colour. Exit 75 or 76 means the alert or the signal could not be sent. Exit 0 after an alert means only that `send_alert` RETURNED 0: whether the message arrived depends on the operator's command (D4: a local mail command returns 0 when the mail is only queued on the scheduler machine), so the proof that an alert arrives is the negative test, not the exit code.
5. **What "exactly one line" means.** The job sends the "all is well" signal only when `psql` exited 0, the output equals `WATCHED|||<n>` and it has exactly one line (`wc -l` counts one newline). The comparison with the output text ignores trailing empty lines (the shell strips them), which is why the line count is tested too. A signal (stop, interrupt, hang-up) sent to the job while a program of the job runs takes effect after that program ends (`psql`: at most 65 seconds later; `send_alert`, `send_ok` and `read_deadman_secret` have no limit, see item 1 of the list above and fact 6); a hang-up ends the job with exit 129, not 130 (run in the nineteenth pass: hang-up during a slow fake `psql`, exit 129, no folder left in `/dev/shm`). The traps are set before the private folder is made, so a signal before the folder exists changes nothing. A signal that arrives between the creation of the folder and the assignment of its name to `D` could leave the folder behind (UNVERIFIED how bash orders that); the next run removes it (fact 2). A hang-up ends the job with 129 only when it was not ignored when the job started: a job started with `nohup`, or in the background by some schedulers, ignores it and the script cannot catch it (UNVERIFIED). The signals QUIT, PIPE and ALRM are caught too and end the job with 131, 141 and 142.

6. **No two runs at once, and the time of the whole job.** The job takes a lock on the open error log (`flock -n`); a second run that starts while the first still holds it ends at once with exit 77, sends nothing and writes one line on stderr. The scheduler must still set a maximum run time for the whole job and refuse overlapping starts itself (item 1 of the list above): the script bounds only `psql`. If the scheduler ends the job with the kill signal, the `trap` cannot run and the 700 folder with the password file stays in memory until the next run removes it (see fact 2) or until a reboot. The lock belongs to the open error log: the job closes descriptor 9 for `psql` and for the three commands, so a program that one of them leaves in the background does not keep the lock (tested in the twentieth pass with a fake `send_ok` that starts a background `sleep`: the next run was accepted; the same script without `9>&-` ended the next run with exit 77, as the reviewer said). The short programs `cp`, `stat`, `chmod`, `date`, `cat` and `sha256sum` still inherit the descriptor; a hang in one of them is bounded only by the scheduler's maximum run time. The exit 77 is given for every failure of `flock -n`, not only for a held lock (util-linux exit codes UNVERIFIED). (Tested with a lock held by another process: exit 77.)
7. **Repeated alerts.** The job keeps no memory of an alert it sent: with one run per minute an unhealthy store sends one alert per minute. A repeat interval or de-duplication belongs to the alert channel or the receiver (D4, D7), whose tool is not chosen yet (UNANSWERED: needs the studio head and the scheduler operator); nothing is built here, so the first alert channel must be able to merge repeats, or the scheduler operator sets a longer run interval for the alert (the signal still needs its own interval).
8. **The environment of the job is the trust root.** The scheduler decides the environment and the `PATH` of the job; the job script cannot make a hostile environment safe. What it does in its first lines (all tested in the twentieth pass with fake programs): it switches off an inherited `errexit` (`SHELLOPTS=errexit` would end the script at the first failing `psql` with no alert: seen with the line removed, exit 1), `allexport`, `xtrace` and `noclobber`; it removes every shell function that came in through the environment (a forged `sha256sum` function made a changed query file pass with exit 0 when that line was removed, and was ignored with it); and it removes every exported variable that starts with `PG` or `PSQL` and `LD_PRELOAD`, `LD_AUDIT`, `OPENSSL_CONF`, `OPENSSL_MODULES`, `OPENSSL_ENGINES`, `BASH_ENV`, `ENV`, `SSL_CERT_FILE` and `SSL_CERT_DIR` after the programs `id`, `stat`, `chmod` and `flock` have run and before `psql` and the three commands start (those four programs run first, because the `PATH` folders are checked first). It cannot undo what happened before its first line: a file named by `BASH_ENV` has already run, and `LD_PRELOAD` has already been loaded into `bash` itself. Therefore the scheduler MUST start the job with a clean environment (for example `env -i` with exactly the settings of the table below and a `PATH` of folders that only the job's user and root can write), and the exact-output test and the exit code of `psql` catch a wrong or silent `psql`, not a hostile environment. Twenty-first pass additions: `psql` gets its connection timeout and the password file as a prefix of its own command (they are no longer exported to the rest of the job), the password file is removed right after `psql` ends, every exported variable whose name holds PASSWORD, PASSWD, SECRET, TOKEN or CREDENTIAL is removed for `psql` only (the job reads the secret ONLY through `read_deadman_secret`; an environment variable is NOT a storage place for it: the same user can read the environment of a running process on Linux, `/proc/<pid>/environ`), every open descriptor other than 0, 1, 2 and 9 is closed, every `PATH` folder must belong to root or the job's user and not be writable by group or others, `CA` must be a readable plain file, `DEADMAN_TMP` must be a safe folder, and the error log is emptied above 10 MB. A full disk makes the write of the error log fail with one line on stderr (see fact 3: visible only by the missing signal). The log's owner is the job's user (checked on the open file). "Tested" here means: run as `root`, with fake programs, in a scratch folder; the refusals that depend on the owner and the mode (the `PATH` folders, `DEADMAN_TMP`, the error-log folder) were NOT shown with a second, ordinary user: UNVERIFIED.
The job also asks the server, through `PGOPTIONS`, for a 5 second statement limit and a read-only session, so these hold even where the role settings S6 and S8 could not be made (UNVERIFIED against a real server; a connection pooler may refuse the option, then the job alarms and the database administrator decides).

## Rules for where it runs (to keep it independent)
1. It runs as `deadman_reader` only: no other table, no write right (least privilege). The agent and the tick do not hold this login; that nobody holds more than this was asserted by
   the rule, not checked here. Which login the tick itself runs under: the patches do not say; `REVIEW.md` RV-X6 says one runtime login serves agent, tick and approval receiver; whether
   a deployment splits them is decision-table row 5 in `README.md` (the studio head decides).
2. It runs outside the process and outside the scheduler it watches. If it runs on the same machine as the tick, a machine failure silences both; whoever sets it up writes down which failure it
   does and does not cover.
3. Its alert goes over a channel that is not the one the tick or the app uses (D4); this note does not pick one.
4. It alerts on an unreachable store and on any non-zero exit of `psql` too: a check that cannot read the store has failed, and says so. The job's OWN exit codes 1, 70, 71, 73, 75, 76 and 77 send no alert (exit table above); they are caught only by the missing "all is well" signal (rule 5).

5. The check itself is watched: the job sends its "all is well" signal only when the check succeeded (every watched step recent: not "all is well" in a wider sense), and a receiver outside the scheduler machine (D7) alarms when the signal stops; the negative test below disables the job to prove it.
## What it does not cover
Two different outages must not be mixed up: an outage while THIS check runs makes `psql` exit 2 and the job alerts (rule 4 above); an outage of the store between the audit write and the delete inside the tick makes the step raise, and this check then reports `STALE` for that step. A tick that runs and succeeds while doing the wrong thing; a slow mail server (the step finishes, the mail is late); a stuck backlog: `audit_reconcile` that drains 0 events because the
audit write path itself is broken records a success, so this check stays green ("green" means the step ran, not that the outbox is empty). The reverse also holds once A-01 is applied
without its per-row guard (`REVIEW.md` row RV-A6): one unreadable outbox row in the chain kind makes the drain raise on every tick, so the step goes RED and this check reports
`NEVER SUCCEEDED` or `STALE` although nothing is lost; the alarm then means "a bad outbox row blocks the drain", not "the tick is dead". The A-01 warning and error log lines are written at
the moment a write fails, but NOTHING reads those lines or alerts on them (no alert kind exists in `src`; a person or a log tool the client sets up would have to), so today they cover
nothing automatically. An audit kind with no `reconcile` method: with the A-01 patch in this folder the step FAILS (its `last_ok_at` stays empty, so this check reports NEVER SUCCEEDED);
an earlier version of the patch skipped quietly and recorded a success, which would have shown green. `K1bAudit` (`k1b/audit_sink.py`) has no `reconcile`, but it is made only by `build_audit` (`k1b/audit_sink.py:59`), whose only caller in `src` is the `k1b` command code (`cli.py:216`, import at `:213`), not by the tick (`app.py:161`).
