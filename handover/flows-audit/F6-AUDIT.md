# F6-AUDIT: the mf-hook entry (the e-mail-style webhook door), static audit

Date: 2026-11-16. Static read only. Nothing was run in n8n, Postgres, HubSpot or SMTP, so every n8n behaviour below is UNVERIFIED until a laptop test. Severity rubric: FINDINGS.md line 27 (severity = what happens in the filmed take; not reachable in the take = Nit, and the row says "a Major for a client build" where it would be one). ## 1. Area and why chosen

Area: the mf-hook door (`n8n-flows-real-v5/mf-hook.json`, same in `n8n-flows-film-v5`; built by `n8n-mainframe/build_mainframe.py:77-95`, called at :121), meaning its input field names, its reply contract, what a hung or failing sub-workflow does to the caller, and what a repeated key does.

Why chosen: (a) no FINDINGS row, lane or lanes13 file checks the hook door's own field names; rows F-009, F-036, F-017, F-010 and F-002 cover it only as "same as mf-form" (auth, copy, credential, empty key). (b) The run sheet and SCENE-FLOW-MAP name only the form door in scenes; `grep mf-hook` in VIDEO-RUNSHEET.md finds nothing. (c) The only tests that post to mf-hook are the generic loop at `mf.py:121`; the kill cases (K1-K5), the review case (mf.py:125) and the repeat case (mf.py:134) use mf-form only. So the hook door ships in the take folder but is the least exercised door.

Already covered, not repeated here: no authentication, size or rate limit (F-009, F-036); mf-form and mf-hook are copies (F-017); one shared Postgres and SMTP credential (F-010); empty lead_key and a bare 500 when Claim fails (F-002); placeholder ids (F-029); a review-state lead is never alerted (F-031).

Checked and found fine (static): Receive uses `responseMode: responseNode` and both replies (ReplyRan/ReplyReview/ReplyStored) are reached on every branch of the door graph (every IF has both outputs wired, mf-hook.json connections); `Claim` is idempotent (`ON CONFLICT DO NOTHING`), so a resend with the same key cannot make two rows or two mails; `Claimed`'s notEmpty check on `lead_key` correctly routes a conflict (zero rows, one empty item) to `Stored`; `ReplyRan` reads `lead_key` and `outcome` that all four sub-workflow end nodes (OutDone, OutUnknown, OutStage, OutLost) set; the door has no secret literal (credential names only, ids are placeholders); the door's Postgres nodes only INSERT and SELECT (the door itself needs no UPDATE right, which makes the F-010 split cheap: build_mainframe.py:19 `pg()` applies one credential to all 14 Postgres nodes in the four flows). Film-v5 and real-v5 door files are identical for these nodes (compared node by node).
