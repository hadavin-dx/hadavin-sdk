## N7-1 No dead-man alert (nothing tells a person that the sweep, n8n or Postgres has stopped)
- **severity:** Major. Why: a lead stays in state processing and nobody is told, but the row is kept, so it is not lost and not doubled (Blocker needs lost or doubled). For a client build this would be a Blocker (a lead nobody looks at is effectively lost).
- **class:** ops (single point of silence). Not an extension of an existing finding: F-008 covers swallowed errors inside the sweep, F-030 covers the shared mail server; neither says "the sweep itself stops".
- **take:** yes. The take stops and restarts n8n by hand (PLAN-4-NLITE-FROM-LEAD.md:95) and claims recovery (VIDEO-RUNSHEET.md:33). If the recovery flow is not active after the restart, nothing is shown and nothing is sent.
- **where:** n8n-flows-real-v5/mf-recovery.json:15 (Every30s, the only timer), :29 ClaimStuck, :105 MarkFailed, :127 AlertClaim (all three `onError: continueRegularOutput`; the first three `onError` lines in the file are 43 ClaimStuck, 97 RunSub, 119 MarkFailed, AlertClaim's is further down: not line-checked); build_mainframe.py:97-117.
- **evidence:** the only alert source is the sweep itself: AlertClaim reads `state IN ('unknown','failed')` (mf-recovery.json:127). If the timer does not fire, ClaimStuck, MarkFailed and AlertClaim never run, so no row is moved out of `processing` and no alert is created. If Postgres is down, those three nodes fail and the error is swallowed (continueRegularOutput). N8N-START.md:33-35 states the recovery flow "must be ACTIVE (n8n logs 'not active and cannot be executed' otherwise)": the only trace is a log line. Nothing in FIX-PLAN item 4 (take-day gate, F-029) checks that the recovery flow is active. Test T14 (mf.py:321) checks that an idle sweep does nothing, not that a stopped sweep is noticed.
- **three cases, what a person sees today:**
  1. Recovery flow inactive, n8n up: webhooks still accept leads; leads that need a retry stay in `processing` forever. Silent.
  2. n8n down: no webhook answers; the sender's own resend loop (1 post + 3 resends, 5 s gap, PLAN-4:94) gives up. The leads never reach the table. Silent unless the sender reports it.
  3. Postgres down: Claim fails (bare 500, F-002); the three sweep nodes fail silently. Silent.
- **proposed fix, RUNG: config (host cron + one SQL read) plus an external ping or second mail route; no new flow code.**
  - A watchdog outside n8n and outside the n8n mail route, run every 5 minutes by the host (cron or a systemd timer). It runs one read-only query: `SELECT count(*) FROM mf_leads WHERE (state='processing' AND claimed_until < now() - interval '3 minutes') OR (state IN ('unknown','failed') AND alert_sent=false AND created_at < now() - interval '15 minutes');` and, if the answer is above 0 OR the query itself fails, sends a message by a second route (not the n8n SMTP credential, otherwise F-030 is repeated). Second route is the client's choice (options-first): self-hosted ping monitor (default), a free-tier monitor service, or a plain mail from the host. The ping carries no lead data (count only).
  - Least privilege: the watchdog gets its own read-only Postgres user with SELECT on four columns of mf_leads (lead_key not needed; state, claimed_until, alert_sent, created_at). No new table, so no second store.
  - Extra for n8n-down (case 2): also have the watchdog call the n8n health address (loopback) and alert on no answer.
- **test:** (a) deactivate the recovery flow, start a lead with the CRM held (K1 style), expect the watchdog to fire within about 8 minutes; (b) healthy idle stack for 10 minutes: expect zero messages (T14 style); (c) stop Postgres for 2 minutes: expect one message; (d) the watchdog's own user is refused an UPDATE (negative test).
- **UNVERIFIED:** how the n8n schedule behaves when a run is still going at the next tick; whether n8n re-activates the recovery flow after a hard kill (my recollection: yes, active state is stored in n8n's database, but this is not in any file).

So the only brake on cost is the spend cap in the stage and HubSpot's own limits (UNVERIFIED).
- **what one fresh request with a junk key causes:** with the real stage (plan only) the stage answers 400 bad_key, Qualify retries once (retryOnFail, maxTries 2, mf-sub-crm-mail.json Qualify settings) and goes to OutStage; the lead is retried by the sweep up to 3 times and ends `failed`, then one **alert mail to the owner per junk key** (AlertClaim, at most 5 per 30 s sweep, about 10 a minute). With the stand-in stage a junk key without `lead_key` gives a 500 handler error, same path. So junk keys flood the table and the owner's mailbox even though no model call is made. A valid-looking e-mail with an invalid shape still creates a row (an invalid e-mail creates a `review` row too, Claim CASE, build_mainframe.py:82).

- **proposed fix:** rungs split.

  2. **n8n node:** header-auth credential on Receive (F-009; owner decision on the secret); an IF node KeyOk before Claim with the exact expression `/^L[0-9a-f]{16}$/.test($json.lead_key)` plus `email.length <= 254` and `name.length <= 200`, answering 422 (ORDER 007 item 1 already asks for the shape check and length cap in the F-002 patch: this finding supplies the reason, the values and the test).
  3. **config:** alert cap (N7-6) so a flood cannot become a mail flood.
- **test:** post 200 junk keys: expect 200 replies 422, 0 rows, 0 stage requests (read `/stats`, stage_server.py:32), 0 mails; post one body of 20 MB: expect refusal before the flow; post 5 fresh valid keys with the spend cap set to 2: expect exactly 2 model calls, 3 failed leads, then the alert cap holds; without the auth header: expect 401/403.
- **UNVERIFIED:** n8n payload default and what n8n answers to an oversized body; the real stage's checks (plan only); HubSpot rate limits.

## N7-5 MarkDone, MarkUnknownA, MarkUnknownB, MailClaim, SetCrmId have no onError
- **severity:** Major. Why: wrong failure path (no onError, no error workflow, F-008): the database error is visible only as a failed run in n8n's run list; the lead may end `unknown` although its mail was delivered, and a person is told "may or may not have been sent" without knowing a database error is the cause. By static reading no path sends a second mail and none loses a lead without a state and an alert (so not Blocker). Extends F-008 (which names six swallowing nodes, not these five that do the opposite: they stop the run).
- **class:** ops.
- **take:** yes (all five are in mf-sub-crm-mail.json, used by the take).
- **where:** n8n-flows-real-v5/mf-sub-crm-mail.json:120 SetCrmId, :207 MailClaim, :289 MarkDone, :312 MarkUnknownA, :335 MarkUnknownB. In the JSON each has only `alwaysOutputData: true`; no `onError` key (parsed: onError appears only on Qualify, CrmUpsert, SendMail). That setting only makes an empty result produce one item; it does nothing for a database error.
- **default behaviour (UNVERIFIED, n8n):** with no onError a failing node stops the run with an error; the sub-workflow run fails; in mf-form/mf-hook `RunSub` has no onError either (mf-form.json:227), so the entry run fails and the webhook, which waits for a Respond node (`responseMode: responseNode`), gets n8n's own error answer (probably a bare 500, as F-002 says for Claim). The sender then resends the same key (PLAN-4:94): Claim sees the key (ON CONFLICT DO NOTHING), Stored reads the state, ReplyStored answers verdict `processing` with `repeat: true` (mf-form.json ReplyStored), so the sender stops resending. In the sweep, `RunSub` has `continueRegularOutput` (mf-recovery.json:90), so the error is swallowed there.
- **the exact order:** SetCrmId (stores crm_id) -> CrmIdOk -> OwnsClaim1 -> **MailClaim** (sets `mail_sent=true` only if still `false`, same claim token and state processing, commits before any mail) -> MailRowBack (a row came back?) -> **SendMail** (retry OFF; the only node that sends the thank-you mail) -> **MarkDone** (state done) on success, or MarkUnknownA on an SMTP error. If MailRowBack finds no row (mail_sent already true, or the lead was taken over) -> MarkUnknownB. (build_mainframe.py:46-73; MailClaim query :54, MarkDone :57.)
- **recovery sweep conditions (ClaimStuck, mf-recovery.json:29):** takes rows with `state NOT IN ('done','review','unknown','failed') AND claimed_until < now() AND attempts < 3`, at most 5, gives a new claim token and a new 45 s lease, attempts + 1. MarkFailed (:105): rows past the lease with attempts >= 3 become `unknown` if `mail_sent`, else `failed`. AlertClaim then picks `unknown` and `failed`.
- **table, one row per node: what a database failure there does (database error before the statement commits, or the answer lost after it commits; both shown where they differ):**
  | node fails | mail double-sent? | mail lost? | what the sweep does next | what a person sees |
  |---|---|---|---|---|
  | SetCrmId | no (mail not reached) | no | after the lease (45 s) ClaimStuck re-runs: Qualify returns the stored label (stage journal), HubSpot upsert runs again (keyed on e-mail, so the same contact), SetCrmId retried, mail then sent once | nothing; a second HubSpot write; if the database stays down for 3 attempts: `failed` + 1 alert |
  | MailClaim, error before commit | no | no | re-run sends the mail normally | nothing |
  | MailClaim, answer lost AFTER commit (`mail_sent=true`, no SendMail ran) | no | **yes, not sent**, but flagged | re-run: MailClaim finds `mail_sent=true`, returns no row, MailRowBack false, MarkUnknownB -> `unknown` -> 1 alert "may or may not have been sent" | an alert; the mail truly was NOT sent. Same safe path as test K3B (RUN-ON-LAPTOP.md:8) |
  | MarkDone | no (MailClaim already set `mail_sent=true`, so a re-run cannot send again) | no (the mail was delivered) | re-run: MailClaim returns no row -> MarkUnknownB -> `unknown` -> 1 alert | an alert saying "unknown" for a mail that was delivered. Same as test K3 (RUN-ON-LAPTOP.md:8). Noise, not damage |
  | MarkUnknownA (after an SMTP error) | no | possibly (SMTP error may mean not sent) | state stays `processing` with `mail_sent=true`; re-run -> MailClaim no row -> MarkUnknownB -> `unknown` + alert | an alert (the intended result, one pass later) |
  | MarkUnknownB | no | n/a | re-run reaches MarkUnknownB again; after attempts >= 3, MarkFailed sets `unknown` (mail_sent is true) | an alert after about 3 leases + sweeps (about 3 minutes) |
  If the database stays down, the sweep nodes also fail silently (swallowed), so nothing resolves until it is back: see N7-1.
- **mail double-send check:** I found no path. The guard is that `mail_sent=true` is committed by MailClaim before SendMail and is never reset; MailClaim runs only while `mail_sent=false`. The remaining double-send risk is outside these five nodes: SendMail has retry off (build settings `retryOnFail: False`), so n8n itself will not repeat it. A lease that expires while SendMail is still waiting (the SMTP transport may wait minutes, comment at build_mainframe.py:11) lets the sweep take the lead over: then the old run's MarkDone has the old token and returns no row (-> OutLost) and the re-run ends `unknown` via MarkUnknownB: one mail, state unknown, one alert (matches F-012 area).
- **what is missing, plainly:** no error workflow (F-008) and no onError on these five, so a database error produces no alert of its own; the person learns of it only through a lead going `unknown` or `failed` a few minutes later, and then the alert does not say "database error".
- **proposed fix, RUNG: n8n node (settings).** (1) Add one error workflow (Error Trigger -> one mail with workflow name and lead_key only, no payload; or a call to the dead-man route of N7-1) and set it in every flow's `errorWorkflow` (F-008). (2) Do NOT add `continueRegularOutput` to these five: swallowing would turn a database error into a wrong success. The default "stop the run" is the safe one here. (3) For SetCrmId, move it after CrmIdOk (F-016) so a failure there does not hide a CRM refusal.
- **test:** for each of the five nodes, make Postgres refuse the statement once (a trigger that raises an error on the matching UPDATE, one-shot) and run one lead; expect per node the outcome in the table above (mail count 0 or 1, never 2; state; alert count 1 for the unknown rows); plus T13/K5 style Postgres kill between MailClaim and SendMail (not run by anyone yet: REPORT.md:5 and :40 say K5 and T13 NOT RUN by the demo session).
- **UNVERIFIED:** every n8n behaviour above (stop-the-run default, what the webhook answers, whether an error in a sub-workflow reaches the parent as an error); the sender's behaviour with the `processing` verdict.
