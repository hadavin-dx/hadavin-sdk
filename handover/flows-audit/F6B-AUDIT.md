# F6B-AUDIT: the recovery workflow and the lead table, static architecture audit

## Summary (plain words)

1. Audited: the recovery flow (it wakes every 30 s, retries stuck leads, marks leads that ran out of tries, and mails an alert), in `n8n-flows-real-v5` and `n8n-flows-film-v5`, plus the lead table (`mf_leads`), its generator and its tests.
2. Nothing was run. Every statement about how n8n or Postgres behaves is UNVERIFIED until a laptop test. The SQL and node settings were read, not executed.
3. The retry and alert logic itself holds up on paper: all times come from the database clock, two ticks cannot take the same lead or alert twice, and the mail step cannot run twice. The weak spots are around it: what a person is told, what happens after an alert, and what happens when two sets or old rows share the table.
4. Counts: 12 rows, 0 Blocker, 0 Major for the take, 7 Major for a client build (marked Nit*). Before the take only two things are worth doing: check or empty the table between scene 4 and scene 5 (F6B-01, F6B-02), and say in the run sheet that "A person decides" has no follow-up step yet (F6B-03, F6B-05).

Ratings follow FINDINGS.md (severity = what happens in the filmed take; not reachable in the take = Nit; "Nit*" = would be a Major for a client build). F6-AUDIT.md used the same style.

## Words used in this file

- recovery tick = one wake-up of the recovery flow (every 30 s). It runs three separate jobs: ClaimStuck (retry), MarkFailed (give up), AlertClaim (alert).
- lease = the time (45 s in the built flows) one run holds a lead before recovery may take it over. attempts = how many runs a lead has had (the first run counts 1; recovery gives up when it reaches 3).
- states: processing (being worked on), done, review (parked, bad e-mail address), unknown (mail may or may not have gone out), failed (could not be finished). `new` is allowed by the table but no flow ever writes it.
- alert = the mail to the owner's alert address. alert_sent = true only after the mail was accepted by the mail server (it does not mean anyone read it).
- take = the filmed recording. Scenes 1 to 4 use real-v5, scenes 5 to 11 use film-v5 (SCENE-FLOW-MAP.md). C1 = the point "switching sets" in SCENE-FLOW-MAP.md line 66.
- "sender" = whatever posts a lead to the entry address; the planned real sender is not in this repository (F6-02).

Date: 2026-11-16. Files read: `n8n-flows-real-v5/mf-recovery.json`, `n8n-flows-film-v5/mf-recovery.json` (they differ only in the two AlertSend address lines 177-178: real = placeholder sender and `$env.DESK_ALERT_TO`, film = constants), `n8n-flows-v4/mf_leads.sql` (the table with alert columns; the file `n8n-flows/mf_leads.sql` still lacks them, F-001), `n8n-mainframe/build_mainframe.py`, `n8n-mainframe/mf.py`. Both v5 recovery files are built with `MF_V4=1`: alert claim window 720 s plus the AlertBackoff node (V5-README.md:8-9).

Not repeated here (already in FINDINGS.md or F6-AUDIT.md): lease shared by up to 5 leads (F-012), alert loop with no cap and swallowed AlertMark error (F-014), review state never alerted (F-031), no dead-man alert if the sweep stops (F-035), six recovery nodes swallow errors and no error workflow (F-008, F-044), one table definition in four places (F-001), name and e-mail kept with no expiry (F-032), alert and lead mail share one mail server (F-030), five sub-workflow database nodes with no onError (F-039), placeholders and `$env` (F-029, F-037, F-018), wording of "A person decides" (RUNSHEET-WORDING N-1), entry door findings (F6-01 to F6-07).

## Checked and found fine (static, nothing run)

- Clock: every lease, window and backoff is computed inside the SQL with the database's `now()` (`build_mainframe.py:98,104,110`; json grep: `now()` only, no `$now`, no `Date` expression in any recovery node). There is no comparison between the n8n computer's clock and the database clock, so a clock difference between them cannot make a lease end early or late. The only n8n clock use is the timer itself. `now()` is the start of the statement's transaction; each query here is one statement, so it is the real time within milliseconds. Test drivers measure with their own clock (`mf.py`, `time.time()`), which only affects the reported seconds.
- Two ticks at once: see F6B-08 (SQL side). `MarkFailed` and `ClaimStuck` cannot both take one row (attempts 3 or more vs below 3). A lead already claimed by tick A is skipped by tick B for 45 s. The mail step is guarded by `claim_token` and `mail_sent`, so a second run of the same lead cannot send a second lead mail (MailClaim `build_mainframe.py:54`); T10 and T11 cover this on the test build.
- Alerts are at-least-once with a token: a second alert for one lead can only come if the first mark failed or the send ran past the 720 s window; no path loses a lead's alert while the table is intact and the sweep runs (F-014, F-035 cover the rest).
- The three jobs touch different columns: recovery needs UPDATE on `mf_leads` only; it does not insert (F-010 covers the single credential).
