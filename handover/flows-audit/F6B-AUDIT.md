# F6B-AUDIT: the recovery workflow and the lead table, static architecture audit

## Do this before the take (4 actions)

1. **Between scene 4 and scene 5, check the lead table and empty it.** Run `SELECT state, count(*) FROM mf_leads GROUP BY state;` (it counts leads per state). It must show only `done`. Then, with made-up data only, run `TRUNCATE mf_leads;` (it deletes every row). Do the same before each re-take (F6B-01, F6B-02).
2. **Keep exactly one recovery workflow switched on.** Between scene 4 and scene 5 switch off the real-set recovery workflow and switch on the film-set one, never both. If both are on, a lead from scenes 2 to 4 can be finished against the stand-in CRM (the fake CRM used in scenes 5 to 11) with no error shown (F6B-01).
3. **Plan for scenes 6 to 8 and for re-takes.** Scenes 6 to 8 create `unknown` leads; the recovery flow alerts each one within about 30 s, so alert mails for scenes 6 to 8 can land before scene 9 and scene 9 may show several (F6B-13). On a re-take, reused lead keys return the stored reply and scene 2 shows no CRM write or mail (F6B-14); empty the table first. Switch off any older recovery flow with the same title (F6B-15).
4. **Say in the run sheet that the alert text "A person decides" has no follow-up step yet.** No document says what the person does next or how to restart the lead (F6B-03, F6B-05). Until that is written, do not tell viewers the person has a next step.

## Summary (plain words)

1. Audited: the recovery flow (it wakes every 30 s, retries stuck leads, marks leads that ran out of tries, and mails an alert) in `n8n-flows-real-v5` and `n8n-flows-film-v5`, plus the lead table (`mf_leads`), its generator and its tests.
2. The retry and alert logic itself looks sound on paper: all times come from the database clock, I found no path that lets two ticks take the same lead or alert at the same time, and I found no path that sends the lead mail twice. An alert mail CAN come twice (if the AlertMark write fails, or a send takes longer than the 720 s window; F-014, AF2, F6B-17), so "alert at most once" is not claimed. The weak spots are around it: what a person is told, what happens after an alert, and what happens when two sets or old rows share the table.
3. Counts: 17 rows. Take: 0 Blocker, 3 Major (F6B-01, F6B-02, F6B-13; F6B-15 Major if an old recovery flow is left active), 1 Nit that may be Major (F6B-08), the rest Nit (F6B-14 is Major if the take re-uses lead keys). Client build: 2 Blocker (F6B-01, F6B-03), the rest Major or Nit; see each row. Nit* is no longer used as a rating; each row gives take and client-build ratings.
4. Before the take only the four actions above are worth doing.

- **recovery flow** = the n8n workflow that wakes every 30 s (one wake-up = one **recovery tick**) and runs three jobs: **ClaimStuck** (take a stuck lead and retry it; "claim" = write my own token and a time limit on the row so nobody else takes it), **MarkFailed** (give up on a lead that has used all its tries) and **AlertClaim** (take a lead whose alert is due, then send the mail).
- **door** = the web address where a lead enters (the form or hook flow). **sender** = whatever posts a lead to the door; the planned real sender is not in this repository (F6-02).
- **lease** = the time (45 s in the built flows) one run holds a lead before recovery may take it over. **attempts** = how many runs a lead has had (the first run counts 1; recovery gives up when it reaches 3).
- **states**: `processing` (being worked on), `done`, `review` (parked, bad e-mail address), `unknown` (the lead mail may or may not have gone out), `failed` (could not be finished). `new` is allowed by the table but no flow ever writes it.
- **alert** = the mail to the owner's alert address. `alert_sent` = true only after the mail server accepted the mail (it does not mean anyone read it). **[demo]** = a prefix typed at the start of the alert subject.
- **Ratings** follow FINDINGS.md: Blocker/Major/Nit = what happens in the filmed take; not reachable in the take = Nit; **Nit*** = old shorthand from earlier versions, no longer used: each row now gives a take rating and a client-build rating.

## Read and found no problem (static read only, nothing run)

- Clock: every lease, window and backoff is computed inside the SQL with the database's `now()` (`build_mainframe.py:98,104,110`; json grep: `now()` only, no `$now`, no `Date` expression in any recovery node). There is no comparison between the n8n computer's clock and the database clock, so I found no path by which a clock difference between them makes a lease end early or late. The n8n clock is used for the timer and for run durations (timeouts, waits), so how long a run lasts against the 45 s lease is measured on the n8n side, not by the database. `now()` is the start of the statement's transaction; each query here is one statement, so it is the real time within milliseconds. Test drivers measure with their own clock (`mf.py`, `time.time()`), which only affects the reported seconds.
- Two ticks at once: see F6B-08 (SQL side). I found no path where `MarkFailed` and `ClaimStuck` both take one row (attempts 3 or more vs below 3). A lead already claimed by tick A is skipped by tick B for 45 s. The mail step is guarded by `claim_token` and `mail_sent`, so I found no path that sends a second lead mail for the same lead (MailClaim `build_mainframe.py:54`); T10 and T11 cover this on the test build.
- Alerts are at-least-once with a token (so a repeated alert is possible, as the summary says): a second alert for one lead comes if the first mark failed or the send ran past the 720 s window; no path loses a lead's alert while the table is intact and the sweep runs (F-014, F-035 cover the rest).
- The three jobs touch different columns: recovery needs UPDATE on `mf_leads` only; it does not insert (F-010 covers the single credential).
