**This is version 3 of the audit (the first was written, then changed after two checks: a reader check of wording and a design review; this version answers a second reader check and a facts check). Every statement is from reading files; nothing was run.**

## Words you need first (full list further down)

- **take** = the filmed recording. It has 11 numbered **scenes** (`VIDEO-RUNSHEET.md`). Scenes 1 to 4 use the **real set** of flow files (real HubSpot CRM, a real mail address). Scenes 5 to 11 use the **film set** (a **stand-in CRM** = a fake CRM made only for filming, and the address `example.test`).
- **recovery workflow** = an n8n automation (n8n = the free workflow tool) that wakes every 30 s and retries leads that got stuck, gives up on leads that ran out of tries, and mails an alert to the owner.
- **lead** = one sign-up. **lead key** = its unique id. **lead table** = `mf_leads`, the Postgres database table with one row per lead. **lease** = the 45 s during which one run holds a lead. **claim** = write my own token and a time limit on the row so no one else takes it.
- **state `unknown`** = the lead mail may or may not have been sent. **`failed`** = the lead could not be finished.
- **F6B-nn** = a row of this file; **F-nnn** = a row of `FINDINGS.md`; **F6-nn** = a row of `F6-AUDIT.md` (all in this folder). **T10, T11, AF1** and similar = named tests; explained in the full list below.
- **Ratings**: for each row, "take" = effect on the filmed recording, "client build" = effect if this were delivered to a client. Blocker, Major and Nit are explained in the full list below.

## Do this before the take (6 steps, in this order)

Order matters: switch flows off first, then check, then truncate, then switch the film set on. All SQL here is PROPOSED and UNTESTED (read, never run). Two cases: **first pass** (between scene 4 and scene 5, real set active) and **re-take** (film set active, scenes 6 to 9 may have left `unknown` or `failed` made-up leads on purpose). Steps 2 and 3 have a separate rule for each case.

1. **Switch off every flow that could touch the table, whichever set is active.** Who: the person filming. When: between scene 4 and scene 5, and before every re-take. Where: the n8n workflow list. On the first pass switch off ALL FOUR real-set flows (form, hook, sub-workflow, recovery; `SCENE-FLOW-MAP.md:66`). On a re-take the film set is the active one: switch off ALL FOUR film-set flows (the files in `handover/demo/n8n-flows-film-v5/`, listed in step 4). If you do not know which set is on, switch off both sets. Then **wait a few seconds for runs already in progress to end** (a form or hook run that started before the switch-off could still insert a row in that small window; whether switching a flow off stops an execution that is already running is UNVERIFIED), and re-run the check in step 2 once more before you truncate. Next check that no older recovery workflow is active (F6B-15). How: in the n8n workflow list, search for "recovery". All 12 `mf-recovery.json` files under `handover/demo/` carry the same workflow title, "Lead desk main frame: recovery (every 30 s)" (read from the files; the title does NOT contain "mf-recovery"), so the title cannot tell the sets apart: open each hit and compare it with the file. The 12 files are in these folders: `n8n-flows`, `n8n-flows/v1-superseded`, `n8n-flows-v3`, `n8n-flows-v4`, `n8n-flows-real`, `n8n-flows-real-v3`, `n8n-flows-real-v4`, `n8n-flows-real-v5`, `n8n-flows-film`, `n8n-flows-film-v3`, `n8n-flows-film-v4`, `n8n-flows-film-v5`. Only the two v5 ones are meant to be used; switch off any other that was imported (on a re-take too, the older sets could still be imported). Which of the 12 were ever imported into the take n8n is UNVERIFIED (not in this repository).
2. **Check the table (read only).** **If you are not certain this is the demo database, stop and ask.** Run `SELECT current_database();` (the demo database name is not in this repository) and compare it with the demo one. Then run `SELECT state, count(*) FROM mf_leads GROUP BY state;` (it only reads and counts leads per state). An empty table (no rows) or an empty result is fine: nothing to clean, go on to step 4.
   - **First pass (between scene 4 and scene 5):** it must show only `done`. **If it shows any other state (`processing`, `unknown`, `failed`, `review`, `new`), stop and do NOT truncate.** Reason: a lead that is not `done` is still being worked on or waits for a person, and deleting its row removes the only record of it (a running lead's later writes need its row, `build_mainframe.py:51,54`, so they would find nothing). A `review` row is a lead parked because of a bad e-mail address and waits for a person, so it also stops you here. Ask the owner what to do with those leads; with the flows switched off nothing changes while you wait.
   - **Re-take (film set was active):** scenes 6 to 9 leave `unknown` or `failed` made-up leads on purpose (UNVERIFIED which ones, F6B-13), so "only `done`" would stop every re-take. Instead run `SELECT lead_key, state, created_at, updated_at FROM mf_leads ORDER BY created_at;` and read every row. You may go on to step 3 ONLY IF every row is a film-set made-up lead that the owner can name (its key was created by the film scenes, the stand-in CRM and the `example.test` address, and `created_at` is after the start of the film set). If even one row is not a film-set lead you can name (for example a scene 1 to 4 lead from the real set that is not `done`, or a `review` row), stop, do NOT truncate, and ask the owner. A `review` row from the film set that you can name is allowed; one you cannot name stops you.
3. **Truncate (only if step 2 allowed it and you are sure this is the demo database).** With made-up data only, run `TRUNCATE mf_leads;`. **WARNING: TRUNCATE deletes every row of the table at once and cannot be undone. If you are not certain this is the demo database, stop and ask.** On the first pass it also deletes the rows of the scene 1 to 4 leads. That is intended: those leads are `done`, they already exist in the real CRM and mailbox, and the table row is only the filming record. A lead from scenes 1 to 4 that is still in flight (not `done`) would have stopped you at step 2. On a re-take it deletes the named film-set leads, including their `unknown` or `failed` rows, which is the point of the clean-up. Same warning in F6B-02. Both statements are PROPOSED and UNTESTED (F6B-01, F6B-02).
4. **Switch on the film set, and only it.** In the n8n workflow list switch on the four flows from `handover/demo/n8n-flows-film-v5/`: `mf-form.json` ("Lead desk main frame: form entry"), `mf-hook.json` ("Lead desk main frame: e-mail-style entry"), `mf-sub-crm-mail.json` ("Lead desk main frame: CRM + mail (sub-workflow)") and `mf-recovery.json` ("Lead desk main frame: recovery (every 30 s)"). On a re-take this step switches the film set back on. The real and film flows share these titles, so check each one you switch on is the film file (the film recovery has constant addresses ending in `example.test`). If both recovery flows are on, a lead from scenes 2 to 4 may be finished against the stand-in CRM with no error shown (F6B-01; that n8n allows this is UNVERIFIED).
5. **Add to the run sheet (`VIDEO-RUNSHEET.md`) a note for scenes 6 to 9 and for re-takes.** If scenes 6 to 8 create `unknown` leads (UNVERIFIED, F6B-13), the recovery flow alerts each one within about 30 s, so alert mails for scenes 6 to 8 can land before scene 9 and scene 9 may show several: film scene 9 from an alert already there, or switch the recovery flow off until scene 9. On a re-take, reused lead keys return the stored reply and scene 2 shows no CRM write or mail (F6B-14): use new keys or empty the table (steps 1 to 3).
6. **Add to the run sheet (`VIDEO-RUNSHEET.md`, wherever the alert is shown) one sentence: "The alert text 'A person decides' has no written follow-up step yet."** No document says what the person does next or how to restart the lead (F6B-03, F6B-05). Until that is written, do not tell viewers the person has a next step.

## Summary (plain words)

1. Audited: the recovery flow (it wakes every 30 s, retries stuck leads, marks leads that ran out of tries, and mails an alert) in `n8n-flows-real-v5` and `n8n-flows-film-v5`, plus the lead table (`mf_leads`), its generator and its tests.
2. The retry and alert logic itself looks sound on paper: all times come from the database clock, I found no path that lets two ticks take the same lead or alert at the same time, and I found no path that sends the lead mail twice. An alert mail CAN come twice (if the AlertMark write fails, or a send takes longer than the 720 s window; F-014, AF2, F6B-17), so "alert at most once" is not claimed. The weak spots are around it: what a person is told, what happens after an alert, and what happens when two sets or old rows share the table.

Client build: 2 Blocker (F6B-01, F6B-03), the rest Major or Nit; see each row.

## Read and found no problem (static read only, nothing run)

- Clock: every lease, window and backoff is computed inside the SQL with the database's `now()` (`build_mainframe.py:98,104,110`; json grep: `now()` only, no `$now`, no `Date` expression in any recovery node). There is no comparison between the n8n computer's clock and the database clock, so I found no path by which a clock difference between them makes a lease end early or late. The n8n clock is used for the timer and for run durations (timeouts, waits), so how long a run lasts against the 45 s lease is measured on the n8n side, not by the database. `now()` is the start of the statement's transaction; each query here is one statement, so it is the real time within milliseconds. Test drivers measure with their own clock (`mf.py`, `time.time()`), which only affects the reported seconds.
- Two ticks at once: see F6B-08 (SQL side). I found no path where `MarkFailed` and `ClaimStuck` both take one row (attempts 3 or more vs below 3). A lead already claimed by tick A is skipped by tick B for 45 s. The mail step is guarded by `claim_token` and `mail_sent`, so I found no path that sends a second lead mail for the same lead (MailClaim `build_mainframe.py:54`); T10 and T11 cover this on the test build.
- Alerts are at-least-once with a token (so a repeated alert is possible, as the summary says): a second alert for one lead comes if the first mark failed or the send ran past the 720 s window; no path loses a lead's alert while the table is intact and the sweep runs (F-014, F-035 cover the rest).
- The three jobs touch different columns: recovery needs UPDATE on `mf_leads` only; it does not insert (F-010 covers the single credential).
