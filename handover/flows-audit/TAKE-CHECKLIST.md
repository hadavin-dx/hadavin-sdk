## Pin procedure (the one place for the pin file; check 1, GO row 4 and FIX-PLAN steps 4 and 9 point here)
Everything below is read in `flow-check/take_check.sh` and `flow-check/take-warns.pin`; nothing was run.
1. **What the pin is.** There is exactly one pin file in use: `flow-check/take-warns.pin`, next to the script. It holds a `# reviewed by:` line, a date line, a line `# flows sha256 ...` (the sha256 of the four flow files the pin was written for) and the WARN lines (a WARN line is a warning the checker prints and a person has read). The script compares the WARN lines and the sha256 of the folder it checks with the pin; a difference exits 4 (`!!! THE WARN SET CHANGED` or `THE FLOW FILES DO NOT MATCH THE SHA-256 WRITTEN IN THE PIN`). No option picks another pin file: setting `TAKE_CHECK_WARN_PIN`, `TAKE_CHECK_FLOWS` or any other `TAKE_CHECK_` variable outside tests is exit 4 ("NOT allowed outside tests"); only `TAKE_CHECK_TEST=1`, set by the test scripts, lifts it, and then a run that would have passed exits 5, which is a test run and never a take check. So the override is never a route to a new pin.
2. **Order of runs (one file, so order matters).** As committed the pin holds the WARN set of the UNFILLED patched copy. So: (a) run check 1 on the unfilled patched copy `$FLOWS` with the pin written for it installed (step 3) and KEEP that log (GO row 4); (b) only then install the export pin (step 5). After the export pin is copied over `take-warns.pin`, the same command on `$FLOWS` exits 4 (its WARN set and sha256 differ), and afterwards only the exported copy is checked. Every run writes to a NEW `$LOG` path.
3. **Pin for the unfilled patched copy.** The regenerated copy is a different folder from the one the committed pin was written for, so it needs its own pin first: `cd "$REPO" && bash handover/flows-audit/flow-check/take_check.sh --flows "$FLOWS" --write-warn-pin "$NEW_PIN"` (run once; `$NEW_PIN` must not exist yet; the pin is written only when the run has no FAIL; the run exits 4 on purpose). A human reads every WARN line of the new file (step 4), the reviewer line is written, the file is copied over `flow-check/take-warns.pin` by hand, the lead commits it, and the `--flows "$FLOWS"` command of check 1 is run again. Planned by the audit, lead to confirm: the one commit of FIX-PLAN step 3 comes first and the pin commit second, so there are two shas (RUNBOOK.md I24, Inputs item 14). The FINAL line of the script prints the sha256 of the four flow files, which names the flows by content whichever commit holds them.
4. **The reviewer line (needs a human).** The line must read `# reviewed by: NAME, YYYY-MM-DD` and the script accepts it only by the rule in Inputs item 14 (NAME of at least 3 letters from letters, spaces, dots, apostrophes and hyphens; none of the stand-in words tbd, todo, name, placeholder, unknown, nobody, someone, anonymous, claude, agent, session, bot, assistant, gpt, model, lead, person, xxx, abc; a real UTC date that is not in the future). An agent's name is rejected, so only a human's name exits 0. Audit proposal, lead to confirm: the owner (or another named human) reads the WARN lines and supplies `$PIN_REVIEWER`; the lead writes it into the file; nobody writes a name for a human who did not read the lines. The sha256 line stays valid when only the reviewer line changes: it covers the WARN lines, not the comment lines.
5. **Pin for the exported copy.** Placeholder WARNs vanish in the export, so the first run exits 4. After a human has read every changed WARN line, write the new pin to a NEW file: `cd "$REPO" && bash handover/flows-audit/flow-check/take_check.sh --flows "$EXPORT" --write-warn-pin "$EXPORT_PIN"` (`$EXPORT_PIN` does not exist yet; the run exits 4 on purpose), copy it over `flow-check/take-warns.pin` by hand with a reviewer line as in step 4, commit it, and run the same `--flows "$EXPORT"` command again with a NEW log path. Whether two shas (folder sha and pin-commit sha) are accepted is RUNBOOK.md input I24 and ORDERS does not answer it: LEAD FILLS.
6. **A later change.** Any later change of a flow file changes the sha256 and needs a new pin (steps 3 to 5).
