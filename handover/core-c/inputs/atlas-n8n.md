## 2. Core concepts
- Workflow = connected nodes. Trigger = node that starts it. Execution = one run. Data items = JSON rows flowing between nodes. Expressions = `{{ }}` snippets. Sub-workflow = Execute Workflow node. UNVERIFIED: I did not re-read those concept pages; standard n8n usage.
- Error workflow: set in Workflow Settings; must start with Error Trigger; one can serve many workflows. Payload: execution id/url, error message+stack, last node, mode, workflow id/name; `execution.id/url` missing if trigger node itself failed; `retryOf` only on retries. Stop and Error node forces a failure. Source: https://docs.n8n.io/flow-logic/error-handling/
- Node settings (https://docs.n8n.io/workflows/components/nodes/): Retry On Fail (docs page gives NO max tries or wait numbers: UNVERIFIED, the editor has max-tries/wait fields), Always Output Data (danger: infinite loop on IF), Execute Once, On Error = stop / continue / continue with error output.
- Queue mode (https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/enable-queue-mode, raw `queue-mode-20261114.md`): main passes the execution ID to Redis, a worker picks it up. Postgres: SQLite with queue mode "isn't recommended". Worker `--concurrency` "defaults to 10"; docs "recommend setting concurrency to 5 or higher". Encryption key of main "must be shared with all worker and webhooks processor nodes". Large webhook response relay: `N8N_WEBHOOK_RESPONSE_RELAY_SIZE_MAX` default 64 (MiB); offload needs 2.34.0 or later on main and webhook instances. Multi-main section lists Enterprise availability. Raw search found no retry, at-least-once or exactly-once text (grep for retry/stalled/at-least/twice returned nothing relevant). (summariser, no raw match: "Optional `n8n webhook` processors route /webhook/* and /webhook-waiting/*", "webhook runs have extra latency".)
- Executions env vars (https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/executions, raw `env-executions-20261114.md`): EXECUTIONS_TIMEOUT -1, EXECUTIONS_TIMEOUT_MAX 3600, EXECUTIONS_DATA_MAX_AGE 336 (hours), EXECUTIONS_DATA_PRUNE_MAX_COUNT 10000, save-on-error and save-on-success `all`, save-on-progress false, manual executions saved true, storage mode database/filesystem/s3/azure (default database), N8N_AI_TIMEOUT_MAX 3600000. (raw `control-concurrency-20261114.md`: self-hosted regular mode, "Concurrency control is disabled by default"; enable with `N8N_CONCURRENCY_PRODUCTION_LIMIT`; excess production executions queue FIFO; queued executions cannot be retried. The earlier "default -1" claim is not on the page and is dropped.)
- Webhook node (https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/): test URL (registered while listening or running an unpublished workflow, data shown in editor) vs production URL (registered on publish, runs seen in Executions). Respond modes: Immediately ("Workflow got started"), When Last Node Finishes, Respond to Webhook node, Streaming. Auth: Basic, Header, JWT, n8n User Auth (OAuth2), none. Methods DELETE/GET/HEAD/PATCH/POST/PUT. Payload max: page wording (raw) "The webhook maximum payload size is 16MB"; self-hosted can change it with N8N_PAYLOAD_SIZE_MAX (pass 2 wrote "16 MiB"; the page says 16MB, quote the page). (summariser, no raw match: form-data file max 200 MiB.) Paths: webhook, webhook-test, webhook-waiting. Page gives no timeout or rate limit (UNVERIFIED; none documented). Node option "Only run if" (expression gate before execution starts) since 2.28.
- Scheduling (raw `schedule-trigger-20261114.md`): Schedule trigger; the Seconds and Minutes intervals "run at uniform intervals measured from workflow publication, rather than on clock boundaries"; Custom (Cron) intervals keep their timing; durable scheduler on by default while `N8N_USE_WORKFLOW_PUBLICATION_SERVICE` stays on. The workflow must be saved and published. (summariser, re-check before quoting: "since 2.45" and "one main claims each run"; the page does not state them.)
- Wait node (https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.wait/): resume after interval, at time, on webhook call (resume URL unique per execution, `$execution.resumeUrl`, Basic/Header/JWT auth), on form. Limit Wait Time available. Waits under 65 s stay in process (not saved to DB). Time resume uses server timezone. Send and Wait for Response (raw, 2026-11-14): present on Send Email (SMTP) and Slack node pages; NOT on the Gmail node page. Data is offloaded to the DB while waiting.
- Data Tables (https://docs.n8n.io/build/work-with-data/data-tables and https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.datatable/rows, raw read 2026-11-14): project-scoped tables inside n8n; node + public API `/data-tables` (NOT `/datatables` as pass 1 wrote) + UI (CSV import/export). Cap 200 MiB per instance (N8N_DATA_TABLES_MAX_SIZE_BYTES); warning at 80 percent; at the cap inserts/updates fail and "cause workflow execution errors". Page says "light to moderate data storage" and lists "Storing markers to prevent duplicate runs" as a use. Code node cannot read them. Row ops: Delete, Get, If Row Exists, If Row Does Not Exist, Insert, Update, Upsert (upsert matches by conditions Equals/Not Equals/Greater/Less/Is Empty/Is Not Empty; Must Match Any or All; Dry Run option). API scopes dataTableRow:create/read/update/delete/upsert. The rows page warns that reading a large table in pages while rows change "might be a bit off. Some records could be missing, some could show up twice". STILL NOT STATED anywhere I read: column types, row-count limit, unique constraints, atomicity or transaction behaviour of upsert/insert under parallel runs. Do not assume an atomic claim. Issue report (not fact): #33440 (closed 2026-07-02) said Get row(s) with Return All on tables over 1000 rows returned duplicates and dropped rows because of pagination without ORDER BY.
- Credentials API (https://docs.n8n.io/connect/n8n-api/build-and-run/credentials, raw read 2026-11-14): CONFIRMED. Exact sentences: list "Retrieve all credentials from your instance. Only available for the instance owner and admin. Credential data (secrets) is not included." and get "Retrieves a credential by ID. Credential data (secrets) is not included." Create body field `data` is marked "Write-only" ("The credential data. Fields also accept n8n expressions, which are strings that start with =". Endpoints: GET/POST /credentials, GET/PATCH/DELETE /credentials/{id}, GET /credentials/{id}/dependencies, GET /credentials/schema/{credentialTypeName}, POST /credentials/{id}/test, PUT /credentials/{id}/transfer. List max limit 250, default 100, cursor paging. Caveat: this is the REST docs only (the API never returns secret values); anyone who can run a workflow that uses the credential still uses the secret at run time, and only the `data` field is write-only. 2.47.5: API rejects edits to read-only credential nodes. 2.46.0: personal credentials usable in team projects with restricted run/publish.
- External secrets (https://docs.n8n.io/administer/manage-credentials/use-external-secret-stores, raw read 2026-11-14): Cloud Enterprise and self-hosted Enterprise only. Providers: 1Password (Connect Server, not a personal account), AWS Secrets Manager, Azure Key Vault, GCP Secrets Manager, HashiCorp Vault (not Vault Secrets), Infisical. Multiple vaults per provider from 2.10.0; project editors can use them from 2.13.0 if enabled. Plaintext values only, "not JSON objects"; resolve only in credential fields. Global vs project-scoped vaults.
- Source control (https://docs.n8n.io/administer/use-source-control-and-environments/understand-source-control and .../push-and-pull-changes, raw read 2026-11-14): Business and Enterprise; instance owner/admin push and pull; project admin push only. Push contains: workflows (with tags and owner email), credential STUBS (ID, name, type; other fields only if they are expressions), variable stubs (ID and name), data table SCHEMAS (names and columns, not row data), folders. So credential secret values and data-table rows are NOT pushed. Pull can change workflow/credential owner (matched by project ID). Public API: GET /source-control/status, POST /source-control/pull and /push; scope sourceControl:pull.
- Variables: Community has NO custom variables (paid). Variables and tags are global, not covered by RBAC.
- Retention/pruning (executions env vars page): prune on by default; max age 336 h (14 days); max count 10000; save on error/success default all; save on progress false; EXECUTIONS_TIMEOUT -1 (off), max 3600 s; storage db/filesystem/s3/azure (s3/azure paid). Redact execution data exists (hardening page; settings UNVERIFIED).
- Logging/audit: Community has logging; log streaming Business+; security audit command exists (hardening page); contents UNVERIFIED.
- Roles (https://docs.n8n.io/administer/manage-users-and-access/set-permissions-and-roles-rbac/see-available-roles, raw read 2026-11-14): project Admin / Editor / Viewer. Editor = Cloud Pro and self-hosted Enterprise; Viewer = Cloud Enterprise and self-hosted Enterprise. Viewers see credentials and executions but cannot run workflows. Variables and tags are global, not covered by RBAC. External secrets for project roles needs the setting enabled (2.13.0+). SSO (SAML and OIDC): Cloud Enterprise; self-hosted Business and Enterprise (https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/configure-sso); SSO via environment variables from 2.18.0. Custom roles exist (pages not read).

## 4. Duplicate / exactly-once, per the docs (updated pass 2, 2026-11-14, raw reads)

## 8. Before you write a plan that uses n8n (checklist, plain words)
n8n is an open-source tool where you connect "nodes" (small building blocks such as "receive a web request" or "write a row") into a "workflow" (one chain of nodes). Each line below is a yes/no check. If the answer is no, stop and ask the person named; do not carry on. Licence statements here are not legal advice and no lawyer has read them.
1. Can you name the one step of the job that n8n does? n8n is a good fit for the front door of a flow (a web form, a "webhook" (a web address that other software calls to start a run), or an email comes in; fields are mapped; our service is called; a branch decides; a message goes out) and for scheduled checks. Our tool ladder (our own order of preference) says to try ready-made no-code tools such as n8n before writing our own code. If no: stop and ask the lead, because the plan may not need n8n.
2. Is it written down where n8n runs: our own "instance" (one running copy of n8n, for demos) or the client's own instance (their own server, or their own n8n Cloud account, which is n8n's hosted service)? "Self-hosted" means we or the client run n8n ourselves; "Cloud" means n8n runs it for a fee. The Sustainable Use Licence ("SUL", n8n's licence for the free self-hosted version) is the licence in question. Per n8n's own FAQ (raw, 2026-11-14), building workflows for a client on an instance only we use is allowed when the client has no way to create or edit workflows; the FAQ is ambiguous on whether clients may sign in to authenticate their own accounts on our instance (section 1). Not legal advice. Our own studio rule is stricter: one n8n of ours never holds several clients' workflows. The licence does not apply to n8n Cloud, whose own terms we have NOT read. Is the setup inside these limits, and for any doubt (a client logging in, embedding n8n in a product, several clients on one instance) has license@n8n.io confirmed it in writing? If no: stop and ask the lead, who asks license@n8n.io.
3. Does the plan avoid the words "exactly once" and "no duplicates" for anything n8n receives? The docs give no such promise for webhooks or queued jobs, and users report one webhook call starting two runs (section 4). The n8n API "Idempotency-Key" header (a caller-chosen label that makes a repeated API call return the first answer instead of doing the work twice) only protects calls TO n8n's own API; it does NOT protect incoming Webhook-node requests. Any claim about a "burst" (many requests at nearly the same moment) must come from our own test. If no: stop and ask the lead.
4. If the flow must not process the same item twice, does it use a Postgres table with a "unique key" (a column the database itself refuses to store twice) and the Postgres node's Insert with "Skip on Conflict" (if the key already exists, do nothing instead of failing)? The docs do not say what a skipped insert returns, so the flow may not be able to tell a new row from a duplicate: test it, with a burst of parallel calls, before relying on it. Do not rely on the Remove Duplicates node when two runs go at the same time: its docs say nothing about parallel runs. If no: stop and ask the lead.
5. Does anything where a mistake costs money or trust stay in our own tested code, with n8n only calling it over HTTP (a web request)? We call these "guarantee-class steps": exact money amounts, spend caps, hiding personal data (redaction: removing it before it reaches a model or a log), the audit trail (a record of who did what that nobody can quietly change), approvals made by a different identity than the doer, keeping each tenant's (client's) data apart, evaluation gates (automatic tests that must pass before a change goes live), and never losing a message. If no: stop and ask the lead.
6. Is every model call (n8n's Anthropic, OpenAI and AI Agent nodes) behind our own spend cap? Those node pages document no spend cap or token cap (raw, 2026-11-14). If no: stop and ask the lead.
7. Are secrets (passwords, API keys) read by our own code from the client's secret manager, not from n8n? n8n's REST documentation never returns saved secret values, and only the credential `data` field is write-only, but any workflow that can run still uses the secret. Linking the client's own vault to n8n ("external secrets") needs n8n's Enterprise plan (the top paid plan, custom price). If no: stop and ask the lead.
8. For approvals, is the approval kept outside n8n, with a separate identity from the one that runs the action? The "Wait" node (pauses a run until someone clicks a link or submits a form) sends the approver through n8n, so it is not enough for guarantee-class actions. If no: stop and ask the lead.
9. If the plan uses "Data Tables" (small tables kept inside n8n), are they only for light, non-critical lookup data? The cap is 200 MiB (about 200 megabytes) per instance, and the docs state no unique-key rule and no atomic behaviour (all-or-nothing, safe when runs happen in parallel). If no: stop and ask the lead.
10. Is one n8n version pinned per client (the version number fixed in the setup), with the release notes read before each upgrade? The changelog says "npm" installs (installing n8n through the Node package manager) stop working with n8n 3.0, and the AI Agent v1 node is removed in 3.0. Has the "v3.0 Breaking changes" page been read before any 3.x plan? If no: stop and ask the lead.
11. If an n8n node lacks an operation (for example HubSpot has no documented generic upsert, which means "create or update in one call"), does the plan use the HTTP Request node (a node that sends any web request) with the existing credential? If no: stop and ask the lead.
12. Does every client flow have an "error workflow" (a separate small workflow n8n starts when a run fails, so the failure is reported instead of lost)? Error-workflow runs do not count toward the execution quota (the monthly number of runs a plan allows): on Cloud from 2.38, on self-hosted Business and Enterprise from 2.28.0 (changelog, raw `release-notes-20261114.txt`). If no: stop and ask the lead.
13. Were the licence and plan checked against section 1 on the day the plan is written? Prices, limits and Community features change (Compare editions says "The pricing page is the source of truth"). If no: re-read section 1 first, then ask the lead.
14. Does the plan's rung table (our table that lists, for each part, which tool-ladder step was tried) cite this file and the raw copy's date for every n8n claim, and mark any claim tagged "(summariser, re-check before quoting)" as UNVERIFIED? That tag means a small summarising model read the page and there is no saved raw copy. If no: stop and ask the lead.
