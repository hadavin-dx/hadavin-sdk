## DECISION
1. **One Postgres server with two databases (n8n's own and the take's): one container, one engine.** n8n's internal data lives in its own database `n8n` (owner role `smk_n8n`); our claim table `mf_leads` lives in an `app` schema of the take's database `postgres`. Three least-privilege roles are built and tested in the re-smoke only (rehearsal roles; the real take has no read-only count role, lines 28 and 33): plan-wp6-resmoke-v5.md line 122 builds `smk_n8n`, `smk_app`, `smk_count`; line 99 says least privilege is proven only if the role checks S1b pass; line 281 builds the `app` schema and the roles. UNVERIFIED until the re-smoke has run; nothing of this has run yet. Config only for the engine: `DB_TYPE=postgresdb` and the `DB_POSTGRESDB_*` names (host, port, database, user, password) in the take's n8n.env (plan line 272, step 1.2b); they are already allowed by n8n_start.sh (allow-list: n8n_start.sh line 173 or 177 depending on the head; plan section 11 row S7, PL:519); the password comes from the secret file, never echoed. The plan sets no `DB_POSTGRESDB_SCHEMA` line, so n8n uses its default schema `public` inside database `n8n` (plan line 272), UNVERIFIED until run. The re-smoke starts Postgres before the n8n imports and checks the engine (no sqlite file, tables in database `n8n`, DB_* names in n8n's process environment).
2. **The desk SQLite and its portal are retired from the take.** They are the Mode A product, not the n8n main frame. Nothing in the video, the owner steps or the scope sheet may say a portal shows these rows. A portal is a later product built on the SAME Postgres through the core store kind, after the video.
3. **Logs: one place = Postgres.** Execution log = n8n's execution history in Postgres (turn "save successful production executions" on for the take only, as PLAN-4 already says). Audit = the lifecycle rows of `mf_leads` (state and timestamps). No new audit table before the video (new nodes would change the proven flows). Process output files (`n8n.out`, stage stderr, result.json) are diagnostics with no lead data and are not stores.
4. **The one exception, stated plainly (brutal honesty): `stage.journal` stays a small file for the take.** It is not a data store anyone reads: it is the model-call write-ahead guard of our code, deliberately independent of n8n (a different identity than the flow that could be wrong, the count is a separate check of ours, not an independent-credential check, see lines 28 and 33). It is proven (WP6 P11: 1 model call per lead, also across the crash scene) and reviewed in rounds. Moving it into Postgres needs a Postgres driver inside the stage (the take is stdlib-only: a pure-Python driver such as pg8000 under a licence check, ladder rung 4), new money-path code with tests, uncapped independent review rounds and a re-smoke: about 1.5 to 2 agent-days, which puts the Wed 18 Nov target at risk and does not change anything the video shows. Trigger to do it: after the video, as a core store-kind item (first client or when the portal is built). If the owner wants literally one before the video, say so and the cost above is accepted.
5. **What this changes now:** no code. (a) The re-smoke records the n8n engine and checks that no sqlite file exists. (b) Owner steps, scope sheet and video script lose any portal claim and name the proof screens: n8n executions, the `mf_leads` rows (the existing `n8n-table-screen` page flows are a candidate: not run in n8n, UNVERIFIED), HubSpot and Gmail. (c) No-single-dependency: Postgres sits behind n8n's own credential layer and the app role; swapping the engine later is a core store-kind task.
## Not decided / UNVERIFIED
