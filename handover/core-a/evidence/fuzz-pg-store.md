## Findings
A10-1 (real, known limit, door-relevant) PostgresStore never reconnects. One `pg_terminate_backend` of the worker's connection leaves the running worker answering 503 to every request (even for stored keys) for as long as it runs; verified for 15 s with a single terminate and nothing else (minimal test `test_c_min_one_terminated_connection_is_survived_without_a_restart`, xfail strict, seeds irrelevant: deterministic), and 8 s then 20 s after the outage in (c). A restart fixes it and the restart leaves the store correct (no double start). Cause: `src/hadavin_sdk/store/postgres.py:516` states it: "A dropped connection fails the call; reconnect-on-error arrives with S11 hosting." The task text expects "correct answers after" recovery; without a restart that does not hold. Owner: core-b (store). Consequence for operations: a Postgres failover or an idle-connection kill by a proxy takes the door down until a supervisor restarts the worker; `/health` is the signal to restart on (not tested here whether `/health` goes 503, a worker that started with the store down does re-check, one that lost it later does not). The xfail turns into a failure the day reconnect lands.
A10-2 (observation, by design) the 256 connection slots are global: while 256 idle sockets are held, a legitimate client gets no answer (84 of 143 stream requests in the "cap" phase were refused). The worker text says a reverse proxy with per-peer limits is required. Below the cap (phase 1, 140 sockets held) the stream lost nothing.
A10-3 (observation) the stdlib listen queue is 5: a burst of connections faster than the accept loop (tight loop of 300 connects, no pause) gets SYN drops and 1 s retransmit delays (38 of 300 connects timed out in 1 s in a scratch run). Paced connects (5 ms) see none. Not a cap violation; I did not file it as a bug.
No finding in the door itself: no duplicate run row, no 5xx for hostile bytes, no 2xx for a bad signature, no wrong run id, no second reservation for a run, day total = sum of the rows in every case (a, b, c, d, all seeds).

## Limits of this evidence
- The children use the test seeding of tests/money_caps_seed.py (day window widened, expiry floor 0), so the real day window and the 3600 s expiry floor are not exercised, same limit as the crash matrix.
- Day cap in the seed is 1.00 and one hold is 0.035964, so each test stays under 27 runs per schema.
- (b) and (c) kill at random moments but the number of runs caught between reserve and settle varies by seed (0 to 2); a run with 0 caught is a pass that exercised less. Counts above are per the logged runs.
- Test files: `/proc/loadavg` is the load source; nothing was timed above load 4.
- Not run: the 16 MB, slow-body-at-the-30 s-boundary variants, more than 2 workers, more than 20 keys.
