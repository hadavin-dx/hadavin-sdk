## The signed trigger door: what it guarantees and its stated limits (reviewed, not bugs)

The door (`hadavin_sdk.triggers`) takes one signed HTTP POST per run. One worker process serves it and runs the agent loop. The text below says what it defends, what it leaves to the deployment, and what is not tested. A "run row" is the stored record of one run. "The tick" is the scheduled step that ends stuck runs.

**Forgery.** A request is accepted only when its HMAC "v0" signature verifies. Nothing of the body is parsed before that. [src/hadavin_sdk/triggers/endpoint.py:1-8; tests/endpoint_mutants.py:11-12] Agent and principal come from configuration, never from the request. [src/hadavin_sdk/triggers/endpoint.py:6-7] Every refusal has an empty body, and no header names the reason. [src/hadavin_sdk/triggers/endpoint.py:10; src/hadavin_sdk/triggers/server.py:240-256]

**Replay.** The timestamp must be within 300 seconds. [src/hadavin_sdk/approvals/hmac_v0.py:19; src/hadavin_sdk/approvals/hmac_v0.py:47] A replay inside the window cannot start a second run: one run per key rests on the primary key of the runs table. [src/hadavin_sdk/triggers/worker.py:12-14] The same key with another document is a 409 and no run is written. [src/hadavin_sdk/triggers/worker.py:549-556] A replay of the identical request is answered from the stored row. [src/hadavin_sdk/triggers/worker.py:549-558]

**Acknowledgement.** A 2xx is sent only after the run row has been read back from the store. The row must be for the same agent, principal and key. 202 means the run is RECEIVED or WORKING; 200 means a later state. [src/hadavin_sdk/triggers/worker.py:1-6; src/hadavin_sdk/triggers/worker.py:549-558] RECEIVED means stored and not started; WORKING means the loop is running.

**Conflict audit.** A signed 409 writes one audit event `trigger.conflict` with the run id, principal, key and both document hashes. It never holds the document or the signature. [src/hadavin_sdk/triggers/worker.py:530-545] At most `triggers.conflict_events_per_minute` events per sender per minute are written; further ones are counted and logged once a minute. [src/hadavin_sdk/triggers/worker.py:387-415] A request that fails the signature writes no audit row, so a caller who cannot sign cannot grow the audit chain. [src/hadavin_sdk/triggers/endpoint.py:366] The number is read from the configuration only (true only on the merged tree, where core-b's `TriggerSettings` holds it). [src/hadavin_sdk/triggers/worker.py:717-721; integ:src/hadavin_sdk/config.py:419-424]

**Secret handling.** The worker reads only the secret names listed for its senders, once at start, through `App.trigger_secret`; it never receives the whole secret provider. [src/hadavin_sdk/triggers/worker.py:55-56; src/hadavin_sdk/triggers/worker.py:650-654] A secret must be at least 32 characters, and the same value under two senders is refused at start. [src/hadavin_sdk/triggers/endpoint.py:50; src/hadavin_sdk/triggers/endpoint.py:243-266] Logs never hold a body, key, header value or secret. [src/hadavin_sdk/triggers/endpoint.py:10-12]

**One secret per tenant and per stage.** The tenant is not in the signed string. A secret shared between tenants or stages makes a request for one valid for the other within the 300 second window. [src/hadavin_sdk/triggers/worker.py:44-45] A worker sees only its own configuration, so a reuse on another worker cannot be detected. Keep one secret per tenant and per stage.

**Connection flood and slow clients.** The server has 256 connection slots, an absolute 30 second read deadline, a 64 KiB request-line cap and a 16382 byte cap on request line plus headers (431 above it). [src/hadavin_sdk/triggers/server.py:50-60; src/hadavin_sdk/triggers/server.py:11] It has no per-peer limit. A reverse proxy with per-peer connection limits is required in front of it. [src/hadavin_sdk/triggers/worker.py:42-43] TLS is the proxy's job. The worker listens on 127.0.0.1 unless `--allow-non-loopback` is given. [src/hadavin_sdk/triggers/worker.py:47-49; src/hadavin_sdk/triggers/worker.py:630-634]

**What the server writes for a refusal.** The server writes its own 400, 414 and 431 in one write, with `Content-Length: 0` and `Connection: close`. It never repeats the request line, a header or the Python version. [src/hadavin_sdk/triggers/server.py:240-256; src/hadavin_sdk/triggers/server.py:1-8] HTTP 2.0 or higher, an underscore in a header name, two `Content-Length` headers and any `Transfer-Encoding` are answered 400. [src/hadavin_sdk/triggers/server.py:13-21] Every normal answer also leaves in one write, so a killed worker cannot leave a bare 2xx status line. [src/hadavin_sdk/triggers/server.py:187-200; tests/triggers/test_d_fix13_single_write.py:192]

**Memory store.** The worker refuses a memory store outside the `demo` stage, because a 202 for a row that vanishes on restart is a false promise. [src/hadavin_sdk/triggers/worker.py:669-682; tests/triggers/test_d_fix18_door_fixes.py:116]

**Start, stop and health.** Exit code 0 is a clean stop after SIGTERM drained the running loops, 2 is a refused configuration, 3 is any other start failure. [src/hadavin_sdk/triggers/worker.py:125; src/hadavin_sdk/triggers/worker.py:845-879; src/hadavin_sdk/triggers/worker.py:1169-1177] A store that is down at start is not an exit: the worker starts degraded, answers 503 everywhere but `/health`, and recovers in the same process. [src/hadavin_sdk/triggers/worker.py:947-1008; src/hadavin_sdk/triggers/worker.py:1060-1080] `GET /health` needs no signature and answers 200, or 503, with a body of exactly `status` and `store_failures`. A permanent store fault shows as `/health` 503 and a warning at most every 5 minutes, never as an exit. [src/hadavin_sdk/triggers/endpoint.py:120-131; src/hadavin_sdk/triggers/worker.py:138-140]

**Settings that bound the worker.** `triggers.max_running` (runs at once) and `triggers.conflict_events_per_minute` are read from the configuration only; the worker holds no second default for either. A settings object without the field is a start error, exit 2. [src/hadavin_sdk/triggers/worker.py:103-104; src/hadavin_sdk/triggers/worker.py:714-721] The defaults (4 and 10) and the bounds belong to core-b's `TriggerSettings` and are true only on the merged tree. [integ:src/hadavin_sdk/defaults.py:280-287; integ:src/hadavin_sdk/config.py:395-425]

**Parallel runs and spend (true only on the merged tree).** With core-b's limits the main model call of a run reserves its worst case before the call and settles after it. Runs side by side cannot pass a cap through that call. [integ:src/hadavin_sdk/runtime/agent_loop.py:567; integ:src/hadavin_sdk/runtime/agent_loop.py:396-404] The ungated sites listed under "Spend limits" are still charged after the fact. The worker warns at start only when `max_running` is above 1 and the limits object has no `reserve`. [src/hadavin_sdk/triggers/worker.py:685-696]

**After the 2xx: a cut-off run is acknowledged and then lost to a person.** If the worker dies or the loop raises after the 2xx, the tick later ends the run as NEEDS_PERSON, the state that asks a person to look. Nobody is notified and the document is not stored, because only its hash is kept. The sender must poll the run state. This is not "never lost" and not "handed to a person". [src/hadavin_sdk/triggers/worker.py:36-39; handover/core-a/CRASH-MATRIX.md:97-99] The tick must run in the deployment, or such a run stays RECEIVED or WORKING for ever. [src/hadavin_sdk/triggers/worker.py:1178-1180] Whether to store the document and notify a person is an open owner decision, called E-door-1 in handover/core-a/ESCALATIONS.md. Option A, the sender polls, stands. Option B, store and notify, is not built. [handover/core-a/ESCALATIONS.md:3-8]

**Polling has no read address.** The door answers `POST` on its trigger path and `GET /health` only. A sender asks "what is the state of this run?" by sending the same signed key and document again; the answer holds only `run_id` and `state`. [n8n/README-trigger.md:617-626; src/hadavin_sdk/triggers/endpoint.py:61] A 200 does not mean "ended": PLAN_READY, WAITING_FOR_APPROVAL, EXECUTING and VERIFYING also answer 200. [handover/core-a/CRASH-MATRIX.md:120]

**What was tested, and the limits of that.**
- Crash matrix: a worker child is killed at 43 points of the "nothing to do" path on PostgreSQL 16; 39 of them also run on the memory store. It is killed at 171 more points on the read, propose and approve paths, on both stores. At each point there is at most one run row and one approval request per key. No second model call follows a kill when a row exists. The retry gets 200 or 202. [handover/core-a/CRASH-MATRIX.md:7; handover/core-a/CRASH-MATRIX.md:91-93; handover/core-a/CRASH-MATRIX.md:107-109]
- Money end state per point (true only on the merged tree, with core-b's live loop): one open hold stays open until expiry. A restarted run never books again. The day total equals the sum of the rows. [tests/triggers/crash_money.py:1-20] The child's seeding widens `max_day_skew` and `min_expiry_age`, so the matrix does not exercise the real day window or the 3600 second expiry floor. [tests/triggers/crash_launcher.py:18-26]
- Not in the matrix: a kill by signal from outside, two tick processes at once, a database that goes away, the real approval receiver and the real action executor. [handover/core-a/CRASH-MATRIX.md:17; handover/core-a/CRASH-MATRIX.md:122-129]
- Mutation testing (`tests/endpoint_mutants.py`) reverts one guard at a time and needs a test to fail. The last full run reached 120 of 120 expected results at commit 5a8c83fd3; see `handover/core-a/evidence/mutants-run19.md` and run 20 when it lands. [handover/core-a/evidence/mutants-run19.md:2-3; tests/endpoint_mutants.py:1-8]
- A seeded fuzz battery (`tests/triggers/test_fuzz_endpoint.py`) checks four properties over 300 cases each. First: only documented statuses and no secret in any answer. Second: no 2xx after a flipped bit or a stale timestamp. Third: one run per key, and 409 for another document. Fourth: one well-formed answer to garbage on a real socket. [tests/triggers/test_fuzz_endpoint.py:2-14]
- Nothing was run on Windows. The n8n sender template ran once, in n8n 2.47.7. n8n queue mode is the deployment we recommend and it is NOT verified: it was never run. In default mode a restart during a 60 second wait lost the run. [n8n/README-trigger.md:3; n8n/README-trigger.md:209; n8n/README-trigger.md:883]

Out of scope: TLS termination, per-peer rate limiting, secret separation across workers, and the sender's own storage of events.
