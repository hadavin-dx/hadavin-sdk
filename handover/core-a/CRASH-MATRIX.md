## How to read the table

One signed request with one key is sent to a worker process. The process is killed at the named point. Then: a new worker process is started, the tick's "stuck" step runs with a clock one day later, and the same request is signed again and sent again.

- A kill point is `<object>.<method>:before` or `:after`, with the number of the call when a method is called more than once. `store.get_run` is the read made by the request thread (`Runner.start`); `loop.get_run` is the same store method called by the agent loop; the other `store.*`, `audit.*` and `llm.chat` are calls of the agent loop (`Runtime.handle`).

Where a row exists, the request thread may or may not have read it before the kill (two threads race), so the table says "possible" and shows what the two runs saw. The test asserts for every case: a 2xx only together with a matching row.
- "Model calls in total" counts calls over the killed process, the restarted one and the retry (a file both processes append to).

## Points that could not be reached, and why

The crash helper stops the program only at a call of an object the test hands in (the store, the audit sink, the model double). The worker has no test hook (ticket D, section 9). So these moments have no point of their own:

- **While the signature is being checked** (before the first store call). No store call happens there. The first reachable point after it is `r1`; nothing is written before it, so the end state is the same.
- **Between `_submit` and the first poll in `Runner.start`** (worker.py:223-232: `_submit` in `_decide` up to the first poll read): not a store call. The nearest point is `store.get_run:before` call 2 (`r2`, `r4`), which is the very next store call of that thread.
- **Between the read that found the row and the answer bytes on the socket**, and a half-written answer: `r5` kills right after the read returned; a kill in the middle of writing the answer cannot be placed. A client that gets a broken answer retries, and the retry is answered from the row.
- **In the middle of a store call** (statement sent, answer not yet read): cannot be placed on purpose. Run 1 hit it by accident at `r4` (see the top).
- **Redaction, the injection check and the post of the abstain card** (agent_loop.py:412, 432, 626): not calls of a wrapped object. Each lies between two reachable points with the same row and the same number of model calls (redaction: h08-after and h09-before; injection check: h09-after and h10-before; card: h18-after and h19-before).
- **Later polls of the request thread that find the row on a chosen poll number**: which poll finds the row depends on timing. `r3` (4th read, row write slowed) and `r5` (first read that returns a row, whichever number it has) cover both sides.

## Conclusion on "an acknowledged request is never run twice" (and what happens to a cut-off one)

For the path tested, the guarantee held at all 43 kill points on PostgreSQL 16 and at the 39 points on the memory store. What holds is this: the worker answers 2xx only after it has read the run row from the store, so whenever a client saw 200 or 202, the row existed after the kill, and after restart and tick it was either the finished run or NEEDS_PERSON "interrupted". Note what that means in plain words, and it is NOT "never lost" and NOT "handed to a person": an acknowledged request that was cut off is acknowledged, then NEEDS_PERSON with no notification and no stored document; the sender must poll the run state. The row keeps only the document hash, the raw document lived in memory and is gone, the tick changes the state and writes an audit record but sends nothing, and the model does not pick the request up again. A person learns of it only if the sender polls and acts (the n8n template has that state check). Making it "stored and notified" is a guarantee-class change for the owner (ESCALATIONS.md, E-door-1). "Never run twice" holds because the row is the only memory: a retry that finds a row is answered from it and starts nothing, so the model was called at most once per key in every case (0 times when the kill came before the model call). A request that was killed before its row was written was never acknowledged, and the sender's retry ran it once. Two conditions carry the guarantee and are outside this matrix: the tick must run in the deployment (without it a cut-off run stays RECEIVED or WORKING and the retry keeps getting 202), and the sender must retry with the same key when it got no answer. The loop paths with tools, proposals and execution were not killed here, so for them the guarantee is shown only by the code reading, not by this evidence.

After the final write (3 points): SUCCEEDED stays.
5. **The retry answer cannot tell a run in progress from a run that waits:** the worker answers 202 only for RECEIVED and WORKING. A run in PLAN_READY, EXECUTING or VERIFYING (and WAITING_FOR_APPROVAL) gets 200 with the state. A sender that treats 200 as "ended" is wrong for PLAN_READY, EXECUTING and VERIFYING. Seen at 11 PLAN_READY points, and at the EXECUTING and VERIFYING points of the approval path.

**Not run, not checked:**
- Request-thread points (`store.get_run` of the Runner, answer bytes on the socket) are not repeated: that code is the same on every path and is in part 1. The Runner's store is wrapped with the same CrashPoints object but no point is armed on it here.
- Reads other than `get_kill_switch`, `spend_totals` and the loop's `get_run` (`get_plan`, `get_gate_decision`, `get_redaction_map`, `audit.events`, the proposal check's store reads) are not wrapped: they change nothing; a kill at one equals the kill at the next wrapped call. `:after` of a repeated pure read is left out (same moment as the next `:before`); the first read of each kind has both.
- The approval path is NOT driven by a real approval receiver or a chat channel: the decision is recorded in the test with `Approvals.decide(record_only=True)` (what the receiver does), the card goes to the fake channel, and the kill is made in a tick child process, not in the worker. The action is a fake executor that counts calls; the verify check is a fake returning true. No real action contract was run through the HTTP executor. No rollback (verify failed) path was killed.
- Not asserted: the audit events and their number. A kill between a state write and the audit write after it is not detectable from the tables.
- A kill of two tick processes at once, a database that goes away, and a kill by signal 9 from outside were not run. The tick here runs the steps `sweep`, `reconcile` and `stuck` only, one hour after the kill (past the stuck floor of 420 s and before the 4 h approval step ends); the other steps were not run. Part 1 used a day.
- The proposal is a `create_draft_record` action of the fixture config (a reversible http contract with a rollback, so the gate asks for approval), at level "suggest", with a replay record written for the test. The k5 action `rollout_undo` could not be used: it is a `none` contract, which can never be at "suggest" (deferred.py:88).

### What could not be built, and why

Nothing was left out for lack of support, but three limits stand: (1) the approval decision is recorded by the test, not by a receiver or a chat channel, because no live service may be used; (2) the executor is a counting fake, so the real HTTP executor, its idempotency check and rollback were not killed; (3) a retry that reaches the worker while a tick child is still running was not driven.
