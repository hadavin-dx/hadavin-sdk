## How to read the table

One signed request with one key is sent to a worker process. The process is killed at the named point. Then: a new worker process is started, the tick's "stuck" step runs with a clock one day later, and the same request is signed again and sent again.

- A kill point is `<object>.<method>:before` or `:after`, with the number of the call when a method is called more than once. `store.get_run` is the read made by the request thread (`Runner.start`); `loop.get_run` is the same store method called by the agent loop; the other `store.*`, `audit.*` and `llm.chat` are calls of the agent loop (`Runtime.handle`).
- "Acknowledgement" = the client got 200 or 202 before the process died. Where a row exists, the request thread may or may not have read it before the kill (two threads race), so the table says "possible" and shows what the two runs saw. The test asserts for every case: a 2xx only together with a matching row.
- "Model calls in total" counts calls over the killed process, the restarted one and the retry (a file both processes append to).
- "seen:" lists run 1, then run 2. `r4` has one value: in run 1 the case failed before it wrote its line.

## Points that could not be reached, and why

The crash helper stops the program only at a call of an object the test hands in (the store, the audit sink, the model double). The worker has no test hook (ticket D, section 9). So these moments have no point of their own:

- **While the signature is being checked** (before the first store call). No store call happens there. The first reachable point after it is `r1`; nothing is written before it, so the end state is the same.
- **Between `_submit` and the first poll in `Runner.start`** (worker.py:130-139): not a store call. The nearest point is `store.get_run:before` call 2 (`r2`, `r4`), which is the very next store call of that thread.
- **Between the read that found the row and the answer bytes on the socket**, and a half-written answer: `r5` kills right after the read returned; a kill in the middle of writing the answer cannot be placed. A client that gets a broken answer retries, and the retry is answered from the row.
- **In the middle of a store call** (statement sent, answer not yet read): cannot be placed on purpose. Run 1 hit it by accident at `r4` (see the top).
- **Redaction, the injection check and the post of the abstain card** (agent_loop.py:412, 432, 626): not calls of a wrapped object. Each lies between two reachable points with the same row and the same number of model calls (h09-after and h10-before; h18-after and h19-before).
- **Later polls of the request thread that find the row on a chosen poll number**: which poll finds the row depends on timing. `r3` (4th read, row write slowed) and `r5` (first read that returns a row, whichever number it has) cover both sides.

## What was run on which store

- **PostgreSQL 16** (port 55433, a fresh schema per case, dropped afterwards): all 43 points, each with a real child process killed at the point (exit code 137 and the helper's marker line asserted), a second child, the real tick step and a signed retry over a loopback socket. Rows are read by plain SQL on a connection of the test's own.
- **Memory store, same process**: 39 points (the 38 points of the agent loop and the first read of the request thread). Here the helper raises an error that kills only the thread that reached the point. That stands in for a kill only where no other thread is at work, so the four other request-thread points are PostgreSQL only: on memory the loop thread would run on to its end, which a real kill never allows. One difference by design: on memory the request thread survives the death of the loop thread and always answers (503 when the loop died before the row, else 202 or 200 from the row); the test expects exactly that.
- One more case checks the table itself (19 calls, before and after, plus 5 request-thread points; unique; every wrapped method appears).

## Conclusion on "an acknowledged request is never lost and never run twice"

For the path tested, the guarantee held at all 43 kill points on PostgreSQL 16 and at the 39 points on the memory store. "Never lost" holds because the worker answers 2xx only after it has read the run row from the store: whenever a client saw 200 or 202, the row existed after the kill, and after restart and tick it was either the finished run or NEEDS_PERSON "interrupted". Note what that means in plain words: an acknowledged request that was cut off is handed to a person; it is NOT picked up again by the model. "Never run twice" holds because the row is the only memory: a retry that finds a row is answered from it and starts nothing, so the model was called at most once per key in every case (0 times when the kill came before the model call). A request that was killed before its row was written was never acknowledged, and the sender's retry ran it once. Two conditions carry the guarantee and are outside this matrix: the tick must run in the deployment (without it a cut-off run stays RECEIVED or WORKING and the retry keeps getting 202), and the sender must retry with the same key when it got no answer. The loop paths with tools, proposals and execution were not killed here, so for them the guarantee is shown only by the code reading, not by this evidence.
