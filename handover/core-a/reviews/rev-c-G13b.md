## MAJOR
1 LEAK stays and the cap fails OPEN (runmap.py:1474 and 1447): the overlap is min(10*longest+16, 16384), unchanged for short secrets. Stacked expansion per secret character: percent 3 per byte (12 for a 4-byte char); an entity 5-6 for ASCII, 10 at most; an entity wrapped in percent 11-12 ('%26%23', 2-3 digits, '%3B'); `undo()` allows 8 layers so growth is geometric ('%' written as '%25' or '&#37;' multiplies the text again per layer): no bound of 10 per character. Exact input (same as before): a 20-char secret, each char spelled '%26%23<dec>%3B' (a 'z' gives 12 per char, 240 total), starting at VIEW_WINDOW-217 in an ASCII text over 65,536 chars: it lies whole in neither window and is sent (overlap 216 < 220). Also with one entity layer on a secret over ~2,700 chars because the cap is hit. At the cap the code does NOT refuse: it silently shrinks the overlap (docstring admits it). No test covers escaped spellings across an edge (g13b_3 uses full-width chars at 1 per char). Fix: fail closed (InputTooLarge) when the spelling could exceed the overlap, or window the decoded view instead of the raw text.
2 NEW super-linear time and memory in `_touching_piece` (runmap.py:1396, 1413, 1399, 1416, 1400, 1417): `piece = left[i:]` and `piece = right[:j]` are now sliced at EVERY position before the heads/tails test (before, only on a hit): O(len^2) memcpy per gap, up to longest-1 chars per gap; longest = 65,536 gives ~2 GB of copying per gap; the deadline is read only every 256 tokens (:1390). `seen` stores every distinct piece string but the charge is capped at 64 chars (`_LOOKUP_COST`); before it was the real length. Bisect compares are uncharged. Memory input: a 10,000-char secret starting 'hunt', a 2 MB text of 'hunt' repeated, a key every 10 KB: ~12 MB of pieces per gap, ~2.5 GB total (estimate, unrun). Fix: test the 4-gram before slicing, charge the real length, bound work per gap.
3 LEAK by narrowing (redact.py:1830-1831, G12b-reg): the patch drops the core for ANY '‹' or '›' anywhere in `full`, not only an escaped `‹KIND_n›`. Input 'password=‹hunter22›' (guillemet quoting, or a password containing such a char): the core 'hunter22' is no longer registered, so a later bare 'hunter22' stays readable (E18 leak again). Fix: key the drop to the regex ‹[A-Z]+_\d+›. No test or mutant pins it either way; the patch adds no test (the 6 E9 tests are the only pins).
