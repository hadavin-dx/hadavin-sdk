# Bible extract R447 to R450 (owner HARD rules 2026-11-06; ladder order, reviewed by two independent readers, fix set 2).

**R447.** [Hadavin practice, owner 2026-11-03, order changed by the owner 2026-11-06; changing needs the owner's explicit yes] Tool ladder before custom code. THE LADDER, in this order, stop at the first rung that holds (owner 2026-11-06; every rung decision rests on dated research, a test and a cost, time and risk calculation, R450): GATE before rung 1: the project scope, the budget, the client's company size and its willingness (R445, R446), and the client's own tool or platform feature: where the client has one and chooses it (R446) it is used in place of rungs 1 to 4 for that component; it is not a rung. (1) NO-CODE and low-code tools (n8n, Make, Clay, Zapier, sheets and similar): first check what they can already do, for plumbing, triggers, connectors and workflow; a guarantee-class step (exact money, redaction, audit, approvals, tenant isolation, eval gates, no lost message) never lives inside a no-code flow, the flow calls a core module for it. (2) OUR CORE MODULES (hadavin-sdk, templates, demos; R363 and the one-source-of-truth rule): reuse what is built and tested, always before outside code. (3) EXISTING FREE or standard TOOLS used as they are: MCP servers (an existing vetted one before writing a connector; R111, R115, R350), plain RAG (GraphRAG only when a golden set shows multi-hop or relationship questions; R320), newer model features (structured output, tool use, caching, batch, long context). (4) FREE LIBRARIES and open code found online: research them, check the licence (R450), TEST them on our own corpus and hostile inputs, then build on top of them, fixing their mistakes and filling what they miss, with the notice kept. (5) OUR OWN NEW CODE, last, only for what remains and for guarantee-class steps no rung above gives. Guarantee-class steps (the 'brain') are: decisions, approval binding with a separate executor identity, redaction before the model, exact money and budget caps (reserve and settle), audit tamper-evidence, tenant isolation and least privilege, eval gates, and no lost or double-applied message. Standard-library code and configuration count as thin glue (using the rung), and beat a model call. Thin glue is under about 50 lines per component with no branching on business data; above that it is a component and gets its own row. In the RUNG TABLE the client's own tool is written as rung 0, and a rung the client has closed (R445) is written 'CLIENT-EXCLUDED, date, source' and counts as tried. No-code PLUMBING means triggers, connectors, scheduling and display; retry, dead-letter, idempotency keys and recording an approval decision are guarantee-class and live in a core module that the flow calls (an approval table in a sheet is display only). A no-code flow never holds approver or executor credentials, receives data only after redaction by our code unless it runs on the client's own instance, and is exported to git and diff-reviewed (EGM or the lead) before it is imported to the client's instance. R363 (no single dependency) stays binding for the core and for what we host; a client-chosen tool may be accepted as one-tool risk in writing (R446), and for a SaaS tool with no self-host (Make, Clay) the quote names the exit plan (export of the data plus a code alternative). Anything reusable and generic that rungs 3 to 5 produce is added to the core modules afterwards (they stay generic building blocks). Every plan, spec, ticket and brief has a ladder line (the RUNG TABLE of R448) naming the rung per component and why the rungs before it were rejected; EGM reviewers check it. Guardrails on every rung: the client chooses (R445, R446); every tool, MCP server or store sits behind a kind with a neutral default and an alternative (R363); MCP servers get an exact tool allowlist, read-only by default, with short-lived credentials (R366); tool descriptions and retrieved text are untrusted input (R196, R350); high-risk parts stay in our tested code; evals still gate (R177-R180); tool facts are re-verified within 90 days; laptop sessions use synthetic data only and our own free-trial accounts. Course link: the course builds an MCP server when more than one app needs the tool (R111); using an existing vendor server is rung 3, and building our own server for one app is not course advice. Until 2026-11-06 the order was: studio code, client tool, no-code, MCP, RAG, model features, code. Source: owner 2026-11-03 and 2026-11-06 (`..\memory\tool-ladder-before-code.md`).

**R448.** [Hadavin practice, owner HARD rule 2026-11-06, said repeatedly; changing needs the owner's explicit yes] CODE LAST. Writing our own code is the last resort, never the default. THE LADDER is R447 (owner order 2026-11-06): no-code first, then our core modules, then existing free tools, then tested free libraries built on top, then our own new code; 'thin glue and configuration' (a few lines connecting tools, no business logic) counts as using the tool, not as new code. Our own new code is allowed only for what the ladder shows no tool can give (the guarantee-class list in R447): a safety guarantee (exact money caps and reserve/settle, redaction before the model, audit tamper-evidence, approval binding with a separate executor identity, tenant isolation and least privilege, eval gates, no lost or double-applied message). GATE: no plan, design, ticket, spec or agent brief may be handed to a builder, and no ticket may enter build-start review, without a RUNG TABLE (the artifact itself carries it; planning documents carry a short one): one row per component with the need, the rungs tried, evidence (source and date, or marked UNVERIFIED), what only our code gives, and a verdict KEEP-CODE (we write it) / CUT-TO-CONFIG+GLUE (a tool does it, we only configure and connect it) / CUT (the component is dropped, nobody needs it). '80 percent' means the share of the component's listed needs (the need column, one line per behaviour) that the higher rung already provides; the ticket author counts it with the evidence, reviewers re-count it, and a doubtful count is settled by the lead. If a higher rung covers 80 percent or more, the component is cut to config plus thin glue unless a written guarantee gap with a test idea proves otherwise. KEEP-CODE is valid only if the 'what only our code gives' cell names one of the guarantees above AND names the single property the tool fails, with a reproduction against the tool (a failing test, or a doc quote with its URL); the code covers only that guarantee path, everything around it stays config and glue. A table row's recommendation is input to the client options list of R446 (the client chooses in client builds; in the demo stage we choose). A thin kind module around a chosen tool (R363) is glue and does not count against the tool's coverage. Deterministic standard-library code or config beats a model call, and a model call beats new code (so 'newer model features' in R447 comes after deterministic code). A guarantee-class step may never live inside a no-code flow, because a flow has no tests or review; no-code tools carry only plumbing, and their licence terms are checked before they ship to a client. Tool facts live in one dated shared register (the cloud handover's TOOLS.md and the studio's research files), tickets cite its lines, a table is at most one page, and components of one kind share one epic-level table. The rung decision is made inside the EGM plan-review round, not as an extra round; security, money and redaction paths keep their no-cap rule and the 80 percent cut does not apply to the guarantee itself. Cut evidence may include the running cost of keeping existing code, but replacing working code still needs the owner's yes. A task that creates no new component (a lookup, an evidence run, a review, a bug fix in existing code) writes 'CODE-LAST n/a: <reason>' instead of a table. A row marked UNVERIFIED may stay in the table, but any verdict (KEEP-CODE, CUT-TO-CONFIG+GLUE or CUT) that rests on an UNVERIFIED row must be verified (a dated source read, or a small test of the tool) before the build starts; the lead checks it. Cuts need written evidence (improve-before-replace: never discard existing working code without evidence and the owner's yes). Reviewers must ask "should this exist at all, and what higher rung covers it?"; a missing or empty rung table is a Major finding. WASTE STOP: a component whose rung table lists a higher rung at 80 percent or more is decided in the same plan-review round and gets no review round of its own. Reasons that do NOT justify code: "we already wrote the ticket", "it is cleaner", "the demo had it". Tool facts are dated; whoever touches the ticket re-checks any fact older than 90 days, and an older fact counts as UNVERIFIED. A review round here means one full pass by the reviewers on the plan or ticket.

**R449.** [Hadavin practice, owner HARD rule 2026-11-06; changing needs the owner's explicit yes] Stages are named DEMO, PILOT and PROD, in that order, and nothing else: never "dev", "staging" or "test" as a stage name in code, config, URLs, docs, tickets or tests. Demo = synthetic or sandbox data, relaxed kinds, labelled as a demo; pilot and prod keep all gates (approvals, least privilege, audit separation). Core config accepts exactly these three stage values; any other value, including "dev", is refused with a message that names the rename. Persisted values: where an old 'dev' value is already stored (config, tenant records, audit entries, hash chains), it is mapped to demo on read and history is never rewritten; the startup check refuses an unknown stage and a half-renamed flag (fail closed, never 'allowed'). The class test looks at stage positions only (config values, enum members, URLs, docs headings), not words such as developer or the ordinary word test. Pilot is the first stage with real client data and the rehearsal of any risky prod change must be written into the pilot plan. Third-party tools that use dev or staging (GitHub environments, Helm values, cloud accounts) are labels mapped to demo or pilot. A project may keep its own environment labels (for example a client's "uat") only as labels mapped to one of the three stages in the project's config; core code tests the stage, never a label.

**R450.** [Hadavin practice, owner HARD rule 2026-11-06; changing needs the owner's explicit yes] Research, test and licence gate for every rung decision, in every project, demo and core change. (a) Independent deep research each time, with dated sources, before choosing a rung: what the no-code tool, our core module, the free tool or the library really does today. (b) Calculation each time: agent hours, tokens, licence or hosting fees, client cost, and the risk if the tool changes or disappears; the numbers go in the RUNG TABLE. (c) Test before adopting: run the tool or library on our own corpus and hostile inputs and record the raw result (R448 evidence); a library that fails is fixed on top or dropped. (d) Licence check before any outside code or tool ships or touches a client: record name, version, SPDX licence, date and verdict in the register of tool facts. Not allowed without the owner's written yes: GPL, AGPL, SSPL, BUSL, non-commercial or unknown licences in anything we ship or run for a client; never copy code without its licence and notice; fair-code tools such as n8n are used for building on the client's own instance, not hosted for several clients on ours (the vendor's licence page decides); SaaS tools (Make, Clay and the like) are used only inside their terms of service and the client's data rules (R445). (e) Copies of third-party code carry their notice (THIRD-PARTY-NOTICES) and are pinned by version and hash. (f) We are not lawyers: contract text keeps the line 'not reviewed by counsel' until a lawyer has seen it; any doubt on a licence stops the work and goes to the owner. (g) PROPORTION: full research and calculation (a) and (b) are for choices that add a dependency, a service, a licence, a recurring cost or a new component, or that touch a guarantee-class step; a small choice inside code we are already allowed to write (which standard-library function, a one-line helper, a bug fix) needs only a one-line rung entry or 'CODE-LAST n/a: reason' and no research. A choice that costs less than about one agent-hour and adds no dependency is small. (h) DEMO STAGE: demos may use any tool on made-up data (R446), and a laptop-only experiment with a restricted-licence tool is allowed if nothing from it ships or is shown as ours; rule (d) binds everything we ship, run for a client or show as our product. (i) HOSTING: where the client has no infrastructure of their own, a fair-code or restricted tool is installed in an account or cloud the client owns and handed over, never kept running for several clients on our account. (j) TERMS: 'kind' = a swappable module with a neutral default and an alternative (R363); 'EGM' = the studio's independent review process (fresh reviewer agents read the work and the evidence; R374); 'the lead' = the main Claude session that coordinates and merges; 'the owner' = Veera Rakesh Kethari; 'guarantee-class' = the list in R447. (k) WRAP, DO NOT FORK: the default for rung 4 is the unmodified, pinned library plus our own wrapper module. Patching the library's own files is allowed only after the patch has been offered upstream, stays under about 200 lines, and carries a yearly maintenance cost line in the RUNG TABLE and a drop-or-replace trigger (library unmaintained for 12 months, patch grows past the limit, or a CVE unpatched upstream for 30 days). (l) LICENCES: allowlist for anything we ship or run for a client: MIT, BSD, Apache-2.0, ISC, PSF, and MPL-2.0 or LGPL used unmodified as a separate package. Everything else (GPL, AGPL, SSPL, BUSL, Elastic, Commons Clause, CC-NC, model or dataset licences with use limits, unknown) needs the owner's written yes. The check covers the whole dependency tree (a licence scanner such as pip-licenses, free), not only the top library, and for open-core products records which edition or directory is used. (m) THREE TIERS of effort: tier A (under about 30 lines of glue or config, no new dependency, no client data, no guarantee path, reversible in a day) needs a one-line rung entry; tier B (a library or tool for internal or demo use, under about 2 days) needs one source read, a 15-minute smoke test and the licence read from package metadata; tier C (client data, ships to a client, a paid or SaaS dependency, credentials, near a guarantee path, over about 2 agent-days, or a core change) needs the full (a) to (f). A fresh register line (TOOLS.md, 90 days) is the research, so repeats cost one lookup; an author other than the builder re-counts the 80 percent only for tier C. (n) 'CODE-LAST n/a: reason' is allowed only when the change adds no new file or module and under about 50 lines; splitting a component to stay under a threshold is a Major finding. (o) ENFORCEMENT STATUS, stated so nobody assumes a hook: automated today are the CODE-LAST v1 marker in general-purpose agent briefs of 300+ characters (hook) and a verdict-plus-date table line in cloud tickets (cloud_check NO-RUNG); REVIEW-ONLY (no automation yet) are the 90-day re-check, THIRD-PARTY-NOTICES, the licence scan, the 80 percent re-count, flow lint and the tier choice; lead-thread work is covered by the table in the ticket or PR and by reviewers. (p) When the research shows a reusable generic piece, it is added to the core modules afterwards (R448 keeps core generic). Source: owner 2026-11-06 (`..\memory\tool-ladder-before-code.md`).
