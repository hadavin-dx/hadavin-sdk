Sibling sweep by me: every `.lower()`, `.upper()`, `.casefold()`, `normalize(`, `re.I`/`IGNORECASE` and `\d` in src, scripts, load_tools, demo_only. No missed sibling in the casefold class. Only finding from the sweep: n2 (a different predicate).
2. **m2 (even share).** Rule `own = left if still == 1 else min(CAP, left / still)` is correct in shape: shares are equal, the last address gets all that is left, the total deadline holds. Run: 8 silent plus one good at 1.2 s all 9 tried, took < 1.5 s, passes; the cap still binds; the overrun test (a connect that ignores its own time-out) stops the call and tries nothing more. docs/limits.md matches the code in its numbers (about 1.3 s per silent address; two addresses at 12 s: 5 s). Gaps: m1 (socket creation outside the try), m4 (tests only pin an upper bound). One more observation without a finding: there is no floor on the share, so many addresses plus a short limit give a tiny share (limit 3 s, 12 addresses is 0.25 s each); a healthy but distant first address (RTT over 0.25 s) is cut off. The r7g review had suggested "a floor". Hosts with that many addresses and such short limits are not known here; I leave it as an advice, not a finding.
3. **n1 (cap).** `LOOKUP_HUNG_MAX = 8` (constants.py:118), refusal is `TimeoutError(LOOKUP_TEXT)`, a fixed text with no host name (r7h test asserts it). After threads end the count goes down (K04 mutant killed, and I read the lock logic: `finished` and `abandoned` are both set under the lock, so no double count). It does refuse a legitimate connect while 8 are hung (by design), including literals (m3). A look-up that never returns at all (a stuck resolver) would refuse every look-up in that process until restart: fail-closed, stated in the docs only as "count goes down as each ends". Concurrency hole: m2.
