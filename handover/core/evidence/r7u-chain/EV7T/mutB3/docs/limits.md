# Limits and details

This page holds the detail behind the section "What is claimed, and what is not" in the README. Skip this page unless you will read the code. Setting names, function names and test names appear in code font so you can search the code for them.

**No measured load figure is stored here.** What was not tested is listed in "What is not claimed (in full)".

**The short version, in plain words:**

1. The desk is for one program running on one computer. It has no login and listens on this computer only unless you change that.
2. Every call to the AI step, the CRM and the mail system is cut off by the desk after a short time (9 seconds at most). A call that is cut off is not stopped: it may still finish, and its late answer is thrown away.
3. At most 4 AI calls, 8 CRM writes, 8 sends and 4 reads of the keyed or blind setting run at once. If they all hang, no follow-up gets past that step until one ends; the waiting follow-ups stay in the desk's records and are shown as `stalled` in the review list (tested only for a full AI cap: `test_full_model_cap_shows_the_row`).
4. A blind mail system cannot recognise a repeated send key; a keyed one can. On a blind mail system a follow-up that may or may not have been sent is marked UNKNOWN and waits for a person; a wrong answer by that person can cause a second email.
5. A computer clock that jumps by 30 seconds or more can make the desk ask again for a follow-up that was still being sent; on the demo keyed mail system the repeated send is ignored (a real mail system may send it twice), on a blind one the follow-up becomes UNKNOWN.
6. A follow-up that the background job moves back to waiting five times in a row ends `failed` even though no email was sent (see the put-back notes below for the tests).
7. Real mail systems, real CRMs, real AI models, 10,000-request loads, power loss and a penetration test were not tested. `scripts/hubspot_probe.py` is a separate script that imports no desk module, so it does not use the desk's HubSpot adapter; the adapter's tests use a demo HubSpot server.
8. The desk records nothing about a connection that the operating system refuses before the desk accepts it; a sender that cannot retry has no other record of it.
9. The rules below are read from the code and checked by the named tests. No measured load figure is stored in this repository.
10. None of this is legal advice or a guarantee.

## What is not claimed (in full)

* This repository does not claim that no lead is ever lost, that no email is ever sent twice, or exactly-once delivery. It does not claim the desk is fit for production, and nothing here is a legal opinion. After an unclear result the desk can send the same email again with the same send key (the lead's id); a keyed demo server mail system then ignores the repeat, a real one may not.
  The licence text has not been reviewed by a lawyer.
* The same person with two email addresses is two leads: `ada+sales@example.com` and `a.da@example.com` are different leads.
  Two people sharing one address are one lead.
* A real mail system or CRM was not tested. The keyed mail system is a simulation; a real provider may remember a send key for a
  shorter or longer time. The AI step is a set of pre-written replies; nothing is said about real AI behaviour.
* **Live model step.** The desk can ask a real AI model for a label (hot, warm or cold), but only when you set `DESK_QUALIFIER=live_claude`, name a key file
  and set a price, a cost cap per run and a cost cap in total (both in US dollars; see `docs/settings.md`). Out of the box (the default `recorded` setting, which means pre-written replies) no model is called and nothing leaves
  the computer. The live step was run only against the local demo model server (`demo_only/fake_model_server.py`).
* **Every call to the AI step, the CRM and the mail system is cut off by the desk after a short time** (`Desk._bounded`). The call runs in a helper thread. The desk waits for it at most `MODEL_CALL_BUDGET_SECONDS` (9 s) for the AI step, and at most `min(send_timeout_seconds, 9 s)` for a CRM write, a send or a read of the keyed or blind setting. A call that is late is abandoned, not stopped: it keeps running until it ends on its own. Its late answer is thrown away and never reaches the desk's records, and the background job carries on with other rows. Tests: `test_reaper_survives_hung_model`, `test_hung_model_spends_the_try`, `test_late_answer_writes_nothing`, `test_blind_send_timeout_is_unknown`, `test_keyed_send_timeout_same_key`, `test_blind_crm_timeout_is_unknown`, `test_late_send_writes_nothing`, `test_late_crm_put_writes_nothing`. What a time-out does to a follow-up:
  * AI step: the time-out uses up one of the 5 automatic tries (`internal:ModelTimeout`). A person's Retry starts the count again at try 1, so one lead can be tried more than 5 times in all.
  * Keyed send or keyed CRM write: it is asked again later with the same key.
  * Blind send or blind CRM write: the follow-up ends `unknown` for a person to look at. A blind call is not started again for the same lead while its old call is still running.
* **At most 4 AI calls, 8 CRM puts, 8 sends and 4 reads of the keyed or blind setting (capability reads) run at once** (`ADAPTER_WORKER_CAPS`; abandoned calls count until they
  end, the place is reserved before the helper thread starts). When a kind is full, or a blind call for the same lead is still running, the
  row is not claimed: it keeps its age and shows up as `stalled` in the review list after `stall_seconds` (`test_busy_give_back_keeps_the_age` and
  `test_full_model_cap_shows_the_row` check the kept age and the stalled list for a full AI cap; `test_blind_call_for_lead_blocks_claim`
  checks only that the row is not claimed while a blind send for the lead runs). `/counts` and the portal summary show
  `hung_workers`. If four AI calls hang for ever, no follow-up gets past the AI step until one ends or the desk restarts; rows stay visible
  in the stalled list. An abandoned call keeps its socket and, with a paid model, may still be charged.
* **A CRM copy of the lead's stage waits for that lead's own hung call.** While an abandoned copy call for a lead still runs, the next copy for the same lead is not started (a late old stage must not overtake a newer one). That refusal is not a try. This wait is for a refusal because an old call is still running; the wait after a failed copy is a different one, see "When the copy of a lead stage to the CRM fails" below.
  * The lead waits 10, 60, 180, then 420 s between looks. The wait grows with every refusal in a row (`test_busy_lead_waits_longer_each_time` checks that the first wait is 10 s and that each later wait is longer).
  * It starts at the step of the lead's earlier failed tries: a lead with two earlier failed tries starts at 60 s, with three at 180 s. It starts afresh when the lead moves to another stage. It is kept in memory, so a restart starts it afresh.
  * The other leads are copied meanwhile, and the lead is copied once the old call ends.
  * A call that never ends keeps that lead's CRM status behind for good: the `crm_error` stays on the lead and the desk never shows "given up". It also holds one of the 8 CRM places until the desk restarts (read from the code; no test checks this).
* **A person cannot answer `not_sent` while a call for that lead is still running** (409 `call_still_running`): the old call may still
  land, so "nothing there yet" proves nothing. Wait until the `send` and `crm` counts in `hung_workers` are back to 0 and a few seconds more (the desk answers `call_still_running` until the old call has ended), look again, then answer (`test_blind_retry_waits_for_old_send`).
* **Time budget.** A follow-up counts as stuck after 30 s with the defaults. This time is called the "stuck grace": the send timeout plus 5 waits of 5 s for a locked database. The reaper puts a `sending` row back only when it is strictly older than the grace. The AI call (at most 9 s) plus saving its answer (at most 15 s: the 10 s write deadline plus one more database wait) is 24 s, strictly below the smallest grace of 25 s, so that one stage always finishes inside the grace. A constant that breaks this rule ends with a Python error (exit code 1) when the program loads. An AI adapter that declares a `timeout_seconds` that is not
  a number above 0, or above 9 s, is refused when the desk is built (exit code 4). So is a `db_path` of exactly `:memory:` (refused right after the settings are read and checked, before the folder and the lock file are made): every request thread opens its own connection, and a private in-memory database would be empty for all threads but the first. A name such as `file::memory:` is not special: the desk turns every other name into an absolute path first, so it is a plain file with that name.
* **A lock after the model answered.** If the database stays locked when the desk saves the AI answer (its time stamp or its label), the answer is thrown away
  and the try stays used up (`internal:ModelAnswerLost`), because the model was really asked; the 5-try limit then bounds how often it is
  asked again (`test_locked_stamp_cannot_ask_for_ever`, `test_answer_lost_real_lock_keeps_try`). A lock before the model is asked gives the try back.
* **A late answer to an abandoned read of the keyed or blind setting** of the CRM or the mail system cannot overwrite a newer one: each read carries
  its start time and an older one is ignored (`test_late_refresh_keeps_newer_mode`).
* A stopped desk does not wait for its handler threads or for a follow-up that is still running: that is the crash case (the stuck row is
  put back at the next start; the ten crash points cover it). A client that sends bytes slowly but steadily can hold a connection
  place until the header or body deadline ends; this costs availability only (`tests/test_slow_sender.py` drips bytes and checks the 408 at the deadline, and checks that a connection closed for room after its body was read but before the desk acts leaves nothing stored; that nothing is stored after a 408 is not tested here) and is deliberate (`tests/test_stall_eviction.py` checks that a steadily sending client is not closed early).
* Do not let another program send mail under the same send key (the lead's id): the desk assumes it is the only sender for that key.
* A crash is simulated inside the program (the test raises an exception at the point) for all ten crash points and for the eleventh, N1 (the reminder email, `tests/test_reminder_email.py`). A real process kill (the desk process ends at once, no clean-up) at a NAMED crash point was done only at D2: twice with the demo mail system over HTTP (keyed and blind), and once with a real mail catcher process that receives mail over SMTP (blind sender); the tests are `tests/test_http.py::test_crash_d2_subprocess` (keyed and blind) and the test next to it in the same file whose name starts with `test_crash_d2_subprocess_with_` (blind SMTP sender).
* Loads of 10,000 requests were not run. The desk is for one computer and one process. There is no login: it listens on this computer only unless you change `DESK_BIND`, and then anyone who can reach that address can read the desk's records (see "The portal and the desk process" below).
* No run result is stored in this repository: no count of passed or skipped tests and no result of the checks in `.github/workflows/lint.yml`. `versions.md` gives only the number of test files (92); no count of collected tests is stored. A test run skips the tests that need another operating system, a tool that is not installed, or the load measurement; the reasons are listed in `docs/tests.md` and `python -m pytest -q -rs` prints them.
* This repository does not claim anything about what happens if n8n crashes before the request reaches the desk, or about other n8n versions or set-ups.
* Reminders (when the lead owner feature is on): a lead is reminded once after the wait if its step is still before `reminder_until`, even if its follow-up email has not been sent yet, because the reminder asks whether the lead moved on, not whether the email was sent. A lead created while the feature was off has no owner, step or reminder, and the step route answers `no_state` for it; only leads created after the switch are covered. A reminder is not sent a second time: one that failed or could not be confirmed is listed for a person (`tests/test_reminder_email.py` checks one reminder over many passes, and that ten racing claims give one winner).
* If a person wrongly answers "not sent" for an UNKNOWN follow-up on a mail system that cannot recognise repeats, a second email can go.
  Nobody is told about UNKNOWN items: they stay unseen unless someone opens the review list.
* A follow-up stuck in `sending` (for example because the database stayed locked through all retries) is put back by the desk's background job (the "reaper", started by `main`, one pass every second) when it has been stuck for more than 30 seconds by the computer's calendar clock. It goes to `pending` on a keyed mail system and to `unknown` on a blind one, when the send may have started.
  * A clock step of 30 s or more forward can put back a follow-up that is still being sent. On a keyed mail system it is sent again with the same key; on a blind one it becomes `unknown`.
  * After a step backward the reaper sets the stamp of a pending or sending row that lies in the future to the new time, so such a row ages normally and is put back 30 s later (`_restamp_future` in `src/lead_desk/desk.py`, `tests/test_clock_steps.py`).
  * Exceptions, case by case: a follow-up that never sent anything (the CRM step was not finished, or the send mark was not written) goes to `pending` on either kind of mail system, or to `failed` on either kind when it has already used all 5 automatic tries (`SEND_MAX_ATTEMPTS`); a follow-up whose send may have started goes to `pending` (or `failed` at the cap) on a keyed system and to `unknown` on a blind one.
  * A person's Retry starts a `failed` follow-up again. A lock on a write after the claim normally gives the automatic try back (the follow-up goes to `pending` at once), except a lock that stops the write of a model answer (`ModelAnswerLost`: the try stays used up); a row stays `sending` for the reaper only when the give-back write is locked too (the database stayed locked through all retries of that write as well).
  * The put-back does not give the try back, so a follow-up that is put back five times in a row (the give-back stayed locked each time, or a drive was held up past the grace) ends `failed` although no email was sent and the CRM was not written (the AI step may have been asked). Restarting the desk does the same at once: the put-back function in `src/lead_desk/desk.py` serves both the reaper and the start-up sweep and sends a row whose tries are used up to `failed`. The two ends are tested in `tests/test_model_stamp_and_reaper.py` (a row at the limit ends `failed` with nothing sent; one below it goes to `pending`); no single test repeats five put-backs in a row.
  * One reaper pass may start new follow-ups for at most `REAPER_PASS_SECONDS` (10 s) and then overruns by the one follow-up it is driving (at most three bounded adapter calls of at most 9 s, plus its database writes) and by its two capability reads at the start (two deadlines): 10 + 27 + 18 = 55 s at the very worst for the drive part of the pass with the defaults and no lock trouble (the CRM copy part and the reminder part that follow in the same pass each have their own 2.5 s clock and add their own time; so a pass can take longer than the 30 s grace; the grace is measured per row, not per pass). `stop_background` waits only its own timeout (10 s); a pass that is still running ends by itself at its next check and the desk keeps track of it until it has ended (`test_stop_waits_only_its_timeout`).
* No penetration test of the desk was done.

## Counters and database rules

What `/counts` adds up: `received = new + duplicate + review + open` (`open` = a receipt with no verdict yet). A request the desk refused before a receipt existed (bad or too large) is not in `received`; it is counted apart in `rejected_envelopes`, which lives in the desk's memory and starts again at 0 after a restart. There is no "failed" verdict for a request; a follow-up that failed is counted apart (`failed_followups`). Two more counters live in the desk's memory and start at 0 after a restart: `decide_transient_errors` (a database fault that is not a lock, such as a disk error, met while deciding a receipt; the receipt stays open, the request gets an error reply, the reaper tries again at every pass, and no verdict is written for it) and `decide_integrity_errors` (a broken database rule; the receipt gets the verdict `review` with the reason `internal_unstorable:integrity`, and `ok` in `/counts` is false while this counter is above 0). A disk fault was only simulated in tests, never a real full disk. Test: `test_reconcile_counts`.

Rules of the desk's records (the database refuses these, for a database created by this version): a receipt cannot be changed or deleted, a verdict is written once, and a verdict `new` must name its lead (`test_write_once_triggers`); a lead cannot be changed or deleted (same test); a follow-up line cannot be deleted or replaced by `INSERT OR REPLACE`, and a `sent` follow-up cannot be changed (same test). A desk's records that lacks one of the database rules (the "triggers") is repaired when the desk starts; this is tested in `tests/test_migration_triggers.py`, which also drops the follow-up delete rule and checks it is back. Not proven by any test: the checks that SQLite cannot add to an existing table (the CHECK on receipts that makes a verdict `new` name its lead) exist only in books created by this version.

## Load and limits

* Burst test: many connections open at the same moment, all for the same lead (the same email under different request
  numbers). To repeat a small one, start the demo (README, "Try it") and run `python -m demo_only.burst --url
  http://127.0.0.1:8765/leads --n 100 --email ada@example.com --ref-prefix run1 --source form` (with
  `PYTHONPATH=src:.`). The address must be on this computer (`127.0.0.1`, `localhost`, `::1`) and use `http`: any
  other address ends at once with exit code 2 and one line, before any name lookup or connection (the one name that is
  looked up is `localhost`: your computer's own name list answers it when the script connects, so write `127.0.0.1` where
  you cannot trust that list; the check that nothing is sent first connects and sends no byte,
  `tests/test_r7c_burst_probe_and_names.py`). The script prints
  `SENT`, `STATUS` (for one lead sent many times expect `201=1` and `200=` all the others), `RETRIES` and then one
  last line: `RESULT sent=<n> expected=<n>` and exit code 0 when the two numbers are equal, or `MISMATCH sent=<n>
  expected=<n>` and exit code 1 when they differ; it does not print the lead count. Read the counts from
  `http://127.0.0.1:8765/counts` (or the portal Overview): for one lead sent many times, the lead count and the
  follow-up count should each be 1 (`tests/test_http.py::test_ten_parallel` checks this for 10). Right after a burst a
  follow-up can show as pending for a short time before the count of pending follow-ups returns to 0 (no length of
  time was measured here).
* Larger bursts: one measurement test is shipped, `LEAD_DESK_LOAD_N=300 python -m pytest tests/test_server_hardening.py -k measure_burst -s -p no:cacheprovider` (add `LEAD_DESK_LOAD_RETRY=1` to let the sender retry a refused connection). It prints how many connections the operating system refused and the status counts. The waiting line is 1024 connections (`LISTEN_QUEUE` in `src/lead_desk/constants.py`) and the operating system can allow fewer. No result of this test is stored here, and no figure from it is claimed for any computer.
  * A connection that the operating system refuses is never seen by the desk, so the desk records nothing about it.
* **Retry rule of the senders in this repository.** The burst script, the portal demo's burst and the load driver (`load_tools/load_driver.py`) retry a refused connection or a 503 by TIME, not by count: the first wait is 0.1 s, each wait doubles up to 1 s, the desk's `Retry-After` is honoured up to that 1 s, and no new try starts more than 30 s after the first (`BURST_BACKOFF_SECONDS`, `BURST_BACKOFF_MAX_SECONDS`, `BURST_RETRY_DEADLINE_SECONDS` in `constants.py`; tests in `tests/test_burst_retry.py`). `max_retries=0` in the burst script means no retry at all. **No total time limit for a whole run (decided to keep, stated here because a reviewer measured it):** the 30 s limit is per request, so a desk that answers first and then dies makes the load driver spend up to 30 s on each request that is still left, divided over its threads (measured: 62.7 s for `burst:8` with 2 threads; `burst:100000` could take hours). Stop such a run by hand (Ctrl+C); a run that is stopped early because the first tries got no answer ends with exit code 3 and one line that names how many requests were never sent or were given up (`STOPPED_EARLY_TEXT`): both kinds are counted in ONE place (`stopped_count` in `load_tools/load_driver.py`), the requests that were never sent (`driver:stopped`) and the ones that were already retrying when the stop was set (`gave_up` is `stopped`); tested in `tests/test_r7f_findings.py` and `tests/test_r7g_findings.py`. The stop rule applies only until the desk has answered once: a desk that answers first and then stops answering is not a stop, but the run still ends with exit code 3: every request that was given up at its 30 s limit is counted as `given_up` in the summary and in ONE line on the error output (`exit_code_and_line` in `load_tools/load_driver.py`, count of given-up, stopped and driver-error requests, each named; r7k added the driver errors, which had counted as nothing), and they show as `error` (or the last code) in `final_status`. A slow desk that used to pass the load driver now fails it; before r7j this ended with exit code 0, which let a script that reads only the exit code take a run with lost requests for a success. Exit code 0 means every request was accepted.
* A connection the desk received can be answered 503 `busy` (database lock wait over). A 503 from a lock wait may have left an open receipt; a 503 from the connection limit does not (it is written at accept time in `src/lead_desk/server.py`, before the request is read, without calling the desk). In both cases send the same request number again. `tests/test_http.py::test_ten_parallel` checks that only one email is sent for the lead (the burst command itself only counts the answers it got: it prints how many answers of each status came back and whether the number of 200, 201 and 202 answers equals the number expected; it does not read the mail count).
* The demo HubSpot server (`demo_only/fake_hubspot.py`, made-up data) reads a request body before it answers, so a late body is not reset on Windows. The exception is a Content-Length that is negative, not a plain number, longer than 7 digits or above 1 MiB: it answers 400 at once WITHOUT reading the body (reading would mean reading until the client stops); a client that really sends more than 1 MiB may therefore see a connection reset instead of the 400. A 5000-digit Content-Length is such a 400 (a digit string that long cannot be turned into a number by Python). Tests: `tests/test_codeant_fakes.py`.
* A request body shorter than the Content-Length it announced: the desk answers 408 `request_timeout` when the body has not fully arrived 10 seconds after the headers ended (`BODY_READ_DEADLINE_SECONDS`) if the sender keeps the connection open, or 400 if the sender closes it; the 408 and the 400 are both counted in `rejected_envelopes` when the stall or close happens in the body of `POST /leads`; a stall while the headers are still arriving gets 408 but is not counted. A Content-Length over the size cap, however long the number, is answered 413 straight away; this holds for the decision body of `POST /review/<id>/resolve` too (after the Host and Origin check). Two different Content-Length values in one request are answered 400. A request target that cannot be parsed is answered 400.

## The portal and the desk process

**Limits and shutdown of the desk process.** The idle-connection behaviour below is covered by `test_idle_sockets_closed_at_deadline`.

* Portal: `/api/ui` answers at most 8 requests at once; more get 503 `busy`. The count "Requests turned away before they were stored" on the Overview page (`refused_at_door`: requests refused as a bad envelope, too large, a body that timed out or a bad request reference, counted as `rejected_envelopes`; a 403 from the Host and Origin check is not counted; not the same as the source of a lead, `form` or `webhook`, called `door` in the data) is kept in memory and starts again at 0 when the desk restarts.
* The portal cannot tell a stopped desk from a lost network connection between the browser and the desk: both show the notice "The desk is offline" with the last values and paused buttons. Check that the desk process runs before you look at the network.
* **Later messages.** The lead panel lists the later messages of a lead: requests with a new request number and an email address the desk already has. It compares each one with the first record only, field by field (name, phone, company, message), and lists a field when the new value is not empty and differs. Not claimed:
  * A later message that went to "Request to check" (for example an invalid email address or a field that is not text) has no lead and never appears under "Later messages"; it is on Needs a person.
  * An empty field cannot clear a value. A change made only of extra space characters between words is not listed (runs of the space character count as one); a change of upper or lower case is listed. Other fields a sender adds are stored with the request but not listed.
  * A later message that repeats a value an earlier later message already sent is listed again.
  * The same request number sent again with different data is not a later message: the first answer stands, the new data is not stored, and it stays on Needs a person as "Same request number, different data".
  * Only the newest 50 later messages of a lead are shown, with the total; older ones stay stored but the panel does not show them. The list part of the panel's answer is at most 3,132,800 bytes (50 later messages, every field at its longest in the characters that take the most bytes); the whole answer also carries the lead and its open items.
  * Times are the desk's clock at arrival in whole seconds, not the sender's time. A later message whose request reached the desk before the first record was written (two requests at almost the same moment) is shown as "Arrived before the first record was written". When the desk clock gives a later message an earlier time than the first message, no gap is shown. Durations are rounded down to whole seconds, minutes, hours or days; the exact seconds are in the tooltip.
  * Approval mode (`DESK_LATER_MODE=approval`, off by default) records one person's choice about a later message and nothing else: the approver is a name picked from the list and is not verified, and nothing is executed by the choice. The desk does not accept, dismiss or answer a later message on its own, sends no notification and no second reply, and handles no later message automatically or with an AI step; suggested replies are not built. Nothing from a later message reaches the CRM or the follow-up email: the test in `tests/test_later_approval.py` that checks a decision changes nothing and sends nothing compares the lead, receipt and follow-up tables and the mail and CRM counts before and after.
  * Email addresses, phone numbers, messages, lead names and request numbers are masked on screen by default (each with its own eye button; a request number is data the sender chose, so it is treated as personal until shown on purpose; companies, lead owners and approver names are shown as they are). A company name can itself be a person's name (a sole trader), and it is shown and searched while names are hidden. The author decided to accept that risk, and a sender who must not be recognisable should not put a name in the company field; the "Hide names and email addresses" switch, when off, shows them and allows searching by name and by email address (while they are masked the search matches only the company and the lead number; this hides values on the page only, see the next bullet). A small eye button beside a masked value shows that one value only: it is kept in memory (never stored), hides again after 30 seconds, on Escape, when the panel closes or the page changes, and when the switch is turned on, and it does not turn on searching by name or address. On the demo controls page the lead pick list shows "Lead 1", "Lead 2" and so on while masking is on. The switch choice is kept for the browser tab's session only (session storage, not local storage), so a new session starts masked and a shown state cannot be left behind; a browser that blocks site storage starts masked and keeps a choice only for that visit. In the comparison of a later message with the first record, an empty phone or message shows as "empty" also when masked; in the Facts list an empty value has no row at all. A masked email address shows as "•••@•••••" (no character of it is kept).
  * Masking is on screen only. The answer the page reads still carries every value, lead names included (the browser's developer tools show it; checked in tests/test_portal_lead_pages.py), and anyone who can reach the desk can call `/api/ui/leads?by_email=1` and search by name or email address: the switch decides only what the pages ask for and show. The desk's own log lines print no email address, phone number or message (every log call is checked by a test); text that the Python runtime itself writes to the error output when a thread fails unexpectedly is covered only on the paths the tests run. Tests: `test_later_values_word_for_word`, `test_later_lower_receipt_number`, `test_later_review_verdict_not_listed`, `test_later_repeat_still_listed`, `test_later_reply_size_is_bounded`, `test_leads_email_search_needs_reveal`, `test_personal_hidden_rule`, `test_reveal_one_value_rules`, `test_log_calls_carry_no_values`, `test_later_messages_log_no_values`.
* Names, email addresses, phone numbers and messages are masked on screen by default; switch the masking off in the Leads page ("Hide names and email addresses") to see them and to search by name or address. The masking is a display choice of that browser: the JSON replies of the desk still carry the values (browser developer tools show them), and the desk's log output held none of the made-up values in the tests that check it (the desk-log test in `tests/test_portal_wording_and_masking.py` and `test_later_messages_log_no_values` in `tests/test_later_messages.py` send made-up values and search the log output; `test_log_calls_carry_no_values` checks every log call in `src/lead_desk`; paths those tests do not run are not covered, see the masking note above).
* Threads: the desk serves each connection on its own thread. Writing a reply has a total limit of `REPLY_WRITE_TIMEOUT_SECONDS` (5 s): the desk stops serving a client that does not read its reply after that time.
* Open files: at start-up the desk checks that the open-file limit of this computer covers `MAX_HANDLER_THREADS` (4 files per thread plus 96 for everything else; contract.md lists what the 4 and the 96 are made of). With the default 1024 threads that is 4192 open files. A computer whose hard limit is lower than that makes the desk exit with code 3; 4096 is a common default inside containers, so there raise the open-file limit of the operating system (for example `ulimit -n 8192`, or the container's own open-file setting).
  * The count is arithmetic (contract.md lists what the 4 and the 96 are made of; `test_connection_holds_counted_files` and `test_reserve_covers_its_items` check the database connection and the portal's connections); DNS lookups and the temporary files SQLite makes are not itemised in the 96. It raises the soft limit to exactly what is needed when the hard limit is unlimited or at least that, and otherwise refuses to start (exit code 3). The message names the open-file limit in force and what the desk needs.
* Exit codes (read from `main` in `src/lead_desk/server.py`): 1 a Python traceback (a constant that is out of range);
  7 the demo servers cannot be reached at start-up (EXIT_ADAPTERS_UNREACHABLE); 2 another desk holds the lock file, or
  the lock file cannot be taken for another reason (a folder, no permission); 3 the open-file limit is too low; 4 the
  desk refuses a setting (a number that is not plain digits or is outside its range, any other bad `DESK_*` value, a
  bind address that is not on this computer while a real service is set, a `db_path` of `:memory:`, a bad approvers file
  or steps file, a steps file that does not fit the steps already stored with the leads, or an AI adapter whose
  `timeout_seconds` is not a number above 0 or is above the AI call budget of 9 s; the message names the setting; an
  error that is not a refused setting never gets code 4); 5 the port could not be bound within `BIND_RETRY_SECONDS` (see
  above).
* Exit codes of the helper scripts (`scripts/`, `load_tools/`, `demo_only/`) are separate from the desk's, and no
  number has two meanings among them: 1 a check ran and did not hold (or n8n answered with an error); 2 a bad command
  line, a bad input or a name that is not exactly one thing; 3 the thing the script talks to cannot be reached or
  answered nonsense; 4 a setting or path that cannot be used (also: `load_tools/check_invariants.py` refuses a log
  with more rows than a run can make; the one exception is `scripts/run_real_check.py`, which ends every refusal at its
  start with 2, a refused setting included, as `docs/settings.md` says); 6 the person answered no, or nobody could answer (nothing was called); 7 the
  desk cannot reach its sender at start-up. `tests/test_r6_refusals.py::test_shared_exit_code_pairs_are_pinned` pins
  these numbers and `tests/test_r7_inputs_and_replies.py` checks that no script ends with a bare number. The reset
  and start scripts (`scripts/reset.sh`, `reset.ps1`, `reset_check.py`) keep their own family because shell scripts
  and tests read it: 3 the desk still runs (or that cannot be told), 4 something still answers on a port or the lead
  book path is refused (two meanings of 4 in the same script, told apart by its one message line), 5 and 6 are
  `reset.sh` refusals about the pid files. They cannot be renumbered without breaking `tests/test_reset_scripts.py`
  and every shell script that reads them.
* A key or password (a file line or an environment value) must be at least 8 characters of plain printable ASCII with
  no space, tab or control character. A key with a non-ASCII character is refused in the file reader and for the
  environment value, before any money is reserved and before any connection is made. A TLS setting that weakens the
  check (no host-name check, no certificate check) is refused when the connection is made, not only when the object is
  built, and a CA file together with a ready-made TLS context is refused.
* Stopping: Ctrl+C or SIGTERM stop the background job first and then give the lock file back. A second signal while that runs is ignored on purpose, so it cannot cut a step short. If the desk is still there after about 10 seconds, stop it by force (`kill -9` on Linux; on Windows, end the process); the lock is dropped and the next start puts every unfinished follow-up back.
* Two limits apply. (1) At most `MAX_CONNECTIONS` (256) connections can be in their reading phase (request line, headers, body) at one time; a connection stops counting when the desk starts writing its reply, so a thread that is still finishing a follow-up does not count here. (2) At most `MAX_HANDLER_THREADS` (1024) handler threads exist in total: a thread counts from the moment it gets a connection until it ends, so the reply write, the draining and the follow-up count too. When either limit is reached and nothing can be closed to make room, the new connection gets 503 `busy` and nothing is stored.
* Idle connections: a client that opens connections and sends nothing holds a place until the header deadline (10 s), then gets 408 and is closed (`test_idle_sockets_closed_at_deadline`). While they hold the 256 places, a valid request gets 503 `busy` (that is the backpressure; send it again).
* Deadlines: request line plus headers must arrive within `HEADER_READ_DEADLINE_SECONDS` and the body within `BODY_READ_DEADLINE_SECONDS` (10 s each, measured in real time from the start of that phase, however slowly the bytes trickle in); a stalled sender gets 408 `{"error":"request_timeout","receipt_id":null}`, and nothing was stored, so the same request number can be sent again.
* Making room: when 256 connections are being read, the oldest one that is still being read (headers or body) and has sent no byte for `EVICT_MIN_IDLE_SECONDS` (2 s) is closed with no reply (its sender sees a dropped connection, nothing was stored, and it must send the request again; the same request number is answered by the desk as a replay, with the same stored answer). A connection that keeps sending is not closed this way (`tests/test_stall_eviction.py` checks a crowd that sends a byte every 0.1 s and one whose work has started).
  * A connection is also safe from the moment its whole request has been read, parsed and checked (JSON and envelope) and the desk starts acting on it. When none can be closed, the new connection gets 503 `{"error":"busy","reason":"busy"}` with `Retry-After: 1`. That 503 is written before any receipt exists, and it is a different 503 from the ones for a database lock (`/leads`) and for more than 8 portal requests at once (`/api/ui`, body `{"error":"busy"}`).
* Keep the desk off networks you do not trust. A `DESK_BIND` of 0 (or another all-zeros form, such as four zeros separated by dots) means every network address of the computer; the desk treats it as reachable by others. Close the portal while you run a load test: every open page asks the desk for its numbers every few seconds.

## What the checks do not cover

The scan for hardcoded literals is a safety net, not a guarantee. Look by eye for: compressed IPv6 addresses (for example `fe80::1`),
host names that end in a word not in the scan's list, UNC paths (`\\server\share`), and bare port numbers. Numbers and ports are NOT checked by that
scan; they live in `src/lead_desk/config.py` and `src/lead_desk/constants.py`. Base64-encoded words are not covered by the optional scan for caller-supplied terms. The list of allowed matches (`exceptions.txt`) allows test function names of 40 or more characters anywhere under `tests/`, because the scan reports only the matched text and cannot tell a `def test_...` line from other text. Whole-file allowances (the web addresses in `constants.py`, the 40- and 64-digit hashes in the workflow and lock files) are not checked line by line by the scan.

## When the copy of a lead stage to the CRM fails

The copy of a lead's stage (and owner) to the CRM is tried again, not given up at once: after a failed try the desk waits 10, 60, 180 and then 420 seconds before the next one (five tries in all, about 11 minutes). This is the wait after a failed copy; the wait after a refusal because an old call is still running is a different one (see above). The waits are counted on the desk's own clock, so a restarted desk starts with no wait left (the waits are kept in memory only, in `_mirror_not_before` in `src/lead_desk/desk.py`). The number of tries already made is kept in the database, so the waits continue from that point and the five tries in all still apply. After the fifth failure the desk gives up on that stage: the lead's side panel shows the chip "Not copied" with a note, and the desk does not try again by itself. Only a later stage restarts the copy: moving the lead to a later step (by hand, or the automatic step after the follow-up) resets the count. A lead that already is at the last stage has no later step, so it is not copied again; the note says so. The five tries and the giving up are tested in `tests/test_mirror_gate.py` (with a fake clock). That test checks that the tries follow the constant `MIRROR_RETRY_WAIT_SECONDS`; it takes its expected times from that constant and not from the literal values 10, 60, 180 and 420. The notes under the chip (the note after a give-up and what it says about a later stage) are tested in `tests/test_stage_confirm_browser.py`; no test asserts the chip label "Not copied" itself (it appears only in the portal script `leads.js`); the count going back to 0 on a later step is tested in `tests/test_mode_safety.py` (the test that a new stage starts the copy again after a give-up).

## Which CRM stage things the desk touches

> **WARNING: this write can start automations in the CRM you connect.** When lead stages are on, the desk writes the contact's lead status field (in HubSpot `hs_lead_status`). Any automation that watches that field (a workflow, sequence, lead rotation, scoring rule, notification, integration or report) may react to the desk's write, for example by emailing the contact, creating a task, changing the owner or sending a chat alert. The desk neither sees nor controls those automations, and it does not know what the automations of the CRM's owner do. The feature is OFF unless `DESK_LEADFLOW_FILE` is set to a file; the desk writes the lead status value named in that file's stage list and, when the lead's owner has a CRM owner id, that owner id (`tests/test_lead_crm_copy.py` checks that the HubSpot request body holds these two properties and nothing else). **Required before you point this at a real CRM:** the CRM admin lists every automation that reacts to lead status changes and confirms each one is safe or switched off, and the first test uses one made-up contact. The desk has no sign-in, so any program that can reach its port could cause this write (the step route) or create contacts and send mail (`POST /leads`, the review routes). With any real service set (a real CRM, the real mail sender or the live AI step) the desk therefore starts only on a loopback address and refuses any other `DESK_BIND`.

A CRM keeps several different "stage" fields. The desk writes only one of them, and only when a lead stage file (`DESK_LEADFLOW_FILE`) is switched on.

| CRM field | What the desk does | Side effects in your HubSpot |
|---|---|---|
| **Lead stage** (the desk's own wording) = in HubSpot the contact property "lead status" (`hs_lead_status`) | **Written.** Each lead stage in the file names the lead status value to copy (the demo file uses `NEW`, `ATTEMPTED_TO_CONTACT`, `CONNECTED`, `OPEN_DEAL`). | **Yes, possibly.** Any automation that watches this field reacts to our write. The desk cannot see or control that. |
| Lifecycle stage (`lifecyclestage`: subscriber, lead, customer and so on) | Not written by the desk. | None from the desk. |
| Lead pipeline stages (HubSpot's separate Leads object) | Not written by the desk. | None from the desk. |
| Deal stages (the Deals object) | Not written by the desk. | None from the desk. |
| Other CRMs | Only that CRM's own status field, and only if its adapter maps the lead stage to it. | Same warning: automations on that field react. |

The three "Not written by the desk" rows rest on two facts in the repository. First, `src/lead_desk/crm_hubspot.py` calls only the contacts and contact-search paths of HubSpot (no lifecycle, lead pipeline or deal path). Second, `set_fields` in that file builds a body of only `hs_lead_status` and, when the CRM owner id is not empty, `hubspot_owner_id`; `tests/test_lead_crm_copy.py` checks that the stored contact of the demo copy of HubSpot then holds those two values, and that the request body of `set_fields` holds those two properties and nothing else.

Not checked here: whether HubSpot's own contact creation or the automations on an account set other fields. Also not checked: the default lead status options of a HubSpot account. This repository does not contain them, and an account can rename or add options, so the file must use values that exist on the account.

The probe script described in `docs/hubspot-probe.md` makes the owner write and the lead status write (`OPEN`) as two separate calls. It imports no desk module, so it does not use the desk's HubSpot adapter, and it does not make the desk's own combined call.

**Name look-up of a mail host.** The mailbox read (`src/lead_desk/imap_count.py`) and the mail sender (`src/lead_desk/smtp_provider.py`) look up the host name and connect inside one time limit (`src/lead_desk/netconnect.py`): a name server that does not answer ends the call with the same time-out error as a silent mail server, at the limit and not later. A look-up that is still running when that happens is left to finish by itself in a helper thread; it holds no connection and no secret. **The limit on look-up threads:** at most `LOOKUP_HUNG_MAX` (8) look-up threads run at once, counted from the moment a caller reserves a place (under a lock, before the thread starts) until the thread ends, whether or not its caller still waits (r7j: r7h counted only look-ups already given up, so many callers at the same moment could start more than 8). While 8 run (a dead name server, or more than 8 callers at the very same time), a new look-up is refused at once with the same time-out text and no new thread is started, and the count goes down as each look-up ends (`hung_lookups()` in `netconnect.py` shows it). So the number of look-up threads is never more than 8. An IP address written in digits (without a `%` zone) needs no look-up thread: the system itself decides it with the flag `AI_NUMERICHOST` (which never asks a name server, so it cannot hang), for every form it accepts (`127.0.0.1`, `127.1`, `0x7f.1`, `2130706433`, a form with a leading zero (read as octal), `::1`); the name `localhost` is answered at once by the calling thread with ONE address, 127.0.0.1 (IPv4 only; `::1` is not added, r7k: a refused `::1` had replaced the time-out error); the limit never refuses either. **Which error wins:** when one address ends in a time-out and a later address is refused, the time-out is raised (a run with a total time limit ends with the time-out); with no time-out the error of the last address is raised. If a look-up thread cannot be started, or fails after it began, its place is given back once (r7k: it was given back twice and the cap could drift above 8). A machine that lacks an address family (no IPv6) fails that one address, and the next address is tried. A look-up that returns no address ends with the same fixed text as every other failed look-up. A host name that the look-up itself refuses (a part of more than 63 characters, an empty part such as `a..b`, a character that is not text, an empty name, or a name the name server does not know) ends the call with one fixed error text, `the host name cannot be looked up`, with no host name and no Python error name in it; the mailbox read then ends with its usual line `the mailbox could not be read` and the mail sender with one unreachable refusal, and nothing is printed to the error output. The mailbox host (`REAL_IMAP_n_HOST`) is checked when the settings are made, by the same rule as the mail sender's host: ASCII letters, digits, hyphens and dots, parts of at most 63 characters; ASCII upper case is allowed (the mail sender's settings turn it to lower case), and any non-ASCII character is refused, also one that lower-cases to an ASCII letter such as the Kelvin sign (the text that is checked is the text that is looked up). Web addresses in the settings (`DESK_LIVE_BASE_URL`, `DESK_HUBSPOT_BASE_URL`) and the `REAL_*` mail host settings follow the same rule: plain ASCII only: `scripts/run_real_check.py` refuses a bad one with exit code 2 and one line before the Start question. **Several addresses:** a host name can have several addresses (for example an IPv6 and an IPv4 one). Each address except the last gets the least of three numbers: `CONNECT_PER_ADDRESS_SECONDS` (5 s), the time left, and an even share of the time left (the time left divided by the number of addresses not yet tried, this one included); the last address gets all the time left; the whole call never takes longer than the limit it was given. So every address gets a turn: with a 12 s limit and eight silent addresses plus a good one, each silent address waits about 1.3 s and the good one is tried; with only two addresses and a 12 s limit a silent first address waits 5 s. A socket is closed on any error. Tests: the `test_f6_*` tests of `tests/test_r7f_findings.py`, `tests/test_r7g_findings.py` and `tests/test_r7h_findings.py`. The load driver's look for a listener (`desk_listening`) uses the same function, so its 1 s limit includes the look-up of the host name; `scripts/reset_check.py` connects to the fixed address `127.0.0.1` (no look-up) and is not changed.
