# Why this code exists

The question for every part: is there a ready-made tool that already does it? The rule followed: try a no-code
workflow tool first, then the Python standard library, then a free library or program, and write own code last, and only for what a tool does not give.
The order the author aimed for: (1) a workflow tool with no code (n8n), (2) the standard library, (3) a free library or
program, (4) own code. This table says where each part ended up and what only the own code gives. "Not checked" means
that tools were not compared for that part in this repository; there is no claim that no tool exists. Terms (atomic insert, UNIQUE key, test doubles, Host and Origin check, CRM dump, UNKNOWN) are explained in the README under "Words used here" and in `docs/tests.md`. Also used here: a demo server is a demo replacement for a real service; idempotency means that doing an action twice has the same effect as doing it once; an outbox is a list of messages written down first and sent afterwards.

Only n8n was compared for the main question (the first row); no other tool was evaluated for any row marked "Not checked".

## Where another service plugs in

The desk talks to three things through three interfaces in `src/lead_desk/contract.py`: `Crm` (the customer database), `Outbox` (the mail sender) and `Qualifier` (the AI step). Each has a demo server in `demo_only/` and the kinds that can be selected are closed lists in `src/lead_desk/constants.py`: `CRM_CHOICES` (`fake`, `hubspot`), `OUTBOX_CHOICES` (`http`, `smtp`, `smtp_provider`) and `QUALIFIER_CHOICES` (`recorded`, `live_claude`). `src/lead_desk/loader.py` turns the chosen kind into an object. To use another CRM, mail service or AI service, do all of these (the licence in `LICENSE` lets you run the software for evaluation but not change it, so changing it needs the author's written permission; one test, the one in `tests/test_mode_safety.py` that checks every kind is listed in the places that describe it, checks only that the kind lists in `constants.py`, `CRM_FIELDS_SENT` and `real_services` agree; it does not check that your module, your `loader.py` branch or your adapter exist or work, so go through all the steps yourself):

1. Write a module that implements the interface (see `src/lead_desk/crm_hubspot.py` and `src/lead_desk/smtp_provider.py` as examples)
2. Add its name to the tuple in `constants.py` (and, for a mail kind that stays on this computer, to `OUTBOX_STAND_INS`)
3. Add one branch for it in `loader.py`
4. Make sure `Config.real_services` in `config.py` counts it as a real service, so the banner, the demo-tools gate and the loopback-only bind rule apply
5. For a CRM kind, add its entry to `CRM_FIELDS_SENT` in `portal_api.py`, which says which lead fields it is sent and drives the data page
6. The interface adapters that talk to the demo servers live in `src/lead_desk/adapters.py` and the demo servers themselves in `demo_only/`; a real kind goes in its own module under `src/lead_desk/` and should not import from `demo_only/` (`test_no_demo_only_outside_loader` in `tests/test_hygiene.py` fails when any `.py`, `.sql`, `.md`, `.txt` or `.toml` file under `src/` other than `loader.py` contains the text `demo_only`).

This demo ships adapters for one CRM service (HubSpot) and one AI service (`live_claude`, which calls one vendor's API); mail has the vendor-neutral `smtp_provider` kind. The tests run these kinds against demo servers only; `scripts/hubspot_probe.py` is a separate script that you run yourself against a free HubSpot account (`docs/hubspot-probe.md`); no run of it is recorded here. No second CRM or AI service is built here. (IMAP counting is not one of the three interfaces: the real-services script uses it to count mails in your mailboxes.)
