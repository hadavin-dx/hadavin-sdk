# The portal

Two words to keep apart: the **lead stage** shown in the portal (New, Contacted and so on) is a step in following up one lead, taken from the lead flow file (`DESK_LEADFLOW_FILE`). It has nothing to do with how the desk is run (as a demo or as a live system).

Open http://127.0.0.1:8765/ui/ in a browser while the desk runs. It shows the desk's records on these pages:

* **Overview**: a summary that counts each received request once, in one of four groups: New, Repeat (the verdict `duplicate`: a second request under a new request number with an email address the desk already knows), Request to check or Not decided yet.
* **Leads**: the leads, with a "Hide names and email addresses" switch (described below). A lead's side panel shows a "Next step:" line for a failed or unknown follow-up and lists the lead's later messages: each new request from the same email address, when it came, how long after the first one, and what it says differently.
* **Needs a person**: incomplete requests, and follow-ups that failed or whose outcome is unknown. It also has tabs for items that are only waiting and for information.
* **Request log**.
* **Data and AI**: what the desk stores and what the AI step (the step that rates a lead hot, warm or cold) receives.

**The "Hide names and email addresses" switch changes only what is shown on screen.** The desk still sends every value to the browser in its JSON replies (the data the page script reads), so a person with the browser's developer tools can read them. By default lead names, email addresses, phone numbers and messages are masked on screen. The switch turns the masking off, so you can see them and search by name or address; the choice lasts only for that browser tab's session. While values are masked, the search matches only the company and the lead number, and request numbers are not searched. A small eye button beside a masked value shows that one value for up to 30 seconds; search by name or address stays off.

How this was checked: the tests in `tests/test_portal_layout.py` and `tests/test_portal_wording_and_masking.py` check the masking on the desk's list reply, and a test reads the page script's text for the masked setting. One browser test, in `tests/test_portal_lead_pages.py`, types a name into the search box while the values are masked and gets no match, then turns the masking off and finds the lead; it is skipped when Playwright is not installed. A test in `tests/test_portal_wording_and_masking.py` found none of a made-up lead's values in the desk's log output. Only that log was checked; other logs were not.

When every part is a demo server (no real CRM, no real mail sender, no live AI step) but the demo extension (the optional `demo_only` folder) is not present, a banner reads "Every lead is demo data. The demo CRM and demo mail are not connected. Nothing here is sent to real customers or real systems."

When any real service is connected, a warm-coloured banner reads "Real services are connected" and names them (CRM, mail, AI step); the demo extension is then not loaded at all.

The pages read the desk's records through a second, read-only database connection (one test tries a write through it and the write fails); the buttons that retry or resolve an item call the same `/review` web addresses as the rest of the desk.

The page cannot tell a stopped desk from a lost network connection, so both show the same notice.

While the desk does not answer, or answers with a problem, the pages keep showing the last values and the Retry and "I checked" buttons are switched off, with the line "Actions are paused until the desk answers." They work again when the desk answers. The buttons pause when any request fails to reach the desk, or when the summary or the review list answers with a server error; a server error on the Leads list or the Request log alone does not pause them.

In the Leads list and the Request log, the follow-up column shows the email state only; a lead whose CRM entry is unclear shows "Waiting for the CRM check" and a second label, "CRM not confirmed".

**What writes:** viewing the pages, and every `GET /api/ui/...` web address (a GET only reads), never changes anything. The Retry button and the answer buttons ("I checked: it was sent" and "I checked: it was not sent" on a follow-up card; "The CRM entry is there" and "The CRM entry is not there" on a CRM card) write, through `POST /review/...`; if you press "I checked: it was not sent" and the email was in fact sent, the desk may send it again, and a mail system that does not report sent mail cannot stop that. Three more controls write: the Move control for the lead stage in a lead's side panel (when a lead flow file is set) writes through `POST /leads/<lead id>/step`; the Approve and Deny buttons (approval mode only) and "I checked the mailbox" on a reminder card write through `POST /review/...`.

When the demo extension is loaded (only when every part is a demo server, which is the default), `POST /api/demo/crash` and `POST /api/demo/burst` are also available. They need no login, so anyone who can reach the desk can use them: `burst` writes made-up leads to the desk's records (it sends test requests to the desk's own lead address), while `crash` sets or clears a flag file that makes the desk stop on purpose at a chosen point, and does not touch the leads.

Every request, including the pages, must come with a `Host` header (the line of a web request that says which name the caller used) that names this computer or its bind address, or a name from `DESK_ALLOWED_HOSTS` (see `docs/settings.md`). A request is refused with the web error 403 before anything is read when its `Host` is foreign, or when it comes from a page on another address (its `Origin` header). The exact routes are in `contract.md`.

**What the Host and Origin check does and does not do.** It is meant to stop web pages in a browser: a page on another web site, and a web site that tricks the browser into talking to this computer under another name ("DNS rebinding": the site makes your browser believe the desk lives under a name the site controls). The tests (`tests/test_portal_api.py`) send hand-made foreign `Host` and `Origin` headers and check the 403; no test drives a real cross-site page. It does NOT stop a person or program that can reach the desk's address and sends the right `Host` header by hand. There is no login. So keep the desk on `127.0.0.1` (the default). If a container (n8n in Docker, for example) must reach it, bind to the one address that only your container network reaches (the Docker bridge or host address), never to the all-zeros address (every network connection of the computer). Also put the name the container uses for the desk into `DESK_ALLOWED_HOSTS`, or every request gets 403. This is possible only while every kind is a demo server: with any real service the desk refuses every bind that is not this computer's own address (a loopback address such as `127.0.0.1`). A bind to any other address than this computer's own exposes every lead (names, e-mail addresses, phone numbers, messages) to everyone who can connect, and the desk prints a warning at start-up when you do that. Close the portal while you run a load test: every open page asks the desk for its numbers again and again, every few seconds.
