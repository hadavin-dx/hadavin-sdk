# Crash points, promises and tests

This page holds the detail behind the short summary in the README. "The desk" is the lead-handling program in this repository (README, "Words used here"). Words such as keyed, blind, demo server, receipt and UNKNOWN are explained there too.

## How to run the tests

The tests need development tools, installed from a lock file (a file that fixes the exact version of every package) into a separate folder named `.venv`, so that nothing else on your computer changes.

Windows PowerShell (Python 3.13 matches the lock file), with the `.venv` folder switched on (the README, section "Try it", shows how):

    python -m pip install --require-hashes -r requirements-dev-win.txt
    python -m pytest -q                                  # the tests

Linux (Python 3.12 matches the lock file), with the `.venv` folder switched on (the README, section "Try it", shows how):

    python -m pip install --require-hashes -r requirements-dev.txt
    python -m pytest -q                                  # the tests

SonarQube is a code-quality service. One automatic check (`.github/workflows/sonar.yml`) uses it and also measures which lines of the code the tests run. On Linux, instead of the install line above, install the dev lock and the coverage lock (it adds `pytest-cov` and `coverage`) with one pip command, as that check does. Then add the coverage options:

    python -m pip install --require-hashes --only-binary=:all: -r requirements-dev.txt -r requirements-coverage.txt
    python -m pytest -q --cov --cov-report=xml:coverage.xml

The settings are in `pyproject.toml` (`[tool.coverage.run]`); the report `coverage.xml` is read by the SonarQube scan through `sonar.python.coverage.reportPaths`. The browser tests skip without Playwright, so lines that only the browser tests run are counted as not covered.

The desk alone: `PYTHONPATH=src python -m lead_desk.server`. The crash scene: `PYTHONPATH=src:. python scripts/crash_desk.py` (the `.` lets Python find the `demo_only` folder; with `PYTHONPATH=src` alone the desk stops with "the folder demo_only is missing"; the demo server must be running first: `PYTHONPATH=src:. python -m demo_only.fakes_server --outbox keyed`) prints the path of a flag file. Write a crash point name (for example `D2`, one of the points in the table under "What each promise rests on") into that file, and the next time the desk reaches that point it ends at once. On Windows set `PYTHONPATH` with `;` between entries when two are needed (`src;.`); the Linux form was run, the Windows form was not run. The tests set the path for their own processes. In the command that starts the demo mail system, writing `blind` instead of `keyed` starts a mail system that cannot recognise a repeated send.

The desk's settings (the `DESK_*` names, plus the extra names of the real-services script and `N8N_URL`, `N8N_API_KEY_FILE` and the `DPLD_*` names; n8n's own `N8N_PORT` and similar are in `docs/n8n-recipe.md`) are in `docs/settings.md`; the exit codes of the desk are in `docs/limits.md`.

The automatic checks in `.github/workflows/lint.yml` are: ruff (style), mypy (types), bandit (known insecure patterns), a schema check, gitleaks (secrets and other leaked values, on the files and the history), a scan for hardcoded addresses, links, absolute paths, e-mail addresses and long tokens, and the test suite (without the browser tests, which skip there; see "Browser tests"). Three more workflows exist. `.github/workflows/codeql.yml` runs GitHub's CodeQL scan (Python, the portal's JavaScript and the workflow files themselves). `.github/workflows/semgrep.yml` runs the open-source Semgrep scanner (see "Semgrep" below). `.github/workflows/sonar.yml` is described with the review services below. `.github/dependabot.yml` asks for version updates of the GitHub Actions. A test (`test_workflows_are_pinned_and_limited`) fails if a workflow uses an Action (a ready-made step taken from another repository) that is not pinned by its full commit SHA (the id of one exact version), has no read-only top-level `permissions:` block, or uses a trigger that passes secrets to pull-request code. Two review services read the pull requests once the author has switched them on in their own settings: CodeRabbit (configured by `.coderabbit.yaml`) and SonarQube Cloud (a scan run by `.github/workflows/sonar.yml`, configured by `sonar-project.properties`; it uses the repository secret `SONAR_TOKEN`, and SonarQube Cloud's automatic analysis must stay off for this project). These files only configure the services; whether a service is switched on, and what it found, is not stated in this repository. No run result is stored in this repository: none of CodeRabbit, SonarQube Cloud, CodeQL, Semgrep or the lint workflow. `tools/hygiene.py` also has an optional scan for a list of terms that the person running it supplies; it does nothing without that list. The demo needs no secrets and no `.env` file; the real-service scripts read their secrets from files you name.

## Semgrep

`.github/workflows/semgrep.yml` runs the open-source Semgrep scanner (its own pinned, hash-checked install in `requirements-semgrep.txt`; no account and no token; usage reporting is switched off, see the network paragraph below) on every pull request and every push to main. It reads the rule packs `p/python` and `p/javascript` from the public Semgrep registry over `src`, `scripts`, `load_tools`, `tools` and `n8n`, and fails the job on a finding of severity ERROR. After the install the job runs `pip check` and `semgrep --version`, so that a package missing from the lock file is reported as an install problem and not as a finding. The findings are printed in the job log only (no code-scanning upload). It belongs with the checks of `lint.yml` and the tests, and it needs the five folders above (a missing folder makes Semgrep exit 2, which the job tries up to three times in all before it fails with a message naming the possible causes). **Network use of the job:** pip downloads the packages of the lock file from the Python Package Index file hosts (every file is checked against its hash); `actions/setup-python` may download a CPython 3.12 build (GitHub-hosted releases of Python builds) when the runner does not already have it; Semgrep downloads the two rule packs from the Semgrep rule download service (a host name that ends in `.dev`) at every run; checkout reads this repository from GitHub. The workflow file names no other host (read from the file; no network capture was made, so this is not measured), and it sets `--metrics=off` and `--disable-version-check` to switch off Semgrep's usage report and version check. Tests in `tests/test_nosemgrep_form.py` run the real scan step against a fake `semgrep` script (only exit 2 is retried) and compare the parsed workflow with an exact whitelist: the triggers, the permissions, the concurrency block, one job on `ubuntu-24.04` with a time limit of at most 20 minutes, exactly five steps with exactly the expected keys (no `if`, `shell`, `working-directory`, `continue-on-error`, extra `env` or extra action), the two Actions pinned to the same commit ids as `lint.yml`, the install command word for word, and the scan command word for word (so a new flag, a `--config=...` or `--exclude=...` form, another pack or a missing folder fails). They also refuse an expression such as `github.event.`, `github.head_ref` or `github.ref_name` inside a `run:` step and any secret or token reference. These tests do not prove the workflow is safe or that it scans correctly on GitHub; they pin its shape and the retry logic (against a fake `semgrep` script).

**Status of the scan:** no run result is stored here. **A green job alone does not prove that rules ran:** a job can end green with no rules loaded or no files read. The proof is the log line "Ran N rules on M files": after any change to the packs or the folders, read it and check that N and M are not zero and are plausible. This workflow has no check of its own for those numbers. `tests/` and `demo_only/` are not scanned, and findings of lower severity were not looked at. The rules are fetched live, so a later run can give other numbers. If a run fails on a finding that already exists, fix the code or suppress that one finding as described below in a separate change.

**Licence and the public log:** the licence terms of the rule packs were not read or checked for this repository; the author agreed to use them here (the workflow loads only the two packs `p/python` and `p/javascript`). The job log of a public repository prints the rule ids and rule messages of every finding, so anyone can read them; the files in this repository contain no copy of any rule.

**What is scanned, and what is not:** `tests/` is left out on purpose: it holds planted fake secrets, hostile inputs and deliberately insecure code that exist to be caught by other checks, and Semgrep would report them. `demo_only/` (fake services and a demo page) is left out because it is not code the desk runs for real. This is a decision made without a scan result; add either folder to the scan command in the workflow and in the command under "Run it on your own computer" if you want them read. `n8n` holds 3 JSON files (the workflows) and is in the command only for completeness: Semgrep is not expected to find anything in the n8n workflows (a JSON file holds the JavaScript of a Code node only as text inside a string); this was not tested here. A comment cannot be put in JSON either, so there is nothing to suppress there.

**Exit codes of the scan** as the workflow handles them (`.github/workflows/semgrep.yml`): 0 = the job passes; 1 = the job prints "findings above" and fails (findings are never retried); 2 = the job tries again, up to three tries in all, 20 seconds apart, then fails (this retry is tested in `tests/test_nosemgrep_form.py`); any other non-zero code is printed as a tool or network error, not a finding, and the job fails. The rules are fetched live and cannot be pinned, so the registry can change what this check reports without any change here: keep it out of the required checks, and if the job fails with exit 2 after three tries, re-run it later.

**Run it on your own computer** from the repository root, in a Python 3.12 virtual environment, with network access (the rules are downloaded): on Linux x86_64 `pip install --require-hashes --only-binary=:all: --no-deps -r requirements-semgrep.txt`, anywhere else `pip install semgrep==1.185.0` (the version pinned in `requirements-semgrep.in`), then `semgrep scan --metrics=off --strict --error --severity ERROR --config p/python --config p/javascript src scripts load_tools tools n8n`. The job adds `--disable-version-check` (no check for a newer Semgrep); on your computer you may leave it out.

**To suppress one wrong finding:** write `# nosemgrep: <rule-id> <reason>` in Python, or `// nosemgrep: <rule-id> <reason>` or `/* nosemgrep: <rule-id> */` in JavaScript, on the line of the finding or on the line above it (for a finding that spans several lines, the first line), with the rule id the log printed, for example `# nosemgrep: python.lang.security.audit.dangerous-subprocess-use.dangerous-subprocess-use the command is a fixed list`. The short spelling `nosem` works the same way in Semgrep and follows the same rule. A suppression without a dotted rule id is refused by a test (`tests/test_nosemgrep_form.py`): Semgrep reads a bare `nosemgrep` or `nosem`, and a colon with nothing after it, as "hide every finding on this line"; it also reads `nosem` followed by any letters, in any upper or lower case, and with the long s `ſ` (U+017F) in place of the `s`, as a suppression, so the test refuses those spellings too. A tab after the colon is read like a space (the id after it is used), so `nosemgrep:` TAB id is accepted by the test like the space form. (The `--ignore-gitleaks-allow` switch of the lint job is a different thing: it concerns the gitleaks secret scan only.) The author is meant to approve any suppression in the pull request; nothing in the repository enforces this.

**To bump the Semgrep version:** follow the comment at the top of `requirements-semgrep.in`. Dependabot is set up for GitHub Actions only, so it covers none of the lock files, this one included; the author is meant to check for a newer version when a Semgrep security advisory appears or about once a quarter (a stated plan, also in `requirements-semgrep.in`; nothing in the repository enforces or reminds it). The lock files of this repository were made by two tools: `pip-compile` made `requirements-dev.txt`, and `uv` made the other lock files (`requirements-dev-win.txt`, `requirements-coverage.txt`, the two browser locks and `requirements-semgrep.txt`); the uv version is written down only for the coverage lock (0.11.32, in `requirements-coverage.in`) and the Semgrep lock (0.13.8, in `requirements-semgrep.in`), and each header or comment gives the exact command. The Semgrep lock and the dev lock are separate installs in separate jobs, so a shared package (for example `typing-extensions`) may have a different version in each; the author expects this to be harmless.

## Browser tests

Some tests drive the portal in a real web browser. For that they need Playwright (a Python package that remote-controls a browser) and a copy of the Chromium browser. Without them these tests are skipped, not failed. They are in `tests/test_portal_browser.py`, `tests/test_portal_lead_pages.py`, `tests/test_stage_confirm_browser.py`, three in `tests/test_portal_wording_and_masking.py`, the tests in `tests/test_mode_safety.py` that use the browser helper, and the layout and look tests (`tests/test_portal_layout.py`, `tests/test_portal_look.py`, `tests/test_portal_phone_layout.py`, `tests/test_portal_long_values.py`, `tests/test_portal_drawer_long_name.py`), which use the same browser helpers. **The checks in `.github/workflows/lint.yml` install only `requirements-dev.txt` and there is no browser job yet, so they do not run the browser tests;** the masking promise (P10, in the promise table below) rests on them, so run them on your own computer.

Playwright is not in the development lock files. It has its own optional lock file, `requirements-browser.txt` (Linux x86_64, Python 3.12) or `requirements-browser-win.txt` (Windows, Python 3.13), with hashes. It holds Playwright 1.63.0 and the three packages Playwright needs (greenlet, pyee and typing-extensions; typing-extensions has the same version as in the development lock). The lock holds only Playwright and its three packages; neither lock file holds an image library such as Pillow. Install it after the development lock, in the same `.venv`:

    python -m pip install --require-hashes -r requirements-dev.txt
    python -m pip install --require-hashes -r requirements-browser.txt      # on Windows: requirements-browser-win.txt
    playwright install chromium

Two settings you may need before the tests run, only if the browser or Node is not in its default place (Node is a program that runs JavaScript; some tests run the portal's script with it). Linux (bash):

    export PLAYWRIGHT_BROWSERS_PATH=<folder that holds the browser>
    export PATH=<folder that holds node>:$PATH

Windows (PowerShell):

    $env:PLAYWRIGHT_BROWSERS_PATH = "<folder that holds the browser>"
    $env:Path = "<folder that holds node>;" + $env:Path

Then run the tests:

    python -m pytest -q -rs

* **The Chromium build must match the Playwright version.** A "build" is the numbered release of the browser that Playwright downloads. Each Playwright version looks for its own build, and `playwright install chromium` fetches the build for the Playwright version that runs it (this repository's lock holds Playwright 1.63.0). If the installed build is not the one the Playwright version wants, Playwright does not find it and the browser tests are skipped (the skip path, with a "no browser:" message that carries Playwright's launch error, is in `tests/test_portal_browser.py`). Keep the Playwright version in the lock and the installed build together.
* **Where the browser is not in the default place,** set `PLAYWRIGHT_BROWSERS_PATH` to the folder that holds it: the tests start the browser with no path of their own.
* **Counting the tests that skip without Node.** Run on a computer with the lock installed (Linux bash; give that one command a `PATH` that does not hold the folder with Node, for example `PATH=$(dirname "$(command -v python)") python -m pytest -q -rs`; first check that `command -v node` prints nothing under that `PATH`) and read the "node is not installed" and "no node" skip lines of its output.
* **Tests skip on purpose when something they need is missing:** another operating system (a Windows-only test; tests that make symbolic links skip on Windows), Python 3.13 (a test that asks Python for the reserved Windows device names), the load measurement (it needs `LEAD_DESK_LOAD_N`), the administrator user (root on Linux can read a file that has no read permission), and the programs `node`, `gitleaks` and Playwright. The number of skipped tests of a run depends on which of these are present, so no fixed count is stored here; `python -m pytest -q -rs` prints the reason of each skip.
* **Keep pytest's scratch folder inside an allowed folder.** If you give pytest its own scratch folder with `--basetemp`, keep it inside one of the allowed folders (the folder you start in, the repository folder, the system temporary folder, or a folder listed in `LEAD_DESK_PATH_ROOTS`; see `allowed_roots` in `tools/pathconfine.py`); otherwise the tools refuse it as outside the allowed folders. That is a set-up problem, not a fault in the desk. Do not run `git pull`, `git stash` or `git checkout` in the same folder while a test run is still writing its output file into it: the file can be replaced and the summary line lost.

## Quality checks and what to do when a check fails

The commands for ruff, mypy, bandit and the schema check are listed under "Dev tools: which lock file for which OS" in `contract.md`, and the same commands, in order, are in `.github/workflows/lint.yml` (that file also has the secret scan and the scan for hardcoded literals). Run them from the repository folder with the `.venv` folder switched on.

When a check fails: read the last lines of its output first; they name the file and line. For a test, run it alone (`python -m pytest -q tests/test_name.py::test_name`). A test that did not run is not a pass: to see why tests were skipped, run `python -m pytest -q -rs` (skip reasons in this repository include "node is not installed" and "no gitleaks program on PATH"). To make a missing secret scan a failure instead of a skip, set `DPLD_REQUIRE_SCAN=1` and `GITLEAKS_BIN` to the program's path.

**If `sonar-project.properties` or `exceptions.txt` has CRLF line endings** (the Windows line end, two characters), `tests/test_hygiene.py` fails and its message names two cures; run the Python one-liner from that message (cure 2). It keeps your edits and works in every state: write `python3` on macOS or Linux, `py -3` on Windows if `python` is not found, replace `<file>` with the path, and if you had run `git add` or `git commit`, run it again after the cure. Cure 1, `git checkout -- <file>`, throws away your edits and works only if you have not run `git add` or `git commit` on the file. A test runs both cures on a planted file, once before and once after `git add` (`test_every_cure_in_the_message_works`). Only these two files are checked, because the `.gitleaks.toml` and `patterns.txt` files and the `requirements-*` files are read without regard to line endings (`tests/test_hygiene.py` says what each of the two files breaks). `.gitattributes` sets LF endings for the file types it lists (and `eol=lf` as the default for everything else) but CRLF for `*.ps1` files.

The repository scan (`patterns.txt`, pattern 9, `[A-Za-z0-9+/=_-]{40,}`) reports an unbroken run of 40 or more of those characters. The prefix and a key name before `=` count towards the 40; a dot, a space or a quote ends the run. A letters-only second project key in `sonar-project.properties` is seen by that scan alone (the sets `ONLY_LITERAL_SCAN` and `ONLY_GITLEAKS` in `tests/test_gitleaks_exceptions.py` say which scan each planted variant is asserted for). The exception for the real key (the `sonar.projectKey` entry in `exceptions.txt` and the allowlist in `.gitleaks.toml`) therefore has to stay exact. `tests/test_gitleaks_exceptions.py` plants near-misses in a temporary copy and fails if either exception is widened. To add a second key of this shape, add its exact text, never a wider pattern or a whole file, and keep that test passing.

## What each promise rests on

The desk was stopped on purpose at each of ten crash points and restarted; all ten are simulated by an exception raised inside the program, and D2 was also tried with a real process kill (`docs/limits.md`). The table says what had happened at each point and what the result was. "Keyed" and "blind" are explained in the README under "Words used here". The two columns are the kind of MAIL system. The outcome at C0 and C1 depends on the kind of CRM instead (both mail kinds gave the same result in the tests in `tests/test_flow.py`), so those two rows say so in words.

| B | the verdict is recorded | one email | one email |
| L | the AI label is stored | one email | one email |

The portal tests that run in Node (`tests/test_portal_mode.py`, `tests/test_portal_log_poll.py`, `tests/test_codeant_demo_only.py`, the banner test in `tests/test_mode_safety.py`, the proof-panel probe in `tests/test_portal_lead_pages.py`; `tests/test_n8n_proof_result.py` also needs node but checks an n8n file, not the portal) skip when `node` is not installed. "Mutation check": the code is deliberately broken in one known way (the break is made inside the test; the source files are not changed) and the named test must fail with the named symptom. `test_mutant_no_unique_key` removes the database rule that stops two leads sharing an email, and the lookup that finds the first one; the duplicate test must fail with "leads == 1" and "got 2". `test_mutant_no_claim` removes the check that only one retry may take a follow-up (and, so that this check alone is tested, also switches off the second guard that stops a blind send while another send of the same lead runs); the retry test must fail with "emails == 1" and "got 2". This shows the tests notice these two faults; it is not proof that the code is correct.

## Terms for developers

* **Atomic insert**: a database write that either happens completely or not at all.
* **UNIQUE key**: a database rule that refuses a second row with the same value (here, a second lead with the same email address).
* **Test doubles**: stand-in parts (the demo CRM, the demo mail system, the pre-written AI replies) used only in tests and demos.
* **CRM dump**: the list of records the demo CRM holds, read back from `/fake/crm`.
* **Host and Origin check**: the desk refuses web requests that name a wrong address or come from another web site.
* **CRLF**: the Windows line ending (two characters); Linux and macOS use one (LF).
* **Receipt**: the desk's first note about a request; each one gets a running number in the order the desk wrote it. It is not the request number, which the sender chooses.
* **UNKNOWN**: the desk is not sure whether a follow-up email left; it does not resend, and a person must check.
