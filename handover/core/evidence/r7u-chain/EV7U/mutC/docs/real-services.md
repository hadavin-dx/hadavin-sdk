# Real-services check

**You do not need this section to run the demo.** The README steps use only the demo servers (small programs in this repository that play the CRM, the mail system and the AI step).
This section is for someone who wants to try the desk against their own free HubSpot account and their own mailboxes.
`tests/test_real_check_dry.py` runs this script against the demo servers (`--dry-fakes`), so what follows describes a script, not a result. The separate, small script `scripts/hubspot_probe.py` (`docs/hubspot-probe.md`) is the only other script that is meant to call a real service. Apart from that probe, this repository's tests and scripts use demo servers; no log of any real-service run is shipped. The script described here is the way to try the rest; until a run is recorded in this file, treat the real-service behaviour as untested, including what the code assumes about HubSpot (for example that it refuses a second create of the same email with a message naming the existing contact).

`scripts/run_real_check.py` runs the same desk against a real CRM (a free HubSpot account) and real e-mail (a mail account reached over an encrypted connection), then COUNTS what really happened. Only the INPUT is made up: about 12 invented people whose addresses end in `example.com` (a domain name reserved for examples); the mail kind used here picks the receiving address only from your configured inbox list, never from a lead's address (`tests/test_smtp_provider.py`, test of the recipient choice). You run it from your own terminal; it asks "y/N" after printing the worst-case number of calls and mails (and dollars, only with `--live-model`), and it refuses to start when a required cap or setting is missing (`tests/test_real_check_dry.py`, test of a missing required name).

1. Copy `scripts/real-run.env.example` to a folder outside the repository and fill it in. Each name is explained inside the file. Secrets are never in that file, only the paths of one-line key files (a HubSpot private-app token with contacts read and write only, called the service key in the config file; the desk does not use HubSpot's owners list, only the probe does; and a mail app password).
   A key file is checked by `scripts/run_real_check.py` before the question (a bad one stops the run before any cost line, any reservation and any connection), and then read AGAIN by each program that uses it (the desk, the probe, the model stand-in). It is not read once and handed over: a file that you damage between the check and that later read (you empty it, make it too big, or turn it into something that is not a plain file) is refused by the program that reads it, with the same one-line message that names the setting only and never the value; a file that you replace with another valid key is used as it then is (the later read does not compare it with the first one). Nothing is cached between the two reads.
1a. **Before turning lead stages on in any real HubSpot account (required; the desk then writes HubSpot's lead status field):** the CRM admin lists every automation that reacts to lead status changes and confirms each one is safe or switched off; test on one made-up contact first. The desk writes the lead status field and cannot see those automations (`docs/limits.md`, section "Which CRM stage things the desk touches").
2. In HubSpot create the contact property `hadavin_lead_id` (single-line text) by hand; the program's HubSpot code uses only the contacts endpoints and creates no property (`src/lead_desk/crm_hubspot.py`, top comment; no test checks what the real HubSpot does when the property is missing: the tests run the code against a demo server that accepts the field anyway and answers every address except the contact addresses with 404, and the create test in `tests/test_crm_hubspot.py` counts one call for one create).
3. Self-test first, no real service: `python scripts/run_real_check.py --dry-fakes`. Then the real run: `python scripts/run_real_check.py --config PATH`. Options: `--live-model` (a real AI model; its dollar limit is set in the settings whose names start with `DESK_LIVE_`), `--cleanup` (archives only the contacts this run made, found by their lead ids).

It sends new people. It then repeats requests through the same door and through the other door (the web form and the e-mail intake). It also sends one person with two different addresses (a CRM that only compares email addresses sees two different people, so it cannot catch that; the desk also treats them as two leads, and the check list names them as "two-leads": `tests/test_load_tools.py` tests that name), stops the desk process abruptly once, after requests have started, restarts it, and sends again. It then reads back the CRM contacts by `hadavin_lead_id`, counts the mails in your two receiving mailboxes at different providers (one block per mailbox in the config) by the header `X-Send-Key` (a header the desk adds to each mail so that a repeated send can be recognised; the code in `src/lead_desk/imap_count.py` fetches only that one header; no test shows that nothing else is read) and prints counts, a pass/fail table of the checks and a per-lead table (failure tables mask e-mail addresses). The same goes into a JSON file.

What it would show: the number of CRM contacts per lead id, the desk's own count of calls and creates, and the number of mails that reached your mailboxes per lead, after a crash and with repeats through both doors. What it would NOT show: that mail would reach a stranger's inbox (no claim about the spam folder or about SPF and DKIM, the checks a receiving mail server makes on the sender: it counts what arrived in your two mailboxes and their spam folders; one message per lead is allowed across both mailboxes together), that the CRM's own e-mail de-duplication did not hide something (the evidence would be the desk's own counts plus the different-address case), or anything about volumes beyond the free plan's limits. After a hard crash a mail that was in flight is recorded UNKNOWN on purpose: the table shows how many of those arrived.

Exit code 0 only when every check in its table passes: the book holds all the leads, the follow-ups that were not in flight at the crash ended `sent`, the mailboxes hold a mail for every `sent` follow-up, the CRM holds a contact for every lead marked done, and the first desk process was really stopped (killed) at the crash point. With `--cleanup`, a contact that could not be archived also makes the exit code non-zero. Failure tables mask e-mail addresses (`tests/test_real_check_dry.py` tests the masking); a refusal does not repeat a setting value (same file); no test covers every line of a failure table. The CRM settings refuse a base address outside the vendor's own domains unless a setting allows it (`tests/test_crm_hubspot.py` tests this refusal); no test checks, over a real connection to HubSpot, that the key goes only to HubSpot (the redirect test in `tests/test_crm_hubspot.py` checks only that when the demo server answers with a redirect to a second demo server, the second one receives no request and no key). The full list of checks is in the script's own result table (printed at the end of a run and written to the JSON result file); its help text (`-h`) describes only the run and its settings; its exit codes and settings names are in `docs/settings.md`.

**Where the files may be.** The config file, and the folders that the config names (`DESK_DB_PATH` and so the run folder, `REAL_RESULT_FILE`, the key and password files), can be anywhere on the computer, also outside the repository (`tests/test_path_confinement.py` tests the lookup of a config outside the allowed folders): the script reads the config you name with `--config` and uses the paths in it as written. The folder checks of `load_tools/README.md` (`LEAD_DESK_PATH_ROOTS`) do not apply to them, because they come from your own files and not from a command line that a faulty script might have filled in. Only the config path itself is checked (no control characters, a symbolic link is replaced by the file it points to, the file must exist), and it is found by looking the name up in the folder listings from the top of the disk (or the network share), so it must be a file in a folder you can list: a config below a folder that you can enter but not list, is refused with a message (copy it to a normal file); a config handed over as `--config <(command)` (a shell feature that hands the output of a program over as a file) is expected to be refused the same way, but no test passes `--config <(command)` to the script itself (the unlisted-name test in `tests/test_path_confinement.py` gives the path check a pipe like the one `<(command)` makes and asserts the refusal).
