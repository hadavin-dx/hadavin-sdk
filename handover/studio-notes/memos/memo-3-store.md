|---|---|---|---|---|
| Reservations (a cap held while a proposal waits) | `pr/49` protocol.py adds `reserve(res, limits, since, request=None) -> str\|None`, `release_reservation(tenant, key) -> int`, `list_reservations(tenant, since)`, `prune_reservations(older_than)` and `StoreBusy(StoreUnavailable)`; table `reservations` PK `(tenant, key)` with `amount BIGINT CHECK (amount > 0)`, `created_at TIMESTAMPTZ`, two indexes (`0005_reservations.sql`) | an insert that counts the same tenant's open rows in the SAME transaction, serialised per tenant; repeat of same key + same content is a no-op (idempotent), same key + other content = `KEY_CONFLICT`; optional approval request saved in the same transaction; `StoreBusy` on lock timeout | per-tenant serialisation (advisory lock or `SELECT ... FOR UPDATE` on a tenant row); memory backend needs the same per-tenant lock, not the global one only | new table + `GRANTS` entry; `release`/`prune` need DELETE: a new grant class (see section 5) |
| Spend reserve/settle (the other money design) | `pr/48` protocol.py lines 111-135: `reserve_spend`, `settle_spend(deltas)`, `prune_spend(before)`; migrate.py adds a `maintenance` role with `UPDATE (usd)` and DELETE on `spend`/`spend_month` | all-or-nothing booking of worst case on the run counter, the agent day counter and the month counter in one transaction; settle exactly once; clamp at zero | one lock order (run counter first, then agent) is documented in `limits.py` (lines ~175 of pr/48) | grant change on existing tables, no new table |

Only in demos: dealdesk `inbox.py` (287 lines: `LedgerStore` protocol, `MemoryLedger`, `SqliteLedger`), Intake `fake_ledger.py`, apexc `intake.py` (inventory-D lines 38-43); three different terminal states for a reused message id | write-ahead record before ack, unique key `(tenant, msg_id)`, one terminal state per id (decision not yet taken), reconcile scan of unacked rows, bounded queue | unique-constraint insert is the race arbiter (Postgres), a dict under the lock (memory) | new table; DELETE or status UPDATE grant |
| Queue (work queue / approval queue) | Intake `workqueue.py` 1013-1017 lines on SQLite with `queue_schema.py` (inventory-B lines 38, 69): "connect is the ONLY way the queue is opened" | claim with a lease (`UPDATE ... | Tenant namespace | dealdesk `store.py` (`check_tenant`, `TenantStore`), refunds `namespace.py` (`Namespace`, `CrossClientAccess`, `config_key`); two different key shapes (inventory-D lines 45-48) | every key and row carries a tenant; a store handle is bound to one tenant and a cross-tenant read raises; `reservations` already carries `tenant` as the first PK column (pr/49) | none beyond the key prefix; but the chosen shape must be applied to Postgres as a column, not only a string prefix | `tenant TEXT NOT NULL` first in every PK of the new tables; existing 0001-0005 tables have none |

Reading across the rows: only reservations (pr/49) and the spend reserve/settle (pr/48) have store code today, and plan-v3 puts neither into a store change before P4b. ## 5. What the store contract suite for memory + Postgres must cover
Today: `tests/contracts/test_store.py` (about 35 tests, lines 28-360, parametrised over `KINDS["store"]` = `memory` (`tests/contracts/kinds/builtin.py:30`) and `postgres` (`store_postgres.py`, runs as a NON-owner runtime role with a separate purge role via `_SplitStore`, skipped without `HADAVIN_TEST_PG_DSN`)). Covered: run copies and `NotFound`, transition CAS, `add_cost`, `touch`, `list_runs`, approval-request CAS, due approvals, latest decision, gate decision write-once, tick state, sent_at/channel_ref, `list_approvals`, spend day/month, dead letters + kill switch, 2-thread CAS race (line 206), `record_decision` atomic (227), tool calls/redaction maps/purges (251-360).
Gaps a v1 suite should add (each with a fail-before test), derived from sections 1-2:
1. **Idempotency and conflict semantics as contract rows**: repeat of the same write is a no-op, same key with other content raises/returns a conflict code (this is the reservation contract; it will be needed by any later table).
2. **Concurrency on the money counters, not only on run CAS**: N threads x `add_spend` give exact totals (Decimal exact); if P4b adds `reserve_spend`/`settle_spend`, the suite adds: N threads at a cap never exceed it; settle twice does not double count; failed settle leaves the reservation; clamp at zero. Plan-v3 section 8 (b) wants an 8-process Postgres race; the suite today is threads in one process, and `MemoryStore` has one global lock, so memory trivially passes; the cross-process test is Postgres-only and must be a separate marked test (needs the CI Postgres service).
3. **Failure atomicity**: a transaction that raises mid-way leaves no partial rows in both backends (Postgres has `psycopg.Rollback`, postgres.py:364; memory must be shown to do the same).
4. **Connectivity classification**: `is_connectivity_error` on a refused connection for Postgres (exists in `test_p7_tick.py`; not in the contract suite).
5. **Privilege rows as part of the suite for the Postgres kind**: the runtime role cannot UPDATE/DELETE audit rows (exists in `test_k2_migrations.py:230`), purge role cannot read mapping contents, maintenance role (if PR #48 pieces return) cannot INSERT. These already exist as separate tests; the suite should reference them so a new table cannot ship without a grant row (the `check_grants` check at migrate.py `check_grants` covers "every relation has a GRANTS entry").
6. **Schema-version / downgrade read**: P3a's "previous release code reads the new schema or fails loudly" (plan-v3 row P3a): a contract row that opens a store at schema N+1 with N code and expects either success or a typed error. Nothing like it exists today; the closest is `migrate.py` refusing "applied migrations have no file in this release" (the `gone` branch).
7. **Missing-method guard**: `missing_methods(store)` must list every Protocol method; add a test that every method of `Store` is exercised by at least one contract test (introspection test), so a new method cannot be added to the Protocol without a contract row.
8. **Tenant key rule (add only when the first tenant-aware table lands)**: a handle bound to tenant A cannot read tenant B, for both backends. Do not add it before the first consumer (plan-v3 puts it in P7b).
Extension point: make the suite table-driven by a list of capability "groups" so P7a/P7b/P7k can append a group (`reservations`, `inbox`, `queue`) without editing existing tests.
