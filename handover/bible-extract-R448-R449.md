# Bible extract (owner HARD rules 2026-11-06), updated after independent design review

**R448.** [Hadavin practice, owner HARD rule 2026-11-06, said repeatedly; changing needs the owner's explicit yes] CODE LAST. Writing our own code is the last resort, never the default. ONE LADDER (R447's rungs plus free libraries and standard tools, which sit beside the no-code rung): reuse studio code; the client's own tool; a free or open-source library or standard tool; a no-code or low-code tool such as n8n; an MCP server; a newer model feature; then thin glue and configuration (a few lines that connect the tools above, no business logic); then our own code. R447 keeps the rung numbers; this rule is the gate that makes R447 binding. Our own code is allowed only for what the ladder shows no tool can give (this list is the same as 'the brain' in R447): a safety guarantee (exact money caps and reserve/settle, redaction before the model, audit tamper-evidence, approval binding with a separate executor identity, tenant isolation and least privilege, eval gates, no lost or double-applied message). GATE: no plan, design, ticket, spec or agent brief may be handed to a builder, and no ticket may enter build-start review, without a RUNG TABLE (the artifact itself carries it; planning documents carry a short one): one row per component with the need, the rungs tried, evidence (source and date, or marked UNVERIFIED), what only our code gives, and a verdict KEEP-CODE (we write it) / CUT-TO-CONFIG+GLUE (a tool does it, we only configure and connect it) / CUT (the component is dropped, nobody needs it). '80 percent' means the share of the component's listed needs (the need column, one line per behaviour) that the higher rung already provides; the ticket author counts it with the evidence, reviewers re-count it, and a doubtful count is settled by the lead. If a higher rung covers 80 percent or more, the component is cut to config plus thin glue unless a written guarantee gap with a test idea proves otherwise. KEEP-CODE is valid only if the 'what only our code gives' cell names one of the guarantees above AND names the single property the tool fails, with a reproduction against the tool (a failing test, or a doc quote with its URL); the code covers only that guarantee path, everything around it stays config and glue. A table row's recommendation is input to the client options list of R446 (the client chooses in client builds; in the demo stage we choose). A thin kind module around a chosen tool (R363) is glue and does not count against the tool's coverage. Deterministic standard-library code or config beats a model call, and a model call beats new code (so 'newer model features' in R447 comes after deterministic code). A guarantee-class step may never live inside a no-code flow, because a flow has no tests or review; no-code tools carry only plumbing, and their licence terms are checked before they ship to a client. Tool facts live in one dated shared register (the cloud handover's TOOLS.md and the studio's research files), tickets cite its lines, a table is at most one page, and components of one kind share one epic-level table. The rung decision is made inside the EGM plan-review round, not as an extra round; security, money and redaction paths keep their no-cap rule and the 80 percent cut does not apply to the guarantee itself. Cut evidence may include the running cost of keeping existing code, but replacing working code still needs the owner's yes. A task that creates no new component (a lookup, an evidence run, a review, a bug fix in existing code) writes 'CODE-LAST n/a: <reason>' instead of a table. A row marked UNVERIFIED may stay in the table, but a KEEP-CODE or CUT decision that rests on an UNVERIFIED row must be verified (a dated source read, or a small test of the tool) before the build starts; the lead checks it. Cuts need written evidence (improve-before-replace: never discard existing working code without evidence and the owner's yes). Reviewers must ask "should this exist at all, and what higher rung covers it?"; a missing or empty rung table is a Major finding. WASTE STOP: a component whose rung table lists a higher rung at 80 percent or more gets no more than one review round before the rung decision. Reasons that do NOT justify code: "we already wrote the ticket", "it is cleaner", "the demo had it". Tool facts are dated; whoever touches the ticket re-checks any fact older than 90 days, and an older fact counts as UNVERIFIED. A review round here means one full pass by the reviewers on the plan or ticket.

**R449.** [Hadavin practice, owner HARD rule 2026-11-06; changing needs the owner's explicit yes] Stages are named DEMO, PILOT and PROD, in that order, and nothing else: never "dev", "staging" or "test" as a stage name in code, config, URLs, docs, tickets or tests. Demo = synthetic or sandbox data, relaxed kinds, labelled as a demo; pilot and prod keep all gates (approvals, least privilege, audit separation). Core config accepts exactly these three stage values; any other value, including "dev", is refused with a message that names the rename. Persisted values: where an old 'dev' value is already stored (config, tenant records, audit entries, hash chains), it is mapped to demo on read and history is never rewritten; the startup check refuses an unknown stage and a half-renamed flag (fail closed, never 'allowed'). The class test looks at stage positions only (config values, enum members, URLs, docs headings), not words such as developer or the ordinary word test. Pilot is the first stage with real client data and the rehearsal of any risky prod change must be written into the pilot plan. Third-party tools that use dev or staging (GitHub environments, Helm values, cloud accounts) are labels mapped to demo or pilot. A project may keep its own environment labels (for example a client's "uat") only as labels mapped to one of the three stages in the project's config; core code tests the stage, never a label.
