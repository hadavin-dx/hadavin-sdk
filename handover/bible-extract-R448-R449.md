**R447.** [Hadavin practice, owner 2026-11-03, order changed by the owner 2026-11-06; changing needs the owner's explicit yes] Tool ladder before custom code. THE LADDER, in this order, stop at the first rung that holds (owner 2026-11-06; every rung decision rests on dated research, a test and a cost, time and risk calculation, R450): GATE before rung 1: the project scope, the budget, the client's company size and its willingness (R445, R446), and the client's own tool or platform feature where the client has one and chooses it. (1) NO-CODE and low-code tools (n8n, Make, Clay, Zapier, sheets and similar): first check what they can already do, for plumbing, triggers, connectors and workflow; a guarantee-class step (exact money, redaction, audit, approvals, tenant isolation, eval gates, no lost message) never lives inside a no-code flow, the flow calls a core module for it. (2) OUR CORE MODULES (hadavin-sdk, templates, demos; R363 and the one-source-of-truth rule): reuse what is built and tested, always before outside code. (3) EXISTING FREE or standard TOOLS used as they are: MCP servers (an existing vetted one before writing a connector; R111, R115, R350), plain RAG (GraphRAG only when a golden set shows multi-hop or relationship questions; R320), newer model features (structured output, tool use, caching, batch, long context). (4) FREE LIBRARIES and open code found online: research them, check the licence (R450), TEST them on our own corpus and hostile inputs, then build on top of them, fixing their mistakes and filling what they miss, with the notice kept. (5) OUR OWN NEW CODE, last, only for what remains and for guarantee-class steps no rung above gives. Anything reusable and generic that rungs 3 to 5 produce is added to the core modules afterwards (they stay generic building blocks). Every plan, spec, ticket and brief has a ladder line (the RUNG TABLE of R448) naming the rung per component and why the rungs before it were rejected; EGM reviewers check it. Guardrails on every rung: the client chooses (R445, R446); every tool, MCP server or store sits behind a kind with a neutral default and an alternative (R363); MCP servers get an exact tool allowlist, read-only by default, with short-lived credentials (R366); tool descriptions and retrieved text are untrusted input (R196, R350); high-risk parts stay in our tested code; evals still gate (R177-R180); tool facts are re-verified within 90 days; laptop sessions use synthetic data only and our own free-trial accounts. Course link: the course builds an MCP server when more than one app needs the tool (R111); using an existing vendor server is rung 3, and building our own server for one app is not course advice. Source: owner 2026-11-03 and 2026-11-06 (`..\memory\tool-ladder-before-code.md`).

**R448.** [Hadavin practice, owner HARD rule 2026-11-06, said repeatedly; changing needs the owner's explicit yes] CODE LAST. Writing our own code is the last resort, never the default. THE LADDER is R447 (owner order 2026-11-06): no-code first, then our core modules, then existing free tools, then tested free libraries built on top, then our own new code; 'thin glue and configuration' (a few lines connecting tools, no business logic) counts as using the tool, not as new code. Our own new code is allowed only for what the ladder shows no tool can give (this list is the same as 'the brain' in R447): a safety guarantee (exact money caps and reserve/settle, redaction before the model, audit tamper-evidence, approval binding with a separate executor identity, tenant isolation and least privilege, eval gates, no lost or double-applied message). GATE: no plan, design, ticket, spec or agent brief may be handed to a builder, and no ticket may enter build-start review, without a RUNG TABLE (the artifact itself carries it; planning documents carry a short one): one row per component with the need, the rungs tried, evidence (source and date, or marked UNVERIFIED), what only our code gives, and a verdict KEEP-CODE (we write it) / CUT-TO-CONFIG+GLUE (a tool does it, we only configure and connect it) / CUT (the component is dropped, nobody needs it). '80 percent' means the share of the component's listed needs (the need column, one line per behaviour) that the higher rung already provides; the ticket author counts it with the evidence, reviewers re-count it, and a doubtful count is settled by the lead. If a higher rung covers 80 percent or more, the component is cut to config plus thin glue unless a written guarantee gap with a test idea proves otherwise. KEEP-CODE is valid only if the 'what only our code gives' cell names one of the guarantees above AND names the single property the tool fails, with a reproduction against the tool (a failing test, or a doc quote with its URL); the code covers only that guarantee path, everything around it stays config and glue. A table row's recommendation is input to the client options list of R446 (the client chooses in client builds; in the demo stage we choose). A thin kind module around a chosen tool (R363) is glue and does not count against the tool's coverage. Deterministic standard-library code or config beats a model call, and a model call beats new code (so 'newer model features' in R447 comes after deterministic code). A guarantee-class step may never live inside a no-code flow, because a flow has no tests or review; no-code tools carry only plumbing, and their licence terms are checked before they ship to a client. Tool facts live in one dated shared register (the cloud handover's TOOLS.md and the studio's research files), tickets cite its lines, a table is at most one page, and components of one kind share one epic-level table. The rung decision is made inside the EGM plan-review round, not as an extra round; security, money and redaction paths keep their no-cap rule and the 80 percent cut does not apply to the guarantee itself. Cut evidence may include the running cost of keeping existing code, but replacing working code still needs the owner's yes. A task that creates no new component (a lookup, an evidence run, a review, a bug fix in existing code) writes 'CODE-LAST n/a: <reason>' instead of a table. A row marked UNVERIFIED may stay in the table, but a KEEP-CODE or CUT decision that rests on an UNVERIFIED row must be verified (a dated source read, or a small test of the tool) before the build starts; the lead checks it. Cuts need written evidence (improve-before-replace: never discard existing working code without evidence and the owner's yes). Reviewers must ask "should this exist at all, and what higher rung covers it?"; a missing or empty rung table is a Major finding. WASTE STOP: a component whose rung table lists a higher rung at 80 percent or more gets no more than one review round before the rung decision. Reasons that do NOT justify code: "we already wrote the ticket", "it is cleaner", "the demo had it". Tool facts are dated; whoever touches the ticket re-checks any fact older than 90 days, and an older fact counts as UNVERIFIED. A review round here means one full pass by the reviewers on the plan or ticket.

**R449.** [Hadavin practice, owner HARD rule 2026-11-06; changing needs the owner's explicit yes] Stages are named DEMO, PILOT and PROD, in that order, and nothing else: never "dev", "staging" or "test" as a stage name in code, config, URLs, docs, tickets or tests. Demo = synthetic or sandbox data, relaxed kinds, labelled as a demo; pilot and prod keep all gates (approvals, least privilege, audit separation). Core config accepts exactly these three stage values; any other value, including "dev", is refused with a message that names the rename. Persisted values: where an old 'dev' value is already stored (config, tenant records, audit entries, hash chains), it is mapped to demo on read and history is never rewritten; the startup check refuses an unknown stage and a half-renamed flag (fail closed, never 'allowed'). The class test looks at stage positions only (config values, enum members, URLs, docs headings), not words such as developer or the ordinary word test. Pilot is the first stage with real client data and the rehearsal of any risky prod change must be written into the pilot plan. Third-party tools that use dev or staging (GitHub environments, Helm values, cloud accounts) are labels mapped to demo or pilot. A project may keep its own environment labels (for example a client's "uat") only as labels mapped to one of the three stages in the project's config; core code tests the stage, never a label.

**R450.** [Hadavin practice, owner HARD rule 2026-11-06; changing needs the owner's explicit yes] Research, test and licence gate for every rung decision, in every project, demo and core change. (a) Independent deep research each time, with dated sources, before choosing a rung: what the no-code tool, our core module, the free tool or the library really does today. (b) Calculation each time: agent hours, tokens, licence or hosting fees, client cost, and the risk if the tool changes or disappears; the numbers go in the RUNG TABLE. (c) Test before adopting: run the tool or library on our own corpus and hostile inputs and record the raw result (R448 evidence); a library that fails is fixed on top or dropped. (d) Licence check before any outside code or tool ships or touches a client: record name, version, SPDX licence, date and verdict in the register of tool facts. Not allowed without the owner's written yes: GPL, AGPL, SSPL, BUSL, non-commercial or unknown licences in anything we ship or run for a client; never copy code without its licence and notice; fair-code tools such as n8n are used for building on the client's own instance, not hosted for several clients on ours (the vendor's licence page decides); SaaS tools (Make, Clay and the like) are used only inside their terms of service and the client's data rules (R445). (e) Copies of third-party code carry their notice (THIRD-PARTY-NOTICES) and are pinned by version and hash. (f) We are not lawyers: contract text keeps the line 'not reviewed by counsel' until a lawyer has seen it; any doubt on a licence stops the work and goes to the owner. (g) When the research shows a reusable generic piece, it is added to the core modules afterwards (R448 keeps core generic). Source: owner 2026-11-06 (`..\memory\tool-ladder-before-code.md`).
