**R448.** [Hadavin practice, owner HARD rule 2026-11-06, said repeatedly; changing needs the owner's explicit yes] CODE LAST. Writing our own code is the last resort, never the default. Order: (1) a free or open-source library, a standard tool, a no-code or low-code tool such as n8n, the client's own tool or platform feature, an MCP server (R447 rungs 1 to 6); (2) thin glue and configuration; (3) our own code, and only for what the ladder shows no tool can give: a safety guarantee (exact money caps and reserve/settle, redaction before the model, audit tamper-evidence, approval binding with a separate executor identity, tenant isolation and least privilege, eval gates, no lost or double-applied message). GATE: no plan, design, ticket, spec or build brief may enter build-start review without a RUNG TABLE: one row per component with the need, the rungs tried, evidence (source and date, or marked UNVERIFIED), what only our code gives, and a verdict KEEP-CODE / CUT-TO-CONFIG+GLUE / CUT. If a higher rung covers 80 percent or more, the component is cut to config plus thin glue unless a written guarantee gap with a test idea proves otherwise. Cuts need written evidence (improve-before-replace: never discard existing working code without evidence and the owner's yes). Reviewers must ask "should this exist at all, and what higher rung covers it?"; a missing or empty rung table is a Major finding. WASTE STOP: a component whose rung table lists a higher rung at 80 percent or more gets no more than one review round before the rung decision. Reasons that do NOT justify code: "we already wrote the ticket", "it is cleaner", "the demo had it". Tool facts are re-verified within 90 days and dated.

**R449.** [Hadavin practice, owner HARD rule 2026-11-06; changing needs the owner's explicit yes] Stages are named DEMO, PILOT and PROD, in that order, and nothing else: never "dev", "staging" or "test" as a stage name in code, config, URLs, docs, tickets or tests. Demo = synthetic or sandbox data, relaxed kinds, labelled as a demo; pilot and prod keep all gates (approvals, least privilege, audit separation). Core config accepts exactly these three stage values; any other value, including "dev", is refused with a message that names the rename. A project may keep its own environment labels (for example a client's "uat") only as labels mapped to one of the three stages in the project's config; core code tests the stage, never a label.
