## BLOCKER

**B1 (ADV-R8-1). The k1b "upper bound" is an estimate, and its input term can be 3 times too low (Answer first 8; C13; V24).**
- Every k1b charge (CallTimeout, UsageMissing, j1-j7) is `worst_case_usd` = `estimate_tokens(system + _dumps(messages))` at 3 characters per token, times the input price, plus `max_tokens` times the output price. The ticket concedes "not a hard bound".
- A second under-count: the OpenAI-compatible body that `_chat` really sends (openai_compat.py 94-116) adds tool specs, `tool_choice` and `schema_hint(system, output_schema)`, none of which the k1b estimate counts.
- Scenario: a dense JSON or code prompt of 30,000 characters at about 1 token per character, prices 3 and 15, `max_tokens` 1024, a kind with 2 requests, HTTP 200 plus parse failure (j1). Booked W = (10,000x3 + 15,360)/10^6 = 0.045360, so 2W = 0.090720. Really billable 2 x (30,000x3 + 15,360)/10^6 = 0.210720. Under-booked by 0.12, 57 percent, on the case the order names.
- Why tests hide it: every C13 row uses P = 100, where the output term dominates (15,360 of 15,660 micro-USD); rows assert equality with the same estimate.
- The ticket rejects a byte-length bound as V24 ("no defect needs it"). Order 14 is that defect.
- Fix: size the input term from the UTF-8 byte length of the full request (system, messages, tool specs, schema hint; one byte per token is a true upper bound); or state to the lead plainly, in row names, that "upper bound" means "requests x the estimate", and get acceptance. Add a C13 row with a dense prompt where the estimate-based booking is below true cost. Until then the words "UPPER bound" in the headline, j1-j7 and PL42 are untrue.

## MAJOR

**M1 (ADV-R8-2). The non-billing recogniser (PL46) cannot work as written and can class a billed failure as non-billing.**
- (a) `http_status` does not exist: `ProviderError` is a bare `RuntimeError` subclass. The only place a non-retryable HTTP error becomes a plain `ProviderError` is `with_retry` (retry.py 97-99, `raise ProviderError(...) from exc`, status on the SDK or urllib `exc`). The ticket says P4a does not touch `retry.py` (P5b1 and P4b2 own it) yet says the status is "set where a kind raises for a non-retryable status"; the kinds do not raise it. Either `retry.py` is edited (hot-file conflict, missing entry) or the 4xx class can never fire in production. j4 and j6 build the chain by hand, so they pass either way; no row drives the real chain from the wire stub through `run_case`.
- (b) The refused-connection class misses the real urllib chain: `post_json` uses urllib (common.py 255-257); urllib raises `URLError` whose `.reason` is the `ConnectionRefusedError`, not in `__cause__`. retry.py's own `_chain` follows `.reason`; the recogniser follows `__cause__` only. Production result is 2W (safe direction), but j5 is false confidence.
- (c) Only the last error is chained (`ProviderExhausted ... from exc`, retry.py 101-103). Scenario: attempts 1 and 2 time out (possibly billed), attempt 3 gets a refused connection or a non-retryable 4xx; the cause is non-billing so the loop books W = 0.015660, while the true upper bound is request 1 plus 3 attempts of request 2 = 4W = 0.062640. A cap is bypassed by 3 requests' worth.
- (d) The status is provider-controlled: `openai_compat` talks to arbitrary gateways; a gateway that rejects with 400 after the upstream billed zeroes request 2's booking.
- (e) The message text is never used, so it cannot fool the recogniser. Open: is "plain `ProviderError`" tested by `type(x) is` or `isinstance` plus exclusions (a P4b2 subclass carrying a status would be classed non-billing under `isinstance`)? Does "at most 4 links" count the `UsageMissing` itself? No test at depth 4 versus 5, none for 399, 400, 499, 500; a range mutant such as 400-500 survives (j3 uses only 503).
- Recommendation (cuts surface, order 8): take the ticket's own alternative. Drop the recogniser, book 2W for every chained shape, delete `http_status`, class (1), class (2), PL46, rows j4/j5, mutants a2-46/a2-47 and the `retry.py` question. Cost: over-booking a rare refused request 2, the safe side. If the lead keeps it, require (i) earlier attempts known non-billing (needs per-attempt data from P4b2-a), (ii) an end-to-end row through `OpenAICompatWire` into `run_case`, (iii) the `.reason` chain, (iv) `type() is` and boundary rows.
