- **Facts I checked myself (they decide rows):**
  1. **CR share (ADV-1, COR-5).** One `\r` per line of n characters plus CRLF is 1/(n+2) of all characters: 18-character lines give exactly 50,000 ppm, 15-character lines 58,824 ppm, 13-character lines 66,667 ppm. So any CRLF file with lines of 18 characters or fewer is `high_nontext` under revision 1. `"\r".isspace()` is `True` and its category is `Cc`, so the two possible denominators (all characters, non-space characters) give different answers; revision 1 names neither.
  2. **JSON byte sizes (ADV-6, COR-13, COR-14).** `json.dumps` with the default `ensure_ascii=True`: `é` 6 bytes, `€` 6, an astral emoji 12, a C0 control 6. With `ensure_ascii=False` encoded as UTF-8: 2, 3, 4 bytes, but a C0 control is STILL 6 (`\u0001`), and `"`/`\` are 2. So the cap `4 * chars + 1 MiB` is wrong under BOTH settings. The true worst case with `ensure_ascii=False` is 6 bytes per character. `json.loads('"\\ud800"')` returns a lone surrogate without error, and `json.dumps(..., ensure_ascii=False).encode("utf-8")` of one raises `UnicodeEncodeError`. Core `models.py:43-47`: `canonical_json` uses `ensure_ascii=False`, `sort_keys=True` and no `default=`, so a `frozenset` (AK1's `Readers`) raises `TypeError`, and `sha256_hex` encodes UTF-8 strictly.
  3. **Deflate ratio (ADV-7, COR-9).** `zlib.compress(b" " * 64 MiB, 9)` is 65,239 bytes (1,028 to 1). The ticket's "about 64 KiB that expands to 64 MiB" is right, and so are both reviewers: 64 MiB is far below the 1,024 MiB limit. A bomb that expands past a 128 MiB test limit needs about 256 KiB of file for 256 MiB of content.
  4. **Idempotence (COR-4), both cases confirmed non-idempotent** on rules c3 -> c4 -> c6 in the ticket's order: (a) `"infor- \nmation"`: pass 1 does not join (space before the newline), c6 strips the space, pass 2 joins `information`. (b) Four pages `ACME REPORT / Confidential draft / <unique body> / Page n of 4`: pass 1 peels `ACME REPORT` and the page line, pass 2 peels `Confidential draft`. A third case I found while building the probe: a footer removed by c4 that sat under a line ending `infor-` leaves `infor-\n<next>` for c3 on pass 2, so c3 must not run before c4.
  5. **Child environment (COR-12), confirmed.** Python 3.13.18 on this Linux container, `subprocess.run([sys.executable, "-I", "-c", ...], env={})`: the child's `os.environ` holds exactly `['LC_CTYPE']`, `sys.flags.isolated == 1`, `sys.flags.utf8_mode == 1` (PEP 538/540 coercion of the C locale). So revision 1's P11 ("only `KIT_PDF_CHILD_ENV` names appear", empty on Linux) fails on a correct build.
  6. **ruff S603 (COR-8), and why the reviewers' fix for ADV-8/COR-11 does not work.** Repo ruff 0.17.1, `--isolated --select S`, on probe files. S603 fires on `Popen(list(ARGV))`, on `[sys.executable, "-I", "-m", _MOD]` (a module-level name), on `[..., self._module]`, on `Popen(self._argv())`, and on `[sys.executable, "-I", "-c", code]`. It does NOT fire on the inline literal `[sys.executable, "-I", "-m", "x"]`. A pure literal `["python3", "-c", "pass"]` gives S607 instead. `pyproject.toml:80-81` ignores only `S101` under `tests/**`, and CLAUDE.md forbids suppressions. So the production argv must be exactly the inline literal `[sys.executable, "-I", "-m", "hadavin_sdk.ingest._pdf_worker"]`. The `_argv()` override that both reviewers propose would itself raise S603 (row 8).
  7. **Code reads.** `guard/injection.py:22-34`: `_SQUASH = [^a-z]` deletes every non-a-z character before the three squashed phrases are matched. So zero-width characters inside those three phrases are caught, and tag characters (U+E0000-E007F) are invisible to the detector (ADV-12, ADV-24). `k1b/bundle.py:181-183`: `_chunks` also `.strip()`s the whole text (K1's shim must allow for it). `pyproject.toml:89` defines a `perf` marker, and `.github/workflows/ci.yml:94` runs `pytest -m perf` in its own step (row 18). `uv.lock` holds no `pytest-timeout` (0 hits; row 21).
