## Blocker
B1. `runmap.canonical` (and `undo()` through it) no longer composes combining sequences, so a decomposed (NFD) copy of a stored accented value is not masked.
- Where: runmap.py 276-285; `nfkc()` (103-109) calls `canonical`; `undo()` (158) calls `nfkc`; `_views()` (413) builds the stage-2 views from `canonical(text)`, `canonical(unescaped)` and `undo(text)`.
- Before (P1a/main) `canonical` was whole-text NFKC (e+U+0301 became the precomposed letter). Now it is per-character NFKC, so no stage-2 view composes. `_sweep` is a literal case-sensitive search and redact.py has no normalize call.
- Scenario: the map holds a precomposed accented NAME or secret; a tool result carries it decomposed (macOS file names, many PDF extractors). Before: stage 2 composed, found, adopted the masked view. Now: stage 1 misses, no stage-2 view composes, the text goes to the model. P2d-2's check is no backstop for NAME/ADDRESS in outcome OUT, for secrets of 8 to 11 characters, or values whose scan key is shorter than 8.
- The new test pins the new behaviour (`tests/test_textnorm_siblings.py:78` asserts `canonical("á") == "á"`); the CHANGELOG calls it FIXED and does not state the redaction consequence. `runtime/evidence.py:57,87-88` also call `canonical`; decomposed vs composed values now fail to ground (false-abstain risk).
- Fix: keep a composed view in `_views` (NFKC of the text with Cf removed, hits adopted like the others), per-character view only for position mapping. Add a `redact_text` row with an NFD copy of a precomposed NAME and secret that fails on this head. Probe: `redact_text("José Alvarez", {"<NAME_1>": "José Alvarez"})` on 2ff0afe vs 4f14ec8.

## Major
M1. `scan_keyset` drops Lm only, not spacing marks (Mc) or modifier symbols (Sk). A copy with a table-source Mc inserted has no matching key, and P2d-2's check uses `scan_keyset` only.
- `_scan_keys` removes only Lm from raw text; `_prefix(..., marks=False)` keeps Mc/Sk and the table reads some as letters/digits: `_confusables.py:278,280,282,286` map U+0C02, U+0C82, U+0D02, U+0D82 to `o`; U+0B03 maps to `8` (273); `tests/test_textnorm.py:1694` asserts "PASSOWORD" in squeeze_views of a Telugu-anusvara copy. `scan_keyset` of that copy yields only `passoword`, so the key `password` is not a substring.
- Scenario: V is `password=<secret>`; a copy with a Telugu/Malayalam anusvara inserted is found by `scan_holds`/`scan_views` but `check_lookalike` uses `scan_keyset` only, so it passes.
- Test gap: Mc/Lm/Sk corpus tests never call `scan_keyset` for Mc or Sk; the property test inserts only U+0301 and format characters. The Lm attack is closed, so Mc/Sk is an inconsistent hole.
- Fix: remove Mc and Sk (as well as Lm) from the raw text in `_scan_keys` or add marks-dropped keys; update the SK-1 key count; test over every Mc/Lm/Sk code point (452/397/125) that "password" is in some key of `scan_keyset("pass"+c+"word")`. Only five table sources were confirmed by grep; the rest not enumerated.
M2. Tests have two positives and four negatives only. NOTE: migration_numbers.py is main's P3a-1 code, in this diff only because P1b is stacked on an older base; review belongs to the P3a-1 record. Fix: match the keyword structurally (ON before the first TO/FROM) or tokenise with `$` as an identifier character; add `$on`, `on$x`, `"on"`, newline and comment cases.
