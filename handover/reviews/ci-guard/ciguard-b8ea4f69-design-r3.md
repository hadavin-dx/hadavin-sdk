## Major
- **M1** Ignore-entry acceptance trusts mutable branch names (ci.yml:199-205; golden line 98). Failing input (no ruleset): a writer pushes a branch named `handover-src/c1a-8460813` or `core/P2d-1` (free name, unprotected force-push, or the PR's own head branch) holding commit C that adds `src/k.py` with a key; the PR's `.gitleaksignore` has `# EXPIRES <today+30d>` and `C:src/k.py:generic-api-key:1`; `git branch -r --contains C` lists the fixed-name branch, so the entry is accepted, C is not in main, no handover notes exist, every other check is clean, gitleaks suppresses the finding. Removing the lane-only branch closed the wip/cloud-* route; the three fixed names are protected only by the ruleset (ci.yml:233-239 says not done). The code could narrow it: reject entries whose commit is reachable from a fixed-name branch the PR's own head ref also names, or restrict the accepted path, or pin allowed shas in a file the PR cannot edit.
- **M2** The guard does not police the toml allowlist beyond two literals (ci.yml:219 `grep -qE 'targetRules|handover/'`; comment :212-214). Failing input: a PR rewrites `.gitleaks.toml` with `[[allowlists]]` `paths=['''.*''']`, or a top-level `[allowlist]` with `commits=[...]` or `regexes=[...]`: none contains `targetRules` or `handover/`, no rule fires, and the gitleaks step (:259) reads that toml from the PR tree. Inline `gitleaks:allow` has the same effect. The M1 fix of round 2 removed the gate for the path checks but did not make the toml trustworthy; the comment ("cannot be allowed to switch the checks off") implies a stronger guarantee than the code gives. Predates this change; closed only by CODEOWNERS or a ruleset (listed, not done), or by failing when `.gitleaks.toml` or `.gitleaksignore` differ from origin/main outside the owner path.
