## The reviewer's answers to the attack list (abridged by the lead)
- Rounding up once per call is the meter's job; the store only validates scale (A2). Negative, NaN and huge amounts are fine once A2 is fixed (`is_finite()` first makes sNaN safe).
- Concurrent reservations across 8 processes: the cap check is one `UPDATE ... WHERE usd + amt <= cap`, so overshoot is impossible on the reserve path; the old `add_spend`/`add_cost` paths are uncapped, so "zero overshoot" holds only if all spend goes through reserve: add that to P4b1's wiring checklist (PENDING item 3).
- Interface sufficiency for P4b1/P4b2: gaps are A5 (expired status, listing by run/agent); also cheap to add now: purpose/model tags for the billing record (R221) and post-booking totals in `reserve_spend`'s return.
- Sweep identity deferred to P4b2 (a fourth role) is correct and safe. The rollback sweep procedure needs a loop, because `limit` defaults to 100.

## Considered and found sound (reviewer's list, abridged)
- Cap check as a single guarded UPDATE per counter; claim-first settle returning the first result to the loser; roll back the whole transaction on a damaged counter (no clamp); `ON CONFLICT DO NOTHING RETURNING *` replay path.
- DDL CHECKs exclude NaN/Infinity; no DELETE grant; closed row frozen by the trigger; `check_id` grammar fits repo ids; fail-closed on a missing kill-switch row; keying retry on SQLSTATE class 40 rather than a class name.
