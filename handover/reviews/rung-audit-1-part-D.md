## The first suspect does not hold (read this first)
Order 54 item 2 suspects "P5b provider adapters: do we need our own wrappers or does a gateway/library cover retries and failover". **None of P5b1 to P5b5 builds a provider wrapper, a retry loop or failover.** They are the five steps of the diagnostics redesign (error-text redaction lane):
- P5b1 adds checked facts (status, a closed error word, a shaped request id) to `ProviderError` and builds the message only from those (`tickets/P5b1.md` "Problem in plain words", line 63). It says outright: "Any change to which errors are retried, how long we wait, or how a call is billed" is NOT taken (`P5b1.md:74`).
- P5b2 lists every `ConfigError` site; P5b3 rewires the writers; P5b4 guards logs, stderr and crash hooks; P5b5 adds pins and an operator page.

The retry layer already exists and is BUILT (`<repo>/src/hadavin_sdk/llm/retry.py`, 108 lines, outside this audit). The vendor SDK retries are switched off on purpose (`llm/anthropic.py:37` `max_retries: 0`; `llm/bedrock.py:51` `total_max_attempts: 1`), so this loop is the only one. That is a money guarantee: P4b2 classifies EVERY attempt as refused, unsent or unknown and books the upper bound for unknown attempts (`tickets/P4b2.md:52-54`). An SDK or gateway that retries out of sight makes N upstream requests that our meter sees as one, so it would under-book. The SDKs would cover retries themselves: READ-WHEEL anthropic 2.1.0 `_constants.py:11` `DEFAULT_MAX_RETRIES = 2`, and it honours `retry-after-ms` and `x-should-retry` (`_base_client.py:878-931`). But they expose the count only as the outgoing header `x-stainless-retry-count` (`_base_client.py:560`), not on the raised error. botocore 1.43.122 `retries/standard.py:44` `DEFAULT_MAX_ATTEMPTS = 3`. **Failover to another model:** R16 and R180 say an alternative model counts only after the golden set passes on it. A gateway fallback (LiteLLM-style `fallbacks`, UNVERIFIED) would switch to a model that never passed the gate. A gateway can still be used today with no code: point the `openai_compat` kind at it and set the gateway's own retries and fallbacks to off (config and the client's choice, R445/R446). So the honest answer to the suspect: no cut, because there is nothing in these tickets to cut, and the built retry loop is "really required" for P4b money rules.
