## Positions
1. **Blocker, choice of design.** Option (a), INSERT-only stop with a derived switch state and a count-checked reset, is the smallest design that removes the lock hold: the runtime holds no privilege on any object another caller can wait on (FOR KEY SHARE needs UPDATE, LOCK TABLE above RowExclusive needs more than INSERT, and it has not even INSERT). Option (b), a watchdog, needs a long-running privileged process, a new identity and an interval during which the stop is still denied. Option (c) is honest and tiny but leaves the stop deniable by the thing it restrains, which is the one property A13(3) exists to prevent. Recommendation: (a); if the evidence run (Position 3) shows the reset-versus-stop race is not closed by the count check, fall back to (c) with the lead's explicit yes. Order 7: this is a security defect, so design growth is allowed; it removes the trigger regex branch, mut-F3 and the rev 7 `hold`-bounding text, so the net surface is roughly neutral.
2. **Rollback recipe versus the regex branch (ADV-R6-3):** remove the regex branch from the trigger (the stop no longer passes through it); the recipe is one `GRANT INSERT, UPDATE` and works for the old release's stop. PENDING LEAD 11 narrows to "`DISABLE TRIGGER` only for a full unguard".
3. **SQL evidence before round 7 (ADV-R6-8).** The lead launches an EVIDENCE RUNNER (it runs and records, it never judges) on a throwaway PG16 with made-up names after the author writes rev 8, and saves the raw output to `handover/evidence/P2a-sql.md` (additions S29 onward; the PG17.10 behaviour stays UNVERIFIED because only 16 is installed).
