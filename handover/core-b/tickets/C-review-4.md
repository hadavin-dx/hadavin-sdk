## Findings

### M1 (Medium) `MemoryStore.reserve_spend` checks the cap in the money context but BOOKS the sum outside it
store/memory.py:337 `self._spend[(agent_id, day)] = booked + usd` runs with the caller's context (the `localcontext` blocks at 324 and 329 closed before). Repro r4.py, caller precision 4: two `reserve_spend` of 1234.123456789012 and 1.000000000001 leave the day counter at **1235**, exact 1235.123456789013. The cap check passed on the exact 60-digit sum, the booking is rounded: it can round DOWN, so the counter under-books and a later reserve passes a cap it should hit. The test `test_memory_month_total_and_reserve_arithmetic` (tests/test_money_context_everywhere.py:63) only sees the cap decision, not the stored value. Same class, same file:
- memory.py:94-95 `add_cost`: `run.cost_usd + usd` outside the context. The run's cost (read back by runtime/agent_loop.py:285 `cost_usd >= cap`, the per-run cap) rounds under a low host precision. Not covered by any test (settle_spend's twin at 365 is covered).
Fix: wrap both lines in `with localcontext(defaults.money_context())` (inside the lock, like the rest of the file) and add one test each at caller precision 4. Low likelihood (host must lower the global precision; memory store is demo/test; default 28 digits is exact for any amount the store accepts), so Medium, not High.

### m2 (Minor) The new Overflow trap and the unmapped `reply` site
Pinned behaviour check: a price is <= 10**6 with 6 decimals (config.py:92-107), tokens are ints, so no product gets near Emax 999999; Overflow cannot fire for any validated route. Where it can in theory (a 4300-digit token count, the most Python's int/str limit lets a JSON or YAML number carry, still far under Emax; so in practice unreachable): `llm/common.py:worst_case_for` catches `Exception` -> SpendRefused("bad_amount") (fine, and tested by round 3); `config.py:105` maps ArithmeticError to a ValueError and `config.py:709` to ConfigError (fine). `llm/common.py:266` (reply pricing), `llm/fake.py:51`, `k1b/loop.py:106` (worst_case_usd, called at k1b/loop.py:158) have no mapping: an Overflow/InvalidOperation there would be a traceback, where before the trap it was Infinity (which `check_spend_amount` would then refuse as bad_amount). Not reachable with validated input; listed because it is a behaviour change. Cheap hardening if wanted: `except ArithmeticError` around the reply price -> treat as unknown cost, forfeit at the worst case. No pinned test changes: all 79 pass.

### m3 (Minor) Per-call context cost
Measured here (3.13): `money_context()` 0.9 us; a full `localcontext(money_context())` + the price expression 2.9 us against 0.66 us bare, i.e. about 2.2 us added per use. The reserve path takes one worst-case price plus two store contexts, a few microseconds against a model call of hundreds of ms and a DB round trip. Negligible; a module-level cached Context would be unsafe-looking for no gain (`localcontext(ctx)` copies it anyway). No change.

## Answers to the questions
1. **Arithmetic left outside the context:** M1 and m1 above. Checked and fine: comparisons (`>=`, `<`, `max`, `min`) never round, so runtime/agent_loop.py:285, memory.py:359 `max`, limits.py `max(...)` are exact whatever the context (the subtraction inside `max` at limits.py:118 and :208 is in the context). store/postgres.py: no Python-side money arithmetic, only `Decimal(d)` conversions at :467, :478 and SQL `usd + %s` (database numeric, not the caller's context); `delta = row["settled_usd"] - row["reserved_usd"]` at about postgres.py:734 is a Python subtraction of two DB values, outside the context (m1-class; both are <= 12 places and < 1e9, so exact at any precision >= 21 and a host at precision < 21 is the same low-likelihood case: list it with m1). models.py: fields only, no arithmetic. guard/: only injection.py:77 (m1). approvals/, audit/, actions/: no money arithmetic. Amount text formatting: `format(v, "f")` (k1b/report.py:36, replay.py:252) and the f-strings at cli.py:580-582 print stored Decimals as they are, no arithmetic, nothing to wrap.
2. **Overflow trap vs pinned behaviour:** see m2. No pinned test depends on Infinity; the one place that could hit it from input (route price check) already maps to a refusal/ConfigError, and `worst_case_for` maps to bad_amount.
3. **`localcontext` safety:** safe. `decimal` contexts are per-thread/per-task (contextvars); `localcontext(ctx)` copies `ctx` on entry and restores the caller's on exit, and `money_context()` builds a new object each call, so nothing is shared across threads or asyncio tasks. No `await` sits inside any of the `with` blocks (all sites are synchronous arithmetic), so no task switch happens while the context is set.
4. **Cost of a context per call:** m3, negligible.
5. **Test importing the removed `llm.common._money_context`:** none. grep over src/, tests/, tools/, demos/: only the handover ticket C-review-3.md mentions the name (history text).
6. **Memory store lock order:** the context is entered INSIDE the lock everywhere in memory.py (212, 291 via callers holding the lock, 324, 329, 363, 372); the lock is a plain `threading.Lock`/RLock held around, never the reverse, so no deadlock or lock/context ordering issue. `Budget` the same (limits.py:70 inside `_lock` at :69-71; :93 and :117 inside the lock). Nested contexts (add_spend -> _month_total) are fine.
