## Purpose, in plain words
Today the runtime login holds UPDATE on `spend`, `spend_month`, `spend_reservations` (and INSERT on the reservations), so a runtime that writes its own SQL can lower a booked amount (E13 H1, H2) and the 0010 trigger is only a tripwire. After this ticket the runtime login holds no write right on those three tables at all. The only writers are a handful of SECURITY DEFINER functions owned by the migration owner, each with a pinned search path; the runtime holds EXECUTE on them and nothing else. The store interface does not change: the same Python methods call the functions instead of running SQL. The promise "a runtime login cannot lower a booked amount except by settling its own open hold, once, up to that hold" then holds by construction, not by a trigger that tries to guess.

## Design

### Rules for every function body (PL/pgSQL, review Major 4)
- `VOLATILE` stated explicitly (never STABLE/IMMUTABLE: a frozen snapshot breaks the claim re-check after a lock wait under READ COMMITTED). Statement order in the body is the lock order: reservation row, day counter, month counter.
- NO `EXCEPTION` blocks (they open a subtransaction, cost time and change the rollback the store relies on for HD003). Errors are raised, never caught inside.
- `#variable_conflict use_column` as the first line of every function that has `RETURNS TABLE`/OUT names (settle, add_spend), AND table aliases on every table reference (`r.reservation_id`), so a column named like an OUT variable never raises "ambiguous".
- Numeric math in SQL is exact; the parity test includes a 12-decimal amount against the Python `defaults.money_context()` delta (postgres.py 945-946).
- No hard-coded limit literals (1e9, 200, 10000000, the scale 12) in the SQL: see "Limits come from defaults, not literals".
- The store calls every function SCHEMA-QUALIFIED, `{schema}.hadavin_reserve_spend(...)` built with `psycopg.sql.Identifier` through the `_t` pattern (postgres.py 635-643), never an unqualified name resolved through the caller's search path (a caller session can `SET search_path` to a schema holding a same-named function). A static test (extension of `tests/test_money_definer_static.py`) asserts every `hadavin_*` call the store makes is qualified, including the five new names and `hadavin_release_expired_spend`.
- Verify-first step (step 2, before bodies are built on it): a tiny test that `RAISE EXCEPTION USING ERRCODE = 'HD001'` reaches psycopg as an exception with `exc.sqlstate == 'HD001'` (the installed psycopg version; class `HD` is a valid uppercase class). The store branches on `exc.sqlstate` and reads the cap kind ('day'/'month') from `exc.diag.message_primary`; if that fails, the codes become `P0001` plus a fixed `HINT`/`DETAIL` token.

### The functions (all in 0011, all `LANGUAGE plpgsql SECURITY DEFINER SET search_path = pg_catalog, pg_temp`, owner = the migration owner, `REVOKE ALL ... FROM PUBLIC` in the same file; `migrate` re-pins to `pg_catalog, <schema>, pg_temp` on every run and grants EXECUTE to the right roles)
Signatures (the store interface above them does not change):
- `hadavin_reserve_spend(p_id text, p_agent text, p_day date, p_usd numeric, p_day_cap numeric, p_month_cap numeric, p_run_id text) RETURNS void`. Body = today's reserve: INSERT reservation (duplicate id -> native unique_violation 23505, store maps to StaleState as now), seed day and month rows `ON CONFLICT DO NOTHING`, conditional UPDATE day then month, cap refusal `RAISE EXCEPTION USING ERRCODE = 'HD001', MESSAGE = 'day'|'month'` (store maps to `SpendCapExceeded`). Whole function is one transaction (the function body runs inside the caller's transaction; the store keeps `with self._db.transaction()` and READ COMMITTED, postgres.py:170-175).
- `hadavin_settle_spend(p_id text, p_actual numeric, p_agent text) RETURNS TABLE (...the nine reservation columns..., claimed boolean)`. Body = `_CLAIM` plus counter move by `settled_usd - reserved_usd` on the row's own day and month plus `UPDATE runs SET cost_usd = cost_usd + p_actual WHERE run_id = row.run_id` (a missing run row ignored). Unknown or foreign id: `ERRCODE 'HD002'` (store maps to NotFound; same text for both, nothing revealed). A second settle returns the stored row with `claimed = false`. A missing counter row: `ERRCODE 'HD003'` (store maps to RuntimeError "spend counter row missing" as now; the transaction rolls back).
- `hadavin_expire_spend_reservations(p_age_s integer) RETURNS bigint` (open -> expired on `clock_timestamp()`; counters do not move).
- `hadavin_purge_spend_reservations(p_before timestamptz) RETURNS bigint` (DELETE settled rows with `closed_at < p_before`; granted to the PURGE role only; the purge role's DELETE on `spend_reservations` and its two column SELECTs are removed from `GRANTS`, so purge also writes through a function). ASK THE LEAD: confirm purge becomes a function (the order says "purge ... if they touch those tables"; they do).
- `hadavin_add_spend(p_agent text, p_day date, p_usd numeric) RETURNS TABLE (day_usd numeric, month_usd numeric)` (two upserts, day then month; raise only).
- `hadavin_release_expired_spend` (0008) is unchanged: it stays the release role's function; its signature, owner and pin are not touched. It runs as owner so the 0010 triggers pass it as today.
- No dynamic SQL anywhere: no `EXECUTE`, no `format()`, no `||` building a statement. All table names are static in the body and resolve through the pinned path. A static-source test enforces this (below).

### Arguments are validated INSIDE every function (the function is the trust boundary; the Python checks stay as the early, friendly refusal but prove nothing)
Each function starts with explicit checks and `RAISE EXCEPTION USING ERRCODE = '22023'` (invalid_parameter_value), text names the parameter never the value:
- any NULL where a value is required (NOT `STRICT`: a STRICT function returns NULL silently, which would look like success; explicit raise instead). `p_run_id` and settle's `p_agent` may be NULL.
- ids (`p_id`, `p_agent`, `p_run_id`): length 1 to 200 (`char_length`), no characters 0-31 or 127-159 (`p_x ~ '[\x00-\x1f\x7f-\x9f]'`; NUL cannot reach a text parameter at all), mirrors `check_store_id` 84-96.
- day: not `'infinity'`, not `'-infinity'`; plus the same plausible window the store uses for a day (builder reads `check_spend_day`; today it only requires a plain `date`, so the function adds only the infinity refusal and the contract tests decide anything stricter).
- amounts (`p_usd`, `p_actual`): not NaN (NaN sorts ABOVE every number, so the check is written positively, `p_usd >= 0 AND p_usd < <amount limit>`, which NaN fails), `scale(p_usd) <= 12`, upper window as `clean_spend_amount`. CAPS ARE A SEPARATE RULE: `check_spend_cap` (119-139) has NO upper bound except the exponent window -12..9 for the number's form, so the cap check is `>= 0`, not NaN, not infinite, and the same form window as `check_spend_cap`; it MUST NOT reuse the amount's `< 1e9` window (a legitimate cap of 1E+9 or 10**12 must keep working; a hostile-table row proves it).
- `p_age_s`: `0 <= p_age_s <= max_expiry_age` (from `hadavin_limits`), same as `check_expiry_age`; NO lower bound (DROPPED, B1: it would break the contract tests `expire_spend_reservations(0)` and diverge from the memory store; documented as a stated residual in the Honest residual paragraph, the runbook and the migration header). `p_before`: not infinity.

### Limits come from defaults, not literals (mechanism DECIDED: the `hadavin_limits` relation)
The amount window, id length, scale, cap exponent window and expiry-age maximum live in `protocol.py`/`defaults.py` (constants read now: `MAX_RESERVATION_ID_CHARS` = 200, `MAX_SPEND_DECIMALS` = 12, `MAX_SPEND_EXPONENT` = 9, `MAX_EXPIRY_AGE_S` = 10**7, and the amount window of `check_spend_amount`, 1e9). The SQL contains NO such literal. Mechanism (no text substitution into function bodies: it would need `CREATE OR REPLACE` on every run and fights the released-manifest and migration-number lexer rules): a small relation, defined in 0011:
```
hadavin_limits (name text PRIMARY KEY, value numeric NOT NULL)   -- one row per limit name
```
Rows (names are the interface; builder B writes them, builder A reads them): `max_amount` (amount window, exclusive upper bound), `max_decimals` (scale), `max_exponent` (cap exponent upper window, lower window is `-max_decimals`), `max_id_chars`, `max_expiry_age` (the `MAX_EXPIRY_AGE_S` maximum). There is NO lower expiry bound (see B1 in the round 2 answers). `migrate` upserts every row from the Python constants on EVERY run (`INSERT ... ON CONFLICT (name) DO UPDATE SET value = EXCLUDED.value`, run by the owner), so a changed default reaches the functions at the next migrate. The functions read the rows as owner (one `SELECT value FROM hadavin_limits WHERE name = ...` per limit, static names, no dynamic SQL); a missing row raises `HD004` (fail closed). GRANTS row: `hadavin_limits`: runtime `""`, purge `""`, every other named role `""`, owner only (the definer functions read as owner); `check_grants` and its test cover it. `tests/test_no_hardcoded_values.py` names only `.py` paths; `tests/test_lockin_guard.py:734-741` DOES scan the migration `.sql` for vendor literals, so 0011 text is scanned by that guard (correction of the round-1 assumption). The guards against SQL literals: the parity test (with a run at a changed default) plus a small grep test over 0011 (`1000000000|10000000|\b200\b` outside comments).
- Parity test: one table of hostile arguments is run through the Python validators AND through the functions called directly by the runtime login; accept/reject sets must be identical (so Python and SQL cannot drift).

### Honest residual (state it in the migration header, the runbook and lead question 5; do not over-claim)
The runtime still chooses the arguments, so it can (1) call `hadavin_reserve_spend` with a huge or disabling cap: the runtime CAN DISABLE CAP ENFORCEMENT (an overshoot of the budget) but CANNOT LOWER A BOOKED AMOUNT (an overshoot, not an erasure; the cap is a caller argument today, as `Limits` passes it; E13 is about lowering, the cap source belongs to core-c's gate config; a database-held `money_caps` table is the named follow-up). So the wall makes "cannot lower a booked amount" true by construction, NOT "the budget is enforced" (today the gate runs in the same process), (2) call `hadavin_settle_spend(id, 0, NULL)` on ANY open hold id it knows, which is the legitimate release of a hold: the counter falls by at most that hold's reserved amount, once (the runtime needs no SELECT on `spend_reservations` for this: ids are caller-chosen and a runtime cannot list other agents' open holds), (2b) call `hadavin_expire_spend_reservations` with age 0 on every open hold (STATED RESIDUAL, no lower bound: a runtime login can expire open holds of every agent at any age, a self-inflicted outage and cost distortion that exists today; safe: holds stay booked at reserved; the real caller `runtime/tick.py:281` passes at least 3600 s, `defaults.RESERVATION_EXPIRE_S`, and the contract suite needs age 0 to work on both stores), plain `add_spend` charges, settled holds and expired holds never fall (a later settle of an expired hold only raises, as now), (3) raise any counter by `add_spend`. What it can no longer do: lower a plain charge, lower any settled or expired amount, forge a settled row, edit usd, or touch a row by SQL. The promise sentence for the docs: "a runtime login cannot lower a booked amount except by settling an open hold it can name, once, by at most that hold's reserved amount". ### Search-path hijack
Each function carries `SET search_path = pg_catalog, <schema>, pg_temp` (placeholder `pg_catalog, pg_temp` in the file, re-pinned by a new `_pin_money_functions` that loops a new `MONEY_FUNCTIONS` tuple exactly like `_pin_money_guard`/`TRIPWIRE_FUNCTIONS` 97-101, 630-635; it must run on EVERY migrate run, also when 0011 is already applied, and for a database that has no 0011 it does nothing). pg_temp last means a TEMP TABLE of the caller never shadows `spend`, `spend_month`, `spend_reservations` or `runs`; pg_catalog first means a user operator or function cannot shadow `+`, `<=`, `greatest`, `sum`, `clock_timestamp`. Function bodies call only pg_catalog built-ins (no user-schema function), so a function the runtime plants in the schema cannot be reached; the CREATE-on-schema refusal above closes that anyway. Residual: `CREATE TEMP FUNCTION`/operators in pg_temp are searched last for functions only when schema-qualified; test below. The migration does NOT revoke TEMP on the database from PUBLIC (a database-wide setting that needs the database owner; recommended in the runbook as extra hardening, not relied on).

## Migration and rollback story
0011 is additive: it creates functions and revokes nothing by itself; the grants flip happens in `migrate()` when roles are named, in the same transaction (one advisory lock, so a runtime never sees functions without grants or grants without functions). Order of the first run: new package `migrate` (creates functions, pins, flips grants), then new application code; NOT the reverse: new store code against a database without 0011 fails with "function does not exist" (fail closed, loud). Old application code against a migrated database fails on its first write with insufficient_privilege (fail closed). Rolling upgrade is therefore NOT supported: stop the runtime, migrate, start the new runtime; the runbook says so. RUNBOOK LINE (M3): stop the `tick` scheduler (cron) and EVERY other runtime-side process (purge, portal, workers) BEFORE migrate 0011; after migrate and the rollout run ONE smoke `tick`. Between steps 2 and 3 (0011 applied, old grants still in place) old-code ticks keep working through the old SQL, and new-code ticks against a database without step 2's migrate fail with "function does not exist" in the `tick` log (FAILED expire/purge steps, loud); after the step-4 flip, an old-code tick fails with insufficient_privilege on expire and purge (FAILED steps in the `tick` log, fail closed, pages). `migrate` prints this order. Step 3 must not ship before step 2 is migrated.
Down path (no automatic down file; the ledger refuses a database newer than the package, migrate.py ~"applied migrations have no file in this release"): as the owner, (1) `DELETE FROM schema_migrations WHERE version = '0011_money_definer'`, (2) `DROP FUNCTION` the five, (3) run the OLD package's `migrate` with the same roles: its `_apply_grants` resets the runtime to the old `_RW` grants and the old purge grants (REVOKE ALL then GRANT per map), so the old grants return and the 0010 tripwire is active again. Document this as the supported rollback and TEST it (up, down, old store contract suite green).
Break-glass in production (a bug in a function, or an operator must repair a counter): the OWNER (never the runtime) either runs the repair SQL directly (the owner has every right; the 0010 triggers pass the owner), or ships a new migration `CREATE OR REPLACE` for the function (the pin is re-applied by the next migrate run). The DISABLE-trigger emergency switch of the 0008/0010 headers (`ALTER TABLE spend DISABLE TRIGGER spend_money_guard`, same for the other two, later ENABLE) keeps working and is now needed only for an owner-run repair that lowers a counter below the booked holds (the triggers still guard the owner's direct UPDATEs only where the owner check fails: inside the definer functions and for the owner login it passes, so DISABLE is rarely needed; the note in the header is reworded accordingly). Re-granting UPDATE to the runtime as an emergency is possible by the owner but is a wall-break: the next migrate run takes it back, and the runbook says to treat it as an incident.

## TRADE-OFF STATEMENT
Chosen: **B** (definer functions, runtime holds no write right). Simpler: **A** (the 0010 tripwire, already merged in the tree, reworded promise, H3/M1/M2/M3 fixed in place): cheap, store SQL stays in Python, but it only stops accidents and naive attacks; the round2 tests reproduce H1, H2, L2 on a PG16.
What B gives up: (1) the SQL logic moves from Python into PL/pgSQL: harder to unit test (needs a database; no debugger; errors surface as SQLSTATEs), harder to review (a second language in the money path), and two implementations to keep equal (memory store in Python, Postgres in SQL), held together only by the contract tests and the hostile parity table. (2) Every change to a store money rule needs a migration, a pin re-run and the no-rolling-upgrade deploy; a hotfix is a migration, not a code push. (3) A bug in a definer function runs with the OWNER's rights (a superuser owner would make it a superuser bug): the functions are short, have no dynamic SQL, validate every argument and are pinned, but a wrong comparison in one of them is a money bug with no second line (the 0010 triggers pass the owner by design: owner-first means the trigger no longer protects against a bug INSIDE the definer functions). (4) The deploy needs a distinct non-runtime owner login and all roles named in one migrate command. (5) About 3 to 4 builder days, instead of zero.
Why B anyway: the money promise ("a runtime login cannot lower a booked amount") becomes true by construction: the right to write is absent, not a rule to be guessed by a trigger, and the residual is exactly stated and small (settling an open hold you can name). A tripwire that a login reproduces the bypass of in four statements is the wrong foundation for the one claim the product sells. The functions are few (five), static and tested by mutants for each pinned setting.
