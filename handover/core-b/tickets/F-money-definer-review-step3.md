## (1) Parity with the old store

Confirmed equal, by reading old code against the function:
- settle returns `(row, claimed)`; second caller waits on `FOR UPDATE`, finds the row settled, gets the stored row back with `claimed=false`; unknown or other-agent id -> HD002 -> `NotFound` (old: `NotFound` for both). Expired row settles to `GREATEST(actual, reserved)`; "expired row that does not rise leaves counters alone" kept; counters move on the row's own day and month, day first.
- reserve: same sequence (row insert, seed+cap UPDATE day, seed+cap UPDATE month); duplicate id -> 23505 -> `StaleState`; cap -> `SpendCapExceeded('day'|'month')`.
- expire: same predicate, db clock, rowcount = `ROW_COUNT` (BIGINT -> int). Purge: `status='settled' AND closed_at < before` (the A11 copy still had `<> 'open'`; the E11 M3 rule is the current one, fine).
- schema qualification and `SELECT *` column access (`row["hadavin_expire_spend_reservations"]` is the right single-column name for a scalar function).
- Exception classes for argument refusals: the Python checks still run first (`check_spend_amount`, `check_reservation_id`, `check_store_id`, `check_spend_day`, `check_spend_cap`, `check_expiry_age`, `check_purge_bound`), so every old pre-DB ValueError is unchanged. The only class the function adds is 22023 -> `ValueError` (no other class). Inputs that the Python check lets through but the function refuses (all were accepted by the old PG store and still are by the memory store):

**Minor 1 (parity, `postgres.py:634-646`, `:909-935`; SQL l.99, l.285):** `p_day < DATE '1970-01-01'` is refused by the function. `check_spend_day` only tests `type(day) is date`, so `reserve_spend(..., date(1969,12,31), ...)` and `add_spend(..., date(1900,1,1), ...)` used to book, still book in the memory store, and now raise `ValueError("spend argument refused by the database")`. A contract test with an old date would diverge. Either add the 1970 bound to `check_spend_day` (both stores) or drop it in SQL. Same for `add_spend`'s agent id: `add_spend` runs no `check_store_id` (only `clean_spend_amount`), so `add_spend("", day, x)` or an id longer than 200 / with a control character used to book (NUL: psycopg `DataError`), memory books it, and now it is a 22023 `ValueError`. Add `check_store_id(agent_id, "agent_id")` and `check_spend_day(day)` to `add_spend` in both stores so the Python and SQL rules are one rule.

**Minor 2 (parity, SQL l.215):** run cost is bumped only `WHERE u.run_id = rec.run_id AND u.agent_id = rec.agent_id`. Old PG code and the memory store (`memory.py:392-398`) add `actual` to the run whatever its agent. Scenario: reserve for agent A with `run_id` of a run owned by agent B (the store never checks the run belongs to the agent), settle: memory raises B's `cost_usd`, PG now does not. Likely the intended hardening, but it is an undocumented divergence: either mirror it in the memory store (and say so in the ticket) or drop the extra condition.

**Minor 3 (message only, SQL l.205-212):** HD003 now also fires when the counter exists but `usd + delta < 0` (a drifted counter); it maps to `RuntimeError("spend counter row missing")`, which is a wrong diagnosis for that case. The memory store has no such guard (counter can go negative). Rename the Python message to "spend counter row missing or below its holds".

Money arithmetic parity: counters are exact `numeric`; the old PG path was also exact in SQL, and the memory store runs a 60-digit `money_context` with ROUND_HALF_EVEN. Inputs are bounded (< 10^9, <= 12 decimals), so every sum, difference and delta has at most 9+12+small digits: the 60-digit context never rounds, so the two give identical values at 12 decimals. `-0`: `clean_spend_amount` removes it in add_spend; reserve/settle pass `Decimal('-0')` unmodified (`check_spend_amount` only), PostgreSQL numeric has no negative zero (`'-0'::numeric` is `0`), and `x - x` is `+0` in both. Run cost: `u.cost_usd + p_actual` is exact like the memory sum. Trailing-zero scale can differ (`Decimal('1.50')` vs `1.5`) but `==` is what the tests and callers use. No counter divergence found.

## (2) `_money_error` breadth and fail-closed behaviour

- `psycopg.errors.DatabaseError` includes `OperationalError`, so a lost connection (57P01 admin_shutdown, 08xxx, lock timeout 55P03, 57014 statement timeout) lands in `_money_error`. Its `sqlstate` is not HD/23505/22023, so it falls to `return exc` and is re-raised as the SAME object (`from None` only drops `__context__`). `is_connectivity_error` then still sees `OperationalError`: not swallowed as `ConfigError`. `InterfaceError` (closed connection) is not a `DatabaseError` and propagates untouched. A dead connection with `sqlstate None` -> unchanged. OK. (The pytest `test_an_unmapped_hd_code...` covers the one case that WOULD be wrong, an unknown `HD***`, which psycopg raises as `OperationalError`.)
- HD004/HD005 -> `ConfigError` (not a connectivity error). Callers: `Limits.reserve` (`limits.py:177-200`) has `except Exception` and maps everything to `SpendRefused("limits_unavailable")`; `SpendRefused` is raised before any model call, so a `ConfigError` cannot escape `reserve`, and there is no `reserve`/`settle` call in `agent_loop.py` at all (`grep`: none; the gate is the host's). I could not construct a stranding scenario at reserve. Tick: `expire_reservations` / `purge_evidence` are steps; `_run_step` catches `Exception`, records FAILED -> exit 1 (not 4, because the post-step `get_tick_state` probe answers), which is the correct "store up, step failed". HD004 never reaches exit 4 or 2.
- `add_spend` is called from `agent_loop.py:353` (`_screen`) and `:513` via `limits.charge`, with no `try` around them: a `ConfigError` (HD004) now propagates where an unlabeled psycopg error did before. Both are "any Exception" for the surrounding step code; the only place `except ConfigError` could change the outcome is `cli.py:95/318/417` (CLI entry points), which would print a config error instead of a traceback for a run command. Not a stranded run: the same propagation as before. Mention only.
- `settle` (`limits._settle`) does not catch: `ConfigError` from HD004 now reaches the host instead of a `psycopg` error. Host-visible class change, same failure semantics. Document it in the Limits docstring if hosts catch `ConfigError` as "bad config".
- Nit (`postgres.py:394`): 23505 maps to `StaleState(f"spend reservation exists: {reservation_id}")` for any call; from `add_spend`/`expire`/`purge` `reservation_id` is None and the text would read "...exists: None". Unreachable today (the upserts handle conflicts) but wrong if it ever happened.

## (3) `_money_call` injection and format safety

`sql.SQL("SELECT * FROM {}.{}({})").format(Identifier(schema), Identifier(function), SQL(placeholders))`: `function` and `placeholders` are string literals at the five call sites (nothing user-derived reaches `sql.SQL`), `schema` is `current_schema()` read once and quoted with `Identifier`. All values go through `%s` placeholders with an explicit `::cast`, in a parameterized `execute`. The placeholder string contains only `%s::type`; no `%` or `{`/`}` leaks into `.format`. Safe. One style point: `sql.SQL(placeholders)` accepts a free string from a private helper; acceptable.

**Minor 4 (false justification, `postgres.py:668-672`, test `test_the_money_function_calls_name_their_schema...`, mutant H23):** the docstring and test say an unqualified function name is looked up in `pg_temp` first. That is wrong: PostgreSQL never searches the temporary schema for function or operator names, even when `pg_temp` is listed first in `search_path`. I ran it on the shared server: with `search_path = pg_temp, public`, a `pg_temp.zzf(int)` decoy and a `public.zzf(int)`, `select zzf(5)` returned the `public` one. So the decoy test cannot fail for an unqualified call, and H23 is not killed by the decoy: it "dies" because the mutated text builds `hadavin_x.hadavin_x(...)` (schema does not exist) and the killer string "decoy was called" appears in pytest's printed source of the test, so the kill is vacuous. The qualification is still worth keeping (search_path independence), but the claim "a temporary function never answers" is untested and the real protection is the `SET search_path = pg_catalog, pg_temp` pin inside the functions. Fix the wording, and re-aim H23 at "money call without schema" with a store whose `search_path` does not contain the schema (killer: `UndefinedFunction`). The unqualified `hadavin_release_expired_spend(...)` call (`postgres.py:~1005`) is consistent with that (equally safe).

## (4) Transactions

The store connection is autocommit. Each function call is one statement, so it is atomic and rolls back by itself on error (a plpgsql function runs in the caller's implicit transaction). `with self._db.transaction()` is therefore NOT needed for correctness: it adds `BEGIN`/`COMMIT` (two extra round trips per call, hot on `reserve`). It is harmless and also gives one rollback path if a later step puts two calls in one block; but "expire and purge now run in a transaction (no change in effect)" is right only for effect, not cost. Locks: row/counter locks are taken inside the function in the same order as before; `lock_timeout` is a session `SET` (`postgres.py:351`), applies to waits inside the function identically, with or without the extra `BEGIN`; the lock is released at COMMIT/statement end either way, and `self._lock` (Python) is held across the whole call as before. Expire/purge: one `UPDATE`/`DELETE`, row locks held for that statement, no longer. No finding beyond the cost note.

**Minor 5 (reserve_mutants H6 "equivalent", `tests/reserve_mutants.py:366-369`):** correct that "insert outside the store's transaction" is equivalent now, but it is the extra `transaction()` that is redundant (point above), not a safety property; the listed reason is sound. No action except to be consistent: if the `transaction()` wrapper is later dropped, nothing in the suite would notice, because no test fails when it is removed. That is acceptable only if someone says so; say so.
