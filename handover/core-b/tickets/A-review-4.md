## MAJOR

1. A transiently refused older row is overtaken by newer rows in the same pass: Major 1 is defeated in the case it was written for.
- chain.py:393-394 (`for event, row_id in items: self._drain_item(...)`) and :411-425 (`_drain_item`, transient branch only counts or flags).
- Scenario (reproduced on the sqlite chain, scratchpad r4.py): outbox rows A (ts 10:00:00, id "b") and B (ts 10:00:01, id "a") of one run. `_append(A)` raises a transient error (lock timeout 55P03, 40001 or 40P01 on A's attempt only; a lock wait that expires on one event and not the next is the normal shape). The pass does not stop: B is appended, A is deferred. Result: chain order is ['a' (B), 'b' (A)], newer before older, and the next tick can never repair it. `_flush_pending` (chain.py:322-340) does stop at the first transient failure; `_drain_pass` does not. A7(e) states the residual only for the inline write path (an intent must not wait on a sick outbox), not for the tick, and no test covers it: test_audit_drain_transient.py:156 and :166 cover only the inline path.
- Fix: in `_drain_pass`, after a transient failure (not permanent, row or memory), stop the pass (break) so no later item is written; permanent refusals are skipped as now. Add a test: two rows, first raises 55P03 once, assert the chain has neither after the pass, then both in ts order after the next. The same applies to a memory event that fails transiently while a newer outbox row succeeds.

## MINOR

1. Unreadable rows can starve newer rows. chain.py:378-390 and :362-370. A row that is valid JSON with a ts but fails `AuditEvent` validation, or whose event_id differs from the body's, is never renamed (A7 says so), stays in every batch in ts order, and is counted each tick. With 500 such rows older than a good row, the good row is never read: the LIMIT counts them. Needs 500 corrupt rows, and the step fails loudly every tick, so Minor. Plain non-JSON bodies sort last and only cost slots when fewer than 500 good rows exist. Quarantined rows do not use slots (test_audit_drain_transient.py:201 covers it); permanent refusals other than 42501 leave the batch. A backlog of 42501 rows does stay, but a missing grant refuses every row alike, so nothing newer could succeed either.
2. Ordering across batches. chain.py:362-370 and :393. The batch is the oldest 500 by lexical ts text; memory events (newer) are merged only with that batch. With a backlog above 500, a memory event can enter the chain before outbox rows older than it that are in a later batch. Also the SQL order is lexical, so mixed offsets or `Z` vs `+00:00` vs fractional seconds can pick the wrong 500 at the batch edge. Inside a batch the Python sort on aware datetimes is correct for mixed UTC offsets (checked by reading; the A7 limit text says so). Stated limit in A7, only edge impact.
3. A naive `ts` in a body raises. chain.py:393: `items.sort` compares naive and aware datetimes (reproduced: TypeError "can't compare offset-naive and offset-aware datetimes"). `_drain_pass` is documented "never raises", and `reconcile` then raises TypeError every tick and drains nothing until the row is removed. `AuditEvent.ts` defaults to an aware now(), so it needs an event built with a naive ts (`_append` treats it as local time). Fix: normalise to aware UTC in the sort key, or treat a naive ts as unreadable.
4. Quarantine on a classifier-unknown exception. chain.py:92-99 (`_is_permanent` last line) with :417-422. An exception with no psycopg MRO that is not StoreUnavailable, OSError or sqlite3.OperationalError counts as permanent, so a transient bug of that kind (for example an AttributeError or RuntimeError raised by a wrapped connection or pool during a reconnect) moves a memory event to `_unwritable` (not lost: retried each reconcile, step stays red) and renames an outbox row to `poison:` (kept, never retried automatically; the step is red every tick and the A7 operator SQL re-queues it). No event is deleted, and the chain dedupes by event_id, so a healed row cannot duplicate. The cost is an unneeded manual re-queue. psycopg_pool errors (PoolTimeout and similar) have a psycopg MRO and no SQLSTATE, so they are transient, correctly. Accepted by A7(a) ("a bug does not heal by waiting"); noted only.

- Major 2: 55P03, 40001, 40P01, 57014 are not in AUDIT_PERMANENT_SQLSTATES (defaults.py:169), so they are transient; `_flush_pending` stops at them and keeps the event in `_pending` (chain.py:327-329); with sqlstate 55P03 raised from `_append` this is pinned by test_audit_drain_transient.py:41. `_transient_stuck` makes reconcile say so (:54).
- Memory events are merged into the same sort as outbox rows (chain.py:386-393; test :147). Test :137 uses ids that sort opposite to ts.
- Quarantine: insert `poison:<id>` (ON CONFLICT DO NOTHING) then delete. Crash between the two leaves both rows; the next tick retries the original: a second permanent refusal makes the insert a no-op and the delete runs; if the cause is gone it is appended once (event_id dedupe at chain.py:178-179 under the advisory lock) and deleted, leaving a stale `poison:` copy that is counted until removed. No duplicate in the chain either way. An operator re-queue of a poison copy after the original already landed is also deduped.
- Per-tick batch: quarantined rows are excluded by `event_id NOT LIKE 'poison:%'`, so 500 quarantined rows cannot block newer ones (ts-ordered LIMIT applies after the filter). Cost: full-table ordered scan per tick, a stated limit.
- Bounded drain on write: `_drain_older_first` runs one pass (batch 500) only when this process parked an outbox row, under `_flush_lock`; the later `_flush_pending` takes the lock after the pass has released it, so no self-deadlock. It never raises, and a transient failure there lets the new event through (stated). The Minor-3 TypeError is caught by its `except Exception`, so a write is not broken by it.
- Mixed UTC offsets and the no-sequence-column workaround: ts-then-event_id order is right for aware datetimes of any offset inside a batch; see Minor 2 for the batch edge.
