## Questions asked, answered
1. Does the local Decimal context protect every money sum? **No, only the three sites changed.** See M1.
2. Is 60 digits enough? **Yes.** Price <= 10**6 with <= 6 decimals is 13 significant digits. Run: max_tokens=2**80, both prices 999999.999999, requests=2**10 -> exact 1237940039284142334864068987.725096645632 (40 digits incl. the 12 ceiling places); `reply` with 2**80 in and out tokens -> exact. The sum adds one digit, `/ 1_000_000` only moves the exponent, `quantize` needs integer digits + 12 <= 60, i.e. 48 integer digits: about 1e48 USD. The store refuses anything >= 1e9 anyway (store/protocol.py:112-125). If the amount ever overflows 60 digits, `quantize` raises InvalidOperation; `worst_case_for` (llm/common.py:160) turns that into SpendRefused("bad_amount"): fails closed. Config has no ceiling on `max_tokens` (config.py `Field(gt=0)`), so that path is reachable only by a silly config, and it refuses the call, not the config. Fine.
3. Does an Inexact/Rounded trap or signal state leak? **No.** A fresh `Context(prec=60)` has its own flags and traps; `localcontext` restores the caller's context on exit. Run with the caller's Inexact and Rounded traps on: worst_case_usd, Route price check and reply all returned normally, and the caller's flags stayed all False afterwards. Inexact cannot fire inside anyway: the products are exact in 60 digits (the `ROUND_CEILING` quantize is the one deliberate rounding).
4. Does the stricter ASCII rule still accept every shipped price format? **Yes.** The only price literals shipped: tests/fixtures/config/config.yaml:6-7 ("3.00", "15.00"), demos/ask-your-data/askdata/fixtures.py:25 ("2", "10", built straight on Route, so `_money` runs and accepts), and the demo's own config.py:42-43 (Decimal fields, not `Money`). There is no examples/ folder and docs/ holds no price. CHANGELOG.md:90-102 documents "0.000001" and the ceiling; both load (test_h3_plain_ascii_prices_still_load).
5. H3 departure (exponent forms accepted): **not a hole.** Run: "1E+6", "1e3", "0.1e1", "+5", "5.", "1E-6" load as the same number; "-0" refused; "1E+999999999", "1E-999999999", a 400-digit integer and a 300-place decimal are refused with a ValidationError (the ceiling/6-place rules do bound them, `quantize` is last). "+0" and "0E+3" load as zero but hit the zero rule in `_price_refusals`. Nothing hides a digit: ASCII, no space, no underscore, printable. The one cosmetic residue is m3.
6. Repr-escaped route name vs pinned text: ordinary names give the identical `routes.<name>.<field>: a zero price is allowed only for the fake llm kind in demo` (tests pin only ZERO_TEXT, tests/test_price_constraint.py:24, and price_mutants.py:109 matches on the text after the prefix). Names with a quote or a backslash change spelling (`a\'b`, `a\\b`), which no test or doc pins. Non-printable and bidi characters are escaped by `repr`. Good. Same class not fixed elsewhere: m2.
7. Accepted risks H1/H4/H6: **none is a Blocker for pilot or prod**, with the caveats below.
   - H1 (stale `prices_as_of` accepted forever): the date is attestation only. Medium as a policy gap, but it is a stated limit in CHANGELOG.md:102 and has an owner (lead, step F). Acceptable for pilot. For prod I would want the date emitted at start-up or in the audit start record before the first client; recorded as a step F gate, not a C defect.
   - H4 (0.000001 USD per Mtok is practically zero): one operator typo or deliberate value defeats the very cap the zero rule protects. The zero rule was added for exactly this failure, so I would not call the floor "nice to have" for prod. Still not a code defect of C (no floor was in the invariants) and the ticket points to step F. Acceptable for pilot; **please make the floor (or an explicit lead decision to live without it) a listed prod entry condition**, not only a pointer.
   - H6 (paths that skip validation: `model_construct`, `model_copy`, the demo loader): runtime sites trust the price. The assertion at `worst_case_for` is cheap and correct; it is a step F item. Acceptable for pilot, because every production path goes through `load_config`. Prod should not ship without that line or a test that no production code constructs a Route another way.

## Findings

### M1 (Medium) The local-context fix covers three sites, not "every money sum"
`defaults.py:174` and the disposition text say the context is set so "a host's own Decimal context cannot round money". Still computed under the CALLER's context:
- `k1b/loop.py:106-108` `worst_case_usd`: the very same `tokens * price + max_tokens * price / 1_000_000` (the ticket's P8 itself names it as "a third place that multiplies by the route prices"). Repro r3b.py: price 123456.123456 / 999999.999999, caller prec 4 -> 4094 instead of 4094.358017353923. It under-charges the K1b replay budget on a timeout (budget.charge at k1b/loop.py:156), the opposite of the safe direction. Under the default precision 28 it is exact for any realistic input.
- `store/memory.py:209-217, 219-229, 299-306` (`add_spend`, `spend_totals`, `_month_total`) and the reservation arithmetic at memory.py:331-336 (`booked + usd <= day_cap`), `limits.py:69` (`sum`), `limits.py:115` and `204` (`actual - reserved`), `evals.py:57` and `k1b/report.py:112` (running cost sums). Repro r3b.py: caller prec 4, `MemoryStore.add_spend("a", day, 1234.123456789012)` then `+ 1.000000000001` returns (1235, 1235): rounded, not 1235.123456789013. The Postgres store sums in SQL and is not affected.
Likelihood is low (a host must lower the global precision; the memory store is a demo/test store; default 28 digits holds the largest amount the store accepts, 9 + 12 places = 21 digits), so Medium, not High. It matters because the round-3 text claims the property wholesale and the tests (test_price_constraint_round3.py:55-110) cover only llm/common.py and llm/fake.py. Fix: either wrap k1b/loop.py:106 (and the memory-store/limits sums) in the same `Context(prec=defaults.MONEY_DECIMAL_PRECISION)`, ideally through one shared helper (the helper `_money_context` exists privately in llm/common.py:69 and the same context is hand-built again in config.py:103 and llm/fake.py:51), or reword the claim to "the price multiplication in llm/ and the price check". Not a pilot/prod stopper.

### m1 (Minor) The context is built from `Context(prec=...)`, which still inherits traps, rounding and Emin/Emax from `decimal.DefaultContext`
config.py:103, llm/common.py:71, llm/fake.py:51. `Context(prec=60)` copies traps, rounding, Emax and Emin from DefaultContext at construction, so a host that edited `decimal.DefaultContext` (new threads, e.g. a worker pool, start from it) can still change rounding mode or add a trap. I could not make it leak in the main thread (the thread's context already exists), so this is theoretical. Pin them: `Context(prec=60, rounding=ROUND_HALF_EVEN, traps=[InvalidOperation, DivisionByZero, Overflow], Emin=-999999, Emax=999999)`. Cheap, and it makes the "not the caller's" comment true.

### m2 (Minor) Route names still echoed unescaped in one more refusal
registry.py:364: `f"agent {a.id}: unknown model_route {a.model_route}"` is the same newline-forging class as H5 (an operator-written name in an error line). Not a price value, so no secret rule is broken; use `!r`. Outside the files named for this round, so only listed.

### m3 (Minor, cosmetic) Exponent-form prices keep their text form downstream
"1E+6", "1E+3" and "0E+3" are stored as given (`Decimal('1E+6')`). `str()` of such a value in a log, audit line or JSON gives "1E+6", and equality/ordering are unaffected. Nothing in C breaks. If a later step prints prices (report, audit start record for H1), format with `format(v, "f")` (k1b/report.py:33 already does). No change needed for C.
