## Major

M1. False claim: "a runtime migrated without --checkpoint-role still writes checkpoints".
- src/hadavin_sdk/store/migrate.py GRANTS `audit_checkpoints` (runtime = "SELECT", unconditional); cli.py `_migrate` (new warning "the runtime login still writes the audit checkpoints"); SECURITY.md:35 ("keeps the runtime login as the checkpoint writer").
- Scenario: `migrate --runtime-role R` with no `--checkpoint-role` (dev, demo, any non-live postgres+chain+signer without `checkpoint_dsn_secret_name`). The grant flip is unconditional, so R has no INSERT on audit_checkpoints. The inline checkpoint (chain.py:330, `_checkpoint_db is None`) and the tick step both hit 42501, which `checkpoint()` swallows into one `_LOG.error("audit checkpoint not signed (InsufficientPrivilege)")` per call. Nothing is ever signed; the only trace is a repeating log line. The CLI warning and SECURITY.md tell the operator the opposite.
- Fix: correct the warning text and SECURITY.md to "without --checkpoint-role NO checkpoint is written at all (runtime has SELECT only)". Add a loud startup warning at app.py build when `kind==postgres and audit==chain and signer!=none and not ck_name` and not live (live already refuses): "audit checkpoints will not be written: set checkpoint_dsn_secret_name". Alternatively, make the checkpoint grant for the runtime conditional on no checkpoint role being named (not recommended: the grant would differ per run).

M2. Quarantine no longer converges when the same event is parked twice.
- 0012_audit_outbox_functions.sql, quarantine `NOT EXISTS (... x.event_id = p_prefix || p_event_id)` and chain.py `_quarantine` (returns 0).
- Scenario: event X is quarantined (row `q:X` stays). The same event_id is parked again (outbox insert is `ON CONFLICT (event_id) DO NOTHING`, and X is no longer present, so a retried/replayed write_outcome re-inserts X). Its drain fails the same way after AUDIT_QUARANTINE_AFTER_S; the rename is refused, returns 0, `marked` stays 0, row X stays in the read set and fails every tick (not_writable) forever. The old INSERT ... DO NOTHING + DELETE converged. The test (test_audit_rights_roles_pg.py:252-256) pins the refusal but not the consequence.
- Fix: on a collision rename to a unique name (e.g. `p_prefix || <n>:` || id, or `p_prefix || p_event_id || ':' || md5(body)`), keeping the no-replace rule; or, when `q:X` exists with an identical body, let the function delete X (nothing is lost).

## Minor

m1. Connections left open on refusal: app.py:310-326. `_refuse_shared_login` raises ConfigError after `store`, `purge_store` and `checkpoint_store` are all connected, and none is closed (same for any later failure in `make("audit")`, e.g. "checkpoint login needs the postgres store", chain.py `build`). Process normally exits on ConfigError, but tests and embedders leak sockets and a logged-in checkpoint role. Fix: wrap in try/except that closes `checkpoint_store` (and the others) before re-raising. Do the login comparison cheaply without keeping it open, or close on every refusal path.

m2. `_refuse_shared_login` compares only against the runtime and purge logins (opened); release/reset/caps are only compared by secret NAME (app.py:236-257). Two names holding one DSN for the checkpoint and the release/reset/caps login pass. The consequence is small (the shared login would then hold the union of grants, which `migrate` refuses at role-distinctness time anyway) but the error message at app.py:~52 implies full coverage. Fix: say "runtime or purge" in the docs, or accept.

m3. Ordering of the new refusals: path-shape and collision checks for `checkpoint_dsn_secret_name` (app.py:235-258) run after `platform_secrets.check_senders` (app.py:~219), which already reads sender secrets. `ck_name` is not in check_senders' forbidden set the way release/reset/caps refs are (it is covered only indirectly through `b.entries()` secret_names). No secret of the checkpoint login is read before the refusal, which is what matters, and the required-in-live refusal (app.py:~170) is first. Fix if tidy: add `{ck_name} - {None}` next to the reset/release/caps refs in the check_senders set and move the ck block above it.

m4. Residual, not a defect, but add to SECURITY.md (the "HONEST RESIDUAL" in 0012 covers part of it): the runtime holds INSERT on audit_entries, so it can plant a row with event_id E and then call `hadavin_audit_outbox_done(E)`, deleting the real parked event E. What that gives an attacker: the DB seq guard (0009) only forces seq = last+1; it does not check prev/hash. (a) A planted row with a wrong prev/hash makes `audit verify` fail permanently and loudly (append-only, cannot be removed): the loss is detected but not undone. (b) A planted row with a correctly computed hash (the hash is unkeyed, the runtime can compute it) verifies; the real event's content is replaced by attacker-chosen content under its event_id, and the next checkpoint signs over it. Net: the wall stops accidental or code-path loss and an SQL-injection DELETE, but a runtime that can write arbitrary audit rows could always lie in the chain; this adds no new authority. Same for quarantine: renaming hides an undrained event from the drain but loses nothing (the row remains and is counted by `quarantined_earlier`). The SECURITY.md text (lines 22-39) says "cannot delete a parked event that is not in the chain" which is true but should say "unless it first appends an entry with that event_id".

## Checked and clean

- 0012: `done` deletes only when an audit_entries row with that event_id exists; NULL/empty refused (22023). `quarantine` refuses NULL/empty id and prefix, skips a row already under the prefix, refuses a rename onto an existing row (see M2 for the side effect). Both SECURITY DEFINER, VOLATILE, no dynamic SQL, `SET search_path = pg_catalog, pg_temp` placeholder, REVOKE ALL FROM PUBLIC.
- migrate.py: both functions in AUDIT_FUNCTIONS, FUNCTION_GRANTS (runtime only; every other named role, checkpoint included, gets REVOKE ALL and is verified by `_apply_money_functions`), re-pinned on every run via `_pin_money_functions` (pg_catalog, schema, pg_temp), unnamed-executor and PUBLIC checks cover them through FUNCTION_GRANTS, unmapped-function guard satisfied. `_OWNED_RELATIONS` adds audit_entries and audit_outbox: refusal when function owner differs from a table owner, and a named role that is, or is a member of, the function owner. A superuser owner short-circuits, as for the money tables (documented exception).
- Grants flip as designed: runtime SELECT on audit_checkpoints, SELECT+INSERT (no DELETE, no UPDATE) on audit_outbox; checkpoint role SELECT on audit_entries, SELECT+INSERT on audit_checkpoints; `effective_problems` check for the checkpoint role added; role distinctness and no-membership messages updated.
- Schema-qualified calls: `_TABLE_NAME` regex now qualifies the two function names (word-boundary, so `audit_outbox` inside `hadavin_audit_outbox_done` is not double-rewritten).
- chain.py: inline checkpoint skipped when `_checkpoint_db` is set; `checkpoint()` reads head, max checkpoint seq and inserts all on the checkpoint connection; `_outbox_done` and `_quarantine` go through the functions only when `self._db.pg`; SQLite keeps the old SQL. No other `DELETE FROM audit_outbox` remains in src (grep). Runtime cannot delete an outbox row any other way.
- app.py refusals: required in live postgres+chain+signer (before any secret is read); path-shaped name; same-name collision with dsn/purge/release/reset/caps; same current_user as runtime or purge. Checkpoint store is built from `model_copy` with purge and checkpoint names cleared, and cli.py's release/reset/caps logins clear `checkpoint_dsn_secret_name` and add it to their sibling-name lists.
- Migration numbering: 0012 added to UNRELEASED_MIGRATIONS; MIGRATIONS.md row, next free 0013, core-a range note, checksum doc and test comments updated.
- Deploy order (docs/stop-state-runbook.md:314-321 says migrate first, then runtime): if the new runtime runs before migrate 0012, `SELECT hadavin_audit_outbox_done(...)` fails (function does not exist, 42883, via the same `except` in `_drain_item`), so every drained row is counted `not_deleted`; `reconcile` raises `RuntimeError("audit outbox: N rows not deleted")` every tick and the `audit_drain` step fails each tick; rows are retained and dedup-deleted after the migrate. If migrate runs but the runtime is the OLD code, its `DELETE` on the outbox fails with 42501 with the same symptom. Intent/outcome writes are unaffected in both cases.
