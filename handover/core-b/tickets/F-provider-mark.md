# Provider-error mark "refused before any response" (post-hoc ticket, written 2026-11-20 06:58 UTC so a fresh reviewer can audit what was built; lead ORDER 013 and ORDER 014 duty a)
Built in commits "code F: providers mark an error that was refused before any response ..." (efaf486 and the first one), tests in tests/test_refused_before_response.py. Files: src/hadavin_sdk/llm/protocol.py (ProviderError.refused_before_response: bool = False), llm/retry.py (with_retry, never_sent, REFUSED_STATUSES = {400, 401, 403, 404, 413, 422}, THROTTLED_STATUS = 429, http_status hook), llm/openai_compat.py and llm/bedrock.py (hooks), llm/common.py.
Purpose in plain words: the model gate settles a reserved cost at 0 only when the provider certainly refused before doing any work; for every other failed call the worst case stays booked. The mark says "certainly refused".
Rule as built: (1) a final error that is not retried (ProviderError) is marked True iff every earlier attempt was "never sent" (connection refused or name lookup failed, no timeout, no HTTP status) AND the final error is never-sent or has a status in REFUSED_STATUSES; (2) when retries ran out (ProviderExhausted) it is marked True iff EVERY attempt was never sent or ended in HTTP 429. Everything else False: 408, 409, 5xx, timeouts, resets, replies that arrived and failed to parse. The openai_compat adapter clears the mark on its second request (the first was answered and billed).
Stated limit: the status list follows the HTTP meaning of the codes; whether a given provider bills a 400, 401, 403 or 429 is not verified (UNVERIFIED for anthropic, bedrock, openai_compat, gemini); a provider that bills one is under-counted by that call. SDK error chains (anthropic/httpx, botocore) were not tested against real errors; detection of "never sent" depends on the OSError being within 8 links of the cause chain and falls back to False.
INVARIANTS: (1) the mark is set only in with_retry; (2) default False on every error; (3) a mark never survives onto a different exception object; (4) no change to which errors are retried, the delays or the messages; (5) any earlier attempt that was answered, timed out or reset keeps the mark False.
Open: core-c's gate ignores the mark on ProviderExhausted by type (requests/to-core-c-1-exhausted-mark.md, to-core-c-2.md).

## RESOLUTION of the result review (2026-11-20 06:59 UTC; report tickets/F-provider-mark-review-1.md)
M1. Rule (2) (the mark on ProviderExhausted) is INERT until core-c changes its gate: the gate ignores the mark on ProviderExhausted by type. The retry.py docstring says so (fix round 1).
M2. For the openai_compat kind only HTTP 401, 403 and 404 count as refused before any response: a router or proxy behind its base_url can answer 400, 413 or 422 after the upstream model consumed tokens. The other kinds keep {400, 401, 403, 404, 413, 422}. The status list of a kind comes from the kind's own hook.
N3. A cause chain longer than the walk limit (8) counts as NOT never-sent.
N5 (corrected 07:30 UTC after the test writer's finding). `except ProviderError: raise` in with_retry is KEPT: a ProviderError that an adapter's own call raises passes through unchanged and unmarked (the safe direction); no built adapter raises one. Parse failures (KeyError, ValueError, JSON errors) are wrapped by with_retry into a new ProviderError and get the rule.
N6. protocol.py docstring: "no response seen and no work known", not "nothing was billed".
N7. New tests: 429 then 400 stays unmarked; a kind that does not retry a 429; a TLS error stays unmarked; one gate-level case once core-c's gate honours the mark.
Code for M1, M2, N3, N5, N6, N7 is "provider mark fix round 1": QUEUED until the merge of cloud/core-b into the F-install integration tree is finished (llm/retry.py is being merged).
