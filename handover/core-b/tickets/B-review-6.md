## Major

### R6-1 Docs: the breaking changes of this round are in no CHANGELOG upgrade step, and two texts now say the opposite of the code
- CHANGELOG.md:24-25 (still says: "a plain `migrate` with no role leaves old grants in place"). Code now refuses it: migrate.py:581-586, cli.py:430-435 (exit 2).
- SECURITY.md:37 (still says: "A plain `migrate` that names no role applies and checks no grants and leaves old ones in place").
- `grep -n "no-roles\|search_path\|db_schema\|MAINTAIN" CHANGELOG.md SECURITY.md README.md` returns nothing. So CHANGELOG has no entry for: (a) the process now refuses to start when the login's effective search_path is not exactly the configured schema (postgres.py:197-231, called from build() at :258, for the runtime, purge, reset and release logins alike, since all go through build()); (b) the new setting `backends.store.db_schema`; (c) `migrate` with no role now exits 2 and `--no-roles` exists (every script or runbook of an operator that ran plain `migrate` after upgrade now fails); (d) migrate resets role-level search_path defaults and revokes MAINTAIN on PG17+.
- Who is hit by (a): the stock unpinned login on `"$user", public` with tables in `public` is NOT broken (current_schemas(false) = [public] = expected, I checked the logic and the test at test_step_b_e5_search_path.py:107-120). Broken at upgrade, with the refusal at start: a login for which a schema named like the login exists (then effective = [login, public]); a database or role default search_path other than `public` (including `ALTER DATABASE x SET search_path = app`, which the old runbook line 77 told operators to use: "Set the same search_path for the migrate and the runtime login"); and `app, public` kept as a role default (db_schema is a single name, so it cannot express this: the operator must pin the DSN or reset the default). Nothing in the repo (demos/, docs/slack-app.md, README, .github) uses the SDK postgres store with such a DSN; demos/ask-your-data uses its own read-only role and `ALTER ROLE ... SET search_path = analytics` (db/roles.sql:66) for a DB that is not the SDK store. CI runs no `hadavin-sdk migrate` (grep of .github/workflows: none). So no demo or CI is broken; operators are.
- Fix: add an Upgrade steps bullet (order: stop processes, run `migrate` with all roles, check `SHOW search_path` of each login or pin `options=-c search_path=<schema>` and set `db_schema`, then deploy), fix CHANGELOG:25 and SECURITY.md:37.

### R6-2 check_role_settings can erase a role-wide search_path that other databases and applications use, silently
- migrate.py:407 selects `s.setdatabase = 0` rows for the named roles (the role-wide default, valid in every database of the cluster), and migrate.py:429-432 builds `ALTER ROLE r RESET search_path` for it with no `IN DATABASE`. The E4 lesson (roles are cluster-wide) applies: if the runtime/purge/reset role is also used by another application or database on the same server and carries `search_path = other_app` role-wide, a plain migrate of this schema wipes that role's setting for all of them. Only the NAMED roles are touched, and rows `IN DATABASE <other>` are not (filter `d.datname = current_database()`), which is correct; the problem is the role-wide row.
- Silent: the return value of `check_role_settings` (what was reset) is discarded at migrate.py:654; neither the CLI nor the audit shows the old value, so it cannot be restored.
- Smallest fix: for a role-wide row, do not RESET; write `ALTER ROLE r IN DATABASE <current_database()> SET search_path = <schema>` (higher precedence than the role-wide row, touches this database only), or refuse and name the row. And print what was changed (role, old value) on stderr.
- Not a finding: `ALTER ROLE ... RESET` cannot reach a role that is not named; the setrole = 0 (database-wide or server-wide) case is refused, not changed.

## Minor

### R6-3 ALTER ROLE needs CREATEROLE with ADMIN on the target (PG16+): the failure is a bare "failed: InsufficientPrivilege", exit 3
Experiment on this PG16 server: a login with CREATEDB only running `ALTER ROLE zz_rt RESET search_path` gets `permission denied to alter role ... Only roles with the CREATEROLE attribute and the ADMIN option on role "zz_rt" may alter this role`. In migrate that psycopg error is not caught (migrate.py:432), the whole migrate transaction rolls back, and cli.py:98-103 prints only `failed: InsufficientPrivilege`. The runbook says "migrate resets it" as if always possible. Catch `errors.InsufficientPrivilege` around the ALTER ROLE and raise a ConfigError that names the role, the setting and "run `ALTER ROLE <r> RESET search_path` as a role that may". (Safe failure, nothing half-applied.)

### R6-4 db_schema alone does not select a schema, but the refusal text says it does
postgres.py:213-215: "Pin it in the DSN (...), set backends.store.db_schema, and run hadavin-sdk migrate". `db_schema` is only the expectation: with an unpinned DSN and no role default it still refuses (test at test_step_b_e5_search_path.py:114). An operator reading the text sets only db_schema and loops. Say "db_schema must equal the pin or the role default; it does not choose the schema". Also `_PIN` (postgres.py:173) takes `\S+`, so a pin written `-c search_path=app, public` (space after the comma) parses as `app,`; use the quoted/escaped form in docs or parse to the next `-c`. And the `%s::regclass` string in migrate.py:481-483 is `schema.table` unquoted: a schema with capitals or special characters resolves wrongly or errors on PG17+ (use `format('%I.%I', ...)` or quote_ident).

### R6-5 PG17 real-server test does not prove the PUBLIC revoke
tests/test_step_b_e5_maintain.py:132-160 grants MAINTAIN on `kill_switch_stops` to PUBLIC but locks only `kill_switch` (whose runtime grant `_apply_grants`' `REVOKE ALL` already removes). Lock `kill_switch_stops` and `kill_switch_clears` too, and add a `pg_maintain` membership case expecting the migrate refusal. CI runs postgres:17.10 (.github/workflows/ci.yml:41,111), so the test will run there on the next push; it is not yet run.

### R6-6 Unchecked after `--no-roles`
`--no-roles` (cli.py:127, migrate.py:576-586) is refused together with any role (test_step_b_e5_no_roles.py:37-40; the CLI reaches the same ConfigError, exit 2). Good. But on an upgraded database `--no-roles` exits 0 with only the "new tables have no runtime grants" warning (cli.py:455) when something applied, and nothing when the schema is already current. The help text and runbook say it "grants and checks nothing"; acceptable, but say in the CLI message "do not use on an existing deployment". Not a code defect.

## Answers to the five questions
1. Unpinned stock login: refuses only when its effective path differs from the configured schema (see R6-1 for who). Error text names the effective path, current_schema() and the configured schema and says what to do (R6-4 caveat). Upgrade documentation is NOT enough (R6-1).
2. See R6-2: only named roles are touched, never an unnamed role or other-database rows; the role-wide RESET is the cluster-wide hazard; silent.
3. check_maintain: gate `current_setting('server_version_num')::int < 170000` is correct for 17.x (17000x), 18 (180000) and the numeric form. I read the SQL carefully and found no syntax or catalog error: `FROM pg_class c JOIN pg_namespace n ON ..., aclexplode(c.relacl) a` (function in a later FROM item sees `c`), grantee 0 is PUBLIC, `privilege_type = 'MAINTAIN'` exists from 17, `has_table_privilege(text, regclass, text)` resolves through (name, oid, text), the REVOKE composition with `sql.Identifier` and `PUBLIC` is valid, and `REVOKE ALL` in `_apply_grants` (migrate.py:195) already takes MAINTAIN from a named role on 17. A non-owner migrate login that cannot revoke gets the "REVOKE it as the owner" refusal. No PG17 server here, so UNRUN. A PG17 run must show: (a) `migrate` on a schema where PUBLIC and the runtime hold MAINTAIN on the three tables completes and `SELECT ... aclexplode` then lists none other than the owner; (b) a runtime login `LOCK TABLE kill_switch_stops IN ACCESS EXCLUSIVE MODE` fails with InsufficientPrivilege (R6-5); (c) `GRANT pg_maintain TO runtime` then migrate is refused with the message naming role and table; (d) `SHOW lock_timeout` on the store connection is the configured value; (e) the whole test file passes with 0 skips on 17.
4. `--no-roles`: grep of docs, CHANGELOG, runbook, scripts, CI, Makefile (none), .github, demos for plain `hadavin-sdk migrate`: runbook updated (lines 8-14, 114), tests updated (test_p7_tick.py:510, no_roles tests); stale text only in CHANGELOG:24-25 and SECURITY.md:37 (R6-1). Exit 2 and the text are actionable. no_roles with a role is refused at migrate.py:576 and tested.
5. Race verify_schema vs concurrent ALTER ROLE: a session's search_path is fixed at login; `verify_schema` reads the live session value, so a concurrent ALTER ROLE changes only the next connection, which verifies again. The store has no reconnect path (postgres.py:289 comment), so no unverified connection exists. A runtime that re-sets a decoy after migrate commits is refused at the next start. Nothing above Minor; the only residual (the running process itself issuing `SET search_path`) is outside the guarantee, as the runbook states.
