### M5 MAJOR: stale-high cap is the silent failure; decide `check-caps` loudness
- Today `Limits.blocked` (limits.py 154-164) reads the REGISTRY cap and `Limits.reserve` passes it; after step 6 the table wins on PG. Scenario: owner lowers `daily` 100 -> 10 in the registry, forgets `sync-caps`: `blocked()` and the dashboards say 10, the table lets the agent spend 100. A safety limit that stays at the old, higher value without any alarm is not acceptable.
- Decision (minimal diff): add a READ-ONLY definer function `hadavin_caps_drift(p_agents text[], p_day numeric[], p_month numeric[]) RETURNS TABLE(agent_id text, reason text)` (or `hadavin_cap_matches(text,numeric,numeric) RETURNS boolean`), STABLE, `REVOKE ALL FROM PUBLIC`, EXECUTE to the runtime. It gives the runtime no table right (T1 stays true: no SELECT on `hadavin_caps`), it only answers "same / differs / missing". A new tick step `check_caps` (append a `TickStep`, tick.py header says later PRs only append) logs an ERROR and writes an audit/alert event naming the agents. `limits check-caps` (reset login) stays for operators. This does not contradict "runtime has no rights": EXECUTE on a read-only comparator is not a table right and cannot change a cap. State that the comparator reveals cap values to a probing runtime (caps are not secrets; they are in the registry the runtime already reads). The ticket sentence at 204 ("the runtime cannot detect drift itself, it has no SELECT") is then reversed; adjust 204 and the trade-off (i) ("not removed" -> "loud, bounded by the tick period").
- Also the raised-registry case (table lower) is safe (refused `daily_budget`, closed); state both directions.
