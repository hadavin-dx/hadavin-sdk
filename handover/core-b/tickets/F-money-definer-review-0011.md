# F-money-definer: hostile review of 0011 (steps 1-2): SQL functions, migrate.py, tests

Reviewer: fresh, read-only on source (no edit, no commit). Server: PostgreSQL 16.15 at 127.0.0.1:55439. Scratch scripts: `/tmp/core-b-scratch-DF/` (world.py, atk1-3.py, race.py, mig1-3.py, h1.py, tmpop.py, tmpop; every schema and role carried a unique `rvdf` prefix and was dropped; 0 left, checked). The hostile login was a LOGIN role with USAGE on the schema and EXECUTE on reserve, settle, expire and add_spend, and nothing else. The test-file run is noted at the end.

## Verdict
No Blocker against the function bodies themselves. Arguments, search-path/temp hijack, settle agent check, double settle, concurrency and the owner check all held. Three Majors are about what is promised versus what is true on this branch, and one logic path that makes the residual "(3) safe" false. Findings below, most serious first.

## Findings

### M1 (Major, promise/doc) The 0011 header says migrate already removed the runtime's write rights; it has not (step 4 is not in this branch)
- `0011_money_definer.sql:1-5` ("After this migration the ONLY writers of the three money tables are the SECURITY DEFINER functions", "`migrate` ... takes every write right ... from the runtime login") and `:8-9` (THE PROMISE).
- `migrate.py:78-80`: `spend_reservations`, `spend`, `spend_month` are still `Grant("table", _RW, ...)`.
- Scenario: a runtime login set up by the migrate of this branch lowers a booked amount with plain SQL. Repro (`/tmp/core-b-scratch-DF/h1.py`, real `--runtime-role` login, autocommit off): `hadavin_add_spend('A', day, 100)`; commit; in one transaction `hadavin_reserve_spend(... 5 ...)`, `hadavin_settle_spend(id, 0, 'A')`, then three times `UPDATE spend SET usd = usd - 5 WHERE agent_id='A' AND day=...`. All three succeed, the counter ends at 85 (a plain charge of 100 lowered). This is the H1 bypass of the 0010 header, still open until step 4.
- Fix: until step 4 merges, the header must say "will be", or the sentence must be scoped ("after step 4"). The 0010 header already says "until step 4 ... also lower a booked amount"; 0011 contradicts it. Not a code bug; a reader of 0011 alone is misled about the live wall.

### M2 (Major, logic) Residual (3) "expire at any age is a safe self-inflicted outage" is false when an operator runs `release-expired`
- `0011:15-17` (residual 3), `:215-243` (`hadavin_expire_spend_reservations`, no lower bound on age), with `0008` `hadavin_release_expired_spend(agent, day)` (no age check; takes every EXPIRED row of the agent and day to settled 0 and lowers both counters).
- Scenario: a hostile runtime calls `hadavin_expire_spend_reservations(0)` while its calls are in flight; every live hold becomes `expired`. An operator who runs `limits release-expired AGENT DAY` (its intended use for stale holds) cannot tell attacker-expired holds from stale ones. The release lowers the counters by the live holds and marks them settled at 0; the real late `settle` then returns `claimed = false`, so the actual cost is never booked and `runs.cost_usd` is never updated.
- Repro (`atk3.py`): reserve 10 as hostile, `expire(0)` returns 1, owner `release_expired_spend('R', day)` returns `(1, 10, 0, 0, 10)`, hostile `settle('r1', 10, 'R')` returns `claimed=false, settled_usd=0`, day counter 0. Net: a booked 10 vanished with one operator action.
- Severity: Major for the E14 sentence ("cannot lower a booked amount") only because a human step is needed; the header's "safe" is wrong. Fix options: a floor on `p_age_s` in the function (the contract suite and memory store accept 0, so the floor must come with a Python/contract change), or make release refuse rows younger than an age, or reword residual (3) to "an operator release after such an expiry loses the booking".

### M3 (Major, migrate check gap) Roles that `migrate` is not told about keep or get EXECUTE, and nothing looks
- `migrate.py:817-852` (`_apply_money_functions`) revokes and verifies only for the five NAMED roles. There is no analogue of `who_else_can_clear` for the money functions.
- Repro (`mig1.py` A, A2): an unnamed role `x` holding a direct `GRANT EXECUTE` on all five functions, and an unnamed role that is a member of the purge role: `migrate` passes; `has_function_privilege(x, purge)` and `(x, reserve)` are true. Same for `ALTER DEFAULT PRIVILEGES IN SCHEMA s GRANT EXECUTE ON FUNCTIONS TO x` (every future overload or function arrives with EXECUTE for `x`).
- Consequence: `settle(id, v, NULL)` lowers any hold (residual 2) for such a role; `purge` deletes settled evidence rows. Contrast the stop state, where "roles other than the reset role" are listed and refused.
- Fix: after the loop, list every role (other than owner, superuser, and the mapped role) with EXECUTE on each money function via `aclexplode(proacl)` plus memberships, and refuse or at least note it.

### m4 (Minor) Overloads: unpinned, PUBLIC-executable function accepted by both maps
- `migrate.py:229` (`_FUNCTION` names only), `:789-801` (`_unmapped_functions` by name), `:731-736` (pin by exact signature).
- Repro (`mig1.py` E): owner creates `hadavin_add_spend(text)` (no SET, no REVOKE): `migrate` passes, `proconfig` NULL, `proacl` contains `=X/postgres` (PUBLIC). A later SECURITY DEFINER overload by a developer would be an unpinned, PUBLIC-executable definer function and the static and runtime checks both say "mapped". Fix: compare full signatures (`oid::regprocedure`) against `FUNCTION_GRANTS` and `EXCLUDED_FUNCTIONS`, in both `check_grants` and `_unmapped_functions`.

### m5 (Minor) `check_grants` comment stripping hides a function when `--` sits in a literal
- `migrate.py:211` and `:237`: `re.sub(r"--[^\n]*", "", text)` also eats the rest of a line after a `--` inside a string or dollar quote. Repro: `CREATE OR REPLACE FUNCTION hadavin_ok() ... $$select '--'; $$; CREATE OR REPLACE FUNCTION hadavin_hidden() ...` on one line: `_functions_created` returns only `hadavin_ok`. Quoted (`"hadavin_x"`) and schema-qualified (`public.hadavin_x`) CREATE FUNCTION are not matched by `_FUNCTION` (the regex needs a bare `hadavin_\w+`). Mitigation that exists: `_unmapped_functions` catches the unqualified/quoted ones in the live schema at migrate time, so this is a CI-time false negative, not a runtime hole. A name that is qualified into ANOTHER schema is not checked at all. 0011 itself has no `--` in a literal (grep).

### m6 (Minor) The function bodies depend on the caller's `standard_conforming_strings`
- `0011:82,166,290` (`'[\x01-\x1f\x7f-\x9f]'`) and the other regex literals are parsed at first call in the caller's session. Repro (`atk2.py`): `SET standard_conforming_strings = off` then any reserve with any argument fails `22021 invalid byte sequence ... 0x9f`. Fails closed (no bypass found), but every call in that session errors and the cause is obscure; a pooled connection that ever sets it is wedged. Fix: pin `SET standard_conforming_strings = on` on the function, or write the class with `E''`/`chr()`-free POSIX `[[:cntrl:]]`. Other tested GUCs (TimeZone including Pacific/Kiritimati and Etc/GMT+12, default_transaction_isolation, plpgsql.variable_conflict, plpgsql.extra_errors, transform_null_equals, escape_string_warning, backslash_quote) changed nothing; all pg_timezone_names zones x 9 dates give the same month bucket as the timestamp form.

### m7 (Minor) Out-of-range day is `22008`, not `22023`
- `0011:105` and `:299` (`date_trunc('month', p_day)` on a date past year 294276 raises `date out of range for timestamp`). Header says a bad argument is 22023 naming the parameter. `reserve(..., '5874897-12-31', ...)` and `'294277-01-01'` give 22008. Fail closed. Fix: bound `p_day` (e.g. 1970..9999) inside the function and raise 22023 `p_day`.

### m8 (Minor) `settle` with a NULL agent is a read oracle on `spend_reservations`
- `0011:173` and the early return at `:174-181`. Without SELECT on the table (after step 4) a runtime that knows an id gets the full stored row (agent, day, run_id, amounts, status, created_at, closed_at) for ANY agent via `settle(id, 0, NULL)` on a settled row (`atk2.py`: "settle B's settled row as NULL"). Also `reserve` with another agent's id returns `23505` (existence oracle). Both need a known id; documented residual (2) covers the lowering, not the read. If the Python store never passes NULL (step 3 not yet in the tree), make `p_agent` required (NOT NULL, HD004/22023) and keep "any agent" only for an owner-only variant.

### m9 (Minor) `runs.cost_usd` is raised for a run of any agent
- `0011:205` (`UPDATE runs u SET cost_usd = u.cost_usd + p_actual WHERE u.run_id = rec.run_id`). `p_run_id` is never checked against `runs.agent_id` (builder A report item 5 admits no check). A hostile runtime reserves with a victim's run id and settles with 999999999: the victim run's cost is inflated. Add `AND u.agent_id = rec.agent_id`. (Today the runtime also holds UPDATE on `runs`, so this only matters after the grants flip.)

### m10 (Minor) Settle has no floor on the counters; `_seed_limits` leaves extra rows
- `0011:196-202`: `s.usd + v_delta` with no `GREATEST(..., 0)` and no CHECK on `spend.usd` (0001:90). After an operator repair or release leaves a counter below its open holds (the drift 0008 reports as `applied_usd`), settling an open hold below its reserve drives the counter negative, which gives the agent MORE headroom than truth. Release floors at 0; settle should refuse (HD003-like) or floor.
- `migrate.py:804-814`: `_seed_limits` upserts the five names; it does not delete extra rows (repro `mig1.py` F: a planted `bogus` row survives; a changed `max_decimals` is put back). Harmless today because the functions read three fixed names; `max_exponent` is seeded but read by nothing (builder A deviation 2), so a tampered `max_exponent` is neither read nor shown.

## What I attacked that held (so it is not re-checked)
- Arguments (atk1.py, ~120 probes, hostile login): NULL for every parameter of all five functions, empty, 201 and 100000-character ids, `%s %I %L %1$s`, `$$`, quotes, control characters (0x01, 0x7f, 0x85, 0x9f), NaN, +-Infinity, `1e999` (usd refused; caps accepted, by design), `-0`, negative, scale 12 accepted / 13 refused, `1e-999`, 1000-digit numerics, +-infinity dates, expire -1 / 10^7+1 / 2^31-1 / NULL, bigint and numeric argument types (no such function). Every bad value gives 22023 naming the parameter, never the value; no table changed. A NUL cannot reach the server (client and server both refuse). No `format()`, `EXECUTE` or dynamic SQL exists in any body.
- Search-path and temp hijack (tmpop.py): temp table `hadavin_limits` with hostile limits, temp operators `>=(numeric,integer)` and `>(integer,numeric)` created in `pg_temp`, caller `search_path = pg_temp, <schema>`: negative amount and a 2e9 expire age are still refused. Operator audit of the bodies: no unqualified function call (`char_length, isfinite, scale, date_trunc, clock_timestamp, make_interval` are all `pg_catalog.`; `GREATEST` and `COALESCE`-style are syntax). Unqualified OPERATORS exist (`>=`, `<`, `<=`, `+`, `-`, `<>`, `=`, `!~`, `~`): with `pg_catalog, <schema>, pg_temp` a same-signature operator in the schema loses to pg_catalog, but a MIXED-type one (`>=(numeric, integer)` for `p_usd >= 0`, `>(integer, numeric)` for `p_age_s > v_max_age`) in `<schema>` would win and let `p_usd = -1000` through, which lowers counters. That needs CREATE on the schema; `migrate` refuses it for a named role (`effective_problems`, repro `mig1.py` D: "can CREATE in schema") and `pg_temp` operators are never found by path. Defence in depth if wanted: cast literals (`0::numeric`) or `OPERATOR(pg_catalog.>=)`.
- Placeholder window: `CREATE FUNCTION` and `_pin_money_functions` run in the one `migrate` transaction (advisory-locked, `db.transaction()`), the function is invisible to other sessions until commit and `REVOKE ... FROM PUBLIC` is in the same file, so no session sees the placeholder `pg_catalog, pg_temp` pin. Under that placeholder the unqualified `hadavin_limits` would resolve to a caller's TEMP table (only `pg_catalog, pg_temp` is searched), so the window would matter for a hand-run `CREATE OR REPLACE` or restore outside `migrate`; documented break-glass says the next migrate re-pins, which leaves the gap until then. Pins found after migrate: `pg_catalog, <schema>, pg_temp` on all five.
- (a) cap: a huge cap is accepted (known residual; `reserve(…,cap 10^12)` booked 5 under a day cap of 1 that was refused with cap 1). (b) another agent's hold with an agent given: HD002, same text as unknown id; with NULL it settles (residual 2). (c) reserve R, settle 0, settle 0 again, settle higher: second and later calls return `claimed=false`, counters unchanged (0 -> 0). (e) purge as the hostile login: 42501; (f) release as the hostile login: 42501. (g) another agent's expired id: 23505, nothing changed.
- (h) race (race.py): 8 threads x 250 random reserve/settle/expire/add_spend plus a purge login, 2 agents x 3 days (two months) under tight caps. Errors: only HD001 (413) and HD002 (185, purged id); no 40P01 deadlock, no lock timeout; each counter equals the sum of rows (open reserved, else settled) plus purged rows plus add_spend totals, for all six agent-days, and each month row equals the sum of its day rows. 0 drift. Lock order row, day, month is consistent across reserve, settle, release; expire takes row locks only.
- (4) migrate.py: a role with PUBLIC EXECUTE on purge -> refused ("can run ... only purge may"); a named role with a hand grant is revoked; schema names needing quotes (`Rv"DF,s abc`) -> pin `pg_catalog, "Rv""DF,s abc", pg_temp` and the functions work; non-superuser owner with a schema owned by it: migrate, EXECUTE grants, reserve/settle as the runtime all work through the 0010 guard; a different login that is not a member fails with `InsufficientPrivilege` (raw, not a ConfigError) before the money steps; a member of the owner is allowed; a table or a function with another owner is refused by name; the runtime login has no right on `hadavin_limits` (42501) and tampered rows are put back at the next run.
