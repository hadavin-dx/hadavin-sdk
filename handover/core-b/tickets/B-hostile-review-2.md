## Verdict
Goal asked: can a stop be lost or reversed without a deliberate reset by the reset login? Through the runtime role's rights, on PostgreSQL 16 with a clean `migrate`: NO route found (every statement in the battery below was refused, or only reached its own session). Three ways a stop is lost or made irreversible were found outside that route: (1) the reset itself silently erases a stop the operator never saw (RUN, Major); (2) a runtime login whose rights drifted after migrate can clear stops and nothing notices (RUN, Major); (3) one audit row from the runtime login makes every reset impossible for ever (RUN, Medium; the stop stays, the direction is safe but there is no way back short of owner DDL). Also: any runtime INSERT flood makes every gate read slow for ever (RUN, Medium), and the runtime can set role-level defaults on itself that make its own stop fail or be lost on a crash (RUN, Low to Medium).

## 1. Major: the reset erases a stop it never showed (RUN)
Code: `Limits.reset` writes the audit intent (limits.py:242), then `set_kill_switch(on=False)` runs `UPDATE kill_switch ...` and then `INSERT INTO kill_switch_clears ... SELECT s.id ... FROM kill_switch_stops s WHERE NOT EXISTS (...)` (postgres.py:632-642): it clears EVERY open stop visible to that statement, not the stops the operator looked at. The CLI then reads back and prints `kill switch OFF`, exit 0 (cli.py:687-700). It lists nothing it cleared, and neither the audit row nor the clear rows say which stops were meant.
Scenario: Alice stopped at 09:00. Carol runs `limits reset`. While Carol's audit intent is being written (chain advisory lock, network, anything, the window is the whole audit write), Bob sets an emergency stop. Carol's clear statement sees it and clears it. Carol sees "kill switch OFF", exit 0. Bob's stop is gone; no message to anyone. The runbook and SECURITY (limit 4) state the window, but the command's output claims success and nothing tells Carol.
Repro (RUN, /tmp/core-b-scratch-B6/a7.py): a hook inserts Bob's stop through the runtime store just before the INSERT of the clears; `cli.kill_switch(Limits(reset_store, audit, None), "reset", "op:carol")` printed `kill switch OFF (by op:carol)`, exit 0, `get_kill_switch().on == False`; the table showed both stops cleared by op:carol; the audit chain held one `reset` row and no `reset_failed`.
Smallest fix: compare-and-clear. `limits reset` first reads the open stops (ids, by, ts), prints them (and puts the ids and count in the audit intent), asks nothing more, then clears only `WHERE s.id = ANY(%s)`. A stop not in the list stays open, the read-back then says "still ON" and exits 2, which is the already-built message. Add the count cleared to the success line. Optionally add the audit intent's event id to `kill_switch_clears` so a clear can be matched to its audit row (today a person with the reset login can clear by hand with no link at all, S3).

## 2. Major: nothing checks the runtime login at start; drift after migrate reverses a stop (RUN)
`who_else_can_clear` and `effective_problems` run only inside `migrate` (migrate.py:745, 702). `build()` (postgres.py:250-283) checks the search path and the table names, never the rights of `current_user`. SECURITY limit 5 admits "a role or grant added later is not seen until the next run".
Scenario: after the clean migrate a DBA or a provisioning tool runs `GRANT ALL ON ALL TABLES IN SCHEMA app TO hadavin_runtime` (common), or the runtime role is added to `pg_write_all_data`, or a snapshot with old grants is restored. The runtime starts without complaint, and its own store object clears a stop with one INSERT.
Repro (RUN, a8.py): after migrate, `GRANT ALL ON ALL TABLES IN SCHEMA hr6b_s TO hr6b_rt`; `make("store", ...)` for that login built fine; `set_kill_switch(on=True)` then `set_kill_switch(on=False)` on that same store: `get_kill_switch().on` went True to False. (DELETE and TRUNCATE on the stop tables were still refused by the trigger; INSERT on `kill_switch_clears` is enough.)
Smallest fix: in `build()` run for `current_user` the same questions as `effective_problems` for the three stop tables only (`has_table_privilege` INSERT on clears; UPDATE, DELETE, TRUNCATE, TRIGGER on all three beyond the grant map; `pg_has_role` MEMBER of the owner or the reset role; `has_schema_privilege` CREATE) and refuse to start, naming the right. One query, no extra privilege needed (the role may ask about itself). Do it in the CLI `limits stop` path too (a bad login should say so before the operator relies on it). A role other than the runtime can still drift; that part stays "run migrate again", and the runbook should say to schedule it.

## 3. Medium: one audit row from the runtime login blocks every reset for ever (RUN)
The chain takes `seq = last.seq + 1` (audit/chain.py:284-285). The runtime holds INSERT on `audit_entries` (migrate.py:73) and the table is BIGINT. A row with `seq = 9223372036854775807` makes the next append overflow; every append raises. `Limits.reset` needs the intent row first (limits.py:242), so `limits reset` exits 3 ("refused: the audit store is unavailable ... Fix the audit store", cli.py:669-675) for ever. The append-only trigger means not even the owner can delete the row without DROP TRIGGER (outside the guarantee). Stops still work (outbox) and the direction is safe, but the stop is then irreversible by any supported means, and the message sends the operator to the wrong place.
Repro (RUN, a6.py): stop exit 0, state ON; `INSERT INTO audit_entries(seq,...) VALUES (9223372036854775807,...)` as the runtime login; `cli.kill_switch(reset...)` returned 3, state still ON; a second stop still worked (exit 0).
Smallest fix: give the reset its own audit-first record that the runtime cannot write: a `kill_switch_resets` table (reset role INSERT, SELECT; runtime SELECT; append-only trigger) written in the same transaction as the clears, holding the operator, the stop ids and the audit event id; the chain row stays as the copy for readers. That also closes S3 (clear by hand with no row) at the database, and the "reset login can append any audit row" cost in SECURITY. Cheaper partial fix: map an audit failure whose cause is not an outage to a different exit/message ("the audit chain is damaged: audit verify") and document the owner's remedy.

## 4. Medium: stop flood makes every gate read slow for ever (RUN)
`get_kill_switch` with the flag off runs `SELECT ... FROM stops s WHERE NOT EXISTS (SELECT 1 FROM clears ...) ORDER BY s.ts, s.id LIMIT 1` (postgres.py:596-606). When all stops are cleared the planner must anti-join the whole stops table; the tables are append-only for every role and nothing prunes them (ticket "What stays out").
Repro (RUN, a5.py): the runtime login inserted 1,000,000 stops in 6.8 s; a read with them open took 0.65 s; the reset took 18 s (no statement timeout); after the reset, each read took 0.44 to 0.66 s on a quiet 16.15 server. Every `Limits.reserve` and `blocked()` pays that (once per model call), for ever; 10 million rows would be about 5 s per call and a reset of minutes. Disk grows with no remedy except owner DDL.
Smallest fix: make the open-stop test O(1): the reset writes a watermark (one row in a `kill_switch_resets` table, see 3) holding the highest stop `ts`/sequence it cleared, and the read looks only at stops newer than the last watermark (needs an index on stops(ts)); or a cap on open stops enforced by a trigger on INSERT (the ticket considered and dropped "StoreBusy and a cap on open stops"; this is the reason to bring a bounded form back). Also set `statement_timeout` on the reset connection so a huge reset fails loudly.

## 5. Low to Medium: the runtime can set defaults on its own role that break its stop (RUN)
`ALTER ROLE <self> SET ...` is allowed for any user-settable parameter (RUN: `ALTER ROLE self IN DATABASE d SET search_path`, `default_transaction_read_only`, `synchronous_commit`, `statement_timeout`, `lock_timeout`, `row_security` all succeeded; `session_replication_role` was refused: permission denied to set parameter). migrate repairs only `search_path` (migrate.py:436-490). `connect()` (postgres.py:143-168) pins only time zone and isolation level.
Effects (RUN, a4.py, a10.py): after `ALTER ROLE hr6b_rt SET default_transaction_read_only = on`, a new store built from that login read fine, and `cli.kill_switch(..., "stop", ...)` printed `kill switch NOT set: the store answered with an error (ReadOnlySqlTransaction); run hadavin-sdk migrate and check the runtime role's grants. Nothing was changed.`, exit 2: the operator's stop does not persist and the message blames grants. With `synchronous_commit = off` the store session reported `off`: an acknowledged stop (exit 0) may be lost if the server crashes within the WAL writer delay (not exercised: no crash was made). `statement_timeout = 1` and the like fail everything closed. Fail-closed for reads and spend, so no reversal; but the one thing that must work in an emergency, the stop write, depends on the role's defaults.
Smallest fix: in `connect()` for the store and in the `limits stop` path set per session `default_transaction_read_only = off`, `synchronous_commit = on`, `statement_timeout` to a bound; have migrate `ALTER ROLE r IN DATABASE d RESET ALL` style repair (or at least print) any role default of a named role other than the expected ones; map ReadOnlySqlTransaction (hot standby after a failover) to a message that says "the database is read-only", not "check grants".

## 6. Low: planted `ts` and `by` (RUN)
0006 refuses non-finite `ts` only. The runtime may insert `ts = '0100-01-01 BC'` or `'20000-01-01'` (RUN, accepted). psycopg cannot load it: every `get_kill_switch` while that stop is open (or while the flag read orders it first) raises `DataError: timestamp too small (before year 1)` (RUN, postgres.py:604-607). Callers fail closed (`reserve` -> limits_unavailable, loop -> limits_unavailable), a reset clears it (the INSERT..SELECT does not parse `ts`), so no reversal; the wrong reason is shown. A planted older `ts` also decides which stop's `by` the CLI prints ("set by ..."), so the runtime can hide the operator's name behind its own text (it can write any `by` anyway). Fix: `CHECK (ts BETWEEN '2000-01-01' AND '9000-01-01')` on both tables, or ignore the column on insert with a trigger-free default (`ts` not insertable: no column INSERT grant on `ts` for the runtime, column grants `INSERT ("by")` only).

## 7. Low: unnamed schema owner (RUN)
SECURITY and the runbook say the schema owner is outside the guarantee. Run (a9.py): schema owned by an unnamed role, tables owned by the migrate login: migrate passed, and that role ran `DROP TABLE kill_switch_clears` and `DROP TABLE kill_switch_stops CASCADE` successfully (a schema owner may drop objects in it). `outside` in `_CAN_CLEAR` is relation owners and superusers only (migrate.py:311-313). Adding `pg_namespace.nspowner` of the schema (and members of it, by the same membership rule) to the listed roles costs one UNION arm. Also RUN, as documented and by design: an unnamed member of `pg_write_all_data` inserted a clear and migrate passed.

## 8. Low: memory store parity (read; no run needed)
`MemoryStore.set_kill_switch` overwrites one object (memory.py:228-230): any caller can clear, a second stop replaces the first stop's `by` (Postgres reports the OLDEST open stop), a reset has no "visible stops" notion, there is no append-only history. Stated in SECURITY ("guarantees nothing") and refused in pilot and prod (`("store","memory")` is DEMO_ONLY), so not a defect. The gap is the contract: tests/contracts/test_store.py:197-203 covers one stop only, so nothing pins stop, reset, stop-again for both stores (a stop after a reset must read ON; two stops then one reset). Add that contract test; it would also have caught `by` semantics drifting.

## 9. Low, UNVERIFIED (by reading, not run): advisory locks
`pg_advisory_lock` is executable by PUBLIC. A login that holds key `hadvnmig` blocks `migrate` (the connect used by migrate sets no `lock_timeout`, postgres.py:143-168, so it waits for ever) and one that holds `hadvnaud` makes audit appends wait until the store's 10 s `lock_timeout`, then fail: reset exits 3 as in item 3. Same class as the A-lane nit 17. Fix: `SET lock_timeout` in migrate's connection, and a different lock mechanism (or table lock) for the chain.

## 10. Info: one login stops
`limits stop` uses the runtime DSN only (cli.py:236-ff). If that login is broken (items 3, 5, a password rotation, connection slots used up) there is no supported way to stop through the reset login, which could do `UPDATE kill_switch SET "on" = TRUE` (the flag is still read). Consider a `limits stop --as-reset` that uses the reset login to set the old flag (one UPDATE), so the stop has a second path.

## Tried and held (RUN unless noted; PostgreSQL 16.15, runtime login after a clean migrate naming all four roles)
- Runtime UPDATE, DELETE, TRUNCATE, TRUNCATE CASCADE on all three stop tables; INSERT into `kill_switch_clears` and `kill_switch` row 2; `INSERT .. ON CONFLICT DO UPDATE` on stops: all permission denied. `ON CONFLICT DO NOTHING` only inserts nothing.
- CREATE TRIGGER, CREATE RULE, ALTER TABLE (disable trigger, rename, owner), DROP TRIGGER, DROP TABLE, CREATE VIEW or FUNCTION in the schema or in public, CREATE SCHEMA: denied. GRANT to self or to PUBLIC by the runtime: succeeded as a no-op (WARNING), rights unchanged. TEMP table named `kill_switch_stops`: allowed, affects only its own session; the store names the schema in every stop statement (postgres.py:567-579), so the stop read ignores it.
- LOCK TABLE: only ACCESS SHARE on all three, ROW SHARE and ROW EXCLUSIVE on stops (none conflicts with a read, a stop or a reset); SHARE and above denied. `SELECT .. FOR SHARE/KEY SHARE/UPDATE` on the stop tables could not be run through my first harness; by the PostgreSQL rule they need UPDATE, which the runtime lacks (not verified by run).
- `SET session_replication_role = replica`, `ALTER ROLE self SET session_replication_role`, `SET ROLE` to the reset role or postgres, `pg_terminate_backend` on the reset login: denied or no effect.
- `ALTER ROLE self SET search_path` (role-wide and IN DATABASE) is allowed (the UNVERIFIED claim of ABC finding 2 is true), but a store built from that login is refused at start by `verify_schema` ("the effective search_path of this login is ... but the store is configured for ...") for db_schema unset or set, and an explicit `<schema>, pg_temp` path equal to the schema starts normally. Decoy schemas need CREATE on the database, which no role has by default; not run.
- Race: stop committed after the reset's UPDATE of the flag but before its INSERT of clears is cleared (item 1); one committed after the INSERT statement began stays ON (their tests E3). Stop ids are random UUIDs; the clear reads no clock: no comparison of any `ts` decides ON or OFF, so a reset from a machine with a skewed clock (RUN of the code path by reading; `ks.ts` is only stored) cannot clear more or less than the statement sees. A skewed client clock only makes the clear row's `ts` earlier or later than the stop's DB-clock `ts` (audit confusion, not a reversal).
- Operator runs reset twice: the second reset writes a second `reset` audit row and, if a colleague stopped in between, erases that stop too (the message warns; item 1's fix removes it). Replayed audit row: `event_id` is UNIQUE and random; a forged `limits.reset` row from the runtime login changes no stop state (their H3) but the chain is unkeyed, so it reads as genuine in an unsigned tail; the clear rows (`by`, `ts`) are the better evidence, see the fix of item 1.
- Stop that does not persist: `Limits.stop` writes the row first, so a failed write raises, the CLI exits 2 or 4, and the audit is not written; the stop INSERT has no rowcount check but a refused or skipped row needs a trigger or a policy the runtime cannot create. When a store read fails, `reserve` and the loop fail closed with `limits_unavailable` (limits.py:186-188, agent_loop.py:277-279). Not covered: a stop whose commit was applied but whose reply was lost prints "Nothing was changed" on exit 4 for `stop` (cli.py:525); the operator retries, which adds a second stop (harmless).
- `who_else_can_clear` on PostgreSQL 16: a named-role clean run passes; PUBLIC and column grants are counted by reading; the real-server test list in tests/test_stop_state_roles.py (105 cases) was not re-run by me, I only used it to avoid repeating cases.
- Event triggers need a superuser: not reachable. SECURITY DEFINER in the migrations: only `hadavin_release_expired_spend` (0008), which touches the spend tables only, has its search path pinned by migrate and EXECUTE revoked from named roles.
- 0006 itself: `CREATE OR REPLACE TRIGGER` binds the function by oid, so a same-named function earlier on a path cannot replace it; the FK check of the clear insert works for the reset role with SELECT only (RUN, reset of 1M rows).
