## Checked, no finding
* Rows lost or duplicated in the table path: the outbox row is deleted only after `_drain` returned None; `_append` dedupes by event_id inside the advisory-lock transaction, so two ticks (or a tick and a writer) cannot write twice (E6 passes; a failed DELETE is counted and the next drain dedupes). Unreadable rows are never deleted.
* Chain order after a partial flush: the triggering event is written first, then the parked ones oldest first; an outage stops at the first failure and keeps the rest in order; reconcile puts `_unwritable` in front of `_pending` under the lock. Each drained event keeps its own `ts`, so a later seq can have an earlier ts; verify has no ts monotonic check (grep) so it stays ok. Outbox rows drain in random event_id order (A6, known).
* Concurrent threads: pop happens only under `_flush_lock`; appends to `_pending` are plain list appends (atomic). A crash between `_append` commit and `pop` only repeats a DuplicateEvent.
* `write_outcome` never raises and `write_intent` raises only its two errors, also with a flush that raises (caught at 281).
* Postgres connection is autocommit, so a failed statement does not leave an aborted transaction that would make every later drain "not writable".

## Suggested fixes (the lead decides)
1. Treat as outage (retry later, stay in `_pending`) also 57014, 55P03, 40001, 40P01, 53300 and 25006, or invert it: only a short list of permanent classes (22xxx data errors, 23xxx integrity, 42501 missing grant, 54000) is "not writable", everything else waits. Also let the inline flush retry `_unwritable` after a successful write that is some time later, or put them back in `_pending` on the next successful flush.
2. Use one classifier for the SELECT: `if not _is_outage(exc): raise`.
3. Document how an operator removes a poison row, or move it to a `audit_outbox_rejected` table; add LIMIT 1000 per tick (the next tick continues).
