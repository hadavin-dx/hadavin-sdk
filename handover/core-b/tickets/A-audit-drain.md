A7. FIX ROUND 4 (E9, ORDER 021; BUILT, code commit "code A: invert the audit outage classifier ..."), wins over A5/A6:
(a) Classifier inverted: `_is_permanent` (chain.py) is true only for SQLSTATE class 22, 23, 42501, 54000 (defaults.AUDIT_PERMANENT_SQLSTATES), a psycopg DataError/IntegrityError without a SQLSTATE, and local data errors (ValueError, TypeError, other non-OperationalError sqlite3 errors, unknown non-driver exceptions). Every other psycopg/OS error (57014, 55P03, 40001, 40P01, 53300, 25006, 08, 57P, 53100) is transient. test_f9 pinned 57014 and 25006 as permanent: wrong, changed (the review's repro r1 showed an event one retry from success dropped at exit).
(b) Inline flush: a transient failure stops the flush and the event stays in `_pending`; the next append retries it. Only a permanent refusal goes to `_unwritable` (retried by reconcile). A transient non-outage error that is still stuck at reconcile fails the step with "N events not writable in memory".
(c) The outbox SELECT: anything but a plain outage (OSError, StoreUnavailable, InterfaceError, no SQLSTATE, 08, 57P) raises "audit outbox: read failed (<class>)". A transient non-outage refusal of a row: "N rows refused for a transient error, retried next tick".
(d) LIMIT: `defaults.AUDIT_DRAIN_BATCH` (500) rows read and drained per reconcile, oldest first; the rest on the next ticks.
(e) ORDER, what was found: YES, a newer inline event could overtake a parked older one. write_outcome parked event A in the outbox after a failed append, then the next write_outcome(B) appended B at once; A entered the chain only at the next tick, after B. Outbox rows were also drained in random event_id order, and memory events before outbox rows. Fix: reconcile merges memory events and the batch of outbox rows and sorts by (event.ts, event_id) (the table has no sequence column and no migration is allowed, so ts is the order; the SQL orders by the "ts" text of the body, a row with no readable ts sorts last); and a write after this process parked an outbox row first runs one bounded drain pass (`_outbox_dirty`). Residual: if the older row is still refused (transient) the new event is written anyway (an intent must not wait on a sick outbox), and another process's inline event can still precede a row parked by a different process until the tick; each event keeps its own ts.
(f) Poison rows: a PERMANENT refusal of an outbox row (not 42501, which an operator mends with a grant and which stays retried) is renamed in place: INSERT under event_id `poison:<event_id>` (defaults.AUDIT_QUARANTINE_PREFIX), then DELETE the old row (the runtime role has no UPDATE). Quarantined rows are skipped by the read (so they do not use the batch), counted by one query each tick, and the step fails every tick with "N poison rows quarantined earlier (event_id prefix 'poison:'; operator removal: tickets/A-audit-drain.md)" (the tick that quarantines them says "N rows not writable"). No new table. Unreadable rows are not renamed; they sort last.
OPERATOR REMOVAL of a poison row (with a login that may DELETE on audit_outbox; the runtime role may): inspect `SELECT event_id, left(body, 200) FROM audit_outbox WHERE event_id LIKE 'poison:%';`. To discard: `DELETE FROM audit_outbox WHERE event_id = 'poison:<id>';` (all: `... LIKE 'poison:%'`); the event is then gone from the audit for good, so note the id in the incident record first. To retry after fixing the cause: `INSERT INTO audit_outbox (event_id, body) SELECT substr(event_id, 8), body FROM audit_outbox WHERE event_id = 'poison:<id>'; DELETE FROM audit_outbox WHERE event_id = 'poison:<id>';` (the next tick drains it).
Still stated limits: `_pending` and `_unwritable` are unbounded lists; the `ORDER BY` sorts the whole outbox table per tick (no index on ts); a body with ts in mixed UTC offsets would sort lexically.

A8. FIX ROUND 5 (review A-review-4; code commit "code A: ..."), wins over A7 where they differ:
(a) A transient refusal of an item (outage, timeout, lock wait, unclassified error), memory or outbox, STOPS the drain pass: nothing newer is written past it, the next tick or write retries in ts order. Permanent refusals are still skipped (quarantine or `_unwritable`). tests/test_audit_drain.py f2 tests were changed to this (a failing row now also holds back the rows after it).
(b) An exception of no known kind (not psycopg, OS, StoreUnavailable, sqlite3, ValueError or TypeError) is no longer permanent: it is retried and never quarantined, and the step fails with "N items refused for an unclassified error (retried, not quarantined)".
(c) Unreadable rows (valid JSON that is not an AuditEvent, or an event_id that differs from the row) no longer use the batch: the read pages on (LIMIT/OFFSET) until it holds AUDIT_DRAIN_BATCH readable rows or the table ends; they are counted each tick ("N unreadable rows kept") and cost one scan of them per tick.
(d) A naive `ts` no longer raises in the sort: it is ordered as UTC (only the order; the event keeps its ts).
(e) Stated limit (Minor 2, not built): batches are cut by the lexical text of `ts` in SQL, so with a backlog above AUDIT_DRAIN_BATCH a memory event can enter the chain before older outbox rows that lie in a later batch, and mixed offsets / `Z` vs `+00:00` / fractional seconds can pick the wrong rows at the batch edge. Order inside a batch is exact.

### A8 addendum (review 5: CLEAN, 0 Major; four Minors recorded as stated limits)
- (f) A persistent outage-class refusal on the head row (a SQLSTATE-less OperationalError or an OSError) holds back every later row and the step stays green (`_is_outage` rows are not counted as deferred, chain.py:425-428). Needs an unusual driver error; the connection layer alarms separately.
- (g) The paged outbox read has no snapshot: a second process deleting or renaming rows between pages can make one tick skip a row (picked up next tick) or read one twice (deduped by event_id; the `done` and `unreadable` counts can double count).
- (h) `_transient_stuck` is reset only in `_flush_pending`; after an outage it can go stale for one tick and raise a false "events not writable in memory" text.
- (i) A naive `ts` is ordered as UTC in `_sort_ts` but stamped as local time by `_append`; on a non-UTC host the order and the stamp can disagree. Events built by the SDK always carry an aware ts.
