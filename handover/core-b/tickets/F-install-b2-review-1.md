## Major

M1. Docs contradict each other and CHANGELOG overclaims. README.md:45-47 and SECURITY.md:76-80 still say "the live run path does not reserve before a model call" (now false; stale in the safe direction, but a reader gets two opposite statements). CHANGELOG.md:6 says "No-overspend now holds ONLY for call sites that go through the live loop (`Runtime.handle`, which reserves ... before each model call)". That is untrue as worded: `Runtime._screen` (agent_loop.py:383-389, llm_judge) is a model call INSIDE the live loop and is charged after the fact (CHANGELOG.md:8 admits it two lines later), and it can push a counter past the cap after the main call settled. The lead's required sentence ("no-overspend is NOT in force until the model gate installs reserve/settle") is no longer in CHANGELOG at all. Fix: keep the lead's sentence verbatim in README/SECURITY/CHANGELOG, and reword CHANGELOG.md:6 to "the live loop's main model call reserves before and settles after; no-overspend is NOT in force: the llm_judge screen call in the same loop, k1b, evals, guard/judge are not gated". Also CHANGELOG.md:99 and :106 ("the live run path does not call it yet", "later change") are now false; add "(live loop main call since B2)".

M2. `_settle_model_call` can raise and can double-count (agent_loop.py:391-398). (a) The docstring says "never raises", but the fallback `store.add_cost` goes through `clean_spend_amount`; when settle failed BECAUSE the cost is bad (NaN, negative, None, over 12 decimals: `check_spend_amount` ValueError in `settle_for`), `add_cost` raises the same ValueError, uncaught, and the run is left in WORKING with the hold open until the stuck-run rule. (b) Ambiguous failure (settle committed in the DB, connection dropped before the reply): `hadavin_settle_spend` already added the run cost (CHANGELOG.md:102), then `add_cost` adds it again: `runs.cost_usd` is double-counted (day/month counters are fine; the hold is already settled). Fix: wrap the fallback in its own try, and on a settle exception first re-read the reservation (or `get_run` cost) / only call `add_cost` when `settle_spend` is known not to have applied; on a bad amount fail closed (NEEDS_PERSON `limits_unavailable`) instead of raising. No test or mutant covers this path (b2_mutants.py has only 3 mutants).

## Minor

m1. "Expires through the tick" (agent_loop.py:393 docstring, CHANGELOG) is misleading: `expire_reservations` (tick.py:277-283) only marks the row expired; the counters do NOT move and the worst case stays booked until an operator runs the release (`release_expired_spend`, migration 0008). So after a provider outage every failed run (ProviderError/ProviderExhausted, KeyboardInterrupt/BaseException, killed process) holds a full worst case on the day AND month counters indefinitely; enough failed runs lock the agent out with `daily_budget`/`monthly_budget` until a manual release. Safe direction, but it is an availability trap and should be in the runbook/CHANGELOG as an operator step. Also a provider failure books nothing to `runs.cost_usd` although the provider may have billed (counter has it, run row does not).

m2. Audit/outcome codes are inconsistent (agent_loop.py:531-537): a store failure inside `Limits.reserve` arrives as `SpendRefused("limits_unavailable")` and is written as `limits.limits_unavailable`, while any other exception (including a `worst_case_for` non-SpendRefused) is written `limits_unavailable`; price failure is `limits.bad_amount`. Two codes for one condition. Fix: map reason `limits_unavailable` to the bare code. Kill switch correctly gives STOPPED/`kill_switch`.

m3. Fail closed on a transient store error is permanent for that run (NEEDS_PERSON, no retry) (agent_loop.py:536-537). The pre-existing `_limits_stop`/`blocked` read at the same step has the same shape, so this is not new, but reserve adds a second write that can fail transiently. Acceptable; state it in CHANGELOG behaviour changes. The kill switch flipping between reserve and `llm.chat` still lets that one call go out (bounded by the held worst case).

m4. Missed/undocumented model-call site: `guard/bedrock_guardrail.py:101` `apply_guardrail` (a paid Bedrock call, not priced, not in the CHANGELOG list of ungated sites). `cards.render_shadow(..., detector=self.detector)` (agent_loop.py:735) hands the detector to a renderer; if that detector is llm_judge, its cost is not charged at all (not even after the fact). Verify and list both. Other `.chat(` sites (k1b/loop.py:81, evals.py:78, guard/judge.py:72) match the documented list.

m5. `worst_case_for` takes `max_attempts` from the client by `getattr` (default 1): a wrapper/test double around a retrying client without the attribute is priced for ONE attempt while retrying. Low risk with the shipped clients (all set `max_attempts`); fix: require the attribute at install, or price an unknown client at a documented maximum.

m6. Test gaps: no test or mutant for the settle-failure fallback (M2), the kill-switch refusal at reserve, a `worst_case_for` failure, or an overshoot reply through the loop. Add one mutant each (remove the `add_cost` fallback; map kill_switch to NEEDS_PERSON).
