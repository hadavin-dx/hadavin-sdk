Small gap: the fake is SQLite (`_refuse` trigger) with an injected clock, not a real subprocess `tick` over Postgres; the production path (`run_tick` -> `reconcile`, tick=True) is the same code, so acceptable. The write-path pre-drain (`tick=False`) never quarantines (a10 test `test_d_the_write_path_pre_drain_does_not_quarantine`).
2. 42501 still never quarantined? Yes. chain.py:553 `sqlstate != "42501" and tick`. Tests: a11 `test_42501_is_never_quarantined_however_old` (fresh instance per tick, 30 days old, 3 ticks) and a10 parametrised `test_d_42501_and_transient_errors_are_never_quarantined`. Transient and unclassified errors never reach this branch (chain.py:560-565).
3. Concurrent tick processes (INSERT `poison:<id>` then DELETE): safe. `_append` runs inside `_db.transaction()` which takes `pg_advisory_xact_lock` (chain.py:193-199) and checks `audit_entries.event_id` first (:289) and the column is UNIQUE (:56): two processes cannot both write the same event; the second gets `DuplicateEvent`, which `_drain` maps to success (:578-586), then its DELETE of the outbox row is a no-op. No double chain write, no 23505 loser reaching the permanent branch (the advisory lock serialises the SELECT and INSERT). Two processes quarantining the same poison row: both INSERT with `ON CONFLICT (event_id) DO NOTHING` and both DELETE: idempotent, one `poison:` row. If the process dies between INSERT and DELETE, both rows remain; the next tick re-quarantines (INSERT is a no-op, DELETE removes the original); the only cost is that the pair is counted/readable for one extra tick. If the INSERT fails the DELETE is skipped (same try block): never a delete without a kept copy. Cosmetic: both processes add 1 to `r.marked`, and the "earlier" count is `total - marked` clamped at 0 (chain.py:431-436), so a racing tick can under-report "earlier" by one for that single tick.

## Findings

### Minor

m1. A ts in the FUTURE (writer host ahead of the tick host, or a bad ts) is never quarantined while it is in the future, and the ticket does not state it.
- chain.py:554-555: age is negative, `negative >= 300` is false. Scenario: writer clock +10 min ahead of the tick host; a poison row it wrote is quarantined only 10 min + 300 s later (harmless, a delay). A far-future ts (a bug, year 2999, or a naive local-time ts east of UTC read as UTC, up to +14 h) is never quarantined: it fails the step with "1 rows not writable" every tick for ever. It does not block good rows: the SELECT sorts by ts, so a future row sorts last (chain.py:476-483, 521), it only takes one batch slot. Acceptable (fail-safe: nothing is lost or hidden, the step stays red, the operator is told), but it is a silent exception to "quarantined after 300 s". Fix: one sentence in tickets/A-audit-drain.md (d) and in the defaults.py:176-180 comment ("a ts in the future is not quarantined until the clock passes it; the step keeps failing"). A cap such as `min(age, ...)` is not needed. Add one test (clock earlier than ts: stays, 3 fresh ticks) if cheap.
- Naive ts: handled. `_sort_ts` (chain.py:130-134) reads it as UTC, so there is no TypeError on the subtraction; covered by a11 `test_a_naive_ts_is_read_as_utc_for_the_age`. Note the existing caveat (ticket (i)): `_append` stamps a naive ts as local time, so on a non-UTC host the age can be off by the UTC offset; same direction rules as above.

m2. Quarantine on the FIRST failed tick of an OLD event (e.g. an event parked for 3 days of outage, then a permanent refusal) is acceptable; no fix needed. Reasoning: the A10 verdict said "fails N ticks" to mean "the refusal is not going away". The classes in `AUDIT_PERMANENT_SQLSTATES` (22 data, 23 integrity, 54000 limit) are deterministic for a given body and schema, so a second failed tick adds no information; the 3-day wait was spent on the outage, which is a transient state that never counts (transient and 42501 errors are never quarantined), and a refusal observed once with a permanent class is the same refusal on tick 2, 3, ... The action is non-destructive and reversible: the body is kept under `poison:` (chain.py:567-576), visible in the step text and log (`quarantined_now=`), operator release by INSERT+DELETE is tested (a10 `test_d_a_quarantined_row_is_readable...`). The cost of the alternative (age from the first failure) needs persisted state (a column or a strike id; the runtime role has no UPDATE), which is what review 8 option 2 priced as more code and more writes. Residual risk worth one ticket line: a class-23 refusal caused by a transient operator state (a migration or trigger not yet applied, a constraint being fixed) quarantines every old row on that tick; the operator releases them in one statement (documented). If the lead nevertheless wants "N observed failures", the smallest fix is a grace on the row's own age only for rows already in the outbox before the failure was first seen, which cannot be done without state; do not build it. Say in the ticket that the age counts from `event.ts`, not from the first failure, and that an old row is quarantined at its first permanent refusal.

## Residual window (stated in ticket, confirmed)
A poison row younger than 300 s takes one `drain_batch` slot per tick (SELECT skips only `poison:` rows, chain.py:482) and keeps the step failing; starvation needs >= `drain_batch` such young poison rows older than every good row, and they leave the window after 300 s. A burst of poison rows with fresh timestamps cannot be older than the good rows around it for long. Confirmed fine.
