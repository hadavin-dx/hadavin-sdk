## C1 FIRST: what purge does with an expired row nobody settled
**It deletes it.** An expired row counts as closed. The sweep sets `status = 'expired'`, `settled_usd = reserved_usd` AND `closed_at = <expiry time>` in one statement (PostgreSQL store/postgres.py:764-766, database clock; memory store/memory.py:391-393). The table forces this: `CHECK ((status = 'open') = (closed_at IS NULL))` (migrations/0007_spend_reservations.sql:16), so a row that is not open always has a closed_at. Purge deletes every row that is not open and whose closed_at is before the bound: `DELETE ... WHERE status <> 'open' AND closed_at < %s` (postgres.py:777; memory.py:403). So the age of an expired-unsettled row is measured from the moment it expired, not from its creation. The tick runs it with the 400-day ceiling (runtime/tick.py:206-208, `held_tool_calls_max_days`) on the purge store.
Consequences, as built:
- A settle that arrives after that purge raises NotFound (memory.py:359-360; postgres.py:726-730, no row). The worst case stays on the counters, which is the safe direction. Before the purge, a late settle claims the row (status "settled", closed_at set anew, postgres.py:703-709).
- Your recommended rule (expire does not set closed_at, purge keeps expired rows until settled) is NOT what is built and cannot be: the CHECK above forbids a non-open row without closed_at.
- A row released by the release command (migration 0008, see P2) is `settled` with `settled_usd = 0` and KEEPS its expiry closed_at (0008 function body; it does not touch closed_at), so purge deletes it by the same rule. A settle after a release but before the purge returns the stored row with applied False and books nothing (the _CLAIM matches only open and expired rows, postgres.py:703-709, then the plain SELECT at 726-731).
- The purge role's reach, stated precisely because the wording "DELETE on closed rows only" is easy to over-read: the role holds table-level DELETE plus SELECT on the columns status and closed_at only (migrate.py:59, `Grant("table", _RW, purge="DELETE", purge_cols=("status", "closed_at"))`; the migrations have no row policy, grep for POLICY and ROW SECURITY finds none). So "closed rows only" is what the METHOD does (the WHERE at postgres.py:777), not something the database enforces against a purge login that issues its own DELETE. It cannot read amounts, ids or run ids.
- "Closed" in README section 1 means status is not open (the version line of README 2.3 says so; the body of section 1 still says "a reservation nobody closed ... is marked expired" in the plain-words paragraph, which reads right once "closed" means "settled by a caller"). I did not edit README: no new sentence is needed there.
