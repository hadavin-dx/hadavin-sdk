**Words used (plain meaning, one meaning each).**
- **assembled agent**: a client's program built from the core and the kit (its own agents, rules, prompts, tools), shipped as one container image.
- **container image**: one packed, read-only copy of the program and everything it needs to run; the same image runs every part below.
- **part**: one job the deployed program does, run as its own process with its own identity: `app` (does the work and answers the web doors), `tick` (housekeeping every minute), `purge` (deletes old evidence), `maintenance` (sweeps abandoned spend reservations, from P4b2), `audit` (signs the audit trail and stores its proof copy), `migrate` (applies the database schema, run once per release).
- **identity**: who the cloud and the database think a process is. "One identity per part" means each part signs in as itself and gets only its own rights.
- **rights**: what an identity may do: exact action, exact resource. **deny-all start**: an identity begins with no rights; every right is added on purpose with a reason.
- **infrastructure-as-code (IaC)**: text files that describe the servers, identities, networks and rights, so a tool can create them the same way every time and a reviewer can read them.
- **cloud adapter**: the part of the kit that turns our cloud-neutral rights list into one cloud's own policy files (AWS, Azure, Google Cloud). In v1 there are none; each is a v1.1 row with the trigger "the client runs on that cloud".
- **neutral default**: the one way the kit deploys without choosing a cloud: plain Kubernetes files (Kubernetes is an open-source system for running containers that every large cloud and many on-premise sites offer).
- **render**: our code writes the deployment files from the client's config. **lint**: our code reads deployment files and refuses any that break a rule (a plan-only check: nothing is created, nothing in any cloud is called).
- **smoke test**: a short check that a deployed part starts, finds what it needs, and is refused what it must not have. **fake mode**: in CI, against made-up secrets and a throwaway database. **live mode**: against the client's real cloud, run only by the lead or the client's operator on a numbered order.
- **checkpoint row**: one row of the database table `audit_checkpoints`: the number of the last audit row it covers (`seq`), that row's hash, a signature over both, and the signing scheme and key label.
- **anchor**: the copy of each checkpoint kept in a store that even we cannot rewrite for a set time (a locked object store). **re-anchor**: putting a checkpoint's copy again because an earlier put may have failed.
- **checked row**: a checkpoint row that passes the three checks of D1 (same key, valid signature, hash equal to the audit row's hash).
- **clock skew**: the difference between two machines' clocks.
- "UNVERIFIED" = I did not read it in code, or it is general knowledge I did not check today. "PENDING LEAD" = a lead or owner decision, my recommendation first. "INFORM" = my decision on my recommendation, final unless the lead says otherwise (order 23 item 4). **OWNER** marks a step only the owner can do.

- **Re-anchor pass (PENDING LEAD 12, answered (a); R2-ADV-1, R2-ADV-8, R2-RES-2).** The audit part stays a scheduled job. `ChainAudit` gains a constructor argument `anchor_recheck: int = 0`; with 0 there is no pass, so `part=None` and every non-audit build behave exactly as today. Only `build_part(part="audit")` passes `defaults.ANCHOR_RECHECK` (30, validated range 1-120 by a guard test). When `anchor_recheck > 0` and an anchor is configured, `checkpoint()` runs the pass at the start of the call, after the signer check (`chain.py:299-300`) and before the early return (`:307-308`):
  1. Read the newest checkpoint rows with `seq <= head` (head = the newest `audit_entries.seq`), at most `defaults.ANCHOR_RECHECK_SCAN` rows (120 = 4 x `ANCHOR_RECHECK`; the guard test checks the relation).
  2. A row is **checked** only if all three hold: (i) its `key_label` equals `signer_label(current signer)` (`chain.py:81`) and its `alg` equals `signer.alg`; (ii) its signature verifies with the current public key over `_signed_message(seq, hash)`; (iii) its `hash` equals `audit_entries.hash` at that `seq`. A row that fails (ii) or (iii) is skipped and logged by kind only ("checkpoint row failed check: signature" or "...: hash"), never put.
  3. **Rotation:** a row under another key fails (i) and is skipped with the log line "signed by a different key: not rechecked". The core holds no old public key (code facts), so it is not re-put. Revision 2's "re-put with the row's own `alg` and `key_label`" is replaced for other keys. A keyring is new surface and joins V8 as a written row.
  4. Put the newest `anchor_recheck` checked rows again. Identical bytes already there count as success; different bytes are logged as `AnchorConflict` and never overwritten. The pass stops at the first put that fails with anything other than `AnchorConflict` (an outage), so one run stays inside the CronJob's `activeDeadlineSeconds` (D2).
  5. Rows beyond the scan cap are counted in one error line. So N junk rows cannot push a genuine row out of the window unless there are more than 3N of them, and then the error line says so.
  It needs no new right (put plus a read of one key by name, already in the audit row below) and no schema change. It counts in checkpoints, not time: at one audit run per minute, N = 30 covers a 30-minute anchor outage.
- **Checked signed-through (R2-RES-1).** The early return in `checkpoint()` stops using `signed_through()` (today's `MAX(seq)`, `chain.py:290-293`, whose only caller is `:307`) and uses a private `_checked_through(head)`: the highest `seq <= head` among checked rows in the same bounded read. A row beyond head is logged by kind ("checkpoint row beyond head"). So one junk row at a huge `seq` no longer stops signing. After a key rotation no older row is checked, so the next pass signs the head with the new key (one extra checkpoint row, not a failure). `signed_through()` itself is unchanged. **Residual, said plainly:** a compromised work part can still pre-fill a range of real future `seq` values so that the genuine inserts conflict; signing then pauses over that range. The pause is detected (`audit verify` reports the invalid signatures; the lag step below fires) but not prevented. Only role separation prevents it: V7, required before any pilot (PENDING LEAD 16 answered, order 45 item 16).

**D5. Clock skew (operator note 1).** All machines of one deployment must keep their clocks within 60 seconds of each other (`operator-notes.md:3`). Boundary: exactly 30 s passes, 31 s fails. **Where a delay sits, and the sign (R2-COR-8):** with a 2 s delay BEFORE the database read and the database 29 s ahead, `db - t0` = 31 s: fails; with the same delay and the database 29 s behind, both differences are at most 29 s: passes; with a 2 s delay AFTER the database read and the database 29 s behind, only `t1 - db` = 31 s exceeds: fails (this case kills "t0 only", M-c12). **When:** only when the smoke test runs at each deployment, not continuously; a continuous check is row V16.
