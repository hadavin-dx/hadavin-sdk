**Words used (plain meaning, one meaning each).**
- **assembled agent**: a client's program built from the core and the kit (its own agents, rules, prompts, tools), shipped as one container image.
- **container image**: one packed, read-only copy of the program and everything it needs to run; the same image runs every part below.
- **part**: one job the deployed program does, run as its own process with its own identity: `app` (does the work and answers the web doors), `tick` (housekeeping every minute), `purge` (deletes old evidence), `maintenance` (sweeps abandoned spend reservations, from P4b2), `audit` (signs the audit trail and stores its proof copy), `migrate` (applies the database schema, run once per release).
- **identity**: who the cloud and the database think a process is. "One identity per part" means each part signs in as itself and gets only its own rights.
- **rights**: what an identity may do: exact action, exact resource. **deny-all start**: an identity begins with no rights; every right is added on purpose with a reason.
- **infrastructure-as-code (IaC)**: text files that describe the servers, identities, networks and rights, so a tool can create them the same way every time and a reviewer can read them.
- **cloud adapter**: the part of the kit that turns our cloud-neutral rights list into one cloud's own policy files (AWS, Azure, Google Cloud). In v1 there are none; each is a v1.1 row with the trigger "the client runs on that cloud".
- **neutral default**: the one way the kit deploys without choosing a cloud: plain Kubernetes files (Kubernetes is an open-source system for running containers that every large cloud and many on-premise sites offer).
- **render**: our code writes the deployment files from the client's config. **lint**: our code reads deployment files and refuses any that break a rule (a plan-only check: nothing is created, nothing in any cloud is called).
- **smoke test**: a short check that a deployed part starts, finds what it needs, and is refused what it must not have. **fake mode**: in CI, against made-up secrets and a throwaway database. **live mode**: against the client's real cloud, run only by the lead or the client's operator on a numbered order.
- **anchor**: the copy of each audit signature kept in a store that even we cannot rewrite for a set time (a locked object store).
- **clock skew**: the difference between two machines' clocks.
- "UNVERIFIED" = I did not read it in code, or it is general knowledge I did not check today. "PENDING LEAD" = a lead or owner decision, my recommendation first. "INFORM" = my decision on my recommendation, final unless the lead says otherwise (order 23 item 4). **OWNER** marks a step only the owner can do.

## The decisions that shape this ticket (read before the fields)

**D0. Options first; the kit never chooses the cloud (BRIEF rule 16; INFORM I1).** For every client the quote lists three ways to deploy, with cost and risk in plain words, and the client chooses; the choice and who carries the tool risk go into the quote and the contract:
- **(a) The client's own platform and tools.** They already run containers (their Kubernetes, their serverless containers, their IaC tool, their CI). We hand over the image recipe, the rendered files and the rights list; their team applies them. Cost: their team's time; no new licence. Risk: we depend on their team's skill; our lint still runs on what they apply (`deploy check`).
- **(b) A vendor tool used directly** (a managed container service, a hosted deploy tool, a vendor IaC product). Cost: the vendor's price, paid by the client. Risk: one vendor can change price, terms or shut down; a vendor IaC tool's licence may not be open source.
- **(c) Our swappable code** (this package): the neutral Kubernetes default in v1, a cloud adapter per cloud in v1.1. Cost: our build time (a new cloud adapter is about one sub-PR, an estimate and UNVERIFIED, when the first client on that cloud signs); hosting is the client's cloud bill. Risk: we maintain it; adapters for a cloud exist only after a client on it.
Plain cost words for the neutral default: the client pays for a Kubernetes service (some clouds charge per cluster hour for the control plane), the machines, a PostgreSQL database, a locked object store for prod, and a secret store if they use one. **Numbers are NOT given here:** a dated read of public price pages is needed (PENDING LEAD 9).

**D1. Parts: each process builds and reads only what its job needs (core change, sub-PR AK-G16-a; INFORM I2, PENDING LEAD 2).** Without D1 there is no least privilege to deploy: per the code facts above, every process needs every secret and the signing right. D1 adds a closed table of five built parts (`app`, `tick`, `purge`, `maintenance`, `audit`) and two further identities that are never built as parts (`migrate`, `operator`):
- **Full parts (`app`, `tick`):** `app.build(..., part=None)`. `None` keeps today's behaviour exactly (every backend, inline signing). With `part="app"` or `part="tick"` the build is today's build except: no signer and no anchor (the audit sink gets `signer=None, anchor=None`), no purge store, and `platform_secrets.check` over `secret_names_for(cfg, part)` only, a set that excludes the purge, maintenance, signer and anchor secrets.
- **Small parts (`purge`, `maintenance`, `audit`):** `deploy.parts.build_part(...)` returns a `PartApp` with exactly six fields (`config`, `store`, `purge_store`, `audit`, `hooks`, `clock`). It builds no model, detector, channel, source, tool, executor or restored key, and runs no scope probe. Today's `app.build` cannot do this (code facts, R1-COR-1); a separate six-field type touches only two reads in `runtime/tick.py`, where making `Runtime` and `Approvals` optional on `App` would touch every caller of `App` in frozen packages (P6a, P6b2, AK1-c, AK-G2-b all edit `app.py`).

**D5. Clock skew (operator note 1).** All machines of one deployment must keep their clocks within 60 seconds of each other (`operator-notes.md:3`). The smoke test compares each part's clock with the database clock and refuses more than `deploy.max_clock_skew_s` (default 30, allowed range 1-30): if every machine is within 30 s of the one database clock, any two machines are within 60 s of each other. **How it is measured (R1-COR-11):** read the local clock (t0), then the database clock, then the local clock again (t1); the part passes only if both `abs(db - t0)` and `abs(db - t1)` are at most the bound, so round-trip time counts against the part (the conservative side). Boundary: exactly 30 s passes, 31 s fails. **When (R1-ADV-8):** only when the smoke test runs at each deployment, not continuously; a continuous check is row V16.
