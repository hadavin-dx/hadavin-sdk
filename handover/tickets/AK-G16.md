**Words used (plain meaning, one meaning each).**
- **assembled agent**: a client's program built from the core and the kit (its own agents, rules, prompts, tools), shipped as one container image.
- **container image**: one packed, read-only copy of the program and everything it needs to run; the same image runs every part below.
- **part**: one job the deployed program does, run as its own process with its own identity: `app` (does the work and answers the web doors), `tick` (housekeeping every minute), `purge` (deletes old evidence), `maintenance` (sweeps abandoned spend reservations, from P4b2), `audit` (signs the audit trail and stores its proof copy), `migrate` (applies the database schema, run once per release).
- **identity**: who the cloud and the database think a process is. "One identity per part" means each part signs in as itself and gets only its own rights.
- **rights**: what an identity may do: exact action, exact resource. **deny-all start**: an identity begins with no rights; every right is added on purpose with a reason.
- **infrastructure-as-code (IaC)**: text files that describe the servers, identities, networks and rights, so a tool can create them the same way every time and a reviewer can read them.
- **cloud adapter**: the part of the kit that turns our cloud-neutral rights list into one cloud's own policy files (AWS, Azure, Google Cloud). In v1 there are none; each is a v1.1 row with the trigger "the client runs on that cloud".
- **neutral default**: the one way the kit deploys without choosing a cloud: plain Kubernetes files (Kubernetes is an open-source system for running containers that every large cloud and many on-premise sites offer).
- **render**: our code writes the deployment files from the client's config. **lint**: our code reads deployment files and refuses any that break a rule (a plan-only check: nothing is created, nothing in any cloud is called).
- **smoke test**: a short check that a deployed part starts, finds what it needs, and is refused what it must not have. **fake mode**: in CI, against made-up secrets and a throwaway database. **live mode**: against the client's real cloud, run only by the lead or the client's operator on a numbered order.
- **anchor**: the copy of each audit signature kept in a store that even we cannot rewrite for a set time (a locked object store).
- **clock skew**: the difference between two machines' clocks.
- "UNVERIFIED" = I did not read it in code, or it is general knowledge I did not check today. "PENDING LEAD" = a lead or owner decision, my recommendation first. "INFORM" = my decision on my recommendation, final unless the lead says otherwise (order 23 item 4). **OWNER** marks a step only the owner can do.

## The decisions that shape this ticket (read before the fields)

**D0. Options first; the kit never chooses the cloud (BRIEF rule 16; INFORM I1).** For every client the quote lists three ways to deploy, with cost and risk in plain words, and the client chooses; the choice and who carries the tool risk go into the quote and the contract:
- **(a) The client's own platform and tools.** They already run containers (their Kubernetes, their serverless containers, their IaC tool, their CI). We hand over the image recipe, the rendered files and the rights list; their team applies them. Cost: their team's time; no new licence. Risk: we depend on their team's skill; our lint still runs on what they apply (`deploy check`).
- **(b) A vendor tool used directly** (a managed container service, a hosted deploy tool, a vendor IaC product). Cost: the vendor's price, paid by the client. Risk: one vendor can change price, terms or shut down; a vendor IaC tool's licence may not be open source.
- **(c) Our swappable code** (this package): the neutral Kubernetes default in v1, a cloud adapter per cloud in v1.1. Cost: our build time (a new cloud adapter is about one sub-PR when the first client on that cloud signs); hosting is the client's cloud bill. Risk: we maintain it; adapters for a cloud exist only after a client on it.
Plain cost words for the neutral default: the client pays for a Kubernetes service (some clouds charge per cluster hour for the control plane), the machines, a PostgreSQL database, a locked object store for prod, and a secret store if they use one. **Numbers are NOT given here:** a dated read of public price pages is needed (PENDING LEAD 9).

**D1. Parts: each process builds and reads only what its job needs (core change, sub-PR AK-G16-a; INFORM I2, PENDING LEAD 2).** Without D1 there is no least privilege to deploy: per the code facts above, every process needs every secret and the signing right. D1 adds a closed table of parts and a `part` argument:
- `app.build(..., part=None)`: `None` keeps today's behaviour exactly (every backend, inline signing). With a part, the build constructs only that part's backends and checks only that part's secret names.
- `hadavin-sdk tick --part <tick|purge|maintenance|audit>` runs only that part's steps through the existing `run_tick(..., steps=...)`.
- Signing and anchoring happen ONLY in the `audit` part when parts are used: other parts build no signer and no anchor, so the chain does not sign inline (`chain.py:203` skips without a signer). The prod refusal of `signer: none` stays a config check and still runs (`config.py:391-392`).
- The operator part `operator` (for `limits stop` and `limits reset`) builds the store and the audit sink without a signer (PENDING LEAD 4). `audit verify` keeps building the signer (limit O7).
Rights per part (cloud-neutral; v1.1 adapters translate them):

| Part | Runs | Secrets it may read | Database role | Cloud rights (neutral words) |
|---|---|---|---|---|
| app | the assembled agent's entry command and the web doors (D4) | runtime login, model key, channel tokens, tool and source tokens, restored-hash key | runtime | call the configured model route; nothing else |
| tick | `tick --part tick`: sweep, reconcile, stuck, reprobe_sources, and later appended steps assigned to it | same names as app (sweep sends messages, reconcile continues runs, `tick.py:79-95`) | runtime | same as app |
| purge | `tick --part purge`: purge_evidence | runtime login (step state, `tick.py:296`), purge login | runtime + purge | none |
| maintenance | `tick --part maintenance`: P4b2's sweep step | runtime login, maintenance login | runtime + maintenance | none |
| audit | `tick --part audit`: checkpoint | runtime login, the signer's own secret if it has one | runtime (no separate audit role in `GRANTS`, PENDING LEAD 3) | sign with ONE key and read its public half; write new objects under ONE prefix of ONE locked store and read back one object by key; no list, no delete, no retention change |
| migrate | `migrate --runtime-role ... --purge-role ... [--portal-role ...] [later roles]`, once per release | migration login | migration owner (not superuser) | none |
| operator (a person, not deployed) | `limits`, `audit verify` | runtime login (+ P2a's stop or reset credential) | runtime, P2a stopper or reset | `audit verify`: list and read the anchor prefix, read the public key (and sign, limit O7) |

"Same names as app" is computed by one function, so a test (P7) shows the two never drift apart. Separate service accounts for app and tick cost nothing and keep one identity per function.

**D2. The neutral default: one image, plain Kubernetes files, rendered and linted by our code (sub-PR AK-G16-b; PENDING LEAD 5).** Options considered:
- (a) **Recommended: plain Kubernetes manifests** rendered from the client's config: a Deployment for `app`, a CronJob per scheduled part, a Job for `migrate`, one ServiceAccount per part, a deny-all NetworkPolicy plus one allow policy per part, and one secret volume per part listing only that part's names. Kubernetes is open source (Apache-2.0, general knowledge, UNVERIFIED today) and offered by every large cloud and on-premise; each large cloud can give a pod its own short-lived cloud identity (workload identity, general knowledge, UNVERIFIED), which a single machine cannot.
- (b) Docker Compose on one machine: cheapest, but every container on the machine shares the machine's cloud identity through the metadata address, so one identity per part fails. Kept as v1.1 row V5 with a written trigger.
- (c) Only per-cloud serverless containers: not neutral; v1.1 row V4.
- Packaging: plain YAML written by our renderer (no Helm, no Kustomize overlays in v1: cut surface, order 8; Helm is row V10). IaC tool for cloud resources: none in v1 (no cloud resources are created by v1); a cloud adapter may use OpenTofu (Mozilla Public Licence 2.0, general knowledge, UNVERIFIED), the client's own IaC tool, or the cloud's own template language, chosen with the client under D0.
- The **image**: one multi-stage container file rendered from a template in the package: base image pinned by digest (`<registry>/<base>@sha256:<64 hex>` from config), one pinned Python (A9 F3: production runs one pinned Python), dependencies installed from `uv.lock` with hashes, the client's agent package copied in, a fixed numeric non-root user from config, no build argument or environment variable that carries a secret, no download from a URL during the build. Build, push and signing happen in the CLIENT's pipeline and registry (PENDING LEAD 8); our CI only builds and scans if the lead adds the job (PENDING LEAD 7).

**D3. Smoke test: fakes in CI, the client's cloud only on a numbered order (sub-PR AK-G16-c; INFORM I3).** `hadavin-sdk smoke --part <p>` builds that part (with probes) and checks, without doing work: the store answers; the part's own secrets resolve; ONE named secret of another part is refused (negative probe; the value, if wrongly returned, is dropped unread and the smoke fails); the database role holds none of the other parts' table rights (`has_table_privilege` reads only, never an attempted write); the clock skew against the database clock is at most `deploy.max_clock_skew_s` (D5). In fake mode (CI) it also runs one made-up item through the `app` part with the fake model and checks one final state and no canary text in the logs. Live mode needs `--live --order <N>`: it never calls the model, never runs a tick step, never writes an anchor (a locked object cannot be deleted), never writes a row; it prints one line with the part, the result and the order number. Only the lead or the client's operator runs it, inside the client's cloud, under that part's own identity (OWNER: the client's written yes and access, PENDING LEAD 10).

**D4. Production hosting of the web doors (sub-PR AK-G16-d; PENDING LEAD 6).** The doors (the approval receiver today, AK-G2's webhook door later) are framework-free functions `(headers, body) -> (status, ...)`. v1 hosts them through the WSGI standard (Python's web server interface, PEP 3333): a small adapter in the core, with the request size checked from `Content-Length` before the body is read, chunked bodies refused, no header or body text in logs. The server program is an image-only dependency group, not a core dependency: default Gunicorn, alternative Waitress (licences MIT and ZPL 2.1 from memory, UNVERIFIED; the builder reads the licence files). TLS, connection limits and rate limits before authentication sit in front, in the client's own ingress or load balancer (option (a) of D0); the kit renders the server's own limits (workers, timeouts, request-line and header caps) from config. Unknown and unsigned requests get one status (AK-G2 PENDING LEAD 4 (vii), `tickets/AK-G2.md:196`).

**D5. Clock skew (operator note 1).** All machines of one deployment must keep their clocks within 60 seconds of each other (`operator-notes.md:3`). The smoke test compares each part's clock with the database clock and refuses more than `deploy.max_clock_skew_s` (default 30, allowed range 1-30): if every machine is within 30 s of the one database clock, any two machines are within 60 s of each other. Time sync itself is the client platform's job (contract line K2). The webhook signature window (`approvals/hmac_v0.py:19`, 300 s) is a separate, looser bound.

**D6. Service time (contract note 1).** `contract-terms-notes.md:3`: the client contract must require a person to answer a chat handed to the queue in less time than `conversations_days`. The deployment record (runbook step R9) writes the contract's service time and the configured `conversations_days` side by side, and the operator does not start the `app` part until the service time is the shorter. No code checks this (the contract is not in the config); said plainly in O8.

## Rules stated once (all sub-PRs)

- **What AK-G16 is and is NOT.** It IS: the parts (D1), the image template, the Kubernetes renderer and the policy lint (D2), the cloud-neutral rights list, the smoke test (D3), the WSGI door adapter (D4), and a runbook. It is NOT: a cloud adapter (v1.1 rows V1-V4); creation of clusters, databases, key stores, buckets or networks in any cloud; a container registry, image signing or the client's CI/CD (PENDING LEAD 8); K7's in-cluster network enforcement beyond the NetworkPolicy files (PENDING LEAD 5 (ii)); the client-facing security-review pack from bible topic 36 (GAPS G16 names it LAPTOP work; not in this ticket).
- **Least privilege by construction (BRIEF rule 11).** Deny-all start: every part starts with no secret, no role, no cloud right, no network. Read-only default: the only writes are the database writes `GRANTS` already gives (`migrate.py:46-68`) and the audit part's locked-object put. Exact names: every secret, role, key, bucket and prefix is a config reference; no `*` anywhere in our rights list, our RBAC (the kit renders no Kubernetes RBAC rights at all; service-account tokens are not mounted) or our network policies (no "allow all"). One identity per part; no part can widen itself.
- **Secrets only through the secrets kind (BRIEF rule 3).** In the neutral default each part's pod mounts only its own secret files (mode 0400) and the config names them; the kit renders secret REFERENCES, never a Secret object with data, never an environment value. No secret in the image, the rendered files, the IaC, the tests or the docs; test values are built from parts at run time; placeholders such as `<SECRET>` only.
- **No spend, no live cloud call in tests (BRIEF rule 4).** Every test is plan-only: render to a temporary folder, parse the YAML, lint it. No `kubectl`, no cloud SDK call, no image push; CI has no internet (`plan-v3.md:67`). The fake model only (order 27 item 55).
- **Database grants come from `migrate.py`, never copied.** The renderer reads the role keyword names from `inspect.signature(store.migrate.migrate)` and maps each to a configured login name; a new role keyword with no mapping fails the render (row R3). Logins are created by a person with the database's admin login once, from the runbook (step R3); our code never holds that login.
- **Cut surface (order 8).** Cut from revision 1 before review: Helm and Kustomize, any cloud adapter, a bundled egress proxy, image signing, a `deploy apply` command (we never apply), a separate audit database role, a health web endpoint (Kubernetes runs `smoke --part app` as its start-up probe instead, UNVERIFIED that the probe timeout suffices), cron syntax beyond the one schedule string per part.
