## Words used in this ticket (one meaning each)
- **environment read**: code that reads, writes, lists or tests for the process environment variables, or starts a process or native call that can do so. The closed list is in field "Interface", item L1.
- **secrets kind**: the `secrets` capability in `TABLE` (`backends/table.py:387`), and the modules its factories name.
- **secret holder**: a module that holds a secret provider or the executor. Today that is the set `SECRET_HOLDERS` in `tests/test_repo_rules.py:131-142`.
- **wiring**: code that builds backends from a config and hands each factory a bound `resolve`. Today: `app.py`, `backends/factory.py`, `backends/platform_secrets.py`, `backends/builtin.py`, plus `cli.py` and `k1b/audit_sink.py` (fact 3).
- **ambient identity** (also called "workload identity"): a cloud SDK signs in with whatever its default chain finds: environment variables first, then files, then the machine's attached role (precedence from memory: UNVERIFIED). Examples are the AWS default chain, Azure `DefaultAzureCredential` and Google Application Default Credentials. Our code passes no credential to the SDK in that case.
- **identity** of a kind: the kind of principal it acts as toward an outside system, one or more words from a closed list of six (field "Interface", item K). **Rights** (the operations a kind needs) are not declared in v1 (pending lead 9): they move to V3.

## Decisions taken in this ticket
- **D1 Ambient identity is pinned, and (pending lead 2) refused when credential variables are present.** The lint checks three things:
  - every explicit-key SDK constructor passes `api_key=` that is not the literal `None`;
  - every ambient-identity constructor sits at one of the 13 pinned sites, each tied to its (capability, kind) with a reason;
  - a new, moved or stale site fails.
  It does NOT rewrite the 13 sites to a narrower credential class: that would be 13 behaviour changes on cloud kinds that cannot be run here. **(pending lead 2)** On top of the pins, it adds the start-up refusal in interface item N2: in pilot and prod, a known ambient-credential variable that is PRESENT stops start-up. What stays open, in plain words: **credential FILES (for example a shared AWS credentials file or a developer's cloud login) are not checked, so a pilot or prod machine with such a file can still sign a cloud SDK in as that person.** That is v1.1 row V1. If the lead refuses N2, the open hole is the one revision 1 stated: "a key left in the environment of a pilot or prod process is used before the attached role, and no v1 code stops that".
- **D2 (pending lead 3) The identity declarations live in `tests/test_kind_identity.py`, not in a src module and not as `Entry` fields.** Keys are (capability, kind) strings. No src file and no `TABLE` line changes for P6b2-b. Nothing at run time read the declarations in revision 1 either.
- **D3 `demos/` is out of the lint in v1.** Demos are dev-only demonstrations, and P8a re-pins them. The evidence prints their reads (report only). v1.1 row V2.
- **D4 No fallback to `HADAVIN_MIGRATE_DSN`.** With no `migrate_credential_ref`, `migrate` refuses, and the message names the new field and says the variable is no longer read. Reading the variable only to warn would itself be the banned read. This is a semantic change for operators (see Rollback).
- **D5 Test files:** `tests/test_env_lint.py`, `tests/test_secrets_import.py` and `tests/test_migrate_credential.py` (P6b2-a), and `tests/test_kind_identity.py` (P6b2-b). `tests/test_repo_rules.py` and `tests/test_lockin_guard.py` are imported from, never edited.
- **D6 Rebase rule (R1-ADV-11).** After each predecessor rebase, the builder re-runs E1, E7 and S1. A NEW environment read, ambient site or holder import is NOT added by the builder: it goes to the lead as a numbered line in `questions-for-lead.md`, with a reason. A REMOVED one removes its entry. A new `TABLE` kind fails I1 until its declaration row is added: (`redactor`, `regex`) -> {`none`} from P5c-1 is known now.

- **Problem in plain words:** The core reads credentials in two ways. The right way: a backend names a secret in its config, and the secrets kind reads it. The wrong way: code reads an environment variable directly. One real secret takes the wrong way today: the migration role's database DSN (`cli.py:322`). Nothing stops a new one, because the existing import rules only list what some packages may NOT import, and no rule looks at environment reads at all. Kinds also do not say which kind of identity they use. This package does five things:
  - it bans direct environment reads outside two secrets modules, with a short allow-list where each entry has a reason;
  - it pins which files may hold a secret provider;
  - it moves the migration DSN behind the secrets kind, with checks that the runtime cannot reach it;
  - it makes every kind declare its identity, with a test that fails when one is missing or wrong;
  - (pending lead) it refuses pilot and prod start-up when cloud key variables are present.
