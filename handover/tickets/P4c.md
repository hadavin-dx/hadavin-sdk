Words used in this ticket (one meaning each):
- **wall**: a spending limit that stops further model calls. Three walls exist: the run wall (`AgentRecord.max_run_usd`, the most one run may spend), the daily wall (`budget_usd.daily`, per agent, per UTC day) and the monthly wall (`budget_usd.monthly`).
- **reserve**: set aside, before a model call starts, the most that call could cost, so the total can never pass a wall. **settle**: after the call, replace the set-aside amount by the real cost. **release**: give the set-aside amount back because nothing was sent. **hold**: P4b1's name for a reserve that is open.
- **metered model object**: P4b1-b's `MeteredLLM`, a wrapper with the same `chat` signature as the model kind, which reserves before every call and settles after it. **scope**: the `with metered.scope(agent_id, run_id=...)` block that tells the wrapper which agent and run pay for the calls made inside it.
- **overshoot**: a model call whose reported cost is above the amount reserved for it (the estimate was wrong).
- **alert**: one message to a named person that a daily or monthly wall was hit. It is not the log line and not the audit row; those are written as well.
- **period**: what an alert is about: the day (daily wall) or the first day of the month (monthly wall). The **previous period** is yesterday, or last month.
- **notice**: the three things written when a run meets a daily or monthly wall: the `limits/wall` audit row, the `budget wall` ERROR log line and (daily and monthly walls only) the alert. One helper writes them (rule 6).
- **deliverable**: an unsent alert row whose agent is still in the registry and still names a person in `alert_to`. Only a deliverable row is sent or counted as waiting.
- **prompt bound**: P4b1-b's refusal of any model call whose counted size passes 100,000 bytes (`METER_MAX_PROMPT_TOKENS` times `PROMPT_BYTES_PER_TOKEN`; each document byte counts 3, `P4b1.md:261-264`, BN-10). It raises `ValueError` before any money is set aside.

## Rules stated once (both sub-tickets)
1. **Money type and units.** Storage and caps stay exact `Decimal` USD with at most 6 decimal places at the Store boundary (A9 B1). The meter works in integer micro-dollars and rounds UP once per call (P4b1). **P4c never turns a `Reply.cost_usd` into a `SpendMicro`; the only conversion is P4b1-b's, rounded up once** (`P4b1.md:266`, `SpendMicro.ceil_cost` at `:94`; the wrapper never reads `Reply.cost_usd`, mutant W31). P4c uses P4d's validators (`check_usd`, `check_cap`, `check_id`) for the registry and does no money arithmetic except comparing caps in tests.
2. **One error rule on every refusal path (fail closed).** Any exception that stops the cap check from being answered (store unreachable, busy, missing table or grant, damaged counter, a prompt P4b1-b's prompt bound refuses, a route or price the wrapper refuses, a count `request_bound` refuses, no open scope) means NO model call is made and the run ends `NEEDS_PERSON limits_unavailable` (main call; inside the judge call a non-`MeterError` ends `guard_unavailable`, `_screen` below). A document over `MAX_DOCUMENT_BYTES` never reaches this rule: the existing size check refuses it first as `document_too_large` with its card (P4c-2 `defaults.py`, PENDING LEAD 25). `MeterUnavailable(code)` maps to `limits_unavailable` and the code is logged (a fixed word, never exception text). Nothing is resolved by "try the call anyway".
3. **The alert never decides anything.** The run state is written first; the alert is sent after it. An alert failure never changes the run state, never raises out of `handle`, never blocks the next run. A failed alert is logged at ERROR, audited, kept as an unsent claim and retried (P4c-1).
4. **ONE total order for the new SQL.** P4c-1 runs ONE SQL statement per method call. `claim_wall_alert` picks one of two statements from its ARGUMENTS, never from a read of the row, and each statement touches only the one `wall_alerts` row it names. It never runs while a hold is open: `claim_wall_alert` and `mark_wall_alert_sent` are called by the alerter after `chat` has returned or raised, never from inside the meter's exit callback (T11(e)). The reserve keeps P4d's order.
5. **Wording for people.** Every text a person reads is built from a fixed template, contains only an agent name, a limit in US dollars, a day or month, a zone name, a reason code and the plain words below, never text from a model, a tool, a document or an exception. Times are UTC with the IST equivalent. One word keeps one meaning: "limit", not "cap", "budget" and "ceiling" mixed.
6. **Outcomes of a refused or mis-booked model call.** The same table is the test table. Every way into a daily or monthly wall goes through ONE notice helper, `_wall_notice(run, reasons, day)` in `agent_loop.py`: the `limits/wall` audit row (guarded: a failing write is logged, never raised), then the `budget wall` ERROR log line, then `Hooks.wall_alert` for the daily and monthly walls only. (c) The gate's `blocked()` read before `authorize` (`agent_loop.py:669-703`) keeps its existing state `DENIED limits.<reason>` (the `_to` at `:702-703`, unchanged), then calls `_wall_notice(run, blocked, spend_day())` when `blocked[0]` is `daily_budget` or `monthly_budget`. # P4c-1: alert ledger in the store (one table, three methods, contract rows)

- Package id and name: P4c-1, durable "alert at least once, normally once, per agent per wall per period" marker (`wall_alerts`) so the alert is not repeated by every run or every process, and an unsent alert can be found and retried within its own period and the one after it.
- Path class: money-adjacent (decides whether a person is told). Extended review (no round cap): yes; Tier A.
- Depends on (merged first): P4d (all five pull requests: `@_writes`, `StoreBusy`, `check_*` validators, `require_backend`, `store_pair`, `pg_driver`, `connect_runtime`), P2a-1 (store files order), P3a (migration numbering).
- Problem in plain words: When a wall is hit, every later run of that agent that day hits it again. Without a durable marker the person would get either one message per run (a flood) or, with an in-memory flag, one per process and again after every restart; and if the process dies between "decide to alert" and "alert sent", the message is lost. The store has no operation for "do this once, and remember whether it was done" (checked: `store/protocol.py` has none; `tick_state` is an unconditional upsert). The promise is "at least once, normally once" within a bound: an unsent alert is retried for the rest of its own period plus one more period, and the tick is red for all of that time; a crash between sending and marking, or a send slower than the retry window, can repeat the message. After that bound, only the ERROR log and the `failed` audit rows remain (PENDING LEAD 20, CONFIRMED by order 24 item 41).

- Problem in plain words: Each agent may set a limit on what ONE run may spend (`max_run_usd`), and pilot and production configurations must set it. Today nothing stops a run before a call that would pass the limit: the check runs after the money is spent, so one long call can overshoot without bound, and several runs at once can each pass the daily check and together overshoot the day. When a daily or monthly limit is reached, nothing tells a person: runs just end quietly. This package puts the one shared model object behind the meter, so every call on the run path (the run's own call and the paid injection check) sets the money aside first; it ends the run and shows a person a card when the meter reports a call that cost more than its largest possible cost or could not be booked; and it tells one named person, at least once and normally once, per day or month. One side effect needs saying: the meter refuses any call whose counted size passes 100,000 bytes, and each document byte counts 3, so a document above about 27 KB could never be sent. Today a run accepts documents up to 256 KiB. This package lowers that limit so such a document is refused at the start with its own card ("document too large"), instead of failing later under a wrong reason.
