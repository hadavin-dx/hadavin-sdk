Words used in this ticket (one meaning each):
- **wall**: a spending limit that stops further model calls. Three walls exist: the run wall (`AgentRecord.max_run_usd`, the most one run may spend), the daily wall (`budget_usd.daily`, per agent, per UTC day) and the monthly wall (`budget_usd.monthly`).
- **reserve**: set aside, before a model call starts, the most that call could cost, so the total can never pass a wall. **settle**: after the call, replace the set-aside amount by the real cost. **release**: give the set-aside amount back because nothing was sent. **hold**: P4b1's name for a reserve that is open.
- **metered model object**: P4b1-b's `MeteredLLM`, a wrapper with the same `chat` signature as the model kind, which reserves before every call and settles after it. **scope**: the `with metered.scope(agent_id, run_id=...)` block that tells the wrapper which agent and run pay for the calls made inside it.
- **overshoot**: a model call whose reported cost is above the amount reserved for it (the estimate was wrong).
- **alert**: one message to a named person that a daily or monthly wall was hit. It is not the log line and not the audit row; those are written as well.
- **period**: what an alert is about: the day (daily wall) or the first day of the month (monthly wall). The **previous period** is yesterday, or last month.

## Rules stated once (both sub-tickets)
1. **Money type and units.** Storage and caps stay exact `Decimal` USD with at most 6 decimal places at the Store boundary (A9 B1). The meter works in integer micro-dollars and rounds UP once per call (P4b1). **P4c never turns a `Reply.cost_usd` into a `SpendMicro`; the only conversion is P4b1-b's, rounded up once** (`P4b1.md:234`, `SpendMicro.ceil_cost`). P4c uses P4d's validators (`check_usd`, `check_cap`, `check_id`) for the registry and does no money arithmetic except comparing caps in tests.
2. **One error rule on every refusal path (fail closed).** Any exception that stops the cap check from being answered (store unreachable, busy, missing table or grant, damaged counter, a prompt the sizing refuses, no open scope) means NO model call is made and the run ends `NEEDS_PERSON limits_unavailable`. `MeterUnavailable(code)` maps to `limits_unavailable` and the code is logged (a fixed word, never exception text). Nothing is resolved by "try the call anyway".
3. **The alert never decides anything.** The run state is written first; the alert is sent after it. An alert failure never changes the run state, never raises out of `handle`, never blocks the next run. A failed alert is logged at ERROR, audited, kept as an unsent claim and retried (P4c-1).
4. **ONE total order for the new SQL.** P4c-1 adds one statement per method, each touching only the one `wall_alerts` row it names. It never runs while a hold is open: `claim_wall_alert` and `mark_wall_alert_sent` are called by the alerter after `chat` has returned or raised, never from inside the meter's exit callback (T11(e)). The reserve keeps P4d's order.
5. **Wording for people.** Every text a person reads is built from a fixed template, contains only an agent name, a limit in US dollars, a day or month, a zone name, a reason code and the plain words below, never text from a model, a tool, a document or an exception. Times are UTC with the IST equivalent. One word keeps one meaning: "limit", not "cap", "budget" and "ceiling" mixed.
6. **Outcomes of a refused or mis-booked model call.** The same table is the test table. The two ways into a daily or monthly wall both go through ONE helper, `_wall_stop(run, reasons, day, cited)` in `agent_loop.py`: (a) the `blocked()` pre-check in `_limits_stop` (below P2a-1's guard; `day` = `spend_day()`) and (b) an `OverBudget` refusal from the metered model object (`day` = `OverBudget.day`). `_wall_stop` handles only `daily_budget`, `monthly_budget` and `limits_unavailable`: it writes the run state FIRST, then the `limits/wall` audit row (guarded: a failing audit write is logged, never raised), then the `budget wall` ERROR log line, then calls `Hooks.wall_alert` for the daily and monthly walls only. The run wall keeps its existing `_abstain(..., "run_budget", cited)` call inside `_limits_stop`, and a `run_budget` refusal from the wrapper goes through the same audit-and-abstain lines. One mapper, `_meter_refused(run, exc, cited) -> Run`, sends each refusal to the right line of this table. The two meter signals (overshoot, settle failure) are set by P4c-2 on `Limits` in `app.build`, and end only the run that made the call.
