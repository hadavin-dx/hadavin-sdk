Words used in this ticket (one meaning each):
- **wall**: a spending limit that stops further model calls. Three walls exist: the run wall (`AgentRecord.max_run_usd`, the most one run may spend), the daily wall (`budget_usd.daily`, per agent, per day in the meter's day zone) and the monthly wall (`budget_usd.monthly`).

- **period**: what an alert is about: the day (daily wall) or the first day of the month (monthly wall).

## Rules stated once (both sub-tickets)
1. **Money type and units.** Storage and caps stay exact `Decimal` USD with at most 6 decimal places at the Store boundary (A9 B1). The meter works in integer micro-dollars and rounds UP once per call (P4b1). P4c passes what P4b1 and P4d define, uses P4d's validators (`check_usd`, `check_cap`, `check_id`, `P4d.md` lines 72, 73, 107) and never does money arithmetic of its own except comparing caps in tests.
2. **One error rule on every refusal path (fail closed).** Any exception that stops the cap check from being answered (store unreachable, busy, missing table, missing grant, damaged counter, a prompt the sizing function refuses, an estimate that cannot be computed) means NO model call is made and the run ends `NEEDS_PERSON` with reason `limits_unavailable` (the code `agent_loop.py:672` already uses). The meter's `MeterUnavailable(code)` maps to `limits_unavailable` and the code is logged (a short fixed word, never exception text). A cap refusal ends the run with the reasons in the table below. Nothing is ever resolved by "try the call anyway".
3. **The alert never decides anything.** The refusal is final first (the run state is written); the alert is sent after it. An alert failure never changes the run state, never raises out of `handle`, never blocks the next run. A failed alert is logged at ERROR level, audited, kept as an unsent claim and retried (below).
4. **ONE total order for the new SQL.** P4c-1 adds one statement per method, each touching only the single `wall_alerts` row it names, so it takes one row lock and no other lock. It is never run inside a transaction that holds a reservation, counter or run lock: `claim_wall_alert` and `mark_wall_alert_sent` are called by the alerter after the hold's reserve returned (refused or not), never inside it. The reserve itself keeps P4d's order (reservation, counter rows, run, day, month).
5. **Wording for people.** Every text a person reads (alert, card label, log line that names a wall) is built from a fixed template, contains only an agent name, a limit in US dollars, a day or month, a zone name and the plain words below, and never any text written by a model, a tool, a document or an exception. Times are given in the zone with the IST equivalent when the zone is UTC. One word keeps one meaning: "limit", not "cap", "budget" and "ceiling" mixed.
6. **Outcomes of a refused model call.** The same table is the test table. The model call count for the step is zero in every row. There are TWO ways into a wall and both go through ONE helper, `_wall_stop(run, which, day)` in `agent_loop.py`: (a) the `blocked()` pre-check in `_limits_stop` (after P2a-1's guard) and (b) a refusal from `Limits.hold` (`OverBudget`). `_wall_stop` writes the run state FIRST, then the `limits/wall` audit row (guarded: a failing audit write is logged, never raised), then the `budget wall` ERROR log line, then calls `Hooks.wall_alert` for the daily and monthly walls only. A wall that is hit by either entry path is audited, logged and alerted. The overshoot of a call whose real cost passed its hold is NOT a P4c outcome (see PENDING LEAD item 14).

# P4c-1: alert ledger in the store (one table, three methods, contract rows)

- Package id and name: P4c-1, durable "alert at least once, normally once, per agent per wall per period" marker (`wall_alerts`) so the alert is not repeated by every run or every process, and an unsent alert can be found and retried within its period.
- Path class: money-adjacent (decides whether a person is told). Extended review (no round cap): yes; Tier A.
- Depends on (merged first): P4d (all five pull requests: P4d gives `@_writes`, `StoreBusy`, `check_*` validators, `require_backend`, `store_pair`, `pg_driver`, `connect_runtime`), P2a-1 (store files order), P3a (migration numbering). Reviewers: correctness + adversarial (fresh agents; diff, this sub-ticket and the evidence only).
- Problem in plain words: When a wall is hit, every later run of that agent that day hits it again. Without a durable marker the person would get either one message per run (a flood) or, with an in-memory flag, one per process and again after every restart; and if the process dies between "decide to alert" and "alert sent", the message is lost. The store has no operation for "do this once, and remember whether it was done" (checked: `store/protocol.py` has none; `tick_state` is an unconditional upsert with no compare-and-set). The promise is "at least once, normally once": a crash between sending and marking, or a send slower than the retry window, can repeat the message; nothing is ever lost silently.
- Source of the code (MANIFEST ids, source repo, commit sha) and what is NOT taken: nothing promoted; written new in the style of P4d-b's reservation methods. NOT taken: PR #48's spend-cap 429, PR #49's hold table, the meter (P4b1), pruning (no owner in v1, below).
- Target module and path in `src/hadavin_sdk/`: `store/protocol.py`, `store/memory.py`, `store/postgres.py`, `store/migrate.py` (one `GRANTS` row), `store/migrations/<next free number>_wall_alerts.sql`, `models.py` (one row model).
- Interface (names, argument and return types, errors):
  - `WallAlert` row model in `models.py` (a `Shape`, carries `schema_version`): `agent_id: str`, `wall: Literal["daily","monthly"]`, `period: date` (the day for `daily`; the first day of the month for `monthly`), `status: Literal["claimed","sent"]`, `claimed_at: datetime`, `sent_at: datetime | None`. (There is no attempt counter: a retry is bounded by the PERIOD, not by a count.)
  - `claim_wall_alert(agent_id: str, wall: str, period: date, *, today: date, retry_after_s: int) -> bool`. `today` is the day from the ONE day function (PENDING LEAD item 16; the caller passes the hold's day or the meter's current day); the store compares no clock of its own for periods. True means THIS caller must now send the alert. Rules: `period` older than the current period of that wall (for `daily` before `today`; for `monthly` before the first of `today`'s month): False, nothing written (a past period is never claimed). No row: insert `claimed`, True. Row `sent`: False. Row `claimed` and younger than `retry_after_s` by the DATABASE clock (memory: its injected wall-time clock): False (someone else is sending, or just did). Row `claimed` and older than `retry_after_s`: `claimed_at` = now, True (a retry). `wall` not in the closed set, a `monthly` period that is not the first of a month, a `period` newer than the current period, `retry_after_s` outside 30 to 86400, a non-`date`, or a `bool` where an int is expected: `ValueError`, nothing written. Errors: `ValueError`, `StoreBusy`; driver errors for an unreachable store or missing table/grant pass through (P4d error rule).

- Package id and name: P4c-2, `max_run_usd` enforced before the call on the run path through `Limits.hold` (run, day and month caps in one reserve); the judge call held the same way; refusals as in rule 6 on both entry paths; a channel-backed once-per-period alert; a retry step in the tick.

- Problem in plain words: Each agent may set a limit on what ONE run may spend (`max_run_usd`), and pilot and production configurations must set it. Today nothing stops a run before a call that would pass the limit: the check runs after the money is spent, so one long call can overshoot without bound, and several runs at once can each pass the daily check and together overshoot the day. And when a daily or monthly limit is reached, nothing tells a person: runs just end quietly. The bible says to set the amount aside before the call and to fail loudly at the wall with a log line and a message to a person. This package makes the run limit a real limit, routes the day and month limits through the same set-aside step (for the run's call AND for the paid injection check), and tells one named person, at least once and normally once, per day or month.
