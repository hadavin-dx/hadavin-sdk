## Rules stated once (both sub-tickets)
1. **Money type and units.** Storage and caps stay exact `Decimal` USD with at most 6 decimal places at the Store boundary (A9 B1). The meter works in integer micro-dollars and rounds UP once per call (P4b1). P4c passes `Decimal` caps and amounts, uses P4d's validators (`check_usd`, `check_cap`, `check_id`; PENDING P4d rev 5 for exact names) and never does money arithmetic of its own except comparing caps in tests.
2. **One error rule on every refusal path (fail closed).** Any exception that stops the cap check from being answered (store unreachable, busy, missing table, missing grant, damaged counter, an estimate that cannot be computed) means NO model call is made and the run ends `NEEDS_PERSON` with reason `limits_unavailable` (the code `agent_loop.py:672` already uses). A cap refusal ends the run with the reasons in the table below. Nothing is ever resolved by "try the call anyway".
3. **The alert never decides anything.** The refusal is final first (the run state is written); the alert is sent after it. An alert failure never changes the run state, never raises out of `handle`, never blocks the next run. A failed alert is logged at ERROR level, audited, kept as an unsent claim and retried (below).
4. **ONE total order for the new SQL.** P4c-1 adds one statement per method, each touching only the single `wall_alerts` row it names, so it takes one row lock and no other lock. It is never run inside a transaction that holds a reservation, counter or run lock: `claim_wall_alert` and `mark_wall_alert_sent` are called by the alerter after the reserve call returned (refused or not), never inside it. The reserve itself keeps P4d's order (reservation, counter rows, run, day, month).
5. **Wording for people.** Every text a person reads (alert, card label, log line that names a wall) is built from a fixed template, contains only an agent name, a limit in US dollars, a UTC day and the plain words below, and never any text written by a model, a tool, a document or an exception. Times are given in UTC with the IST equivalent. One word keeps one meaning: "limit", not "cap", "budget" and "ceiling" mixed.
6. **Outcomes of a refused model call** (the same table is the test table). The model call count for the step is zero in every row.

# P4c-1: alert ledger in the store (one table, three methods, contract rows)

- Package id and name: P4c-1, durable once-per-day alert marker (`wall_alerts`) so the alert is sent once per agent per wall per day across processes and restarts, and an unsent alert can be found and retried.
- Path class: money-adjacent (decides whether a person is told). Extended review (no round cap): yes; Tier A.
- Depends on (merged first): P4d (all its pull requests; P4d rev 5 gives `@_writes`, `StoreBusy`, `check_*` validators, `require_backend`, `store_pair`, `pg_driver`), P2a-1a (store files order), P3a (migration numbering). Reviewers: correctness + adversarial (fresh agents; diff, this sub-ticket and the evidence only).
- Problem in plain words: When a wall is hit, every later run of that agent that day hits it again. Without a durable marker the person would get either one message per run (a flood) or, with an in-memory flag, one per process and again after every restart; and if the process dies between "decide to alert" and "alert sent", the message is lost. The store has no operation for "do this once, and remember whether it was done" (checked: `store/protocol.py` has none; `tick_state` is an unconditional upsert with no compare-and-set).
- Source of the code (MANIFEST ids, source repo, commit sha) and what is NOT taken: nothing promoted; written new on ce70eb5 in the style of P4d-b's reservation methods. NOT taken: PR #48's spend-cap 429, PR #49's hold table, the meter (P4b1), pruning and the maintenance identity (P4b2).
- Target module and path in `src/hadavin_sdk/`: `store/protocol.py`, `store/memory.py`, `store/postgres.py`, `store/migrate.py` (one `GRANTS` row), `store/migrations/<next free number>_wall_alerts.sql`, `models.py` (one row model).

- Package id and name: P4c-2, `max_run_usd` enforced before the call on the run path through the meter's reserve with a run cap; day and month walls through the same reserve; refusals as in rule 6; alert sink interface, channel-backed default, once-per-day alert, retry step in the tick.

- Problem in plain words: Each agent may set a limit on what ONE run may spend (`max_run_usd`), and pilot and production configurations must set it. Today nothing stops a run before a call that would pass the limit: the check runs after the money is spent, so one long call can overshoot without bound, and several runs at once can each pass the daily check and together overshoot the day. And when the daily limit is reached, nothing tells a person: runs just end quietly. The bible says to set the amount aside before the call and to fail loudly at the wall with a log line and a message to a person. This package makes the run limit a real limit, routes the day and month limits through the same set-aside step, and tells a named person once per day.
