## Words used here (plain meaning, once)
- **Spelling variant**: one of the at most three ways the fold reads a text (for example: Greek "ypogegrammeni" U+0345 dropped, or read as an iota; or the look-alike table applied before the case fold).
- **Check name** (code: "key"): the text the fold makes from one reading. `identity_key` is one check name; `identity_keys` is all of them.
- **View**: one reading of a text that a scan looks through. `fold_views` and `squeeze_views` give every view; `fold`, `squeeze` and `identity_key` give ONE reading.
- **Spacing marks**: here always the three Unicode categories Mc (spacing combining mark, for example the Devanagari visarga U+0903), Lm (modifier letter, for example U+02B0, a small raised h) and Sk (modifier symbol, for example `^`).
- **Marks-dropped text**: the raw text with every spacing mark removed, before any normalisation.
- **DENY check**: `could_be_same_person` (and the `LOOKALIKE` verdict of `allow_equal`, which calls it). It refuses when two names could be the same person. Matching too much is the safe side; matching too little lets a person approve their own request.
- **Ban rule**: a ruff lint setting (`banned-api`, error code `TID251`) that makes `ruff check` fail when code imports or calls a named function.

### Item 6 (ORDER 175): the same-class fix at the textnorm choke point

**Bug class (named):** a reader that must match a name or a protected value reads ONE spelling of it (`fold`, `squeeze`, `identity_key`, or its own `unicodedata.normalize`) instead of every view, so a character that this one reading keeps hides the value. Here the hiding characters are spacing marks. Standards: UTS #39 section 4 (compare skeletons after removing what does not change the look); UAX #15 (NFKD turns some Lm into a plain letter, U+02B0 into `h`, so marks are removed before NFKD).

**What is wrong today (reproduced on `bf955e9`, Python 3.13.18, Unicode 15.1.0):** `"ali" + U+0903 + "ce"`, `"al" + U+02B0 + "ice"` and `"ali^ce"` are NOT "could be the same person" as `alice` (`allow_equal` DIFFERENT) and `has_mixed_script` is False for all three; `squeeze_views` and `fold_views` already find all three. Also found by this revision (same class, mixed-script signal): `"ра^ypal"` (Cyrillic "ра", `^`, Latin "ypal") is NOT flagged by `has_mixed_script`, because the `^` splits the word in two before the script check.

**F6-1 (DENY check, ACCEPTED by ORDER 177 q387).** `_keys` (textnorm.py:765-769) builds its check names with `_views(raw, casefold=True, collapse_ws=True, marks_dropped=True)`. `identity_keys` returns at most 6 check names: the spelling variants of the raw text, then those of the marks-dropped text, repeats removed (`_views` already removes them), each with the `key_tag()` prefix like today. `could_be_same_person` and `allow_equal` change through it only. `identity_key`, `fold`, `squeeze` and the views do NOT change.
- **Reversal stated plainly (for ticket, docstrings and CHANGELOG "behaviour change"):** ORDER 79 item 3 said a spacing vowel sign changes a name. That stays true for `identity_key`, `fold` and the spelling variants. It is reversed for the DENY check only: two names that differ only by spacing marks are now "could be the same person", so a person must look. Measured cost on `tests/fixtures/textnorm_names.json` with the real `_keys` change: Hindi 94 names, 4,371 pairs, 0 before, **2 after** (दीपक / दीपिका, सविता / स्वाति); Thai 64 names, 1 pair before and after (นิภา / นภา); Thai chosen pairs 15 names, 8 pairs before and after. The same over-match exists in every script that writes with Mc or Lm, measured on single examples: 佐々木 / 佐木 (U+3005, Lm), コーヒー / コヒ (U+30FC, Lm), Arabic محمد with and without the tatweel U+0640 (Lm), Thai ดีๆ / ดี (U+0E46, Lm). These hand-made lists are not a sample of real names; the rate on a real population is not known.
- **Empty check name:** a text made only of spacing marks (for example U+0903 alone) gets the check name `""` from its marks-dropped text, so it is "could be the same person" as any other text whose check name is empty (for example a lone zero-width space). Safe side; pinned in T6-2.
- **F6-1b (cost):** `_view_pairs` builds the marks-dropped variants only when the text holds a spacing mark (`_without_spacing_marks(raw) != raw`). The result is identical (repeats are removed today); without it the DENY check does all its work twice for every text. Measured on this machine (best of 3, Python 3.13.18; `could_be_same_person(x, x[::-1])` at the cap): distinct-characters row 1.63 s before, 1.45 s after F6-1; Greek-with-U+0345 row 0.60 s to 1.18 s; spacing-marks row 0.30 s to 0.61 s. The ceilings (8.0 s) still hold; F6-1b should bring the rows without marks back to their old time, and the perf evidence shows it.

**F6-2 (mixed-script signal; replaces the rev 2 text that the codebase review B2 showed unbuildable).** Inside `has_mixed_script` only:
1. Before NFKC, besides what is dropped today (Mn, Me, invisible characters, the micro and ohm signs), **remove every Sk character**. Sk has no script; removing it joins the two halves of a word it split, the same rule that already applies to invisible characters. This also covers the compatibility Sk that NFKC would turn into a space (U+00B4 in `"ра" + U+00B4 + "ypal"`).
2. **Word split:** a word is a maximal run of characters that are alphanumeric, `_`, or **Mc**. So a spacing mark no longer splits a word (today `\w+` splits at U+0903).
3. **Rule (a), unchanged:** a word with a Latin letter and a letter of a look-alike script (`_NON_LATIN_SCRIPTS`) is mixed.
4. **Rule (b), new (mark-script rule):** a word is mixed when it holds a Latin letter AND an Mc whose script group (`_script_of`) is not `LATIN` and is the group of no letter in the same word. So `"ali" + U+0903 + "ce"` and `"iPhone" + U+093E` are flagged (a Devanagari sign glued to Latin letters with no Devanagari letter); `"Ramesh" + "जी"` is not (the sign belongs to the Devanagari letter in the word); `"राम"` is not (no Latin letter). Every one of the 452 Mc code points flags in `"ali" + mark + "ce"` (prototype count: 0 misses), and none flags in a word made of a letter of its own group plus the mark (0 code points; 54 of the 56 Mc groups have a letter, MUSICAL and VIETNAMESE have none and flag only inside a Latin word).
5. **Mn and Me (U+0301, U+FE0F):** still removed before the split, as today, so they never flag. `"cafe" + U+0301`, `"café"`, `"naïve"`, `"ok" + U+FE0F`: False.
6. **Lm stance:** unchanged. Lm is a letter, so it is already inside its word. NFKC turns most Lm into their Latin letter (`"al" + U+02B0 + "ice"` becomes "alhice": Latin only, False); an Lm whose name starts with a look-alike script word (GREEK, CYRILLIC, ...) counts as that script (rule a, today); an Lm named "MODIFIER LETTER ..." that NFKC keeps counts as no script. An Lm never flags by itself. The DENY check (F6-1) is what catches an inserted Lm.
7. **Sk stance:** removed (step 1), never flags by itself; `"ali^ce"` and `"x^y"` are False. A new false flag is possible when a `^` or backtick sits between a Latin and a look-alike letter (`"x^α"` is now one word, flagged); fail-closed, accepted.
8. The docstring's "Honest limits" paragraph names rules (a) and (b), and that a Devanagari or other Mn sign (non-spacing) inserted into a Latin word is not flagged here (the fold drops it, so the DENY check catches it). The script DATA work of BN-14 (Runic, Tamil in the look-alike list) stays in P1b.
