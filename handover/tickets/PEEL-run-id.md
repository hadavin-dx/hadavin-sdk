# Package ticket PEEL-run-id: `run_id` keyword on `Runtime.handle` (lead ORDER 174 q382(1), "take the peel")

Short ticket (well under 250 lines). Source of the option: `tickets/AK-G2.md` BN-21 and round 1 resolve row ADV-22.

- Package id and name: PEEL-run-id (the peel of AK-G2-a item 6, first half)
- Path class: money (a second run for one message is a second model spend and a second possible action). Extended review (no round cap): yes
- Depends on (merged first): nothing. Base `origin/main` 0dabf1f. P5c and P4c-2 also edit `runtime/agent_loop.py`; they rebase onto this PR.
- Problem in plain words: Today `Runtime.handle` always gives a new run a fresh random id, so a caller cannot say "this message is run number X". The planned inbound door (AK-G2-a) needs to start a run with an id it chose (derived from the message id), so that a message handed in twice cannot start two runs: the store already refuses a second run with the same id. This PR adds only that keyword. It does not add the door, the receipt table or the "return the existing run" step; those stay in AK-G2-a.
- Source of the code: new, written against `agent_loop.py` at 0dabf1f. NOT taken: the idempotent return of an existing run (AK-G2 item 6, rows D2/D2b/D2c), `StartRun`, the ledger.
- Target module and path: `src/hadavin_sdk/runtime/agent_loop.py` (`Runtime.handle`, new error `InvalidRunId`), `src/hadavin_sdk/models.py` (`RUN_ID_PATTERN` next to `new_id`).
- Interface: `Runtime.handle(agent_id, principal_id, document, trigger_kind="event", trigger_ref="-", mapping=None, *, run_id: str | None = None) -> Run`. Keyword-only, so no existing positional call changes. `None` (default) = today's behaviour (`Run` default factory `new_id("run")`). A given id must match `RUN_ID_PATTERN` = `run-` plus exactly 32 lower-case hex characters (the shape of `new_id("run")`, and of AK-G2's `run_id_for`, 36 characters); otherwise `InvalidRunId` (a `ValueError`) is raised before anything is written. If a run with that id already exists, `store.create_run` raises `StaleState` (existing behaviour of both stores) and `handle` lets it propagate: nothing else is written (no "received" note, no redaction, no model call, no meter hold), because `create_run` is the first write. The result is a typed refusal, never a second run.
- Neutral default / alternative: not a kind; no external dependency.
- Files: CHANGE `agent_loop.py` (signature, validation, pass-through, docstring lines), CHANGE `models.py` (one compiled pattern), CREATE `tests/test_peel_run_id.py`, CREATE this ticket, CREATE `handover/studio-notes/bd-peel-report.md`, CHANGE `handover/ledger.md` (side finding rows).
- Existing core code reused (checked): `models.new_id`, `Run`, `store.create_run` refusal (`store/memory.py` and `store/postgres.py` raise `StaleState`), `Unqualified` pattern. No existing run-id validator exists (grep for `fullmatch`/`re.compile` in `models.py`, `store/`, `runtime/`: none for run ids), so one pattern is added beside `new_id`, the single place that makes run ids. `Run.run_id` itself is NOT tightened: stored rows and existing tests use other ids.
- Security and least-privilege notes: no new identity, right or secret. The closed pattern keeps a caller-chosen id from carrying path, SQL, log-forging or control characters into the store, audit notes and file names (the id is used in `call_id = f"{run_id}:{n}"`, audit rows and redaction-map keys). Money path: the same-id refusal is what stops a double spend.
- Side finding, `Run.trigger_kind` accepts only `event`/`schedule`/`user` (`models.py:94`); `"webhook"` fails validation. Decision: NOT fixed here. AK-G2 (item 6) calls `handle(..., trigger_kind="event", ...)` and says "a signed web request" is an `event`; its "Runs today" paragraph says "a trigger needs NO change to the run shape". The ticket does not allow a new kind, so a change here would go against the frozen ticket and the stored-row contract. Recorded in `handover/ledger.md` (BL-core-peel-001) as a lead decision.
