## Words used (plain meaning, one meaning each)

- **item**: one row in the queue that says "a person must look at this". It holds ids, a closed reason code, the people who could see it when it opened, its state and times. It NEVER holds message text, a body, a user id or an exception text.
- **subject**: the thing an item points to. Two kinds in v1: a **chat** subject (a conversation and the run of the exchange that was handed off, AK-G1) and an **inbound** subject (one received message at one generation, AK-G2).
- **queue reader**: a person (a principal of kind `person` in `principals.yaml`) listed in config as allowed to see the items of one tenant. Not the same as AK1's `readers` of a document. The item's `readers` field records the queue readers at the time it opened (PL18 (a), order 43: it is a record only, and the current config decides access).
- **claim**: a person takes an item for a limited time (the **lease**). While the lease is live, nobody else can claim it. **Release**: the holder hands the item back unfinished. (Revision 1's "assign", claiming for another person, is cut: row V15.)
- **close**: the holder ends the item with one **outcome** from a closed set. `closed` is the item's ONLY final state. A closed item never changes again.
- **reopen an item**: make a NEW item, round + 1, for the same subject, linked to the closed one. The closed item stays closed. This is NOT AK-G2's "reopen" of a receipt. To avoid one word with two meanings, this ticket calls AK-G2's action **re-run a message** (outcome `rerun`, which performs AK-G2's `reopen_inbound` update).
- **binding (content binding)**: a SHA-256 digest of the item's ids (never of text). A person who acts must send the binding of the item they saw, so an action can never land on another item or another round.
- **version**: a counter on the item that every write raises by exactly 1. Every write is a compare-and-set on it (the lease token rule of order 38 item 85 and order 39).
- **age**: now minus the time the item was opened. **Service time**: the time from opened to closed. The **service-time limit** (`queue.service_time_days`) is the number the client contract sets; it must be shorter than `retention.conversations_days` (`contract-terms-notes.md` item 1; order 39 item 2) and than `inbound.body_days`.
- **waiting item**: an item in state `open` or `claimed`. The **ceiling** (`queue.max_waiting_items`) is the most waiting items one tenant may have; above it a new item is refused loudly (`queue_full`), never dropped.
- **clock window**: the most that a stored time may differ from the database's own clock (`defaults.QUEUE_CLOCK_WINDOW_S`, 600 seconds). It bounds forged times; it does not replace the injected clock.
- **queue worker identity**: a NEW database role and connection (`queue_worker`) used only by the code that acts for persons (claim, release, close, reopen, re-run). The agent runtime never holds it.
- **re-run function**: the one database function `hadavin_queue_close_rerun` (PL15 (a), order 43) that closes an item with `rerun` and re-runs its message in one transaction. It is the only way to re-run a message.
- **re-run owner role**: the NOLOGIN database role that owns the re-run function, and nothing else (AK-G2 BN-24). Its name is given to `migrate` as a required argument, never written into code. No login role is a member of it. It is NOT the migration role.
- **decoy**: an item planted by someone holding the runtime connection, made to look like a real hand-off or a real waiting message, so that the real one is not seen. The insert trigger, the dedupe check and the collect-side comparison stop most decoys; the remaining case is stated in Security notes.
- **erased**: the subject's content was deleted by retention or by `forget_user` (owner rule R98). The item stays, holding ids only, and shows `subject_erased`.
- **pilot/prod**: a config whose `environment` is `pilot` or `prod`.
- **`<schema>`**: the store's schema name as P2a-1 merges it (UNVERIFIED); every relation in the re-run function and the queue triggers is written with it.
- Row ids: Q = queue core (AK-G15-a), N = inbound side (AK-G15-b), W = wiring (AK-G15-c), R = rollback rehearsal, V = later rows. Mutants M-a, M-b, M-c by sub-PR. INFORM decisions are I1-I14 (no test row uses the letter I).
- "UNVERIFIED" = not read in code or not run by me. "PENDING LEAD" = a lead or owner decision, my recommendation first; "NEEDS LEAD" marks those touching money, redaction, erasure, least privilege, tenant isolation or an owner rule. "INFORM" = my decision on my recommendation, final unless the lead says otherwise (order 23 item 4). "ANSWERED" = the lead decided it (the order is cited).

## The decision that shapes this ticket (INFORM I1, recommended; read before the fields)

Options for "durable queue of needs-a-person items" (options first, BRIEF-PREAMBLE rule 16):
- (a) **Recommended: our own store-backed queue** behind a small interface (`NeedsPersonQueue`), one table in the existing store (Postgres in pilot and prod, memory in tests), ids only, compare-and-set on every write, one final state, a lease, audit on every person action. It is the neutral, self-hostable default (it runs wherever the store runs). Tool ladder rung 7 (our own code): it decides who may act, binds the action to what the person saw, and can start a second paid run, so it is "the brain" (approval binding, audit, money) and stays in our tested code.
- (b) **The client's own ticketing or help-desk tool** (rung 2). Written outline, NOT built (row V1): a mirror adapter that copies each item to the client's tool as an ids-only ticket with a link, and copies "closed" back through AK-G2's signed door. Our table stays the record of state, because the client's tool cannot give our guarantees by itself: compare-and-set on a version, one final state that never changes, dedupe on the idempotency key, no text in the item, and erasure of the content without losing the item. **Trigger:** "a client already runs a ticketing or help-desk tool and chooses it in writing, after the options were shown in the quote". Cost and risk in plain words: the tool sees ids and links (not text); if the tool breaks or changes price, items still exist in our table; the quote and the contract's tool schedule say who carries that risk (options-first rule).
- (c) A workflow engine or a vendor queue service as the queue itself: rejected for the core (a new dependency for what one table and the tick already do; the same guarantee gap as (b)). Kept as the written alternative under the trigger of (b).

Why (a): it closes the BLOCKER (GAPS G15) for both consumers that exist on paper (AK-G1 hand-offs, AK-G2 waiting messages) with one table, adds no vendor, and is what the mirror of (b) would sit on. Confidence 80 percent; reversible (the interface lets a mirror be added without touching callers).

- **Problem in plain words:** When the core decides that a person must look at something, it only sets a run's state to `NEEDS_PERSON`. Nothing tells a person, nothing lists those runs except a query that returns the oldest 100 (`store/protocol.py:64-66`), nothing records who is looking at what or since when, and two people can work on the same thing at once. The chat package (AK-G1) hands conversations to a person through a hook that has no real implementation yet, and the inbound package (AK-G2) leaves messages waiting for a person with no way to list them, re-run them on a person's decision, or compare our received ids with the sender's ids (owner rule R368). As AK-G2's frozen text stood before build note BN-24, the agent's own database role could even re-run a waiting message by itself, with no person, item or record (R1-RES-1); BN-24 closes that, and AK-G15 builds the only door that remains. AK-G15 adds one durable queue: every needs-a-person event becomes exactly one item that survives a restart, a person claims it for a limited time, closes it with one recorded outcome, and may reopen it; only a person's close can re-run a message, at most a configured number of times; the item holds ids only, never message text, and erasure of the content always wins.
