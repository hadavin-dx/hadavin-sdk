## Rules stated once (all sub-tickets)
- Error rule: a refused WRITE is `StaleState` (conflict, replay of a closed reservation, lost compare-and-set) or `ValueError` (a value the store cannot hold). The money refusals are their own classes in `store/protocol.py`: `SpendCapExceeded` (attribute `which`: `"run"`, `"day"` or `"month"`) and `KillSwitchOn`; `StoreBusy` (below). An unreachable store, a missing table or a missing grant stays a driver error; `is_connectivity_error` classifies it and returns false when the driver error's `sqlstate` is one of `40001`, `40P01`, `55P03`, `57014` (the store answered; it is busy or the call was cancelled).
- Retry and timeout: the Postgres wrapper retries a whole write transaction at most 3 times, and ONLY on SQLSTATE `40001` and `40P01` (never `40003`: the write may have been applied), and never for add-style writes that have no key (`add_spend`, `add_cost`, `add_dead_letter`, `touch`): those raise `StoreBusy` at once. Every money transaction runs `SET LOCAL lock_timeout = <n> ms` (n from the new setting `PostgresSettings.lock_timeout_ms`, default 5000, allowed 100 to 60000: PENDING LEAD on the default); `55P03` becomes `StoreBusy`. `StoreBusy` (new, subclass of `StoreUnavailable`; mirrors PR #49 per memo-3, UNVERIFIED) means "busy, try later"; PENDING LEAD whether it should subclass `StoreUnavailable` (that makes `tick` exit 4).
- ONE total lock order (all five new methods, plus `add_spend` and `add_cost`, which each use a part of it in the same order): (1) the reservation row (insert, or the claim UPDATE); (2) the "ensure counter rows" inserts (`spend` day row, then `spend_month` row); (3) `UPDATE runs` (only with `run_id`); (4) `UPDATE spend` (day); (5) `UPDATE spend_month` (month). The kill-switch read is outside the order (it takes `FOR KEY SHARE`, which conflicts with no ordinary update). The ensure-rows step stays BEFORE the run lock: moved after it, a call could wait on another transaction's uncommitted counter insert while that transaction waits for the run row. `SpendCapExceeded.which` is reported in the same order: when several caps fail, the first failing one in the order run, day, month is named.
- Money type (A9 B1): storage stays NUMERIC (existing columns unchanged); no money-column migration (the new table in P4d-b is the migration A3 anticipated; it changes no existing column). At the Store boundary the NEW methods take exact `Decimal` USD with at most 6 decimal places and return amounts quantized to exponent -6; the meter converts integer micro-dollars and rounds UP once per call (R214). Old methods keep accepting 8 decimals (`test_store.py` stores `0.00108225`).
- Fail-before wording: a "fail-before" test fails on an ASSERTION on ce70eb5. A new-feature row that fails only because the method is missing is labelled "new feature; killed by mutants". A row that already passes on ce70eb5 is a "regression pin; killed by mutant Mx".

Boundary: a booking that leaves a total EXACTLY at its cap is allowed; one micro-dollar over is refused (`limits.blocked` refuses at `>=`, `limits.py:26`: two stated boundaries, both tested). Caps are supplied by the caller on every call; the store does not hold them (P4b1 owns where caps live).
  - "Same content" means exactly `(agent_id, day, reserved_usd, run_id)`, compared numerically. Replay of an id with the same content: if status is `open`, returns the stored row (`applied=False`) and books nothing; if status is `settled`, `released` or `expired`, raises `StaleState`. Same id with different content, including a different `day`, is `ReservationConflict` and changes nothing (the first reservation's day stands; a retry across midnight must reuse the original day). Caps are not stored and not part of identity. Ids are caller-generated random strings; agent B using agent A's id gets `ReservationConflict`.
  - `settle_spend(reservation_id: str, actual_usd: Decimal) -> SpendOutcome`. Validation (`check_usd`) runs FIRST on every call, so an invalid amount is `ValueError` even for a closed reservation. The first valid call for an `open` reservation sets status `settled`, stores `settled_usd`, and lowers the counters by `reserved - actual` (`applied=True`). A later valid call on a `settled` or `released` row returns the stored first result (`applied=False`; the second amount is ignored and documented as such). A valid call on an `expired` row may correct DOWNWARD ONCE: if `actual <= reserved` it sets status `settled`, stores `settled_usd = actual`, lowers the counters by `reserved - actual`, `applied=True` (the sweep's amount was a guess, a measured one replaces it); a second call returns that result. `actual_usd` of zero is allowed. Errors: `NotFound`; `ValueError` (invalid amount, or `actual > reserved` on an open or expired row: the row stays as it is and the meter settles at the reserved worst case). If a counter is lower than the amount to lower (damaged data), the whole transaction is rolled back, the row stays as it was, an error is logged and `StaleState` is raised; no silent clamp.
  - `release_spend(reservation_id: str) -> SpendOutcome`: validation first; an `open` or `expired` row becomes `released` (`settled_usd` stays NULL), the counters are lowered by the full reserved amount; later calls return the stored result. A release is distinct from a settle at zero (P4b2's billing contract needs both).

  - `list_open_reservations(agent_id: str | None = None, run_id: str | None = None, limit: int = 100) -> list[SpendReservation]` (read): open rows, oldest first, optionally filtered; `limit` by `check_int(1, 1000)`. This lets a run's cleanup find and release the reservations of a crashed call.
