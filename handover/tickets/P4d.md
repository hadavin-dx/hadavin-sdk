## Rules stated once (all sub-tickets)
- Error rule: a refused WRITE is `StaleState` (conflict, replay of a closed reservation, lost compare-and-set), `ValueError` (a value the store cannot hold) or `NotFound`. The money errors are their own classes in `store/protocol.py`, none derived from `ValueError` or `ConfigError`: `SpendCapExceeded(RuntimeError)` with `which` (`"run"`, `"day"`, `"month"`), `cap`, `current`, `requested` (R215 wants numbers); `KillSwitchOn(RuntimeError)`; `CounterDamaged(RuntimeError)`; `ReservationConflict(StaleState)` (callers that retry on `StaleState` will see it; documented); `StoreBusy(RuntimeError)`, a SEPARATE class: not a `StoreUnavailable`, not a `ConfigError`. An unreachable store, a missing table or a missing grant stays a driver error classified by `is_connectivity_error`. `is_connectivity_error` tests `StoreBusy` FIRST and returns false, and returns false for driver errors whose `sqlstate` is `40001`, `40P01`, `55P03`, `57014` (the store answered; it is busy). A caller-test row pins `StoreBusy` at each of the four callers (`chain.py:533`, `cli.py:368`, `tick.py:342,362`); what they do with "answered but busy" (a message that says "run migrate" would be imprecise) stays PENDING LEAD (item 4).
- Retry and timeout: the Postgres wrapper retries a whole write transaction at most 3 times, ONLY on SQLSTATE `40001` and `40P01` (never `40003`), with backoff `20 ms * 2^n` plus jitter, and never for add-style writes with no key (`add_spend`, `add_cost`, `add_dead_letter`, `touch`): those raise `StoreBusy` at once. Every wrapped write runs in ONE transaction opened by the wrapper (today the connection is autocommit, `postgres.py:146`, and only `record_decision` `:359` and `add_spend` `:419` open a transaction; a single autocommit statement cannot keep a `set_config(..., true)` value, so the wrapper makes every wrapped write a transaction; one extra statement per write: cost UNVERIFIED), and its FIRST statement sets the timeouts: `SELECT set_config('lock_timeout', %s, true), set_config('statement_timeout', %s, true)` with the values passed as `str(ms)` TEXT (A8; an integer parameter fails with 42883, PG 16.15 run; `SET LOCAL ... = <n> ms` cannot take a bind parameter), values from the new settings `PostgresSettings.lock_timeout_ms` (default 1000, range 100-60000) and `call_budget_ms` (default 5000, range 500-60000; also the total wall-clock budget of one call across retries; when spent the call raises `StoreBusy`). `statement_timeout` is set per attempt to the REMAINING `call_budget_ms` and `lock_timeout` to the smaller of the setting and the remaining budget (so six lock-taking statements cannot add up to more than the budget by much: at most one statement's timeout over; UNVERIFIED how close), and the back-off sleep happens OUTSIDE `self._lock` and outside the transaction (a stop from the same handle never waits through a sleep). `55P03` and `57014` become `StoreBusy`. The wrapper takes an injectable `on_retry` hook (default `None`, nothing recorded; `PostgresStore(conn, *, on_retry=None)`): it is called with `(sqlstate, attempt)` at every retry, so tests can count retries; a test that passes only because a retry hid a deadlock is a defect (A2/C3). Said plainly: the store keeps one connection behind one in-process lock (`postgres.py:193-197`), held for a whole transaction including lock waits, so another call from the SAME handle (for example `Limits.stop()` in the same process) can wait up to `call_budget_ms`; the one-connection design is not changed in this ticket; a separate short connection for `set_kill_switch` is recorded as a v1.1 row (trigger: a stop observed delayed past `call_budget_ms`). Defaults are PENDING LEAD (item 4).
- ONE total lock order for the four new write methods plus `add_spend` and `add_cost` (which use a part of it in the same order): (1) the reservation row (insert, or the claim UPDATE); (2) the "ensure counter rows" inserts (`spend` day row, then `spend_month` row); (3) `UPDATE runs` (only with `run_id`); (4) `UPDATE spend` (day); (5) `UPDATE spend_month` (month). The kill-switch read is a plain `SELECT` (takes no row lock) and is outside the order. No deadlock argument is claimed for the position of the ensure-rows step (every method uses the one order, so any fixed position is safe; round-4 A11 asked to drop the claim), and no mutant pins it. `SpendCapExceeded.which` is reported in the same order: the first failing cap in run, day, month.
- Kill-switch read (A1/C13): `reserve_spend` reads the switch with a plain `SELECT "on" FROM kill_switch WHERE id = 1` in the same transaction, through ONE private helper that `get_kill_switch` also calls (Postgres: `_kill_switch_row(db)`; memory: `_kill_on()`), fail closed when the row is missing. No locking clause: a locking read needs UPDATE privilege on the table, which P2a removes from the runtime role, and a plain read never blocks `set_kill_switch` anyway. Stated semantics: a reserve that read "off" may commit after a stop commits (a window of at most one transaction); the stop switch stays an advisory check at reserve time, and P2a/P4b1 own anything stronger. On a `settled` or `released` row it returns the stored first result (`applied=False`, the second amount ignored, even when it is larger than reserved). On an `expired` row it may correct DOWNWARD ONCE: if `actual <= reserved` the row becomes `settled` with `settled_usd = actual`, `closed_at` is set to now (`expired_at` keeps the time of expiry) and the counters drop by `reserved - actual`. `actual > reserved` on an open or expired row is `ValueError` (the row stays; the meter then settles at the reserved worst case). EXIT PATH: the sweep (open to expired) moves no counters, so it closes such a row without raising and the budget stays held at the worst case; an `expired` row whose counter is damaged stays `expired`. Drift check (documented read, not a method): the counter is always at least `sum(open reserved) + sum(expired reserved) + sum(settled)` for the same agent and day; a smaller counter means damage. The invariant is an inequality in production because `add_spend`/`add_cost` are mixed in.
