## Rules stated once (all three sub-tickets)
- Error rule: a refused WRITE is `StaleState` (conflict, replay of a closed reservation, lost compare-and-set) or `ValueError` (a value the store cannot hold). The two money refusals are their own classes, defined in `store/protocol.py`: `SpendCapExceeded` (attribute `which`: `"day"`, `"month"` or `"run"`) and `KillSwitchOn`; both are listed here so the rule stays complete. The Postgres store retries a whole write transaction at most 3 times on such an error, then raises `StoreBusy` (new, subclass of `StoreUnavailable`; mirrors PR #49 per memo-3, UNVERIFIED; PENDING LEAD whether it should subclass `StoreUnavailable`, which makes `tick` exit 4).

Errors: `ValueError`, `KillSwitchOn`, `SpendCapExceeded(which)`, `ReservationConflict` (new, subclass of `StaleState`), `StaleState` (replay of a closed id), `NotFound`. Boundary: a booking that leaves a total EXACTLY at its cap is allowed; one micro-dollar over is refused (`limits.blocked` then refuses at `>=`, `limits.py:26`: one counter, two stated boundaries, both tested).
  - "Same content" means exactly `(agent_id, day, reserved_usd, run_id)`, compared numerically. Replay of an id with the same content: if status is `open`, returns the stored row (status `"open"`) and books nothing more; the Protocol docstring tells callers to check `status`; if status is `settled` or `released`, raises `StaleState` (a content-derived id reused after settle must not look like a held reservation). Same id with different content, including a different `day`, is `ReservationConflict` and changes nothing (the first reservation's day stands; a retry across midnight must reuse the original day). Caps are not stored and not part of identity: a replay does not re-check caps. Reservation ids are caller-generated random strings (use `new_id`-style); agent B using agent A's id gets `ReservationConflict` and changes nothing (tested).
  - `settle_spend(reservation_id: str, actual_usd: Decimal) -> SpendReservation`. The first call for an open reservation sets status `settled`, stores `settled_usd`, and lowers the same counters by `reserved - actual`. A later call, whatever its amount (even an invalid-looking one that is a valid Decimal), returns the FIRST result unchanged and books nothing; the second amount is ignored and documented as such. `actual_usd` of zero is allowed (settled at zero). Errors: `NotFound` (unknown id), `ValueError` (invalid amount; or `actual_usd` greater than the reserved amount: the reservation stays open, and the meter then settles at the reserved worst case: what a missing usage means is the meter's job). If a counter is lower than the amount to lower (damaged data), the whole transaction is rolled back, the reservation stays open, an error is logged and `StaleState` is raised; there is no silent clamp.
  - `release_spend(reservation_id: str) -> SpendReservation`: first call on an open reservation sets status `released` (`settled_usd` stays NULL) and lowers the counters by the full reserved amount; later calls return the stored first result. A release is distinct from a settle at zero, so P4b2's billing contract can tell them apart.
