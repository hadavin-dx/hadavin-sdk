## What the "statement check" means here, in plain words (read this first)
No code can see what a provider does with our text. This ticket is therefore NOT a technical switch that makes a provider stop training. (The plan row and the package name say "lock"; in README, CHANGELOG, the log line and the refusal texts the word is "no-training statement", so nobody reads them as a block.) The fixed sentence in all of them is: "This records a promise by the operator; it does not stop a provider from training." What the code enforces is three things:
1. A written, dated statement in the client's config, per llm backend: which kind of promise protects us (the provider's written terms for API customers, or a setting we switched on in our own account, or a model we run ourselves), the document it comes from, the servers (host names) the statement is about, and the date a person last read it. The code checks the statement is present, well formed, allowed for that backend, written for the servers the config really talks to, and not older than a limit (default 90 days). The code does NOT check the statement is true: the log says "operator-attested" (same wording as `scope_inventory` in `app.py`).
2. A refusal: in a client environment (pilot or prod) a backend with no valid statement does not start. Dev is not affected.
3. A test that walks a hard-coded list of the llm kinds and fails with an instructive message when `TABLE["llm"]` gains a kind that the list does not know, so whoever adds a fifth backend has to add a sample and a declaration. What actually stops a new kind from running in pilot or prod without a statement is not that test: it is the fail-closed default (`Entry.no_training` is empty unless the entry declares otherwise) plus refusal (a). The test makes the author notice; the default and the refusal enforce.
What the code does NOT check, stated plainly: that the statement is true; the key or account tier behind a key (the Gemini unpaid-versus-paid case uses the same host, so the hosts field does not see it); whether `self_hosted` is really a server the client runs (code cannot tell a client's server from a public one; the hosts field only puts the host in writing beside `self_hosted`); and that a running process stays within the age limit after start-up (see "Interface", age).
Per-request flags: I found none documented in the repo and could not read a provider page, so v1 sets none, on every backend. Candidates exist (UNVERIFIED, from my own memory as of 2026-11-05, not read today): an OpenAI-shaped `store: false` and an OpenRouter-style `provider.data_collection: "deny"` field. Neither is a training switch with certainty, and a compatible server that does not know a field may reject the request, which would break callers. PENDING LEAD 1.
