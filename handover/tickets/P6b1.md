## What the "statement check" means here, in plain words (read this first)
No code can see what a provider does with our text. This ticket is therefore NOT a technical switch that makes a provider stop training. The plan row and the package name say "lock". In the README, the CHANGELOG, the log line and the refusal texts the word is "no-training statement", so nobody reads them as a block. The fixed sentence in all of them is: "This records a promise by the operator; it does not stop a provider from training."
The code enforces three things:
1. A written, dated statement in the client's config, one per llm backend. It says:
   - which kind of promise protects us: the provider's written terms for API customers, a setting we switched on in our own account, or a model we run ourselves;
   - the document it comes from;
   - the servers (host names) the statement is about;
   - the date a person last read it.
   The code checks that the statement is present, well formed, allowed for that backend, written for the servers the config really talks to, and not older than a limit (default 90 days). It does NOT check that the statement is true: the log says "operator-attested", the same wording as `scope_inventory`.
2. A refusal: in a client environment (pilot or prod), a backend with no valid statement does not start.
3. A test that walks a hard-coded list of the llm kinds. It fails with an instructive message when `TABLE["llm"]` gains a kind the list does not know. What actually stops a new kind from running in pilot or prod without a statement is the fail-closed default (`Entry.no_training` is empty unless declared) plus refusal (a). The test makes the author notice; the default and the refusal enforce.
What the code does NOT check, stated plainly:
- That the statement is true.
- The key or account tier behind a key. My recollection (UNVERIFIED, 2026-11-05) is that unpaid and paid Gemini keys fall under different data terms on the same host, so the hosts field cannot see the difference.
- Whether `self_hosted` is really a server the client runs. The hosts field only puts the host in writing beside `self_hosted`.
- That a running process stays within the age limit after start-up (see "Interface", age).
- The `dev` label. `environment` is written by the operator. A config labelled `dev` can name a real model backend and send real text to it with no statement at all, and this check does not stop that. Client data must never run in a `dev` config. (PENDING LEAD 10.)
- The model behind a host. The statement is bound to host names only, and terms can differ per model or product on the same host: partner models on Vertex or Bedrock, preview models. Routes choose the model per route, and the statement does not see that. An `openai_compat` gateway can forward requests to upstream providers whose terms the statement does not cover. The README sample therefore says that `reference` names the product or model family and, for a gateway, the gateway's terms for its upstreams. Binding to route model ids is a v1.1 row (PENDING LEAD 11).
- The guardrail detector. `detector: bedrock_guardrail` sends client text to a cloud call and is NOT covered (see class-level notes and the v1.1 list).
Per-request flags: none in v1, on every backend. I found none documented in the repo and could not read a provider page. Candidates from my own memory (UNVERIFIED, not read today): an OpenAI-shaped `store: false` and an OpenRouter-style `provider.data_collection: "deny"`. A compatible server that does not know a field may reject the request. PENDING LEAD 1.

    - (c) The basis is not in the kind's set: `llm: <kind>: no_training basis <basis> not allowed (allowed: <sorted list>)`.
    - (f) The hosts differ from the endpoint: `llm: <kind>: no_training hosts do not match the configured endpoint (expected: <sorted hosts>): read the terms for that endpoint and update the statement`.
      - Expected is `sorted(set(h.lower() for h in entry.hosts(settings) if h))`, or `[]` when `entry.hosts` is None.
      - When expected is empty, the text says `expected: none (the endpoint has no host name)`.
      - The statement's list is compared as `sorted(set(...))` of the lower-cased names, so order, repeats and letter case do not matter. A missing host and an extra host both refuse.
    - (d) `checked_on` is more than slack days after `today`: `llm: <kind>: no_training checked_on is in the future`.
    - (e) The statement is older than the limit: `llm: <kind>: no_training statement is <n> days old (limit <m>): read the provider's terms again and update checked_on`.
    - The messages join the existing `refused` list, so one `ConfigError` shows every refusal at once.
    - The reference text is never put in a message (hosts may be, in (f)).
    - Age is `(today - checked_on).days`: exactly the limit passes, limit+1 is refused.
    - The age is checked only at load. A running process is not re-checked; the next restart after the limit refuses to start (README says so).
    - With no statement, (c), (f), (d) and (e) cannot be evaluated. (d) and (e) cannot both hold.
  - Error rule: every problem on this path is a refusal (a `ValueError` inside a validator, so a `ConfigError` at load). A bug that raises another exception also stops start-up. Nothing is caught and ignored, and there is no default that lets a kind through.
  - `backends/factory.make` gets a module logger and logs one INFO line when it builds the `llm` capability.
    - With a statement, the line holds: the kind, basis, hosts, `checked_on`, `age checked at start-up against no_training_max_age_days (default 90 days)`, the reference, the words "operator-attested, not verified by code", and the fixed sentence.
    - With no statement: `no_training: none: allowed only in dev; do not send client data`. (`make` cannot see the environment, so it does not claim "dev".)
    - No computed date is printed.
    - The text is pattern-limited, so no newline can forge a log line (T11).
    - LIMIT, stated: an llm passed into `build(llm=...)` skips `make`, so no line is logged for it (`app.py:162`; `app.py` is out of scope). The refusal at load does not depend on this.
