## What "lock" means here, in plain words (read this first)
No code can see what a provider does with our text. A "lock" in this ticket is therefore NOT a technical switch that makes a provider stop training. It is three things the code can enforce:
1. A written, dated statement in the client's config, per llm backend: which kind of promise protects us (the provider's written terms for API customers, or a setting we switched on in our own account, or a model we run ourselves), the document it comes from, and the date a person last read it. The code checks the statement is present, well formed, allowed for that backend and not older than a limit (default 90 days). The code does NOT check the statement is true: the log says "operator-attested" (same wording as `scope_inventory` in `app.py`).
2. A refusal: in a client environment (pilot or prod) a backend with no valid statement does not start. Dev is not affected.
3. A test that walks every kind in `TABLE["llm"]` and fails if one has no declared way to satisfy (1) and (2), so a fifth backend cannot be added silently without a lock.
Per-request flags: I found none documented in the repo and could not read a provider page, so v1 sets none, on every backend. Candidates exist (UNVERIFIED, from my own memory as of 2026-11-05, not read today): an OpenAI-shaped `store: false` and an OpenRouter-style `provider.data_collection: "deny"` field. Neither is a training switch with certainty, and a compatible server that does not know a field may reject the request, which would break callers. PENDING LEAD 1.
