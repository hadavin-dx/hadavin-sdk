## The problem in plain words
After P1d, when an approval request's text holds something that looks like a split secret, the card sent to the approvers shows a fixed sentence instead of the text, has no buttons, and cannot be approved. The operator (the person who runs the deployment for the client) gets one log line with the request id and a reason code, but no way to see WHICH part of the request caused it. Today (R) the only ways out are that the request moves up its approval steps and expires (`requests.sweep`, `requests.py:191-231`), or that someone reads the raw request in the database, which shows the raw secret to a person and is not recorded. If false withholds happen (P1d measures the rate), a request the business needs is blocked with no explanation.

## Words used
- **Withheld request** = a stored approval request whose card P1d replaced by its withheld text.
- **The check** = the ONE function P1d's approve path calls on the raw stored summary and plan inputs (P1d rev 6, "Operator route and approve path" (3): `approvals.channel.clean` with the same arguments, raising `LookalikeCopy` when it withholds; BS-0 names the exact function and arguments on the built P1d). This package never calls a second masker.
- **Leaf** = the summary, or one string value inside the plan inputs (depth-first, in stored order).
- **Label** = the name printed in front of a leaf: `summary`, or `inputs.` followed by the path to the leaf. A path element is printed as written only if it matches `[A-Za-z0-9_-]{1,32}`; otherwise as `#<position>` (a key is text the request's author controls).
- **Operator view** = the result of the check for one request, computed by the runtime and stored masked (below). **View log** = one stored row per `approvals show` call.
- **Terminal-safe** = every character of Unicode category Cc, Cf, Co, Cs, Cn, Zl or Zp, and ESC, replaced by `?`, except the line breaks our own code puts between lines.

## Behaviour of option B, exactly
**Design in one line:** the RUNTIME (which already reads raw request text) computes a masked operator view with the check and stores it; the operator's command reads ONLY that masked view, under its own read-only identity, after writing a view-log row; the next tick puts each view-log row into the hash-chained audit.
1. **Computing the view (new tick step `operator_views`, runtime identity):** for each PENDING request that has no row in `withheld_views` for its `(approval_id, plan_hash)`:
   - Run the check on the request's units exactly as the approve path does. If it does not withhold, store a row with `withheld = 0` and no text (the card already shows that text).
   - If it withholds, build the shown set by the **joined rule** (review Major 1): start with an empty set S; for each leaf i in order (summary first): the candidate text is the lines `<label>: <leaf>` of S plus i, joined by line breaks; if the candidate is longer than `P1D_MAX_TEXT_CHARS` or i is past `P1DC_MAX_LEAVES`, i is withheld with reason `size`; else the check runs on the candidate (one call, call-local map, the same as at card and approve time); if it raises `LookalikeCopy`, i is withheld with reason `check`; else i joins S. The stored block is the check's OUTPUT for the final S (so a value learned in one leaf is masked in every other leaf: one map, one call), made terminal-safe. The terminal-safe step comes AFTER the check, because the check reads an escape code or control character as a joiner of a split key, while `?` would hide that join; replacing a character by `?` can only break text apart, never join it.
   - Stored row: `approval_id`, `plan_hash`, `computed_at`, `withheld` (count), `shown` (count), `block` (the masked, checked, terminal-safe text), `refused` (a JSON list of `{label, reason}`; labels are made of our own allowlist and reasons from the fixed set `size | check`).
   - Property: the stored block passes the check again unchanged (`test_stored_block_passes_the_check`); no two shown leaves can be joined into a withheld secret, because the check ran on all of them together.
   - The check writes P1d's operator log line for each withheld candidate (`source=card`; P1d's fixed source set). No content is logged.
2. **The command:** `hadavin-sdk [--config DIR] approvals show APPROVAL_ID --by WHO`.
   - Refusals (exit 2): `WHO` not matching `[A-Za-z0-9_.@-]{1,64}`; a configuration error; the memory store, with a message naming this command (the existing refusal at `cli.py:176` picks the command name from a small mapping that gains `approvals show`; today it names only `audit verify` or `the kill switch`).
   - It connects with the operator identity only (rule 4): the DSN comes from the secrets kind under the name in config `approvals.operator_dsn_secret_name`; it never builds the runtime store or the audit kind.
   - FIRST it inserts one row into `operator_view_log` (`view_id`, `approval_id` as typed if it matches `[A-Za-z0-9_-]{1,64}` else `?`, `by_name`, `at`; `db_user` defaults to and is checked against `current_user`). If the insert fails, nothing is printed and it exits 3 ("view not recorded, so not shown").
   - Then it reads the request's status columns and its `withheld_views` row. Unknown id, or no view yet: exit 5 with "no request with that id, or its view is not computed yet (the next tick computes it)". `withheld = 0`: prints "not withheld: the approval card shows this request" and exits 0.
   - Otherwise it prints, all terminal-safe: `approval <id> status <STATUS> step <n>` (status from the fixed set, id only if it matches the id grammar), `view computed at <UTC time>`, the stored block, then one line per refused leaf `withheld: <label> (<reason>)`. Exit 0.
   - It never approves, denies, re-sends or changes a request (no right to; rule 4).
   - Exit codes, complete: 0 shown or "not withheld"; 2 refused; 3 failure (view-log row not written, or any uncaught error, as `main` does today for every command, `cli.py:19-20`); 4 store unreachable (as `limits`, `cli.py:200`); 5 no request or no view yet (R: no command returns 5 today; `grep -n "return [0-9]" cli.py` shows 0-4 only).
3. **Audit row (ORDER 173):** the view-log row is written before anything is shown, under its own identity, in an append-only table (a trigger refuses UPDATE, DELETE and TRUNCATE for every role, as the audit tables do). The tick step `operator_views` also reads view-log rows after a cursor kept in `tick_state` and writes each into the audit kind as one event (`domain=approvals`, `operation=operator_view`, `event_id` from `view_id` so a repeat is a duplicate and is skipped, `principal` = `db:<db_user>/by:<by_name>`, `object_ref` = the approval id, no content). So every view is in the hash chain one tick later; `audit verify` covers it. Honest bound: between the print and the next tick (30-60 s, R `cli.py:6`) the record exists only as the append-only row, not yet in the chain.
4. **Least privilege (review Major 4):** a new database role for the operator, granted by `migrate --operator-role R` through the existing grant map (`store/migrate.py:46`, new field `operator` with column lists):
   | identity | may read | may write | why |
   |---|---|---|---|
   | operator role (new) | `withheld_views` (all columns: masked text only); `approval_requests` columns `approval_id`, `status`, `current_step`, `step_expires_at` only | INSERT into `operator_view_log` only | read the masked view and the request's state; record the view. It can NOT read `summary`, `plans`, `redaction_maps`, the audit, or other view-log rows, and can NOT change any request. |
   | runtime role (existing) | + `operator_view_log` | + INSERT into `withheld_views` | compute views (it already reads the raw text); chain the view log |
   | purge role (existing) | `withheld_views` columns `approval_id`, `computed_at` | DELETE on `withheld_views` | the view is deleted with the request's evidence (BS-0 names the purge function and adds the table to it) |
   The `_excess_privileges` check (`migrate.py:356`) runs for the operator role too. Credential: short-lived where the store supports IAM sign-in (`iam_auth`, R `postgres.py:158`), else a secret from the secrets kind; never the runtime DSN. The command holds no write right on any request, so "read only" is enforced by the database, not by our code alone.
5. **Marker:** `runmap.P1DC_APPLIED = True`. P1d's client-profile check reads a list of three marker names (`P1d.md:45`); this package adds `P1DC_APPLIED` to that list and to the parametrised `test_client_profile_refuses_without_marker`.
