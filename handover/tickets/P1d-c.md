## The problem in plain words
After P1d, when the summary of a plan that needs approval holds something that looks like a split secret, no approval request is saved; a card with a fixed sentence and no buttons is posted once, and the run ends as "a person must look" with the reason `card_withheld` (`P1d.md:192-193`). The operator (the person who runs the deployment for the client) gets one log line with the run id (`ref=`) and a reason code (`P1d.md:187`), but no way to see WHICH part of the plan caused it. The plan itself, with its raw inputs, is still stored (R: table `plans`, `0001_core.sql`). Today the only way to look is to read the raw plan in the database, which shows the raw secret to a person and is not recorded. If false withholds happen (P1d measures the rate), work the business needs stops with no explanation.

## Words used
- **Withheld run** = a run that P1d ended with reason `card_withheld` because `requests.summary(plan)` raised `LookalikeCopy`.
- **The check** = `approvals.channel.clean(text, ref=..., source=...)` as P1d rev 7 defines it (`P1d.md:188`), the same function `requests.summary` calls (R `requests.py:39`). This package never calls a second masker.
- **Leaf** = one piece of the plan that `requests.summary` puts into the card text (R `requests.py:40-42`): the action line (agent id, action id and version, risk class, target system: our own fields), each string value inside `plan.inputs` (depth-first, in stored order), and `expected_outcome`.
- **Label** = the name printed in front of a leaf: `action`, `expected`, or `inputs.` followed by the path to the leaf. A path element is printed as written only if it matches `[A-Za-z0-9_-]{1,32}`; otherwise as `#<position>` (a key is text the plan's author, possibly a model reading a hostile document, controls).
- **Operator view** = the result of the joined rule for one withheld run, computed by the runtime and stored masked. **View log** = one stored row per `approvals show` call.
- **Terminal-safe** = every character of Unicode category Cc, Cf, Co, Cs, Cn, Zl or Zp, and ESC, replaced by `?`, except the line breaks our own code puts between lines.

## Behaviour of option B, exactly
**Design in one line:** the RUNTIME (which already holds the raw plan) computes a masked operator view with the check at the moment P1d withholds the card, and stores it; the operator's command reads ONLY that masked view, under its own read-only database identity, after writing a view-log row; the next tick puts each view-log row into the hash-chained audit.
1. **Computing the view (runtime, at withhold time):** in `app.request_approval`, right after P1d's `card_withheld` branch (`P1d.md:192`; BS-0 names the exact line on built P1d), call `operator_view.compute(plan)` and `store.put_withheld_view(view)`. Any exception there logs one fixed line (`operator view not stored: <class name>`) and changes nothing in P1d's outcome (the run still ends `card_withheld`; the command then answers "no view", exit 5).
   - **Joined rule (review Major 1):** start with an empty set S; for each leaf i in order: the candidate is S plus i. i is withheld with reason `size` if the candidate's rendering is longer than `P1D_MAX_TEXT_CHARS` or i is past `P1DC_MAX_LEAVES`. Otherwise the check runs TWICE, once on each form of the candidate: (a) the labelled rendering, lines `<label>: <leaf>` joined by line breaks; (b) the leaves concatenated in order with nothing between them (so a key split across two shown leaves is joined for the check even where the labels would separate it). If either call raises `LookalikeCopy`, i is withheld with reason `check`; else i joins S. Each call uses its own call-local map, as `clean` does at card time; within one call, a value learned in one leaf masks its copies in every other leaf.
   - Honest bound: the check sees the shown leaves in stored order. Pieces placed in reverse order across leaves are not joined by the check, which is the same bound P1d's card check has (it sees one order, the summary's); this view is no weaker than the card P1d would have accepted.
   - The stored block is the OUTPUT of call (a) for the final S, then made terminal-safe. Terminal-safe comes AFTER the check, because the check reads an escape code or control character as a joiner of a split key, while `?` would hide that join; replacing a character by `?` can only break text apart, never join it. Property test: the stored block passes the check again (`test_stored_block_passes_the_check`).
   - Stored row (`withheld_views`): `run_id`, `plan_id`, `computed_at`, `shown` (count), `withheld` (count), `block` (masked, checked, terminal-safe text), `refused` (a JSON list of `{label, reason}`; labels from our allowlist, reasons from the fixed set `size | check`). One row per run (primary key `run_id`; a second insert is a no-op).
   - Each withholding check call writes P1d's operator log line (`source=card` and `card_joined` as `clean` does; P1d's fixed source set). No content is logged.
   - Requests stored BEFORE P1d (rows whose card `Approvals.decide` refuses, `P1d.md:196`) get no view: no client data exists before P1d merges (ORDER 165 M6 hard dependency), so such rows exist only in demo databases and expire through `sweep` (`P1d.md:207`).
2. **The command:** `hadavin-sdk [--config DIR] approvals show RUN_ID --by WHO`. `RUN_ID` is the id the operator log line prints as `ref=` (format `run-` + 32 hex characters, R `models.py:23-24,91`).
   - Refusals (exit 2): `RUN_ID` not matching `run-[0-9a-f]{32}`; `WHO` not matching `[A-Za-z0-9_.@-]{1,64}`; a configuration error; the memory store, with a message naming this command (the existing refusal at `cli.py:176` picks the command name from a small mapping that gains `approvals show`; today it names only `audit verify` or `the kill switch`).
   - It connects with the operator identity only (rule 4): the DSN comes from the secrets kind under the name in config `approvals.operator_dsn_secret_name`; it never builds the runtime store or the audit kind.
   - FIRST it inserts one row into `operator_view_log` (`view_id`, `run_id`, `by_name`, `at`; `db_user` defaults to `current_user` and a CHECK refuses any other value). If the insert fails, nothing is printed and it exits 3 ("view not recorded, so not shown").
   - Then it reads the run's `state` and its `withheld_views` row. No row: exit 5 ("no withheld view for this run: the run does not exist, its card was not withheld, or the view could not be stored; see the operator log").
   - Otherwise it prints, all terminal-safe: `run <id> state <STATE>` (state from the fixed set), `view computed at <UTC time>`, the stored block, then one line per refused leaf `withheld: <label> (<reason>)`. Exit 0.
   - It never approves, denies, re-sends or changes anything (no right to; rule 4).
   - Exit codes, complete: 0 shown; 2 refused; 3 failure (view-log row not written, or any uncaught error, as `main` does for every command, `cli.py:19-20`); 4 store unreachable (as `limits`, `cli.py:200`); 5 no view. R: no command returns 5 today (`grep -n "return [0-9]" cli.py` shows 0-4 only).
3. **Audit row (ORDER 173):** the view-log row is written before anything is shown, under its own identity, in an append-only table (a trigger refuses UPDATE, DELETE and TRUNCATE for every role, as the audit tables do). A new tick step `chain_operator_views` reads view-log rows after a cursor kept in `tick_state` and writes each into the audit kind as one event (`domain=approvals`, `operation=operator_view`, `event_id` derived from `view_id` so a repeat is a duplicate and is skipped, R `chain.py:214-219`; `principal` = `db:<db_user>/by:<by_name>`; `object_ref` = the run id; no content). So every view is in the hash chain one tick later and `audit verify` covers it. Honest bound: between the print and the next tick (every 30-60 s, R `cli.py:6`) the record exists only as the append-only row, not yet in the chain.
4. **Least privilege (review Major 4):** a new database role for the operator, granted by `migrate --operator-role R` through the existing grant map (`store/migrate.py:46`, new field `operator` with column lists):
   | identity | may read | may write | why |
   |---|---|---|---|
   | operator role (new) | `withheld_views` (masked text only); `runs` columns `run_id`, `state` | INSERT into `operator_view_log` only | read the masked view and the run's state; record the view. It can NOT read `plans`, `approval_requests`, `redaction_maps`, the audit or other view-log rows, and can NOT change anything else. |
   | runtime role (existing) | + `withheld_views`, `operator_view_log` | + INSERT into `withheld_views` | store views (it already reads the raw plan); chain the view log |
   | purge role (existing) | `withheld_views` columns `run_id`, `computed_at` | DELETE on `withheld_views` | the view is deleted with the run's evidence (BS-0 names the purge function, `store/protocol.py:129-153`, and adds the table) |
   The `_excess_privileges` check (`migrate.py:356`, today for the portal role) runs for the operator role too. Credential: short-lived where the store supports IAM sign-in (`iam_auth`, R `postgres.py:158`), else a secret from the secrets kind; never the runtime DSN. "Read only" is enforced by the database, not only by our code.
5. **Marker:** `runmap.P1DC_APPLIED = True`. P1d rev 7 already lists it in the start gate in `app.build` (`P1d.md:52`, its open question 1, default applied), so the client profile cannot start before this package merges.
