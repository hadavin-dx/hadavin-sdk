**Words used (plain meaning, one meaning each).**
- **trigger**: an outside event that should start work. In v1 there is one kind: a signed web request from another system (a **webhook**). An e-mail, a file or a time on the clock reaches us as a webhook sent by a **forwarder** (the client's own mail, automation or scheduler tool) (decision I1, PENDING LEAD 1 and 5).
- **sender**: the outside system that sends a webhook. **source**: one configured webhook address, bound in config to exactly one tenant, one readers list, one agent and one principal.
- **delivery**: one arrival of a message. The same message can arrive more than once (the sender retries). **sender id**: the id the sender gives its message (for example an e-mail's message id), read only from the signed body, from the source's configured field.
- **receipt**: the row we write BEFORE we answer the sender. "Write-ahead" means: the receipt and the message body are saved first; only then does the sender hear "accepted".
- **delivery key**: a SHA-256 built from the tenant, the source and the sender id (exact formula in Interface 2). We store this hash, never the raw sender id (a sender id can hold an e-mail address).
- **duplicate**: the same sender id with the same body bytes again: nothing new happens. **id reuse**: the same sender id with DIFFERENT body bytes: the first stays untouched, the new one is recorded as its own refused row WITHOUT its body, and the sender hears "conflict" (so it knows we did not accept it).
- **claim / lease**: a worker takes ONE receipt for a limited time (the lease). If it crashes, the lease runs out and another worker can take the receipt again. **release**: a worker hands a receipt back unfinished after a failure that may pass (so it is tried again).
- **final state**: `done`, `needs_person` ("a person must look") or `refused`, the same three words as AK1's `Outcome`. Every receipt ends in exactly one. Open states are `received` and `claimed`. `done` means exactly one run exists for this message; how that run ends is the run's own state.
- **dead letter**: a row in the existing `dead_letters` table for a receipt that failed too many times; the receipt itself ends `needs_person`.
- **backpressure**: when too many receipts of one source are open, we answer "busy, retry later" BEFORE saving anything; the sender still holds the message. We never accept and then drop.
- **dispatch**: the tick step that claims receipts and hands each one to an AK1 `Step`.
- **pilot/prod**: a config whose `environment` is `pilot` or `prod` (`config.py:317`).
- "UNVERIFIED" = I did not read it in code or could not run it. "PENDING LEAD" = an owner or lead decision, with my recommendation first. "INFORM" = my decision on my recommendation, final unless the lead says otherwise (order 23 item 4).

## The decision that shapes this ticket (INFORM I1, recommended; read before the fields)

Options for "one input kind feeding the AK1 step contract" (order 23 item 2 lists e-mail inbox, signed webhook, scheduler, file drop, queue pull):
- (a) Build every way in now: webhook, schedule, mailbox reading, folder drop, queue pull, each with its own adapter and contract suite. Biggest surface; four of the five have no consumer yet and each brings a vendor, clock or file-system edge.
- (b) **Recommended: ONE door.** v1 builds ONE ledger (the old P7a, fixed) and ONE signed webhook door. A mailbox, a folder, a queue or a clock reaches the door through a forwarder that signs with `hmac_v0`: the client's own mail, automation or scheduler tool, or a self-hosted no-code flow the client agrees to (the "signed webhook in" door of the client-chooses-tools policy, item 5; tool ladder rung 3 names triggers and schedulers as plumbing). Native readers and a built-in schedule are later rows (V1-V3, V5) with triggers. Every delivery becomes one `StepInput` handed to `run_step`.
- (c) A workflow engine or message broker as the inbound layer: rejected for v1 (a new dependency for a problem a table and a tick already solve; kept as the written alternative below).

Why (b): it closes the BLOCKER for the first shape (document intake by e-mail works once the client's mail is forwarded) with the least new code, and every later door reuses the same ledger, key rule and tests. **Deviation, said plainly:** revision 1 still built a schedule source; revision 2 cuts it (resolve row ADV-15), so the word "scheduler" in order 23 item 2 is served through the door, not by our own code (PENDING LEAD 5). Cost: a client whose mail cannot be forwarded and who refuses a forwarding tool is not served by v1 (PENDING LEAD 1); an all-code client must run one scheduled job that signs its request (core has no signing command today; `hmac_v0.sign` is a library function, `hmac_v0.py:31`). Confidence 75 percent; reversible (a native reader or a schedule is a new source that writes to the same ledger).
