**Words used (plain meaning, one meaning each).**
- **trigger**: an outside event that should start work. In v1 there is one kind: a signed web request from another system (a **webhook**). An e-mail, a file or a time on the clock reaches us as a webhook sent by a **forwarder** (the client's own mail, automation or scheduler tool) (decision I1, PENDING LEAD 1 and 5).
- **sender**: the outside system that sends a webhook. **source**: one configured webhook address, bound in config to exactly one tenant, one readers list, one agent and one principal.
- **delivery**: one arrival of a message. The same message can arrive more than once (the sender retries). **sender id**: the id the sender gives its message (for example an e-mail's message id), read only from the signed body, from the source's configured field.
- **receipt**: the row we write BEFORE we answer the sender. "Write-ahead" means: the receipt and the message body are saved first; only then does the sender hear "accepted".
- **delivery key**: a hash built from the tenant, the source and the sender id (exact formula in Interface 2). We store this hash, never the raw sender id (a sender id can hold an e-mail address). Revision 3 writes it as a KEYED hash (an HMAC, which cannot be recomputed without the key), PENDING LEAD 6. The field `body_sha256` keeps its name and holds the keyed hash of the body under the same rule.
- **duplicate**: the same sender id with the same body bytes again: nothing new happens. **id reuse**: the same sender id with DIFFERENT body bytes: the first stays untouched, the new one is recorded as its own refused row WITHOUT its body, and the sender hears "conflict" (so it knows we did not accept it).
- **claim / lease**: a worker takes ONE receipt for a limited time (the lease). If it crashes, the lease runs out and another worker can take the receipt again. **release**: a worker hands a receipt back unfinished after a failure that may pass (so it is tried again).
- **try**: one counted attempt at a message. A crash or an overrun (the lease ran out) counts; a step failure (`step_error`) counts. An **infrastructure failure** (the audit trail or the store could not be reached) does NOT count, and it ends that dispatch call.
- **run row is the commit point**: once a run row exists for a receipt's run id, dispatch never starts that work again by itself. A message whose run was cut off goes to a person (**run interrupted**).
- **generation**: a counter on the receipt, 0 at first. A person's **reopen** (AK-G15's action, over this ticket's store method) raises it by one and gives the message a NEW run id, so a new run can start. A reopen can cost money again; that is the person's choice.
- **final state**: `done`, `needs_person` ("a person must look") or `refused`, the same three words as AK1's `Outcome`. Every receipt ends in exactly one. Open states are `received` and `claimed`. `done` means exactly one run exists for this message's current generation and that run did not end in a way a person must see (Interface 5); how that run ends is the run's own state.
- **dead letter**: a row in the existing `dead_letters` table for a receipt that failed too many times; the receipt itself ends `needs_person`.
- **backpressure**: when too many receipts of one source are open, we answer "busy, retry later" BEFORE saving anything new; the sender still holds the message. We never accept and then drop.
- **orphan source**: a (tenant, source) pair that still has open or waiting receipts in the store but is no longer in the config (removed, renamed, or moved to another tenant).
- **dispatch**: the tick step that claims receipts and hands each one to an AK1 `Step`.
- **pilot/prod**: a config whose `environment` is `pilot` or `prod` (`config.py:317`).
- "UNVERIFIED" = I did not read it in code or could not run it. "PENDING LEAD" = an owner or lead decision, with my recommendation first. "INFORM" = my decision on my recommendation, final unless the lead says otherwise (order 23 item 4).

## The decision that shapes this ticket (INFORM I1, recommended; read before the fields)

Options for "one input kind feeding the AK1 step contract" (order 23 item 2 lists e-mail inbox, signed webhook, scheduler, file drop, queue pull):

  5. **The inbox (-a, `triggers/ledger.py`).**
     - **Plain records (resolve row R2-COR-1).** Frozen dataclasses: `InboundSource(name, tenant, readers, agent_id, principal_id, max_open)`, validated in `__post_init__` with the name pattern `[a-z][a-z0-9_-]{0,39}`, AK1's `TENANT_PATTERN` and `Readers`, and `max_open >= 1`; `DispatchSettings(lease_s: int, max_attempts: int, dispatch_budget_s: int)`. `Inbox` and `dispatch` take only these; -b's config maps onto them.

     - `receive(source: InboundSource, sender_id: str, body: bytes) -> Literal["new", "duplicate", "id_reuse", "id_reuse_capped", "busy"]`. Order: (0) `check_sender_id` (`ValueError`, nothing written); (1) `receive_inbound(rec, body, max_reuse=defaults.INBOUND_MAX_REUSE_ROWS, max_open=source.max_open)` with `readers=source.readers`, `generation=0`, `run_id=run_id_for(key, 0)`: `new`, `duplicate` and `busy` are returned as they are; (2) on `conflict`, one more `receive_inbound` of the id-reuse row (`state="refused"`, `reason="id_reuse"`, `reuse_of` = the original key, `run_id=None`, body `None`, `max_reuse` = 8); its `new` or `duplicate` gives `id_reuse`, its `conflict_capped` gives `id_reuse_capped`. So a retry of an accepted message is `duplicate` even while the source is full (row L11b). A repeat of the same reused body writes nothing and is answered `id_reuse` again, never `duplicate`: answering 202 would tell the sender we hold a body we did not keep. Store errors propagate (the door answers 503).
     - `dispatch(sources: Sequence[InboundSource], step: Step) -> tuple[int, bool]`: (receipts finished or released, whether an infrastructure failure ended the call). Round robin over the sources, ONE receipt per source per turn, until no source has work, the monotonic time spent reaches `settings.dispatch_budget_s`, or an infrastructure failure happens. Before EACH claim for a source: if `source.agent_id not in qualified`, or `limits.blocked(source.agent_id)` is not empty (any of `kill_switch`, `daily_budget`, `monthly_budget`, `limits.py:20-30`), that source is skipped for this call and its receipts stay `received`. Then `claim_inbound(..., lease_s=settings.lease_s)`; per claimed receipt, in `_each`-style isolation (`runtime/tick.py:63`), in this order:
       - (1) **Does a run exist?** `store.get_run(rec.run_id)`. If it returns a run, `step` is NOT called: the receipt is finished by `_classify(run, source, rec)` (below). Only `NotFound` goes on.
       - (2) **Tries used up?** If `rec.attempts >= settings.max_attempts`: (a) `list_dead_letters(rec.run_id)`; add `DeadLetter(run_id=rec.run_id, reason="inbound_attempts_exhausted", errors=[rec.last_reason or "lease_expired"])` only if none with that reason exists (`errors` is a closed value, never exception text); (b) `finish_inbound(..., "needs_person", "attempts_exhausted")`. A crash between (a) and (b) brings the receipt back; (a) then finds the row and only (b) runs. With this check right after the claim, `max_attempts` counted tries run before exhaustion.
       - (3) Read the body (`None` gives `finish_inbound(..., "needs_person", "body_missing")`), build `StepInput(item_id=rec.item_id, tenant=rec.tenant, readers=rec.readers, body=body, run_id=rec.run_id, agent_id=source.agent_id)` and call `run_step(step, inp, audit=audit, principal="trigger:" + source.name)`. No meter scope and no masking run is open here, so AK1's (a2) check passes (`AK1.md:118`).
       - (4) By the output: `done`: read the run back with `get_run(rec.run_id)` and finish by `_classify` (`NotFound` here gives `done`: a step that makes no run, such as D3a's fake steps; `StartRun` always makes one); `refused` (any reason) gives `finish_inbound(refused, reason)`, final at once; `needs_person step_error` gives `release_inbound("step_error")` and the source PAUSES for the rest of this call (so it is tried again no sooner than the next tick); `needs_person audit_unavailable` gives `release_inbound("audit_unavailable")` (not counted) and is an infrastructure failure; any other `needs_person` reason gives `finish_inbound(needs_person, reason)`.
       - **Infrastructure failures (resolve row R2-ADV-2, R2-COR-9).** An `audit_unavailable` output, or `StoreUnavailable` from `limits.blocked`, `claim_inbound`, `get_run`, the body read, `finish_inbound` or `release_inbound`, ENDS the dispatch call for every source (the store and the audit trail are shared): dispatch logs the class name and returns `(n, True)`. So an outage costs at most one claim per tick. Said plainly: if the store fails between a claim and the end of that receipt, the receipt stays `claimed` until its lease runs out, and that expiry counts as a try; in a full outage the claim itself fails first, so no claim is made.
       - `StaleState` on finish or release is logged at debug and skipped (another claimer holds it). A stop request propagates out of `run_step` (`AK1.md:69`) and out of `dispatch`; the receipt stays `claimed` and the lease brings it back.
     - **`_classify(run, source, rec) -> (state, reason)`**, first match wins: `run.agent_id != source.agent_id` or `run.principal_id != source.principal_id` or `run.trigger_ref != rec.item_id` gives `needs_person run_mismatch` (a foreign run under this id is never `done`); `(run.state, run.reason_code)` in `LIMITS_END` gives `needs_person run_limits`; `run.state` in `tick.STUCK`'s keys (`RECEIVED`, `WORKING`, `PLAN_READY`, `EXECUTING`, `VERIFYING`, `tick.py:112-119`) gives `needs_person run_interrupted` (we hold the only claim, so nobody is running it; the run itself is left to the `stuck` step, and `EXECUTING` is never re-executed); anything else gives `done`.
     - **`LIMITS_END`** (resolve row R2-ADV-4, R2-COR-3) `= {(STOPPED, "kill_switch"), (NEEDS_PERSON, "limits.daily_budget"), (NEEDS_PERSON, "limits.monthly_budget"), (NEEDS_PERSON, "limits_unavailable")}`. The two budget strings are taken from P4c's `WALLS` (`P4c.md:182`, the run `reason_code` of the rule 6 table, `P4c.md:82-83`); `kill_switch` and `limits_unavailable` are P4c's constants for those rows (`P4c.md:84`, `:87`, `:89`). `run_budget` is NOT in it: that is the run's own outcome, and the receipt is `done`. A `run_limits` receipt keeps its body to the ceiling (Interface 3) and a person's reopen re-runs it. An automatic re-run is rejected: `limits_unavailable` also follows a paid call (P4c's exit-settle failure, `P4c.md:89`), so it could pay twice.
     - **The remaining race, stated (no longer silent).** `blocked()` is a read, so a kill switch, a daily or monthly wall, or a meter outage can begin between dispatch's check and `handle`'s own check (`agent_loop.py:359`). That run ends at once, and the receipt goes to a person as `run_limits`, body kept. At most one message per dispatching process per switch or wall crossing (PENDING LEAD 4 (v)). A check inside `handle` before `create_run` was rejected: it is also a read, so it narrows the window without closing it.
     - `compare_ids(tenant, source, sender_ids: Iterable[str], since) -> IdComparison(missing_in_ledger: list[str], unknown_in_ledger: int, open: int, counts: Mapping[str, int])`: hashes each given sender id with `delivery_key` and the same `key`, and compares both directions (dealdesk `inbox.py:271-287`); id-reuse rows are counted under `refused`, never as unknown; `missing_in_ledger` lists the caller's own ids (it gave them), `unknown_in_ledger` is a count (we hold only hashes). Not to be confused with the tick's `reconcile` step (`tick.py:251`). KEPT: comparing against the source's own ids is one of P7a's controls and bible R368 (an owner hard rule). **Said plainly (resolve row R2-ADV-17):** `compare_ids` and `list_inbound` have no caller in v1; nobody can compare ids or list waiting messages without code until V7 or AK-G15 ships (PENDING LEAD 4 (viii)).
  6. **Start a run, at most once per generation (-a).** `Runtime.handle(..., run_id: str | None = None)`: when given, the `Run` is built with that id; if `create_run` raises `StaleState` FOR THAT GIVEN ID, `handle` reads `store.get_run(run_id)`: if its `agent_id`, `principal_id` and `trigger_ref` equal the call's, it is returned at once (no "received" note, no redaction, no model call, no meter hold); else the `StaleState` is raised again (`run_step` maps it to `step_error`, the receipt is released, and the next claim finds the run and gives `run_mismatch`). A run cut off by a crash or an error after `create_run` goes to a person as `run_interrupted`; the `stuck` step moves the run itself to `NEEDS_PERSON` after `stuck_after_s` (`tick.py:112-122`). Only failures BEFORE `create_run` are retried: `Unqualified` (`agent_loop.py:339-340`; the agent fell out between check and run; `run_step` gives `step_error`), a `StoreUnavailable` from `create_run` itself (`step_error`), and `audit_unavailable` on the AK1 intent (not counted). **Reopen** (AK-G15, over `reopen_inbound`) gives a NEW run id (`run_id_for(key, generation + 1)`), so a new run starts and can pay again; that is a person's choice.   7. **The webhook door (-b, `triggers/webhook.py`).** `handle_inbound(inbox, doors: Mapping[str, tuple[InboundSource, WebhookSource, tuple[str, ...]]], path: str, headers: Mapping[str, str], body: bytes, now_ts: float) -> tuple[int, Mapping[str, str], bytes]`; `doors` maps each source name to its ledger record, its config entry and its resolved secrets (current first), built once by `app.build` and never logged. In order (the status order 404, 413, 401 is intended): (1) path must `re.fullmatch(r"/inbound/([a-z][a-z0-9_-]{0,39})", path)` and name a configured source, else 404; (2) `len(body) > max_body_bytes` gives 413 BEFORE any HMAC work (a body of exactly `max_body_bytes` is accepted); (3) `hmac_v0.verify(headers, body, now_ts, secret, header_prefix)` tried with each resolved secret in order; none true gives 401; (4) only now is the body parsed: `json.loads` with an `object_pairs_hook` that refuses a repeated key; it must be UTF-8 JSON whose top level is an object holding `id_field`, and that value must be a JSON string (a number gives 400); any parse error (`ValueError`, which covers bad UTF-8 and bad JSON, and `RecursionError` from deep nesting), a repeated key or a missing field gives 400; (5) `check_sender_id` on that value (`ValueError` gives 400); (6) `inbox.receive`: `new` and `duplicate` give 202, `id_reuse` and `id_reuse_capped` give 409, `busy` gives 503 with `Retry-After: <retry_after_s>`; a store error gives 503; any other exception gives 500. Every reply body is `b""`. Nothing is logged but the source name, the status and a closed code; refusals (404, 413, 401, 400) are logged at DEBUG only, so a flood of forged requests writes nothing at INFO or above (row W16; rate and flood handling are AK-G16's; the revision 2 once-a-minute limiter is cut). `serve(...)`: a dev-only stdlib server like `receiver.serve`, with its OWN copy of the two-line Content-Length parse (`receiver.py:45-52`; a shared helper is row V12); it looks the source up from the path BEFORE reading the body, so it applies that source's `max_body_bytes` to Content-Length.
     - **Forwarder contract (what a sender must do; goes into the runbook).** Re-sign EVERY attempt with a fresh timestamp; a 401 after a retry means "re-sign and send again", not "give up". Send one JSON object per request, with unique keys. Put the message's id in `id_field` as a JSON string. Resend a retry byte for byte (a re-formatted retry is an id reuse, 409). On 503, wait `Retry-After` seconds and retry.
     - **Accepted limit (dev server only):** a caller can tell a configured source name (401) from an unknown one (404). Source names are configuration, not secrets; AK-G16 owns the production door and may answer one status for both (PENDING LEAD 4 (vii)).

- **Security and least-privilege notes (identity, rights, secrets, personal data, dev-only flag):**
  - **Identities.** No new identity. The runtime role gets exactly: `inbound_receipts` SELECT, INSERT, UPDATE (limited by the trigger); `inbound_bodies` SELECT, INSERT. Per-action reason: INSERT (write-ahead receipt and body), UPDATE (claim, release, finish, reopen; receipts only; final rows frozen by the trigger), SELECT (claim, dispatch, `compare_ids`, the orphan count), DELETE (purge of final bodies, purge role only). Negative tests: rows L14, L15.

  - **Signed inputs.** Unsigned, stale (more than 300 s either way) or wrongly signed requests are refused before the body is parsed and before any write. Replay inside 300 s is a `duplicate`. Replay after 300 s fails the signature. Replay to ANOTHER source of the same deployment fails, because no two sources share a secret (C7). The sender id comes from the signed body only. The tenant, readers, agent and principal come from config only.
