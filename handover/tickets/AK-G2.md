**Words used (plain meaning, one meaning each).**
- **trigger**: an outside event that should start work: a signed web request from another system (a **webhook**), or a time on the clock (a **schedule**). An e-mail reaches us in v1 as a webhook sent by a forwarder (see PENDING LEAD 1).
- **sender**: the outside system that sends a webhook. **source**: one configured way in (one webhook address or one schedule), bound in config to exactly one tenant, one readers list and one agent.
- **delivery**: one arrival of a message. The same message can arrive more than once (the sender retries). **sender id**: the id the sender gives its message (for example an e-mail's message id), read only from the signed body.
- **receipt**: the row we write BEFORE we answer the sender. "Write-ahead" means: the receipt and the message body are saved first; only then does the sender hear "accepted".
- **delivery key**: the SHA-256 of `tenant_key(tenant, source, sender id)`. We store this hash, never the raw sender id (a sender id can hold an e-mail address).
- **duplicate**: the same sender id with the same body again: nothing new happens. **id reuse**: the same sender id with a DIFFERENT body: the first stays untouched and the new one is kept as its own refused row (it is never dropped and never merged).
- **claim / lease**: a worker takes a receipt for a limited time (the lease). If it crashes, the lease runs out and another worker can take the receipt again.
- **final state**: `done`, `needs_person` ("a person must look") or `refused`, the same three words as AK1. Every receipt ends in exactly one. Open states are `received` and `claimed`.
- **dead letter**: a row in the existing `dead_letters` table for a receipt that failed too many times; the receipt itself ends `needs_person`.
- **backpressure**: when too many receipts of one source are open, we answer "busy, retry later" BEFORE saving anything; the sender still holds the message. We never accept and then drop.
- **pilot/prod**: a config whose `environment` is pilot or production (P6a).
- "UNVERIFIED" = I did not read it in code or could not run it. "PENDING LEAD" = an owner or lead decision, with my recommendation first. "INFORM" = my decision on my recommendation, final unless the lead says otherwise (order 23 item 4).

## The decision that shapes this ticket (INFORM I1, recommended; read before the fields)

Options for "one input kind feeding the AK1 step contract":
- (a) Build every way in that GAPS G2 lists now: webhook, schedule, mailbox reading, folder drop, queue pull, each with its own adapter and contract suite. Biggest surface; three of the five have no consumer yet and each brings a vendor or file-system edge.
- (b) **Recommended: one door plus the clock.** v1 builds ONE ledger (the old P7a, fixed), ONE signed webhook door and ONE schedule source on the existing tick. A mailbox, a folder or a queue reaches the door through a forwarder that signs with `hmac_v0` (the client's own mail or automation tool, or a self-hosted no-code flow; this is the "signed webhook in" door of the client-chooses-tools policy, item 5). Native readers are later rows (V1-V3) with triggers. Every delivery, whatever its door, becomes one `StepInput` handed to `run_step`.
- (c) A workflow engine or message broker as the inbound layer: rejected for v1 (a new dependency for a problem a table and a tick already solve; kept as the written alternative below).

Why (b): it closes the BLOCKER for the first shape (document intake by e-mail works once the client's mail is forwarded) with the least new code, and every later door reuses the same ledger, key rule and tests. Cost, said plainly: a client whose mail cannot be forwarded and who refuses a forwarding tool is not served by v1 (PENDING LEAD 1). Confidence 75 percent; reversible (a native reader is a new source that writes to the same ledger).

- **Fail closed, and never lose.** A store error before the receipt commits answers 503 (the sender retries); after the commit, every failure leaves the receipt open, and the lease brings it back. Exactly one run per message: the run id is derived from the delivery key (INFORM I3).
