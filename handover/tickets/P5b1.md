## Words used in this ticket (defined once)
- **provider**: the company whose model Hadavin calls (Claude API, Amazon Bedrock, an OpenAI-shaped server, Gemini). **Provider text**: any string a provider (or a library reading its reply) produced: an error message, an error body, a status line phrase, a header value, an error code string. It can quote the request, so it can hold personal data, a document line or part of a key.
- **fact**: one small checked value about a failure: a number in a fixed range, a word from a fixed list, or a short token of a fixed shape. A fact is never free text.
- **closed list**: a list fixed in our source code; a value outside the list is replaced by `other` or dropped, never copied. **Shape check**: a whole-string pattern check (`re.fullmatch`) that rejects anything else, including a trailing newline.
- **adapter** (the plan calls it a "per-kind hook"): a small function that reads one failed call's exception object and returns the facts. One per kind that has its own error library (Claude library, Amazon library); every other kind uses the neutral one that knows only the Python standard library.
- **attempt**: one request sent to the provider. `max_attempts` is the setting (1 to 10, `backends/table.py:40`).
- **hostile**: chosen by someone who wants to put text, numbers or size where our code does not expect them: a provider, a server in the middle, or a misconfigured gateway.
- **step R1P**: the second step of the diagnostics redesign (P5a is step R1, the closed codes and the safe text; this package is step R1P, the provider part: it fills the facts that P5a's `diagnose` reads). Nothing else is meant by the letters.
- **read-recorder test**: a test where a stand-in error object writes down the name of every attribute our adapter reads, and the test compares that list with the allowed list. (Revision 1 called this a "tripwire".)
- **mutant**: a deliberate small break of the new code (for example, delete one check). The tests must fail on it. A mutant the tests do not catch is a gap in the tests. **Stand-in**: an object built by the test instead of one produced by a real library or wire; every stand-in is named and labelled in the tables.
- **strict expected failure** (`xfail(strict=True)`): a test known to fail today for a named reason; it must fail now and turns into a build failure the day it starts to pass, so the label is removed on purpose.

## Problem in plain words
When a call to a model provider fails, our retry code builds an error message from text on the provider's side: the error code string for Amazon Bedrock (`llm/bedrock.py:101`) and the class name of whatever the library raised (`retry.py:79`); the class name of an Amazon error is the provider's own error code. The error also carries no machine-readable facts, so nobody can tell "wrong key" from "rate limited" from "provider down" without reading text. The redesign forbids printing provider text at all, because an error body can quote the request (a document line, a name, part of a key). This package gives the error object a few checked facts (HTTP status, a word from a fixed list for the kind of error, a request id of a fixed shape, whether it was retried, and which attempt failed) and builds the message only from those and from the class name that P5a's `class_name_of` allows. After it, the message and the stored text of every provider failure hold nothing a provider typed, and a hostile reply (injected text, a wrong-sized number, a huge body, an object that raises) cannot put text or numbers into them.

## Interface (names, argument and return types, errors)
Names come from `P5a.md` (READ) or D5/D6; where the merged P5a differs, the builder follows the merged code and records the difference in the evidence.

1. `ProviderError.__init__(self, *args, status=None, error_type=None, request_id=None, retryable=None, retry_count=None)` (all keyword-only; `ProviderError("text")` and `ProviderExhausted("text")` stay valid, and so does a subclass that passes only text, such as P4a's `UsageMissing`: its five attributes read `None`). It calls `super().__init__(*args)`. Attributes of the same names, class-level defaults `None`, set in `__init__` (so they sit in `vars(err)`, where P5a reads them). Each is CHECKED at construction and an invalid value is DROPPED to `None` (the constructor never raises; an error inside error handling is worse than a missing fact):
   - `status`: exact type `int`, not `bool`, 100 to 599, else `None`.
   - `error_type`: a member of `ProviderErrorType` (P5a: `rate_limit, overloaded, invalid_request, authentication, permission, not_found, server_error, timeout, connection, throttled, quota, other`), else `None`. A plain string is not accepted.

Stored as the plain `str` value. Else `None`.
   - `retryable`: exact `bool` (True = our retry rule treated this failure as worth another attempt), else `None`.
   - `retry_count`: exact `int` 0 to 1000 (P5a's bound for `retry_count`, P5a.md line 37), else `None`. `with_retry` always sets the number of the FAILING attempt, counted from 1.
   Subclass `ProviderExhausted` inherits all of it. Pickle and `copy` keep the attributes (default behaviour, pinned by a test). `__cause__` is not pickled (standard Python).

### From facts to the closed code (the "which code" table; D4)
The code is chosen when the error is diagnosed by P5a's `diagnose` (P5a.md line 38) plus this package's follow-on edit (Interface 6). The code names are P5a's (`provider_http, provider_timeout, provider_rate_limit, provider_invalid_request, provider_auth, provider_exhausted`).
1. Class `ProviderExhausted` -> `provider_exhausted` always. The facts (`http_status`, `provider_error_type`, `request_id`, `retry_count`) still show (follow-on edit (b)).
2. Plain `ProviderError`: by status first: 429 -> `provider_rate_limit`; 401, 403 -> `provider_auth`; 400, 404, 422 -> `provider_invalid_request`. Status absent or not in that list -> by error_type: `rate_limit`, `throttled`, `quota` -> `provider_rate_limit`; `authentication`, `permission` -> `provider_auth`; `invalid_request`, `not_found` -> `provider_invalid_request`; `timeout` -> `provider_timeout`; `overloaded`, `server_error`, `connection`, `other` -> `provider_http`. Nothing known -> `provider_http`.
3. A failure to understand a 200 reply (missing key, bad JSON, `ValueError` from the Gemini parser) is a plain `ProviderError` with no status and no error_type -> `provider_http`.

## Retry interplay
- The retry decision (`transient`), the wait (jitter, `retry_after`), the number of requests, and which class is raised are IDENTICAL to ce70eb5 for every input that does not make the old code raise a raw exception. Pinned by a table of (kind, status or failure) -> request count that PASSES on ce70eb5 (regression pins, R2).
- **Inputs whose outcome changes (stated plainly).** On ce70eb5 each of these lets a raw Python exception escape `with_retry` (the callers catch only `ProviderError`): (1) a `status_code` or `code` property that raises; (2) a `reason`, `__cause__` or `__context__` property that raises, or an `__eq__` that raises, inside the chain walk; (3) a kind `retryable` hook that raises; (4) a Bedrock `ClientError` whose `response` is not a dict (`retryable` at :108); (5) a `headers` object whose lookup raises something other than the three caught errors (`retry_after`). After this package (1)-(4) end as a plain `ProviderError`, not retried, one request, no facts; (5) waits 0 seconds. This is a money-adjacent change: `askdata/pipeline.py:163` bills `ProviderExhausted | OSError | TimeoutError` and treats a plain `ProviderError` as "refused, free" (READ), so a call that crashed raw before (UNVERIFIED how each caller then billed it) is now counted free there. PENDING LEAD 4 asks whether that should be refused or exhausted; recommended: refused for v1 (a fail-closed refusal is the safe side, and P4b2's settle-at-reserved covers the money).
- Facts are read once per RAISED error (the last failing exception), not per attempt, so a retried failure costs nothing extra. `retry_count` is the attempt number at which the error was raised: 1 for an immediate refusal, `max_attempts` for exhaustion, 2 when attempt 1 was retried and attempt 2 was refused (row 29). `retryable` is the answer of `transient()` for that last exception (True for exhaustion, False otherwise). P4b2, which counts every failed attempt, calls `safe_facts` itself per attempt (Hot files).
- A hostile status (outside 100 to 599, not an `int`, a `bool`) is NOT copied as a fact and NOT printed, but the retry rule is not changed: ce70eb5 retries any `int` status of 500 or more (`retry.py:39-40`; RAN: a real server can make `urllib` produce status 777). I did not make it "no retry" because that would turn a today-"exhausted" (billed by `askdata/pipeline.py:163`) into a "refused, free" error. Both this and the unbounded success-body read belong to P4b2's billing contract: I READ `P4b2.md` and `P4a.md` and neither carries a row for a made-up status or for a body size cap (a grep for `777` finds one unrelated test value; a grep for a response cap finds nothing). PENDING LEAD 10 asks the lead to have P4b2 add both.
- `with_retry` still re-raises `ProviderError` from `call` untouched (P4a's "refuse an estimate" error, `UsageMissing` and any later billing marks pass through with their own attributes).
- **One counter meaning.** `retry_count` (here) and P4b2's `attempts` both mean "requests started, up to and including the failing one", so on every error raised by `with_retry` they are equal. P4b2 derives one from the other or its test T6 also asserts equality.

## Fail-closed behaviour (each item has a test row)
1. A fact that fails its check is dropped (`None`); a string that is not in a closed list is `other` or dropped. Nothing provider-typed is ever copied, truncated and kept.
2. Nothing in the failure path can raise out of `with_retry` except `ProviderError`/`ProviderExhausted` (and `KeyboardInterrupt`/`SystemExit`): not the facts adapters, and also not `status`, `retry_after`, `_chain`, `transient`, the kind `retryable` hook, `_code`, or the Bedrock `retryable` on a non-dict `response`. Exact-type checks (`type(x) is dict`, `type(x) is str`) mean a subclass of `dict` or `str` that overrides `get`, `__eq__`, `__hash__`, `__len__` or `__iter__` cannot choose the error type or make us loop. Tested end to end through `with_retry` (R5), not only on the adapter.
3. If the adapter itself fails, the error is STILL raised as before (`ProviderError` or `ProviderExhausted`) with no facts; the diagnosis then says `provider_http` (or `provider_exhausted`) with no extra facts. Never silence, never a generic crash.
4. `KeyboardInterrupt` and `SystemExit` from an adapter or a hook propagate (they are not `Exception`).
5. A missing optional library (Google auth for Vertex) never raises `ImportError` inside `facts` (same lazy import pattern as `anthropic.retryable`).
6. The message of our error is built from a fixed grammar (tested), so even a future adapter bug cannot put text into it.
7. A kind that forgets to set `facts` gets the neutral adapter, not "no facts and a raw message".

## Security and least-privilege notes (identity, rights, secrets, personal data, dev-only flag)
- No new identity, role, grant, secret, kind or setting. The adapters read only the exception object; they receive no key, no prompt, no document. No `dev_only` flag (no kind added).
- Personal data: provider text is never printed (design section 1). The allow-list table above is the enforcement; the read-recorder test (R4) and the message grammar (R6) prove it; the source guard (R7) keeps it from regressing inside `llm/` until P5b3's full taint guard exists.
- Hostile values: numbers are bounded; tokens have a shape; words come from closed lists; types are exact; objects are read through `safe_attr`; the work per failure is constant (no loop over body, headers or message text; the only loop is `_chain`, 8 deep, existing).
- Request ids are logged-grade identifiers (a provider support reference), not secrets; they are shape-checked because a hostile provider could otherwise put chosen text there.
- Wording rule: no new operator-facing text beyond the existing message grammar; labels stay the existing kind names.
- State and races: no database, no multi-row SQL, no lock order. Adapters and the checks are pure functions of one exception object; `NetworkLLM` keeps no new state, so there is no race test (the retry loop is per call, as today).
