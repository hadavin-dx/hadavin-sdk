**Words used (plain meaning, one meaning each).**
- **person**: the human who writes to the agent (for example a shop's customer). **user id**: the made-up id of that person in our records (for example `user-1`).
- **conversation**: one chat between one person and one agent, kept as an ordered list of **turns**. A **turn** is one message: either the person's (role `user`) or the agent's (role `assistant`). One **exchange** = the person's turn plus the agent's answer turn.
- **reply**: the text the agent sends back to the person for one exchange. A **fixed reply** is a reply whose words come from configuration, not from the model (for example "A person will take over this conversation.").
- **hand-off**: the agent stops answering in this conversation and a person takes over; one item is put into the "needs a person" queue (AK-G15).
- **history**: the earlier turns the model is shown on each call (the model remembers nothing between calls, R94).
- **mask / placeholder / put back**: as in P5c (`tickets/P5c.md:64`): a protected value such as an e-mail address is replaced with a placeholder such as `<EMAIL_1>` before text goes to the model; put back = replace the placeholder with the real value again.
- **lease**: a short claim on a conversation while one exchange is being answered, so two messages of one conversation are never answered at the same time. It expires after a set time so a crash cannot block the conversation for ever.
- **recipient gate**: AK-G22's one path for text sent TO a named person or system (check the recipient is allowed, send limits, no duplicate send). **AK1 gate**: AK1's one path for text sent to a third party for PROCESSING (the model). Order 27 item 63: every outbound text goes through one of the two.
- **pilot/prod**: a config whose `environment` is `pilot` or `prod` (`config.py:317`).
- "UNVERIFIED" = not read in code by me, or not run. "PENDING LEAD" = an owner-only decision, with my recommendation first. "INFORM" = my decision on my recommendation, final unless the lead says otherwise (order 23 item 4).

## The decisions that shape this ticket (read before the fields)

**D1 (INFORM I1): extend the existing Runtime, do not write a second agent loop.** Options: (a) a new chat loop module with its own model call, tool step, limits and audit: duplicates `handle`'s guards (caps, map saves, screens, audit), which every later fix would have to make twice; (b) **recommended:** a new method `Runtime.handle_turn` beside `handle`, with the read-tool block of `handle` (`agent_loop.py:455-538`) moved verbatim into one private method `_tool_step` that both call; actions keep going through the existing `_submit` (`:632-722`); (c) call `handle` once per message with the history packed as the "document": `handle` drops the reply text (`:450-451`) and sends the history as an untrusted document, so it cannot answer a person without the same edit as (b). Why (b): one tool step, one limits check, one audit shape, one meter scope per run (P4c-2). Cost: `runtime/agent_loop.py` is a hot file (P4c, P5c, amendment A9 F6), so AK-G1-b builds after both. Confidence 80 percent; reversible.

**D2 (INFORM I2): one run per exchange, ending `NO_ACTION` with reason `replied`.** Each person message starts one `Run(trigger_kind="user", trigger_ref="<conversation id>:<turn number>")`; ids only in `trigger_ref`. An answered exchange ends `NO_ACTION` with `reason_code="replied"` (the run took no action; the reason says it answered). A new state `REPLIED` would need a migration of the `runs.state` CHECK (`0001_core.sql:12`) and a change to `ALLOWED` (`runs.py:10-21`) for no safety gain: cut (row V9). The exchange ends through `_to`, never through `_abstain`, so no abstain card is posted to the approvals channel per message (`_abstain` posts at every level, `:569-597`).

**D3 (INFORM I3): no put-back into replies in v1.** The reply to the person is masked again and every placeholder is shown as a plain label (`<EMAIL_1>` becomes `[hidden email]`). Reason: a placeholder in the reply can stand for a value from a TOOL result (another customer's address, for example); putting it back would send that value to this person. Telling apart "the person's own value" from "a tool's value" needs a per-placeholder origin record: more surface. Cut; row V3 with trigger. Owner-visible limit (PENDING LEAD 3): the person sees `[hidden email]` even for the address they typed themselves.

**D4 (INFORM I4): a placeholder never means two values in one conversation.** The history is stored masked. Only identifier kinds of the map are saved (`storable`, `agent_loop.py:252-254`), so after a restart the counters for an e-mail would start again at 1 (`redact.py:899-908` counts from map keys) and a new address could become `<EMAIL_1>` while `<EMAIL_1>` in the history meant another one. A model that then passes `<EMAIL_1>` to a tool would look up the wrong person. Fix at the choke point: the conversation record keeps `floors` (label -> highest number ever issued in this conversation), and every exchange opens the mask session with the saved map AND the floors, so numbering always continues upward. An earlier placeholder whose original was not saved stays a placeholder (it is never put back to a wrong value; a tool given it finds nothing). If P5c's built mask session has no way to take floors, AK-G1-b adds one keyword argument `floors` to it (one P5c file edit, after P5c-2 merges; UNVERIFIED until then).

**D5 (INFORM I5): the conversation's map reuses the `redaction_maps` table.** It is saved with `put_redaction_map(conversation_id, storable(map))`; a conversation id (`conv-<32 hex>`) cannot equal a run id (`run-<32 hex>`). `purge_redaction_maps` already ages a map whose key is no known run by its own time (`store/protocol.py:145`; implementation UNVERIFIED, pinned by row A11). Each exchange re-saves it, so an active conversation's map is not purged under it. Cost: none new; `forget_user` deletes it by key.

**D6 (INFORM I6): hand-off is final for the agent in v1.** After a hand-off, the agent never answers that conversation again; new messages are stored masked and not sent to the model, and no reply is sent (the host shows the status from the result). A person continues through the AK-G15 queue. Giving the conversation back to the agent is row V2. Smallest surface; the safe direction.

**D7 (INFORM I7): actions proposed in a chat always need a person.** A conversational agent must have `levels` set (never `None`, the dev slice-1 path that can execute on `allow`, `agent_loop.py:552-558` and `:710-722`) and every level must be `shadow` or `suggest`; config load refuses anything else in every environment. When the model proposes an action, the exchange's reply is a fixed reply ("Your request was passed to a person."), never model text. Telling the person the final outcome later is row V4.

**D8 (INFORM I8): no summaries in v1.** History is cut to the last N turns (R96, default 8). Summaries (R97, with its delimited user-role block and compaction rules) are row V1.

**Ladder line (tool-ladder rule).** Rung 1 (reuse core): the loop, the store, the masking, the meter. The chat window itself and the transport (a web widget, a messaging app) are NOT in this package: the host app or AK-G2's signed webhook brings the message in and calls `handle_turn`; a no-code tool may be that host on the client's say-so (client-chooses-tools rule). No third-party agent memory service (R98 forbids it).
