Message: `"migrations are inconsistent: "` + problems joined by `"; "`, capped. Every file name or ledger name in a message is written as `ascii(name)[1:-1]` (escapes control characters, ANSI escapes and undecodable bytes, so a hostile name cannot inject into a terminal or make `print` fail; the slice removes the outer quotes that `ascii()` adds, so the old messages keep their exact text, as `test_plant_badly_named_file_is_caught`, `test_k2_migrations.py:50-55`, requires). At the CLI a `ConfigError` is printed as `refused: <message>` and exits 2 (`cli.py`, function `main`); other exceptions exit 3, so every new refusal must be a `MigrationNumberError`.
  - `list_migration_files(folder: Path) -> list[Path]`: `os.scandir` entries whose name ends in `.sql` in any letter case, sorted. Entries without that suffix are ignored at runtime, as today.
  - `check_ledger(paths: list[Path]) -> list[str]`: THE implementation (list-based). It returns problems and never raises for a bad file. For each path: a name not matching `NAME`; number `0000` (`<file>: number 0000 is not allowed, numbers start at 0001`; today the gap check counts from 1 and never reports it); an entry that is not a regular file or a symlink to one (`not p.is_file()`: directory, dangling link) gives `<file>: not a regular file (a directory, or a link that points nowhere)`; then `p.read_bytes()` decoded as UTF-8, where `OSError` or `UnicodeDecodeError` becomes `<file>: cannot be read (<exception class name>)`, because `is_file()` is not a readability test. - Security and least-privilege notes (identity, rights, secrets, personal data, dev-only flag):

P3a creates no role, adds no command and widens no right. The hand recipe is run by the migration role only (a database administrator, not the runtime and not an agent); it records nothing automatically, so the change-log line in the recipe is the audit trail (no persistent mark exists; a column would need its own migration, left to a later package; Open point 8).
  - `schema_migrations` is not in the grant map, so no runtime right exists on it, and a PUBLIC grant on it is refused (`tests/test_k5_round10_postgres.py:137-142`).
  - Tests use throwaway schemas on the test database (CI: trust-authentication container); the test connection is the owner role and reads `pg_catalog`. No secret, no real data; planted SQL and seeded rows are made up.
