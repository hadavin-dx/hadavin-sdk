## Words used in this ticket (defined once)
- **text**: the string a caller hands in (a name, an invoice number, a document line). **fold**: the function that turns text into a comparison form in which look-alike characters, invisible characters and case no longer matter.
- **key**: the folded text (a string) a view returns. A key can hold personal data; never log it. **key_digest**: the SHA-256 hex string of a key (stored form, P1c; with a salt it is an HMAC). Unsalted it is only a pseudonym: anyone with a list of likely names can recompute it. **table_digest**: the SHA-256 of the look-alike table (not of a key).
- **view**: one named function that returns a key or a key-set for one purpose. The four view names are exactly `identity_key`, `id_key`, `scan_keyset`, `id_keyset` (the constant `VIEWS`); no other spelling is used anywhere (`names_equal` is a prose helper, not a view).
- **DENY decision**: "block this if it looks like a protected value" (blocklists, leak scans, same person); over-matching is the safe side. **ALLOW decision**: "accept only if it IS the verified value"; the fold is never used for it; `allow_equal` is the only allow path.
- **reading**: one complete way of turning a text into a key. A **key-set** is the small set of keys one text gets (one per reading); two texts match when their key-sets share a key. **FOLD_VERSION**: ONE string naming exactly which fold produced a key (P1a).
- **hidden channel**: tag characters (U+E0000 to U+E007F) and variation selectors (U+FE00 to U+FE0F, U+E0100 to U+E01EF): characters that show nothing but can carry text. **refuse**: the caller treats the text as blocked.

## P1c: stored keys (SEPARABLE; PENDING LEAD: the resolve report recommends dropping it from v1 into a later ticket; if dropped, delete this section and every P1c word above)

- **Interface.** All arguments keyword-only. Errors (all derive from `TextnormError`): `MalformedStoredKey`, `FoldVersionMismatch`, `SaltMismatch`. Constants: `TEXTNORM_MIN_SALT_BYTES = 16`; `key_id` grammar `[A-Za-z0-9._-]{1,32}` (the resolve report gives 32; correctness C6 gave 64).
  - **`view_version(view_name) -> str` (A8).** One version string PER VIEW: `f"view={view_name}|alg={alg}|beh={12 hex of the constants of THAT view}|tbl=...|ucd=...|ud=..."`, built from `BEHAVIOUR_CONSTANTS[view_name]`. A change of a scan-only constant (entity rounds, class map) therefore does not invalidate identity keys; `html.entities.html5` is NOT in the identity view's `beh` (that view has no entity step; the digest can change with a Python patch release). P1c drops the `p` from `alg` (`fold2`); `FOLD_VERSION` stays the all-views display string.
  - **`stored_form(*, view_name, text, salt: bytes | None, key_id: str | None, unsalted_pseudonym: bool = False) -> str`** (the stored record is named `stored_form`, a record, not a key: A18). `view_name` is one of `identity_key`, `id_key` (single-key views); `stored_form_keyset(*, view_name, text, salt, key_id, unsalted_pseudonym=False) -> str` takes `scan_keyset` or `id_keyset`. **Salt rules (A7, C6):** with a salt, `key_id` is REQUIRED and `len(salt) >= TEXTNORM_MIN_SALT_BYTES` (an empty or short salt raises); without a salt the call is refused unless `unsalted_pseudonym=True`, and then `key_id` must be None. The record: `f"{view_version}#kid={key_id or 'none'}#kcv={kcv or 'none'}#{digest}"`; `kcv` (key check value) = first 16 hex of `HMAC-SHA256(salt, b"textnorm-kcv\x00" + key_id.encode("ascii"))`; the digest is `HMAC-SHA256(salt, frame(view_version, key))` with `frame(*parts)` = each part as `f"{len(p)}:{p}"` concatenated (**domain separation: the same key from another view or version gives another digest, and one salt no longer links all views**); unsalted it is `SHA-256` of the same frame. Comparison uses `hmac.compare_digest`. A set record is `f"{view_version}#kid=...#kcv=...#{d1},{d2},..."`, per-key digests sorted and unique (fixed 64-hex length, so no ambiguity); **the `n=` count of revision 4 is dropped**; the number of digests still shows how many keys the text had (tags, Eta or Ze present), documented. **The stored digest list is the only per-key form; `keyset_encode` (P1a) is the ONE canonical text of a key-set and is used for hashing a whole set in the golden test; the two are different objects (a canonical text and a list of per-key digests) and the ticket never calls both "the key-set form".** **Empty key-set rule:** `stored_form_keyset` raises `EmptyKey` when the key-set is empty (a text that shows nothing is not a stored identity); `stored_form` raises `EmptyKey` for `""`; so `stored_form_keyset_matches(stored=stored_form_keyset(x), text=x)` is True for every `x` that can be stored (C6 b).

## Which view each caller uses, and the stated limits
Names, e-mail, domains, separation of duties, blocklists of words: `identity_key` for equality and unique indexes, `same_person`, and `deny_hit` over `scan_keyset` for substring checks. Invoice numbers, PO numbers, IBAN, account numbers (letters and digits ids): `deny_hit` over `id_keyset`, built with `prepare_needles(..., view="id_keyset")`. The look-alike table has NO ASCII sources (0 entries below U+0080, probed), so capital I, lowercase l, digit 1, letter O and digit 0 are equated ONLY by the id view (`squeeze("paypaI", loose=True)` equals `squeeze("paypal", loose=True)`), while `fold_key("paypaI")` is `paypai`: a word-blocklist check does not cover I/l/O/0 confusion. The id view strips punctuation, and the loose map also equates S/5, B/8, Z/2, G/6, Q/9 and the class map equates 2 and 3, so it over-matches (the safe side for DENY, never for ALLOW). Known limits, each pinned by a row: a text that needs the capital-letter reading at one place and the lowercase-first reading at another (pass A and B mixed); a payload split between the visible text and the hidden channel with other visible text between (refused by default); I/l/O/0 in the word view; Tamil or Runic letters beside Latin (not folded, not flagged); the adversarial scan time of a final-code build (UNVERIFIED until the builder measures).
