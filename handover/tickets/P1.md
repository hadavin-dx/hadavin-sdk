## Words used in this ticket (defined once)
- **text** or **raw text**: the string a caller hands in (a name, an invoice number, a document line).
- **fold**: the function that turns text into a comparison form in which look-alike characters, invisible characters and case no longer matter.
- **key**: the folded text (a string) a view returns. A key may hold personal data; never log it.
- **digest**: the SHA-256 hex string of a key (the stored form). A digest of a name is only a pseudonym: anyone holding a list of likely names can recompute it. It is not protection.
- **view**: one named function that returns a key (or a set of keys) for one purpose: `identity_key`, `id_key`, `scan_views`, `name_key`. A caller picks the view that matches its job.
- **DENY decision**: "block this if it looks like a protected value" (blocklists, leak scans, same person). Over-matching is the safe side. **ALLOW decision**: "accept this only if it IS the verified value". The fold is never used for ALLOW; `allow_equal` is the only allow path.
- **key-set**: the small fixed set of keys a DENY check builds for one text (defined under P1b).
- **FOLD_VERSION**: ONE string that names exactly which fold produced a key (defined under P1a).

  - **The DENY key-set (P1b; decisions A13(4), construction proposed here and reviewed in round 2).** Identity is ONE string: Cyrillic Ze (U+0437, and capital U+0417) reads as `3` in it, as in PR #50 (probed: `fold("з")` gives `'3'`). The key-set is built from three yes/no choices applied to the WHOLE text, never per letter: (1) case reading: "own case" (each letter mapped by its own case before the final case fold: capital Eta reads `H`, small eta reads `n`, which is what a human sees) or "case first" (the identity pipeline); (2) Ze reading: `3` or `z`; (3) word splitting: glued or spaced (gap 5). That is at most 2 x 2 x 2 = 8 keys; duplicates collapse. `defaults.TEXTNORM_MAX_SCAN_KEYS = 8`; the builder raises `ScanKeysExceeded` (a deny error, never truncates) if code ever produces more, and a test proves it cannot (all code points plus hostile text). Because every letter is read by its own case in one key and case-first in another, a text that mixes capital Eta and small eta is covered (test: "ΗηΗη" in `scan_keyset` and the blocklist entry "hnhn" match); no per-position product exists, so 20,000 ambiguous letters cost the same 8 keys. Empty keys are left out of the set. **Encoding:** `keyset_encode(keys)` = the unique keys sorted by code point, each written `"<len>:<key>"`, concatenated (so `("ab","c")` and `("a","bc")` cannot collide); used only when one value for a whole set is needed. Matching and storage use one digest PER KEY. **Match rule:** `scan_match(a, b)` is True if the two key-sets share at least one key (non-empty intersection). **`same_person` in P1b is `scan_match`, which is NOT transitive:** "з" matches "3" and matches "z", but "3" does not match "z". Never use `same_person` for a unique index, a dedupe or a group-by; use `identity_key` equality, which is transitive.
  - **P1b stored keys.** `stored_key` returns `f"{FOLD_VERSION}#{view}#{digest}"` where `digest` is the SHA-256 hex of the view's key (for the key-set view: one such string per key, as a tuple, never a joined string). If `salt` is given the digest is HMAC-SHA256 with that key (the caller gets it from the secrets kind) and comparison uses `hmac.compare_digest`; without salt it is a pseudonym, as stated above. `stored_key` refuses an empty key (`EmptyKey`). `parse_stored` raises `MalformedStoredKey` (no content echoed) unless the string matches the format. `check_stored` raises `FoldVersionMismatch` if the version differs from `FOLD_VERSION` or the view is not the expected one; the message shows a version only if it matches `^alg=fold[0-9]+\|` and then at most 80 characters, otherwise a fixed text. It never returns False. A key from another version is never compared silently: the caller re-folds from raw text it kept (under its own protection) or sends the item to a person (F3). Cost, stated plainly (A5): P1b changes the algorithm id, so every `fold1` key anyone stored is refused; callers that store keys (P3b, maybe P2a) must keep raw text or accept one human decision per stored item per version bump; their tickets must name who decides.
