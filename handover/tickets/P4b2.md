- **release**: give the whole reserved amount back (`release_spend`; row status `released`, `settled_usd` empty). Only on proof that no bill is possible.

## Rules stated once (both sub-tickets)
1. **The one rule (fail closed).** A reservation is RELEASED only on positive proof that no bill is possible. Every doubt, every unreadable value, every exception type nobody classified, and every error on the billing path keeps the worst case or MORE. The only direction a mistake may go is "counted too much". Releasing a call that was billed is the one error this package must make impossible. Where billing is unknown the book is the UPPER bound (LEAD-ORDERS 14(3)).
2. **Terms of proof (one definition each).**
   - *refused*: the provider answered the attempt with an HTTP status that is in the allow-list constant `REFUSED_STATUSES = (400, 401, 403, 404, 405, 413, 415, 422, 429)` in `llm/retry.py`, each entry with a one-line reason (the request was rejected before the model ran). Every other status is *unknown*: 402, 408, 409, 418, 424 (Bedrock `ModelErrorException`: the model failed while processing), 499, every 5xx, and any number outside 100-599 (status 777 in P5b1 item 9). `bool` is not a status.
   - *unsent*: no request byte left this process. Proven in one way only: the attempt failed with no int status and its EXPLICIT cause chain (`__cause__` and `.reason`, at most 8 deep, never `__context__`) holds `ConnectionRefusedError`, `socket.gaierror` or `ssl.SSLCertVerificationError` and holds none of the "may have sent" list (`TimeoutError`, `ConnectionResetError`, `ConnectionAbortedError`, `BrokenPipeError`, `EOFError`, `ssl.SSLEOFError`, `ssl.SSLZeroReturnError`, `http.client.HTTPException`).
   - *unknown*: every other end of an attempt: any other status, a timeout, a reset or EOF after connecting, any other `OSError`, a parse failure of an answer (billed), any exception with no status, an attempt whose callable raised a `ProviderError` of its own, and an ANSWERED attempt of a chat that later failed (it was billed and its usage is lost).
   - Per attempt, exactly one of refused, unsent, unknown. The stamp holds `attempts` (attempts started), `refused`, `unsent` and `answered` (attempts that returned an answer). For a FAILED chat: unknown = `attempts - refused - unsent`. For a chat that SUCCEEDED: `prior_unknown = attempts - refused - unsent - answered` (the answered attempts are priced by their own usage).
3. **Counts are per chat and ride on success too (P4a PL51).** `NetworkLLM.chat` makes ONE call-scoped counter (defined in `llm/retry.py`) and every `_retry` of that chat adds into it, so the two requests of the OpenAI-compatible kind form one count. How the counter reaches `_retry` (an argument, or a `contextvars.ContextVar` set in `chat` and reset in `finally`; never a module global and never an instance attribute shared by two threads) is for the builder; the ticket fixes the behaviour, rows T11 and L8 test it. On success, `chat` copies `prior_unknown` onto the `Reply` (one field, below).
4. **The stamp.** The only stamp is a frozen `AttemptCounts` value (validated ints, `0 <= v <= MAX_COUNT`, `MAX_COUNT = 10**6`) that only `llm/retry.py` builds and stores in one private instance slot of the error it raises. `billing_outcome` reads it with `vars(exc).get(<slot>)` and accepts it only if `type(v) is AttemptCounts`. No stamp, a class-level value, a subclass of `AttemptCounts` or any other object means unknown: kept, booked at the whole-call maximum. There is no class attribute for counts, no "class default means unknown" rule and no `attempts == 0` release clause (revision 1 had all three; no layer stamps 0 and that clause was a fail-open edge).
5. **Release rule.** The wrapper releases iff the error is a `ProviderError` (or subclass) with a valid stamp, `attempts >= 1`, `refused + unsent == attempts` (so unknown is 0). Anything else keeps. The decision is by COUNTS, never by exception class: a `ProviderExhausted` made of three 429s is released; a `ProviderError` made of a billed answer that could not be parsed is kept (G9).
6. **What a kept failure and a success book (the wrapper's table; W as defined above).**
   - success: the answered usage + `prior_unknown x W` (P4b1-b's success booking, `P4b1.md:265`, unchanged by P4b2-a).
   - kept failure with a readable stamp: `max(reserved, unknown x W)`.
   - kept failure with no readable stamp, or any other exception (`KeyboardInterrupt` and `SystemExit` included): the whole-call maximum, `request_bound(inner) x max_attempts x W`, with `max_attempts` read by P4a's total rule (`P4b1.md:268`: an `int` of at least 1, not a `bool`, else `CHARGE_FALLBACK_ATTEMPTS`).
   - released: nothing (the counters return to the value before the reserve).
   Made-up example, single-request kind, reserved = W = 1000, `max_attempts` 3, answered usage 400 (whole numbers, units are made up): 200 on the first try books 400. 408 then 200 books 400 + 1000 = 1400. 500, 500, then 200 books 400 + 2000 = 2400. 500 three times books `max(1000, 3000)` = 3000. 429 three times releases (0 booked). 429, 429, 500 books `max(1000, 1000)` = 1000. One 401 releases. An unreadable stamp books 3 x 1000 = 3000.
   Two-request kind (reserved 2000, W 1000, `max_attempts` 3): two timeouts then 200 on request 1, request 2 not needed: usage + 2000. Request 1 answered, then request 2 fails three times: P4a-2 re-raises request 2's failure as a NEW `UsageMissing("absent", "usage")` chained with `from` to the real error (`P4a.md:315`, row C16 at `:363`), raised in `openai_compat` outside `with_retry`, so it has no stamp: it books the whole-call maximum 2 x 3 x 1000 = **6000**, whatever the three failures were. The stamped error inside it (its `__cause__`, which `billing_outcome` does not read) holds attempts 4, answered 1: 3 x 429 gives unknown 1, a stamped booking of `max(2000, 1000)` = **2000**; 3 x 5xx gives unknown 4, `max(2000, 4000)` = **4000**. Request 2 answered with no usable usage (its own `UsageMissing`, not wrapped, C16 (iv)) is stamped through the pass-through: attempts 2, answered 1, unknown 2, `max(2000, 2000)` = **2000**. So end to end the OpenAI-compatible request-2 failure always books 6000 in v1; 2000 and 4000 are the stamped figures, asserted at the counter and wrapper level (T11, G15). Copying the stamp onto P4a-2's re-raise is a v1.1 row (PENDING LEAD 24).
   A pre-flight failure inside `NetworkLLM.chat` after the reserve (an unknown route `KeyError`, or `tools_for`'s `ValueError`, `common.py:218-219`) has no stamp and is not a `ProviderError`, so it books the whole-call maximum although nothing was sent: an accepted over-count, row G17 (the wrapper's own route check runs before the reserve, `P4b1.md:291` row B9). No new reason code.
   A booking above the reservation can push a counter above its cap by up to `(max_attempts - 1) x reserved` for one call; the next reserve is then refused (fail closed). That is accepted and stated, not hidden (the invariant of G11 is worded to it).
7. **Provider error vs timeout.** The two classes keep their meaning for the agent loop (`provider_error` vs `provider_exhausted` end codes) and do not decide billing. A timeout after the request was sent is *unknown*. A refused connection, a DNS failure or a certificate-check failure before any request byte is *unsent*. A 401, 400 or 429 is *refused*. A 5xx is *unknown*.
8. **Release vs settle at zero.** Release is a cancellation (status `released`). Settle at zero is a price (status `settled`, `settled_usd` 0). The meter releases only through rule 5. In v1 it never settles at zero: P4b1 refuses `Hold.record(SpendMicro(0))`, and a reply with missing, zero-token or invalid usage is a `UsageMissing` and is kept (P4a). Mutant a10 implements a release as a settle; the status value kills it.
9. **Money type.** Storage stays `NUMERIC`, the Store boundary takes exact `Decimal` USD with at most 6 decimals (A9 B1, P4d). The meter works in integer micro-dollars, rounds UP once per call (R214). P4b2 adds no money column, no new money SQL and no rounding rule (P4b2-b's actor trigger only compares `settled_usd` with `reserved_usd` and refuses; it computes no amount).
10. **Error rule.** A refused store write is `StaleState` or `ValueError` (P4d rule). On any deny or refuse path the answer is refuse.
11. **Lock order.** P4b2 adds no multi-row SQL and no lock (P4b2-b's row trigger takes none). The sweep is P4d's; its lock order is unchanged.

- Problem in plain words: When a model call fails, the meter has to guess what the failure cost. Intake's meter settles every failure at the worst case, which is safe but wrong in one way: a call that was refused (a bad key, a malformed request, a rate-limit answer) or never left the machine (the provider's address could not be reached) cost nothing, yet its worst case stays counted until the day or month rolls over. After a key expires, every retry of every run adds a phantom worst case. The opposite error is worse and is the main purpose of this package: a call can be BILLED more than once. One reservation covers a call that may send up to three attempts per request, and a request that timed out or failed with a 5xx may have been billed even though no answer came back. Today a retried call that finally succeeds books only the last answer, and a call that fails three times books one worst case, so the real bill can pass the limit. This package makes the layer say what it knows, makes "I do not know" the default, releases only on proof, and books the upper bound when billing is unknown. Stated limit, in plain words: a provider that silently drops connections ends as a connect TIMEOUT, which is kept, so the outage case is only partly fixed: refused connections, name-lookup failures and certificate failures are released; silent drops are not (v1.1 list).

- Problem in plain words: When a process dies in the middle of a model call, its reservation stays open for ever and holds its worst case in the counters. P4d adds the means to mark such rows "expired" (the sweep) but nothing calls it, and today the only login that could run it is the runtime login that makes every model call. The owner's least-privilege rule says one identity per function and that a runtime role must never get sweep or delete rights (LEAD-ORDERS 21 item 13 keeps the separate identity; amendment F2 stands). So this sub-ticket gives the sweep its own login that can do that one thing and nothing else (it cannot create, delete or change an amount, and it cannot touch the counters), makes the runtime login unable to expire a row, wires the sweep as a bounded step in the tick, and fixes the rules for how old a reservation is (on Postgres, measured on the database clock, which the application cannot move; the memory store's default clock is the wall clock and carries no such claim). Stated plainly, so nobody over-reads it: expiry changes a label, not money. An expired reservation KEEPS its worst case in the counters until the day or month counter rolls over; a caller who finishes late corrects it downward once (P4d-b). Releasing an abandoned reservation early would need a separate decision and is not in this package.

  - **Age of a reservation (the monotonic rules).**
    - A1. On Postgres, the reservation age of an open row is measured by ONE clock that no application, caller or application host can move: `clock_timestamp() - created_at`, both from the database server (P4d-b). On the memory store the age comes from its one injected clock, whose DEFAULT is `models.now`, the wall clock (`P4d.md:160`, `models.py:19-20`): dev and test only, and NO monotonic claim is made for memory with the default clock (R2-ADV-2). The tick, the wrapper and every caller pass a DURATION (`orphan_age_s`), never a timestamp, and no code in the sweep functions themselves (the tick step and the store's sweep method) reads `time.time`, `datetime.now`, `models.now` or `ctx.now`; the memory store's default clock is bound in its constructor, outside that code. (Words: hold age is P4b1's process-clock number for a log line; reservation age is this one. They are never compared.)
    - A2. Wall-clock time is used for exactly one money purpose: the calendar `day` of the counters (R214, a day in a named zone). That is P4b1's and P4d's, not changed here. OBSERVATION for P4b1 (not taken): `day` comes from the application clock (`Limits.charge` uses `now().date()`); a host clock set forward starts a new day's counter early. Recommended there: derive the day from the database date or refuse a `day` far from it.
    - A3. What a clock error can and cannot do (the analysis; P4d-b made it true). A reservation swept too early (the database clock stepped forward, a very slow call, a too-small `orphan_age_s`) becomes `expired` but KEEPS its amount in all three counters. So early expiry cannot cause an overspend. If the call finishes, its real settle (by the runtime login, which may still settle an `expired` row) corrects the row downward ONCE (P4d-b rule) and a second close returns that result. The only effects of a wrong clock are a mislabel and a late correction. A clock stepped BACKWARD only delays expiry (more rows stay open longer: over-counted, safe).
    - A4. The database server's own wall clock can step (an NTP correction). It is not monotonic. This package does not claim otherwise: it claims that no APPLICATION clock participates, that one server clock serves every process (so processes cannot disagree), and that a step cannot overspend (A3). Rows E3 and M1-M3 test exactly that.
