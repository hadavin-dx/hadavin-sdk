Plain words used here (each keeps one meaning):
- **usage**: the token counts a model provider reports for one call.
- **the classes of usage**: input (prompt tokens billed at the normal input price), cache write (prompt tokens the provider stored for reuse), cache read (prompt tokens served from that store), output (tokens the model wrote; on Claude and Gemini this includes the private working the provider calls thinking, which this core does not report as a separate count: the thinking count on `Usage` is cut, V26). This core prices only input and output; a non-zero cache count is refused.
- **prompt tokens**: input + cache write + cache read (everything the model was sent).
- **reserved amount**: the money the meter (P4b1) sets aside BEFORE a call. Only the meter has one.
- **estimated worst-case amount**: `k1b.loop.worst_case_usd(route, system, messages, *, requests=1)`: a prompt-size ESTIMATE times the input price, plus `max_tokens` times the output price, times `requests`, the number of requests' worth that the caller books (rounded up once to 8 decimals). It is an estimate, NOT a bound: three characters a token is a guess, and a token-dense prompt can cost more. It lives in `k1b/loop.py` and has no other consumer (the relocation to `llm/pricing.py` is cut, V33); the meter (P4b1) sizes its reserved amount with its own function; P4d and P4b1 own what happens when the real cost is higher.
- **refuse**: raise a typed error and return nothing; no cost number is made up.
- **request count of one call** (`request_bound(llm)`): the most billed requests one `chat()` can send when every request is answered, as DECLARED by the kind in its class attribute `REQUESTS_PER_CHAT`: 2 for the OpenAI-compatible kind (it may ask once more when the forced answer is missing), 1 for every other kind and for `FakeLLM`. It does not count retries after a failure. It is STRICT: an object with no declaration, or a bad value, is refused (`TypeError` or `ValueError`). It is for the reservation; the refused-answer charge in `k1b/loop.py` uses the same request-count multiplier, read by `_charge_factor` (below), except for the chained request-2 shape, which books one request (Answer first 8).
- **reservation versus charge after the fact**: the reservation is set aside BEFORE a call (the meter, P4b1-b); a loud refusal there is intended, because no money has been spent. A charge after the fact books money that has ALREADY been spent or may have been spent (an abandoned call, a refused reply; exhausted retries are P4b2's); there the code must never raise, and a missing value is replaced by the larger fallback so that the number of ANSWERED requests (and, for the abandoned call, of attempts) is not under-counted (the size of each request is still an estimate, see "estimated worst-case amount" above and Answer first 8; a request that was never answered is P4b2's).
- **charge factor** (`_charge_factor(llm, with_attempts)` in `k1b/loop.py`, private, total): the number of requests' worth of the worst case that one of those after-the-fact charges books: the request count of one call, times the number of attempts only when `with_attempts` is true (the abandoned-call charge; the refused-answer charge passes false; the chained request-2 charge books one request and does not call it). Each of the two numbers is read from the object when it is an `int` of at least 1 and otherwise taken from a named fallback constant (`CHARGE_FALLBACK_REQUESTS`, `CHARGE_FALLBACK_ATTEMPTS`, `defaults.py`).
- **attempts**: after a failure with no answer (for example a read timeout) `with_retry` sends the SAME request again, up to `max_attempts` times (default 3, `backends/table.py:40`). The provider may have processed and billed an attempt whose answer never arrived; no `Reply` carries that usage.
- **route**: one entry of `routes` in `config.yaml`: a model id, its prices and `max_tokens` (`Route`, `config.py:55-59`).
- **a model with prompt-length price tiers**: a model whose price per token rises above a stated prompt size.

- **Problem in plain words:** When a model provider's reply has no token counts, the shared code guesses them from the text it sent and received, and when a provider reports a real zero (for example zero output tokens) the same line replaces it with a guess. The guess becomes the cost the spend counters add up, so a cap can be reached late and the books can show a number the provider never charged. One kind (Anthropic) does not even fail cleanly: with no usage object it raises a plain error that the ask-your-data pipeline then settles as free.
