Plain words used here (each keeps one meaning):
- **usage**: the token counts a model provider reports for one call.
- **the five classes of usage**: input (prompt tokens billed at the normal input price), cache write (prompt tokens the provider stored for reuse), cache read (prompt tokens served from that store, cheaper), output (tokens the model wrote, thinking included on Claude), thinking (the part of output spent on private working; shown for visibility, never priced again).
- **prompt tokens**: input + cache write + cache read (everything the model was sent).
- **reserved amount**: the money the meter (P4b1) sets aside BEFORE a call. Only the meter has one.
- **highest possible price**: the largest per-million-token price among the prompt classes of one route (`Rates.highest_prompt()`). It is a price, never an amount of money.
- **estimated worst-case amount**: `estimated_worst_case_usd(...)`: a prompt-size ESTIMATE times the highest possible price, plus `max_tokens` times the output price. It is an estimate, NOT a bound: three characters a token is a guess, and a token-dense prompt can cost more. The meter may use it as the size of a reserved amount; P4d and P4b1 own what happens when the real cost is higher.
- **refuse**: raise a typed error and return nothing; no cost number is made up.
- **route**: one entry of `routes` in `config.yaml`: a model id, its prices and `max_tokens` (`Route`, `config.py:55-59`).

## Rules stated once (both sub-tickets)

- **One error rule.** Anything that makes the cost of a call unknowable or unpriceable is a `UsageMissing` (or its subclass `UnpricedUsage`): REFUSE. No default substitutes a number. Both are `ProviderError`s, neither is `ProviderExhausted`, neither is retried. The message is built only from a fixed reason and a fixed field name; it never holds response text, request text or a reported value (a provider reply can echo a document; personal-data rule).
- **Closed reasons** (`USAGE_REASONS` in `llm/protocol.py`): `absent` (no usable usage object, or the field is missing or null), `invalid` (not a plain int, negative, above the cap, thinking above output, a sum above the cap, a bad nested count), `implausible_zero` (prompt tokens are zero on a route with a positive input price), `unpriced_class` (a class has a non-zero count and no price, an unknown pricing word, or a prompt above the route's `max_prompt_tokens`). `UnpricedUsage` always has reason `unpriced_class`. Closed field names: `usage`, `input_tokens`, `output_tokens`, `cache_write_tokens`, `cache_read_tokens`, `thinking_tokens`, `prompt_tokens`, `service_tier`, `speed`.
- **No raw `ValueError` or `decimal` error may leave a kind's `chat()`** (ADV-F2, COR-F2). `agent_loop.py:430` catches only `ProviderError`, and `with_retry` turns a stray `ValueError` raised inside the retried call into a plain `ProviderError` that `pipeline.py:163` settles at zero. So every kind builds its usage through ONE choke point, `build_usage` (below), which checks everything first and raises `UsageMissing("invalid", field)`; `Usage.__post_init__` raising `ValueError` is only a backstop for programmer error and a test proves no kind reaches it.
- **Only the llm kind may read a provider's usage object.** Callers see `Reply` and `Usage` (R362).
- **Money type and exactness.** Exact `Decimal` USD; counts are plain `int` (`bool` refused); prices are USD per million tokens with at most 6 decimals, at most `MAX_PRICE_USD_PER_MTOK` (1000). Proof that `cost_usd` is exact: a price is `a / 10**6` with `a` an integer up to 10**9, a count `n` is at most 10**9, so `a * n` is at most 10**18 (19 digits) and four classes sum below 10**19; dividing by 10**6 only moves the point. That fits the default 28-digit `decimal` context, so `decimal.Inexact` is unreachable for admitted inputs. `cost_usd` still runs in a local 60-digit context with the `Inexact` trap as a defensive check, and converts any `decimal.DecimalException` into `UsageMissing("invalid")` so nothing outside `ProviderError` can escape. No mutant is claimed for the context (it cannot be killed with admitted inputs).
- **Named constants** (one place, `defaults.py`): `MAX_USAGE_TOKENS_PER_CLASS = 1_000_000_000` (Intake's bound, `model_anthropic.py:178-182`), `MAX_PRICE_USD_PER_MTOK = 1000`, `OPENAI_COMPAT_REQUESTS_PER_CHAT = 2`. - **Problem in plain words:** When a model provider's reply has no token counts, the shared code guesses them from the text it sent and received, and when a provider reports a real zero (for example zero output tokens) the same line replaces it with a guess. The guess becomes the cost the spend counters add up, so a cap can be reached late and the books can show a number the provider never charged. One kind (Anthropic) does not even fail cleanly: with no usage object it raises a plain error that the ask-your-data pipeline then settles as free. This pull request makes the shared code refuse: a reply without usable counts raises `UsageMissing`, a reported zero is kept as zero, a count or a sum that cannot be real is refused before any number is built, nothing is retried, and the second request of an OpenAI-compatible call is not sent. Settling the unknown cost at the reserved amount is the meter's job (P4b1); this package only guarantees the meter is told.
