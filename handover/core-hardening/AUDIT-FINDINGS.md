## Summary in plain words (read this first; terms are explained in section 1, right below)
What is broken. The core promises safety controls: a spend limit, a kill switch (a switch that stops all actions), a record of every action (the audit log), and a second check that finds secrets (called G5). Five places in the code call a model (`.chat(`): the main agent loop (agent_loop.py:425), the model-quality test command `gate` (evals.py:73), the replay tool in `k1b` (k1b/loop.py:94), the checking model call in guard/judge.py:72, and the document reader extract.py:47 (nothing in the core calls extract; see C-20). The demo `ask` command is a sixth path that never reaches the controls. The builders found that the controls are wired to the main agent loop only (the judge call is charged by its caller but not checked before the call). Whether they WORK there was not checked: nothing was run. The other places skip some or all controls. Also, G5 is built nowhere (A-02), a zero model price breaks the spend limit on every place (C-01), and some state lives only in one running program and may be lost or never seen by the next one.
Important scope note: in pilot and prod the core executes no action today (app.py:52 and :173, deferred.py:55; an approved plan ends as NEEDS_PERSON). So the approval and action findings (A-03, A-04, A-05, X-16) describe the build that adds an executor and the dev build; they do not mean approved actions run in production today. The severity rule in section 1 was applied unevenly by the builders (for example X-02 has no code for a money guarantee but is Major, while A-02 is a misleading comment but is Blocker): this is why the lead must decide section 2b.
Worst items. There are three lists and none is yet decided; the lead decides (the owner decides only the questions marked "owner" in section 10). ## 1. Words used (read before section 0)
Lane = one builder's part of the audit (A security: actions, approvals, audit log, secret-hiding code; B state and runtime: storage, runtime, replay tool, sources; C model code and top-level files; D1 tests; D2 demos compared with the core; D3 documents, build checks (CI), hooks, settings and the shape of handover/). Hook = a small script Claude Code runs before a tool call. CI = the automatic checks GitHub runs on a pull request.
Run = one unit of agent work (one question handled by the runtime). "Nothing was run" means no program was executed. Kind = a swappable part behind a fixed interface (for example a secrets store or a model client). Store = a place that keeps data (a database, a file, a list in memory); STORE is also a finding label. Tick = the scheduled background job that expires approvals, finishes approved actions, rescues stuck runs, writes audit checkpoints, deletes old evidence and re-checks data sources. Outbox = the holding area where audit events wait when the main log is busy. Reconcile = write the waiting events to the log afterwards. Audit chain = the log in which every entry carries the fingerprint of the one before it, so changes show. Checkpoint and anchor = a signed summary of the chain and a copy of it kept elsewhere. G5 = the planned second, independent secret check at the message gate (not built). Redaction = hiding secrets and personal data. Kill switch = the flag that stops all agent work. Meter = the counter of money spent. Ledger = a list of records; here "ledger" means the blocker ledger (handover/ledger.md) unless it says "spend ledger" or "demo ledger". Principal = the identity of the person or system a run acts for. Choke point = the single place all callers pass through, so one fix covers all of them. Egress = traffic leaving the program to the network. Gate = the message gate in approvals (G5) OR the `hadavin-sdk gate` test command (C-04); the text says which. CRM = customer-relationship tool.
Finding labels (class): SECURITY = a safety or secret or money risk; STORE = data kept in a place with no written reason; WALK = a check of how a request travels through the code; DEAD = code or settings that nothing uses but that look live; INCONSISTENT = two places say different things; DUPLICATE = the same job written twice; OPS = running and watching the system; UNVERIFIED-CLAIM = the text promises something no code or test shows.
More terms. k1b = the replay-and-score tool for recorded model runs (src/hadavin_sdk/k1b). desk = the studio's case-handling tool in front of the runtime; n8n = a ready-made workflow tool (neither is judged wrong in this audit). stage = the setting `environment` with values dev, pilot, prod (the audit proposes renaming dev to demo). Reserve and settle = take the worst-case cost from the budget BEFORE a model call, then replace it with the real cost AFTER. Promote = move code from one demo into the core so every build shares it. Heartbeat = a timestamp the tick job writes each time it finishes; a dead-man check raises an alarm when that timestamp gets too old. Replay Check = a separate program named in demo notes that shares the meter file (question 6). Store (capital S) = the core's database layer; STORE = the finding label for a data place with no written reason.
Severity. Blocker = a stated guarantee about secrets, money, redaction, approvals or audit can fail, or has no code or test. Major = duplicate store or engine, text and code that contradict, or dead code that looks live. Nit = stale name or harmless idle part. Note: Blocker here does not mean "stops all work".
Verdicts (proposals): NEEDED, DUPLICATE, NOT-NEEDED, CRM-COULD-DO (a desk or CRM tool could do this job; this word NEVER applies to code for money, approvals, redaction or audit). No CRM-COULD-DO assessment was made in this audit: the order asked for the verdict but no builder judged any job at that rung. Extra words used: FIX-NEEDED (the thing is needed but wrong) and UNVERIFIED (needs a running system or another repository). IDs: <lane>-<nn>; X-nn is a finding that crosses lanes. "The lead" = the laptop lead who gave the order; "the owner" = the studio owner; the lead decides severity questions unless this text says the owner.
