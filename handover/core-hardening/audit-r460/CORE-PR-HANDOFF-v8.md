Sheet row, once a month: the seven parts, the invoice total, the difference. 6. **Arithmetic caveat (once):** token and dollar figures use the 3-characters-per-token estimator (`llm/common.py:59-62`) and the fixture route 3.00 / 15.00 US dollars per million tokens, `max_tokens` 1024 (`tests/fixtures/config/config.yaml:6-8`). The only measured figure I read is `0.00225` per fake call (`tests/test_s4_llm_guard.py:39`, `tests/test_s5_runtime.py:76`). E0-5 prints the rest. The estimator is too small for text with few characters per token (for example Chinese or base64): that is why the input margin exists (D20). The **sanity floor** (4.1) is therefore **not a lower bound** of the true token count (it is a high estimate for English and a low one for such text); v8 names it a sanity floor, says so, and does not use it as a bound anywhere.
7. **Words I use for properties nothing has run:** "is designed to" or "the test E0-x checks that". Words like "never" and "cannot" appear only for what a type or a database constraint makes impossible, and each such sentence names the test.
8. **What this design does not protect against (stated once, so no later sentence has to hedge):** code running inside the agent process with the provider key can call the provider directly and skip every check below. The design is built to stop **mistakes and bugs** (a loop, a retry storm, a wrong estimate, a restart, a late date, a skewed clock) and to bound what a hostile runtime can do **in its own database rights**; it does not stop one. What that process **can** do with the database role it holds is listed in section 5 (it can insert a reservation or a direct row for **another** agent's id and so use up that agent's caps, unless the optional per-agent role table is filled, D29; it can write a `settle` of 0 for its own reservation). The caps are enforced by the store methods and the lock protocol, **not by a database constraint**: a writer that skips the methods and inserts rows directly is bounded only by the trigger rules. The hard stop for a hostile process is the provider-side limit (item 5a); the detection is the invoice comparison (item 5b), which sees such money only after the month.

## 4. Designs

### 4.1 Spend: reserve, settle, release, relieve (resolves v7 security M-A, M-B, M-F, M-G, M-I, nits 1, 2, 4, 5, 7; readiness majors 2, 3, 4, 5, 6, 9)

**Words used here, explained once.** A *reservation* is money set aside before a model request is sent, so the daily, monthly and per-run caps count it at once. An *attempt* is one request sent to the model provider. A *call* is one `chat(...)` from our code; it holds one or more attempts (retries, and the OpenAI-compatible kind's second request). *Settle* = replace the reservation by what the answer really cost. *Release* = give the reservation back. *Keep* = leave the full reservation booked as spent. *Relieve* = an operator later gives back part or all of a kept or stuck reservation (audited). A *nano-dollar* is one billionth of a US dollar (0.000000001 USD); the new tables store whole numbers of nano-dollars, so adding rows never loses a fraction (D5). The *basis* of a final row says why it books what it books: `reported` (the provider's own token counts), `floor` (our sanity floor was higher than the reported cost), `unknown` (usage missing or zero, so the whole reserve stays booked), `failed` (the attempt failed in a way that may have been billed, so the whole reserve stays booked).

**Admission rule (honest bound, M-E).** The sum of admitted reservations stays within a cap **because every writer that follows the protocol takes one per-agent lock and compares inside one transaction**. That is a property of the lock protocol, **not a database constraint**: a database role that inserts `spend_op` rows directly is stopped only by what the two triggers below check. The money actually billed can pass a cap by the estimator error: at most, over the attempts that were sent, the sum of (booked cost minus reserved amount) where positive; with N attempts in flight at once, N times the per-attempt error. A request already sent cannot be recalled. "Exact cap" is not claimed. A database-enforced cap (a trigger that sums and refuses) is a named trigger, not built: build it when a client wants the cap to hold against a hostile runtime role, because the provider-side limit (section 0 item 5a) already bounds that case.

**What a reservation covers: one attempt.** `with_retry` can send up to `max_attempts` requests for one `chat` call (`retry.py:92-107`, default 3, `backends/table.py:40`), and the OpenAI-compatible kind can run **two** `_retry` loops inside one `chat` (`llm/openai_compat.py:117-129`: the second runs when the forced answer is missing), so one call can hold up to `2 x max_attempts` attempts. Each attempt has its own reservation, its own outcome, its own booking. Attempt numbers come from **one counter inside the call's `CallBook`** (4.2), so the reservation ids of one call are `<call_id>:1`, `<call_id>:2`, ... with no collision. `call_id` is `models.new_id("res")` (`models.py:23`), fresh per call.

**Money unit (D5, OWNER-OPEN, default applied).** Every amount in the new tables and the new store methods is a whole number of nano-dollars (`int`, Postgres `BIGINT`). `Reply.cost_usd`, `Route` prices and `Budget` stay `Decimal` US dollars (they exist today); one module, `store/amounts.py` (standard library only), converts at the edge. **Two functions, two roundings (nit 5):** `to_nano(usd: Decimal) -> int` is for **amounts spent or reserved**: it calls `usd.is_finite()` **before any comparison** (a signalling NaN raises on `<`), refuses negative and above `MAX_SPEND_NANO`, and rounds **up** (`ROUND_CEILING`), so rounding can only over-count. `cap_to_nano(usd: Decimal) -> int` is for **caps** (daily, monthly, run): same checks, rounds **down** (`ROUND_FLOOR`), so rounding can only make a cap stricter; v7 rounded caps up, which could let a cap pass by under one nano-dollar. `from_nano(n: int) -> Decimal` is exact. `MAX_SPEND_NANO = 10**15` (1,000,000 USD, **chosen by me** as a sanity ceiling far above one call; the table `CHECK` repeats it and a test pins the two equal). `llm/spend.py` holds the same ceiling in dollars, `MAX_SPEND_OP_USD = Decimal(1_000_000)` (so `llm` never imports `store`); a test pins `to_nano(MAX_SPEND_OP_USD) == MAX_SPEND_NANO`. A route price per million tokens with at most three decimals gives a whole number of nano-dollars per token (3.00 USD per million = 3,000 nano-dollars per token), so for today's routes no rounding happens at all. **Config rule:** a configured daily, monthly, run or per-call cap whose value has more than 9 decimal places is refused at config load, so `cap_to_nano` never has to round a real cap (nit 5).

**Store: both stores, new migration** `src/hadavin_sdk/store/migrations/0006_spend_op.sql` (name fits `_FILE`, `store/migrate.py:71`; `0001`-`0005` exist, no gap). Three new tables and one function; the first two tables are append-only. **Changes against v7 (nits 1 and 2):** the key is `PRIMARY KEY (kind, res_id)`, replacing v7's `op_id` text key and two partial unique indexes, so a lookup by (kind, id) can never read the wrong kind and an `ON CONFLICT DO NOTHING` has one obvious target; a new `basis` column with a check that treats a missing value correctly (`IS NOT NULL` is written out: a `CHECK` whose expression is NULL passes); covering indexes; and the relief label is restricted.

CREATE TABLE spend_op (
    kind        TEXT NOT NULL CHECK (kind IN ('reserve', 'final', 'direct')),
    res_id      TEXT NOT NULL,           -- 'res_...:<n>' for a call attempt; 'dir_...' for a direct row
    agent_id    TEXT NOT NULL,
    run_id      TEXT,                    -- NULL for eval scopes and direct rows

    actual_nano BIGINT CHECK (actual_nano BETWEEN 0 AND 1000000000000000),   -- final/settle only

CREATE OR REPLACE FUNCTION spend_op_guard() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE r spend_op%ROWTYPE;
BEGIN
  IF current_setting('transaction_isolation') <> 'read committed' THEN
    RAISE EXCEPTION 'spend_op: needs READ COMMITTED' USING ERRCODE = 'check_violation'; END IF;
  PERFORM pg_advisory_xact_lock(spend_lock_key('agent:' || NEW.agent_id));
  IF EXISTS (SELECT 1 FROM spend_agent_role) AND NOT EXISTS
     (SELECT 1 FROM spend_agent_role WHERE agent_id = NEW.agent_id AND role_name = session_user) THEN
    RAISE EXCEPTION 'spend_op: this role may not write this agent' USING ERRCODE = 'check_violation'; END IF;
  IF NEW.kind = 'final' THEN
    SELECT * INTO r FROM spend_op WHERE kind = 'reserve' AND res_id = NEW.res_id;
    IF NOT FOUND THEN
      RAISE EXCEPTION 'spend_op: no reserve for this final' USING ERRCODE = 'foreign_key_violation'; END IF;
    IF NEW.agent_id <> r.agent_id OR NEW.day <> r.day OR NEW.run_id IS DISTINCT FROM r.run_id THEN
      RAISE EXCEPTION 'spend_op: final differs from its reserve' USING ERRCODE = 'check_violation'; END IF;
    IF EXISTS (SELECT 1 FROM spend_adjust WHERE res_id = NEW.res_id) THEN
      RAISE EXCEPTION 'spend_op: reserve already relieved' USING ERRCODE = 'check_violation'; END IF;
    IF NEW.how = 'release' AND NEW.usd_nano <> -r.usd_nano THEN
      RAISE EXCEPTION 'spend_op: release amount' USING ERRCODE = 'check_violation'; END IF;
    IF NEW.how = 'keep' AND NEW.usd_nano <> 0 THEN
      RAISE EXCEPTION 'spend_op: keep amount' USING ERRCODE = 'check_violation'; END IF;
    IF NEW.how = 'settle' AND (NEW.actual_nano IS NULL OR NEW.usd_nano <> NEW.actual_nano - r.usd_nano) THEN
      RAISE EXCEPTION 'spend_op: settle amount' USING ERRCODE = 'check_violation'; END IF;
    IF NEW.how <> 'settle' AND NEW.actual_nano IS NOT NULL THEN
      RAISE EXCEPTION 'spend_op: actual only on settle' USING ERRCODE = 'check_violation'; END IF;
  END IF;
  RETURN NEW;
END $$;
CREATE TRIGGER spend_op_guard BEFORE INSERT ON spend_op FOR EACH ROW EXECUTE FUNCTION spend_op_guard();

CREATE OR REPLACE FUNCTION spend_adjust_guard() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE r spend_op%ROWTYPE; f spend_op%ROWTYPE;
BEGIN
  IF current_setting('transaction_isolation') <> 'read committed' THEN
    RAISE EXCEPTION 'spend_adjust: needs READ COMMITTED' USING ERRCODE = 'check_violation'; END IF;
  PERFORM pg_advisory_xact_lock(spend_lock_key('agent:' || NEW.agent_id));
  SELECT * INTO r FROM spend_op WHERE kind = 'reserve' AND res_id = NEW.res_id;
  IF NOT FOUND THEN
    RAISE EXCEPTION 'spend_adjust: no reserve' USING ERRCODE = 'foreign_key_violation'; END IF;
  IF NEW.agent_id <> r.agent_id OR NEW.day <> r.day OR NEW.run_id IS DISTINCT FROM r.run_id THEN
    RAISE EXCEPTION 'spend_adjust: differs from its reserve' USING ERRCODE = 'check_violation'; END IF;
  IF NEW.reduce_nano > r.usd_nano THEN
    RAISE EXCEPTION 'spend_adjust: more than the reserve' USING ERRCODE = 'check_violation'; END IF;
  SELECT * INTO f FROM spend_op WHERE kind = 'final' AND res_id = NEW.res_id;
  IF FOUND AND f.how <> 'keep' THEN
    RAISE EXCEPTION 'spend_adjust: only open or kept reservations' USING ERRCODE = 'check_violation'; END IF;
  RETURN NEW;
END $$;
CREATE TRIGGER spend_adjust_guard BEFORE INSERT ON spend_adjust FOR EACH ROW EXECUTE FUNCTION spend_adjust_guard();

| Insert | Allowed when | `usd_nano` / amount | Refused with |

| `reserve` | `usd_nano >= 0`; the store has passed the caps under the lock | the reserved amount | `check_violation` |

| `direct` | `usd_nano >= 0` | the amount | `check_violation` |

**Serialising writers, the isolation level and the lock wait (M-A, M-G).** Every spend transaction (`reserve_spend`, `finish_spend`, `adjust_spend`) runs these statements, in this order (`finish_spend` inserts a read of the reserve between (2) and (3), below): (1) `SET TRANSACTION ISOLATION LEVEL READ COMMITTED` (explicit, so a changed server default or a pooled session cannot change it; the trigger refuses anything else); (2) `SELECT set_config('lock_timeout', '<n>ms', true)` with `n = spend.lock_timeout_ms` (D27; the `true` makes it local to the transaction); (3) `SELECT pg_advisory_xact_lock(spend_lock_key('agent:' || %s))`. A wait longer than the timeout raises SQLSTATE `55P03` (`lock_not_available`), which the store maps to `StoreUnavailable`, which `SpendMeter.reserve` maps to `SpendRefused("meter_unavailable")` (a refusal, no model call). One lock per agent covers the day, month and run checks, because every run belongs to one agent; two agents whose keys collide only wait for each other and never over-admit. The lock is `xact`-scoped, so commit or rollback frees it. Both triggers and the store call the same `spend_lock_key`, so there is one lock per agent whichever statement takes it first, and `finish_spend` and `adjust_spend` for the same reservation can no longer both pass their "the other one does not exist" check: the second waits, then (READ COMMITTED gives each statement a fresh snapshot) sees the first one's committed row and refuses (M-A). `READ COMMITTED` is what makes this work: under REPEATABLE READ the snapshot would predate the lock.
**The reviewer's second point, "do not hold the Python lock across the lock wait", is not done as worded, and why (M-G).** `PostgresStore` has **one connection behind one `threading.Lock`** (`store/postgres.py:191-197`, comment "one connection behind one lock per process"; the connection is `autocommit=True` at `:146`; `add_spend` at `~:416-431` uses `with self._lock, self._db.transaction()`). If a second thread ran its statements on that connection without the Python lock while the first thread's transaction is open, its statements would join the first thread's transaction. So the Python lock must stay, and a wait for the database lock holds it. What bounds the damage is `lock_timeout` (default 2000 ms, D27): a stuck holder in another process delays this process's spend calls by at most the timeout, then they are refused with `meter_unavailable`. Named trigger for a dedicated second connection for spend (so other store methods do not wait behind a spend wait): the first measurement in E0-3 showing other store calls delayed more than 1 second by a spend wait. The memory store has no database lock; it uses its own `threading.Lock` and the same decision function (below).

**Booking rule for one attempt (D23).**
| What happened to the attempt | Booking | Basis | Why |
|---|---|---|---|
| a usable answer (parsed) with known usage, reported cost at least the floor | `settle` at the reported cost, clamped at `MAX_SPEND_NANO` | `reported` | normal; includes a reply that later fails the caller's own checks |
| the same, reported cost below the sanity floor | `settle` at the floor | `floor` | usage looks too small to be real (4.1 below) |
| a usable answer with **unknown** usage (rule below) on a network route that is not self-hosted | `keep` (the whole reserve stays booked), logged `spend_cost_unknown`; the final `Reply` gets `usage_estimated=True` | `unknown` | the real cost cannot be read, so book the largest sound number |
| the same on a **self-hosted** route (D11) | `settle` at the floor (the price is 0, so the number is 0) | `floor` | nothing is billed; keeping a zero reserve would only add noise |
| a **definite client error**: HTTP 400, 401, 403, 404 or 422 (a kind hook `refused(exc)`) | `release` | none | the provider refused before generating |
| anything else: timeout, connection error, 408, 429, any 5xx, an unparseable 200 (F6), a certificate error, any other `Exception`, `KeyboardInterrupt` or another non-`Exception` exit | `keep` | `failed` | the attempt may have been billed (D23); a missing status is also `keep` |
| the gate refuses the **next** attempt | no new reservation; earlier attempts keep what they were booked as | | the refused attempt sent nothing |
| the process dies or the store write fails | the reservation stays open and counted | | fail closed; `limits orphans` lists it |
**N answered attempts in one call** (the OpenAI-compatible second request): each answered attempt is settled at the moment its own answer is parsed, from that answer's own token counts, so a call with two answered requests writes two `reserve` rows and two `final(settle)` rows and the call's booked total is their sum. The call's `Reply.cost_usd` is the existing combined price (`llm/openai_compat.py:122,131`) and equals the sum of the two settles when no floor binds (the test checks it).

**The status hook (lock-in watch point).** `NetworkLLM` gets a class attribute `refused: Callable[[BaseException], bool | None] | None = None`, the same shape as `retryable` (a class attribute set with `staticmethod` in the kinds, for example `bedrock.py:115-116` and `anthropic.py:93`). The generic rule is `retry.status(exc)` in {400, 401, 403, 404, 422}. `llm/bedrock.py` sets its own hook that reads `response["ResponseMetadata"]["HTTPStatusCode"]` (where `detail()` at `bedrock.py:93-101` and `retryable()` at `:104-110` already read it). A hook that returns `None`, an exception with no status, or **a hook that itself raises** gives "not refused": the attempt is `keep` (over-counts, never under-counts).

**Unknown usage, the sanity floor, and what the floor is not (M-F).** `answer_usage(ans)` in `llm/common.py` returns the token pair of one answer or `None` (unknown): unknown when the input count is missing or 0, or when the output count is missing or 0 **and** the answer carries text or tool calls. This is the same condition under which `reply()` falls back to its estimator (`common.py:164-165`; `estimate_tokens` is `:59-62`), so `Reply.usage_estimated` (new field, default False, in `models.py`) is true when **the estimator fired in `reply()` or `book.unknown_seen` is set** (v7's "exactly when the booking was unknown" was wrong for the OpenAI-compatible two-request path: `reply()` combines two answers, so the flag is the OR over both, and `book.unknown_seen` carries the per-attempt fact). The floor is `floor_for(est, ans) -> Decimal` in `llm/common.py`, with `est` the `Estimate` of 4.1 below: (input tokens estimated over what was sent) x input price / 10^6 + (output tokens estimated over the answer's text and the JSON of its tool calls) x output price / 10^6. **The floor is not a lower bound of the true cost** (v7 called it one in effect): the 3-characters-per-token estimator is high for English and low for text with few characters per token, so the floor is a **sanity floor**: it catches usage of zero or absurdly small, and nothing else. It is not used anywhere as a bound. Because it can lift a booking, the monthly report names the lifted part separately (basis `floor`), so the invoice rule is no longer disturbed by it. **The invoice rule is revised** (section 0 item 5b): the over-count parts are shown apart from the reported part, and only a total **below** the invoice is the alarm. The floor and "unknown means keep" apply only to **network** kinds; a named test double wrapped by `MeteredLLM` (demo stage, 4.2) books its own `reply.cost_usd` with floor 0 (this keeps `tests/test_k5_tools.py:723-731` passing). Output bound: the output of one request is bounded by `max_tokens` for the Anthropic and Bedrock kinds (request bodies read, `anthropic.py:107-120`, `bedrock.py:132-154`); for Gemini the body sets `maxOutputTokens` and no thinking setting (`gemini.py:54-83`) and `_parse` adds `thoughtsTokenCount` to the output (`gemini.py:97-100`); for the OpenAI-compatible kind the body sets `max_tokens` or `max_completion_tokens` (`cap_field`) and no reasoning setting (`openai_compat.py:94-116`). **Not known:** whether a vendor counts hidden reasoning tokens inside those caps; so for Gemini and OpenAI-compatible no output bound is claimed: the reserve is an estimate, `settle` books the reported usage whatever it is, an excess over the reserve is booked and logged `spend_overrun`, and the provider-side limit is the backstop.

**Prices: tiers, a size limit and a cache price (M-B, D26).** `Route` (`config.py:55-60`: `model_id, input_usd_per_mtok, output_usd_per_mtok, max_tokens`) gets optional fields, all validated by one `model_validator`: `tier_above_tokens: int | None`, `tier_input_usd_per_mtok: Money | None`, `tier_output_usd_per_mtok: Money | None` (all three or none), `cache_read_usd_per_mtok: Money | None`, `max_input_tokens: int | None` and `self_hosted: bool = False`. The rule in `.claude/rules/model-choice-and-cost-follow-bible.md` (dated 2026-11-04) lists a Haiku 5.5 price of 0.10 / 0.50 US dollars per million tokens for prompts up to 100,000 tokens and 0.50 / 2.50 above, with a cache-read price of 0.01; I could not check the vendor's page (no network), so **those numbers are UNVERIFIED here** and are not written into any default: a route states its own. **One price function**, `cost_of(route, input_tokens, output_tokens, cached_tokens=0)` in `llm/common.py`, used by `reply()` and by the gate, so there is one place: it uses the tier prices for the **whole call** when the reported input tokens exceed `tier_above_tokens` (assumed: that the higher tier applies to the whole call and not only to the tokens above the threshold; **UNVERIFIED**, a vendor fact; the assumption errs high). The **reserve** uses the tier price when `input_estimate x margin` is above the threshold. A route that declares `max_input_tokens` makes `NetworkLLM.chat` refuse a call whose estimated input exceeds it with `SpendRefused("prompt_too_large")`, before any reservation; a route with neither tier fields nor `max_input_tokens` is a flat price and says so in the config. **Cache:** none of the four kinds sends a cache marker (F19), so no cache price is applied today; `cache_read_usd_per_mtok` exists so the field is ready, and **a guard test fails if `cache_control`, `cachedContent`, `cached_tokens` or `cache_read` appears in `llm/*.py`** until the estimator and the settle step read cached tokens (a kind that starts caching must extend `cost_of`, not slip past it). A provider that caches on its own and reports cached tokens inside the input count makes our cost higher than the invoice, which is the safe side. No batch discount is applied (errs high). Whether any model-reply cache exists in the repository is **not verified** (section 0 item 3).

**Self-hosted models in live stages (M-H, D11).** The zero-price refusal (`k1b/replay.py:85-91`) would make a self-hosted model unusable in pilot and prod. v8 ships the flag now: a route may have a zero price only if the llm kind is `fake` (demo stage; the fake kind is already refused in pilot and prod, F14), **or** the route sets `self_hosted: true`, the llm kind is `openai_compat`, and its `base_url` is `http` on loopback (`127.0.0.1`, `localhost` or `::1`, the set `_LOOPBACK` in `backends/table.py:66-85`, whose settings validator already allows `http` only with no key and on loopback). **Settle details.** `finish(res, how, booked_usd, basis)` on the meter: (1) a booked cost that is not finite or is negative books as `keep` with basis `failed` and logs `spend_bad_cost`; (2) a booked cost above `MAX_SPEND_NANO` is booked **as** `MAX_SPEND_NANO` and logged `spend_actual_capped`; (3) a cost above the reserve is booked and logged `spend_overrun`; it never refuses after the provider billed. **It catches every `Exception`** from the store, logs `spend_finish_failed` (class name only) and leaves the reservation open and counted (M-C: v7 caught four named classes, so a `ConnectionResetError` from the store escaped into the retry classifier, which treats an `OSError` as transient and would have sent the same billed request again; 4.2 adds the test). ```
def one_attempt():
    att = book.begin()                                  # raises SpendRefused only
    try:
        ans = call()                                    # the kind's request + its _parse
    except Exception as exc:
        how = "release" if _refused(self, exc) else "keep"     # _refused catches any exception from the hook -> False
        book.finish(att, how, None, None if how == "release" else "failed"); raise
    except BaseException:
        book.finish(att, "keep", None, "failed"); raise
    try:
        usage = answer_usage(ans)                       # None = unknown (4.1)
        if usage is None and not book.route.self_hosted:  # unknown usage (a self-hosted route is priced at the floor, 4.1)

### 4.7 `extract()` masking and restore (resolves v4 security B-4, B-5, M-7 to M-9, N-2; v5 security major 9)

- **What a compromised runtime can and cannot do (reworded, M-E).** Code running in the agent process holds the provider key and the runtime database role. It can call the provider directly and skip every check here (section 0 item 8); this design does not prevent that. With the new tables and the default setup it **cannot**: edit or delete any row, write a second final for one reservation, write an adjustment, or write a final that differs in agent, day or run from its reserve. It **can**, and this is stated rather than hidden: (1) write a `settle` with an `actual_nano` of 0 for its own open reservation (the same as a release), once per reservation, and so hide money of calls it made; (2) **insert a reserve or a `direct` row carrying another agent's `agent_id`**, because `agent_id` is a free column and the runtime role holds `INSERT`: this fills that agent's daily and monthly caps (a denial of service on the other agent) and, for a reserve with no final, stays counted until an operator relieves it; (3) insert reservations that it never finishes. **Control, optional (D29):** fill `spend_agent_role`, one database role per agent; then the trigger refuses a row whose `agent_id` is not that role's agent. **Negative tests** (below, items 14 and 15) show both the gap (map empty) and the control (map filled).
