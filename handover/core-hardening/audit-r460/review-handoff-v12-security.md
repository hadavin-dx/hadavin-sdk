# Hand-off v12 security and money-path review (egm-design, uncapped path; condensed copy of the inline report), 2026-11-16
Target: audit-r460/CORE-PR-HANDOFF-v12.md. Verdict: NOT clean. 1 blocker, 5 majors, 6 minors. Nothing was run; Postgres findings come from reading source plus memory of how Postgres orders checks, not from a test.

## BLOCKER
- B1 DB-1 `CHECK (usd >= 0)` (Q34) most likely breaks every give-back and settle on Postgres. store/postgres.py:419-430 `add_spend` is `INSERT ... VALUES (agent, day, usd) ON CONFLICT DO UPDATE SET usd = spend.usd + EXCLUDED.usd`. Postgres checks CHECK/NOT NULL on the proposed INSERT row before resolving the conflict, so a settle delta (actual minus worst, nearly always negative) or a give-back (negative worst) fails with 23514 even if the stored total stays positive. After DB-1 is applied: every settle and give-back fails, every call keeps its full worst case, refused reserves leak, agents hit daily_budget within a few calls, spend_settle_failed rows flood. The Q34 premise ("only refuses a negative total") is wrong for this write shape; the document repeats it (5.6, L7). E0-DB-1's positive control (reserve, then give back to 0) would probably catch it, but only at build time. Fix: negative deltas use `UPDATE ... SET usd = usd + %s WHERE agent_id=%s AND day=%s RETURNING usd` (INSERT only for positive amounts) in the S-2a store code, or put the rule in a BEFORE UPDATE trigger on the resulting value; tell the lead the Q34 premise was wrong.

## MAJOR
- M1 The decrease-log trigger (5.6(b), `WHEN NEW.usd < OLD.usd`) is evaded by rewriting the row key. The runtime role has UPDATE on the whole table (store/migrate.py:53-54; PK (agent_id, day) at 0001_core.sql:87-92). `UPDATE spend SET day = day - 3650 WHERE agent_id='x'` (or renaming agent_id; spend_month via month) keeps usd equal, logs nothing, and the next reserve upserts a fresh row at 0. "Decrease larger than one call cap" is also defeated by many small decrements, and by zeroing a total below the cap. Fix: BEFORE UPDATE trigger that raises on any key-column change, or GRANT UPDATE (usd) only; alarm on the per-agent-day sum of decreases. Drop "DB-1 makes the first visible afterwards" (5.6 item 6(b), L8) unless fixed.
- M2 The qualify gate counts a spend refusal as a pass. guard/judge.py:108 `passed += v.reason_code != "guard_unavailable" and v.flagged == case["injection"]`; evals.py:104-110 uses it for judges_green. The new default flag mode returns flagged=True, reason_code="spend_refused", so every injection:true case passes without the judge running once cap or window is hit mid-qualification. The document's remedy (raise only "if it runs inside a run", UNVERIFIED) misses it. Fix: qualify excludes spend_refused or always uses spend="raise"; add a mutant.
- M3 GRANTS timing makes `migrate()` fail on main after DB-1 merges. `check_grants` (store/migrate.py:150-166) raises "GRANTS names X, which no migration creates" and scans only store/migrations/. A GRANTS entry for spend_decrease_log added in DB-1 while the SQL sits in migrations_held/ breaks every migrate() and Postgres CI job. The entry must go in the lead's move PR; E0-DB-1 must monkeypatch GRANTS. `_SAFE_CREATE` (:80-85) accepts CREATE OR REPLACE FUNCTION but not plain CREATE FUNCTION: say "use OR REPLACE". (Same finding as the readiness review B1.)
- M4 `CallGate.admit` keeps a fail-open branch after S-2a: step (c) "no reserver -> return None". Any `build_gate(cfg, clock, window)` without a reserver silently meters nothing; census C2 only checks that make() gets gate=. Fix: require the reserver from S-2a (ConfigError) or an explicit window_only flag only S-1 and tests may set; census plus mutant.
- M5 File 2 (new table, SECURITY DEFINER function, trigger, GRANTS entry) and the Infinity clause go beyond Q34 (ORDERS.md:217, only CHECK usd >= 0). Only the Infinity clause is put to the lead (L7); file 2 needs its own lead yes. The trigger adds one extra INSERT per call inside the single-connection, single-lock transaction; the log has no purge or index; a full disk or lock on the log makes every settle fail (fails closed but stops agents).
