## 1. Words used (each means one thing everywhere)

- **Call**: one `chat(...)` on a model kind. **Attempt**: one request sent to the provider. One call makes one attempt, or up to `max_attempts` when the provider fails and the call is retried (`llm/retry.py:83-108`); the OpenAI-compatible kind can make two such groups inside one call (`llm/openai_compat.py:117-129`).
- **Spend record**: the two existing counters in the store, one per agent per UTC day and one per agent per UTC month (`Store.add_spend`, `store/protocol.py:107`). Nothing here moves money; "booking" means changing these counters. We never pay anything. The provider bills the studio later.
- **Reservation**: before an attempt, the counters are raised by the most that attempt could cost (the **worst case**). If the raised counters would pass a limit, the call is refused and the raise is taken back.
- **Settle**: after an attempt that returned a usable answer, replace the reservation with the real cost the provider reported. **Keep**: leave the reservation as it is (used after a failed attempt, because the provider may have billed it). **Release**: take a reservation back off without an answer. v11 releases in two cases only: our own gate refuses (no request was sent), or the provider answers with a definite client error (status 400, 401, 403, 404 or 422: the provider rejected the request itself). After any other failure once a request was sent, the reservation is kept (section 5.3).
- **Wall**: a limit that stops further calls: the daily budget, the monthly budget, the window end, or the one-call cap.
- **Window end** (`spend.window_end`): the last UTC date on which live model calls are allowed. A call is refused from 00:00 UTC on the next date, which is 05:30 IST that day. The last allowed moment is 23:59:59 UTC, which is 05:29:59 IST the next day.
- **Gate**: code that runs before every attempt and may refuse it. **Scope**: the information "this call belongs to agent X, with these limits" that the gate needs to reserve against X's budget. In v10 a paid call with **no scope is refused** (`scope_missing`), never let through unmetered; command-line paths get a scope from a cap the person types (`--max-usd`), section 5.8. A **paid kind** is a configured backend that sends text to a priced service (section 5.1).
- **The customer demo** is the event the owner is preparing for. **The demo stage** is a core stage name (R449) and is always written in code font as `demo`. v10 never names a stage in a rule, so the stage rename does not touch it.
- **Money type (OWNER-OPEN, question D5; v11 grants itself no exception and picks no default).** CLAUDE.md says "money is integers". The money values that exist today are `Decimal` US dollars: `Reply.cost_usd` and `Verdict.cost_usd` (`models.py:294`, `:305`), `Route` prices (`config.py:57-58`), `Budget` (`registry.py:33-36`), the `spend` and `spend_month` tables (`store/migrations/0001_core.sql:87-92`, `0003_approvals_tick.sql:15-20`) and `runs.cost_usd` (`models.py:98`). Step 1 (S-1, S-2a, S-2b) adds **new** `Decimal` money values next to them (the `Config.spend` amounts, `Reply.booked_usd`, `SpendScope`, `Ticket`), because the store, `Limits`, `Budget` and every price are `Decimal` already and the two spend columns are `NUMERIC`. The owner's options, with the price of each in plain words: **(A)** keep `Decimal` US dollars for step 1 and for any later new table, as a written exception to the integer rule (no migration; the risk is rounding mistakes that integers avoid; the code never uses floats and always rounds a reservation up and a limit down); **(B)** whole nano-dollars (1 nano-dollar = 0.000000001 US dollar) in `BIGINT` for a **new** table only, the existing `Decimal` values stay (two money units in one code base and one conversion function); **(C)** integers everywhere (a migration of both spend tables and a rewrite of every reader and every price field; the largest change, the most consistent with the rule). **No option is the default.** S-1 does not start until the owner answers D5 (section 7.1, start gates), and the answer is written into this section. Review-by date 2026-12-31: if D5 is still open on that date, the gate stays closed and the lead tells the owner.

## 3. Extend or replace: evidence (improve-before-replace)

**What exists.** (a) The demo meter (F1, F2): the right protocol, proved by its tests: reserve the worst case before, settle after, keep on failure, refuse leaves nothing booked, cap holds under four racing processes. (b) `k1b/loop.py:115-122` (F3): the worst-case formula for an abandoned call plus a per-invocation budget. (c) The core's own counter `Store.add_spend` with day and month totals and `Limits.blocked` (F4, F5): atomic in Postgres, shared by every process on the same database.

**What each lacks.**
| Piece | Lacks |
|---|---|
| Demo meter | per-attempt reservation (it reserves once per call); a window end; the store (it is a local file, one host); per-agent caps; any use outside the demo (core must not import from `demos/`, and a client hand-over deletes that folder) |
| k1b worst case | it is a copy of the formula, not shared; it prices only a timed-out call |
| `add_spend` and `Limits` | any reservation before a call (the charge happens after the answer, `agent_loop.py:440`, so one call can pass a cap by one call's cost plus its retries); a window end; protection against a negative amount; a clock |

**Verdict: extend, do not replace.** Take the demo meter's **protocol** (not its code) and run it on the existing store: reserve the worst case with `add_spend` (atomic, returns the new totals), refuse and give back if a total would pass its limit, settle with the difference. One shared formula `llm/spend.py:worst_case_usd`/`cost_of` replaces the three copies: `k1b/loop.py` calls it (a test pins equal numbers on the fixture route, E0-S1-4) and the demo can later pin the core commit and drop its copy (promotion table, a follow-up, not in this document). **Why not the file meter:** one host only; the core supports several processes on one database. **Why not a new ledger first:** the lead's smaller first step needs no migration of money columns; a ledger is justified only by the triggers in 5.10.

### 5.1 Settings (S-1)

`Config.spend` (new, `extra="forbid"`, default `SpendSettings()` through `Field(default_factory=...)`, so every existing config without the block still loads), in `config.py` beside the stage table (the model validator at `config.py:349`). A **paid kind** is any configured backend that sends text to a priced service: `backends.llm.kind` other than `fake`, or a detector kind listed in the new `defaults.PAID_DETECTOR_KINDS` (today one entry, the Bedrock guardrail kind). The window rule below follows **paid kinds**, not only the llm kind (security major 7).
- `window_end: date | Literal["none"] | None = None`. Required (a date) whenever any paid kind is configured; `none` only with `environment == "prod"` and a `window_owner` (role label, pattern `[a-z][a-z0-9_-]{1,40}`). `null`, a missing key, `None`, `NONE` are refused with "write the date 2026-12-01 or, in prod only, the word none". A **date and time** (YAML `2026-12-01 10:00`) is refused with "write a date only"; an unquoted or quoted date is accepted (YAML reads an unquoted date as a date and `~`/`null`/empty as null, `config.py:400-415`; E0-S1-2). With no paid kind (all fake) the whole rule is ignored.
- `max_call_usd: Money | None = None` and the per-call cap rule: `Limits.call_cap(agent_id)` returns `max_call_usd` if set, else the agent's daily budget divided by 4 and **rounded up** to 8 decimal places (`Decimal.quantize(Decimal("1E-8"), rounding=ROUND_UP)`). One owner of the number (5.5).
- `reserve_margin: Decimal = 3` (minimum 1): multiplies the **input** estimate only. The output part is `route.max_tokens` times the output price. The estimator (`llm/common.py:59-62`, `len(text)//3`) is a high guess for English and a low guess for text with few characters per token (Chinese, base64). 3 is my choice, **not measured** (5.9 item 3). Measuring it needs a real tokenizer count on real text, which only the lead can supply (L2); until then the default stays and the document says "unmeasured".
- Every number in `Config.spend` is checked **finite** at load (security minor N4: `reserve_margin`, `max_call_usd`, `guardrail_usd_per_call`, `unattributed_*`, `cli_*`, `max_plausible_tokens`); `reserve_margin` must be at least 1 and at most 100; a `NaN`, `Infinity`, negative or zero value is a `ConfigError` (test E0-S1-2). ### 5.2 The window end (S-1)

One pure object `SpendWindow(end: date, clock)` in `llm/spend.py`; `check()` raises `SpendRefused("window_ended")` when `clock().astimezone(UTC).date() > end`. - **Where.** `NetworkLLM._retry` runs the gate's `admit` before every attempt (5.3). `SpendRefused` is defined in `errors.py` and is not a `ProviderError`; `with_retry` gets one changed line, `except (ProviderError, SpendRefused): raise` (`retry.py:95-96`, new import `errors`), so a refusal is never wrapped or retried. Consequence: the `except ProviderError` sites (`k1b/loop.py:176`, `agent_loop.py:432-433`) no longer catch it, which is what we want; the S-2a builder reads `k1b/loop.py` 85-215 and gives the replay a defined end for a `SpendRefused` (test in E0-S2-4). A retry loop that crosses 00:00 UTC stops on the next attempt.
- **Fake kind decision (readiness blocker 1 and security major 7).** The fake kind (`FakeLLM`, `llm/fake.py:21`) is a plain class, not a `NetworkLLM`, has no gate and no reservation, and is refused outside the `demo` stage (`DEV_ONLY`, `backends/table.py:593-602`, `config.py:366-369`). **The guardrail is independent of the llm kind**: with `llm.kind: fake` and a guardrail detector configured, `build_window` still returns a window and the detector checks it before `apply_guardrail`. Test: fake llm + guardrail + a past date → the guardrail refuses and no `apply_guardrail` request is made.

Bound: S-3 and the invoice comparison; database time comparison is L-1 (trigger: skew above 60 seconds, or machines the studio does not control). **Overshoot after the end, named (security major 6):** a request admitted at 23:59:59 UTC is billed after midnight; the bound is one request per attempt in flight at that moment, per process (each priced at most its worst case), and the retry sleep (at most 8 seconds, `retry.py:23`) cannot add an attempt because the next attempt checks the window.

**One attempt.** `_retry` keeps its signature `def _retry(self, call: Callable[[], Answer]) -> Answer`; `self._retry_args()` is the existing keyword list of `common.py:233-241` moved into a helper:

```python
def _retry(self, call):
    gate = self.gate
    if gate is None:                              # only with unmetered=True (tests of the kind itself)
        return with_retry(call, **self._retry_args())
    ctx = _CALL.get()
    if ctx is None:                               # a paid request outside chat(): fail closed
        raise SpendRefused("call_context_missing")
    def attempt():
        ticket = gate.admit(ctx)                  # window, abandoned, kill switch, scope, one-call bound, reserve
        try:
            answer = call()
        except BaseException as exc:
            if spend.definite_client_error(exc):  # status 400, 401, 403, 404 or 422 (defaults.NO_BILL_STATUSES)
                gate.release(ticket, ctx)         # the provider rejected the request itself: nothing was billed
            else:
                gate.keep(ticket, ctx)            # the provider may have billed it: stays booked
            raise
        gate.settle(ticket, ctx, answer.tokens)   # never raises; adds what it booked to ctx.booked
        return answer
    return with_retry(attempt, **self._retry_args())
```

`answer.tokens` is `tuple[int | None, int | None]` (`Answer.tokens`, `common.py:184-189`: input count, output count), fixed here as the only shape `settle` accepts (readiness major 6). `BaseException` includes `KeyboardInterrupt`: kept, then re-raised unchanged. `spend.definite_client_error(exc)` reads the status with `retry.status` (`retry.py:31-36`) on the error itself and on its cause chain; the set of statuses is `defaults.NO_BILL_STATUSES = {400, 401, 403, 404, 422}` (dated 2026-11-16). **UNVERIFIED:** that each of the four kinds' error objects exposes a status that `retry.status` can read (the Bedrock error object may not) and that no vendor bills these statuses; a kind whose error shows no status keeps the reservation (the safe direction), and E0-S2-4 prints a per-kind table of what each stub error exposes.

**The gate's actions** (`llm/callgate.py`):
1. `admit(ctx) -> Ticket | None`, in this order, all before any request: (a) `window.check()`; (b) `if _ABANDONED.get()` is set → `SpendRefused("abandoned")` (5.8); (c) no reserver → return `None` (S-1); (d) `scope = _SCOPE.get()`; none → `SpendRefused("scope_missing")` (**fail closed**: v9 security major 5; there is no default scope, so a paid call that belongs to no agent is never booked against a shared pseudo agent by accident (readiness major 2 of v10); a thread started without the context, a command-line path with no cap, a library caller with no scope all stop with a loud code instead of spending unmetered); (e) `ctx.booked + ctx.worst > scope.max_call` → `call_too_large` (before any write). **The cap is for the whole call, retries included** (security major M4: v10 compared one attempt only, so one failed call could keep three worst cases, about 75 percent of the day at the default cap; now one call keeps at most `max_call`, about 25 percent); (f) `reserver.reserve(scope, day, ctx.worst)` with `day = clock().astimezone(UTC).date()`. Any `decimal.InvalidOperation` or non-finite value met in this arithmetic is `SpendRefused("bad_amount")` (fail closed, the right code: security minor N4).
2. `Limits.reserve(scope, day, worst) -> Ticket`: reads the kill switch (`store.get_kill_switch`, security minor 3: a switch set during a run now stops the next attempt) and raises `SpendRefused("kill_switch")` if on; runs `store.add_spend(agent, day, +worst)` (which returns the new day and month totals); **refuses when a new total is at or above its limit (`>=`, the same comparison as `Limits.blocked`, `limits.py:26,28`; security minor 2: v9 admitted a total exactly at the limit with `>`, which `blocked` would then refuse on the next call)**, after giving the amount back with `add_spend(agent, day, -worst)` and raising `daily_budget` or `monthly_budget`. Any other exception from the store (including `StoreUnavailable`) means the spend record could not be read or written: `SpendRefused("limits_unavailable")`; if the give-back itself fails the amount **stays booked** (fail closed), `_LOG.error("spend_giveback_failed")` is written and an audit row `spend_giveback_failed` is written the same best-effort way (security minor N3); `limits status` (S-2b) counts both audit rows for the month. A reserve whose acknowledgement is lost after the database committed leaves the amount booked and the call refused: a safe over-count (v9 security minor 7), stated here and tested (E0-S2-4). **The same holds for settle** (security minor N7): if the acknowledgement of a settle is lost after the database committed, the call returns its answer while the spend record holds the real cost, or if the write never happened the worst case; the count is then too high by at most `worst - actual`, never too low.
3. `CallGate.settle(ticket, route, tokens) -> Decimal` **never raises** and returns the amount the spend record now holds for this attempt (security major 3). Body: `ticket is None` → 0. `spend.clean_tokens(tokens, route, settings)` returns the two counts and a status. Limits: input `route.max_input_tokens`, or `spend.max_plausible_tokens` (5.1) when the route has none; output `route.max_tokens * 4`. Status **ok**: both counts are `int` (not `bool`) with `0 < n <= limit`. **missing**: `None`, zero, negative, a float or a bool: **keep**, `usage_missing` is logged and the worst case stays booked (v9 security majors 1 and 2: zero or negative usage must never become a small number). **high** (security minor N1: v10 left the bound undefined): an `int` above its limit, for example hidden reasoning tokens: book `max(worst, cost_of(route, n_in, n_out))`, never less than the reservation, log `spend_usage_above_bound` at error level and write an audit row (below). Otherwise `actual = max(cost_of(route, n_in, n_out), 0)` and `reserver.settle(ticket, actual)` runs `store.add_spend(agent, ticket.day, actual - worst)` (the same day as the reservation). **The whole body sits in `try/except Exception`**: on any failure it logs `spend_settle_failed` (class name only) **and writes one audit row** `spend_settle_failed` through `Limits.audit.write_outcome` (best effort: if the audit write also fails, the error-level log line stays; security minor N3, because the later PR L-1 is triggered by "any `spend_settle_failed`" and a log line alone would not be found), does **not retry** (a retry after a lost acknowledgement would book twice), and returns `worst` (the reservation stays). Because `settle` never raises, a failed settle can no longer be classed transient by `with_retry` (an `OSError` is, `retry.py:63`) and **can no longer cause a second paid request** (the v9 flaw), and a paid answer is never thrown away because the spend store failed.
4. `keep(ticket, ctx)`: writes nothing to the store; adds `ticket.worst` to `ctx.booked` and to `scope.kept` (the run's own cost record includes it, 5.5). `release(ticket, ctx)`: `reserver.release(ticket)` runs `add_spend(agent, ticket.day, -worst)`; if that fails it behaves as a failed give-back (the amount stays booked, so `keep(ticket, ctx)` is applied, logged and audited). Both never raise.

**What each outcome books:**
| Outcome of an attempt | Booked | Why |
|---|---|---|
| usable answer with sound usage numbers | the real cost (`settle`, never below zero) | normal |
| usable answer with missing, zero, negative, non-integer or implausible usage | the worst case stays (`keep`) | a missing number must not become a small number |
| a failed settle (store error) | the worst case stays; answer returned; one log line | no second request, no lost answer |
| the provider answered 400, 401, 403, 404 or 422 (a definite client error) | nothing (`release`) | the provider rejected the request itself; UNVERIFIED that no vendor bills it (5.9 row 5); a wrong key books nothing |
| any other exception after the request started (timeout, connection error, 408, 429, 5xx, malformed 200, certificate error, status not readable, anything else, `KeyboardInterrupt`) | the worst case stays (`keep`) | the provider may have billed it |
| usable answer with a token count above its bound (`high`) | `max(worst, cost of the reported counts)` | hidden reasoning tokens must not under-book (N1) |
| our own gate refuses (window, abandoned, kill switch, scope missing, one-call cap, daily or monthly limit, prompt too large, store unreadable) | nothing (the give-back already ran) | no request was sent |

A wrong key (401) or a malformed request (400) books nothing, so it cannot empty the day (v10: four calls). A 429 storm or a 5xx outage keeps the worst case of each attempt, but one call keeps at most `max_call` in all (admit step (e)). Releasing 408, 429, 5xx and timeouts is L-6 (needs invoice evidence).

**Reply and verdict.** `Reply` gains `booked_usd: Decimal = Decimal(0)` (set by `model_copy(update=...)` in `NetworkLLM.chat`: `Reply` is a pydantic `Shape`, not frozen, `models.py:289-297`); `Verdict` gains `booked_usd` the same way; `JudgeDetector.check` copies `reply.booked_usd`; `injection.combine` sums it beside `cost_usd` (`injection.py:77`). `reply()` (`common.py:164-172`) and the gate use the **one** `clean_tokens` and `cost_of` (security major 1: today `tokens[0] or estimate` lets a negative count through to a negative `Reply.cost_usd`). For the OpenAI-compatible kind `booked_usd` is the sum of its settles and `Reply.cost_usd` is priced from the summed tokens; equal for a flat price (E0-S2-4).

### 5.4 Numbers that could lower a total: refused at the choke point (S-2a)

Class: **a value that is negative, zero where a count is meant, not finite, or implausible reaches a money total.** The choke points are `Store.add_spend` (all writers) and `Limits.charge`/`settle` (our writers). Fixes, each with a hostile-input test:
1. Prices, budgets and every `Config.spend` number: finite, `ge=0` (5.1; security minor N4: v10 applied the finite rule to `Route` and `Budget` only).
2. Token counts: `clean_tokens` (5.3 item 3); `reply()` uses it, so a negative count no longer prices negative.
3. `Limits.charge(agent_id, usd, booked=Decimal(0))` adds `max(usd - booked, 0)` and refuses a non-finite `usd` or `booked` with `ValueError`; a negative `usd` is clamped to 0 (a negative reply cost from a buggy kind no longer lowers the total).
4. **Both stores, same rule** (`store/postgres.py:416-431`, `store/memory.py:196-204`): `add_spend` first refuses a non-finite `usd` (`ValueError`), and refuses any change that would leave a day or month total **below zero**: Postgres checks the two values returned by the upserts inside the same transaction and raises, which rolls both back (psycopg's `transaction()` context rolls back on an exception); the memory store computes before it commits. This is the code-level refusal that stands in for the database `CHECK` (5.6). It does not stop a writer that bypasses our code.
5. Excess over the worst case: `settle` books the real cost even when it is above the reservation (real money was spent; the counters should show it). A reported cost that is huge but passes `clean_tokens` is bounded by the plausibility limits, and booking it errs on the side of a stop, never a pass.

### 5.5 The runtime side (S-2a)

- **Scope.** `Limits.scope(agent_id) -> SpendScope` builds it (`daily`, `monthly` from the agent's `Budget`, `max_call = call_cap`); `Runtime.handle` opens it with a context manager around the run body (sets and resets `_SCOPE`). ### 5.6 The database side

1. **DB-1: migration `0006_spend_nonneg.sql`, scheduled (section 7.1, merge order 4), applied only on an owner yes (lead's answer Q34).** (a) *What it does:* `ALTER TABLE spend ADD CONSTRAINT spend_usd_ok CHECK (usd >= 0 AND usd < 'Infinity'::numeric)` and the same for `spend_month`. **For the lead, because Q34 did not name it: the second clause `usd < 'Infinity'`.** Q34 says the check "only refuses a negative total" (`usd >= 0`). In Postgres a not-a-number value sorts above every other number, so `NaN >= 0` is true: plain `usd >= 0` lets a not-a-number total in (and, from Postgres 14, an infinite one). `usd < 'Infinity'` refuses both (NaN sorts above Infinity); UNVERIFIED here, E0-DB-1 tests it.
