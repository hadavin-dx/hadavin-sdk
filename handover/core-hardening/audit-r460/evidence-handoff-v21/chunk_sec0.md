8. **What this design does not protect against.** Code running inside the agent process holds the provider key and can call the provider directly. This design stops **mistakes and bugs** (a loop, a retry storm, a wrong estimate, a restart, a late date, a stuck lock) and nothing stronger. The only hard stop for a hostile process is a spend limit set at the provider (S-3, owner, POST-DEMO). A process holding the runtime database role can also change the spend tables directly (including another agent's rows) until DB-3 is applied; after DB-3 it can still reserve and settle under any agent name (5.6 item 1(o), "What stays true"). No sentence here says "no unmetered spend" or "cannot overspend"; section 6 lists every paid path.
9. **Stated, not closed, with the reason** (nothing here is a "known limitation" I chose to leave if I could fix it; each needs a design decision, the owner, or a person who runs something): (a) the single runtime login can settle a reservation under ANY agent name and can reserve any amount below the ceiling of 1,000,000,000,000 under any name and settle it back, so it can under-report; one login per agent (L-4) and the invoice comparison (7.3) are the controls; (b) agent ids that differ only in letter case are separate budgets, and a hostile login can choose any name; (c) a settle with `actual` above `worst` raises a total: it can only over-report spend, and refusing it would lose a true cost; (d) row spam inside the day window: unlimited rows by name and day; (e) a DELETE of the switch row is not recorded: a missing row reads as ON, the safe direction; (f) the 60 s `statement_timeout` of the DB-3 file is per statement and overrides a stricter value of the caller for that transaction (the nine `ALTER TABLE` statements could take up to nine minutes in total, and the file's comment now says so); (g) the start-up query does not pin function bodies by a hash of the stored text (`pg_proc.prosrc` or `prosqlbody`): I could not show that text is the same on 14, 16 and 17 (UNVERIFIED); the file guard pins the SQL text instead; (h) the store must treat an empty result of `spend_reserve` or `spend_settle` as an error (5.6c item 3, E0-F5).
