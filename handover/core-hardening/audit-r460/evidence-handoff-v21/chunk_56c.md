### 5.6c The guard, the DB-3 file text, the start-up check and the status check: the specs as they stand

**1. The guard rules after S1 to S7 and N1 to N3 (`evidence-handoff-v21/secdef_guard_v21.py`; its docstring has the same list).** Each rule below was found by a reviewer or by an independent runner, shown to work **on the real server (16.15)** in `pg_v21.py` and shown **missed by the previous guard** in `secdef_mutants_v21.py` (the counts are in section 8). The earlier guard is kept in the folder as `secdef_guard_v20.py` only for that comparison.
- **Bodies.** A `SECURITY DEFINER` function whose body is `RETURN <expression>` is scanned like any body; a definer whose head is not `BEGIN ATOMIC` or exactly one string or dollar-quoted body is a problem (a definer with nothing to scan is not a pass). A call written as `%I.name(` inside an `EXECUTE` string follows the same call rules. `MERGE INTO`, `DELETE ... USING` and `TABLE x` inside an atomic body count as touching the table they name. Expressions inside the allowed shapes (`CHECK`, `DEFAULT`, `GENERATED ... AS`, index expressions, trigger `WHEN`) are read with the same call rules; allowed calls are the dated list `CALLS_OK` plus `btrim`, `char_length`, `extract`. `SET` is allowed after `UPDATE` only in the `SET column = ...` shape.
- **Triggers are pinned per file** (`TRIGGER_PINS_BY_FILE` in `allow_v21.py`: ten in DB-2, four in `0002_audit_chain.sql`). `DROP TRIGGER` of an unpinned name, and any `CREATE OR REPLACE TRIGGER` whose text differs from the pin (for example `WHEN (false)`), are problems. **`DROP TRIGGER IF EXISTS x ON t` must name the same table `t` as the `CREATE TRIGGER x` that follows** (the v20 guard did not compare the two tables).
- **Each listed definer has a text fingerprint and a statement-kind pin.** The fingerprint is the first 16 hex digits of the sha256 of the JSON list `[kind, gap, text]` of every token of the statement with comments removed (`FN_PINS_BY_FILE`); `gap` says whether white space came before the token, so `@-` and `@ -` (a different operator) and `E'x'` and `E 'x'` (a string and a syntax error) no longer give one fingerprint. The kind pin (`KINDS_BY_FILE`) lists the statement kinds a body may contain: `kill_switch_release` may contain only `UPDATE`; `DELETE`, `TRUNCATE`, `MERGE`, `COPY` and a `WITH` that writes are problems. **Cost, said plainly:** any edit of a pinned function, even a comment inside the body, needs the pin regenerated (`python3 -I -B make_allow_v21.py` shows how the v21 pins were derived from the v20 ones, and `python3 -I -B chk.py` prints the new values) and a second independent review. **The pins live in the same PR as the SQL: a PR that edits both passes the guard. This is why the guard is a tripwire; the reviewer reads the pin diff next to the SQL diff.**
- **The tokenizer follows the server's scanner.** Word characters include all non-ASCII characters; a dollar-quote tag may contain them; the white-space set is the server's; **a `--` comment ends at a line feed or a carriage return** (v20 ended it only at a line feed; shown on the server in `pg_v21.py`, section "v21"); **case folding is ASCII-only** (Postgres folds `A-Z` only: the Kelvin sign U+212A and the long s U+017F keep their identity, so `clocK_timestamp(` is not the allowed call `clock_timestamp(` and `ſelect(` is not `SELECT`; the server answers `42883` for both). The form feed is a separator for the server and for the tokenizer; a vertical tab is refused by the server (`42601`) and treated as a separator by the tokenizer, which is harmless.
- **`SET search_path` items are folded like the server folds them** (`_sp_item`): an unquoted name is folded ASCII-only, a quoted name keeps its case, so `"PG_CATALOG"` is not `pg_catalog` (the server keeps it as typed: `SHOW` prints `"PG_CATALOG", pg_temp`).
- **The relation scan** of a `BEGIN ATOMIC` body skips an alias column list (`FROM spend AS d (a, b), pg_authid`: the old scan stopped at the list and missed `pg_authid`) and `TABLESAMPLE ... REPEATABLE (n)`; a word after `AS` and before `(` is an alias or a type modifier, not a call. Words that can name a function (`KEY`, `FILTER`, `OVER`, `CONFLICT`) are treated as syntax only in their syntax position; `NOTHING` and `ELSIF` are not in the syntax set.
- **Timeouts and inheritance.** `SET LOCAL lock_timeout` or `statement_timeout` with a zero value (which switches the limit off) is refused. `CREATE TABLE ... INHERITS (...)` is refused (a child of `spend` would be read by `spend` queries).
- **Unit-test sentinel.** `PIN_ANY` switches one pin off in a test; `None` means nothing is pinned, so every listed item is a problem.
- **B1 of the independent runner of v20: the text of `ALTER TABLE ... ADD` was not pinned.** The runner changed the agent-id rule to `CHECK (true)` (H75), raised the ceiling to 1e30 (H76) and weakened the checks of the `spend` table alone (H67, H68); all four were judged clean and all four applied through `migrate()`. **Fix at the choke point:** `ADD_PINS_BY_FILE` in `allow_v21.py` pins the fingerprint of every `ALTER TABLE ... ADD` statement of every held file (the column, its default, the constraint name and the whole `CHECK` expression); a listed file with an `ALTER TABLE ... ADD` statement of another text is a problem. Tests: mutants W21 to W27 (each flagged by the v21 guard and missed by the v20 guard) and controls W28, W29 in `secdef_mutants_v21.py`. **Sibling class:** the product migrations `0001` to `0005` are reviewed code in git history and are not pinned this way (stated). **Not done, and why (impossible now):** the start-up check does not compare the stored text of the constraints (`pg_get_constraintdef`) with the pinned text, because I cannot show that text is the same on Postgres 14, 16 and 17 and only 16.15 exists here; next step: the S-2b builder adds the comparison and an independent runner repeats it on 14 and 17. Until then a weakened constraint applied by another route is found only by review.
- **What the guard does not do (stated, with the next step):** @@GUARD_OPEN@@

**2. The DB-3 file text (hash in section 8).** (a) **Agent id:** an ASCII allow-list, `CHECK (agent_id ~ '^[A-Za-z0-9][A-Za-z0-9._:@/+-]{0,199}$')`, on both tables (`IS NFC NORMALIZED` needs a UTF8 server and the control-character rule depended on the locale; fullwidth letters, a zero-width space, a leading no-break space and a right-to-left override were separate budgets before). **This is my own choice of characters, not a lead answer (L25): the lead must confirm that the real agent ids fit.** Result on real databases: UTF8 with `C.utf8` and with `C` collation work; LATIN1 works; SQL_ASCII: the product's own `migrate()` stops with a `TypeError` before any held file (psycopg returns bytes for names), so a client on SQL_ASCII must be told. **The pseudo agent names `-cli` and `-unattributed:<agent>` start with `-` and are refused by this rule: see item 8 (L26b).** (b) **No `NOT VALID`:** `NOT VALID` checks every new version of an old row, so an old row that breaks the rule could never be settled again; now the apply itself refuses (23514) and the whole transaction rolls back (nothing applied: shown). (c) `spend_settle`'s day update also requires the month row to exist. (d) **A settle that its checks reject returns no row** (the final `SELECT` ends with `AND p_worst >= 0 AND p_actual >= 0`; `NULL` makes the comparison `NULL`, so no row): v20 returned the current row, so with rows present (an existing reservation) a negative or `NULL` settle looked like a success and left the reservation open. Shown in `pg_v21.py` (G6: totals and open amount unchanged, no row) with the v20 file as control (it returns one row). (e) The comment on `statement_timeout` now says it is per statement.

**3. What the store code does with a refusal or an empty result (security major M2 of v20; findings F4 and F5 of the independent runner of v19).** `spend_reserve` with an amount of 0, a negative number, `-Infinity` or `NULL` returns **no row and no error**; `spend_settle` with a negative worst or actual, `-Infinity`, `NULL` (worst, actual or day), an agent or a day without a row, or a month without a row **also returns no row, raises nothing and changes nothing** (the independent runner of v20 listed these as silent no-ops; they are by design and the reservation stays open, which is the safe direction; shown in `pg_v21.py`, checks G6 and G6b); a settle larger than what is open raises `23514`. **The store code treats an empty result as a refusal that is never booked** (test `E0-F5`, below: the fake store returns no row, and, in the DB-3 move PR, the real functions are called with rows that exist). The day window is enforced at both ends (shown). **F4:** a runtime login can create a `TEMP` table named `spend` and a trigger or rule on it in its own session; the DB-3 functions still write the real table because their `search_path` is `pg_catalog, pg_temp` (temp last); that order is why the `SET search_path` rule of the guard is a safety rule, not a style rule. Both are tested in `pg_v21.py`.

**4. The start-up check: product inputs and ONE signature.**
- **Where it lives:** `src/hadavin_sdk/store/secdef.py` (new, written by the S-2b builder; S-2b hot file), holding `FUNCTION_POLICY` (signature, kind, who may execute, 5.6c item 5) and **`secdef_problems(db, *, roles, policy=None, owner=None) -> list[str]`**. This is the only signature in this text; the `migrate()` step and `PostgresStore.startup_checks` call the same function. The prototype is `secdef_audit_v21.py`; the builder copies it and renames nothing.
- **`roles`:** `{"runtime": <the runtime role name>, "operator": <spend.operator_role or "">}`. **Config key `spend.operator_role`** is a field of `SpendSettings`, added by S-2b (not S-1: it matters only once DB-3 exists), default empty, with a test in `tests/test_startup_secdef.py` that an empty value is a problem (not a `KeyError`) when a listed function needs the operator role. S-2b hot files gain `config.py` (`SpendSettings.operator_role`) and `store/secdef.py`.
- **`owner`:** `None` means the database owner (`pg_database.datdba`), read at start-up and never from config; with the dedicated owner role of item 8 (L26) the caller passes that role's name. The migration role is NOT used as the expected owner unless it is the database owner.
- **`policy`:** `None` means `policy_for_applied(db)`: **which files are applied is read from the database, not from a file ledger** (a hand-made function must not look like an applied file): DB-3 is applied when the column `spend.open_usd` exists, DB-2 when the table `spend_decrease_log` exists. A function of an unapplied file is not on the policy, so if it exists anyway it is reported as unexpected. When neither is applied the function checks pass vacuously and the output says so in one line (`no DB-2 or DB-3 function installed: nothing to check`); the L19 check still runs.
- **What it reads and reports** (runtime connection, no table privilege: `pg_proc`, `pg_roles`, `pg_depend`, `pg_trigger`, `aclexplode`): a function that is not on the policy, in another schema, or not a definer; an owner that is not the expected owner or a superuser; settings other than exactly `search_path=pg_catalog, pg_temp`; an `EXECUTE` holder (real ACL, or the default ACL when none is stored, so PUBLIC shows) other than the roles of the grant table; `EXECUTE` held with grant option; a listed function that is missing (when its file is applied); a runtime role that is a member of the operator role; for a `BEGIN ATOMIC` body, a relation it is bound to in another schema and **a function or operator it is bound to outside `pg_catalog`** (a body binds names at creation with the creating session's `search_path`; a hostile `>(numeric,integer)` or `date_trunc` earlier in that path would be called by the owner; security minor m10); **a trigger function of DB-2 whose trigger is missing or not enabled** (`pg_trigger.tgenabled` must be `O`: `ALTER TABLE ... DISABLE TRIGGER` by the owner at run time, or `ENABLE REPLICA`, is invisible to every file check; security note on M2 of v19). In `prod` and `pilot` a problem is a `ConfigError`, in `demo` a warning; `limits status` prints the count.
- **L19 detection, stated once (readiness major M2).** The temporary-table check of 5.6 item 1(h) runs when the decrease record exists OR the audit-reader role exists. Record: `SELECT to_regclass('spend_decrease_log') IS NOT NULL`. Role: `SELECT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = %s)` with `PostgresSettings.audit_reader_role` (empty = no role, check off). Both run on the **runtime** connection (no table privilege needed). 5.6 item 1(h) and G-4(v) use this one rule.

**5. Who may call each function: ONE grant table (readiness blocker B2).** This table is the policy in `FUNCTION_POLICY`, the text in 5.6(o) and the check in `secdef_audit_v21.py`; there is no other list.

| Function | Runtime role | Operator role | Anyone else |
|---|---|---|---|
| `spend_reserve(text, date, numeric)` | EXECUTE | no | no |
| `spend_settle(text, date, numeric, numeric)` | EXECUTE | no | no |
| `kill_switch_engage()` | **no (default, L22b)** | EXECUTE | no |
| `kill_switch_release()` | no | EXECUTE | no |
| trigger functions of DB-2 (`spend_log_decrease`, `kill_switch_log_change`, `kill_switch_log_insert`) | no | no | no (the trigger machinery runs them) |

Table rights after DB-3: the runtime role holds `SELECT` on `spend`, `spend_month` and `kill_switch` and nothing else on them; the operator role holds no table right; `PUBLIC` holds nothing. **L22b (OWNER-OPEN, default stated):** who may call `kill_switch_engage()`. **Default: the operator role only** (least privilege: a hijacked runtime login could otherwise write the switch row, and a stop it did not make is still a denial of service). **Alternative: the runtime role as well**. **What each costs:** with the default, the operator command `limits stop` (the only caller of the stop; `limits.py:43-46`, `cli.py:391`; the running agent never calls it) must connect with the operator login, so the operator holds one more credential for `stop` as well as `reset`, and nothing in the agent process can switch the database switch on; with the alternative, the agent process can stop all agents through the database (for example from a future breaker) but a hijacked process can also stop them. In-process stops are not affected either way. `pg_v21.py` tests the default (MA4: runtime `[T,T,F,F]`, operator `[F,F,T,T]` for reserve, settle, engage, release) and one audit mutation that grants engage to the runtime role (the start-up query reports it). The alternative is a one-line policy change plus its test; it needs no new review of the SQL.

**6. One grant mechanism.** `migrate()` gets one new keyword, `function_grants: Mapping[str, Sequence[str]] | None` (function signature to the role names that may execute it). `GRANTS` (table grants) is unchanged in kind; there is **no `Grant` kind "function"**: v20's 5.6(o) and 7.1 named it and 5.6c named the keyword, which was two mechanisms. The keyword is applied after the files and after the table grants, **at every `migrate()` call**, in the same transaction, through the one function `apply_function_grants` (prototype in `secdef_audit_v21.py`: per function `REVOKE ALL ... FROM PUBLIC` and from the runtime and operator roles, then `GRANT EXECUTE` to exactly the listed roles, then a re-read of `pg_proc.proacl` that must equal the list, else the transaction fails), and then calls `secdef_problems` in the same transaction so a problem rolls the run back. Role names come from config and are quoted as identifiers, never part of the SQL of a file. The store code (`PostgresStore`) calls the functions with `SELECT * FROM fn(...)` and treats an empty result as a refusal (item 3). **The runtime role's `GRANTS` entries for the three tables become `SELECT` in the same PR (start gate G-5(c)).** The operator read path (how the operator sees the two records) is `limits status` with the audit-reader login; nothing else reads them.

**7. `limits status --check` (readiness major M3 of v20).** Exit **0**: every check passes (or nothing is installed, said in one line). Exit **1**: at least one check fails; one line per check, `PASS name detail` or `FAIL name detail`, no secret and no agent id in a line. Exit **2**: it could not connect or the config is invalid (nothing was checked). Checks and their data:
- the start-up check of item 4;
- **the kill switch is not on for longer than `spend.kill_switch_alert_minutes`** (default 60; my number, no source). **Data:** `kill_switch."on"` and `kill_switch.ts`, read on the runtime connection (it holds `SELECT`, today and after DB-3); the duration is the database clock now minus `ts` while `"on"` is true. **DB-2 is not needed for this check** (the decrease record is not read); with DB-2 and the audit reader, the line also names the login that switched it on (`who` of the newest `kill_switch_log` row). A missing switch row reads as stopped, and the line says `FAIL kill_switch_row_missing`; example line: `FAIL kill_switch_on_too_long on for 75 min since 2026-11-16T10:00:00Z (15:30 IST)`;
- the row counts of the two records against the L13 thresholds (1,000,000 rows or 400 days: `WARN`, exit 0);
- **the kill switch was turned OFF by a login other than the operator role** (DB-2 and audit reader only): `FAIL kill_switch_released_by_other` (this replaces v20's default "alert on decreases not made by `spend_settle`", which could not be built: the decrease record has no column for the function and `who` is `session_user`, so the record cannot tell a settle from a hand-made UPDATE);
- the audit reader cannot write (a negative probe in a rolled-back transaction).

**Who runs it and how an alert reaches a person (OWNER-OPEN L13, no person is named).** The command is a plain scheduled job: its exit code and lines are the alert. Default schedule, so that the 60-minute number means something: **every 10 minutes** (5 to 15 is acceptable; security minor m12). A no-code scheduler (tool ladder rung 3, for example n8n on our own free tier; the client chooses, `client-chooses-tools-policy`) or the operating system's own scheduler runs it and sends a message to the named person when the exit code is not 0; the scheduler only moves the signal, the checks stay in our code. **Until a person and a scheduler are named, nothing runs it: the detection time of a stuck switch is unbounded, and no number is promised.** Test `E0-L13` uses a scratch database in each state and made-up lines only.

**Volume of the decrease record (L24).** Measured on 16.15 (`pg_v21.py`, m5 line): 1000 reserve and settle pairs with actual below the worst case wrote 2000 rows, 270,336 bytes, 135 bytes a row. **So every ordinary settle below its reservation writes two rows once DB-3 is applied: the decrease record is volume, not a tamper signal, and the 1,000,000-row warning is reached by volume alone at a few hundred thousand settles.** **Default (my choice, the lead decides in L24):** keep DB-2 as built; the `WARN` thresholds stay, and the only `FAIL` lines come from the kill-switch records (above), which are few. **Alternative:** DB-2 writes a decrease row only when the new total is lower than the old one and by more than one call cap (a change to DB-2 that needs a new review round and a new hash).

**8. The two designs that are the lead's choice (both OWNER-OPEN; defaults stated; nothing here is decided for the lead).**
- **L26: a dedicated no-login owner role for the DB-3 functions (security major M3 of v20).** *Problem:* every definer function runs with the rights of its owner, today the database owner or the migration role, so a guard bypass runs with the full rights of that role (audit tables, DDL, `DROP`). *Design:* one role `spend_definer` with `NOLOGIN`, owning only the three functions of DB-3 and holding exactly: `SELECT, INSERT, UPDATE` on `spend`, `spend_month` and `kill_switch`; `INSERT` on `spend_decrease_log` and `kill_switch_log` when DB-2 is applied; no `DELETE`, no `TRUNCATE`, no `CREATE`, no membership, no `TEMP`. The migration role creates the functions, then `ALTER FUNCTION ... OWNER TO spend_definer` (the guard refuses `OWNER TO` in a file, so this is a `migrate()` step like the grants, not SQL of the file) and `secdef_problems(owner="spend_definer")` checks it. The DB-2 trigger functions need the same role, with `INSERT` on the two records. *Cost:* a new role, one more migrate step and test (the negative test: the role cannot `DELETE` from `audit_entries`, cannot `DROP`), an `ALTER DEFAULT PRIVILEGES` decision, and one more thing the operator must create (the role needs `CREATEROLE` or the owner to create it). *Not built here:* the role is a text design; the reference tests in `pg_v21.py` run with the migration role as owner and say so. **Default: not built; owner = the database owner as today, and the residual risk is named in section 0 item 9.** Alternative: build it with DB-3. It does not change the file's SQL, so the hash does not change.
- **L26b: the pseudo agent names `-cli` and `-unattributed:<agent>` under DB-3 (security major M1 of v20).** The store books the command line (`-cli`) and unattributed calls (`-unattributed:<agent>`) under names that start with `-`. The DB-3 agent-id rule refuses them (`23514`), so every CLI call that reaches a store would fail closed, and an existing row of that name makes the apply refuse (shown in `pg_v21.py`, section "v21"). **Option A, widen the rule:** `CHECK (agent_id ~ '^(-cli|-unattributed:[A-Za-z0-9][A-Za-z0-9._:@/+-]{0,180}|[A-Za-z0-9][A-Za-z0-9._:@/+-]{0,199})$')`. Cost: the DB-3 file and its hash change again, a new review round on money SQL, a new test for each spelling; the pseudo names then go through the same functions and the same grants; nothing else changes. (This pattern was not run on a server; the plain Python `re` accepts and refuses the cases of the test list.) **Option B (the lead's stated default): the store skips the DB-3 functions for pseudo ids and keeps the statement path of 5.4 item 4 for them.** **Correction, said plainly: that default cannot work as the lead wrote it.** After DB-3 the runtime role holds only `SELECT` on `spend`, and the table rule refuses these names, so "the old path" has nowhere to write. Option B needs a second table `spend_pseudo` (its own `CHECK (usd >= 0)`, the runtime role keeps `INSERT` and `UPDATE` on it) and store code that picks the table by the first character of the id. Cost: a new held file and a new hash, the pseudo-id totals stay lowerable by the runtime login (the exposure DB-3 closes for named agents stays open for them), the daily window sum must add two tables. **Default as the lead stated it: Option B, with the table.** **My recommendation, for the lead to accept or refuse: Option A**, because it keeps one write path and no unprotected totals. Until the lead answers, DB-3 is not applied (it is not applied without L22 anyway), so no CLI call fails today.

**9. Cutover into DB-3 (security minor m6).** The migration runs inside one transaction (`migrate()` uses `db.transaction()` and an advisory lock; checked in `migrate.py`), so `SET LOCAL lock_timeout` and `SET LOCAL statement_timeout` in the file take effect; **a runner that does not wrap each file in a transaction makes them do nothing (shown: the server only prints a notice)**. Procedure: (1) **drain**: stop the runtime or wait until no reservation is open (`open_usd` is 0 for every row); (2) before applying, run `SELECT agent_id FROM spend WHERE agent_id !~ '^[A-Za-z0-9][A-Za-z0-9._:@/+-]{0,199}$'` and the same on `spend_month`, **the day-window query of the file header, and a count of rows named `-cli` or `-unattributed:%`** (L26b); any row listed must be fixed or removed by the owner, otherwise the apply stops with `23514` and **nothing is applied** (shown on a real server, including a `-cli` row); (3) apply; the new column `open_usd` starts at 0, so **a reservation made before the cutover is refused at its settle with `23514` and the total stays as booked (the safe direction)**; with nothing in flight, new reserves and settles work (shown); (4) **rollback:** before the commit, the transaction rolls back by itself on any error; **after the commit there is no down file** and I did not write one: undoing DB-3 means a new reviewed file that drops the four functions and the two columns, stated here because a down file for a money table needs its own review.

**10. Hashes.** Full values of the five held files are in section 8; in this section, short forms always carry the file name: DB-2 `spend_decrease_log.sql` `c0c4913eede84ead...` (unchanged since v19), DB-3 `spend_guarded_writes.sql` `@@DB3_SHORT@@` (changed in v21).
