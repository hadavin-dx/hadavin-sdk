## 1. Words used (each means one thing everywhere)

- **Call**: one `chat(...)` on a model kind. **Attempt**: one request sent to the provider. One call makes one attempt, or up to `max_attempts` when the provider fails and the call is retried (`llm/retry.py:83-108`); the OpenAI-compatible kind can make two such groups inside one call (`llm/openai_compat.py:117-129`).
- **Spend record**: the two existing counters in the store, one per agent per UTC day and one per agent per UTC month (`Store.add_spend`, `store/protocol.py:107`). Nothing here moves money; "booking" means changing these counters. We never pay anything. The provider bills the studio later.
- **Reservation**: before an attempt, the counters are raised by the most that attempt could cost (the **worst case**). If the raised counters would pass a limit, the call is refused and the raise is taken back.
- **Settle**: after an attempt that returned a usable answer, replace the reservation with the real cost the provider reported. **Keep**: leave the reservation as it is (used after a failed attempt, because the provider may have billed it). **Release**: take a reservation back off without an answer. v9 releases only when our own gate refuses; it never releases after a request was sent (section 5.3).
- **Wall**: a limit that stops further calls: the daily budget, the monthly budget, the window end, or the one-call cap.
- **Window end** (`spend.window_end`): the last UTC date on which live model calls are allowed. A call is refused from 00:00 UTC on the next date, which is 05:30 IST that day. The last allowed moment is 23:59:59 UTC, which is 05:29:59 IST the next day.
- **Gate**: code that runs before every attempt and may refuse it. **Scope**: the information "this call belongs to agent X" that the gate needs to reserve against X's budget; calls with no scope get the window check only.
- **The customer demo** is the event the owner is preparing for. **The demo stage** is a core stage name (R449) and is always written in code font as `demo`. v9 never names a stage in a rule, so the stage rename does not touch it.
- **Money type exception.** CLAUDE.md says "money is integers". The money fields that exist today are `Decimal` US dollars: `Reply.cost_usd` and `Verdict.cost_usd` (`models.py:294`, `:305`), `Route` prices (`config.py:57-58`), `Budget` (`registry.py:33-37`), the `spend` and `spend_month` tables (`store/migrations/0001_core.sql:87-92`, `0003_approvals_tick.sql:15-20`) and `runs.cost_usd` (`models.py:98`). **They stay `Decimal` in step 1. This is a named exception to the integer rule, dated 2026-11-16, reason: changing them is a migration plus a rewrite of every reader, and step 1 must not need a migration of money columns. Exit:** the first PR that adds a **new** spend table (L-1, section 5.7) uses whole **nano-dollars** (1 nano-dollar = 0.000000001 US dollar) in `BIGINT`; that default ships with L-1 unless the owner answers D5 differently. No new `Decimal` money column is introduced by v9.

## 3. Extend or replace: evidence (improve-before-replace)

**What exists.** (a) The demo meter (F1, F2): the right protocol, proved by its tests: reserve the worst case before, settle after, keep on failure, refuse leaves nothing booked, cap holds under four racing processes. (b) `k1b/loop.py:115-122` (F3): the worst-case formula for an abandoned call plus a per-invocation budget. (c) The core's own counter `Store.add_spend` with day and month totals and `Limits.blocked` (F4, F5): atomic in Postgres, shared by every process on the same database.

**What each lacks.**
| Piece | Lacks |
|---|---|
| Demo meter | per-attempt reservation (it reserves once per call); a window end; the store (it is a local file, one host); per-agent caps; any use outside the demo (core must not import from `demos/`, and a client hand-over deletes that folder) |
| k1b worst case | it is a copy of the formula, not shared; it prices only a timed-out call |
| `add_spend` and `Limits` | any reservation before a call (the charge happens after the answer, `agent_loop.py:440`, so one call can pass a cap by one call's cost plus its retries); a window end; protection against a negative amount; a clock |

**Verdict: extend, do not replace.** Take the demo meter's **protocol** (not its code) and run it on the existing store: reserve the worst case with `add_spend` (atomic, returns the new totals), refuse and give back if a total would pass its limit, settle with the difference. One shared formula `llm/spend.py:worst_case_usd`/`cost_of` replaces the three copies: `k1b/loop.py` calls it (a test pins equal numbers on the fixture route, E0-S1-4) and the demo can later pin the core commit and drop its copy (promotion table, a follow-up, not in this document). **Why not the file meter:** one host only; the core supports several processes on one database. **Why not a new ledger first:** the lead's smaller first step needs no migration of money columns; a ledger is justified only by the triggers in 5.7.

## 5. Design: the first step (three small PRs, no money-column migration)

Order and size are in section 7. Sizes: S-1 about one builder session of up to 60 minutes, S-2 about two. "S-n" is a PR; "L-n" is a later PR that exists only if its trigger fires.

### 5.1 Settings (S-1)

`Config.spend` (new, `extra="forbid"`), in `config.py` next to the stage table (the model validator at `config.py:349`):
- `window_end: date | Literal["none"] | None = None`. Required (a date) whenever `backends.llm.kind` is not `fake`; `none` is allowed only with `environment == "prod"` and a `window_owner` (a role label such as `studio-owner`, pattern `[a-z][a-z0-9_-]{1,40}`, so an e-mail address or a name with a space is refused). Writing `null`, leaving it out, or any other spelling of the word (`None`, `NONE`) is refused with the message "write the date 2026-12-01 or, in prod only, the word none". YAML reads an unquoted `2026-12-01` as a date and `~`/`null`/empty as null (`config.py:400-415`); both quoted and unquoted dates are accepted (E0-S1-2). The fake kind ignores the whole rule (5.2 says how).
- `max_call_usd: Money | None = None` (one agent's single attempt may reserve at most this; default per agent: its daily budget divided by 4, rounded up to 8 decimal places; one owner for the number, `Limits.call_cap`, 5.4).
- `reserve_margin: Decimal = 3` (minimum 1): multiplies the **input** estimate only. The output part is `max_tokens` times the output price, which anthropic and bedrock cannot exceed (F15). The estimator is a high guess for English and a low guess for text with few characters per token (Chinese, base64), which is why a margin exists; 3 is my choice, not measured (E0-S2-5 measures it on recorded replies, which do not exist: the lead supplies them or the default stays).
- `store_timeout_ms: int = 2000` (100 to 10000, my choice): the bound of 5.5.
- `Route` gets `price_basis: Literal["flat","tiered"] | None = None`, `max_input_tokens: int | None = None`, `self_hosted: bool = False`.

Config checks (all in the one model validator, errors become `ConfigError` through `load_config`, `config.py:451-454`):
1. **Price basis is a required confirmation.** For every route used by a non-fake llm kind, `price_basis` must be written. `tiered` is **refused** in step 1 with "tiered prices are not metered yet: write flat and set max_input_tokens below the vendor's tier threshold". `None` is refused with "read the provider's price page and write flat or tiered". This closes the v8 hole where a person had to notice a tier: the field cannot be left out.
2. **Known-tiered refusal.** `defaults.KNOWN_TIERED_MODEL_PREFIXES` (a dated list; today one entry, the Haiku 5.5 id prefix, threshold 100,000 prompt tokens, from the project rule file of 2026-11-04, **UNVERIFIED here**) makes the validator require `max_input_tokens` at or below the threshold for a flat route whose `model_id` starts with a listed prefix. Gate refusal code `prompt_too_large` when the input estimate exceeds `max_input_tokens`. The list is a safety list, not routing; routes and prices stay in config.
3. **Cached tokens.** No kind sends a cache marker (F15), so a vendor cache read cannot appear through our code; if a vendor caches automatically and reports cached tokens **inside** the input count, we over-book (safe); if it reports them **outside** the input count we under-book (UNVERIFIED, E0-S2-6 lists the four kinds' response fields). A guard test fails if `cache_control`, `cachedContent` or `cache_read` appears in `llm/*.py` until the estimator is extended.
4. **Zero price.** A route with a zero input or output price is refused for a non-fake kind unless `self_hosted: true` with the `openai_compat` kind and an `http` loopback `base_url` (no key). One function `zero_price_allowed(cfg, route)` in `config.py` serves the validator and `k1b/replay.py:85-91` (which refuses a zero price today). Trigger to widen to a private network host: an exact-hostname allowlist `spend.self_hosted_hosts` (a client with a model on another machine).

### 5.2 The window end, per attempt (S-1)

One pure object `SpendWindow(end: date | None, clock)` in `llm/spend.py` with `check()`: it raises `SpendRefused("window_ended")` when `clock().date() > end` (a naive clock raises `ValueError`, a programmer error). `clock` is `models.now` by default (`models.py:19-20`) and `app.build` passes its own `clock` (`app.py:73`) so tests can fix time.

- **Where.** `NetworkLLM._retry(call)` wraps `call` in a closure `attempt()` that runs `window.check()` **before every attempt**, then `call()`. `with_retry` re-raises a `ProviderError` at once (`retry.py:95-96`) and `SpendRefused` is a subclass of `ProviderError` (defined in `llm/protocol.py` beside it), so a refusal is never wrapped and never retried, and no edit to `retry.py` is needed. So a retry loop that crosses the end date at 00:00 UTC stops on the very next attempt (test: fixed clock moves past the end between two attempts).
- **Who passes the window.** `NetworkLLM.__init__(routes, max_attempts, sleep=time.sleep, *, gate: CallGate | None = None)`; each of the four kind `make(settings, deps)` functions passes `gate=deps.gate`; `Deps` gains `gate: Any = None` and `ALLOWED["llm"] = frozenset({"routes", "gate"})`. A `NetworkLLM` built with `gate=None` is refused in every stage by `app.build` and `cli` (a start-up check: `type(llm)` is a `NetworkLLM` subclass and `llm.gate is None` raises `ConfigError("llm kind built without a spend gate")`); direct constructions in tests pass `gate=None` explicitly and are not refused there because they never go through `app.build`.
- **Fake kind (readiness major 1).** The fake kind is a plain class, not a `NetworkLLM` (F16). `app.build` and `cli` call `build_gate(cfg, clock, limits)` (a function in `llm/callgate.py`), which reads **`cfg.backends.llm.kind`**: for `fake` it returns `None` (no window, no reservation); for any other kind it returns a `CallGate`. `Limits` gets `window=None` for the fake kind by the same one function, so `Limits.blocked` never returns `window_ended` for it. Test: a fake-kind config with a past `window_end` still runs; a non-fake config with a past date is refused at the first attempt.
- **Three places, one rule** (D1 of v8, narrowed): (a) the per-attempt check above; (b) `Limits.blocked` returns the reason `window_ended` first, so a run does not even start; (c) the guardrail (5.6). Each place calls the same `SpendWindow.check`.
- **Exposure, stated here (security nit).** The window is judged by the clock of the machine that runs the agent, not by the database. A wrong host clock moves the end by its error. The bound is the provider-side limit (S-3) and the invoice comparison; comparing with the database clock is part of L-1 (5.7), trigger: any observed skew above 60 seconds, or a client that runs agents on machines it does not control.

### 5.3 Reserve before every attempt, settle after (S-2)

**Scope.** `SpendScope(agent_id, max_call_usd, day_factory)` lives in `llm/spend.py`; a `ContextVar` holds it. `Limits.scope(agent_id)` (the one owner of the per-call cap, 5.4) builds it; `Runtime.handle` opens it around the run body. A call with no scope (the CLI `gate`, `replay`, evals, the guardrail) gets the window check only and books nothing; section 6 lists them.

**One call.** `NetworkLLM.chat` (existing, `common.py:208-220`) keeps its name and body, and, when `self.gate` is not `None`, first computes the **worst case** of one attempt: `input = estimate_tokens(system + text of all turns + json of tool specs + json of output schema) * reserve_margin` priced at the input rate, plus `route.max_tokens` priced at the output rate; refuses with `prompt_too_large` if `input` exceeds `max_input_tokens`; stores it in a `ContextVar` `_CALL` (route, worst case, scope); calls `self._chat(...)`; resets the variable in `finally`. The estimate uses the existing function `estimate_tokens` (`llm/common.py:59-62`). Because the variable is read inside `_retry`, which runs on the same thread inside `chat`, no kind's `_chat` changes except the constructor line.

**One attempt** (the closure `attempt` in `NetworkLLM._retry`, signature `def _retry(self, call: Callable[[], Answer]) -> Answer`, unchanged for the kinds). Pseudocode, valid Python in the fence so the snippet check parses it:

```python
def _retry(self, call):
    gate, ctx = self.gate, _CALL.get()
    if gate is None or ctx is None:           # no gate, or called outside chat (a test)
        return with_retry(call, **self._retry_args())
    def attempt():
        gate.window.check()                   # 5.2: raises SpendRefused("window_ended")
        ticket = gate.reserve(ctx)            # None when there is no scope: window check only
        try:
            answer = call()
        except BaseException:
            gate.keep(ticket)                 # the provider may have billed it: stays booked
            raise
        gate.settle(ticket, ctx.route, answer.tokens)
        return answer
    return with_retry(attempt, **self._retry_args())
```
`self._retry_args()` is the existing keyword list of `common.py:233-241` (label, max_attempts, sleep, retryable, detail) moved into a helper so both paths share it. `BaseException` includes `KeyboardInterrupt`: it is kept (fail closed) and re-raised unchanged.

**The gate's three actions** (`llm/callgate.py`, class `CallGate(window, reserver, clock)`; `reserver` is any object with the three `Limits` methods below, so `llm/` imports no store):
1. `reserve(ctx)` -> `Ticket | None`. No scope: return `None`. With a scope: refuse `call_too_large` if `ctx.worst > scope.max_call_usd` (before any write); then `day = clock().date()`, `reserver.reserve(agent, day, ctx.worst)` = `Limits.reserve`, which runs `store.add_spend(agent, day, +worst)`, compares the returned day and month totals with the agent's budget (`daily`, `monthly`) using **`>`** (admit when the total after my own raise is at or below the limit), and on a breach runs `store.add_spend(agent, day, -worst)` to give it back and raises `SpendRefused("daily_budget" | "monthly_budget")`. Any other exception from the store means "could not read or write the spend record": the call is refused with `SpendRefused("limits_unavailable")`; if the give-back fails the amount stays booked (fail closed) and `_LOG.error("spend_giveback_failed")` is written. The `Ticket` carries `agent_id`, `day`, `worst`.
2. `settle(ticket, route, tokens)`: if `ticket` is `None`, nothing. If either token count is `None` (the provider gave no usage): **keep** (the reservation stays; `usage_missing` is logged). Otherwise `actual = cost_of(route, tokens_in, tokens_out)` (the one shared function, also used by `reply()`), and `Limits.settle(ticket, actual)` runs `store.add_spend(agent, ticket.day, actual - worst)` (the **same day as the reservation**, so a call that crosses midnight settles where it reserved). A settle that raises is logged `spend_settle_failed` and **not retried** (see "failed settle" below). The attempt's booked amount is added to `scope.booked` so the runtime does not charge it a second time (5.4).
3. `keep(ticket)`: nothing is written; add `worst` to `scope.kept` (so the run's own cost record includes it, 5.4).

**What each outcome books** (D23 of v8, narrowed so no safety property rests on a vendor fact):
| Outcome of an attempt | Booked | Why |
|---|---|---|
| usable answer with usage | the real cost (`settle`) | normal |
| usable answer without usage | the worst case stays (`keep`) | a missing number must not become a small number |
| any exception after the request started (timeout, connection error, 408, 429, any 5xx, 400 to 404, 422, malformed 200, certificate error, anything else, `KeyboardInterrupt`) | the worst case stays (`keep`) | the provider may have billed it; **v9 releases nothing after a request was sent** |
| our own gate refuses (window, one-call cap, daily or monthly limit, prompt too large, store unreadable) | nothing (the give-back already ran) | no request was sent |

The over-count has a cost: an outage or a wrong key fills the daily limit faster, and the wall (5.4) says so to a person. That is a loud stop, not a silent one. Releasing a definite client error (400, 401, 403, 404, 422) would be correct if the vendors do not bill those; that is **UNVERIFIED per vendor**, so it is a later change with its own evidence (the monthly invoice comparison, 7.3), not a default. Trigger: the invoice sheet shows over-count above the owner's tolerance for two months in a row.

**Reply.** `Reply` gains `booked_usd: Decimal = Decimal(0)` (what the gate put into the spend record for this reply's successful attempts, set by `model_copy(update={...})` in `NetworkLLM.chat` because `Reply` is a pydantic model, not a dataclass, F14). `Verdict` gains `booked_usd` the same way; `JudgeDetector.check` copies `reply.booked_usd` into its verdict and `injection.combine` sums it (`guard/injection.py:77`). For the OpenAI-compatible kind (two request groups in one call) `booked_usd` is the sum of its settles, and `Reply.cost_usd` is priced from the summed tokens (`openai_compat.py:122,131`), which is equal for a flat price (Decimal multiplication distributes exactly at 28 digits; E0-S2-4 tests it). A price tier would make the two differ, which is why `tiered` is refused (5.1).

**Failed settle (security major 2).** A settle is one `add_spend` with a difference; it is **not idempotent** (a retry after an acknowledgement that was lost would book twice), so v9 does not retry it blindly. What a failed settle leaves is the reservation at its worst case: that is at or above the true cost (output is bounded by `max_tokens`, input by the margin), so the total is too high, never too low, **except** when the real cost exceeded the worst case (an estimator miss or a vendor counting hidden tokens, F15). That excess is not booked on a failed settle; it is also not booked today (today the charge happens after the answer and a store failure there loses it entirely). The run's own cost record (`runs.cost_usd`) is written from `reply.cost_usd` by the runtime and does not depend on the settle. **This is the first named gap that could justify L-1:** an idempotent settle needs a reservation id. The trigger is exact: any `spend_settle_failed` log line in a live window, or E0-S2-3 (the crash test) showing a total that cannot be explained. Not deferred silently: it is a stated, tested over-count with a stated trigger.

**Safety on a refused give-back and on contention.** The raise-then-compare design briefly shows other callers an inflated total (they may be refused when the real room is there): a wrong refusal, never a wrong admission. Two callers cannot both be admitted past a limit: each `add_spend` returns a distinct post-update total from one atomic upsert, so if both are admitted the sum of their reservations is at or below the limit. **UNVERIFIED on Postgres**: that `ON CONFLICT DO UPDATE ... RETURNING` returns the value after this transaction's own update under READ COMMITTED with the row lock held (documented Postgres behaviour; not run here). E0-S2-3 runs it with two connections.

### 5.5 The database side (S-2)

1. **Migration `0006_spend_nonneg.sql`**: `ALTER TABLE spend ADD CONSTRAINT spend_usd_nonneg CHECK (usd >= 0); ALTER TABLE spend_month ADD CONSTRAINT spend_month_usd_nonneg CHECK (usd >= 0);`. Class fixed: a total that goes below zero, by a bug or by a writer holding the runtime role, can no longer wipe a limit by driving it negative (security major 1). It does **not** stop a writer from lowering a total to zero (a hostile runtime can still erase its own agent's spend; the bound is S-3). `GRANTS` needs no entry (no new table). The memory store refuses a total below zero with `ValueError` (parity; E0-S2-2). **Before applying it**, the operator runs `SELECT count(*) FROM spend WHERE usd < 0` and the same for `spend_month`; a non-zero count fails the migration, which is the right outcome and is the detection of an earlier wipe. Whether the migration guard accepts the file (F12 says it should) is **UNVERIFIED**: `E0-S2-2` runs `migrate` and the ledger check.
2. **Bound on waiting (security majors 3 and 4).** `PostgresStore.add_spend` and `spend_totals` take the Python lock with `self._lock.acquire(timeout=store_timeout_s)` and raise `StoreUnavailable` on timeout; inside the transaction the first statement is `SELECT set_config('lock_timeout', '<n>ms', true)` (transaction-local), so a row lock held by another session ends the wait with SQLSTATE `55P03`, mapped to `StoreUnavailable`; the gate turns `StoreUnavailable` into `SpendRefused("limits_unavailable")` (a stop, never a pass). So a stall costs a refused call, not a hung process, and **no spend call waits for more than about twice the timeout** (one for the Python lock, one for the database). Other methods of the store keep their existing waits.
3. **No second connection in step 1, and why (stated plainly).** A second connection for spend would stop a spend stall from blocking `Limits.blocked`, the kill switch and approvals on the main connection. Step 1 does not add one because its only spend write is the existing `add_spend` (two upserts, no new lock) and the bound above caps the stall. **Trigger to add it (L-3):** any `55P03` or Python-lock timeout in a live window, or E0-S2-3(d) measuring a spend call over 1 second. That is a measured trigger on a money path, not a hope.
4. **No advisory lock, so no advisory-lock attack.** v8's advisory lock, two triggers and `direct` rows are not in step 1. The attack "any database role calls `pg_advisory_lock` on the key and blocks reserve and settle" therefore does not exist in step 1. What a session of the runtime role **can** do in step 1: hold an open transaction that updates the agent's own day row, blocking that agent's reserve until `lock_timeout`; the bound is the `lock_timeout` above plus `statement_timeout` and `idle_in_transaction_session_timeout` set on the runtime **role** by the operator (`ALTER ROLE ... SET ...`; **UNVERIFIED**, E0-S2-3(f) tests that the setting applies to a new session). A hostile holder is bounded by those role settings and by S-3, not by this code.
5. **Per-agent database roles (v8 D29) cannot work on one connection, and v9 does not ship them.** `PostgresStore` has one connection, so the database sees one `session_user`; a rule "the row's agent must be the session user" would refuse every agent but one. It could work only as **one store (one connection, one lock) per agent role**, each with its own secret name (`store.dsn_secret_name` per agent), which is a different deployment, not a column. v9 drops it from step 1 and from the later PRs unless a client does not trust the agent process (then L-4 is designed against that client's deployment). Consequence, stated: in step 1 one agent's process can raise or lower another agent's counters with the shared role; the controls are the provider-side limit and the invoice comparison.
