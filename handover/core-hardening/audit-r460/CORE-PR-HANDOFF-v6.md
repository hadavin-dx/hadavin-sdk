## 4. Designs

### 4.1 Spend: reserve, settle, release (resolves security B1, M3, M4, M5, M6, M7, M8, nits 12; readiness M1, M2)

**Admission rule (honest bound).** The sum of admitted reservations never exceeds a cap, because the compare and the insert are one store transaction taken under one per-agent lock (below). That is a statement about reserved amounts. The money actually billed can pass a cap by the estimator error: at most the sum, over attempts that were sent, of (booked cost minus reserved amount) where positive; with N attempts in flight at once, N times the per-attempt error. A call already sent cannot be recalled. "Exact cap" and "can never be admitted wrongly" are not claimed.

**What a reservation covers: one attempt, not one call (security B1).** `with_retry` can send up to `max_attempts` requests for one `chat` call (`retry.py:92-107`, default 3, `backends/table.py:40`) and any of them may be billed. v5 held one reservation for the whole call and released it when the last attempt was refused, which could un-book an earlier attempt that had been billed. v6 reserves **before every attempt** and decides what to do with **that attempt's** reservation from what happened to that attempt (outcome table below). The bound "N calls in flight" becomes "N attempts in flight", and a call that retries holds at most `max_attempts` kept reservations (D15 availability bound).

**Store (the choke point), both stores, new migration** `src/hadavin_sdk/store/migrations/0006_spend_op.sql` (name checked against `_FILE`, F21; D5 must be answered first):
```
CREATE TABLE spend_op (
    op_id      TEXT PRIMARY KEY,          -- '<res_id>:reserve' | '<res_id>:final' | 'direct:<id>'
    res_id     TEXT NOT NULL,
    agent_id   TEXT NOT NULL,
    run_id     TEXT,                      -- NULL for eval scopes and direct bookings
    day        DATE NOT NULL,             -- UTC day taken from the reserve op, never from a later caller

    how        TEXT CHECK (how IN ('settle', 'release', 'keep', 'correction')),
    usd        NUMERIC(24,8) NOT NULL CHECK (usd BETWEEN -1000000 AND 1000000),
                                          -- reserve/direct: the amount (>= 0); final: the CHANGE to the day total
    actual_usd NUMERIC(24,8) CHECK (actual_usd BETWEEN 0 AND 1000000),
    ts         TIMESTAMPTZ NOT NULL,
    CHECK ((kind = 'final') = (how IS NOT NULL)),
    CHECK (kind = 'final' OR usd >= 0)
);                                         -- BETWEEN also refuses NaN and infinity (they sort above every number)
CREATE UNIQUE INDEX spend_op_one_reserve ON spend_op (res_id) WHERE kind = 'reserve';
CREATE UNIQUE INDEX spend_op_one_final   ON spend_op (res_id) WHERE kind = 'final';
CREATE INDEX spend_op_by_agent_day ON spend_op (agent_id, day);
CREATE INDEX spend_op_by_run       ON spend_op (run_id) WHERE run_id IS NOT NULL;
CREATE INDEX spend_op_reserves_ts  ON spend_op (ts) WHERE kind = 'reserve';   -- the orphan query
CREATE OR REPLACE FUNCTION spend_op_guard() RETURNS trigger ...   -- BEFORE INSERT, below
CREATE TRIGGER spend_op_guard BEFORE INSERT ON spend_op FOR EACH ROW EXECUTE FUNCTION spend_op_guard();
```
- **Grants** (`store/migrate.py:46-67`, the one map; `check_grants` refuses the migration without it): add `"spend_op": Grant("table", _APPEND)` (that is `SELECT, INSERT`: no UPDATE, no DELETE, readiness M1), and **shrink** `"spend"` and `"spend_month"` to `Grant("table", "SELECT")` (they become frozen history; `_apply_grants` does `REVOKE ALL` then `GRANT`, so the next `migrate --runtime-role` removes UPDATE from an existing runtime role, F21). `spend_op` has no sequence (text key), so no `*_seq_seq` entry. The migration guard reads `CREATE TABLE ... (`, `CREATE [UNIQUE] INDEX`, `CREATE OR REPLACE FUNCTION` and `CREATE TRIGGER` (F21): all four forms above are in its allowed list, **unverified: not run** (E0-1 runs `check_grants` and the ledger check).
- **The trigger** is a plain function (not `SECURITY DEFINER`: it reads `spend_op` with the caller's own SELECT right). For `kind = 'final'` it requires: the matching reserve row exists with the same `agent_id`, `day` and `run_id`; `usd >= -reserved`; `how` in (`release`, `correction`) means `usd = -reserved`; `keep` means `usd = 0`. So even a raw `INSERT` by a compromised runtime cannot lower a total below what that reservation added, and the unique index allows one final per reservation (security M6). It **cannot** force a `settle` to carry a realistic cost: a hostile runtime can write a final that equals a release (booked cost 0). That is the limit and it equals "the runtime can undo its own reservation once", which section 5 states. **Specified, unverified: E0-3 runs it on two database roles.**
- **Totals come from the table, not from counters (security M6).** `spend_totals(agent, day)` = the frozen `spend` / `spend_month` rows (history before 0006) + the sum of `spend_op.usd` for that agent over the day and over the calendar month. No code writes `spend` or `spend_month` after 0006; the old `add_spend` writes a `direct` row instead. The runtime role therefore holds no UPDATE on any total.
- **Serialising reservers without counters:** `reserve_spend` first takes `pg_advisory_xact_lock(hashtextextended(agent_id, 0))` (executable by any role; held to the end of the transaction), so two reservers for one agent queue and each sees the other's row; across agents there is no waiting. One lock covers the day, month and run checks because every run belongs to one agent. **Unverified: E0-3, 8 threads on two connections.** Memory store: the same steps under `self._lock`.

**Store methods** (protocol home `store/protocol.py`; result types `Reserved`, `Finished`, `OpenReservation` as frozen dataclasses next to `Store`; `UnknownReservation(NotFound)` in `errors.py`; both stores):
```
Store.reserve_spend(res_id: str, agent_id: str, run_id: str | None, day: date, usd: Decimal,
                    daily: Decimal, monthly: Decimal, run_cap: Decimal | None) -> Reserved
    Reserved(admitted: bool, which: "daily_budget" | "monthly_budget" | "run_budget" | None,
             day_total: Decimal, month_total: Decimal)
Store.finish_spend(res_id: str, how: "settle" | "release" | "keep" | "correction",
                   booked_usd: Decimal | None) -> Finished
    Finished(applied: bool, day_total: Decimal, month_total: Decimal)
Store.list_open_reservations(older_than: datetime, limit: int) -> list[OpenReservation]
    OpenReservation(res_id, agent_id, run_id, day, usd, ts)
```
- `reserve_spend`: one transaction: take the lock; if `<res_id>:reserve` already exists, **compare** its agent, run, day and amount with the arguments: equal returns the recorded grant (`admitted=True`) and adds nothing; different raises `ValueError("res_id reused with different values")` (security M8, the repeated-id test); compute the day, month and run totals (the run total is `SUM(spend_op.usd) WHERE run_id = ?`, **so it counts this run's open reservations and its settled calls together**, security M4); refuse in this order: `daily_budget` if day total + `usd` is greater than `daily`, then `monthly_budget`, then `run_budget` if `run_cap` is given and run total + `usd` is greater than it; **only if admitted** insert `<res_id>:reserve`. A refusal writes nothing, so there is no briefly visible refused amount and no undo step. A zero `usd` never trips a zero cap (`0 > 0` is false), so zero-price fake routes keep working. The comparison is `>` (would exceed); `Limits.blocked` keeps `>=` (already at the cap); both are pinned by a test side by side.
- `finish_spend`: one transaction: read the recorded reserve (unknown id raises `UnknownReservation`; the reserved amount, agent, run and day come from that row, never from the caller); insert `<res_id>:final` (the unique index makes a second one a no-op returning `applied=False`, and `applied=False` returns the current totals). Day-total change: `settle` = `booked_usd` minus reserved; `release` = minus reserved; `keep` = 0; `correction` = minus reserved. **In the same transaction** it adds to `runs.cost_usd` (`UPDATE runs SET cost_usd = cost_usd + ? WHERE run_id = ?`, the runtime already holds UPDATE on `runs`, `migrate.py:47`): `settle` the booked amount, `keep` the reserved amount, `release` and `correction` nothing. A missing run row raises and rolls the whole finish back (the reservation then stays open and counted). So a crash can no longer leave the run's cost row low while the day total is right (security M3); the per-run cap itself reads `spend_op`, not `runs.cost_usd`, so editing the `runs` row cannot lower the cap's view (it is a display copy, kept in step).
- `list_open_reservations`: reserves older than `older_than` with no final: `WHERE kind='reserve' AND ts < ? AND NOT EXISTS (final with the same res_id)`, oldest first, at most `limit`.
- `add_spend(agent, day, usd)` stays (the operator `Limits.charge` and tests use it) but writes a `direct` row (`op_id = 'direct:' + new id`, non-negative only) and returns the totals.
- **Validation at the choke point (security B1 of v4, nit):** one helper `spend_amount(usd) -> Decimal` in new `store/amounts.py`, called first by every method above, in both stores: it calls `usd.is_finite()` **before any comparison** (a signalling NaN raises on `<`, so the order matters; E0-3 fuzzes sNaN), refuses negative, refuses above `defaults.MAX_SPEND_OP_USD`, and rounds **up** to 8 places (`ROUND_CEILING`; under D5 integers: to nano-dollars). Violations raise `ValueError` before any write. `MAX_SPEND_OP_USD` is a new constant, **1,000,000 USD, chosen by me as a sanity ceiling** (far above one call; it exists only so an arithmetic bug cannot write `1e30`); the table's `CHECK` repeats the number and a test pins the two equal. `Money` (`config.py:41-47`) rejects NaN, infinity and negative at the type (covers `Route` prices, `Budget`, `max_run_usd`); `Budget` refuses `daily > monthly` (E0-7 greps configs); `Reply.cost_usd` gets `Field(ge=0, allow_inf_nan=False)` (`models.py:294`), `Verdict.cost_usd` the same (`:305`).
- `day` is chosen where the reservation is made: `SpendMeter` uses `clock().astimezone(UTC).date()`; a clock that returns a naive time raises at construction (test). Month and day rollover between reserve and finish is correct by construction because finish takes the day from the reserve row (test: reserve at 23:59:59 UTC, finish after midnight, the reserved day's total changes).

**`SpendMeter` (`limits.py`; needs only a store and a clock, so the CLI can build it without a registry or audit sink):**
```
SpendMeter(store, clock=models.now, spend: SpendSettings, max_call_usd: Decimal)
  .gate          -> CallGate (4.2), built from spend.window_end, reserve_margin, max_call_usd and clock
  .scope(key, daily, monthly, *, run_id=None, run_cap=None) -> context manager   # sets the active SpendScope
  .reserve(scope, usd, floor_usd, res_id) -> Reservation(res_id, key, day, usd, floor_usd, run_id)  # raises SpendRefused
  .settle(res, reply) / .release(res) / .keep(res)                     # never raise
```
`SpendRefused` and `ProviderRefused`'s replacement (a kind hook, below) live in `llm/protocol.py`: `SpendRefused(Exception)` with `.code` in {`kill_switch`, `window_ended`, `daily_budget`, `monthly_budget`, `run_budget`, `call_too_large`, `unmetered`, `meter_unavailable`}. It is **not** a subclass of `ProviderError`, so `agent_loop`'s `except ProviderError` (`:431`) does not swallow it.
`reserve` steps in order: (1) kill switch on (store read; a store error is `meter_unavailable`) -> `kill_switch`; (2) `gate.check_window()` -> `window_ended`; (3) `usd` above `max_call_usd` -> `call_too_large` (D19); (4) `store.reserve_spend(...)` with `res_id`, the scope's agent, run and caps; not admitted -> the `which` code. The per-run cap is checked **inside the store transaction** (step 4), not before it.
`res_id` is built by the caller of the attempt as `models.new_id("res")` for the call plus `":" + attempt number` (a fresh random 128-bit id per call, so two calls cannot collide; a repeated id with different values is refused by the store).

**Booking rule for one attempt (this replaces v5's per-call table):**
| What happened to the attempt | Booking | Why |
|---|---|---|
| a usable answer (parsed, priced) | `settle` (rule below) | normal; includes a reply that later fails the caller's own checks |
| a **definite client error**: HTTP 400, 401, 403, 404 or 422 (a kind hook `refused(exc)`, below) | `release` | the provider refused before generating |
| anything else: timeout, connection error, 408, 429, any 5xx, an unparseable 200 (F6), a certificate error, any other `Exception`, `KeyboardInterrupt` or another non-`Exception` exit | `keep` (one worst case stays booked) | the attempt may have been billed (D23); a missing status is also `keep` |
| the gate refuses the **next** attempt (window, daily, monthly, run cap, call too large) | no new reservation; **earlier attempts of this call keep what they were booked as** | the refused attempt sent nothing; earlier ones are not touched (security B1 test) |
| the process dies or the store write fails | the reservation stays open and counted | fail closed; the orphan view lists it |
**The status hook (security uncertainty 1, lock-in watch point):** `NetworkLLM` gets `refused: Callable[[BaseException], bool | None] | None = None`, the same shape as `retryable` (`common.py:244`). The generic rule is `retry.status(exc)` in {400, 401, 403, 404, 422}. `llm/bedrock.py` sets its own hook that reads `response["ResponseMetadata"]["HTTPStatusCode"]` (the place `detail()` already reads, `bedrock.py:93-101`) because `retry.status()` does not see it. A hook that returns `None` or an exception with no status gives "not refused", so the attempt is `keep` (over-counts, never under-counts). This replaces v5's new `ProviderRefused` class: no change to `with_retry`'s classification is needed, only the `SpendRefused` pass-through in 4.2.

**`settle` (security M5):** `settle(res, reply)` computes the booked cost from the reply:
1. `reply.cost_usd` is finite and not negative (the `Reply` field now guarantees it; if it is not, book as `keep` and log `spend_bad_cost`).
2. **Floor:** on a non-fake route the floor is `res.floor_usd` = (input tokens estimated by `estimate_tokens` of what was sent) x input price / 1,000,000; the booked cost is `max(reply.cost_usd, floor_usd)`. A reply that reports a cost of 0 while it carries text or tool calls on a priced route is booked as `keep` (the whole reserve) and logged `spend_cost_missing`. (A fake-kind call has `floor_usd = 0`: its recorded token counts are exact for the test, `fake.py:50-53`.)
3. **Cap:** a booked cost above `MAX_SPEND_OP_USD` is booked **as** `MAX_SPEND_OP_USD` and logged `spend_actual_capped`; `settle` never raises (v5 said "never raise" but the amount check could; now the check is a clamp).
4. If the booked cost is larger than the reserve, the extra is booked and `spend_overrun` is logged. It never refuses after the provider billed.
`settle`, `release`, `keep` call `finish_spend`; `finish_spend` writes the run cost itself (above), so there is no separate `add_cost`. If the store raises (`StoreUnavailable`, `NotFound` for the run), they catch it, log `spend_finish_failed` (class name only), and leave the reservation open and counted. The caught exceptions are exactly `StoreUnavailable`, `NotFound`, `UnknownReservation` and `ValueError` (a bad amount); anything else propagates, so "never raise" in this document means "never raises these four" and the list is in the code and its test (security nit 10).

**Worst case, full input.** New `llm/common.py:reserve_estimate(route, system, messages, documents, specs, output_schema, margin) -> Estimate(reserve_usd, floor_usd)` (named so it does not share a name with `k1b/loop.py:115`; the import direction is `llm` never imports `k1b`, readiness N2). Input tokens are estimated over `system` + the JSON of `messages` + the JSON of the tool list as the kind sends it (`tools_for`, `common.py:65-83`, which also turns `output_schema` into the forced answer tool) + each document decoded the way `turns` does (`common.py:86-100`; the `decode("utf-8", "replace")` is at line 92), at `estimate_tokens` (3 characters per token). `floor_usd` = those input tokens x input price / 1,000,000. `reserve_usd` = ((input tokens x `margin`) x input price + `route.max_tokens` x output price) / 1,000,000. The margin applies to the input part only (D20; F19: no thinking budget, no cache write, so the output is bounded by `max_tokens`). The estimator is not defined for PDF or image bytes (`extract` refuses them, D22; the runtime sends text only). `k1b/loop.py:115-124` keeps its own function, unchanged (D25).

**Orphan view and correction (security M8, readiness M7).** `Limits.orphans(older_than)` (read, calls `list_open_reservations`) feeds `hadavin-sdk limits orphans` (4.3); the tick logs a warning when any is older than `spend.orphan_alert_after_s` (default `defaults.SPEND_ORPHAN_ALERT_AFTER_S` = 3600 seconds; reason: the socket timeout is 60 s per operation and 3 attempts, `backends/table.py:34-40`, so an hour is well above any real call; the lead may change it). `Limits.correct(res_id, by, reason)` mirrors `Limits.reset` (`limits.py:48-51`): `audit.write_intent(...)` first (if the audit write fails, nothing changes), then `finish_spend(res_id, "correction", None)`. **Bulk relief** is the CLI `limits correct --older-than SECONDS` (4.3): it lists the matching reservations, prints the count and total, and corrects them one by one, each with its own audit intent row, after an explicit `--yes`. **What this does not enforce:** database grants cannot separate values inside one table, so a compromised runtime could call the same store method; the trigger above limits it to undoing the amount that one reservation added, once. What bounds it further: a census test allows `correction` only in `cli.py` and `limits.py`, and the CLI branch builds its own store connection (`cli.py:183-190`), so an operator can run it under a different database role. If the owner wants grants to enforce it, the option is a separate `spend_correction` table with INSERT only for that role and totals computed as spend minus corrections; trigger: first pilot config.

**Retention and cost of the table (nit 12, D24):** 2 rows per attempt; the indexes above cover the day sum, the run sum and the orphan query; no deletion; rollup trigger in D24.

### 4.7 `extract()` masking and restore (resolves v4 security B-4, B-5, M-7 to M-9, N-2; v5 security major 9)

The placeholder-to-original map is **not a public field**.
