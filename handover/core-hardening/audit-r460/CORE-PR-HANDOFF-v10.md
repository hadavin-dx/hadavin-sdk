## 1. Words used (each means one thing everywhere)

- **Call**: one `chat(...)` on a model kind. **Attempt**: one request sent to the provider. One call makes one attempt, or up to `max_attempts` when the provider fails and the call is retried (`llm/retry.py:83-108`); the OpenAI-compatible kind can make two such groups inside one call (`llm/openai_compat.py:117-129`).
- **Spend record**: the two existing counters in the store, one per agent per UTC day and one per agent per UTC month (`Store.add_spend`, `store/protocol.py:107`). Nothing here moves money; "booking" means changing these counters. We never pay anything. The provider bills the studio later.
- **Reservation**: before an attempt, the counters are raised by the most that attempt could cost (the **worst case**). If the raised counters would pass a limit, the call is refused and the raise is taken back.
- **Settle**: after an attempt that returned a usable answer, replace the reservation with the real cost the provider reported. **Keep**: leave the reservation as it is (used after a failed attempt, because the provider may have billed it). **Release**: take a reservation back off without an answer. v9 releases only when our own gate refuses; it never releases after a request was sent (section 5.3).
- **Wall**: a limit that stops further calls: the daily budget, the monthly budget, the window end, or the one-call cap.
- **Window end** (`spend.window_end`): the last UTC date on which live model calls are allowed. A call is refused from 00:00 UTC on the next date, which is 05:30 IST that day. The last allowed moment is 23:59:59 UTC, which is 05:29:59 IST the next day.
- **Gate**: code that runs before every attempt and may refuse it. **Scope**: the information "this call belongs to agent X, with these limits" that the gate needs to reserve against X's budget. In v10 a paid call with **no scope is refused** (`scope_missing`), never let through unmetered; command-line paths get a scope from a cap the person types (`--max-usd`), section 5.8. A **paid kind** is a configured backend that sends text to a priced service (section 5.1).
- **The customer demo** is the event the owner is preparing for. **The demo stage** is a core stage name (R449) and is always written in code font as `demo`. v9 never names a stage in a rule, so the stage rename does not touch it.
- **Money type exception.** CLAUDE.md says "money is integers". The money fields that exist today are `Decimal` US dollars: `Reply.cost_usd` and `Verdict.cost_usd` (`models.py:294`, `:305`), `Route` prices (`config.py:57-58`), `Budget` (`registry.py:33-36`), the `spend` and `spend_month` tables (`store/migrations/0001_core.sql:87-92`, `0003_approvals_tick.sql:15-20`) and `runs.cost_usd` (`models.py:98`). **They stay `Decimal` in step 1. This is a named exception to the integer rule, dated 2026-11-16, owner: the studio owner through the lead (question D5), review by 2026-12-31, reason: changing them is a migration plus a rewrite of every reader, and step 1 must not need a migration of money columns. Exit:** the first PR that adds a **new** spend table (L-1, section 5.10) uses whole **nano-dollars** (1 nano-dollar = 0.000000001 US dollar) in `BIGINT`; that default ships with L-1 unless the owner answers D5 differently. No new `Decimal` money column is introduced by v9.

## 3. Extend or replace: evidence (improve-before-replace)

**What exists.** (a) The demo meter (F1, F2): the right protocol, proved by its tests: reserve the worst case before, settle after, keep on failure, refuse leaves nothing booked, cap holds under four racing processes. (b) `k1b/loop.py:115-122` (F3): the worst-case formula for an abandoned call plus a per-invocation budget. (c) The core's own counter `Store.add_spend` with day and month totals and `Limits.blocked` (F4, F5): atomic in Postgres, shared by every process on the same database.

**What each lacks.**
| Piece | Lacks |
|---|---|
| Demo meter | per-attempt reservation (it reserves once per call); a window end; the store (it is a local file, one host); per-agent caps; any use outside the demo (core must not import from `demos/`, and a client hand-over deletes that folder) |
| k1b worst case | it is a copy of the formula, not shared; it prices only a timed-out call |
| `add_spend` and `Limits` | any reservation before a call (the charge happens after the answer, `agent_loop.py:440`, so one call can pass a cap by one call's cost plus its retries); a window end; protection against a negative amount; a clock |

**Verdict: extend, do not replace.** Take the demo meter's **protocol** (not its code) and run it on the existing store: reserve the worst case with `add_spend` (atomic, returns the new totals), refuse and give back if a total would pass its limit, settle with the difference. One shared formula `llm/spend.py:worst_case_usd`/`cost_of` replaces the three copies: `k1b/loop.py` calls it (a test pins equal numbers on the fixture route, E0-S1-4) and the demo can later pin the core commit and drop its copy (promotion table, a follow-up, not in this document). **Why not the file meter:** one host only; the core supports several processes on one database. **Why not a new ledger first:** the lead's smaller first step needs no migration of money columns; a ledger is justified only by the triggers in 5.10.

### 5.1 Settings (S-1)

`Config.spend` (new, `extra="forbid"`, default `SpendSettings()` through `Field(default_factory=...)`, so every existing config without the block still loads), in `config.py` beside the stage table (the model validator at `config.py:349`). A **paid kind** is any configured backend that sends text to a priced service: `backends.llm.kind` other than `fake`, or a detector kind listed in the new `defaults.PAID_DETECTOR_KINDS` (today one entry, the Bedrock guardrail kind). The window rule below follows **paid kinds**, not only the llm kind (security major 7).
- `window_end: date | Literal["none"] | None = None`. Required (a date) whenever any paid kind is configured; `none` only with `environment == "prod"` and a `window_owner` (role label, pattern `[a-z][a-z0-9_-]{1,40}`). `null`, a missing key, `None`, `NONE` are refused with "write the date 2026-12-01 or, in prod only, the word none". A **date and time** (YAML `2026-12-01 10:00`) is refused with "write a date only"; an unquoted or quoted date is accepted (YAML reads an unquoted date as a date and `~`/`null`/empty as null, `config.py:400-415`; E0-S1-2). With no paid kind (all fake) the whole rule is ignored.
- `max_call_usd: Money | None = None` and the per-call cap rule: `Limits.call_cap(agent_id)` returns `max_call_usd` if set, else the agent's daily budget divided by 4 and **rounded up** to 8 decimal places (`Decimal.quantize(Decimal("1E-8"), rounding=ROUND_UP)`). One owner of the number (5.5).
- `reserve_margin: Decimal = 3` (minimum 1): multiplies the **input** estimate only. The output part is `route.max_tokens` times the output price. The estimator (`llm/common.py:59-62`, `len(text)//3`) is a high guess for English and a low guess for text with few characters per token (Chinese, base64). 3 is my choice, **not measured** (5.9 item 3). Measuring it needs a real tokenizer count on real text, which only the lead can supply (L2); until then the default stays and the document says "unmeasured".
- `guardrail_usd_per_call: Money | None` (required and greater than 0 when a detector of a paid detector kind is configured outside the fake setup; the operator writes the price from the vendor's price page that day, the code holds no vendor price), `unattributed_daily_usd: Money | None`, `unattributed_monthly_usd: Money | None` (both required with a paid detector kind: the approval summary screen has no agent to charge, `app.py:157-159`; its guardrail calls are charged to the pseudo agent `-unattributed`, section 5.7).
- `Route` (`config.py:55-59`) changes: `input_usd_per_mtok` and `output_usd_per_mtok` become `Money` with `ge=0` **and finite** (the shared `_money` at `config.py:40-44` is extended to refuse `NaN` and `Infinity`, which it accepts today because it rejects floats only); new `price_basis: Literal["flat","tiered"] | None = None`, `max_input_tokens: int | None = Field(default=None, gt=0)`, `self_hosted: bool = False`. `Budget` (`registry.py:33-36`) `daily` and `monthly` get the same `ge=0` finite rule (same `Money` fix).

Config checks (all in the one model validator; errors become `ConfigError` through `load_config`, `config.py:451-454`):
1. **Price basis is a required confirmation** for every route used by a paid llm kind: `None` refused ("read the provider's price page and write flat or tiered"); `tiered` refused in step 1 ("tiered prices are not metered yet: write flat and set max_input_tokens below the vendor's tier threshold").
2. **Known-tiered refusal.** `defaults.KNOWN_TIERED_MODEL_PREFIXES` (dated list; today the Haiku 5.5 id prefix, threshold 100,000 prompt tokens, from the project rule file of 2026-11-04, **UNVERIFIED here**) requires `max_input_tokens` at or below the threshold. Gate refusal code `prompt_too_large` when the input estimate exceeds `max_input_tokens`.
3. **Cached tokens.** No kind sends a cache marker (F15). A guard test fails if `cache_control`, `cachedContent` or `cache_read` appears in `llm/*.py` until the estimator is extended. ### 5.2 The window end (S-1)

One pure object `SpendWindow(end: date, clock)` in `llm/spend.py`; `check()` raises `SpendRefused("window_ended")` when `clock().astimezone(UTC).date() > end`. A naive clock raises `ValueError` (programmer error); an aware clock in another zone is **converted to UTC first** (a +05:30 clock would otherwise move the end by up to 5.5 hours; security minor 1; test with an IST clock at 23:00 UTC on the end date). `clock` is `models.now` (`models.py:19-20`, returns UTC) by default; `app.build` passes its own `clock` (`app.py:73`).

- **Who builds it: one function.** `build_window(cfg, clock) -> SpendWindow | None` in `llm/callgate.py`: returns `None` when no paid kind is configured (all fake); otherwise a window (for `window_end: none` a window that never ends, `end=None`). The same object goes to `Limits(window=...)` and to the gate and the guardrail, so there is **one rule in three places** (per-attempt check, `Limits.blocked`, the guardrail).
- **Where.** `NetworkLLM._retry` runs the gate's `admit` before every attempt (5.3). `SpendRefused` is a subclass of `ProviderError` (defined in `llm/protocol.py`), and `with_retry` re-raises a `ProviderError` at once (`retry.py:95-96`), so a refusal is never wrapped or retried and `retry.py` does not change. A retry loop that crosses 00:00 UTC stops on the next attempt.
- **Fake kind decision (readiness blocker 1 and security major 7).** The fake kind (`FakeLLM`, `llm/fake.py:21`) is a plain class, not a `NetworkLLM`, has no gate and no reservation, and is refused outside the `demo` stage (`DEV_ONLY`, `backends/table.py:593-602`, `config.py:366-369`). **The guardrail is independent of the llm kind**: with `llm.kind: fake` and a guardrail detector configured, `build_window` still returns a window and the detector checks it before `apply_guardrail`. Test: fake llm + guardrail + a past date → the guardrail refuses and no `apply_guardrail` request is made.
- **Exposure.** The window is judged by the clock of the machine that runs the agent, not the database. Bound: S-3 and the invoice comparison; database time comparison is L-1 (trigger: skew above 60 seconds, or machines the studio does not control). **Overshoot after the end, named (security major 6):** a request admitted at 23:59:59 UTC is billed after midnight; the bound is one request per attempt in flight at that moment, per process (each priced at most its worst case), and the retry sleep (at most 8 seconds, `retry.py:12`) cannot add an attempt because the next attempt checks the window.

```python
def _retry(self, call):
    gate = self.gate
    if gate is None:                              # fake-like or a directly built test kind
        return with_retry(call, **self._retry_args())
    ctx = _CALL.get()
    if ctx is None:                               # a paid request outside chat(): fail closed
        raise SpendRefused("call_context_missing")
    def attempt():
        ticket = gate.admit(ctx)                  # window, abandoned, kill switch, scope, reserve
        try:
            answer = call()
        except BaseException:
            gate.keep(ticket)                     # the provider may have billed it: stays booked
            raise
        ctx.booked += gate.settle(ticket, ctx.route, answer.tokens)   # never raises
        return answer
    return with_retry(attempt, **self._retry_args())
```

`answer.tokens` is `tuple[int | None, int | None]` (`Answer.tokens`, `common.py:194-196`: input count, output count), fixed here as the only shape `settle` accepts (readiness major 6). `BaseException` includes `KeyboardInterrupt`: kept, then re-raised unchanged.

**The gate's actions** (`llm/callgate.py`):
1. `admit(ctx) -> Ticket | None`, in this order, all before any request: (a) `window.check()`; (b) `if _ABANDONED.get()` is set → `SpendRefused("abandoned")` (5.8); (c) no reserver → return `None` (S-1); (d) `scope = _SCOPE.get() or default_scope`; none → `SpendRefused("scope_missing")` (**fail closed**: security major 5; a thread started without the context, a command-line path with no cap, a library caller with no scope all stop with a loud code instead of spending unmetered); (e) `ctx.worst > scope.max_call` → `call_too_large` (before any write); (f) `reserver.reserve(scope, day, ctx.worst)` with `day = clock().astimezone(UTC).date()`.
2. `Limits.reserve(scope, day, worst) -> Ticket`: reads the kill switch (`store.get_kill_switch`, security minor 3: a switch set during a run now stops the next attempt) and raises `SpendRefused("kill_switch")` if on; runs `store.add_spend(agent, day, +worst)` (which returns the new day and month totals); **refuses when a new total is at or above its limit (`>=`, the same comparison as `Limits.blocked`, `limits.py:26,28`; security minor 2: v9 admitted a total exactly at the limit with `>`, which `blocked` would then refuse on the next call)**, after giving the amount back with `add_spend(agent, day, -worst)` and raising `daily_budget` or `monthly_budget`. Any other exception from the store (including `StoreUnavailable`) means the spend record could not be read or written: `SpendRefused("limits_unavailable")`; if the give-back itself fails the amount **stays booked** (fail closed) and `_LOG.error("spend_giveback_failed")` is written. A reserve whose acknowledgement is lost after the database committed leaves the amount booked and the call refused: a safe over-count (security minor 7), stated here and tested (E0-S2-4).
3. `CallGate.settle(ticket, route, tokens) -> Decimal` **never raises** and returns the amount the spend record now holds for this attempt (security major 3). Body: `ticket is None` → 0. `tokens = spend.clean_tokens(tokens, limit)`: each count must be an `int` (not `bool`) with `0 < n <= limit` (`limit` = `route.max_input_tokens`, or `defaults.MAX_PLAUSIBLE_TOKENS` when the route has none, for output `route.max_tokens` times 4 as the plausibility bound); anything else (None, zero, negative, a float, a huge number) means **keep**: `usage_missing` is logged and the worst case stays booked (security majors 1 and 2: zero or negative usage must never become a small number). Otherwise `actual = max(cost_of(route, n_in, n_out), 0)` and `reserver.settle(ticket, actual)` runs `store.add_spend(agent, ticket.day, actual - worst)` (the same day as the reservation). **The whole body sits in `try/except Exception`**: on any failure it logs `spend_settle_failed` (class name only), does **not retry** (a retry after a lost acknowledgement would book twice), and returns `worst` (the reservation stays). Because `settle` never raises, a failed settle can no longer be classed transient by `with_retry` (an `OSError` is, `retry.py:63`) and **can no longer cause a second paid request** (the v9 flaw), and a paid answer is never thrown away because the spend store failed.
4. `keep(ticket)`: writes nothing; adds `worst` to `scope.kept` (the run's own cost record includes it, 5.5).

**What each outcome books:**
| Outcome of an attempt | Booked | Why |
|---|---|---|
| usable answer with sound usage numbers | the real cost (`settle`, never below zero) | normal |
| usable answer with missing, zero, negative, non-integer or implausible usage | the worst case stays (`keep`) | a missing number must not become a small number |
| a failed settle (store error) | the worst case stays; answer returned; one log line | no second request, no lost answer |
| any exception after the request started (timeout, connection error, 408, 429, 5xx, 400 to 404, 422, malformed 200, certificate error, anything else, `KeyboardInterrupt`) | the worst case stays (`keep`) | the provider may have billed it; **v10 releases nothing after a request was sent** |
| our own gate refuses (window, abandoned, kill switch, scope missing, one-call cap, daily or monthly limit, prompt too large, store unreadable) | nothing (the give-back already ran) | no request was sent |

An outage or a wrong key fills the daily limit faster; that is a loud stop (5.5). Releasing a definite client error (400, 401, 403, 404, 422) is L-6 (invoice evidence).

**Reply and verdict.** `Reply` gains `booked_usd: Decimal = Decimal(0)` (set by `model_copy(update=...)` in `NetworkLLM.chat`: `Reply` is a pydantic `Shape`, not frozen, `models.py:289-297`); `Verdict` gains `booked_usd` the same way; `JudgeDetector.check` copies `reply.booked_usd`; `injection.combine` sums it beside `cost_usd` (`injection.py:77`). `reply()` (`common.py:164-172`) and the gate use the **one** `clean_tokens` and `cost_of` (security major 1: today `tokens[0] or estimate` lets a negative count through to a negative `Reply.cost_usd`). For the OpenAI-compatible kind `booked_usd` is the sum of its settles and `Reply.cost_usd` is priced from the summed tokens; equal for a flat price (E0-S2-4).

### 5.4 Numbers that could lower a total: refused at the choke point (S-2a)

Class: **a value that is negative, zero where a count is meant, not finite, or implausible reaches a money total.** The choke points are `Store.add_spend` (all writers) and `Limits.charge`/`settle` (our writers). Fixes, each with a hostile-input test:
1. Prices and budgets: `ge=0` and finite (5.1).
2. Token counts: `clean_tokens` (5.3 item 3); `reply()` uses it, so a negative count no longer prices negative.
3. `Limits.charge(agent_id, usd, booked=Decimal(0))` adds `max(usd - booked, 0)` and refuses a non-finite `usd` or `booked` with `ValueError`; a negative `usd` is clamped to 0 (a negative reply cost from a buggy kind no longer lowers the total).
4. **Both stores, same rule** (`store/postgres.py:416-431`, `store/memory.py:196-204`): `add_spend` first refuses a non-finite `usd` (`ValueError`), and refuses any change that would leave a day or month total **below zero**: Postgres checks the two values returned by the upserts inside the same transaction and raises, which rolls both back (psycopg's `transaction()` context rolls back on an exception); the memory store computes before it commits. This is the code-level refusal that stands in for the database `CHECK` (5.6). It does not stop a writer that bypasses our code.
5. Excess over the worst case: `settle` books the real cost even when it is above the reservation (real money was spent; the counters should show it). A reported cost that is huge but passes `clean_tokens` is bounded by the plausibility limits, and booking it errs on the side of a stop, never a pass.

### 5.6 The database side

1. **No migration in S-2a or S-2b** (the brief's order). Section 0 item 1 explains the conflict. **DB-1 (stand-alone, unscheduled, nothing depends on it; needs the lead's confirmation of the conflicting answers, then the owner's yes before it is applied):** migration `0006_spend_nonneg.sql`: `ALTER TABLE spend ADD CONSTRAINT spend_usd_ok CHECK (usd >= 0 AND usd < 'Infinity'::numeric)` and the same for `spend_month`. In Postgres a `NaN` sorts above `Infinity`, so `usd < 'Infinity'` also excludes `NaN` (UNVERIFIED here; E0-DB-1 tests `NaN`, `Infinity`, `-Infinity`, `-0.01` each refused with `23514`). v9's `CHECK (usd >= 0)` alone would have let `NaN` through (security major 1). `GRANTS` needs no entry (`store/migrate.py:46-67`; the migration guard flags `ALTER TABLE ... SERIAL`, `AS IDENTITY` and `CREATE SEQUENCE` only, `migrate.py:87-90`; UNVERIFIED that it accepts the file). **Repair path for the pre-flight** (security major 9: v9 said a non-zero count "fails the migration" and gave no way forward): the operator, under the migration role, runs `SELECT agent_id, day, usd FROM spend WHERE usd < 0 OR usd = 'NaN'` (and `spend_month`), saves the rows to the evidence folder, **then** corrects them with one reviewed `UPDATE` to the correct total taken from the invoice comparison or to 0 and writes an audit note; only then the migration runs. DB-1 ships with its own negative test (the runtime role's insert of a negative total fails) and an over-breadth line.
2. **Bound on waiting (security major 4; the v9 claim "no spend call waits more than about twice the timeout" was false).** Facts: one connection behind one Python lock (`postgres.py:192-197`); `connect` sets only `connect_timeout=10` (`postgres.py:146` area, `connect()` in `store/postgres.py`); a row lock held by another session is bounded by `lock_timeout` only if set; a stalled network socket is not bounded by any database setting. S-2b: `PostgresStore.add_spend` and `spend_totals` take the Python lock with `acquire(timeout=T)` (T = new postgres kind setting `statement_timeout_ms`, default 2000, range 100 to 10000, my choice, in the kind's own settings class), and inside the transaction the first statement is `SELECT set_config('lock_timeout', 'Tms', true), set_config('statement_timeout', 'Tms', true)` (transaction-local); `connect()` passes libpq `tcp_user_timeout=T` so a dead socket ends in about T (libpq parameter, **UNVERIFIED here**, E0-S2-3(g)). Mapping: `55P03`, `57014` (statement timeout), Python-lock timeout and a socket error become `StoreUnavailable`; the gate turns it into `limits_unavailable`. **The true bound, stated:** one `add_spend` waits at most T for the Python lock plus about 3T inside (two upserts and the commit), so **about 4T**; a refused reserve (reserve then give-back) about **8T**: with the default, 8 seconds and 16 seconds. Other store methods (`Limits.blocked`, the kill switch read, approvals) still queue behind a spend call on the same lock, each for at most the holder's 3T, so with k spend calls queued the wait is up to 3kT. Under **B** the new modules `llm.spend` and `llm.callgate` sit inside the package `llm`, whose `__init__` imports `llm.fake` and `llm.protocol` (`llm/__init__.py`), and `llm.common` is already in a cycle with them today; so under B they **join that existing cycle through the package, not through any new edge between modules**.
