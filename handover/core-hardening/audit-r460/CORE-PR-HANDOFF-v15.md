## 1. Words used (each means one thing everywhere)

- **Call**: one `chat(...)` on a model kind. **Attempt**: one request sent to the provider. One call makes one attempt, or up to `max_attempts` when the provider fails and the call is retried (`llm/retry.py:83-108`); the OpenAI-compatible kind can make two such groups inside one call (`llm/openai_compat.py:117-129`).
- **Spend record**: the two existing counters in the store, one per agent per UTC day and one per agent per UTC month (`Store.add_spend`, `store/protocol.py:107`). Nothing here moves money; "booking" means changing these counters. We never pay anything. The provider bills the studio later.
- **Reservation**: before an attempt, the counters are raised by the most that attempt could cost (the **worst case**). If the raised counters would pass a limit, the call is refused and the raise is taken back.
- **Settle**: after an attempt that returned a usable answer, replace the reservation with the real cost the provider reported. **Keep**: leave the reservation as it is (used after a failed attempt, because the provider may have billed it). **Release**: take a reservation back off without an answer. this design releases in two cases only: our own gate refuses (no request was sent), or the provider answers with a definite client error (status 400, 401, 403, 404 or 422: the provider rejected the request itself). After any other failure once a request was sent, the reservation is kept (section 5.3).
- **Wall**: a limit that stops further calls: the daily budget, the monthly budget, the window end, or the one-call cap.
- **Window end** (`spend.window_end`): the last UTC date on which live model calls are allowed. A call is refused from 00:00 UTC on the next date, which is 05:30 IST that day. The last allowed moment is 23:59:59 UTC, which is 05:29:59 IST the next day.
- **Gate**: code that runs before every attempt and may refuse it. **Scope**: the information "this call belongs to agent X, with these limits" that the gate needs to reserve against X's budget. In this design a paid call with **no scope is refused** (`scope_missing`), never let through unmetered; command-line paths get a scope from a cap the person types (`--max-usd`), section 5.8. A **paid kind** is a configured backend that sends text to a priced service (section 5.1).
- **The customer demo** is the event the owner is preparing for. **The demo stage** is a core stage name (R449) and is always written in code font as `demo`. **Today the config literal is still `dev`** (`src/hadavin_sdk/config.py:317`, `Literal["dev", "pilot", "prod"]`) until PR H-0 renames it (readiness minor 4). So wherever this document says "outside the `demo` stage" it means "any environment other than `pilot` and `prod`", and the new spend tests and fixtures write `environment: dev`; H-0 renames them (other-tracks file, H-0).
- **Money type (OWNER-OPEN, question D5, non-blocking: lead's answer Q28; v13 ASSUMES option A for the design below, as a working assumption and not as the owner's answer).** CLAUDE.md says "money is integers". The money values that exist today are `Decimal` US dollars: `Reply.cost_usd` and `Verdict.cost_usd` (`models.py:294`, `models.py:305`), `Route` prices (`src/hadavin_sdk/config.py:55-58`), `Budget` (`registry.py:33-36`), the `spend` and `spend_month` tables (`store/migrations/0001_core.sql:87-92`, `0003_approvals_tick.sql:15-20`) and `runs.cost_usd` (`models.py:98`). Step 1 (S-1, S-2a, S-2b) adds **new** `Decimal` money values next to them (the `Config.spend` amounts, `Reply.booked_usd`, `SpendScope`, `Ticket`), because the store, `Limits`, `Budget` and every price are `Decimal` already and the two spend columns are `NUMERIC`. The owner's options, with the price of each in plain words: **(A)** keep `Decimal` US dollars for step 1 and for any later new table, as a written exception to the integer rule (no migration; the risk is rounding mistakes that integers avoid; the code never uses floats and always rounds a reservation up and a limit down); **(B)** whole nano-dollars (1 nano-dollar = 0.000000001 US dollar) in `BIGINT` for a **new** table only, the existing `Decimal` values stay (two money units in one code base and one conversion function); **(C)** integers everywhere (a migration of both spend tables and a rewrite of every reader and every price field; the largest change, the most consistent with the rule). **D5 does not block any PR (Q28).** v12 made it a start gate (G-3); that contradicted Q28 and is removed. Everything below is written for option A. **What changes if the owner later picks B or C, and for the merge order while D5 is open (readiness major 3):** under B, S-1, S-2a and S-2b stay as they are (they touch only the existing `Decimal` tables); every new money table, which today is only the DB-2 log (`old_usd`, `new_usd`), is re-issued with `BIGINT` nano-dollar columns and one conversion function before it is applied; DB-1 is unchanged. Under C, the new money values of S-1 (`Config.spend` amounts, `Reply.booked_usd`, `SpendScope`, `Ticket`), both existing spend tables, their readers and every price field change: that is a new PR series after S-2b, and the held files are re-issued for integer columns; merged code is changed, not thrown away, and a replacement needs a written reason. **Merge order while D5 is open: unchanged (7.1).** The one rule that follows: DB-1 and DB-2 are applied only after the owner has answered D5 or has accepted option A in writing at the move (start gate G-4). ## 3. Extend or replace: evidence (improve-before-replace)

**What exists.** (a) The demo meter (F1, F2): the right protocol, proved by its tests: reserve the worst case before, settle after, keep on failure, refuse leaves nothing booked, cap holds under four racing processes. (b) `k1b/loop.py:115-122` (F3): the worst-case formula for an abandoned call plus a per-invocation budget. ### 5.2 The window end (S-1)

One pure object `SpendWindow(end: date | None, clock=models.now)` in `llm/spend.py` (`end=None`: a window that never ends, for `window_end: none`); `check(now: datetime | None = None)` raises `SpendRefused("window_ended")` when `(now or clock()).astimezone(UTC).date() > end`. **Each caller passes its own clock reading** (`Limits.blocked` passes `self.clock()`, `CallGate.admit` passes the gate's `clock()`), so a test can give `Limits` a clock on the end date and the gate a clock on the next day (5.2b, readiness major 1). A naive clock raises `ValueError` (programmer error); an aware clock in another zone is **converted to UTC first** (a +05:30 clock would otherwise move the end by up to 5.5 hours; security minor 1; test with an IST clock at 23:00 UTC on the end date). `clock` is `models.now` (`models.py:19-20`, returns UTC) by default; `app.build` passes its own `clock` (`app.py:73`).

- **Who builds it: one function.** `build_window(cfg, clock) -> SpendWindow | None` in `llm/callgate.py`: returns `None` when no paid kind is configured (all fake); otherwise a window (for `window_end: none` a window that never ends, `end=None`). The same object goes to `Limits(window=...)` and to the gate and the guardrail, so there is **one rule in three places** (per-attempt check, `Limits.blocked`, the guardrail).
- **Where.** `NetworkLLM._retry` runs the gate's `admit` before every attempt (5.3). `SpendRefused` is defined in `errors.py` and is not a `ProviderError`; `with_retry` gets one changed line, `except (ProviderError, SpendRefused): raise` (`retry.py:95-96`, new import `errors`), so a refusal is never wrapped or retried. Why not a `ProviderError` subclass (v10's choice): the one edge `guard.injection -> llm.protocol` it needed merged the guard module group into the import cycle of the `llm` group (independent check `raw-merge-probe-v14.txt`, 8.1). Consequence: the `except ProviderError` sites (`k1b/loop.py:176`, `agent_loop.py:432-433`) no longer catch it, which is what we want; the S-2a builder reads `k1b/loop.py` 85-215 and gives the replay a defined end for a `SpendRefused` (test in E0-S2-4). A retry loop that crosses 00:00 UTC stops on the next attempt.
- **Fake kind decision (readiness blocker 1 and security major 7).** The fake kind (`FakeLLM`, `llm/fake.py:21`) is a plain class, not a `NetworkLLM`, has no gate and no reservation, and is refused outside the `demo` stage (`DEV_ONLY`, `backends/table.py:593-602`, `src/hadavin_sdk/config.py:366-369`). **The guardrail is independent of the llm kind**: with `llm.kind: fake` and a guardrail detector configured, `build_window` still returns a window and the detector checks it before `apply_guardrail`. Test: fake llm + guardrail + a past date → the guardrail refuses and no `apply_guardrail` request is made.
- **Exposure.** The window is judged by the clock of the machine that runs the agent, not the database. Bound: S-3 and the invoice comparison; database time comparison is L-1 (trigger: skew above 60 seconds, or machines the studio does not control). **Overshoot after the end, named (security major 6):** a request admitted at 23:59:59 UTC is billed after midnight; the bound is one request per attempt in flight at that moment, per process (each priced at most its worst case), and the retry sleep (at most 8 seconds, `retry.py:23`) cannot add an attempt because the next attempt checks the window.

### 5.3 The gate: contract per PR, wiring order, one attempt (S-1 and S-2a)

**Types.** `SpendRefused(Exception)` is defined in `errors.py` beside `ConfigError` (the one module with no imports, so `guard/injection.py` and `limits.py` can name it with no new cycle, section 8.1) and is **not** a `ProviderError`; it has `code`, and `str(exc)` is the code and nothing else: no prompt text, key, document text or amount (canary test E0-S2-9, security minor F13).
```python
def _retry(self, call):
    gate = self.gate
    if gate is None:                              # only with unmetered=True (tests of the kind itself)
        return with_retry(call, **self._retry_args())
    ctx = _CALL.get()
    if ctx is None:                               # a paid request outside chat(): fail closed
        raise SpendRefused("call_context_missing")
    def attempt():
        ticket = gate.admit(ctx)                  # window, abandoned, kill switch, scope, one-call bound, reserve
        try:
            answer = call()
        except BaseException as exc:
            status = self.status_of(exc)
            if spend.definite_client_error(status):   # 400, 401, 403, 404, 422 (defaults.NO_BILL_STATUSES)
                gate.release(ticket, ctx, status=status)   # the provider rejected the request itself: nothing was billed
            else:
                gate.keep(ticket, ctx, failure=str(status) if status is not None else type(exc).__name__)  # may have been billed: stays booked
            raise
        gate.settle(ticket, ctx, answer.tokens)   # never raises; route is ctx.route; adds what it booked to ctx.booked
        return answer
    return with_retry(attempt, **self._retry_args())
```

**The gate's actions** (`llm/callgate.py`):
1. `admit(ctx) -> Ticket | None`, in this order, all before any request: (a) `window.check()`; (b) `ev = _ABANDONED.get()`; `ev is not None and ev.is_set()` → `SpendRefused("abandoned")` (5.8; security minor m5: an `Event` object is always truthy once it exists, so the plain `if ev` of v12 would refuse every call that has an event; mutant: the `is_set()` test removed); (c) `scope = _SCOPE.get()`; none → `SpendRefused("scope_missing")` (**fail closed**: v9 security major 5; there is no default scope, so a paid call that belongs to no agent is never booked against a shared pseudo agent by accident (readiness major 2 of v10); a thread started without the context, a command-line path with no cap, a library caller with no scope all stop with a loud code instead of spending unmetered); (d1) `ctx.worst > scope.max_call` → `call_too_large` (one attempt alone is bigger than the cap: the call can never run); (d2) `ctx.booked + ctx.worst > scope.max_call` → `call_retry_budget` (earlier failed attempts of this call kept money and one more attempt would pass the cap: the call is out of retries, it is not too large; security minor F9: v11 used `call_too_large` for both, which read as a configuration error); both before any write. **The cap is for the whole call, retries included** (security major M4: v10 compared one attempt only, so one failed call could keep three worst cases, about 75 percent of the day at the default cap; now one call keeps at most `max_call`, about 25 percent); (e) `reserver.reserve(scope, day, ctx.worst)` with `day = clock().astimezone(UTC).date()`. Any `decimal.InvalidOperation` or non-finite value met in this arithmetic is `SpendRefused("bad_amount")` (fail closed, the right code: security minor N4).
2. `Limits.reserve(scope, day, worst) -> Ticket`: reads the kill switch (`store.get_kill_switch`, security minor 3: a switch set during a run now stops the next attempt) and raises `SpendRefused("kill_switch")` if on; runs `store.add_spend(agent, day, +worst)` (which returns the new day and month totals); **refuses when a new total is at or above its limit (`>=`, the same comparison as `Limits.blocked`, `limits.py:26-27,28`; security minor 2: v9 admitted a total exactly at the limit with `>`, which `blocked` would then refuse on the next call)**, after giving the amount back with `add_spend(agent, day, -worst)` and raising `daily_budget` or `monthly_budget`. Any other exception from the store (including `StoreUnavailable`) means the spend record could not be read or written: `SpendRefused("limits_unavailable")`; if the give-back itself fails the amount **stays booked** (fail closed), `_LOG.error("spend_giveback_failed")` is written and an audit row `spend_giveback_failed` is written the same best-effort way (security minor N3); `limits status` (S-2b) counts both audit rows for the month. A reserve whose acknowledgement is lost after the database committed leaves the amount booked and the call refused: a safe over-count (v9 security minor 7), stated here and tested (E0-S2-4). **The same holds for settle** (security minor N7): if the acknowledgement of a settle is lost after the database committed, the call returns its answer while the spend record holds the real cost, or if the write never happened the worst case; the count is then too high by at most `worst - actual`, never too low.
3. `CallGate.settle(ticket, ctx, tokens) -> Decimal` (the route is `ctx.route`) **never raises** and returns the amount the spend record now holds for this attempt (security major 3). Body: `ticket is None` → 0. `spend.clean_tokens(tokens, route, settings)` returns the two counts and a status. Limits: input `route.max_input_tokens`, or `spend.max_plausible_tokens` (5.1) when the route has none; output `route.max_tokens * 4`. Status **ok**: both counts are `int` (not `bool`) with `0 < n <= limit`. **missing**: `None`, zero, negative, a float or a bool: **keep**, `usage_missing` is logged and the worst case stays booked (v9 security majors 1 and 2: zero or negative usage must never become a small number). **high** (security minor N1: v10 left the bound undefined): an `int` above its limit, for example hidden reasoning tokens: book `max(worst, cost_of(route, n_in, n_out))`, never less than the reservation, log `spend_usage_above_bound` at error level and write an audit row (below). Otherwise `actual = max(cost_of(route, n_in, n_out), 0)` and `reserver.settle(ticket, actual)` runs `store.add_spend(agent, ticket.day, actual - worst)` (the same day as the reservation). **The whole body sits in `try/except Exception`**: on any failure it logs `spend_settle_failed` (class name only) **and writes one audit row** `spend_settle_failed` through `reserver.note` (for `Limits` an audit row, for `ProcessCap` a log line only, see the signatures above; best effort: if the audit write also fails, the error-level log line stays; security minor N3, because the later PR L-1 is triggered by "any `spend_settle_failed`" and a log line alone would not be found), does **not retry** (a retry after a lost acknowledgement would book twice), and returns `worst` (the reservation stays). Because `settle` never raises, a failed settle can no longer be classed transient by `with_retry` (an `OSError` is, `retry.py:63`) and **can no longer cause a second paid request** (the v9 flaw), and a paid answer is never thrown away because the spend store failed.
4. `keep(ticket, ctx, *, failure=None)`: writes nothing to the store; adds `ticket.worst` to `ctx.booked` and to the run's `KeptTotal` (`_KEPT`, above; the run's own cost record includes it, 5.5); when `failure` is set it also calls `reserver.note("spend_kept_after_failure", agent_id, failure)`. `release(ticket, ctx, *, status=None)`: `reserver.release(ticket)` runs `add_spend(agent, ticket.day, -worst)`; when that worked and `status` is set it calls `reserver.note("spend_released_client_error", agent_id, str(status))`; if the give-back fails it behaves as a failed give-back (the amount stays booked, so `keep(ticket, ctx)` is applied, logged and audited as `spend_giveback_failed`). Both never raise. **One rule for a client error:** a request is released only when its status is in `defaults.NO_BILL_STATUSES` (400, 401, 403, 404, 422) or `RELEASE_EXTRA_STATUSES`; every other 4xx (for example 408, 409, 413, 429) is kept.

**What each outcome books:**
| Outcome of an attempt | Booked | Why |
|---|---|---|
| usable answer with sound usage numbers | the real cost (`settle`, never below zero) | normal |
| usable answer with missing, zero, negative, non-integer or implausible usage | the worst case stays (`keep`) | a missing number must not become a small number |
| a failed settle (store error) | the worst case stays; answer returned; one log line | no second request, no lost answer |
| the provider answered 400, 401, 403, 404 or 422 (a definite client error) | nothing (`release`) | the provider rejected the request itself; UNVERIFIED that no vendor bills it (5.9 row 5); a wrong key books nothing |
| any other exception after the request started (timeout, connection error, 408, 429, 5xx, malformed 200, certificate error, status not readable, anything else, `KeyboardInterrupt`) | the worst case stays (`keep`) | the provider may have billed it |
| usable answer with a token count above its bound (`high`) | `max(worst, cost of the reported counts)` | hidden reasoning tokens must not under-book (N1) |
| our own gate refuses (window, abandoned, kill switch, scope missing, one-call cap, daily or monthly limit, prompt too large, store unreadable) | nothing (the give-back already ran) | no request was sent |

A wrong key (401) or a malformed request (400) books nothing **if the kind's status can be read** (E0-S2-4 builds each kind's real error offline, security major F2), so it cannot empty the day. **Open availability risk, stated (security major F3).** A 429 storm or a 5xx outage keeps the worst case of each failed attempt. One call keeps at most `max_call` (by default one quarter of the day), so **four failed calls can stop an agent for the rest of the UTC day**, and the run then ends `NEEDS_PERSON` with `limits.daily_budget`, which reads like a spent budget although little money was spent. Three controls ship; none closes the risk: (1) every kept amount after a failure writes an audit row `spend_kept_after_failure` (agent, status or class, amount) so `limits status` (S-2b) prints how much of today's total is kept after failures and a person can tell a storm from real use; (2) the card text for `daily_budget` adds that figure; (3) releasing 429 is prepared and **off**: `defaults.RELEASE_EXTRA_STATUSES = frozenset()`, and E0-S2-4 runs the 429 case with both settings. **The choice between "keep every failed attempt" (money-safe, the default) and "release 429" (a request the vendor rejected for rate was probably not billed; UNVERIFIED) is the owner's: question O1, section 10.** Kept-after-failure money is also counted in the run's cost and in the invoice comparison (7.3), which therefore can show our total above the invoice; the status line gives the figure to subtract. Releasing 408, 5xx and timeouts is L-6 (needs invoice evidence).

### 5.4 Numbers that could lower a total: refused at the choke point (S-2a)

Class: **a value that is negative, zero where a count is meant, not finite, or implausible reaches a money total.** The choke points are `Store.add_spend` (all writers) and `Limits.charge`/`settle` (our writers). Fixes, each with a hostile-input test:
1. Prices, budgets and every `Config.spend` number: finite, `ge=0` (5.1; security minor N4: v10 applied the finite rule to `Route` and `Budget` only).
2. Token counts: `clean_tokens` (5.3 item 3); `reply()` uses it, so a negative count no longer prices negative. **S-1 owns this edit** (`reply()` and `clean_tokens`, `llm/common.py:164`), not S-2a.
3. `Limits.charge(agent_id, usd, booked=Decimal(0))` adds `max(usd - booked, 0)` and refuses a non-finite `usd` or `booked` with `ValueError`; a negative `usd` is clamped to 0 (a negative reply cost from a buggy kind no longer lowers the total).
4. **Both stores, same rule, and the shape of the Postgres write (security blocker B1).** `add_spend` first refuses a non-finite `usd` (`ValueError`) in both stores. **Postgres (`store/postgres.py:416-431`), new shape, inside the same `with self._lock, self._db.transaction()`:** for `usd >= 0` the two existing statements stay (`INSERT ... ON CONFLICT DO UPDATE SET usd = spend.usd + EXCLUDED.usd RETURNING usd` for `spend`, the same for `spend_month`); for `usd < 0` each table gets `UPDATE spend SET usd = usd + %s WHERE agent_id = %s AND day = %s RETURNING usd` (and the month form). If either UPDATE returns no row, the code raises `LookupError("a negative change to a total that does not exist")` and the transaction rolls both rows back. A refusal by the database rule (`psycopg.errors.CheckViolation`, 23514: the resulting total would be below zero) is mapped to the same `ValueError` the memory store raises, so both stores give one exception type: **`ValueError` for a result below zero or not finite, `LookupError` for a negative change on a missing row** (run on 16.15, `raw-pg-v15-run1.txt` A5 to A11). **Why the shape matters (run on 16.15):** Postgres tests a check rule on the row an INSERT proposes before it looks at the conflict rule, so with the old shape every lowering change, a settle (actual minus worst, nearly always negative) or a give-back, is refused with 23514 once DB-1 is applied, even when the stored total would stay above zero (the real old `add_spend` with the default held file: `raw-pg-v15-run1.txt` A5, error 23514; earlier runs `raw-pg-b1-v14.txt` T1 and T1b). An UPDATE is tested on the resulting value (`raw-pg-v15-run1.txt` A6 and A7; earlier T2). **Memory store (`store/memory.py:196-204`):** compute both new totals first, refuse if either is below zero, then commit. This code-level refusal stands in for the database rule when DB-1 is not applied; it does not stop a writer that bypasses our code. **Test that fails on the old shape (E0-S2-2, on Postgres with DB-1's file applied in a throwaway database):** a change of -1 on a row that holds 2 succeeds and leaves 1; a give-back to exactly 0 succeeds; a change that would leave -0.01 raises `ValueError` and both rows are unchanged; a negative change on a missing row raises `LookupError`; the same first two cases run against the v12 shape fail with 23514 (the proof that the test depends on the shape). **A change larger than the total (security minor 3 of v14, the "wedge"):** -1 on a total of 0.5 raises `ValueError` and changes nothing, and the agent-day keeps working afterwards (A8). The prototype is `evidence-handoff-v15/pg_v15.py` (`add_spend_v15`; not product code; 93 of 93 checks in two runs). **The finite check does not depend on the held file:** both stores refuse a not-a-number or infinite `usd` before any statement (A10, run), so the protection against those two values does not wait for L7. **DB-1 is applied only after this code is merged and running (start gate G-4).**
5. Excess over the worst case: `settle` books the real cost even when it is above the reservation (real money was spent; the counters should show it). A reported cost that is huge but passes `clean_tokens` is bounded by the plausibility limits, and booking it errs on the side of a stop, never a pass.

### 5.7 The guardrail call (paid, metered from S-2a)

`GuardrailDetector.__init__(client, guardrail_id, version, threshold, *, gate, price: GuardrailPrice | None = None, unmetered=False)`, where `GuardrailPrice(usd_per_unit, unit_chars, max_chars)` is built from the three settings of 5.1 (same rule as the llm kinds: a gate, or `unmetered=True` said out loud, 5.3); `make(settings, deps)` (`guard/bedrock_guardrail.py:61`) reads `deps.gate`. The attempt is **kept** after success or failure (a guardrail answer carries no cost field, so there is no settle; `keep` adds it to the run's `KeptTotal`, which the runtime reads into the run's cost, 5.3 and 5.5). `admit` runs the window check (S-1) and, from S-2a, reserves against the run's scope, or, on the approval summary screen, against `-unattributed` through `ScopedDetector` (5.5). **What is UNVERIFIED and what it can do (5.9 row 7):** whether the vendor bills this check per unit of text, per policy type or per request.
