## What the files say
- Unique index: YES in the file. mf_leads.sql (v4): lead_key text PRIMARY KEY. Not seen in the take database itself (it does not exist yet): 'index not seen' there until the lead has created the table.
- Claim node (mf-form.json:97, node 'Claim'): INSERT ... ON CONFLICT (lead_key) DO NOTHING RETURNING lead_key, claim_token, state. It sets claimed_until = now() + 45 seconds. The node has alwaysOutputData: true, so a duplicate (zero rows returned) still passes one empty item on; the next node 'Claimed' is an IF that sends only items whose lead_key is not empty onward. So a duplicate stops there. UNVERIFIED in n8n 2.46.6 (not run).
- A second send of the same lead id is skipped while the earlier record (the row) of that id still exists, whether the 45 seconds have passed or not. The lease does NOT decide the duplicate case. The skip ends if the row is gone (the lead empties mf_leads at clean start, Q20.2), so 'however long you wait' is not claimed.
- The lease matters for crashes: mf-recovery.json 'ClaimStuck' re-claims a row whose state is not done, review, unknown or failed, whose claimed_until is in the past and whose attempts is below 3 (checked every 30 seconds, read from mf-recovery.json real-v5), then processes it again. Claim (mf-form.json real-v5) inserts attempts=1 for a lead going to processing and ClaimStuck adds 1 each time, so at most two re-pickups: up to three tries in total, the first one included. After that 'MarkFailed' sets state failed (or unknown if the mail was already sent) and an alert mail follows.
## Correction to the lead's note (ORDERS.md Q21.2: 'no takeover after expiry')
That is not what mf-recovery.json says: after the lease runs out, the recovery flow DOES take over an unfinished lead (up to 3 attempts). It does not take over a lead that reached done, review, unknown or failed. The test is only 'lease over and not finished', so a first run that is merely slower than 45 seconds is re-claimed too (earliest pickup about 45 to 75 seconds after the claim). mf-sub-crm-mail.json real-v5: no node there sets claimed_until (only Claim and ClaimStuck do), so no lease renewal was found; its writes (SetCrmId, MailClaim, MarkDone, MarkUnknown) all check claim_token, so an older run that was re-claimed cannot mark done or send the mail; MailClaim sets mail_sent before the send.
