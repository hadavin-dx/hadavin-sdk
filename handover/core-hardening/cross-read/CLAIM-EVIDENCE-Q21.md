- Unique index: YES in the file. mf_leads.sql (v4): lead_key text PRIMARY KEY. Not seen in the take database itself (it does not exist yet): 'index not seen' there until the lead has created the table.
- Claim node (mf-form.json:97, node 'Claim'): INSERT ... ON CONFLICT (lead_key) DO NOTHING RETURNING lead_key, claim_token, state. It sets claimed_until = now() + 45 seconds. The node has alwaysOutputData: true, so a duplicate (zero rows returned) still passes one empty item on; the next node 'Claimed' is an IF that sends only items whose lead_key is not empty onward. So a duplicate stops there. UNVERIFIED in n8n 2.46.6 (not run).
- A second send of the same lead id is skipped whenever the row already exists, whether the 45 seconds have passed or not. The lease does NOT decide the duplicate case.
- The lease matters for crashes: mf-recovery.json 'ClaimStuck' re-claims a row whose state is not done, review, unknown or failed, whose claimed_until is in the past and whose attempts is below 3 (every 30 seconds per the earlier reading), then processes it again; after 3 attempts 'MarkFailed' sets state failed (or unknown if the mail was already sent) and an alert mail follows.
## Correction to the lead's note (ORDERS.md Q21.2: 'no takeover after expiry')
That is not what mf-recovery.json says: after the lease runs out, the recovery flow DOES take over an unfinished lead (up to 3 attempts). It does not take over a lead that reached done, review, unknown or failed. The lead should re-read mf-recovery.json 'ClaimStuck' before approving the sentence below.
