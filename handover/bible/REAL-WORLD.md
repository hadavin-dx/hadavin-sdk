# Real world: course lab → real client builds

The course runs in a lab: an OpenAI-compatible gateway, lab models, JSON-file stores, stdlib mock APIs, SQLite, CSV and print scripts under `/root`. Real Hadavin builds keep **every course step and rule**, and swap the lab parts for the client's own cloud. This file is the translation table. Each topic's "Course → real world" section has the topic-specific detail.

**Sources and labels**
- Course: `topics/NN-*.md`, cited as `NN` or `NN L2`. `NN §8` means that topic's "Course → real world" section.
- `[Hadavin practice]`: studio rule, not in the course.
- `[research 2026-10-29: <file>]`: `..\research\research_notes\FDE stack and AI software factory 2026\` (`ml_engineer_work.md` = ML, `practitioner_stack.md` = PS, `ai_software_factory.md` = ASF).
- `[stack 2026-10-28]`: `..\archive\warden-archive\research-2026-10-28-stack.md`.
- `[decision 2026-10-28]`: `..\memory\decisions-2026-10-28.md`.
- **Prices, regions and GA dates are as seen on the date given. Re-check live before quoting a client.**

**Choosing the column:** the client's cloud decides. Defaults are AWS: Claude on Amazon Bedrock in the client's own account. Use Foundry on Azure and Vertex AI on GCP. The direct Claude API is used only on request `[decision 2026-10-28 #5]`. Build only the backends a real client needs `[decision 2026-10-28 #3b]`.

**Neutral defaults** `[Hadavin practice, no single dependency; owner rule 2026-10-31]`: wherever the table below names an AWS product (or one vendor's model) as the "Hadavin default", it is one backend of a kind. ## 2. AI Software Factory pillars → hadavin-sdk modules

> **PROPOSAL, pending EGM review.** This section is design, not a sourced fact. Under the owner's EGM rule it goes through `/egm:egm-review-loop` (then `/egm:egm-resolve`) before any build. No hadavin-sdk code exists yet `[decision 2026-10-28]`. Source: `[research 2026-10-29: ASF Q1–Q6]`.

**Where the pillars come from.** "AI Software Factory" is [vendor-inspired name removed]'s framing, not a product name. Port's docs list seven pillars: [vendor-inspired name removed], Workflows & tools, Port AI, Agent management, Interface builder, Governance layer, Platform administration. The five pillars below regroup them; Port does not use this five-pillar list itself (ASF Q1 inference).

**Shape.** One Python service with five small modules over one Postgres schema, exposed as one MCP server (`catalog.query`, `actions.run`, plus a read-only flag) and a REST API (ASF Q6). The agent never holds raw credentials. It can only call governed actions, filtered by an allowlist and a policy; the executor holds the credentials (ASF Q2 inference, from Port's `run_action` model).

## 3. Code standards

Every client build follows these. Course rules are cited; the rest is `[Hadavin practice]`.

1. **Segregated modules.** `config` / `adapters` / `core` / `evals` / `cli` or `api` (05 §8). Core logic never touches provider shapes. The read → loop → write shape becomes adapter (read) → core (per item) → adapter (write) (05 §8).
2. **One interface per capability; one adapter per backend.**
   - Examples: llm, embeddings, store, retrieve, injection_check, pii, extract, connector, approval_channel, audit.
   - The client's config picks the backend.
   - Build only the backends a real client needs.
   - Every backend passes the same contract tests and the golden gate `[decision 2026-10-28 #3b]`.
3. **Typed config, validated at start-up.**
   - Model ids per route, price sheet, thresholds, top-k, rerank depth, budgets, timeouts, max steps, the abstain phrase, prompt file paths, region and account all live in typed config (e.g. Pydantic settings).
   - A bad config fails loudly at boot, not mid-request (07 §8, 14 §8, 25 §8, 32 §8).
4. **No literals.**
   - No model id, env, region, account, endpoint or threshold literal in code.
   - No real-looking token in tests: build fixture tokens from parts (owner rule).
   - Prompts are versioned files (09 §8).
5. **Secrets by reference.**
   - Config holds only the secret's name or ARN. The workload's identity fetches the value at runtime through the secrets kind (named lookup; backends SSM SecureString, Secrets Manager, Key Vault, Secret Manager or a self-hosted vault).
   - Secrets never go in the repo, a `.env` file, a prompt, a tool result, a log line or a trace attribute.
   - CI scans every PR for secrets (23 §8, 36 §8).
6. **Tests + evals gate every PR** (required checks; merge only on green):
   - `ruff`, and `pytest` with fake backends for unit tests;
   - contract tests per adapter;
   - the cross-user leak test (19 §8);
   - the outbound-PII test (36 §8);
   - flaky-tool and garbage-tool cases (21 §8);
   - the golden-set pass-rate gate (28), the hit-rate floor (29), trap-abstain and false-abstain rates (32), and the judge audit on rubric changes (27).
   - Thresholds come from config and match the contract. Lowering one needs the client's written OK (28 §8).
7. **Structured logs + OpenTelemetry.**
   - JSON logs; the trace id is the request id; stages are child spans (35 §8).
   - The model-call span carries model id, tokens, latency, cost, route, `fell_back` and cache hit.
   - Default logs are metadata-only.
   - Pin the OTel GenAI semconv version `[research 2026-10-29: PS §4]`.
8. **Errors are typed and bounded.**
   - Every external call has a timeout.
   - Retries with backoff live in the adapter.
   - Tool errors carry a `retryable` flag and no secrets or stack traces (21 §8).
   - Guards fail closed (31 §8).
9. **Governed actions only.** Allowlist + schema validated in code + approval for risky actions + audit with the service-account identity. Write retries are idempotent or approval-gated (11 §8, 21 §8, 23 §8).
10. **Self-contained delivery** `[decision 2026-10-28 #4]`:
    - the client gets a frozen vendored copy plus a hash file;
    - nothing is fetched from the owner's GitHub, org, packages, registries, reusable workflows, actions or images, at build, in CI or at runtime;
    - third-party packages are hash-locked from PyPI or the client's mirror, with an SBOM;
    - a test fails if any file names the owner's org or account;
    - updates arrive only as a new vendored copy the client accepts.
11. **Runbook commands are real entry points** of the package (re-index, eval, rotate), never ad-hoc scripts (41 §8).
