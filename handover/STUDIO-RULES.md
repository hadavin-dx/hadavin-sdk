# Studio rules for work on the Hadavin core (summary in the studio's own words)

These rules are the studio's. The laptop lead checks your work against the full rule book; this file lists what you need so you do not have to guess. If a rule here conflicts with a ticket, the rule wins and you write the conflict into `handover/questions-for-lead.md`.

1. **Honesty.** Lead every report with what failed, what is uncertain and what was not checked. Never write done, passed or verified without the command and its output. Admit slips plainly. Do not hide gaps behind "known limitation": every problem you find is fixed and verified in the same piece of work, except what is impossible now, needs the owner, or needs a third party (state it plainly with the next step). Findings from other agents are unverified until you check them.
2. **No single dependency.** Every external dependency (cloud, vendor, tool, model, library) sits behind a kind: an interface with a neutral or self-hostable default and at least one working alternative, or a written outline with a named trigger. Vendor SDK imports live only inside their kind module (a repo test enforces this). A test double is not an alternative.
3. **Least privilege everywhere.** Deny by default; read-only by default; exact actions and resources (no `*`); short-lived credentials (no long-lived keys); one identity per function (agent runtime, executor, approver, audit writer, audit reader, migrations, CI deploy); an agent never holds approver or executor credentials and cannot widen its own scope. Every new role or kind ships its policy text, a per-action reason, a negative test (the identity is refused what it must not do) and an over-breadth review. Dev-only kinds are flagged and refused in the client profile.
4. **No hardcoding, no secrets.** Environment names, regions, account ids, model ids, prices, thresholds, paths and hostnames come from validated config with documented defaults in one place. Secrets only through the secrets kind. Fake credentials in tests are built from parts; the only literal allowed is AWS's `AKIAIOSFODNN7EXAMPLE`. Never print, paste or commit a secret, an account number or a personal e-mail address.
5. **Personal data (PII) is masked before it reaches a model, a log or the audit trail.** Money is integers (minor units; micro-dollars for spend). Anything that can pay, approve or delete needs a person's approval unless the ticket says otherwise.
6. **No real client data** in tests, fixtures or notes. Made-up data only.
7. **No spend.** Do not call any paid model or service. Use the fake or recorded model. Do not change repository settings, branch protection, visibility, secrets or DNS. The lead merges; you open pull requests.
8. **EGM order for every package** (see the plan, section 3): ticket review, build, evidence by a separate runner, two independent reviews on a snapshot, ledger, resolve, repeat. Reviewers get the diff, the ticket and the evidence, never the author's verdict. Money, redaction and security packages have no round cap; others get at most 2 fix batches.
9. **Class-level fixes.** For each bug: name the class of bug, fix it at the shared choke point with an allowlist or a grammar taken from the specification, search for siblings, add property or fuzz tests, and prove the new tests fail on the old code.
10. **Reuse before writing.** Look in the core first. Do not copy a demo file when the core already has the capability; improve what exists instead of replacing it, unless you write the evidence down.
11. **One source of truth.** A demo never hand-edits a core copy. Generic fixes go to the core and the demo re-pins.
12. **Wording.** Everything written for the owner, a client or the public uses precise, plain words that a non-technical reader can follow: explain a label before using it, one word keeps one meaning, say who does what, no unexplained codes. Client-facing text says Hadavin.
13. **Public repository hygiene.** This repo is public. No vendor-inspired product names (a repo test lists the banned strings), no screenshots or third-party course material, no private notes beyond the handover folder, which is deleted at the end.
14. **Times** are given in UTC and IST (IST = UTC+5:30).
15. **Speed.** Plan whole packages, batch fixes, run one full evidence run per fix batch. Speed never lowers a quality gate.
16. **Handover files stay on the handover branch.** Evidence, reviews and tickets (files under `handover/evidence`, `handover/reviews`, `handover/tickets`) are committed only on `core/cloud-handover`. A builder or evidence runner on any other branch (`wip/*`, `core/*`) keeps them outside the branch and the session copies them; the CI security job fails a pull request whose history carries them. Run `/home/user/build/bin/check-no-handover-files.sh <branch-name>` before every push (ORDER 266).
