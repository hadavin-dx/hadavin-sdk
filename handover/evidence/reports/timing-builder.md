BLOCKER (guard fired on non-waiting tiny calls under CPU contention)
Class: a one-sample test on a noisy signal; one scheduler pause (5 ms or more) inside a tiny sizing batch (tens of microseconds of work) has wall/CPU ratio over 50 and was read as "work that waits".
Fix at the choke point (tests/fixtures/timing.py `_batch_timer`): a batch that looks like waiting (wall >= 5 ms and > 50 x processor time) is run again; `Untimeable` is raised only after WAIT_TRIES = 3 tries of the same batch in a row all look like waiting. Waiting (sleep, I/O, lock, child process) repeats in every try, a pause does not. The batch size is not grown on a suspect batch, so a sleeping function is refused after 3 tries (about 60 ms), not after a huge batch. I chose this by reasoning and then by experiment over the alternatives (judge only batches that reached MIN_BATCH_S would not catch sleep in the sizing batch before a huge batch; minimum over repeats has the same problem in the sizing phase). The wall clock is now injectable (`wall=` on seconds_per_call / seconds_per_call_each) so the guard is tested deterministically.
Tests: WallModel (made-up cpu and wall clocks): one 8 ms pause inside a 60 microsecond batch at call 1, 2, 3, 5 does not raise; two pauses in a row on the same batch do not raise; work that waits 8 ms in every call raises after exactly 3 tries; plus the existing real sleep and child-process tests.
