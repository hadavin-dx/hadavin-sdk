## Read this first: gaps and caveats

1. **The machine was NOT quiet.** Five other agents shared it. The one-minute load average before each run is in the raw logs and in the table below. Every load-driver run and every protocol run was marked NOISY (load 4 to 23, bounded wait of 10 x 30 s did not reach below 3.0). Only the `pytest ... measure_burst` runs of pass 1 started on a quiet machine (load 0.5 to 1.1). Timing results from noisy runs (driver lag, drain seconds) are upper bounds, not clean figures. The fixed 10 s deadlines (idle, body, drip) are wall-clock and were not affected.
2. To keep inside the time box I waited for a quiet machine once per batch, not before every single run; the load is recorded per run.
3. The author's Windows figures ("150 all answered", "from about 300 the operating system refused") cannot be re-measured here (Linux). I report the Linux values next to them; they are a different operating system, not a proof that the Windows claim is wrong.
4. NOT measured (reason in the table): 9-second call cut-off, reaper retry waits (1, 2, 4, 8 s), 1024 handler threads, listen queue 1024 (`ss` is not installed), clock jump of 30 s, 10,000-request load, the seven after-load checks of `check_invariants.py` (needs the SMTP catcher and a CRM dump wiring; I did not run it, so claims about check 6 and check 7 defaults are not run through the checker; the drain and 503 numbers below come from my own reading of the request log and `/counts`).
5. My own slip: my first protocol run built body sizes of 65525/65526 bytes (wrong padding). It was thrown away (`raw/proto-p1-firstattempt.jsonl`) and re-run with exact 65536/65537 sizes.
