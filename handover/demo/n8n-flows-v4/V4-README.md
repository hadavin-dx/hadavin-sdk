# Design A v4: alert claim window longer than any single SMTP wait. BUILT, NOT RUN.
Trigger: lane3 on v3 (6ebb7f62, n=1): the SMTP answer for the alert held 90 s, longer than the 60 s first claim window: the claim expired while send 1 waited, the sweep re-claimed at 91 s, 2 alerts at about 120 s. Duplicate, not loss. The v3 text "at most one alert" was wrong for this case.
Choice (a2, a third way): NOT "set the node timeout below the claim window" (the Send Email node has NO timeout setting; I could not lower it) and NOT only "lengthen the claim" (a long claim would also delay the retry after a quick failure).
- AlertClaim: alert_until = now + 720 s (12 min). Basis, READ from the nodemailer library inside n8n 2.46.6 (smtp-connection): connect 2 min, greeting 30 s, socket inactivity 10 min; so one hung step ends within 10 min and a 12 min claim outlasts it. NOT MEASURED: AF2 (which would measure the node's real wait) has not run, so I have NO measured node timeout value to give.
- NEW node AlertBackoff on the error output of AlertSend: sets alert_until = now + 60 s x min(alert_attempts, 5) (60, 120, 180, 240, 300 s) for the same token, so a failed send is retried at the old backoff, not after 12 min.
- Everything else as v3. Folders: n8n-flows-v4 (lease 120, plus mf_leads.sql, same table as v3), n8n-flows-film-v4, n8n-flows-real-v4. Builder switch: MF_V4=1 (default unset = v3 byte for byte; checked by script against the pushed v3 JSON).
## What this still does not guarantee
- A send that outlasts 12 min (several slow steps in a row) can still produce a duplicate. A mark that fails after a sent alert can still produce a duplicate.
- If n8n dies while sending, the alert waits up to 12 min for its retry (late, not lost). A hung SMTP can make an alert come up to about 12 to 13 min late.
