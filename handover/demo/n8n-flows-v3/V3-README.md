# Design A v3: alert as state (no lost notification). BUILT, NOT RUN.
Why: v2 sent the "unknown" and "failed" alerts from a fire-and-forget node after the state was already final. If that SMTP send failed or hung, nothing ever sent the alert again (lane3 F-c, found by reading: AlertUnknown / AlertFailed, continue on error, state excluded from recovery).
Folders: n8n-flows-v3 (lease 120), n8n-flows-film-v3 (lease 45, 2 tries, 10 s), n8n-flows-real-v3 (HubSpot node, same film values). Built by `n8n-mainframe/build_mainframe.py` (same switches as before). The v2 folders are untouched. Table: n8n-flows-v3/mf_leads.sql (four new columns; the v2 flows also run on it).
## Nodes changed against v2 (diff computed with a script, node by node; form and hook flows are identical)
- mf-sub-crm-mail: REMOVED AlertUnknown (the in-run alert). The unknown paths (MarkUnknownA, MarkUnknownB) now go straight to OutUnknown; the two IF nodes after them are kept and both outputs lead to OutUnknown (kept to keep the diff small).
- mf-recovery: REMOVED FailedRow and AlertFailed. CHANGED MarkFailed: state is `unknown` when mail_sent is true, else `failed` (wording point: a lead that may have been mailed is never "failed"). ADDED AlertClaim, AlertRow, AlertSend, AlertMark (the sweep).
## The sweep (every 30 s tick, last branch of the recovery flow, after MarkFailed so a lead failed in this tick is alerted in this tick)
1. AlertClaim: takes up to 5 rows with state in (unknown, failed), alert_sent=false, alert_until empty or past (FOR UPDATE SKIP LOCKED), sets a new alert_token, alert_attempts+1 and alert_until = now + 60 s x (1 + min(attempts, 4)) (60, 120, 180, 240, 300 s). Two recovery copies cannot take the same row.
2. AlertRow: only a returned lead id is work (the Postgres node returns one empty item otherwise).
3. AlertSend: the alert mail, subject by state (unknown: "mail outcome unknown for <id>", failed: "lead failed <id>"). Success output goes on; the error output goes nowhere (row stays alert_sent=false).
4. AlertMark: sets alert_sent=true ONLY after AlertSend succeeded, only for the same token and only while false.
## Rules this gives (by design, not measured)
- A dead SMTP never loses the alert: the row stays alert_sent=false and the sweep retries with backoff (about every 1 to 5 minutes per lead, 5 leads per tick), no hard stop. I did NOT use a retry cap: a cap would end in a lost notification again. Nothing is written to a log with lead data.
- At most 1 alert per lead, except: (a) the send succeeded but AlertMark failed, (b) an alert send outlasts its claim window (60 s first time) and succeeds later (the node has no timeout setting): then a second alert can arrive. Both give a duplicate, never a loss.
- DEVIATION from the order: I did not keep an immediate alert inside the run. One send path only (the sweep), so the alert comes up to about 30 s after the state is set. Tests therefore wait for the alert (mf.py wait_final now waits for alerts>=1 when the state is unknown/failed; need_alert=False for AF1).
- UNTESTED node detail: AlertMark reads the lead id with $('AlertRow').item (paired item through the Send Email node). If a run shows alert_sent stays false after a delivered alert, that is where to look; AF1 checks alert_sent.
