The exact sonar key line passes both scans. 25 near-misses are planted as whole files written as bytes (the same bytes on Windows and Linux): another project key (letters and digits, and letters only), last character changed, dash, equals, space-and-text, pure trailing blank, dot suffix, upper-case value, capital first letter, lower-case and upper-case name, another character at the dot of the name (`sonar` + X + `projectKey`), spaces around `=`, text before the name, the key twice (space between, and joined), CRLF line ending, look-alike file name, another character at the dot of the file name, text after the file name, another folder, another .toml file, another character at the dot of `.gitleaks.toml`, README. Each is reported by the literal scan, by gitleaks, or by both (a table in the test file says which). A blank in front of the exact line is allowed by both (the same public text). The exact line in a sub-folder is reported by the literal scan only; gitleaks lets it through by its path rule (harmless).
- Mutants (evidence-m2-2): 17 widened versions of the exception in `exceptions.txt` or `.gitleaks.toml` (value class, missing end anchor, any file, missing start anchor, dot instead of `\.` in the name, in the path and in `exceptions.txt`, any properties path, path without anchors, case-insensitive, a whole-file path allowlist with the regex removed, `regexTarget = "line"` and `"secret"`); each is caught by at least one named test (1 to 18 failures each); no survivor.
- Without gitleaks: 23 of the new tests skip (and 3 in `test_hygiene.py`); with `DPLD_REQUIRE_SCAN=1` the new tests fail (23 failed). Without git on PATH the new tests skip (evidence-m2-3). The gitleaks program is found with the helper of `tests/test_hygiene.py` (bare name looked up on PATH, then made absolute).
- Detector measurement (evidence-m2-1, raw output; the docs note in `docs/tests.md` says only this): with gitleaks 8.30.1 and the repo config, a made-up value after `hadavin-dx_` in a `key=value` line was reported at 20, 30, 40, 50 and 60 random lowercase letters and digits, and not reported when it held letters only, letters and hyphens only, or one repeated letter, at any of those lengths. One digit made the hyphenated words reported, and did not for the repeated letter. The real key holds a digit (`n8n`) and is reported when the allowlist is removed. So the first version's wording ("lowercase 40 or more characters after the prefix are not reported") was too broad: it was true of the planted values (letters only), not of the real key's shape. The cause inside gitleaks was not read; the data fit "no digit" or "too little variety". The repository scan (`patterns.txt`, pattern 9, `[A-Za-z0-9+/=_-]{40,}`) counts an unbroken run including the prefix and a key name before `=`; a dot, space or quote ends the run. It reported every `key=value` line measured. With the name `projectKey=` before it, 20 characters after the prefix already make a run of 42 and were reported; in a prose line 20 characters after the prefix (31 in all) were not.
- The CRLF copy of the exact line is reported by gitleaks (a generic-api-key finding; an allowlist ending `\r?$` made it pass in an experiment, not shipped). The test pins this CURRENT behaviour on purpose: a future benign `\r?$` fix would fail it and the test would then be changed with it. Consequence: `.gitattributes` (`* text=auto eol=lf`) makes every checkout LF, so neither CI nor a developer on Windows sees a finding; only a hand-saved CRLF copy of `sonar-project.properties` in a working tree would. I did not change `.gitleaks.toml`.
