VERDICT ON ROUND-2 FIXES (checked by reading)
- Attempts as ownership token: holds.
  - `attempts` is written only by the claim (desk.py:85-94). resolve, _defer_pending, _record_send_result and the requeue never change it. It never decreases, so a token value cannot repeat for one row.
  - A person's Retry resets `auto_attempts`, not `attempts` (the CASE in the claim SQL). The two counters are separate.
  - The claim reads the token inside its own BEGIN IMMEDIATE (desk.py:896-900) and keeps it in thread-local storage. `_take_token` runs on the same thread right after the claim, so I found no cross-thread mix-up.
  - A stale owner's `_mark_crm`, `_touch` and `_record_send_result` match 0 rows once the row is `pending`, `unknown`, `failed` or has a later claim. This closes the round-2 double-put.
- The 3-strike limit works (see M4 for its edges). A restart does not loop forever: the counter reaches 3 again within 3 reaper passes.
- Replay-only-if-due, the time budget and requeue-at-cap are sound apart from the findings below. Rows are ordered by `updated_at`, and a driven row moves to the back. I found no way for the budget to skip a row forever. One slow row can overshoot a pass by one send timeout, which is harmless.
- CASE backfill: the `sent` exclusion and the ordering are correct. It still has the gaps in M3 and m3.

CHECKED, NO DEFECT FOUND
- Token reuse: no path found (see the verdict above).
- m6, a failed `crm_done=1` write: the row stays `sending` with `crm_done=2`, and `_crm_step` returns False before any send. After the stuck time the reaper requeues the row.
  - Keyed outbox: back to `pending`, or `failed` at cap. The next drive re-puts on a keyed CRM, and a not-keyed CRM goes to `crm_unconfirmed`. There is no double put.
  - Blind outbox: this is M1.
- `ambiguous_prior` with requeue-at-cap: a keyed row at cap becomes `failed` with `ambiguous_prior=1`. Retry then sends with the same key, which is idempotent, and re-checks for a blind sender before sending. That is consistent.
- Resolve SQL placeholder order (10 parameters) matches its 10 placeholders. `crm_present` and `sent` are mutually refused as intended.
- A stale owner A that did pass `_touch` and is inside `outbox.send` or `crm.put` is not stopped by the token. It is covered only by keyed idempotency. For blind modes the mode-dependent unknown or `crm_unconfirmed` rules cover it, but M1 makes those rules wrong when the stall is before the send.
