# Portal addendum 4: logs, "what the AI can read", data safety, focus, real mouse pointer (lead, owner request 2026-11-09)

Owner words: show the logs; show clearly what the AI can read and that personal data is safe; make the duplicate-proof main points the focus; the moving dot looks like a test, use a real mouse pointer.

## 0. What is true today (checked in code, so we never claim more)
* The AI step (`Qualifier.qualify(lead_id, email_key)`, desk.py around line 851) receives ONLY the lead id and the lower-cased email address. It never receives name, phone, company or message. (In this demo the AI is a recorded, pre-written reply list.)
* The desk has NO masking or redaction layer, NO encryption at rest, NO login. Data lives in one local database file; the desk listens on 127.0.0.1 only; the portal reads it through a separate read-only connection; Host and Origin checks refuse other web pages. We therefore say exactly that, and NOT "personal data is secure" or "encrypted" or "compliant".
* Request history: the lead book keeps one row per request (receipts: request id, door, outcome, times). A replay of the same request id adds no row. There is no per-lead event history table. The log below is built from receipts and says so.
* All data in the demo is made up.

### 1.2 Request log (new, read-only, from receipts)
Table, newest first, 100 rows with "Load more": Time, Request (short id, full id on hover/copy), Door, Result (New lead / Repeat, no second lead / Needs review / Not decided yet), Lead, Follow-up (current state). Filter: result. Caption: "Every request the desk received. The same request sent again is answered 'seen before' and is not added again." Honest note: "This is the desk's request record, not a full audit log: it keeps the latest follow-up state, not every step." No personal details beyond the lead's display name; no email, phone or message in the log.
Endpoint: `GET /api/ui/log?limit=100&before=<received_at>:<receipt_id>` -> `{"items":[{"request_id":"...","received_at":1794...,"door":"web_form|email_message","result":"new|duplicate|review|open","lead_id":"...|null","lead_name":"...|null","followup_state":"pending|sending|sent|failed|unknown|null"}],"next":"<cursor>|null","total":N}`; same one-read-transaction rule as /summary, caps in constants.py, keyset on (received_at, receipt_id), 400 bad_query on a bad cursor/limit.

### 1.3 Data and AI (new page, static facts built from code so they cannot drift)
Three blocks. (a) "What the AI step can read": lists exactly the inputs ("Lead id", "Email address (lower case)") with a "Never given to the AI: name, phone, company, message" list; line "In this demo the AI is a recorded list of pre-written answers: no live AI is called". Live "AI calls since the desk started: N" is added by the demo extension (not product). (b) "What the desk stores and where": table of stored fields (name, email, phone, company, message, request id, door, times, follow-up state, AI label) with "Stored in: the desk's local database file", purpose; "Leaves this computer: nothing (the desk talks only to the mail system and CRM it is configured for, here simulated)". (c) "How access is limited": desk listens on this computer only; this portal reads through a read-only connection and cannot change data; other web pages are refused (host and origin check); no login in this demo ("Not in this demo: login, encryption of the file, masking: a client build adds them"). Display-only "Hide personal details on screen" switch (masks email/phone in tables and drawer; label says "display only; the data stays stored").
Endpoint: `GET /api/ui/data-map` -> `{"ai_step":{"receives":["lead_id","email_key"],"never_receives":["name","phone","company","message"],"mode":"recorded|live"},"stored":[{"field":"email","where":"lead book","purpose":"identify the lead"}],"access":{"bind":"127.0.0.1","portal_read_only":true,"host_check":true,"origin_check":true,"login":false,"encryption_at_rest":false,"masking":false}}`. `receives` is derived with `inspect.signature(Qualifier.qualify)` at call time (excluding self) and `never_receives` is the set of lead fields minus those that appear in `receives`: a test fails if the signature gains a parameter that is not documented, so the page cannot lie. `bind`/`host_check` come from Config. `mode` comes from the loaded qualifier class attribute (recorded for RecordedQualifier).
