# What n8n does and what the desk does (one page, plain words)
Written 08:03Z by the demo cloud session for the lead. Basis: the NEEDED-CHECK verdict named in the lead's order (n8n is the one base and front door; the desk keeps the guarantee steps), plus my own measured numbers. The n8n numbers are from n8n 2.46.6 self-hosted on one Linux cloud machine, made-up data (the published figures quoted next to them are the author's own earlier laptop run). The two desk crash rows are from the desk run on the same machine, not from n8n. Make was never tested. "Measured" means I ran it; the n8n rows are in `n8n-rerun/` and `N8N-RERUN-1.md`, the desk crash logs in `n8n-rerun/D2-scene-*`. "Stated" means it comes from the lead's order or the repo text and I did not test it here. Runs are named R2 (one full run on one n8n), R2b (variance runs on one n8n), R2c and R2d (each test on a freshly built n8n); a burst is one ten-at-once send; a kill run stops n8n in the middle of a flow and starts it again.

## Words
- **Variants** (tests of the same flow with the duplicate check done in different places; each is only a label here): **a** n8n's own default duplicate-removal node; **b** a database insert that ignores repeats; **c** a data-table upsert; **d** variant a limited to one execution at a time; **e** variant b plus a status column and a re-send job. **CRM**: the customer-record system. **Counts page**: the desk's page of totals.
- **n8n**: the workflow tool where each step is a box. **Desk**: our small program (`src/lead_desk`) that sits behind it. **Fresh stack**: a newly built n8n plus database used for one test. **Reused stack**: one n8n that ran many tests in a row. **Keyed**: a mail system or CRM that recognises the same send key twice and acts once (the desk's "keyed claim" below is a different thing: it uses such a key). **Blind**: one that does not. **UNKNOWN**: with a blind mail system, when the desk cannot tell whether an email left, it does not guess, does not resend, and marks the follow-up for a person (with a keyed mail system an unclear end is retried with the same key instead). **Ten at once**: ten identical lead submissions sent together.

## What n8n owns in the demo (stated)
Intake (form, e-mail, webhook), field mapping, the ten-at-once trigger, alerts, and plain sends in client builds. These are the flow stages and credentials; they stay in the no-code tool so a client can change them.

## What the desk owns, and why (stated, with what I measured)
The desk keeps the steps where a wrong answer costs money or trust: a receipt written before anything else happens, a keyed claim (a send key, so a repeated send is recognised by a keyed mail system), ambiguous sends marked for a person, approval of changed repeats, a spend limit for the model, hiding of personal data in logs, and a count that does not depend on n8n. I did not test the spend limit or the hiding of data. I found no "redact" word in the code under `src/` by a text search; the lead should check that label before it is used. Plain claim, not stronger: in the repo's tests, with its stand-in mail and CRM programs, the desk never sent a second e-mail by itself; the repo explicitly does not claim exactly-once delivery or "never twice" in general. Cases where it cannot protect: with a blind mail system a stop at D1b gives no e-mail and UNKNOWN; with a blind CRM a stop at C0 gives no CRM row, no e-mail and UNKNOWN; with a keyed mail system a repeat is safe only if that mail system honours the key.

## What follows, facts only
- n8n's default duplicate node let duplicates through at ten-at-once on a reused stack in my runs; the first burst on a fresh stack was clean 12 of 12 (counting the first bursts of R2 and R2b), but later bursts on fresh stacks also had duplicates (R2d: 2 of 10), and no significance is claimed. The cause is NOT established. So a claim "n8n alone is enough" cannot be made from these numbers, and neither can "n8n is broken": three alternatives (b, c, d) that put the one-time check in a database gave 20 of 20.
- The desk's two D2 rows are one run each. Their outcomes (keyed one e-mail; blind one e-mail and UNKNOWN) match the table in `docs/tests.md`; `contract.md` and `docs/limits.md` also report a real process kill at D2 in the repo's own tests (keyed and blind, and a third with a real mail catcher). The `sent` state, the counts-page number and exit code 137 in my rows are my own observations.
- Not tested: Make; any n8n version other than 2.46.6; n8n cloud; n8n in queue mode.
