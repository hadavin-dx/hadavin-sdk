## 3. R1 root cause (reproduced and proven for the 401 flake; NOT for the two closed-port tests)
Method: copy of b29bb1f + the new CI patch (`_local\scratch\dpld-r1-orig`), five port-heavy test files (`test_crm_hubspot, test_smtp_provider, test_smtp_outbox, test_http, test_infra`), `-n 3 --dist loadgroup`, 4 busy-loop CPU burners, heavy_slot 2 slots, private temp (`raw4\r1\stress.sh`).
* Original tests, 12 runs (`raw4\r1\orig.summary`): 11 clean (197 passed), 1 failed: `test_crm_hubspot.py::test_4xx_is_refused_and_stored_nothing[unauthorized]` with `CrmError: ConnectionAbortedError` (`raw4\r1\orig-2.txt`). Closed-port tests: 0 of 12 failed.
* Why the freed-port theory is weak on Windows: Windows hands out ephemeral ports in sequence. Measured (`_local\scratch\portreuse.py`): a freed port was handed to the very next `bind(0)` in 0 of 300 tries, and was not handed out again within 200 more binds. Another worker would have to wrap the whole 16k range inside the test's few milliseconds.
* PROVEN cause of the observed flake: `demo_only/fake_hubspot.py` answers a rejected call (`_gate` 401, also 404 and other early answers) and closes the connection (`Connection: close`) without reading the request body. http.client sends the headers and the body as separate writes, so the body can arrive after the fake has closed; the system then resets the connection and the client's unread answer is thrown away (Windows: WinError 10053). It is timing, worst under load; it also explains the earlier `test_key_is_read_at_call_time` ConnectionAbortedError. Deterministic probe (`_local\scratch\rstprobe.py`: headers first, body 0.3 s later): old fake loses the answer 30 of 30, fixed fake 0 of 30.
* Fix (a patch, not an edit of a public repo): `runbook-files\fake-hubspot-read-body-before-answer.patch`: `_send` reads the unread body before it answers (flag set by `_json`); one new regression test `test_a_rejected_call_still_gets_its_answer_when_the_body_arrives_after_the_close` (sends the body late on purpose). No test is weakened and no retry exists. Test result: with the OLD fake the new test FAILS, with the fixed fake it passes (1.3 s each).
* Closed-port tests: left exactly as in b29bb1f. A 3-try retry that passes on any raise (old patch) is not used. If the cloud window sees either fail, hand it back.
* Proof on the fixed tree (`_local\scratch\dpld-r1` = b29bb1f + CI patch + the fake-hubspot patch), `raw4\r1\fixed.summary`: 30 of 30 runs passed (118 tests each: `test_crm_hubspot.py` + `test_smtp_provider.py`, `-n 3 --dist loadgroup`, 4 CPU burners, 55-60 s per run; includes the closed-port tests unchanged and the new regression test). Honest limits: the proof uses 2 files, not the 5 of the failing original run (the original failed 1 of 12 = 8 percent, so 30 clean runs make a rate that high unlikely, about 0.92^30 = 8 percent chance of 30 clean if the flake were still 8 percent: NOT conclusive on its own; the deterministic probe 30/30 lost vs 0/30 lost and the new test failing on old code are the real proof). The full 2391-test suite was not re-run on the fixed tree in this phase. Windows only; the same race exists on Linux in theory but was not measured there.
* Class sweep not done: other fake servers in `demo_only\` (smtp, imap, model server) may answer before reading a request body; `tests\support.py::free_port()` (bind 0, close, return) is used 46 times and has the same "freed port" shape, but no failure from it was seen. Listed for the lead; not fixed.
