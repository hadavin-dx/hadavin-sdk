# Film variant of Design A (lease 45 s, stage and CRM 10 s x 2 tries). Same flows as ../n8n-flows/ otherwise; built by the same script.
Build: `MF_TRIES=2 MF_TMO_MS=10000 python n8n-mainframe/build_mainframe.py OUT PG_CRED_ID SMTP_CRED_ID SUB_WORKFLOW_ID 45` (placeholder ids in the pushed files). The tests accept the same two variables: `MF_TRIES=2 MF_TMO_MS=10000 python run_chain.py ... --lease 45` (run_chain passes --lease; export the two variables before it).
Edits against the design flows: stage call and CRM call each 2 tries (was 3) with a 10 s node timeout (was 15 s), 1 s between tries; lease 45 s (was 120 s). Nothing else.
## Worst normal run, arithmetic (NOT measured)
stage 2 x 10 s + 1 s = 21 s; CRM 2 x 10 s + 1 s = 21 s; database steps and mail a few seconds; SMTP node has NO timeout setting (a slow server holds it). Sum without the SMTP hold: about 42 s + a few s = 45 s or more. So a 45 s lease is MARGINAL: a worst-case live run can outlast it, and recovery would then take the lead (safe, but state unknown with 1 alert, see T10). A lease of 60 s covers that worst case with margin for a normal SMTP answer; a stalled SMTP server still exceeds any lease. If the film shows a kill and the recovery, the normal run (a few seconds) is far below 45 s, so 45 s is fine for a filmed happy path; do not claim it is safe for the worst case.
