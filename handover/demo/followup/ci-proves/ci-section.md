## What each check on main proves and does not prove

Read from the repository files at main commit 61ded9e (the three workflow files, `pyproject.toml`, `sonar-project.properties`, the review-service settings files). Nothing here comes from a GitHub setting, a run log or a timing: this repository has no file that shows branch protection, so "needed to merge" is not shown by the repo files for every check below. **The Semgrep workflow (pull request 13) and the job that runs the tests in a copy without `demo_only/` (the "nodemo" job) are open pull requests. They are not on main and are not described as checks here.** Every workflow runs on a GitHub-hosted Linux runner (`ubuntu-24.04`); no workflow on main uses a Windows runner.

| Check | Runs when | Needed to merge? |
|---|---|---|
| lint job (`.github/workflows/lint.yml`, all steps below) | pull request to main, push to main | not shown by the repo files |
| SonarQube Cloud analysis (`.github/workflows/sonar.yml`) | push to main; pull request opened, updated or reopened, but skipped for a pull request from a fork or from Dependabot | not shown by the repo files |
| CodeQL (`.github/workflows/codeql.yml`) | pull request to main, push to main, and a weekly schedule | not shown by the repo files |
| Dependabot (`.github/dependabot.yml`) | weekly | not shown by the repo files (it opens update pull requests; it is not a pass or fail check) |
| CodeRabbit, CodeAnt, DeepSource | pull requests, if the owner has switched the service on | not shown by the repo files; whether a service is switched on is not shown either |

**The lint job** installs the gitleaks release binary (version 8.30.1, its checksum is compared before use) and the pinned development tools (`--require-hashes --only-binary=:all:`), in this order. Each step below fails the job when it fails; one red step means the job is red.

* **Gitleaks on the tree and on the history.** Runs `gitleaks dir .` and `gitleaks git .` with the repository's `.gitleaks.toml`, `--redact` and `--ignore-gitleaks-allow`. Green proves: no text in the checked-out files or in the history that the checkout holds matches this repository's rules (long hex values, addresses, links, absolute paths and similar), after the allowances written in `.gitleaks.toml`. The checkout is full-depth (`fetch-depth: 0`). It does NOT prove: that no secret exists; only the shapes these rules describe are seen, and secrets of any other shape pass. Which branches the history step reads is not stated in a repository file, so it is not claimed here. Red: the output names the file and rule; remove the value (a leaked real value must also be revoked), or, for a harmless one, add the narrowest exact allowance and keep `tests/test_gitleaks_exceptions.py` passing.
* **Ruff** (`ruff check .` and `ruff format --check .`). Green proves: the code follows the rule families set in `pyproject.toml` (E, F, W, I, S and PLR2004) and the format. It does NOT prove the code is correct, and it is not a security review beyond the S rules. Red: run `ruff check .` and `ruff format .` locally.
* **Mypy** (`mypy --platform linux` and `mypy --platform win32`). Green proves: the folders `src`, `tools` and `scripts/hubspot_probe.py` pass strict type checking, once for each of the two platform branches of the code. It does NOT prove the program runs on Windows (nothing runs there), and it does not check `tests/` or `demo_only/`. Red: fix the type named in the output.
* **Bandit** (`bandit -ll -r src tools scripts`). Green proves: no finding of medium or high severity in those three folders. It does NOT look at `tests/` or `demo_only/`, and it does not report low severity. Red: fix the finding.
* **Schema check** (`python scripts/check_schema.py`). Green proves: the database schema file loads into SQLite and each trigger and constraint it fires once behaves as the script expects. It does NOT prove anything about the application code. Red: the output lists the failed check.
* **Hardcoded-literal scan** (`git grep` with `patterns.txt`, minus the lines matched by `exceptions.txt`). Green proves: every tracked line that looks like an IP address, a link, a host name with a common ending, an absolute path, an e-mail address, a long hex value or any run of 40 or more letters, digits and dashes is listed in `exceptions.txt`. It does NOT prove the exceptions are all harmless (each one is a decision), and it does not see shapes the nine patterns do not describe. Red: the output lists `path:line:match`; rewrite the text (describe it in words or build it from parts) before adding an exception.
* **Canary guard.** Fails if the text `def test_hygiene_scan_public` is not found under `tests/`. Green proves only that this test function still exists; the next step runs it.
* **Tests** (`python -m pytest -q`, with `DPLD_REQUIRE_SCAN=1`, `DPLD_REQUIRE_DEMO=1` and the path of the gitleaks binary). Green proves: the tests that were collected passed on Linux with the `demo_only/` folder present (a missing folder or a missing gitleaks program stops the run instead of skipping). That includes `tests/test_hygiene.py`, whose scanner tests plant a canary for each rule and run gitleaks on tree and history, and whose `test_workflows_are_pinned_and_limited` fails when a workflow uses an Action that is not pinned by a full commit id, lacks a read-only top-level `permissions:` block, or uses a `pull_request_target` or `workflow_run` trigger. It does NOT prove: that the browser tests ran (the job installs only `requirements-dev.txt`, which holds no Playwright, so those tests are skipped; see "Browser tests" above); that the tests that need Node ran (they skip when `node` is missing; whether the runner has it is not shown by a repository file); anything about Windows; or anything about a copy of the repository without `demo_only/`, because the job refuses to run without it. The tests use the made-up data and the local fakes in `demo_only/`; no repository file makes a check fail on a real network call, so "no real vendor, mail or CRM call is made" rests on how the tests are written and on the review instruction in `.codeant/instructions.json`, not on a blocking check. Red: run the failing test alone (`python -m pytest -q path::name`); read the skip reasons with `-rs`.

**SonarQube Cloud analysis.** Runs `python -m pytest -q --cov --cov-report=xml:coverage.xml` with the demo present, then the SonarQube scan with the repository secret `SONAR_TOKEN`, using `sonar-project.properties`. Green (the job) proves: the tests passed, the scan ran and sent its results, including the coverage file, to SonarQube Cloud. The workflow itself does not wait for or print the quality gate; the gate result and its conditions are shown in and set in SonarQube Cloud, and no file here states them. The coverage figure is the share of lines executed during this one CI test run: it does NOT prove the behaviour is checked, only that the lines ran. Per `pyproject.toml`, `tests/` and `demo_only/` are left out of the figure, and code that only a separate process runs (a test starts the desk as its own process) is not measured. The browser tests are skipped here too. A pull request from a fork or from Dependabot gets no analysis at all (the job is skipped). Red: open the SonarQube Cloud report the check links to; for a failed test step, treat it like the Tests step above.

**CodeQL.** The workflow analyzes `python`, `actions` and `javascript-typescript` without a build (`build-mode: none`) and uploads the results to GitHub code scanning. No query suite is named in the file, so the tool's default applies; the file does not say which that is. Green proves: the analysis ran for the three languages. It does NOT prove there is no vulnerability; the alerts live in GitHub code scanning, and whether an open alert blocks a merge is not shown by a repository file. The `actions` language reads the workflow files themselves. Red: read the alert in the code scanning view.

**Dependabot.** Version updates for GitHub Actions only, weekly. It does not cover the Python lock files; the file says the development tools are pinned by hand. It proves nothing about the current state of any pin.

**Review services (settings files only).** `.coderabbit.yaml` asks CodeRabbit to review pull requests to main (profile "assertive", with actionlint, zizmor, gitleaks and ruff switched on, and all its write-to-branch features switched off). `.codeant/configuration.json` asks CodeAnt for code, secret and dependency analysis and skips the lock files and `demo_only/`; `.codeant/instructions.json` gives it two review instructions. `.deepsource.toml` sets Python and JavaScript analyzers and the test file patterns. These are advice for a reviewer, not tests; this repository does not show whether they are installed or what they found.

**Not run by any check on main:** Windows (no Windows runner; the Windows lock files are not installed by any workflow); the browser tests; a copy of the repository without `demo_only/` (the "nodemo" job is an open pull request); the full demo with real services; the Semgrep scan (open pull request 13). **Time limits** are ceilings set in the files (lint 60 minutes, SonarQube 60, CodeQL 30), not measured run times.
