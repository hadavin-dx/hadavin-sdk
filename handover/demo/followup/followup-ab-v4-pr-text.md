## What this change does and what it does not do

Plain words first: this is a set of small fixes and tests that follow PR #4. Each guard below lists what it catches and what it does not.

**Path checks for tool options.** The fake model server now checks `--key-file`, `--call-log` and `--control-file` like the load tools check their paths: the file must lie in the folder you started in, the repository, the temporary folder, or a folder listed in `LEAD_DESK_PATH_ROOTS`. A path outside these, which worked before, is now refused with a message and the server does not start. `LEAD_DESK_PATH_ROOTS=/` allows every file; that is what the variable is for.

**Test that lists the known places (not a proof).** `test_each_known_site_still_uses_the_path_helper` reads the source files as plain text and checks that each listed function still contains its helper call. It is a list of the known sites, not a proof that no site is missing. It catches a listed call that is deleted or a function that is renamed. It does not catch a raw open added in a place that is not on the list, a comment that keeps the call text, or a call moved to the end of the last function of a file. The behaviour tests (start the tool with a path outside the allowed folders and see the refusal) are the real check. An earlier attempt at a code-analysis test was removed because it could not be made reliable.

**Windows network paths and books (text level only).** `--book` refuses a Windows network or device path (`\\server\share\...`, `//server/share/...`, mixed slashes, `\\?\...`, `\\.\...`, the NT form `\??\...`), empty text, and text with a control character. SQLite takes only an empty or `localhost` name after `file://`, so such a path could never be opened; the refusal is now a clear input error instead of a traceback. This was checked on Linux with Python's `ntpath` module that models Windows path text. It was NOT run on Windows, and SQLite on Windows was not run. On Linux and macOS nothing else changes: the same paths build the same text as before.

**Another project's `tools` package.** `load_tools/load_driver.py`, `check_invariants.py` and `catcher.py` notice a foreign `tools` package that has none of the path-helper names, drop it, and use this repository's. They do NOT notice a foreign `tools.pathconfine` that has the same names: it is used as it is. `tools/scrub_n8n_export.py`, `scripts/n8n_api.py` and `demo_only/fake_model_server.py` do not handle a foreign `tools` at all: with one first on the path they stop with a Python traceback. Run them from the repository folder and keep another project's `tools` off `PYTHONPATH`. In `scripts/n8n_api.py`, the order "src before the repository folder" holds only when neither folder is already on `PYTHONPATH`.

**Hard links.** A hard link is a second name for the same file contents. A hard link made inside an allowed folder to a file outside it passes the check, and reading or writing it reads or changes the outside file. Only someone who can write in an allowed folder can make one. This is documented, and a test pins it; it is not fixed.

**Tests.** Tests for the new behaviour fail on the old code where they test behaviour: of the new and changed test ids in `test_path_confinement.py`, `test_followup_b.py` and `test_sonar_p2_choke_points.py`, 69 of 111 new ids and 1 changed existing test fail on main 61ded9e. The other new ids pass on old code by nature (the list of known sites, import checks, one test that records current hard-link behaviour, one that pins the unchanged Linux output, and 11 that are an existing test renamed). A test of the same-process fallback for a foreign `tools` package covers the import blocks that only a subprocess test reached before (coverage on the new lines of the touched files: 66 of 66 in the tests measured). The "client copy without demo_only" job was run on this tree and is green (888 passed, 87 skipped, none unexplained).

**Not checked.** Windows itself, macOS, the full suite in this write-up, and Sonar's final numbers.
