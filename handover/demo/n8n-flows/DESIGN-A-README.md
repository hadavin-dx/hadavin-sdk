# Design A (n8n is the main frame): flows, table, stand-ins (no results, no numbers in this file)

Status: current version v2 (order D-N2a). Built from scratch for n8n 2.46.6. Credentials by NAME only; ids in the JSON are placeholders (PG_CREDENTIAL_ID, SMTP_CREDENTIAL_ID, SUB_WORKFLOW_ID) that a deploy step replaces. The earlier version (updated_at rule) is kept in v1-superseded/ for the compare only.

## Files here
- mf-sub-crm-mail.json : the ONE sub-workflow (Execute Workflow) used by the main flows and by recovery: cap stage, CRM create-or-update, mail.
- mf-form.json, mf-hook.json : main flows (form entry, e-mail-style webhook entry). Webhook paths mf-form and mf-hook, Respond to Webhook.
- mf-recovery.json : recovery every 30 s (lease claim) plus the failed-lead alert.
- mf_leads.sql : the lead table.
- Build script: ../n8n-mainframe/build_mainframe.py (args: out dir, postgres credential id, smtp credential id, sub-workflow id, lease seconds). This copy was built with lease 120.

## Flow, step by step
Main: Webhook -> Edit Fields (lead_key, email, name) -> Valid (e-mail pattern) -> Postgres Claim: INSERT ... ON CONFLICT (lead_key) DO NOTHING RETURNING (state processing, claimed_until = now + lease, claim_token = new random id, attempts 1; an invalid e-mail is stored as state review with attempts 0) -> IF row came back: IF processing: Execute Workflow (sub) then Respond with verdict; IF review: Respond review. No row (a repeat): Postgres SELECT state, Respond with the stored state mapped to a verdict.
Verdict values: new (this run finished it), processing (a duplicate while another run works, or the stage failed so recovery will retry), done, review, unknown, failed.
Sub-workflow: Qualify (HTTP Request to the cap stage, retry 3, error output) -> IF label is hot/warm/cold and not unknown_model (else NO CRM write and NO mail: fail closed) -> CRM create-or-update (HTTP Request, keyed on the lead id property and the e-mail) -> Postgres SetCrmId (conditional on claim_token and state processing) -> Postgres MailClaim: UPDATE mail_sent = true WHERE mail_sent = false AND claim_token matches RETURNING -> IF a row came back: Send Email node (Retry On Fail OFF, On Error = continue with error output) -> success: state done (conditional); error output: state unknown + one alert. If no row came back (mail_sent already true): state unknown + one alert (never a resend). Every update is conditional on the claim token, so a run that lost its lease changes nothing (outcome lost_claim, verdict processing).
Recovery (fixed 2026 11 14, finding F-REC-EMPTY from lane3: the Postgres node returns ONE item {success: true} when an UPDATE ... RETURNING matches no row, so an idle recovery run used to start the sub-workflow and an alert; now an IF (StuckRow, FailedRow: lead_key not empty) sits in front of RunSub and AlertFailed): Schedule 30 s -> ONE Postgres statement claims up to 5 rows: state not in (done, review, unknown, failed) AND claimed_until < now() AND attempts < 3, ORDER BY created_at, FOR UPDATE SKIP LOCKED, sets a new lease and token, attempts + 1, RETURNING -> same sub-workflow. Second branch from the same trigger: rows with attempts >= 3 and an expired lease -> state failed + one alert (the row can only be returned once).
Constants in the nodes (no expression): mail recipient intake at example.test, alert recipient alerts at example.test. Mail subject: [demo] lead <lead id>. The Send Email node cannot set a custom header, so the lead id token in the subject is the count key.

## Lease
Design value: 120 seconds. Reason: it must be longer than the longest normal run (cap stage up to 3 tries of 15 s, CRM up to 3 tries of 15 s, mail up to a few seconds), so recovery never takes a lead that a live run still holds. In the tests a shorter lease (20 s) is used so recovery fits inside a test run; a lease SHORTER than a slow mail step gives a safe but unneeded state unknown (found in test T10: recovery took the lead while the first run still waited for the SMTP answer, saw mail_sent already set and marked it unknown, 1 mail, 1 alert, nothing doubled).

## n8n environment the flows read
MF_CRM_URL (base address of the CRM), MF_STAGE_URL (base address of the cap + model stage), MF_STAGE_TIMEOUT_MS (optional, default 15000); environment access in nodes must be allowed (N8N_BLOCK_ENV_ACCESS_IN_NODE=false in 2.46.6). Credentials by name: n8n-publish-pg (Postgres), mf-mail-smtp (SMTP). Execution saving off for success and error runs in the workflow settings.

## Stand-ins (all in ../n8n-mainframe/ and ../n8n-tests/; made-up data, loopback only)
- crm_stub.py PORT LOGFILE : POST /upsert (hadavin_lead_id, email, label) create-or-update keyed on lead id AND e-mail; POST /search (lead_key); POST /create; GET /rows; POST /control with one-shot or timed faults: upsert_delay_ms (hold BEFORE storing), upsert_ack_delay_ms (store first, answer late), search_blind_s (search answers empty for N s after a write), search_delay_ms, create_ack_delay_ms. Every request is logged (upsert_start, upsert with created true/false).
- ../n8n-tests/smtp_catcher.py PORT FILE : plain SMTP, one JSON line per mail in FILE (envelope recipients, subject, header names). Control files next to FILE: .delay (seconds to wait after storing, before the acknowledgement), .pre (seconds before the greeting), .drop (number of mails to accept and then drop the connection without acknowledgement); FILE.conn has one line per connection (counts SMTP node executions).
- stage_server.py PORT JOURNAL MAILFILE (needs the desk checkout and its live-model settings in the environment): POST /qualify (lead_key, email) calls the desk's own LiveQualifier and SpendLedger (reserve before, settle after, caps); a per-lead journal means a re-run never calls the model twice, and a lead with a started call and no answer returns label unknown (no second call). POST /control (mode ok, refuse, error, timeout; sleep) switches the cap stage fault modes. GET /mail_count (second count from the mail stand-in file; NOT called from inside the flow).
- The desk has no endpoint for this stage today; stage_server.py is the small wrapper (about 45 lines, desk source untouched). For the real take the desk needs one endpoint: qualify (lead id in, label out, journal, unknown on a started-but-unanswered call).

## Counting rule for a kill script
Count OUTSIDE n8n after each run: expected set (lead ids sent) against observed sets from the mail stand-in file (subject starts with [demo] lead), the CRM stand-in rows and the model call log; extras are failures. Final states to expect: done (1 CRM row, 1 mail), unknown (mail may or may not be delivered, a person decides, 1 alert), failed (after 3 tries, 1 alert), review (invalid e-mail). Lost = no final state in time, or done without its CRM row or mail. Doubled = more than 1 CRM row, mail, model call or alert per lead id.

## Change 2026-11-14 (lane3 finding, CRM refuses every call: lead stayed processing, no failed state, no alert)
Cause (read from the flow, not yet proven by a run): in mf-recovery both branches start from one timer and n8n runs them one after the other; an error in the first branch (RunSub failing, first through the phantom empty-claim item, and in general whenever a re-run of a real lead errors) ended the execution before MarkFailed / AlertFailed ran. The F-REC-EMPTY guard alone does not remove this: a real lead whose re-run errors in every cycle can still starve the failure branch.
Now: (1) MarkFailed branch runs FIRST in the timer's connection order; (2) ClaimStuck, RunSub (recovery), MarkFailed and AlertFailed are set to continue on error, so one branch's error cannot stop the other; (3) in the sub-workflow the CRM call has an error output (after its 3 tries) that goes to the same stage_failed outcome as the cap stage, so the main run answers verdict processing instead of HTTP 500 and the row waits for recovery. Test T15 (mf.py): CRM refuses every call from the start; pass = state failed, exactly 1 alert naming the lead, 0 mails to the intake recipient, 0 CRM rows, within 3 x lease + 150 s (about 3 x 120 + 150 s with the design lease).
