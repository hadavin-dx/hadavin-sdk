# CONTRACT-DELTA (cloud fix 1, ORDER 200) - text for the lead to paste into contract.md / README.md

## New or changed rows
- POST /leads, `source_ref` with a control character (NUL included), outside 1..128 characters, or a lone surrogate, and an unknown `source` (when reaching `Desk.process`): 400 `{"error":"bad_envelope","receipt_id":null}`, no receipt, counted in `rejected_envelopes`. (server.py already does the length check; the desk now repeats it and adds the control-character rule.)
- Verdict `review`, reason `bad_field:<field>` now also for any control character (Unicode category Cc, NUL included) in name, email, phone, company; and in message except tab, line feed, carriage return. Reason `internal_unstorable` (new): a payload that passed every check but was still refused by the database (integrity, value or overflow error that is not a lock) gets verdict review instead of a 500 and an open receipt.
- POST /leads: 503 `{"error":"busy","receipt_id":null}` is also answered when 32 requests are already inside the desk and no place frees up within 5 s. No receipt is written in that case, so the client can send the same request again safely.
- Follow-up send results: a reply that came back with the wrong mode is now `unknown` / `mode_mismatch` (was `failed`). A refused or unreachable sender (nothing sent), an unclear end on a KEYED sender (sending again is safe), a CRM that failed, or an AI step that failed puts the follow-up back to `pending` (last_error `refused` / `unreachable` / `ambiguous` / `internal:<class>`, `attempts` counts the tries) and the reaper tries again after 1, 2, 4, 8 s; after 5 tries in all it becomes `failed`. Only an unclear end on a BLIND sender goes to `unknown` at once (the email may have left; a person decides). A person's Retry starts the count again (try 1): if the sender refuses once more the follow-up is `pending` again (backoff running), not `failed`.
- POST /review/{id}/retry: never 200 with state `sending`; if the result could not be recorded: 409 `{"error":"in_progress"}`.
- GET /counts: new keys `failed_followups`, `unknown_followups`, `sending_followups` (integers). `pending_followups` keeps meaning pending + sending. `ok` is true only when open = 0, rejected_envelopes = 0, expected matches, pending_followups = 0, failed_followups = 0, unknown_followups = 0. `rejected_envelopes` is an in-memory counter of this process (resets at restart); say so in README.
- Review list: a request id that comes again with a different payload keeps its first answer (`payload_matches:false`) and adds a D item `D<receipt_id>`, kind `replay_payload_differs`, reason `same request id, different payload`, informational (retry/resolve answer 409 not_actionable). If the receipt is also a duplicate-with-new-info, there is still ONE D item (kind `duplicate_with_new_info`).
- Email: an apostrophe is allowed before the @ (o'brien@example.test); every other exclusion stays.
- Start-up: `Desk.startup()` raises RuntimeError when called twice or after the desk served/drove anything. With `start_background()` called first, start-up no longer drives pending follow-ups (the reaper does), so serving starts at once.
- Schema (user_version stays 1): receipts.payload_conflict, followups.crm_done, followups.auto_attempts, followups.ambiguous_prior; view review_items changed; two partial indexes (`receipts_open_ix` on open receipts, `followups_active_ix` on pending/sending follow-ups). A lead book made by the first release gets the four columns, their backfills, the view and the indexes in ONE transaction at start-up (db._migrate): a crash in the middle changes nothing, and a book that has the columns but lost the view or an index is repaired at the next start. Backfills: `crm_done=1` for every row (not `sent`) with attempts > 0 and a label (the first release asked the CRM before the first send, so a blind CRM is not asked again); `ambiguous_prior=1` for a `pending` row whose last_error is `crash_while_sending`.
- CRM: the CRM put runs only after a won claim. `followups.crm_done` is an intent mark: 0 not asked, 2 a put was started (written BEFORE the put, together with a fresh `updated_at`), 1 the put came back. A leftover 2 (the desk died, or the write of 1 failed) means the put may have reached the CRM. A CRM that is keyed (a `capability` attribute equal to `keyed`) is simply asked again (harmless). Any other CRM, and a CRM with no `capability` attribute (the desk cannot know), is not asked again: the follow-up becomes `unknown`, last_error `crm_unconfirmed`, and a person looks in the CRM. The same happens at once when a put of such a CRM ends unclear (timeout, reset, 5xx, odd answer). A put that provably stored nothing (the exception has `nothing_stored` true: refused with a 4xx answer, or not reached) resets the mark to 0 and the follow-up is tried again after the backoff. The person answers `not_sent` (resolve) and then Retry: `not_sent` clears the leftover mark and `ambiguous_prior`, so the next try asks the CRM again (check the CRM first: an extra row may need deleting by hand). The window that is left: none for a keyed CRM; for a CRM that is not keyed no second put is ever made without a person's decision. `HttpCrm` now has `capability` (the mode named in its last answer, `None` before the first answer, which counts as not keyed) and raises `CrmNothingStored` for the proven-nothing cases. The in-process demo `FakeCrm` has no `capability`; the lead can add `capability = "keyed"` to it in demo_only (not touched here) to get the harmless re-put in tests.
- Follow-up `ambiguous_prior` (new column): set when an email may have left (a start-up or reaper requeue of a `sending` row, an unclear end of a keyed send); a row with it is never sent by a BLIND sender: it becomes `unknown`, last_error `ambiguous_prior` (the reaper does this without a claim, `_send_claimed` does it as the last check before sending). Resolve `not_sent` clears it.
- Claims: `Desk._claim(conn, lead_id, from_states)`; run_followup, the reaper and the start-up sweep claim only `('pending',)`; only a person's Retry claims `('pending','failed')` (and starts the automatic count at 1). Any other state list raises ValueError.
- Stage times: `updated_at` of a `sending` row is moved to now before the CRM put (the intent mark) and before the send, so the reaper's 20 s counts from the last stage. If the row is no longer `sending` at that moment (the reaper took it back), the stage is not run.
- Reaper: reads the sender's capability again only when a `sending` row is stuck, after a wrong-mode reply, or at most every 30 s (`gate.OUTBOX_REFRESH_SECONDS`); no requeue decision is made when the capability could not be read (start-up leaves such rows `sending` for the reaper).
- Decision safety net: also RecursionError, `sqlite3.DataError`, a stored payload that is not readable JSON, and a lone surrogate (UnicodeError) give verdict `review` / `internal_unstorable`. A plain ValueError is no longer caught: it is a 500 `internal` and the receipt stays open (the reaper and a restart try again). A payload nested so deeply that it cannot be written down in `Desk.process` is 400 `bad_envelope` (counted in `rejected_envelopes`), as at the HTTP layer.
- Write gate: one per resolved lead-book path (`gate.gate_for`), so desks on different books do not wait for each other. It is not re-entrant: nothing may ask for it while holding it (`Desk._write` is never nested).
- `startup()` also refuses after a `retry`, `resolve` or `_claim` call.
- Journal mode: db.connect raises RuntimeError unless the file is in WAL mode (private :memory: exempt).
- Lock file: the db path is resolved first (symlinks); BlockingIOError = another desk; on Windows only EACCES (locking violation) and EDEADLK mean another desk; any other OSError, and a lock file that keeps being replaced (3 tries), = `LockUnavailableError` (could not be taken for another reason; still a refusal).

# CONTRACT-DELTA (cloud fix 5, review cloud-review-2) - changes on top of the text above

## Rows that change
- Migration backfill of `crm_done` REPLACES the rule written under "Schema" above (the old rule marked every tried row 1). New rule: a `sending` row gets 2 (a put may have started; the safe path decides); a row whose `last_error` starts with `internal:` (the CRM or AI step broke) keeps 0, so the next try asks the CRM; a `failed` row with a label and any other error gets 1 (the first release asked the CRM before it sent); any other row that was tried (`pending` or `unknown`, attempts > 0) gets 2. A `sent` row is never touched.
- Follow-up ownership: the claim's `attempts` value is the owner's token. Every write of the drive that won the claim (`crm_done` marks, the stage time `updated_at`, the send result) only matches `state='sending'` AND the same `attempts`. A drive that stalled and was put back by the reaper therefore changes nothing in a later drive's claim (no second CRM put, no overwritten result). `updated_at` is also moved right after the claim, BEFORE the AI step. Private function signatures changed (`_mark_crm`, `_touch`, `_record_send_result`, `_crm_step`, `_send_claimed` take the token); `_claim` still returns a bool.
- Receipt that cannot be decided (a plain error that is not a lock, not an "unstorable" error): after 3 failed tries in a row (counted per receipt in memory; a restart counts again from 0) it gets verdict `review`, reason `internal_error` (new). A database that stays locked is never counted. Contract text: add reason `internal_error` next to `internal_unstorable`.
- POST /review/{id}/resolve: new decision `crm_present`. It is accepted only for an `unknown` follow-up whose `last_error` is `crm_unconfirmed`; it sets `crm_done=1` and the state `failed` (last_error `person: crm row present`), so the person's Retry goes straight to the email without asking the CRM. `sent` is refused (409 `{"error":"wrong_decision","hint":...}`) for a `crm_unconfirmed` row, because no email was ever tried; `crm_present` for any other `unknown` row is also 409 `wrong_decision`. `not_sent` is unchanged (it clears the mark, so the CRM is asked again: check the CRM first). `bad_decision` (400) now means "not one of sent, not_sent, crm_present". Review-list hint text for a `crm_unconfirmed` item (the desk has no hint field for F items; put this text in contract.md / README): "The CRM may or may not hold this lead. Look in the CRM, then answer crm_present (the row is there) or not_sent (the row is not there). sent is refused: no email was tried."
- `HttpCrm.refresh()` (new) reads `crm_capability` from GET /fake/info; the desk calls it at start-up, whenever it reads the sender's mode again, and before it judges a leftover `crm_done=2`. `HttpOutbox` keeps capability and mode as ONE tuple (a reader never sees half a change). NOTE for the lead: `demo_only/fakes_server.py` `/fake/info` must also answer `"crm_capability": <crm mode>` (not touched here); until it does, refresh() raises, the cached value stays and `None` counts as not keyed (the safe side).
- `_pending_to_unknown` (reaper, sender became blind, `ambiguous_prior` row) sets `last_error='ambiguous_prior'`.
- A `sending` row that is put back (start-up or reaper) with `auto_attempts` already at the cap goes to `failed` (keyed sender; a person's Retry still works) instead of `pending`; a blind sender still gives `unknown`.
- Before a row with `ambiguous_prior=1` is sent, the sender's mode is read again (`_refresh_outbox`); if it is blind now the row becomes `unknown` / `ambiguous_prior`.
- A client replay of a `new` request drives the follow-up only if it is due: no automatic try yet, or its backoff is over. Replays can no longer use up the 5 tries.
- `crm_done=1` is written in a retried transaction. If it still cannot be written, the drive does NOT go on to the send: the row stays `sending`, and the reaper puts it back flagged `ambiguous_prior` (the leftover 2 then follows the keyed / not-keyed rule). Tests changed for this in fix5: `test_g2_blind_crm_not_asked_twice` and `test_g2_keyed_crm_may_be_asked_again` (tests/test_hardening_cloud_b.py) now expect the row to be `sending` right after the lost mark (not `pending`/`refused`) and run 3 and 4 reaper passes. `test_g2_unclear_put_on_blind_crm_is_unk` and `test_g2_person_can_go_on_after_not_sent` were NOT changed.
- The lead-book path is resolved once in `Desk.__init__` (`Desk._db_path`) and used for the connections and the write gate, so a later chdir cannot send a new thread to another file.
- Reaper pass: `gate.REAPER_DRIVE_BATCH` (20 follow-ups) is replaced by `gate.REAPER_PASS_SECONDS` (10 real seconds): the pass stops driving when the time is used up; the rest is still due and comes first next pass. New `gate.DECIDE_FAIL_LIMIT = 3`.

# CONTRACT-DELTA (cloud fix 7, review round 4: lenses 1 to 3, each finding checked against fix6 first) - changes on top of the text above

## Rows that change
- Backfill rule (fix 5/6, restated): the migration sets `crm_done` for a book of the first release as written in "fix 5" above. The new column `send_started` is backfilled to 1 for a `sending` row with `crm_done=1` (it may have sent: the safe side) and stays 0 elsewhere.
- Fix 6 M1 (kept): a `sending` row whose CRM step is not finished (`crm_done` not 1) never reached the send; at a requeue it goes to `pending` (or `failed` at the cap) whatever the sender's mode, and the CRM rule decides at the next drive.
- Hint key: a 409 `wrong_decision` and a review item of kind `unknown` carry a `hint` key (a plain sentence). Fix 7 adds a second sentence for an unknown row whose CRM step is finished: "The CRM row is already done; what is unclear is the email ... crm_present is refused here."
- Busy receipts (fix 6, kept): a 503 `busy` that comes after the receipt was written leaves it open; the reaper decides it at its next pass (it does not wait for `stall_seconds`). The client may send the same request id again (a replay of the open receipt).
- NEW COLUMN `followups.send_started` (INTEGER NOT NULL DEFAULT 0; user_version stays 1; added in the same one-transaction migration, with its backfill). It is the intent mark of the send: every claim clears it, and the same UPDATE that moves `updated_at` just before `outbox.send` sets it. A `sending` row with `send_started=0` never sent anything, so a requeue (start-up or reaper) puts it back to `pending` (`failed` at the cap) on a BLIND sender too (before: `unknown`); `ambiguous_prior` is set only for a row with `crm_done=1` AND `send_started=1`. If the mark cannot be written (a lock), nothing is sent. A requeue also no longer needs the sender's mode for such rows: with the mode unread, only rows that may have sent wait for the read.
- POST /review/{id}/resolve: `sent` is accepted only for an `unknown` row with `crm_done=1` (409 `wrong_decision` otherwise: no email was ever tried); `crm_present` is accepted for an `unknown` row with `crm_done=2` whatever its `last_error` (before: only `crm_unconfirmed`). `not_sent` is unchanged (clears `crm_done=2` only for `crm_unconfirmed`).
- Ambiguous row (`ambiguous_prior=1`): the sender's mode is read again before the send; if it cannot be read, nothing is sent and the row goes back to `pending` (`unreachable`, one automatic try).
- An error BEFORE the send (reading the row, the mode read, the intent mark) is no longer taken for an unclear send: it counts as one automatic try (`internal:<class>`, row `pending`); a lock only gives the try back. Only `outbox.send` itself decides `ambiguous`.
- A lock inside the steps after the claim (the AI step, the CRM mark) is not an error of the follow-up: the claimed try is given back (`auto_attempts` minus 1, row `pending`, no `last_error`). If even that write is locked, the row stays `sending` and the reaper puts it back. Nothing `internal:OperationalError` is recorded any more.
- `_touch` (stage time) answers "not ours" (False) when the write hit a lock; the drive then stops (before the send this means: no mark, no send).
- A `pending`/`sending` row stamped later than now (the clock was set back) is set to now by the reaper, then ages normally. An open receipt stamped in the future counts its age from the first reaper pass that saw it open.
- A claim that failed with an exception clears the thread's ownership token.
- Load and fairness (all inside one desk process): the in-flight limit is a first-come-first-served counting semaphore (`gate.FairSemaphore`, 32 places); follow-up drives have their own 8 places (`gate.DRIVE_MAX`); a drive that finds no place within 5 s is left to the reaper (only when `start_background()` was called; without a reaper it waits for its place, because nobody else would drive the row. NOTE: this tree's server.py does not call `start_background()` yet - see hook 1 above - so the reaper does not run in the load script). The write gate has two lines: request writes first, drive and reaper writes second (`FairGate.acquire(timeout, low)`). A wait for the gate that runs out is NOT tried again (no new ticket at the tail). All tries of one write share one deadline (`gate.WRITE_DEADLINE_SECONDS` = 10 s); a whole `process` call has one deadline (`gate.REQUEST_DEADLINE_SECONDS` = 15 s) that includes the in-flight wait. The reaper's stuck grace is now send timeout + 4 busy waits (20 s), longer than the longest result write (write deadline 10 s + one SQLite busy wait 5 s). contract.md line 15 and 85 wording on 503 with an open receipt: unchanged (still accepted); the ORDER 202 wording "no open receipts after a 503" is NOT promised for a 503 that comes after the receipt was written (the receipt is decided by the reaper).
- Email: a character that lower-cases to ASCII (the Kelvin sign U+212A gives k; U+0130 gives i plus a mark) is refused: verdict `review`, reason `invalid_email`. Other non-ASCII letters are accepted as before (the key is their lower-case form). Decision: the desk does NOT normalise to NFC (two spellings of one mailbox stay two leads; this can only split a mailbox, never merge two).
- Verdict `review`, reason `bad_field:<field>` also for: name, phone, company: any format character (Unicode category Cf: zero-width space/joiner, byte-order mark, right-to-left override) and the line and paragraph separators (Zl, Zp: U+2028, U+2029). message: Zl, Zp and the direction controls (U+202A to U+202E, U+2066 to U+2069); the zero-width joiners that emoji need stay allowed in a message.
- The AI step's answer must be one of hot, warm, cold (checked in `_label_step`). Anything else is an error of the AI step (`internal:ValueError`, one automatic try); the CRM is not asked and the label stays empty.
- Review item and retry/resolve ids: a number with a leading zero (R0012) or more than 18 characters is 404 `not_found` (an item has exactly one id). Before: 4301+ characters raised a ValueError and answered 500.
- `Desk.process` never raises for non-JSON-native direct input (mixed-type keys, a set, a date, a 4301-digit number): 400 `bad_envelope`, counted in `rejected_envelopes`.
- `Desk.review`, `lead` and `counts` answer through the error shell (500 `internal` or 503 `busy` as bodies) instead of raising; `lead` of an id with a control character or lone surrogate is 404.
- Adapters: the reply is read up to `constants.REPLY_MAX_BYTES` (1 MiB; longer is an error, treated as unclear like any bad reply); a 3xx answer is an error and is never followed (a redirected POST would have become a GET).
