## FAILURES FIRST
### MAJOR 1 (crlf v6): cure 1 is a silent no-op after `git add` or `git commit`, and the text says it works everywhere
- Measured on the real clone (autocrlf=true, 9c53207 + v6, real `.gitattributes` `* text=auto eol=lf`): write CRLF into sonar-project.properties, `git add` (git warns "CRLF will be replaced by LF the next time Git touches it"; `git ls-files --eol` = `i/lf w/crlf`), then each candidate cure; CR bytes left after it:
  `git checkout -- f` 14 | `git checkout -f -- f` 14 | `git restore f` 14 | `git restore --worktree --source=HEAD f` 14 | `git checkout HEAD -- f` 14 | `git update-index --really-refresh` 14 | `git add --renormalize f` 14 | `rm f && git checkout -- f` 0 | the Python one-liner 0.
  Same after `git commit` (14 CR, `i/lf w/crlf`). Without `git add` (file only modified in the work tree) cure 1 works (8 of 8 real-clone runs, below). Cause: git sees the entry as stat-clean and skips the file; the planted-tree test never plants this state (my mutant B11, `git add` after the plant, dies: so the state was reachable, just not pinned or mentioned).
- Why it matters: a Windows editor that saves CRLF, then `git add` or a commit hook, is the ordinary path to this guard failing; the user follows cure 1 (the lead's own "git checkout -- file first"), nothing changes, the guard fails again. The text in CRLF_HINT says "Cure 1, on every system" and docs/tests.md says it "works everywhere".
- Fix (one clause plus one case): hint: "...`git checkout -- <file>` (it does nothing once you ran git add or commit: then use cure 2)"; docs/tests.md the same words; one more case in test_every_cure_in_the_message_works with `_git(tree, "add", ".")` after the plant that asserts cure 2 cures it (and, if the lead wants cure 1 to be honest, that cure 1 leaves the CR). Not measured: whether the hint with the clause still passes the HINT_PHRASES pin ("git checkout -- <file>" stays in it).
