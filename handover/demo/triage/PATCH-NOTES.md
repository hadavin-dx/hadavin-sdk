## What the patch does NOT fix (read first)

- **The DeepSource finding type "missing let/const (implicit var)" is NOT resolved by this patch.** The portal JavaScript still has 504 `var` statements: 422 in `src/lead_desk/portal` (7 files) and 82 in `demo_only/portal_demo.js`. The count is the same before and after the patch (ESLint `no-var`: 504 and 504; `evidence-js-resolve-var-count.txt`, `evidence-js-resolve-eslint-full.txt`).
  - Why they were left alone: they are STYLE, not a fault. Every one of these files runs in strict mode (`'use strict'` once per file, inside its own function wrapper), so a `var` cannot leak into the global scope. No variable is assigned without being declared: ESLint `no-undef`, `no-global-assign` and `no-implicit-globals` report 0 hits in the shipped portal files after the patch. The whole portal is written in the older JavaScript style on purpose (0 uses of `let`, `const` or arrow functions in it). Changing 504 places to `let`/`const` is not a mechanical edit: `let` inside loops gives each round its own copy, and a `let`/`const` name cannot be used before its line (the "temporal dead zone"), so code that works today could behave differently. That needs a decision on the browser level the portal supports and a run of the real-browser (Playwright) tests, which could not run here.
  - Who decides and the next step: the owner decides between (a) keep the older style and mark this rule as accepted for the portal in DeepSource (the rule id has to be read from the DeepSource dashboard, which nobody on this lane could open), or (b) a separate change that converts `var` to `let`/`const` file by file, with the Playwright browser tests run on a machine that has Playwright.
- **The builder never saw the DeepSource report.** The builder worked only from the cluster descriptions. The text of the DeepSource bot comment was saved later (`deepsource-comments-plain.txt`, line 15: "lots of implicit var via missing let/const"); it is a prose summary with no file, line or rule per finding. The per-finding list is only on the DeepSource dashboard; it was not opened by the builder, the reviewer or the resolver. So it is not proven that every DeepSource item of this type is one of the 504 `var` statements, or that DeepSource has no further item.
