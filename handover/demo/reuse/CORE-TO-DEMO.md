## 2. Pair (a) text folding / look-alike detection: core P1a, P1b, P2d-1 vs demo identity keys
Core side (read on origin/core/P1b, newest, alg `fold5`; P1a is the older `fold4`; P2d-1 is a separate branch that carries its own textnorm.py copy plus the redact.py change that uses it, 725 lines vs 1138; P1b is compared because its textnorm.py is the newest and largest, but it is not a superset of every file: redact.py is 1256 lines on P1b and 1753 on P2d-1, and P2d-1 has no _scripts.py):

Functions: `identity_key`, `identity_keys`, `could_be_same_person`, `allow_equal` (EQUAL / VARIANT / LOOKALIKE / DIFFERENT), `scan_holds`, `names_equal`, `has_mixed_script`.
- Its own header says (P1b textnorm.py): fold is for a DENY decision (it over-collides on purpose) and WRONG for an ALLOW decision (:18-20; example "this address equals the verified address"); "Do not use `fold` to display or store text" (:5-6); "Nothing in v1 stores a check name": a package that must keep a person or id stores the RAW text and folds it again with the current `identity_key` (:15-16); the spelling-variant match behind `could_be_same_person` is not transitive, so it is "never a unique index, a dedupe or a group-by: use identity_key equality there" (:59-63; this sentence is about `could_be_same_person`, not about fold in general); off the pinned Unicode version every key starts with a U+E000 tag plus the interpreter's Unicode version (:118-132). Against that, the `identity_key` docstring (:828) calls it "stable and idempotent, so it stays the check name to keep and to index": core's own text is not consistent on whether a key may be stored.
Demo side:
- src/lead_desk/identity.py:39-41 `normalise_email` = strip + lower only (the dedupe key, stored as leads.email_key, schema.sql:39, unique index schema.sql:43). identity.py:78-82 `_lower_keeps_ascii_apart` REFUSES an address where lower-casing turns a non-ASCII character into ASCII (Kelvin sign, dotted capital I) so two mailboxes are not merged. identity.py:58-71 refuses invisible/format characters in non-email fields; identity.py:85-93 `_valid_email` refuses any category C character. crm_hubspot.py:380,400,447 repeat `.strip().lower()` for CRM matching.
- Names: identity.py:129-140 `_collapse` and `diff_fields` only collapse spaces and compare text; no fold.
SAME: both want one stable key per person text and both reject invisible/control characters.
DIFFERS: the demo keys by plain lower-case and rejects (refusal to `review`) only a narrow set at the door: characters whose lower case becomes ASCII (Kelvin sign, dotted capital I; identity.py:78-82) and control or invisible/format characters (identity.py:58-71, 85-93). It does NOT reject Cyrillic or Greek look-alike letters: `_EMAIL_RE` (identity.py:15) accepts them and they keep their own key. Core FOLDS look-alikes together. A Cyrillic-a address is stored as a separate lead in the demo today (it is a valid, different mailbox); with core `identity_key` it would collapse onto the Latin one, i.e. two real mailboxes merged into one lead. That is a behaviour change. What the core header says, both sides (see the bullet above): a dedupe or unique index should use `identity_key` equality, not `could_be_same_person` (:59-63), and `identity_key` is "the check name to keep and to index" (:828); but v1 stores no check name and a package keeps the RAW text and refolds (:15-16), and fold is not for storing text (:5-6). The demo's email_key IS a stored, uniquely indexed key, so putting an `identity_key` there goes against core's v1 rule (:15-16) as well as against my reading that two mailboxes are two people. Conclusion unchanged: folding the demo's stored email key is the wrong direction.

PARTLY for the name field only (a duplicate-warning, "same name?" hint in the review item) because `could_be_same_person` is a DENY-style hint and would only add a warning; but the demo has no place that asks "same person?" today, so adopting adds a feature, not a replacement.
