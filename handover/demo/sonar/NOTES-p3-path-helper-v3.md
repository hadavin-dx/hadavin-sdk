## What changed, per finding
* V-1 (Major) `--config` below a folder that can be entered but not listed (mode 0711). Reproduced as uid 65534 (python `os.setuid` in a child process started as root): v2 refused ("a folder on the path cannot be listed"), v3 reads it (evidence-p3v3-1). Rule: only in `anywhere` mode, when the listing cannot confirm the file (a folder cannot be listed, or the name is not in the listing), the result is the first of `realpath(arg)`, `arg` that exists, which is what base does with an unchecked `open`. Not found by either: "no such file". Inside the allowed folders (not anywhere) a listing refusal stays a refusal. Same fallback fixes `--config <(command)` (`/dev/fd/63`, a process substitution: the listing never shows the pipe's real name; v2 refused it, base worked). Tests: fake refusing listing (runs everywhere), real uid 65534 test (needs root, skipped otherwise; it SKIPPED nowhere in my run, I ran as root), pipe test (Linux).
* V-2 (Minor) message and docs. `confine(..., output=False)` is the default: a missing last name says "no such file". New keyword `output=True` is set at the seven write sites (check_invariants `--json`; load_driver `--log` and `--facts`; catcher `--out` and `--control`; scrub `out.json`). Only they keep the new-name rules and message. Control characters in an EXISTING name: behaviour kept (refused for everyone, deliberate: they reorder or hide printed text), the false claim "an existing file may have any name" is corrected in the helper text and load_tools/README.md ("any name except one with a control character"); a test reads both texts and a real file named `nl\nname`.
* V-3 (Minor, Windows) a NEW name is refused when it ends with a dot, or when the part before the first dot is a device name (`con prn aux nul com1-9 lpt1-9`, any case), on every OS, like core pathguard R6/R7 (read-only from wip/cloud-sonar-probe: `git show ...:src/hadavin_sdk/pathguard.py`; core's list also has CONIN$, CONOUT$, CLOCK$ and superscript digits: not needed here, the new-name table has no `$` and no non-ASCII; core rule "trailing space" is also moot, a space is not in the table). An existing file is unaffected. Tests: 4 shapes x 24 names x 3 cases, the ntpath cross-check, near misses (`console.json`, `com10`, `lpt0.txt`, `a.nul`) stay allowed, end-to-end (`--json nul.json` refused before anything is created).
* V-4 (Minor, macOS) the listing match is: exact name first, else equal after NFC and normcase (`_match`, `_key`). So a name typed NFC finds the file stored NFD. Limits, said in the helper text and the README: the allowed folder itself (the first part, from cwd/repository/temp) is compared as written, so only names BELOW it are matched across forms; case on macOS still must match (normcase is the identity there). If a listing holds both forms the exact one wins (tested: a loose match must not pick the wrong file).
* V-5 (Nit) survivors. New tests isolate: `_inside` called directly with the prefix sibling (`/base/in-evil/x` vs `/base/in`); the path-length check (many short names beyond 4096 characters says "too long"; a path at the limit is refused for another reason); a file in the middle of the path ("is not a folder", with and without `anywhere`); the normcase of the match (the test patches `os.path.normcase` to lower-case as ntpath does, and back to identity). Mutants M01, M03, M05, M07 of the reviewer are now killed (evidence-p3v3-2), 15 mutants in all, all killed. The helper grew by about 45 lines (213 in all) mostly comments and the match function.
* Reviewer notes P-1..P-6 concern the probe, not this patch; not touched.
