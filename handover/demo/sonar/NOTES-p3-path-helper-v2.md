## Which sanitizer shape, and why (from the 12 flows, flows-s8707-s8706.json)
What the flows show: each flow is source `a = ap.parse_args()` (argparse, worded "a user can craft an HTTP request") then a store into a field of the namespace (`a.model_log`, `a.book`, `a.config`...), a read of that field, a call, and the sink at `read_text`/`open`/`write_text`/`sqlite3.connect` INSIDE the callee ("a malicious value can be injected into the caller"). Calls such as `Path(x)` or `.resolve()` are listed as "can propagate malicious content to its return value" (scrub 178, 179, n8n_api 192). So the engine is call-summary based: for each function it records whether the parameter reaches the return value or a sink. That predicts: (1) a helper that VALIDATES but returns something derived from its parameter (realpath, resolve, Path(...)) is still a propagator, so a validate-and-return-the-same-text helper (the first P3) is the form least likely to be accepted; (2) a function whose return value is built only from things the file system reported (a directory listing entry) has no parameter-to-return dependency, so its summary is "clean" and a helper is as good as inline; (3) a guard that only raises (commonpath + raise) is accepted only if the engine models it as a validator, which nothing in the flows shows. So v2 uses shape (2): the helper looks the file up by name in `os.scandir` listings from an allowed folder and returns the entry's own path; a not-yet-existing output file's name is rebuilt from a character table (each character looked up in a dict, the dict's value is used). I kept the helper rather than inlining because by (2) the summary decides, not the place; probe-ab tests helper against inline at 10 of the 12 sites so this choice can be corrected after one push. Reasoning is inference, not documentation: docs.sonarsource.com is not reachable here.
Risk I know of: the allowed-folder list reads os.getcwd(), a temp folder and the environment variable LEAD_DESK_PATH_ROOTS; if the engine treats environment reads as a taint source for the root, the listing text is tainted again. Probe A/B in probe-ab.patch do not isolate that; if the helper sites stay open after the probe, that is the next thing to try (drop the environment variable).

## Review findings, one by one
* MAJOR-1 (documented real run broken). Policy changed: the confinement applies to paths from COMMAND LINES only. `scripts/run_real_check.py --config` is checked and resolved but allowed in any folder (`confine(..., anywhere=True)`, one call in `_run` before anything else; no control characters, links followed, file must exist). The paths INSIDE the config (DESK_DB_PATH, run folder, REAL_RESULT_FILE, key/password files) are not confined at all: they are the operator's own file and `read_book` no longer confines (the command line of check_invariants confines in `main`, up front, before anything is read). So no late refusal is possible and nothing is refused after the y/N question. Tests: config outside cwd/repository/temp reaches the question; the whole run against the local fakes with config and book outside the folders runs to exit 0 (these fail on the old P3: evidence-p3v2-3); docs/real-services.md (new last paragraph "Where the files may be") and docs/settings.md (LEAD_DESK_PATH_ROOTS bullet) say it. Honest note: `anywhere=True` fences nothing; for --config the helper only guarantees a checked, resolved, existing path.
* MAJOR-2 (f-string mutant): test `test_the_book_reader_uses_the_helper_for_a_name_with_a_question_mark` (book `x?mode=rw.db`, read, write on its connection fails, `%3F` in the URI). Mutant `f"file:{path}?mode=ro"` now FAILS (evidence-p3v2-4).
* MAJOR-3 (siblings). Confined: `load_tools/catcher.py --out/--control` (refused with exit 2, nothing created; test). Decision, not confined: `scripts/run_live_check.py --key-file/--ledger` (and `n8n_api` `N8N_API_KEY_FILE`): their documented place is OUTSIDE the repository (docs/settings.md: "keep it outside the repository"), the operator names them on purpose, Sonar did not flag them, and the real-run patch also edits run_live_check.py (conflict risk); confining them to cwd/repo/temp would break the documented use and `anywhere` mode would add no fence. Config-derived (REAL_RESULT_FILE, *_PASSWORD_FILE, DESK_DB_PATH, run folder, crash flag) and demo_only servers: same reason / out of Sonar scope. README states this.
* MINOR-5: the three load tools import the helper with a fallback that adds the repository folder to sys.path (try/except ModuleNotFoundError, no noqa comment). Test starts `python load_tools/<tool>.py --help` with PYTHONPATH removed: fails on old P3, passes now.
* Nits: link loop is refused ("a link on the path does not resolve (a loop)", a link left after resolution) and the docstring says what is true; labels are the flag names (`--requests`, `--catcher`, `--model-log`, `--crm`, `--facts`, `--drain`, `--json`); `load_driver.main` prints `ERROR: ...` and returns 2 instead of a traceback; `_facts_say_live` is no longer special (main confines every path first, so a refused facts path stops with an input error); README and helper docstring say plainly: this fences wrong arguments, not an agent that controls the shell (it can start the tool elsewhere or set LEAD_DESK_PATH_ROOTS), and not a swap between check and open. Broad roots (temp folder, repository, cwd) are kept and stated.
* Also changed: a NEW output file may only use letters, digits, `.`, `_`, `-` in its name (an existing file may have any name). New behaviour for people: an n8n export in Downloads must be copied into the repository or its folder listed in LEAD_DESK_PATH_ROOTS (README, helper message names the variable).
