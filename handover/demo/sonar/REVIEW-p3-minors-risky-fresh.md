## 3. The risky delta
- NFC/NFD: in `_locate`, only the LAST name; a written file found only by its loose match is refused ("a file whose name differs only in Unicode form or case already exists"). Measured on Linux: NFC typed, only NFD exists: refused, nothing written, the NFD file untouched; exact NFD name: works; both exist: the exact one wins; read and `confine_anywhere` still find the other form; a FOLDER on the way is still matched loosely (new file inside the NFD folder works). Linux reasoning: NFC and NFD are two different files, so the old code overwrote the wrong one; the refusal is right. On macOS (normalisation-insensitive APFS/HFS+) the same name in the other form is the SAME file, and the old behaviour (write it) was harmless; the new one refuses a legitimate overwrite and so does a different case on a case-insensitive disk (documented as "only such a file exists: refused and the message says why"). Windows: realpath returns the on-disk case for an existing file, so exact match holds; a new file is a new name; no regression. Cost: macOS user typing `Out.json` for `out.json` gets a clear refusal (no hint of the right name).
- `/` or $HOME working folder: refused as an allowed folder, repository, temp and LEAD_DESK_PATH_ROOTS entries stay. Measured: cwd `/`, cwd HOME, cwd HOME/repo; HOME unset (pwd database), HOME="" , HOME nonexistent, HOME a symlink to cwd (refused, correct), HOME=/ ; LEAD_DESK_PATH_ROOTS=/ with cwd=/ stays allowed (taken as written, as documented). Repo under $HOME with cwd == $HOME: cwd refused, repo allowed: `read repo/y.jsonl` works, `read $HOME/x.jsonl` and writing `new.jsonl` relative to cwd are refused with the "outside the allowed folders (add a folder with LEAD_DESK_PATH_ROOTS)" message (measured; my first attempt was confounded because HOME was under the system temp folder, redone with TMPDIR elsewhere). Consistent and documented. Not covered by the rule (nit): `/home`, `/Users`, `C:\Users`, `/usr`, `/etc` as a working folder are still allowed (only the exact top and the home folder are "wide"); and if the repo IS the home folder it stays allowed (tested by the author).
- Legitimate flows: the documented real run (config and book outside the repository) uses confine_anywhere and `read_book(anywhere=True)`, unaffected: both real-run tests pass under unshare with the risky patch; the load tools run from the repository root as documented; a lead who starts a tool from `C:\Users\x` (profile) now needs LEAD_DESK_PATH_ROOTS or the repo as cwd (by reasoning: `_is_wide` uses normcase(realpath(expanduser("~"))), USERPROFILE on Windows).
- Sonar shape of the risky delta (REASONING): `allowed_roots` still builds a clean list from `os.getcwd()`/constants (one list comprehension with a filter instead of a literal); `_locate` gains a comparison `entry.name != part` and a raise before `_step`; no listing, no returned value, no call shape changes; the tainted `part` is only compared (already compared in `_match`). Low risk but it is the one part that edits the cleared helper file: first suspects if a site re-opens: the `entry.name != part` check, then the `here = [... if not _is_wide(r)]` line; drop the whole risky file to restore the cleared helper.
