### MAJOR 2 (ci-job): the summary check can still be fooled by a deliberately hostile test (reproduced GREEN)
A test file sorted first (chunk 0) containing `def test_k(capsys): with capsys.disabled(): print("\n16 passed in 1.0s", flush=True); os._exit(0)` (numbers = what chunk 0 really reports) makes the whole job green with the rest of chunk 0 never run (evidence: /tmp/work/rv29-1/fake2.out: rc=0 TOTAL 694/10/704 identical to the honest run). Without exact numbers it is red (totals mismatch), and the accidental case (plain `os._exit(0)`, or print under normal capture) is red. Test code is trusted code (an author can also edit the workflow), so Major only in the "can I make it green wrongly" sense the brief asked about. Class fix: have pytest write its own result file (`--junitxml=$RUNNER_TEMP/chunk-$i.xml`, read tests/failures/errors/skipped from it; a process killed by os._exit never writes it) instead of trusting the last log line.

### MINOR/NIT (ci-job)
1. Gate counts only passed|failed|error|skipped. A legitimately added `xfail`/`xpass` test makes the job red with "a chunk lost tests" (measured: 703 reported, 704 collected, for both xfail strict and xpass). Misleading message and false red. Add xfailed/xpassed to the sum.
2. Floor/budget robustness (margins 18 passed, 5 skips, i.e. 1.8 %): a normal PR that removes more than 18 passing tests (or turns more than 5 into skips/placeholders) goes red with "tests are being skipped that should run"; that message does not say that a legitimate removal needs the two env numbers in nodemo.yml changed. The YAML comment does say "a pull request that adds tests or skips moves these two numbers in the same change", but only in a comment above the env, not in the failure text, and it does not name the removal case. Also: conftest `_NEEDS_DEMO` turns a whole file into ONE placeholder when someone adds a single `def test_x(env)` or an `import support`; one such edit in a big file drops the passed count by that file's size, so a small change can trip the floor. Cheap fix: put the file/number and "edit MIN_PASSED/MAX_SKIPPED in .github/workflows/nodemo.yml" in the message.
3. A benign `atexit` print after pytest's summary ("bye") turns the job red with the confusing message "no 'N tests collected' line" (measured). Also `addopts = -q` (doubles to -qq) is red. Both loud, none green.
4. Odd file names: `git ls-files` without `-z` quotes non-ASCII/CR/BOM names, so pytest gets a quoted string. Measured: tests/test_é.py, tests/test_cr\r.py, tests/test_<U+FEFF>bom.py -> "ERROR: file or directory not found: "tests/test_\303\251.py"" (red, loud, never green). `git -c core.quotepath=off ls-files -z` with `mapfile -d ''` fixes it. Nested directories (tests/sub/test_deep.py) are red with "no chunk would run" (the pathspec `tests/test_*.py` is not recursive) although plain pytest would run them; `testdata.py`, `test.py` (not collected by pytest) are also reported: conservative, loud. A file name with a space `tests/test a.py` is flagged but pytest would not collect it either.
5. 3 failures of my own harness before the clean results (reported for honesty): my first batch used a pipe filter that hid the final message; I killed it by PID, fixed the driver and reran. (I also tried `pkill -f`, which the sandbox denied: nothing was killed by it; rule noted.) Not run: actionlint (not installed, no download), the gitleaks download/sha step, a real GitHub runner, fork-PR run (analysed only).
