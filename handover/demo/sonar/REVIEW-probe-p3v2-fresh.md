## FAILURES FIRST

### P-1 MAJOR (probe design) the helper form A mixes two mechanisms in ONE return value, so a "still open" A result cannot be read
`tools/pathconfine.confine` returns either the listing's own path (existing file) or `os.path.join(current, _new_name(part))` (file not yet there). A summary-based engine takes the union of both returns: if the engine judges the table branch (`"".join(_NAME_CHARS[c] for c in name)`: a dict READ keyed by tainted text; many engines propagate taint through a subscript key) as tainted, the READ sites 63/597/178 stay open too, although their value came from a listing. The note's reading rule ("if 63/597/178 vanish and 179/366/377 stay, only the output step is not accepted") only works if the engine separates the branches, which a function summary does not. Also the roots come from `os.environ` (LEAD_DESK_PATH_ROOTS) and become the START of the listing walk: if the engine counts environment reads as a source, A is tainted again while B (roots only in a condition) is not: A and B differ in this too. The note names this risk but the probe does not isolate it.
Free fix inside this same PR (each pair differs in ONE thing, so a result is readable):
* check_invariants 63: new `confine_existing(path)` (no new-name branch; a missing file is an InputError). 597: the current combined helper. -> split vs combined.
* scrub 178 (read): split helper but `roots=[str(REPO_ROOT)]` built from `__file__` (no environment). 63 vs 178 -> environment or not.
* load_driver 366 keeps the dict table; 377 uses a table made by iteration over a constant: `"".join(next(k for k in _ALLOWED if k == c) for c in name)` (the value is an element of the constant, `c` only in a condition). -> dict vs iteration.
No new file is needed; about 25 lines.

### V-1 MAJOR (narrow) v2 `--config` (anywhere mode) is refused when an ancestor folder can be entered but not listed
`confine(..., anywhere=True)` walks from `/` with `os.scandir` at every level. Measured as uid 65534 (`perm.py`): config at `.../perm/a/b/cfg.env` with `perm/a` mode 0711: `open()` works, `confine` raises "--config: a folder on the path cannot be listed". Base code reads it. Typical causes: a home or mount folder with mode 0711/0111, a drop folder, some container volume layouts. The documented real run (config outside the repo) is therefore not always possible. Fix: in `anywhere` mode a listing refusal on an ancestor of the ALREADY resolved real path should not refuse (the resolved path from `os.path.realpath` is the file system's own text); or only walk the part below the first listable folder.

### V-2 MINOR the "new name" refusal message is shown for things that are not new names
`confine` cannot tell "typo, file does not exist" from "new output": a MISSING read file whose name has a space or non-ASCII letter says "the name of a new file may only use letters, digits, '.', '_' and '-'" instead of "no such file". Measured: `read_jsonl("my log.jsonl")` (probe and v2), `--config /dev/fd/63` (process substitution, `bash <(secret-tool ...)`: refused, base works) and `--config` with a typo and a space. The docstring/README say "an existing file may have any name": false for names with a control character or newline (refused for everyone; measured "nl\nname": REF). Say so, or give readers (existing-only) their own message.

### V-3 MINOR Windows only (reasoning, NOT run): v2 allows what core's pathguard refuses
Core pathguard R6/R7 (trailing dot or space, device names CON/NUL/AUX/COM1.. including with an extension) have no equivalent. In v2's table `.` is allowed and no device names are refused: on Windows a NEW `--json nul.txt` / `aux.json` opens the device (output silently vanishes), and `new.` and `new` are the same file (two requested names, one file; on Linux they are distinct). No data leaves the folder, it is silent data loss and a collision. Cheap: refuse a name ending in `.`/space and names whose stem is a device name, on every OS (core does).

### V-4 MINOR macOS (reasoning): non-ASCII existing names
Listing walk matches `e.name` to the typed part by plain equality (normcase is identity on macOS). An existing file typed in the other Unicode form (NFC vs NFD), or a folder typed in other case, is not found: the last part is then treated as a "new name" and refused if non-ASCII, a folder part is "does not exist". The README says case must match; it does not say Unicode form. Windows: normcase lowercases (OK), and a case-sensitive directory with two names equal after lowercasing returns the first entry (still inside the root, so safe but possibly the wrong file).

## Question 1: which shape would Sonar's engine accept? (opinion; docs not reachable; nothing measured)
From flows-s8707-s8706.json: source `a = ap.parse_args()`; each field store ("previously assigned to the field model_log"); every call on the way is "can propagate malicious content" (Path(), `.resolve()` are listed as "propagate ... to its return value" at scrub 178/179 and n8n_api 192); the sink sits INSIDE the callee ("injected into the caller" / "used as argument"). So it is interprocedural and summary-based, field-sensitive, not path-sensitive. My ranking:
1. B (inline realpath + commonpath + raise + open(real)): most likely NOT accepted (about 85 percent): the guard is control flow, `real` is still derived from the parameter by a propagator (`realpath`). Core's `pathguard.inside` has the same property (it returns `Path.resolve()` of the argument; its base for the atomic-writer probe is `path.parent`, derived from the same argument, so even as a guard it checks nothing; core's operator_dir/operator_file check shape only). I expect core's form to behave like B or worse.
2. A (return value built from listing entries): the only shape that gives a summary "return does not depend on the parameter", so it is the best chance, but only if (a) the table branch is clean (P-1: use the constant-iteration form), (b) the environment is not a source (P-1). My honest estimate: 35-50 percent for reads with the split helper, less for the combined one.
3. Not in the probe, better third shape for the cost: a name-only contract, `os.path.basename` (or `werkzeug.utils.secure_filename`) joined to one fixed folder. Engines of this kind model basename/secure_filename/safe_join as sanitizers more often than anything custom. Behaviour cost: files only directly inside a fixed folder, so not free for the owner; as a PROBE it is free (use it on one duplicate site, e.g. scrub 178 reading `os.path.join(FIXED, os.path.basename(src))`, not for merging). werkzeug is not a dependency here (not in requirements-dev.in), so use basename.
Free additions listed in P-1 and P-2 give: split vs combined (63/597), env vs no env (63/178), dict vs iteration table (366/377), inline vs helper on writes (366/377). The sites then double as the third-shape test without new sites. Keep the controls as they are.
If none clears, the note's fallback is right: owner marks the 12 reviewed in the Sonar UI; no suppression comment.
