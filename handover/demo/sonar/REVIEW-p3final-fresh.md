## Failures / risks first
MAJOR-1 (REASONING, not measurable here): `confine_anywhere` starts its walk at `top`, and `top` is DERIVED FROM THE TAINTED ARGUMENT (`_resolve(text)` -> `os.path.splitroot` -> `drive + root`). In the cleared shapes the walk start (`root`) comes from `allowed_roots()` (a loop variable over a clean list), so `os.scandir(current)` yields clean entries. In anywhere mode `os.scandir(top)` takes a tainted string; if the engine propagates arg->return through `scandir`/`DirEntry.path` (it does for `Path(x)`, see flows: "This invocation can propagate malicious content to its return"), every returned path stays tainted and `config.read_text` (load_env, base line 645) stays open, possibly also reported at `_entry`. The probe never had a tainted walk start, so the "same walk as the cleared ones" claim does not hold for the one input that differs. Fix (tested on Linux, adv/top_alt.py): pick the start by EQUALITY from a clean list (`os.sep`, anchors of cwd/repo, `os.listdrives()` on Windows) and refuse other drives/UNC shares: `for a in anchors: if a == top: return a, tail`. This is the equality-allow-list shape (probe #14: no issue). Cost: UNC shares not in the list are refused (the builder's UNC fix would be lost), so make it a second step only if 645 stays open. read_book S8706: only the `anywhere` branch is affected, and only if a tainted value reaches it; all current callers pass clean values, so I expect it to clear.
Strip order if sites stay open: (1) the tainted `top` (above); (2) `_match` as own function: `_entry` now gets the result via a function boundary and a stored `loose = e` instead of the probe's single `next(generator)`; if a read site stays open, put it back as `entries=list(listing); next((e for e in entries if e.name==part),None) or next((e for e in entries if _key(e.name)==_key(part)),None)`; (3) `read_book(anywhere=)` if-between-two-helpers: both branches reassign `path`, so low risk; simplest alternative is callers confine and read_book takes a clean path; (4) `_resolve` split out of `_real_inside` (a deviation the builder did NOT list: probe had the try/realpath inline); (5) optional `roots=` / `_roots`: untainted at every caller, low risk.

MINOR-2 `--config` regressions, all measured: mode-0711 folder -> "a folder on the path cannot be listed" (uid 65534 test); `<(cmd)` -> "no such file"; `/dev/stdin` from a pipe -> "no such file" (from a redirected file it works). `<(...)`, 0711 and /dev/fd/N are documented (docs/real-services.md, load_tools/README.md, docs/settings.md); `/dev/stdin` on a pipe is not named. On macOS (case-insensitive, normcase is identity) a config path typed in a different case than on disk is now "no such file" for ANY folder of the path, where base opened it; README only says this for folders below an allowed root. No documented command is broken: README/docs/env.example only use `--config PATH`; tests only use real files.
MINOR-3 After real-run-fixes-v5 lands, P3's own test `test_run_real_check_reads_a_config_outside_the_allowed_folders` fails (asserts "the config lacks", v5 rewords it); and v5 prints a doubled prefix `refused: --config: --config: no such file` (PathRefused text starts with `--config:`; v5 adds its own). Fix either `what="the config file"` or drop the prefix in v5.
NIT-4 `read_book` puts the raw base name into `what` before the check: `book a<ESC>[31m...: contains a control character` is echoed (terminal escape; the module text says the message "never prints the value"). Pre-existing wording but now contradicts the docs. Also n8n_api import prints only "(PathRefused)" and the raw `a[2]`, so the user never learns about LEAD_DESK_PATH_ROOTS.
NIT-5 UnicodeDecodeError from a non-UTF-8 `--config` prints the first bad byte and its offset ("can't decode byte 0xe9 in position 4"): one byte of an arbitrary file; same as base; v5 fixes it.
NIT-6 NFC-typed NEW name when an NFD file of that name exists writes to the existing NFD file (macOS intent, but on Linux that is a different file). If cwd is `/` or `$HOME` the "allowed folder" is the whole disk (documented as "started in"). AST test only checks that the function calls a helper somewhere, not that it dominates the sink (dominance verified by me by reading); the notes say "a test checks it by AST" (true per site, not a whole-tree sweep; my grep finds no realpath/commonpath outside tools/pathconfine.py and tests).
