## FAILURES FIRST
### MAJOR-1 The patch breaks the documented real run (config outside the repository) and fails late, after real spend
Measured, cwd = repo clone, files in /var/tmp (outside cwd, repo and /tmp):
* `python scripts/run_real_check.py --config /var/tmp/rv8d/run.env` -> `refused: config file: path is outside the allowed folders`, exit 2. docs/real-services.md step 1 says "Copy real-run.env.example to a folder outside the repository"; the argparse help says "(outside the repository)". * Worse, the DESK_DB_PATH from the config is also confined, silently, deep in the run: run_real_check.py L418 `sending_rows()` calls `read_book(db)`; the patch makes that raise InputError for a db outside the roots and the code `except InputError: return 0` (so unknown_allowance is computed from 0 in-flight rows: a wrong number, not an error), and L980 `read_book(db)` fails with "cannot read the desk's book" and EXIT_FAILED AFTER the real HubSpot calls and mails were already made. `--dry-fakes` uses tempfile.mkdtemp, so the tests and the dry self-test cannot see this. `read_book` on /var/tmp/.../desk.db reproduced: `InputError: book: path is outside the allowed folders`.

### NIT-6 Symlink loop is not refused (docstring says it is)
`ln1 -> ln2 -> ln1` inside the folder: confine returns it (ALLOWED), because os.path.realpath(non-strict) returns the looped path without raising on py3.13 (and older). The later open raises OSError (ELOOP). Safe (cannot be opened) but the docstring "a link loop ... cannot be resolved" is wrong and write sites (load_driver run, scrub main) give a traceback. Use `os.path.realpath(text, strict=False)` plus an explicit `os.stat` loop test or just drop the claim.

## Will Sonar's taint engine accept a helper one call away? Honest opinion
docs.sonarsource.com and rules.sonarsource.com: NOT reachable from this shell (curl code 000). `sonarcloud.io/api/rules/show` needs `&organization=hadavin-dx`, then returns name/CWE (S8707: "Agentic workflows should not be vulnerable to path injection attacks", cwe 20 and 22; S8706 connection string injection) but no description text. So I could not read the sanitizer list; everything below is inference from the flows (flows.json):
* The engine is interprocedural and summary based: sinks are reported as "a malicious value can be injected into the caller" at `path.read_text` inside read_jsonl, with the flow going back to `a = ap.parse_args()` (the source, worded "a user can craft an HTTP request"), through attribute `a.model_log` on the argparse namespace. So it does follow one or more calls.
* What the engine models as a sanitizer is a known library call whose return value it treats as clean. A user-written function `confine()` is analysed as code: `os.path.realpath` and `Path(...)` are propagators (taint passes through to the return value), and a guard that only raises (commonpath test) is, as far as I know, not understood as a validator by this engine. So the summary of `confine` is "return value derived from parameter" = still tainted, and the sink `read_text(confined)` would keep being reported. My estimate that the call-through-helper form clears the 11 path issues: 15-25 percent (the notes say 30-40; I think that is generous). For S8706: `Path.as_uri()` and string concatenation are propagators too; 25-35 percent, only if quoting is a modelled sanitizer for that rule; the flow text for L96 shows "concatenated into the string" at the sink, so removing the f-string alone may not be enough.
* Inline does not by itself fix this: the same three lines inline (realpath, commonpath, raise) put the guard where the engine can see it, but whether it models the guard is the same unknown. Do not spend a push on the whole patch to find out.
* Cheapest measurement: push ONE probe commit that changes only check_invariants.read_jsonl (L63) to each candidate form in turn, and read the re-run flows with the same API call (flows are returned; it tells whether the sink moved or vanished). Candidates, in order:
  1. Inline guard right before the sink in the same function: `real = os.path.realpath(path)`; `if os.path.commonpath([os.path.normcase(real), os.path.normcase(root)]) != os.path.normcase(root): raise InputError(...)`; then `open(real, ...)`. (what the notes call the fallback.)
  2. Flow-breaking form that does not rely on a guard model: take the value from a trusted collection instead of the input: `match = next((c for c in trusted_listing if os.path.realpath(c) == real), None)` where trusted_listing is an enumeration of the allowed folder (`os.scandir(root)`/`Path(root).iterdir()`); open `match` (the filesystem's element, never the argument text). Works for readers; for outputs match the parent folder, then `os.path.join(parent_from_listing, os.path.basename(name))` and refuse if basename != name. Costs: more code, directory listing, behaviour only for direct children of roots unless walked.
  3. A name-only contract (`os.path.basename` / `werkzeug.utils.secure_filename`-style, files only inside one fixed folder) is the form such engines model best, but it removes the "any path under cwd" behaviour; owner decision.
* If none clears, the issues are false positives in the sense that the argv is the operator's own input (these are developer CLI tools, rule is for agent-supplied args); the remaining honest options are marking them reviewed in Sonar by the owner (a UI action, not a code suppression comment). Say that to the owner with the numbers rather than add NOSONAR.
